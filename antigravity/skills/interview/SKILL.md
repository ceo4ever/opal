# 요구사항 수집 인터뷰 스킬

사용자에게 효율적으로 질문하여 정확한 요구사항을 수집하고, 의사결정 사항을 체계적으로 기록합니다.

## 인터뷰 원칙

1. **한 번에 3~4개 질문**: AskUserQuestion 도구를 사용하여 관련 질문을 묶어서 전달
2. **선택지 제공**: 가능하면 구체적인 선택지를 제시하여 의사결정 부담을 줄임
3. **맥락 설명**: 각 질문의 배경과 영향 범위를 간략히 설명
4. **누락 감지**: 답변을 받은 후 기존 산출물과 비교하여 누락된 항목 자동 감지
5. **라운드 최소화**: 2~3라운드 이내에 필요한 정보를 모두 수집하는 것이 목표

## 인터뷰 프로세스

### Step 1: 요구사항 초기 분석
```
사용자의 요청을 받으면:
1. 요청 내용에서 명시적 요구사항 추출
2. 기존 산출물(정책서, 설계서 등)이 있으면 Read로 확인
3. 요청과 기존 산출물 사이의 갭/충돌 식별
4. 불명확한 점을 질문으로 구조화
```

### Step 2: 질문 구성
```
AskUserQuestion으로 질문할 때:
- header: 12자 이내의 짧은 레이블 (예: "엔티티 관계", "인증 방식")
- question: 명확한 질문 + 배경 설명
- options: 2~4개 구체적 선택지 (장단점 포함)
- 한 번에 최대 4개 질문
```

### Step 3: 답변 분석 및 추가 질문
```
답변을 받으면:
1. 각 답변이 기존 규칙/산출물과 일관되는지 검증
2. 답변에서 파생되는 추가 결정사항 식별
3. 필요 시 2라운드 질문 구성
4. 충분하면 결과 정리 후 다음 단계로 진행
```

### Step 4: 의사결정 기록
```
인터뷰 결과를 다음 형식으로 정리:

[결정 사항 요약]
1. {질문 주제}: {결정 내용} — {근거/맥락}
2. ...

[영향 범위]
- 영향받는 산출물: {목록}
- 필요한 업데이트: {목록}
```

## 질문 유형별 템플릿

### 엔티티/관계 질문
```
"{A}와 {B}의 관계는 어떻게 되나요?"
선택지:
- 1:1 (A 하나에 B 하나)
- 1:N (A 하나에 B 여러개)
- N:N (다대다 관계)
```

### 정책 결정 질문
```
"{기능}의 범위는 어떻게 할까요?"
선택지:
- A 방식: {설명} — 장점: {}, 단점: {}
- B 방식: {설명} — 장점: {}, 단점: {}
```

### 우선순위 질문
```
"다음 중 우선 포함할 항목은?"
선택지: (multiSelect: true)
- {항목A}: {설명}
- {항목B}: {설명}
```

## 기존 산출물과의 교차 검증

인터뷰 중 프로젝트에 관련 산출물이 있으면 반드시 교차 검증한다:

| 새 요구사항 영역 | 확인할 산출물 |
|-----------------|-------------|
| 엔티티 변경 | 정책서, DB 설계서, API 설계서 |
| 화면 변경 | 와이어프레임, 화면 정의서 |
| 데이터 처리 변경 | 정책서, 배치 설계서 |
| 지표 변경 | 프로젝트 표준 지표 정의, 필드 매핑 |
| 권한 변경 | 정책서 권한 섹션 |

## 인터뷰 주의사항

- 사용자가 간단히 답변하면, 해석한 내용을 요약하여 확인 요청
- 사용자가 새로운 개념을 제시하면, 기존 용어와의 관계를 반드시 질문
- 기술적 제약이 있는 요구사항이면, 제약 사항을 설명하고 대안 제시
- 모든 결정은 산출물에 반영될 때까지 추적
