# 단위 테스트 경량 경로 제안서

> 상태: 제안
> 작성: 알투(PM)
> 작성일: 2026-10-02
> 대상: opd 설계·구현·테스트 단계 구성, PLAN.md 형식(성공 기준·통합 절), 설계 게이트, `op-dev-execute`, 구현 GATE(신규), `test-tool` 기록·잠금·검사, `opal-test-agent`, `opal-evaluator-agent`, `harness/red-first.md`, TEST-SCENARIO 단계 폐지
> 목적: 테스트 시나리오 단계를 없애고, 설계에서 PM이 정한 성공 기준을 구현 워커가 단위 테스트로 통과시키게 하며, 도구 검사와 독립 판정으로 품질을 지킨다. 설계와 시나리오 사이의 문서 동기화를 없애고 호출을 줄이며, 전체 시간 감소는 측정으로 확인한다.

## 1. 결론

opd의 개발 흐름을 **설계 → 설계 GATE → 구현 → 구현 GATE → 테스트 → 테스트 GATE**로 바꾸고, TEST-SCENARIO 단계를 없앤다.

- **설계(PM)**: PM이 PLAN.md 안에 공통·기능별 성공 기준(관찰 가능한 문장 + 핵심 예시값), 설계, 구현 순서, 통합 대상을 쓴다. 기능은 단위 테스트로 증명한다.
- **설계 GATE**: 도구가 형식을 검사하고, `opal-evaluator-agent`가 기준과 설계를 독립 검증한다.
- **구현(구현 워커)**: 구현 순서대로 단위 테스트 작성 → RED → 잠금 → 구현·테스트·재수정 → GREEN. 테스트 수정은 정해진 형식의 기록을 남기고 도구로 잠금을 푼다.
- **구현 GATE(도구 + `opal-test-agent`)**: 구현이 끝난 뒤 1회. 도구 판정을 통과한 경우에만 test-agent가 단언·수정 근거·통합 진입 가능 여부를 추론 판정한다.
- **테스트(`opal-test-agent`)**: 설계에서 정한 통합을 실행·판정한다. 스킵을 거부하고 통합으로 올릴 수 있다.
- **테스트 GATE(PM)**: test-agent의 판정을 검토해 종료를 결정한다. FAIL·미실행은 PASS가 되지 않고, 사용자가 잔여 위험을 승인한 경우에만 조건부 완료가 된다.

도구가 보장하는 것은 **형식**(RED·GREEN이 실제 실행에서 나왔는가, 테스트가 잠겼는가, 단언이 비어 있거나 약화되지 않았는가)이고, **요구 충족**(단언이 기준을 지키는가)은 설계 검증자와 test-agent가 판정한다. 품질 강화 제안서의 분리형(test-agent 작성 + 구현자 구현)과 같은 품질이라는 보장은 아직 없으며 §11 측정으로 확인한다.

품질 강화 제안서의 테스트 계층 정의(§3.1), 통합 주체와 PM 대행 경계(§3.3), 완료 상태(§3.6), 요소별 테스트 환경(§6)은 그대로 쓴다.

## 2. 배경

### 2.1 품질 강화 제안서의 무게

품질 강화 제안서는 검토(Critical/High 0)를 마쳤지만, 모든 단위 테스트를 test-agent가 쓰고 execute-agent가 구현하도록 해 W마다 디스패치·소유권 이관·상태 전이가 늘었다. 함수 하나를 고치는 작업에도 PLAN 열 추가, W 상태 관리, 조기 판정 경로가 따라온다. 간단한 개선·수정에는 과하다.

### 2.2 현재 opd의 공백

- **RED 적용을 PM이 판단한다**(`harness/red-first.md` §1). "구현 후 검증"으로 분류된 W는 테스트 코드 없이 정적 확인으로 끝나기 쉽다. pug 015는 PLAN에서 단위 테스트로 검증한다던 적립액 계산이 TEST-SCENARIO에서 실행 관측으로 바뀌었고 테스트 파일이 없었다. stl 011은 "신규 단위 테스트 없음"을 명시했다(품질 강화 제안서 §2.1).
- **설계와 시나리오가 두 단계·두 문서다.** PLAN의 검증 의도가 TEST-SCENARIO로 옮겨지며 바뀐다(위 pug 015). 두 문서의 W·AC 연결을 따로 맞춰야 한다.
- **잠금이 하나다.** `scenario-lock`은 RED 대상 전부의 실패 관찰 뒤에만 걸리고(`opal/tools/test-tool/lib/scenario.py:411`), 그 뒤 `scenario-red`를 거부한다(`:603`).
- **테스트 불변은 문서 규칙이다**(`red-first.md` §1.5-5). 도구가 확인하지 않는다.
- **단위 결함이 TEST에서 고쳐진다.** TEST FAIL → fix 모드 디스패치 → 재실행(최대 3회)으로 단계를 오간다.

## 3. 프로세스 개요

```
설계 ─ PM: PLAN.md (성공 기준·설계·구현 순서·통합 대상)
  │
설계 GATE ─ 도구(형식) + opal-evaluator-agent(독립 검증)
  │
구현 ─ 구현 워커, 구현 순서대로 (전제 기능 → 병렬)
  │    단위 테스트 → RED(도구) → 잠금 → 구현 ↔ 테스트 → GREEN
  │    테스트 수정: 수정 기록 → 도구 잠금 해제·증거 무효화
  │    W 완료 검사: 도구 결정론 검사(대역 포함) → 확정 위반은 워커가 고침
  │
구현 GATE ─ 구현 종료 후 1회. 도구 판정 → test-agent 추론 판정
  │         실패 → 재구현 요청
  │
테스트 ─ test-agent: 통합 실행·판정 (스킵 거부·상향 가능)
  │       코드 수정 필요 → 구현 워커(fix) → 단위 회귀 + 재판정
  │
테스트 GATE ─ test-agent 판정 + PM 종료 결정
  │
CLOSE
```

| 단계 | 작성·수행 | 판정 | 산출 |
|---|---|---|---|
| 설계 | PM | — | PLAN.md |
| 설계 GATE | — | 도구 + evaluator | 게이트 기록 |
| 구현 | 구현 워커 | — | 테스트·소스, RED·GREEN 기록 |
| 구현 GATE | — | 도구 + test-agent | 판정 기록 |
| 테스트 | test-agent | test-agent | 통합 실행 기록 |
| 테스트 GATE | — | PM(종료 결정) | 통과·재요청 |

TASK·ANALYSIS·CLOSE 단계는 바꾸지 않는다.

## 4. 설계

### 4.1 성공 기준은 PLAN.md 안에 쓴다

별도 문서로 두지 않고 PLAN.md 안의 절로 쓴다.

| | PLAN.md 안의 절 (채택) | 별도 문서 |
|---|---|---|
| 일관성 | 기준·W·테스트 파일이 한 문서에 있어 어긋나지 않음 | W ID·파일 경로를 두 문서에서 맞춰야 함 |
| 설계 GATE | 문서 1개 검증 | 두 문서 간 연결까지 검증 |
| 작성 흐름 | PM이 설계하며 기준을 바로 씀 | 설계 뒤 따로 쓰게 되어 TEST-SCENARIO 단계가 사실상 되살아남 |

도구의 기록 파일(`test-scenario.json`)은 유지한다. 도구가 PLAN의 성공 기준·통합 표를 읽어 만들고, RED·GREEN·판정 증거를 여기에 쌓는다. 사람이 보는 기준의 SSOT는 PLAN.md다. 통합 실행 세부(주체·방식·검증자)는 테스트 단계에서 test-agent가 기록 파일에 쓴다.

### 4.2 PLAN.md 구성

```
## Approach
## Decisions and contracts   ← 공통 기능의 공개 시그니처(함수·클래스·API 이름과 입출력)
## Work items                ← 변경 대상을 소스와 테스트 파일로 구분
## 성공 기준                   (신규)
## 통합                       (신규)
## 테스트 대역                 (신규)
## Risks
## Release and recovery
```

**Work items** (`op-dev-plan/references/plan-guide.md` §4 기준, 바뀌는 칸만)

| 칸 | 변경 |
|---|---|
| 변경 대상 | 소스와 테스트 파일을 구분해 적는다. 단위 테스트로 증명하는 기준이 연결된 W는 테스트 파일이 1개 이상 |
| 구체적 변경 | 다른 W나 테스트가 기대는 공개 시그니처를 적는다(공통 기능은 Decisions and contracts에) |
| 선행 작업 | 전제 기능 W를 적는다(§4.5) |
| 실행 그룹 | 그대로(같은 그룹은 선행 관계 없음 + 변경 파일 겹침 없음) |

**성공 기준**

| ID | AC | W | 기준 | 핵심 예시값 | 종류 | 증명 수단 |
|---|---|---|---|---|---|---|
| SC-1 | AC-2 | W-1 | 등급별 적립액을 계산한다 | (10,000원, GOLD) = 300원 | 신규 | 단위 테스트 |
| SC-2 | AC-4 | W-3 | 같은 주문의 중복 결제를 막는다 | 같은 주문 2회 → 2회째 거부 | 버그 재현 | 단위 테스트 |
| SC-3 | AC-5 | W-4 | 정산 규칙 문서에 새 등급을 반영한다 | GOLD 행 존재 | 신규 | 결정론 검사 + 내용 검토 |

**통합**

| ID | AC | 흐름 | 성공 기준 | 허용 주체 | 환경 |
|---|---|---|---|---|---|
| IF-1 | AC-1 | 가입 → 주문 → 적립 확인 | 적립 내역에 300원 표시 | test-agent (PM 대행 불가) | dev 준비됨 |

통합이 없으면 `통합 아님`과 사유를 적는다.

**테스트 대역**

단위 테스트에서 의존을 mock·fake로 대신하는 것은 설계 결정이다. **기본값은 대역 없음(실제 사용)**이며, 이 표에 적은 의존만 대역으로 대신할 수 있다.

| ID | 의존 대상 | 사용 W | 사유 | 입력 | 기대 결과 | 근거 | 대역 작성 W | 실제 연결 검증 |
|---|---|---|---|---|---|---|---|---|
| TD-1 | `PointCalculator.calc` | W-2, W-3 | 책임 분리 — 계산은 W-1에서 검증, 소비 W는 주문 흐름만 검증 | (10,000, GOLD) | 300 | SC-1 | W-1 | W-2: 주문 → 실제 calc → 적립 반영 / W-3: 결제 금액 → 실제 calc → 적립 예정액 |
| TD-1 | | | | (10,000, 등급 없음) | 예외 `InvalidGrade` | SC-1 | | |
| TD-1 | | | | 등급 ∈ {GOLD, SILVER, BRONZE}, 금액 ≥ 0 (범위 규칙) | SC-1 계산식 | SC-1 | | |
| TD-2 | `PaymentGateway.pay` | W-3 | 외부 연동 — dev 결제 비용 발생 | 정상 카드 | 승인 `{status: OK, …}` | 결제사 API 문서 §3 | W-3 | IF-1 (또는 미충족 잔여 위험) |

- **사유는 필수**이며 목록에서 고른다: `외부 연동` · `느림·비용` · `저장소 규칙상 경계`(예: pug `testing.md`의 persistence 포트 모킹) · `책임 분리`(다른 W에서 검증) · `아직 없음`. 사유 없는 대역은 허용하지 않는다.
- **값은 재사용한다.** 내부 공통 기능의 행은 연결된 성공 기준의 예시값을, 외부 경계의 행은 API 문서 샘플을 쓴다. PM이 새로 쓰는 분량은 작다.
- PM은 계약 데이터만 쓴다. 대역 코드(fake·fixture·stub 헬퍼)는 `대역 작성 W`가 만든다(§5.4).
- 행은 점 사례뿐 아니라 범위 규칙(입력 도메인)도 쓸 수 있다. 근거가 SC인 점 사례는 그 SC의 예시값에도 있어야 한다(없으면 PM이 SC에 예시를 추가해 한 출처를 유지). 외부 API는 문서 샘플만 쓰고 모든 사례를 새로 만들지 않는다.
- **실제 연결 검증**(필수): 대역을 쓰는 소비 W마다 실제 연결 검증을 지정한다. 전체 통합을 늘리는 것이 아니라 핵심 소비자 → 실제 제공자 조합을 한 번 증명하는 것이다.
  - **내부 의존**(이 태스크의 W가 제공): 소비 W 안의 **실제 연결 테스트 1개**만 허용한다. 그 의존을 대역으로 바꾸지 않고 실제 제공자에 연결해 소비 기능의 결과·부작용을 단언한다. IF로 미루지 않는다(W 완료와 TEST 진입이 서로 기다리는 교착을 막기 위해).
  - **외부 경계·`아직 없음`**: 실제 연결이 지금 불가능하므로 통합 IF로 지정하거나, 미충족으로 두고 사용자 잔여 위험 승인 대상으로 적는다.
  - 하나의 실제 연결 테스트나 IF가 여러 TD·소비 W의 경계를 실제로 덮으면 실행 증거 하나를 공유해도 된다. 소비 W·의존별 매핑과 해당 단언은 표에 남긴다.
- **적용 범위**: 이 태스크의 W가 제공하는 의존과 외부 경계에만 적용한다. 시계·난수·logger 같은 테스트 도구와 저장소 공용 테스트 헬퍼는 표에 넣지 않는다.
- `대역 작성 W`가 소비 W와 **다르면** 소비 W의 `선행 작업`에 들어 있어야 한다. 같은 W가 대역을 만들고 쓰는 경우(예: TD-2의 W-3)는 선행 관계를 요구하지 않는다. 외부 경계 대역을 소비 W 안에 둘지 별도 W로 둘지는 PLAN에서 고른다.

### 4.3 성공 기준 작성 규칙

- **기준은 PM이 정한다.** 구현 워커는 기준을 바꾸지 않고, 기준을 통과하는 테스트와 구현을 만든다. 기준이 틀렸으면 설계 변경(`requirement_change`)이다.
- 기준은 관찰 가능한 문장이고, 핵심 예시값(입력 → 기대값) 1개 이상을 둔다. 예시값은 TASK·문서 근거로 정하고, 근거가 없으면 사용자 확인 항목으로 올린다.
- **종류**: `신규` 또는 `버그 재현`. 버그 재현은 원본 코드에서 실패해야 RED로 인정한다(§5.2).
- **증명 수단**은 작업 성격에 따라 정한다.

| 작업 | 증명 수단 |
|---|---|
| 기능(계산·규칙·상태 전이·API 동작) | 단위 테스트 (필수) |
| 문서·설정·구조 | 결정론 검사(형식·스키마·링크) |
| 화면 모양·동작 | 흐름 실행(브라우저) 또는 사람 확인 |
| 실행 규칙 문서(파일럿·하네스·에이전트 규칙) | 결정론 검사 + 내용 검토(독립 평가자) |

### 4.4 통합 정의

- 설계에서 PM이 통합 대상 여부, 흐름, 흐름 성공 기준, 환경 준비 여부를 정한다. 환경은 `test-tool e2e env-check`로 미리 확인한다(계정·데이터·브라우저·사람 조작 필요 여부).
- 통합이 필요한 경우는 품질 강화 제안서 §3.2를 따른다(여러 기능·경계를 잇는 흐름, 단위로 증명할 수 없는 연결).
- 허용 주체(test-agent · PM 대행 · 사용자 · PM+사용자)와 PM 대행 여부는 설계에서 정한다. 대행은 품질 강화 제안서 §3.3 대행 경계(dev 환경, 되돌릴 수 있는 조작) 안에서만 허용하고, 설계 GATE가 확인한다.
- 방식·검증자·실행 세부는 테스트 단계에서 정한다(§6.2).

### 4.5 구현 순서

- 원칙: **전제 기능(공통) 먼저, 그 뒤 병렬.**
- 전제 기능 W는 `선행 작업`으로 연결하고, 전제가 끝나면 후속 W를 실행 그룹 안에서 병렬로 돌린다.
- 같은 파일을 고치는 W는 같은 실행 그룹에 두지 않는다(현행 `plan-guide.md` §4 병렬 판단).

### 4.6 설계 GATE

**도구 (결정론)** — 하나라도 위반이면 FAIL.

- 모든 AC가 성공 기준(SC) 또는 통합(IF)에 연결됐다.
- 성공 기준마다 예시값·종류·증명 수단이 있다.
- 증명 수단이 단위 테스트인 기준의 W 변경 대상에 테스트 파일이 있다.
- 기능 작업으로 분류된 W의 기준에 단위 테스트 증명 수단이 있다(결정론 검사만으로 덮인 기능 거부).
- 실행 규칙 문서를 바꾸는 W의 기준에 내용 검토가 있다.
- 선행 관계에 순환이 없고, 같은 실행 그룹 W의 변경 파일이 겹치지 않는다.
- 통합 표가 있거나 `통합 아님`과 사유가 있다.
- 테스트 대역 행마다 사유(목록 값)·근거·대역 작성 W·실제 연결 검증이 있고, 근거가 SC인 점 사례가 그 SC의 예시값과 일치한다. 대역 작성 W가 소비 W와 다르면 소비 W의 선행 작업에 있고, 선행 관계에 순환이 없다(같은 W는 이 검사에서 제외). 내부 의존 TD의 실제 연결 검증이 IF가 아니라 소비 W의 실제 연결 테스트다.

**`opal-evaluator-agent` (독립 검증)** — 기존 `design-rubric` phase를 확장한다. 지금도 PM 경로 설계 게이트에서 PLAN 설계 4축과 시나리오 3축을 함께 판정하므로(`opal/agents/opal-evaluator-agent/AGENT.md` phase 표, `harness/actor.md` §독립 검증 경계), 시나리오 3축을 성공 기준 축으로 바꾼다.

- 기준이 관찰 가능하고 AC를 충분히 덮는가
- 예시값이 근거와 맞는가
- 기능·비기능 분류와 증명 수단이 맞는가(계산을 결정론 검사로 둔 경우 등)
- 통합 대상이 빠지지 않았는가, `통합 아님` 사유가 타당한가
- 구현 순서(전제 기능 지정)가 타당한가
- 테스트 대역의 사유가 타당한가(예: 돈 계산을 `느림·비용`으로 대신하는 경우를 잡는다), 지정한 실제 연결 검증(실제 연결 테스트 또는 IF)이 소비 기능 진입점에서 실제 제공자를 연결하는 경계를 실제로 덮는가

작성자(PM)와 검증자가 분리된다. evaluator는 판정만 하고 PLAN을 고치지 않는다. 반복 상한은 현행 설계 게이트(3회, `harness/design-gate.md`)를 따른다.

## 5. 구현

### 5.1 구현 루프

구현 워커(`opal-be-agent`·`opal-fe-agent`·`opal-db-agent` 등 PLAN `담당`)가 W를 구현 순서대로 맡는다.

1. **단위 테스트 작성**: 성공 기준과 핵심 예시값으로 테스트를 쓴다. 테스트와 소스의 스타일은 §5.6 코드 작성 순서(주변 스타일 우선, 문제 시 언어 색인 → 교본 절)를 따른다. 예시값은 그대로 쓰고, 테스트 이름·주석에 SC-ID를 단다. 신규 기능은 공개 시그니처대로 스텁을 두고 본문을 미구현 표지(예: Kotlin `TODO()`, Python `raise NotImplementedError`)로 채운다. 버그 재현은 원본 코드를 건드리지 않는다.
2. **RED (도구)**: `test-tool`이 테스트를 실행해 유효한 RED를 기록한다(§5.2). 무효면 1로 돌아간다.
3. **잠금 (도구)**: RED 시점의 테스트 해시로 테스트를 잠근다.
4. **구현 ↔ 테스트**: 구현 → 실행 → 재수정. 상한은 `harness/guards.md` 자동 검증 루핑 제약(unit 3회, build/type 2회)을 따르고, 같은 실패에 누적하며 재개해도 초기화하지 않는다. 상한을 넘으면 결과를 제출하고 PM이 사용자 결정으로 올린다.
5. **리팩터**: GREEN 뒤 중복 제거·이름 정리 후 다시 실행한다. GREEN을 유지하고 테스트는 바꾸지 않는다.
6. **GREEN (도구)**: `test-tool`이 실행해 GREEN을 기록한다. 테스트 해시가 잠금 해시와 다르면(§5.3 해제 없이) 거부한다. 실행 증거에 소스·테스트 해시를 남긴다.
7. **W 완료 검사 (도구)**: GREEN 실행과 같은 실행에서 W 범위의 결정론 검사를 함께 기록한다(같은 테스트를 두 번 돌리지 않는다). 검사 범위는 W의 역할에 따라 다르다(§5.4 단계별 대역 검사). 검사 기록은 W·현재 소스·테스트·TD 계약 리비전에 묶이고, 관련 파일이나 TD가 바뀌면 무효가 되어 다시 검사한다. 이전 통과 기록이 있다는 것만으로 현재 완료를 열지 않는다. 확정 위반은 워커가 내부 루프에서 고친다(상한은 4와 같음). 통과 기록이 있어야 W를 완료로 처리하며, `state-tool`이 확인한다. 경고는 워커 단계에서 막지 않고 기록만 해 구현 GATE ②로 넘긴다 — 워커가 경고를 없애려고 의미 없는 단언을 넣는 식으로 맞추지 않게 하기 위해서다(의미 없는 단언 자체는 정적 검사의 확정 위반).

**필수 엣지 케이스** (ECC `agents/tdd-guide.md` "Edge Cases You MUST Test" 8종 — null, 빈 값, 잘못된 타입, 경계값, 오류 경로, 동시성, 대용량, 특수문자 — 을 기준으로 고름): null·빈 값, 잘못된 입력, 경계값(최소·최대·0·음수), 오류 경로(외부 연동·저장 실패), 권한 없음, 동시 호출·특수문자·대용량(해당 시). 기준과 무관한 항목은 생략할 수 있다.

### 5.2 유효한 RED

| 종류 | 실행 기준 | 유효한 RED |
|---|---|---|
| 신규 | 공개 시그니처 스텁(본문은 미구현 표지) | 해당 테스트의 단언 실패 또는 등록된 미구현 표지 실패 |
| 버그 재현 | 원본 코드 그대로 | 원본 코드에서 해당 테스트의 단언 실패 |

- 버그 재현 RED는 도구가 그 W의 변경 대상 소스 파일이 아직 수정되지 않았는지(W 시작 시점 해시와 같은지) 확인한 뒤에만 기록한다. 같은 태스크의 앞선 W가 바꾼 다른 파일은 범위에 넣지 않는다. 재현되지 않으면 원인 분석으로 돌아간다. 기존 본문을 `TODO()`로 바꿔 만든 실패는 버그 재현 증거가 아니다.
- 컴파일·import·환경 오류, 테스트 수집 실패는 무효다.
- 미구현 표지 종류는 요소별 테스트 환경(`test-tools.yaml`)에 등록한다(품질 강화 제안서 §6.1).

### 5.3 테스트 수정 — 기록을 남기고 도구로 잠금 해제

구현 중 테스트를 고쳐야 하면, 워커는 정해진 형식의 수정 기록을 남기고 `test-tool`로 잠금 해제를 요청한다.

| 항목 | 내용 |
|---|---|
| 수정 유형 | 목록에서 선택: `픽스처 오류` · `테스트 코드 결함`(잘못된 호출·설정) · `환경·러너 차이` |
| 연결 기준 | 영향받는 SC-ID |
| 실패 근거 | 수정 전 실패 출력(명령, 종료 코드, 핵심 줄) |
| 변경 내용 | 수정 전후 diff(도구가 첨부) |

- **새 테스트 파일 추가는 수정이 아니다.** 잠긴 테스트 파일과 공유 fixture를 건드리지 않고 **새 테스트 파일**을 추가하는 것(예: §5.5 반례를 정식 테스트로 옮기기)은 잠금 해제 없이 할 수 있다. 기존 잠긴 파일에 테스트를 덧붙이면 해시가 바뀌므로 위 수정 절차(기록·해제·재잠금)를 따른다. 새 파일은 같은 SC-ID에 연결하고, 구현이 이미 있으면 사후 검증으로 표시해 GREEN을 기록하며, 정적 검사·구현 GATE 판정·GATE 입력 해시·전체 회귀에 포함된다.
- "성공 기준이 틀렸다"와 "공개 시그니처를 바꿔야 한다"는 수정 유형이 아니다. 워커는 PM에 올리고, PM이 설계 변경(PLAN 재검토)으로 처리한다. 설계 변경이 승인된 뒤에만 관련 테스트의 잠금이 풀린다.
- 도구는 형식이 맞으면 바로 해제한다(워커가 대기하지 않음). 수정된 테스트는 **수정 테스트**로 표시하고, 그 테스트의 기존 RED·GREEN 증거를 무효화한다.
- 수정 시점이 구현 전(아직 스텁·원본 상태)이면 §5.2 기준으로 RED를 다시 기록하고 다시 잠근다.
- 구현 뒤의 수정이면 RED를 다시 만들지 않는다. 이미 구현된 코드에서는 고친 테스트가 바로 통과할 수 있고, RED를 얻으려고 현재 구현을 되돌리지 않는다. 이 테스트는 **사후 검증**으로 표시하고, 현재 해시로 다시 잠근 뒤 GREEN을 기록한다. 구현 전 사본을 따로 만들어 재실행하는 방식은 빌드 비용이 크고 구현 전후 차이만 증명하므로 쓰지 않는다. 약화 여부는 아래 GATE 판정이 맡는다.
- 수정 테스트(사후 검증 포함)는 구현 GATE에서 반드시 판정한다(§5.5). 해제 자체는 승인이 아니다.

### 5.4 공통 기능 수정

구현 GATE를 구현 종료 후 1회만 하므로, 공통 기능의 결함은 후속 기능의 테스트 실패로 드러나고 구현 워커가 그때 고친다. 이 방식이 안전하려면 다음을 지킨다.

- **동시 수정 금지**: 공통 기능 파일을 고치는 동안 그 파일을 변경 대상으로 가진 다른 병렬 W는 멈춘다. 한 파일에는 한 시점에 한 워커만 쓴다.
- **영향 재실행**: 공통 기능을 고치면 도구가 그 기능을 선행 작업으로 가진 W의 단위 테스트를 다시 실행한다. 이미 GREEN이던 W가 깨지면 그 W를 다시 구현 루프로 돌린다.
- **mock 한계와 테스트 대역**: 공통 기능을 소비 W가 제각각 mock하면 공통 결함과 계약 불일치를 드러내지 못한다(예: 공통 기능은 등급 없음에 예외를 던지는데 소비 W는 0을 가정하고 mock). 그래서 대역은 설계의 테스트 대역 표(§4.2)로만 허용하고 다음을 지킨다.
  - **공유 대역**: `대역 작성 W`(내부 공통 기능은 그 기능을 구현하는 W, 외부 경계는 PLAN이 지정한 W)가 표대로 공유 대역 코드를 만든다. 소비 W는 이 공유 대역만 쓴다.
  - **계약 양방향 검증**: 같은 표의 행을 실제 구현 테스트(내부 공통 기능)와 공유 대역 양쪽에 돌린다. 둘 다 통과하면 **등록된 계약 사례에 한해** 대역과 실제가 일치한다. 호출 순서·상태 변화·예외 전달·부작용은 표에 사례로 넣었거나 실제 연결 테스트로 검증한 경우에만 보장된다. 외부 경계는 실제 쪽을 돌릴 수 없으므로 실제 연결 검증(IF) 또는 미충족 잔여 위험으로 처리한다.
  - **실제 연결 테스트**(내부 의존에 한정): 내부 의존 대역을 쓰는 소비 W는 §4.2에 지정된 실제 연결 테스트 1개를 쓴다. 외부·아직 없음은 IF 또는 미충족으로 아래 단계표를 따른다. 소비 기능 진입점에서 실제 제공자를 연결하고 기준 결과·부작용을 단언하며, 그 경계를 대역으로 바꾸지 않는다. 양방향 검증이 못 잡는 소비 측 오류(인자 변환, 오류 전달, 결과 반영)를 여기서 잡는다.
  - **표 밖 입력**: 공유 대역은 표의 점 사례·범위 규칙 밖의 입력을 받으면 "계약 미선언 입력"으로 명시 실패한다. 소비 W에 필요한 입력이면 워커는 PM에 설계 보완(표·SC 예시 추가)을 요청한다.
  - **단계별 대역 검사**:

    | 시점 | 검사 범위 |
    |---|---|
    | 제공 W(대역 작성 W) 완료 | 자기 코드, 표 사례를 자기 실제 구현(내부일 때)과 공유 대역에 적용한 양방향 검증. 아직 없는 소비 테스트는 요구하지 않음 |
    | 소비 W 완료 | 대역 작성 W가 다른 W면 그 W가 완료됐고 현재 계약 사례가 통과 중. 같은 W면 자기 코드 안에서 공유 대역 생성·현재 표 사례 검증이 먼저 통과(외부 경계 대역은 실제 쪽 검사를 하지 않고 미검증으로 남긴다. 실제 외부 호출은 IF에서만 하거나 사용자 승인 잔여 위험으로 둔다). 자기 테스트가 지정 공유 대역만 사용. 내부 의존은 실제 연결 테스트 현재 PASS. 외부·아직 없음은 IF 예정 또는 미충족으로 표시(W 완료를 막지 않음) |
    | 구현 GATE | 모든 현재 소비 W의 대역 검사 + 내부 의존 실제 연결 테스트 현재 PASS + 외부·아직 없음 TD마다 유효한 IF 계획 **또는** 추적 가능한 미충족 기록(대상 TD·소비 W·기준·사유·잔여 위험·후속 검증 계획). 미충족 기록은 실제 검증 PASS가 아니다 |
    | 테스트 GATE·CLOSE | IF로 지정한 TD는 현재 IF PASS. 미충족 TD는 현재 대상·리비전에 대한 사용자 잔여 위험 승인이 있어야 조건부 완료. 거부·미승인이면 CLOSE 불가 |

    외부·`아직 없음`의 실제 쪽 검사를 성공으로 간주하지 않는다.
  - **공통 기능의 조기 결정론 확인**: 공통 기능 W도 §5.1 7(W 완료 검사)을 거치므로, 후속 W가 기대기 전에 형식·약화·테스트 실패·양방향 검증이 확인된다. 별도 조기 GATE(test-agent 호출)는 두지 않는다. 공통 기능의 의미 오류는 구현 GATE ②에서 잡고, 그 재작업 비용은 §11 결함 주입 측정으로 판단한다.
- 공통 기능의 공개 시그니처가 바뀌면 설계 변경이다(PLAN 재검토, 재진입 상한 2회).

### 5.5 구현 GATE

구현이 모두 끝난 뒤 1회 판정한다.

**진입 조건과 안정 경계**

- 모든 구현·fix 워커가 결과를 제출하고 멈췄을 때만 GATE에 들어간다. 도구가 진행 중인 writer가 없음을 확인한다.
- GATE 입력(소스·테스트·실행에 쓰이는 설정)은 진입 시점의 작업 트리 해시 하나로 식별한다. 도구가 만드는 로그·영수증·빌드 출력과 반례 임시 경로(②)는 해시에서 제외한다. GATE 동안 쓰기는 금지하고, 재실행 전후와 판정 기록 시점에 해시가 같아야 결과를 채택한다.
- GATE 뒤 코드·테스트가 바뀌면(테스트 단계의 fix 포함) 그 GATE의 증거와 판정은 무효이며, 바뀐 상태로 다시 판정한다.
- 구현 중 실행(RED·진행 GREEN)도 실행 전후 해시가 다르면(다른 워커가 실행 중 파일을 바꿈) 그 결과를 채택하지 않고 다시 실행한다. 쓰기를 줄 세우거나 사본을 만들지는 않는다.

**① 도구 (결정론)** — 확정 위반은 추론 판정 없이 FAIL, 경고는 ②에서 반드시 판정.

- 단위 테스트 증명 수단인 모든 기준에 유효 RED(사후 검증 테스트는 제외)와 GREEN 기록이 있다.
- **현재 상태 재실행**: 도구가 GATE 시점의 소스·테스트로 단위 테스트 전체를 1회 실행해 모두 GREEN인지 확인한다. 구현 중 기록된 GREEN은 진행 기록이고, GATE 증거는 이 재실행 결과다. 공통 소스가 나중에 바뀌어 낡은 GREEN이 남는 문제를 이 실행으로 막는다.
- 증거는 연결된 성공 기준 행(SC)의 리비전에 묶는다. PLAN의 성공 기준 행이 바뀌면 그 SC에 연결된 RED·GREEN과 판정을 무효화하고 다시 판정한다.
- 수정 테스트마다 수정 기록이 있고, 유형이 목록에 있고, SC-ID가 연결돼 있다.
- SC-ID에 연결된 테스트가 삭제되지 않았고, skip·only가 추가되지 않았다(확정).
- **경고**(보수적 필터 — 의미 동치를 판별하지 못함): 핵심 예시값 문자열이 단언에 없음, 수정 전보다 단언 수 감소, 약화 패턴. 경고는 자동 FAIL이 아니라 ②에서 test-agent가 근거를 남기고 판정한다. 예: `assertEquals` 하나를 같은 값을 보는 `assertTrue` 여러 개로 나눈 타당한 변경은 근거와 함께 통과시킬 수 있다. 판정 없이 넘어가지 못한다.
- 약화 패턴 목록: 예: `==`가 `>`나 `!= null`로, `assertEquals`가 `assertTrue`로, `toBe`가 `toBeTruthy`로 바뀜, 예외 기대 제거. 언어별 패턴은 `test-tools.yaml` 요소 선언에 등록한다.
- 테스트 정적 검사(단언 없음, `assertTrue(true)`, 예외 삼킴 금지)와 SC-ID 연결 검사를 통과한다.
- 결정론 검사 증명 수단인 기준의 도구 통과 기록이 있다.
- 결정론 검사는 W 완료 검사(§5.1 7)에서 이미 통과했더라도 GATE에서 전부 다시 실행한다. 정적 검사는 짧을 것으로 예상해 재사용 이득이 작고(언어별 비용은 측정), 실행 검사는 그 뒤의 변경 때문에 앞선 결과를 믿을 수 없다.
- **테스트 대역 검사**:
  - 대역 표에 없는 의존을 mock한 경우: 확정 위반. spy는 실제 호출을 유지할 수 있으므로, 대상 호출을 대체(stub)하는지 판정할 수 있는 경우만 확정 위반이고 애매하면 경고. 언어별 패턴 예: Kotlin `mockk<…>()`·`@MockK`·`spyk`, TS `jest.mock`·`vi.mock`·`vi.spyOn`, Python `patch(…)`·`MagicMock(spec=…)`. 패턴은 `test-tools.yaml` 요소 선언에 등록한다.
  - 표에 있는 의존을 공유 대역이 아닌 즉석 mock으로 대신한 경우: 확정 위반.
  - 소비 W 테스트가 공유 대역을 사용하는지, 공유 대역이 표의 모든 행에서 같은 결과를 내는지(양방향 검증, 외부 경계는 대역 쪽만), §5.4 단계별 대역 검사의 구현 GATE 행(내부 실제 연결 PASS, 외부는 IF 계획 또는 미충족 기록): 통과 조건.
  - 테스트 코드 안의 가짜 구현(예: `class FakeCalculator : PointCalculator`), wrapper·alias·동적 생성처럼 문법만으로 의존 대상을 확정할 수 없는 대체: 경고 → ②에서 판정.
  - **실행 커버리지(보조 진단)**: 연결 보장이 아니다. 지원되는 스택에서만 소비 테스트별 커버리지로 실제 제공자 코드가 실행됐는지 참고 증거로 남긴다. 전체 누적 파일 커버리지로 W별 기여를 판단하지 않는다. 지원되지 않으면 실제 연결 테스트 경로로만 판정하고, 커버리지 플러그인 자동 설치나 빌드 설정 변경은 하지 않는다.

**② `opal-test-agent` (추론)** — 구현자와 다른 디스패치. 정상 경로에서는 같은 디스패치가 이 판정을 기록한 뒤 이어서 테스트 단계(§6)를 수행한다. 판정이 FAIL이면 통합으로 넘어가지 않고 결과를 반환한다.

판정 순서 — **기준 먼저, 테스트 나중, 의심 부분만 반례 실행**:

1. **기준 먼저**: 구현자의 테스트를 보기 전에 PLAN의 성공 기준·예시값과 언어 색인의 엣지 케이스로 SC마다 "있어야 할 경계값·오류 경로" 목록을 짧게 만들어 기록한다. 구현자의 테스트를 먼저 보고 따라가는 앵커링을 막는다.
2. **테스트 대조**: 그 목록과 구현자의 테스트를 대조하고, 아래 판정 항목을 본다.
3. **의심 부분만 반례 실행**: 아래 대상에만 테스트 밖의 추가 입력(반례)을 실행해 증거로 남긴다. 문장으로 "충분하다"고 판정하는 것보다 강한 증거다.
   - 대상: ① 경고가 뜬 테스트, 사후 검증 테스트, 공통 기능(선행 작업으로 지정된 W)의 테스트, 그리고 1단계 목록 중 테스트에 없는 항목. 그 밖의 기준에는 반례를 의무로 두지 않는다.
   - 실행: 모아서 한 번에 실행한다(빌드 1회).
   - 근거: 반례마다 성공 기준·예시값 중 무엇에서 나왔는지 적는다. 근거 없는 반례는 실행하지 않는다.
   - 예산: SC당 3개 이하, 태스크당 총량 상한(초기값은 구현 태스크 PLAN에서 정함). 대상이 예산을 넘으면 경고·사후 검증 → 공통 기능 → 목록 누락 순으로 고르고, 실행하지 못한 대상은 "반례 미검증"으로 PM에 보고한다. 예산 초과를 PASS로 처리하지 않는다.
   - 위치와 실행: 도구가 지정한 반례 임시 경로에 둔다. 이 경로는 정식 테스트 탐색(전체 단위 실행·최종 회귀)에서 제외하고, 도구가 반례만 명시 실행한다. GATE 입력 해시에서도 제외하며 커밋하지 않는다. 프로덕션 소스·기존 테스트·빌드 설정은 고치지 않는다.
   - 기록: 반례 내용 해시, SC 리비전, 명령, 출력을 반례 기록에 남긴다. 반례나 SC가 바뀌면 그 기록은 재판정에 재사용하지 않는다.
   - 결과: 반례가 준비·수집까지 성공한 뒤 **성공 기준의 단언이 실패**한 경우만 그 SC를 FAIL로 판정하고, 반례와 실패 출력을 구현 워커에게 넘긴다. import·컴파일·수집 오류나 환경 오류는 반례 작성·도구 문제이므로 "검증 불가"로 따로 기록하고 test-agent가 반례를 1회 고쳐 다시 실행한다. 그래도 실패하면 PM 경로로 보낸다. 검증 불가는 SC PASS 증거로도 쓰지 않는다. 구현 워커는 결함을 고치고 반례를 정식 테스트로 추가한다(§5.3 테스트 추가). 반례 자체가 기준을 잘못 읽은 것이라는 반론은 PM이 성공 기준에 비춰 판정한다.

판정 항목:

- 단언이 성공 기준과 예시값을 실제로 검증하는가(느슨한 단언 포함)
- 필수 엣지 케이스가 기준에 비춰 빠지지 않았는가
- 수정 테스트의 근거가 타당하고, 원래 기준과 같거나 더 엄격한가(사후 검증 테스트는 RED가 없으므로 반드시 판정)
- 내용 검토 증명 수단인 기준(실행 규칙 문서)을 판정한다
- 통합 테스트에 들어갈 수 있는가(빌드·실행·연결)
- 스타일 출처 기록(§5.6)이 있고, 주변 스타일과 어긋난 부분에 규칙 문서·교본 근거가 있는가
- AI 회귀 패턴(§5.6 test-agent 판정용 `ai-regression-testing`)에 해당하는 누락이 없는가
- 외부 경계 대역(실제 쪽 양방향 검증이 불가능한 행)의 계약이 근거 문서와 맞는가, 테스트 대역 경고(가짜 구현·wrapper)가 타당한가
- 실제 연결 테스트가 소비 기능 진입점에서 실제 제공자를 연결하고 기준 결과·부작용을 단언하는가, 그 경계를 대역으로 바꾸지 않았는가

- 반례 실행 결과(실행한 경우)

판정이 FAIL이면 PM이 해당 W의 구현 워커에 재구현을 요청한다. 재구현으로 바뀐 테스트·소스의 증거와 판정은 무효화하고, 그 범위를 ①·②로 다시 판정한다. 상한은 3회(guards.md L3a)이며 넘으면 사용자에게 올린다.

### 5.6 코드 스타일과 언어별 교본

**코드 작성 순서 — 주변 스타일 먼저, 문제가 있을 때만 교본**

구현 워커와 test-agent는 코드·테스트를 쓸 때 아래 순서를 따른다.

1. **주변 관찰**: 같은 패키지·모듈의 소스와 같은 종류의 기존 테스트를 읽는다(권장 상한: 소스 2~3개, 테스트 1~2개. 같은 디스패치에서 이미 본 파일은 다시 읽지 않는다). 이름 짓기, 구조, 오류 처리, 의존성 주입, 테스트 프레임워크·스펙 형식, mock 사용법을 본다.
2. **대조 (항상)**: 적용하기 전에 저장소 규칙 문서와 언어 색인의 안티패턴 요약으로 주변 스타일을 대조한다. 이 둘은 문제가 있을 때만 읽는 교본 원문과 달리 매번 확인한다.
3. **적용 또는 문제 판정**: 문제가 없으면 주변 스타일 그대로 쓴다. 아래 중 하나면 "문제 있음"이다. 판정 기준은 주관이 아니라 문서와 목록이다.
   - 저장소 규칙 문서와 어긋난다(예: pug `backend/docs/claude/rules/*.md`). 규칙 문서 경로는 요소 선언(`test-tools.yaml`)의 `conventions`가 가리킨다.
   - 언어 색인의 안티패턴 목록에 해당한다.
   - 버그 위험이 있다(테스트의 sleep 대기, 테스트 간 공유 상태, 예외 삼킴).
   - 참고할 주변 코드가 없다(새 모듈, 첫 테스트).
4. **교본 참고**: 문제가 있을 때만 언어 색인에서 해당 절을 찾아 그 줄 범위만 읽고 적용한다. 적용 범위는 이번 변경 파일 안이다. 주변 기존 코드는 고치지 않고 결과에 "개선 후보"로 보고한다.
5. **출처 기록**: 결과에 적용한 스타일의 출처(주변 파일 경로, 규칙 문서, 교본 절)를 적는다. 구현 GATE에서 test-agent가 확인한다.

**언어별 교본과 색인 — 평소에는 색인만 읽는다**

교본 원문은 길다(예: ECC `kotlin-testing` 825줄, `python-testing` 817줄). 매번 읽지 않도록 스킬이 언어별 색인을 관리한다.

```
op-dev-execute/references/guides/
  INDEX.md                  언어·프레임워크 연결표 → 색인 경로, 사용법 (1쪽)
  SOURCES.md                원문 출처·커밋·라이선스·판정·내용 해시
  licenses/                 라이선스 고지
  kotlin/INDEX.md           색인: 교본별 목차·줄 범위·언제 읽나·읽지 않음·안티패턴 요약
  kotlin/<교본>/GUIDE.md    원문 (원본 SKILL.md를 이름만 바꿈)
  java/ · typescript/ · python/ · sql/ …   같은 구성
  common/ …                 언어 무관
opal-test-agent/references/guides/
  INDEX.md                  판정용 교본 색인 (AI 회귀 패턴, 통합·E2E)
  SOURCES.md · licenses/ · <교본>/GUIDE.md
```

언어 색인 예시(`guides/kotlin/INDEX.md`):

```
# Kotlin 교본 색인
사용법: 평소에는 이 색인만 읽는다. 2단계(대조)는 아래 안티패턴 요약으로 매번 한다.
        4단계(교본 참고)에서만 표의 줄 범위를 Read(offset/limit)로 읽는다. "읽지 않음" 절은 읽지 않는다.
우선순위: 저장소 규칙 > 주변 코드 > 이 교본

| 교본 | 절 | 줄 | 언제 읽나 |
|---|---|---|---|
| kotlin-testing | Kotest 스펙 스타일 | 31-120 | 첫 테스트, 스펙 형식이 섞여 있을 때 |
| kotlin-testing | MockK | … | mock 방식이 규칙과 다를 때 |
| kotlin-testing | 코루틴 테스트 | … | runBlocking·sleep으로 기다릴 때 |
| kotlin-testing | Kover 커버리지 | … | 읽지 않음 (OPAL 소유) |
| kotlin-patterns | … | … | … |

안티패턴 요약 (3단계 판정 기준)
- 테스트에서 Thread.sleep·delay로 대기 → runTest·가상 시간
- …
```

- **색인은 도구가 만든다.** 교본 등록 때 원문 제목에서 절과 줄 범위를 뽑아 색인 뼈대를 만들고, 사람이 "언제 읽나"·"읽지 않음"·안티패턴 요약을 채운다. 원문은 커밋에 고정하므로 줄 범위가 바뀌지 않는다. 원문을 갱신하면 색인을 다시 만들고 메모를 다시 검토한다.
- **크기 상한**: 언어 색인은 2KB 안팎, 최상위 `INDEX.md`는 1KB 안팎. 넘으면 교본 수를 줄이거나 절을 묶는다.
- **연결**: 최상위 `INDEX.md`는 언어 색인과 `common/` 색인을 함께 가리키고, `opal-test-agent/references/guides/INDEX.md`(판정용)는 test-agent 디스패치에만 주입한다.
- **선택**: 요소 선언(`test-tools.yaml`)의 언어·프레임워크로 색인과 교본 묶음을 고른다(아래 "교본 활용 장치" 1). PM은 디스패치할 때 요소의 언어 색인 경로만 넘기고, 원문 경로는 넘기지 않는다. 자동 활성화(트리거)에 기대지 않는다.
- **공유**: 구현 워커와 test-agent는 같은 사본을 쓴다. test-agent는 구현 GATE에서 같은 색인으로 단언·스타일을 판정한다.
- **출처**: `affaan-m/ECC`(MIT). 로컬 확인본 커밋 `c70874fa`(2026-09-29). `ceo4ever/ECC` fork는 원본보다 커밋 221개 뒤처져 있으므로(2026-10-01 GitHub compare) 원본 커밋에 고정한다. 교본별 상단에 출처·커밋·라이선스 고지를 둔다.

1. **프레임워크 연결표**: 언어만으로 고르면 보관 교본은 연결될 길이 없다(예: pug `app_android`는 Kotlin이지만 Android 교본이 필요). 최상위 `INDEX.md`에 언어+프레임워크 → 교본 묶음 연결표를 둔다.

   | 언어 + 프레임워크 | 교본 묶음 |
   |---|---|
   | Kotlin + Spring(WebFlux·jOOQ 등) | kotlin-patterns, kotlin-testing, hexagonal-architecture |
   | Kotlin + Android·KMP | kotlin-patterns, kotlin-coroutines-flows, kotlin-testing |
   | Java + Spring MVC·JPA | springboot-patterns, springboot-tdd, springboot-verification |
   | TypeScript + Next·React | react-best-practices, composition-patterns, next-best-practices, react-testing |
   | TypeScript + Vite·React | react-best-practices, composition-patterns, vite-patterns, react-testing |
   | TypeScript + Node·Express | backend-patterns, api-design |
   | Python + FastAPI | python-patterns, python-testing, fastapi-patterns, modern-python |
   | Python (도구·CLI) | python-patterns, python-testing, modern-python |
   | PostgreSQL | database-migrations, postgres-patterns |

   - 요소의 언어·프레임워크는 opi가 저장소를 검사하고 사용자 확인으로 확정해 요소 선언에 기록한다(품질 강화 제안서 §6.1). PM은 연결표로 고른 색인 경로를 디스패치에 넣는다.
   - 연결표에 없는 조합은 언어 색인만 쓰고, 결과에 "연결표 없음"을 보고해 연결표를 늘리는 근거로 삼는다.
2. **설계 단계 활용**: PM은 설계할 때 해당 요소 색인의 설계 체크리스트(색인에 "설계 시 확인" 표시가 된 절)를 확인한다. 예: API 계약 → `api-design`(자원 명명·상태 코드·오류 응답), 마이그레이션 → `database-migrations`(안전한 컬럼 추가·무중단 인덱스), 모듈 경계 → `hexagonal-architecture`. 설계 GATE의 evaluator도 같은 체크리스트로 판정한다. 원문 전체가 아니라 색인의 체크리스트 줄만 읽는다.
3. **사용 기록과 개선 루프**: 구현 워커와 test-agent는 결과에 읽은 교본 절과 걸린 안티패턴을 적는다(§5.6 5단계 출처 기록에 포함). 태스크가 끝나면 도구가 집계한다. 자주 걸리는 패턴은 색인 안티패턴 요약에 올린다. 오래 쓰이지 않은 절은 자동으로 내리지 않는다. 역할·위험(보안·마이그레이션처럼 드물지만 중요한 항목)·설계 체크리스트 여부를 검토한 뒤에만 "읽지 않음"으로 바꾼다. 집계는 §11 측정에 포함한다.
4. **원문 갱신 절차**: 원문은 커밋에 고정한다. 주기적으로(분기 1회 또는 사용자 요청 시) 도구가 원 저장소의 최신 커밋과 비교해 바뀐 교본·절을 보고한다. 바뀐 교본은 원문을 교체하고 색인을 다시 만든 뒤 판정·연결표를 다시 검토한다. 교체 전후 내용 해시를 `SOURCES.md`에 남긴다.

품질 강화 제안서 §6.2·§6.4와 같은 방향이며, 이 제안서가 먼저 구현한다. 원문 저장 현황과 교본 활용 장치는 이 제안서에만 있고, 품질 강화 제안서는 이 결과를 참조한다.

## 6. 테스트

### 6.1 통합 수행 판단

| 설계 | 테스트 단계 | 허용 |
|---|---|---|
| 통합 대상 | 수행 | 기본 |
| 통합 아님 | **상향**(통합 수행) | test-agent가 사유를 남기고 할 수 있음 |
| 통합 대상 | **대체 증거** | 다른 실행 증거(API 호출·단위 테스트 등)가 IF의 흐름 성공 기준을 그대로 증명한다고 test-agent가 근거와 함께 판정한 경우만 PASS. PM 단독 판단 불가 |
| 통합 대상 | **하향**(미실행) | test-agent·PM 단독 불가. 해당 IF는 "미실행"으로 남고 PASS가 되지 않는다. 사용자가 잔여 위험을 승인하면 조건부 완료(품질 강화 제안서 §3.6), 승인 전에는 CLOSE 불가 |
| 통합 아님 | 스킵 | 설계의 사유를 기록에 남기고 스킵 |

test-agent가 상향하는 사유의 예:

- 구현이 설계보다 넓게 경계(API·DB·외부 연동·화면 흐름)를 건드렸다.
- 단위 테스트가 경계를 mock으로 대신했다.
- 구현 GATE에서 우려가 지적됐다.

상향할 때 흐름 성공 기준은 test-agent가 설계의 AC를 근거로 제안하고 PM이 확정한다. 기준을 정하는 권한은 PM에게 있다.

### 6.2 통합 시나리오 세부

test-agent가 설계의 통합 표(IF)를 실행 가능한 시나리오로 쓴다.

| 항목 | 내용 |
|---|---|
| 주체 | 설계 IF의 허용 주체 안에서 고른다. 설계에 없는 대행·주체로 바꾸려면 PM이 설계 변경으로 처리 |
| 방식 | API · 브라우저 · 도구 · 혼합 (추가 가능) |
| 시나리오 | 단계 순서, 데이터, 호출·화면 요소 |
| 검증자 | 판정 주체(test-agent 기본) |
| 성공 기준 | 설계 IF의 흐름 성공 기준(바꾸지 않음) |

### 6.3 실행과 수정

- 실행 대상은 두 가지다: 통합 표의 IF, 그리고 증명 수단이 흐름 실행·사람 확인인 성공 기준(SC). 단일 화면 동작처럼 통합이 아닌 SC도 여기서 실행·판정한다(통합으로 부르지 않는다). 도구는 PLAN→기록 파일 생성 때 이런 SC를 실행 행으로 만든다.
- 행별로 실행하고 증거를 기록한다(`test-tool e2e`·`scenario-mark`).
- 코드 수정이 필요하면 PM이 구현 워커를 fix 모드로 호출한다. 수정 뒤 해당 W의 단위 테스트를 다시 GREEN으로 만들고(잠금 유지, 테스트 수정은 §5.3), 바뀐 범위는 구현 GATE ①·②를 다시 거친 뒤 통합을 재실행한다.
- 반복 상한은 현행 TEST FAIL 루핑(3회, `opal-pilot-dev` STEP 5)과 E2E 1회(guards.md L3b)를 따른다.
- 최종 판정 전에 마지막 수정 기준의 단위 전체 회귀 증거를 확보한다(`harness/test-cycle.md` §최종 TEST Gate). 다음이 모두 같을 때만 구현 GATE의 전체 재실행 결과를 재사용하고 다시 실행하지 않는다: 작업 트리 입력 해시, 단위 실행 범위와 명령, 실행 환경 서명(러너 버전·설치 의존성·테스트에 영향을 주는 환경값), 읽을 수 있는 PASS 출력. 기존 `test-cycle.md`의 증거 재사용 조건과 같다. 변경이 있었으면 영향 범위를 먼저 검증하고 마지막 상태로 전체 회귀를 1회 실행한다.

### 6.4 테스트 GATE

- **test-agent**: 통합 시나리오별 PASS/FAIL을 증거와 함께 판정한다.
- **도구**: 모든 SC·IF에 증명 수단별 현재 증거(단위·결정론은 구현 GATE 재실행, 내용 검토는 구현 GATE 판정, 흐름 실행·사람 확인과 IF는 테스트 단계 실행)가 있는지, 스킵·상향·하향·대체 증거 사유가 기록됐는지 확인한다.
- **PM**: 판정과 증거, 사유, 잔여 위험을 검토해 통과 또는 재요청을 결정한다. FAIL·미실행은 누구도 PASS로 바꾸지 않는다. 남은 FAIL·미실행을 안고 끝내려면 PM이 `await_user`·`decision_request`로 사용자에게 잔여 위험 승인을 요청하고, 승인되면 **조건부 완료**로 기록해 DONE.md 잔여 위험 절에 남긴다(품질 강화 제안서 §3.6). 거부되면 BLOCKED다. 품질 강화 제안서 §3.6은 조건부 완료를 설계에서 승인된 예외 계획(mock 대체) 행에만 쓰므로, 이 제안은 그 범위를 테스트 단계에서 사용자가 잔여 위험을 승인한 FAIL·미실행 행까지 넓힌다. 이 행은 일반 PASS와 구분해 기록하고 `close.final` 전에 사용자 승인 기록이 있어야 한다. TEST 실행·판정을 서브에이전트가 맡는 현행 경계(`harness/actor.md` §독립 검증 경계)를 유지한다.

| 에이전트 | 역할 | 모델 / effort | 하지 않는 것 |
|---|---|---|---|
| PM (메인 세션) | 기준 결정, 조율, 종료 결정 | 세션 설정(작업 트리 세션 standard) / 세션 | 구현 GATE·테스트 판정 |

| 구현 워커 (be·fe·db) | 단위 테스트 + 구현 (주변 스타일 우선, 문제 시 언어 색인 → 교본 절) | standard / 미선언 (현행) | 성공 기준 변경 |
| `opal-test-agent` | 구현 GATE 판정, 통합 실행·판정 (언어 색인 + 판정용 색인) | standard / 미선언 (현행) | 소스·테스트 수정 |

**단계별 수행**

| 단계 | PM | 도구 | evaluator | 구현 워커 | test-agent |
|---|---|---|---|---|---|
| 설계 | PLAN 작성(기준·설계·순서·통합) | env-check | — | — | — |
| 설계 GATE | 지적 반영 | 형식 검사 | 독립 검증 | — | — |
| 구현 | 순서대로 디스패치, 상한 초과 시 사용자에게 | RED·잠금·해제·GREEN 기록, 영향 재실행, W 완료 검사 | — | 테스트·구현·리팩터, 수정 기록, 공유 대역 작성, W 완료 검사 위반 수정 | — |
| 구현 GATE | 재구현 요청 | ① 결정론 판정 | — | — | ② 추론 판정 |

| 테스트 GATE | 종료 결정 | 증거 커버 확인 | — | — | 시나리오별 판정 |

- 정상 경로에서 구현 GATE ② 판정과 테스트 단계는 test-agent 디스패치 1회로 이어서 수행한다. 판정 기록과 GATE는 분리되며, 구현 GATE가 FAIL이면 그 디스패치는 통합으로 넘어가지 않고 반환한다. 재구현 뒤 재판정은 새 디스패치다.
- `opal-plan-agent`는 이 경로에서 설계를 쓰지 않는다(PM이 직접 작성 — 현행 coordinator 경로와 같음). worker actor 경로에서의 쓰임은 별도로 정리한다(§12).

## 8. 형식 가드와 요구 충족

| 위험 | 막는 장치 | 종류 |
|---|---|---|
| 기준을 구현자가 정함 | PM이 설계에서 기준·예시값 결정, evaluator 독립 검증 | 요구 충족 |
| 거짓 RED | 도구가 직접 실행, 단언 실패·미구현 표지만 유효, 버그 재현은 원본 코드 | 형식 |
| 테스트를 고쳐서 통과 | 잠금 해시, 수정 기록 형식, 예시값 유지·단언 수·약화 패턴 검사 + test-agent 수정 근거 판정(사후 검증 테스트는 필수) | 형식 + 요구 충족 |
| 낡은 GREEN | 구현 GATE의 현재 상태 전체 재실행, SC 리비전 변경 시 무효화 | 형식 |
| 껍데기 테스트 | 테스트 정적 검사, SC-ID 연결 검사 | 형식 |
| 약한 단언·같은 오해 | 예시값 그대로 사용 + 구현 GATE 추론 판정 | 요구 충족 |
| 공통 결함 전파 | 동시 수정 금지, 영향 재실행, 구현 GATE·통합의 실제 연결 확인 | 형식 + 요구 충족 |
| mock 우회·계약 불일치 | 설계의 테스트 대역 표(사유 필수), 공유 대역 + 양방향 검증(등록 사례 한정), 실제 연결 테스트 1개 의무, 표 밖 입력 명시 실패, 즉석 mock 금지, 커버리지는 보조 진단 | 형식 + 요구 충족 |
| 판정자의 자기 확인 | 판정(evaluator·test-agent)과 종료 결정(PM) 분리, FAIL·미실행은 PASS 불가(사용자 승인 시 조건부 완료) | 구조 |

형식 가드 통과는 요구 충족을 뜻하지 않는다. 보고·DONE에서 둘을 구분해 적는다.

### 9.3 ECC와의 관계

ECC(`affaan-m/ECC`)의 tdd-guide는 한 에이전트가 기준을 정하고 Red-Green-Refactor를 돌며 커버리지 80%로 확인하고, orch 파이프라인은 계획 승인과 커밋 전 두 번 사람이 확인한다. 이 제안은 한 워커가 테스트와 구현을 함께 하는 단순함을 가져오되, 기준을 PM이 먼저 정하고(evaluator 검증), RED·GREEN을 도구가 기록·잠그며, 구현 GATE에서 독립 판정을 더한다. 리팩터 단계와 필수 엣지 케이스 목록을 ECC에서 가져오고, 전역 커버리지 목표는 가져오지 않는다.

## 11. 측정

opst 단계별 소요 시간·비용에 더해 현재 opd와 비교한다. 품질 지표를 비용 지표와 함께 본다.

- **품질**
  - 숨은 인수 테스트 통과율
  - 구현 GATE·테스트에서 발견한 누락·느슨한 단언 건수, 그리고 구현 GATE가 놓쳐 테스트·숨은 테스트에서 드러난 건수(판정 에이전트 model·effort 비교의 기준)
  - 기능 기준 중 단위 테스트로 증명된 비율
  - 테스트 수정 건수와 그중 약화로 판정된 건수
  - **결함 주입 측정**: 공통 기능에 알려진 결함을 넣은 시나리오와, "제공자는 맞지만 소비자의 인자 변환·오류 전달·결과 반영이 틀림", "대역 표 사례만 정상", "누적 커버리지만 정상" 시나리오로, 공통 기능 W 완료 검사·후속 W 테스트·구현 GATE ① ②·테스트 단계 중 어디서 잡히는지와 재작업 시간을 잰다. 공통 기능 조기 GATE(test-agent) 도입 여부의 판단 근거다.
  - 테스트 대역 위반·경고 건수, 양방향 검증 실패 건수
  - 교본 사용 기록: 읽은 절, 걸린 안티패턴 건수, 연결표 없음 보고 건수(§5.6 교본 활용 장치 3)
- **비용·속도**
  - 태스크 전체 소요 시간·비용(설계 증가분, TEST-SCENARIO 단계 제거분 포함)
  - TEST fix 반복 횟수, 구현 GATE 재구현 횟수

판정 에이전트(evaluator·test-agent)의 model·effort는 "놓친 건수"를 기준으로 standard와 advanced를 비교해 조정한다. 분리형(품질 강화 제안서 §4)은 숨은 테스트 실패나 GATE가 놓친 건이 특정 범주(돈·권한·데이터)에 몰리면 그 범주에 도입을 검토한다.

## 12. 구현 단계

| 단계 | 내용 | 대상 |
|---|---|---|
| L1 설계 계약 | PLAN.md 성공 기준·통합 절, Work items 테스트 파일 구분, 설계 GATE 결정론 검사, evaluator `design-rubric` 성공 기준 축 | `op-dev-plan`·`plan-guide`·설계 게이트 검사·`opal-evaluator-agent` |
| L2 도구 | PLAN 표 → 기록 파일 생성, 행 단위 RED·GREEN 기록(전체 잠금 대신), 버그 재현 소스 해시 확인, 잠금·해제와 수정 기록, 증거 무효화, 영향 재실행, 약화 패턴·정적 검사·SC-ID 연결, 파일 잠금 + 원자 쓰기 | `test-tool` |
| L3 단계 구성 | TEST-SCENARIO 단계 폐지와 `state-tool` 파이프라인 행 변경(구현 GATE 행 추가), `opal-pilot-dev` STEP 구성, `op-dev-execute` 구현 루프, `opal-test-agent` 구현 GATE·통합 상향, `red-first.md` 개정, `op-dev-test-scenario`·목표 커버 게이트 정리 | 파일럿·스킬·에이전트·하네스 |
| 교본 | 원문은 저장 완료(§5.6 원문 저장 현황). 언어 색인·최상위 연결표(언어+프레임워크) 작성, 색인 뼈대 생성 도구, 설계 체크리스트 표시, `coding-principles.md` §4에 코드 작성 순서 추가, PM 디스패치에 색인 경로 주입, 사용 기록 집계, 원문 갱신 비교 도구 | `op-dev-execute/references/guides/`·`opal-test-agent/references/`·하네스 |
| 환경 | 요소별 테스트 환경(품질 강화 제안서 T2) | opi·`test-tool` |

- L1과 환경은 병행할 수 있다. L2는 L1의 표 형식을, L3는 L2의 기록·잠금 명령을 쓴다.
- 커버리지 소비 테스트별 귀속과 언어별 공유 대역 작동은 구현 착수 때 작은 fixture 저장소(Kotest·MockK·Gradle, Vitest/Jest, pytest)로 먼저 확인한다. 도구 이름만으로 같은 동작을 가정하지 않는다.
- L2·L3 회귀 검증에 부정 테스트를 포함한다: 사유 없는 대역 행 거부, 표에 없는 의존 mock 거부, 표에 있는 의존의 즉석 mock 거부, 공유 대역이 표 행과 다른 결과일 때 거부, 표 밖 입력에 공유 대역이 예외, 실제 연결 검증이 지정되지 않은 TD 거부, 내부 의존 실제 연결 테스트 없는 소비 W 완료 거부(외부 IF·미충족 경로는 통과), 외부 TD에 IF 계획도 미충족 기록도 없으면 구현 GATE 거부, 미충족 TD의 사용자 승인 없이 CLOSE 거부, 같은 W 대역 생성·사용 정상 통과, 서로 다른 W 대역 선행 순환 거부, 내부 의존 실제 연결을 IF로 지정하면 설계 GATE 거부, 제공 W 완료 시 미래 소비 테스트를 요구하지 않음, 대역 작성 W가 다른 W인데 소비 W 선행 작업에 없으면 거부, 외부 경계 실제 쪽 미검증을 PASS로 처리하지 않음, 관련 변경 뒤 이전 W 완료 기록 재사용 거부, W 완료 검사 통과 기록 없는 W 완료 거부, 테스트 대조 전 기준 목록 기록 없는 ② 판정 거부, 근거 없는 반례·상한 초과 반례 거부, 반례 파일이 GATE 입력 해시를 바꾸지 않고 정식 테스트 탐색에 잡히지 않음, 반례 단언 실패만 SC FAIL·컴파일 오류는 검증 불가, 기존 잠긴 파일에 덧붙인 테스트의 GREEN 거부, 실행 환경 서명이 다를 때 최종 회귀 재사용 거부, 해시가 다를 때 최종 회귀 재사용 거부, 잠금 뒤 해제 없는 테스트 수정의 GREEN 거부, 형식이 틀린 수정 기록의 해제 거부, 버그 재현 행에서 소스가 바뀐 RED 거부, 컴파일 오류 RED 거부, 약화 패턴 검출, 수정 테스트의 판정 없는 GATE 통과 거부, 공통 기능 수정 시 영향 W 재실행, 서로 읽는 병렬 W 실행 중 파일 변경 시 결과 미채택, writer가 남아 있을 때 구현 GATE 진입 거부, GATE 실행·판정 중 파일 변경 시 결과 미채택, GATE 뒤 fix가 이전 PASS를 재사용하는 경우 거부, 흐름 실행 SC가 통합 아님 태스크에서 실행 행으로 생성됨, 경고 미판정 시 GATE 통과 거부.
- **구형 태스크**: 새 계약 버전이 없는 태스크는 TEST-SCENARIO가 있는 기존 경로로 끝까지 진행한다. 계약 버전 기록·해석 규칙은 품질 강화 제안서 §9.1을 따른다.
- **활성화**: 신규 태스크의 기본 계약을 이 제안의 흐름으로 바꾸는 시점은 날짜가 아니라 능력 확인으로 정한다. 이 제안의 소비자(L1 설계 GATE 검사·evaluator, L2 `test-tool`(PLAN→기록 파일 생성, 구현 GATE 도구 판정 포함), L3 `state-tool` 파이프라인·`opal-pilot-dev`·`op-dev-execute`·`opal-test-agent`, 교본, 환경)가 각자 지원하는 계약 버전을 보고하고, 모두 새 흐름(TEST-SCENARIO 없는 단계 구성 포함)을 지원할 때만 바꾼다. 그 전에 새 계약을 명시해도 지원하지 않는 소비자가 있으면 시작 시점에 거부한다.
- **worker actor 경로**: plan-agent가 PLAN을 쓰는 worker 경로에서도 성공 기준은 PM이 정한다. plan-agent는 설계·구현 순서를 쓰고 PM이 성공 기준 절을 쓰는 분담을 L1에서 정한다.
