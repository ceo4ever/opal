## 1. 결론

추진 순서는 **응답 중복 제거 → P1(디스패치 대상별 로드) → 제한된 P2(적용 범위가 분명한 문서 분리)**다.
P3(목차 + 필요한 절만 로드)는 별도 실험으로 분리하고, 앞 단계의 측정 결과를 본 뒤 추진 여부를 정한다.

- 1차 태스크: 응답 중복 제거 + P1(에이전트 항목 선별만, 플랫폼 공통 문서 유지) + 1차 receipt 계약(대상·호출 연결·반환 본문 검증) + 버전·호환 정책 + 검증 소비자 갱신(§4.3)
- 2차 태스크: 제한된 P2 (multi-repo 캡슐 소유권 계약 분리부터) + 조건 근거 receipt
- 별도 실험: P3 + 절 집합·추가 receipt

원칙은 하나다. **필수 규칙의 선택은 매니페스트와 도구가 정하고, 모델 판단에 맡기지 않는다.**
ECC처럼 모델이 스킬을 불러올지 판단하는 방식은 적용이 보장되지 않으므로 채택하지 않는다.

### 1.1 진행 현황

**1차 — 적용완료 (태스크 175, `tasks/175-261001-opd-이벤트-로딩-경량화/`)**

- **응답 중복 제거**: 모든 이벤트 load 응답이 `response_version: 2`를 갖고, 본문은 `documents[].content`에 한 번만 담긴다. 실측(설치본): `session.assistant` 응답 26,912 → 14,730바이트, `pm.activate` 148,614 → 76,229바이트(문서 본문 합계는 같음).
- **P1 대상별 디스패치**: `worker.dispatch`는 코드 블록 바깥 헤딩만 절 경계로 보고 대상 에이전트 항목 1종만 보낸다. 담당을 배정하는 역할과 하위 디스패치 3종은 항목 전체를 받는다. 일반 대상 본문 합계 46,244 → 32,499~32,697바이트(약 29% 감소), 응답 바이트 98,203 → 약 39.6K.

## 3. 단계별 제안

### 3.1 응답 중복 제거 (1차)

- **변경**: load 응답에서 본문은 `documents`에만 한 번 담고, `required_documents`·`optional_documents`는 id·경로·해시·바이트만 담은 메타데이터로 바꾼다.
- **효과**: **중복된 본문 바이트**가 사라져 응답 본문이 절반이 된다. JSON 메타데이터는 남으므로 전체 응답량이 정확히 50% 줄지는 않는다. 전달되는 규칙은 같다.
- **호환**: §4.2의 버전·호환 정책을 따른다.

### 3.2 P1. 디스패치 대상별 로드 (1차)

현재 절차는 Step 0에서 `worker.dispatch`를 로드한 뒤 Step 4에서 에이전트를 선택한다(`dispatch-process.md:10-24`, `:66`). 대상을 모르는 시점에 전체를 받는 구조다.

**순서 변경**

1. 가벼운 매핑 목록(`agents.md` §전문 에이전트 매핑 테이블)으로 대상 에이전트와 호출 역할을 먼저 확정한다.
2. 대상별 규칙을 로드한다: `load --event worker.dispatch --agent <에이전트> --role <역할> --dispatch-id <식별자>`.
3. 같은 대상·역할·식별자를 주고 verify한 뒤 호출한다(§4.1).

**로드 범위 (1차는 에이전트 항목만 선별)**

- 유지: 문서 머리말, §프로젝트 문서 주입 계약, §전문 에이전트 매핑 테이블, §플랫폼 sub-agent 어댑터 변환 규칙 전체(플랫폼 공통), §폴백 규칙, §탐색 경로, 그리고 `dispatch-process`·`context-injection`·`observability` 전문
- 선별: 에이전트 항목(`### opal-*-agent` 등)은 대상 1종만
- 제외: 다른 에이전트 항목, §에이전트 추가 가이드(하위 절과 그 안의 예시 포함), §향후 추가 에이전트
- 예외: 다른 워커의 담당을 배정하는 역할(예: `opal-plan-agent`)에는 에이전트 항목 전체를 함께 준다.
- 1차에서는 플랫폼별 어댑터 규칙을 선별하지 않는다. 플랫폼 판정 근거·불명 시 처리·receipt 검증이 정해지기 전에 넣으면 범위가 커진다.

**절 경계 판정 규칙**

- 절 경계는 펜스 코드 블록(```) 바깥의 헤딩만으로 정한다. 코드 블록 안의 헤딩은 절이 아니라, 그 블록을 담은 절의 본문이다.
- 예: `agents.md` §프로젝트 전문 에이전트 생성의 "프로젝트 에이전트 예시" 코드 블록(`opal/core/references/agents.md:333-358`) 안에 있는 `## 프레임워크 에이전트 로드`·`## 프로젝트 전용 규칙`·`### 확정 기준` 등은 mams 프로젝트 예시다. 이를 별도 절로 떼어 보내면 BaseRepository 상속·소프트 삭제 같은 예시 규칙이 모든 프로젝트의 지시로 읽힌다. 같은 이유로 §향후 추가 에이전트의 템플릿 블록(`:372-384`) 안 헤딩도 절로 보지 않는다.
- 이 규칙은 event-loader의 선별 구현과 `static-check`가 같이 따른다.

**효과(절별 측정 기반 추정)**

- agents.md: 30,600바이트 → 약 15,800바이트(코드 블록 바깥 유지 절 합계 약 14,800 + 대상 항목 1종 약 1,000)
- worker.dispatch 본문: 46,244바이트 → 약 31,400바이트
- 대상별 실제 값은 1차 구현 후 측정해 확정한다.

### 3.3 제한된 P2. 적용 범위가 분명한 문서 분리 (2차)

범용 절 필터는 만들지 않는다.

- worktree 문서의 multi-repo 캡슐 소유권 계약을 별도 문서로 분리하고, 매니페스트가 **조건부 필수 문서**(`layout: "multi-repo"`일 때 필수)로 선언한다.
- Phase 1 legacy gate와 Codex identity 연결은 layout 조건으로 분리하지 않는다. 별도 조건이 정해지기 전까지 공통 문서에 남긴다.
- 조건 근거는 시점별로 정한다.
  - 태스크 생성 전: `pilot.start`는 `state.json`·worktree 등록 정보가 없을 때도 필요하므로 프로젝트 설정(`.opal/worktree.json`의 `layout`)을 근거로 쓴다.
  - 재개 시: 저장된 `state.json`·registry를 근거로 쓴다.
- 근거 값이 없거나 서로 충돌하면 조용히 빼지 않고 **포함**한다.
- 에이전트 플랫폼(Claude·Codex 등)은 terminal-context의 `host`와 다른 축이다. `host`는 터미널 환경(`orca`·`cmux`·터미널 프로그램)을 뜻하므로(`opal/tools/terminal-context/terminal_context.py:21-25`) 플랫폼 조건에 쓰지 않는다.
- **효과**: monorepo 호출에서 약 11.5KB(해당 문서를 제외할 수 있는 호출에 한정).

### 3.4 P3. 목차 + 필요한 절만 로드 (별도 실험)

큰 문서(PROJECT.md, pm-process, citation-rules, design-gate, pm-review-gate)를 "필수 절 + 나머지 목차"로 보내고 필요한 절을 `event-loader section`으로 가져오는 방식이다. 효과는 가장 크지만 다음 이유로 후순위다.

- `[MUST]` 표기가 없는 문장에도 의무·금지·예외가 있고, `[MUST]` 절이 다른 절의 정의나 적용 범위를 참조할 수 있다.
- multi-repo 전용 `[MUST]`처럼 조건부로만 필수인 규칙이 있으므로, **항상 필수**와 **조건이 성립하면 필수**를 구분해야 한다.
- 절마다 안정적인 ID, 적용 조건, 의존 절을 선언하고 도구가 의존 절까지 함께 보내야 한다.
- 정적 검사는 누락된 ID·깨진 참조·의존 관계까지만 확인할 수 있다. 절이 혼자 읽혀도 의미가 완전한지는 문서 검토와 행동 실험으로만 확인된다.

## 4. receipt·검증 계약

현재 verify는 문서 전체의 경로·해시·바이트 합계를 검사하고(`opal/tools/event-loader/event_loader.py:332`), `state-tool event-verify`는 이 검증에 위임한다. 변경의 핵심 위치는 event-loader다. receipt 변경은 단계별로 나눠 선언하며, 앞 단계에서 뒤 단계의 기반을 미리 만들지 않는다.

### 4.1 1차: 대상·호출 연결과 반환 본문

- receipt에 기록: 대상 에이전트 이름, **실제로 선택된 에이전트 문서의 경로·해시와 선택 출처**(프로젝트 `{project}/.opal/agents/` 또는 프레임워크 `~/.opal/agents/`), 호출 역할, 역할 문서의 경로·해시(역할 문서가 있을 때), 디스패치 식별자, 실제 반환한 본문 해시.
- 에이전트 탐색은 프로젝트가 프레임워크보다 우선이다(`opal/core/references/agents.md:279-284`). 같은 이름의 프로젝트 에이전트가 프레임워크 에이전트를 덮어쓸 수 있으므로, 이름만으로는 어떤 문서가 호출되는지 정해지지 않는다.
- verify는 **이번 호출의 대상·역할·디스패치 식별자를 인자로 받아** receipt 기록과 대조한다. receipt 안의 대상만 검사하지 않는다.
- verify는 같은 탐색 규칙으로 에이전트 문서를 다시 해석해 receipt의 경로·해시와 비교한다. 문서가 바뀌었거나, 프로젝트 에이전트가 새로 생기거나 사라져 선택 출처가 바뀌었으면 거부한다.
- 대상 에이전트가 같아도 역할이 다르면 다른 호출이다. 예: opd2의 Verifier와 Reviewer는 둘 다 `opal-task-agent`로 호출되므로(`opal/skills/opal-pilot-dev2/SKILL.md:93-100`) 역할과 역할 문서(`agents/verifier.md`·`agents/reviewer.md`) 해시로 구분한다.
- 디스패치 식별자가 다른 receipt를 재사용하면 거부한다. 식별자 발급 주체(PM·state-tool·run-log의 `worker_run_id` 재사용 중 무엇)는 1차 PLAN에서 정한다.

### 4.2 1차: 버전·호환 정책

- 응답과 receipt에 형식 버전을 명시한다. 현재 receipt의 `schema_version: 1`(`event_loader.py:288`)을 기준으로 새 형식은 버전을 올린다.
- **새 계약과 구형 호환을 load 시점에 가른다.** load와 verify 모두 소비자가 넘긴 계약 버전으로 형식을 정한다.
  - 새 계약 버전을 요구한 호출: 대상·역할·디스패치 식별자 중 하나라도 없으면 load·verify 모두 거부한다. 구형 방식으로 자동 전환하지 않는다. 그래야 새 검증이 적용됐다는 사실이 보장된다.
  - 계약 버전도 `--agent`도 없는 구형 호출(전환 기간 한정): 지금처럼 전체 문서와 구형 receipt를 돌려주고 경고 코드(예: `legacy_dispatch_contract`)를 함께 낸다. 이 receipt는 **구형 검증만 통과한 호출**로 기록하며, 대상·역할 검증까지 적용된 것으로 표시하지 않는다. install은 이미 실행 중인 세션이 읽어 둔 지시를 바꾸지 못하므로, 진행 중인 작업이 갑자기 막히지 않게 하려는 장치다.
  - 전환 중에는 구형 호출 건수를 receipt와 run-log로 집계해, 호환 경로가 계속 쓰이는지 확인한다.
- **호환 종료(기본 동작을 명시 거부로 전환)는 날짜가 아니라 전환 확인을 기준으로 한다.** 세 조건이 모두 충족되면 종료한다.
  - 저장소의 모든 디스패치 호출(PM 절차, 파일럿 문서, 하위 디스패치 에이전트 3종)이 새 계약으로 갱신됐다. `event-loader static-check`가 소스에서 구형 호출을 찾지 못한다.
  - 직접 디스패치와 하위 워커 디스패치의 새 계약 검증 시나리오가 통과한다.
  - 설치 전부터 실행 중이던 세션이 종료됐거나 새 계약을 다시 로드했다. 집계된 구형 호출 건수가 0이다.
- 구버전 receipt를 새 verify로 검사할 때: receipt 형식 버전으로 구버전임을 식별하고, 전환 기간에는 기존 규칙으로만 검증한다(결과에 구형 검증임을 표시). 호환 종료 후에는 명시적으로 거부한다. 형식을 추측해 통과시키지 않는다.
- 설치본과 소비자 문서(파일럿·dispatch-process)의 버전이 다를 때:
  - 현재 verify는 소비자 문서의 버전을 입력으로 받지 않으므로 검출할 수 없다. 소비자가 **요구하는 계약 버전을 인자로 넘기고**(예: `verify --contract-version <N>`), verify가 설치된 event-loader가 그 계약을 지원하는지 판정한다.
  - 판정 기준은 설치 버전 전체의 일치가 아니라 **응답·receipt 형식 계약의 호환**이다. 지원 범위 밖이면 오류로 보고하고 install 후 재로드를 안내한다.
  - 소비자 문서가 계약 버전을 어디에 선언할지(파일럿 SKILL 본문 또는 매니페스트의 이벤트 선언)는 1차 PLAN에서 정한다.

### 4.3 1차: 검증 소비자 갱신

새 verify 인자(대상·역할·디스패치 식별자·계약 버전)는 그 인자를 전달하는 쪽이 함께 바뀌어야 의미가 있다. 소비자를 그대로 두면 두 가지 중 하나가 된다 — 새 인자를 필수로 만들면 워커가 막히고, 생략을 허용하면 새 검증이 건너뛰어진다.

- **PM 쪽**: `state-tool event-verify`(`opal/tools/state-tool/state_tool_parts/gates.py:2640`)가 현재 이벤트·receipt만 전달하므로, `worker.dispatch`일 때 새 인자를 받아 event-loader verify로 그대로 넘기도록 확장한다. `pm/dispatch-process.md` Step 0과 디스패치하는 파일럿 문서(예: `opal-pilot-dev2/SKILL.md` §worker.dispatch 이벤트 게이트)의 호출 형식도 같이 갱신한다.
- **워커 쪽**: `worker.dispatch` 진입 게이트를 가진 에이전트 16종(`opal/agents/*/AGENT.md`, 예: `opal/agents/opal-be-agent/AGENT.md:15`)은 지금 `verify --receipt <path> --event worker.dispatch`만 실행한다. 디스패치 프롬프트가 넘긴 대상·역할·디스패치 식별자·계약 버전을 같은 verify 호출에 전달하도록 갱신한다. 게이트 문장은 에이전트마다 복제돼 있으므로, 한 곳을 원문으로 두고 나머지는 참조하도록 정리할지도 1차 PLAN에서 판단한다.
- **하위 디스패치 에이전트**: 자기가 하위 워커를 부르며 `load --event worker.dispatch`와 verify를 직접 실행하는 에이전트 3종 — `opal-task-action-agent`(`opal/agents/opal-task-action-agent/AGENT.md:28`), `opal-sdd-action-agent`(`AGENT.md:27`), `opal-loop-action-agent`(`AGENT.md:30`) — 도 새 계약(대상·역할·디스패치 식별자·계약 버전)으로 load·verify하도록 갱신한다. 이 경로는 headless 채널(`opal-agent`)에서도 실행되므로 같은 event-loader 버전을 쓰는지 1차 PLAN에서 확인한다.
- **디스패치 프롬프트**: PM이 워커에게 넘기는 `[WORKER]` 프롬프트(`pm/dispatch-process.md` §워커 컨텍스트 주입 템플릿)에 위 인자를 담는 항목을 추가한다.
- **누락 인자 처리**: `worker.dispatch` 새 형식 receipt를 검증할 때 대상·역할·디스패치 식별자·계약 버전 중 하나라도 빠지면 verify가 거부한다. §4.2의 구버전 호환 정책과는 receipt 형식 버전으로 구분한다.

### 4.4 2차: 조건 근거

- receipt에 조건 판정 근거(값·출처)와 선택된 문서 집합을 기록한다.
- 로드할 때와 검증할 때 조건이 달라지면(예: monorepo → multi-repo) 기존 receipt를 거부한다.

### 4.5 P3 실험: 절 집합과 추가 receipt

- receipt에 선택된 절 집합과 절 해시를 기록한다.
- 나중에 추가로 가져온 절은 기존 receipt를 수정하지 않고, **원본 receipt를 참조하는 별도 receipt**로 남긴다. 병렬 호출 간 충돌과 과거 기록 변경을 피하고, 추가 로드량도 따로 셀 수 있다.

## 5. 검증

- **기능 동등성**: opst로 같은 시나리오(예: `smoke-version-flag`, `function-stockctl-multiloc`)를 변경 전후로 돌려 숨은 테스트와 준수 항목이 같은지 본다. 전후 2회는 초기 확인용이며, 품질 동등성을 확정하려면 반복 수를 늘린다.
- **1차 계약 시나리오**: 대상 불일치, 같은 대상·다른 역할 receipt 재사용, 다른 디스패치 식별자 receipt 재사용, 반환 본문 해시 불일치, 선택된 에이전트 문서 변경, 프로젝트·프레임워크 선택 출처 전환을 각각 거부하는지 확인한다. 코드 블록 안 예시 헤딩이 절로 선별되지 않는지도 확인한다.
- **소비자 시나리오**: PM 쪽 `state-tool event-verify`와 워커 진입 게이트가 새 인자를 실제로 전달하는지, 새 형식 receipt에서 인자 하나라도 빠지면 거부되는지, 같은 receipt를 다른 워커 호출의 인자로 검증하면 거부되는지 확인한다.
- **호환 시나리오**: 구형 호출이 전체 전송 + 경고 + 구형 검증 표시로 처리되는지, 새 계약 호출에서 인자 누락 시 load·verify가 거부되는지, `--agent` 없는 기존 호출, 구버전 receipt 검증, 소비자가 넘긴 계약 버전을 설치본이 지원하지 않는 경우가 §4.2 정책대로 처리되는지 확인한다.
- **2차 계약 시나리오**: 조건 불명·충돌 시 포함, 로드 후 조건 변경 시 거부, 필수 문서 누락 시 거부를 확인한다.
- **로드량**: 문서 본문 합계와 **실제 응답 바이트**(JSON 전체)를 각각 측정한다. 로드마다 남는 receipt로 태스크 단위 합산하고, 재검증(verify)은 중복으로 세지 않는다.
- **비용·시간**: 본문 합계와 응답 바이트는 입력 토큰·청구 비용과 다르므로 opst의 비용·시간 지표로 따로 비교한다.
- **목표**
  - 응답 중복 제거: 중복 본문 바이트 0 (응답 본문 절반)
  - P1: worker.dispatch 본문 46,244바이트 → 약 31,400바이트 (대상별 실측으로 확정)
  - 제한된 P2: monorepo 호출의 pilot.start 본문 약 11.5KB 감소

## 6. 위험과 비채택안

- **같은 문서를 다시 보내지 않는 중복 제거는 채택하지 않는다.** 긴 대화에서 컨텍스트가 요약되면 앞서 받은 규칙이 사라질 수 있다. citation-rules처럼 여러 이벤트에 실린 문서는 P3 실험에서 다룬다.
- **P1은 디스패치 순서를 바꾼다.** 태스크 168의 opd2 Builder·Verifier·Reviewer 디스패치 계약(`opal/skills/opal-pilot-dev2/SKILL.md` §worker.dispatch 이벤트 게이트)과 opst 판정이 현재 순서를 전제로 하는지 1차 PLAN에서 확인한다.
- **1차에서 플랫폼별 어댑터 규칙은 선별하지 않는다.** 플랫폼 판정이 따로 정해질 때까지 공통으로 보낸다.
- **모델 판단 기반 로딩(ECC 스킬 방식)은 채택하지 않는다.** 내용 계층의 아이디어만 참고하고, 필수 규칙의 선택은 매니페스트가 소유한다.
