> 상태: 제안
> 작성: 알투(PM)
> 작성일: 2026-10-02
> 대상: TEST-SCENARIO 작성 계약, 설계 게이트, EXECUTE 단위 테스트 책임, TEST 통합 검증, `opal-test-agent`, `test-tool`(resolve·scenario·e2e), opi의 테스트 환경 생성, 언어별 테스트 교본

## 1. 결론

테스트를 **단위**와 **통합** 두 계층으로 나누고, 계층마다 무엇을·언제·누가 증명하는지를 시나리오에 미리 정한다.

- **단위**: 기능 하나가 통과 기준대로 동작하는지 증명한다. 시나리오에는 통과 기준만 적는다. EXECUTE에서 **테스트 코드는 test-agent, 구현은 execute-agent**가 나눠 쓴다. 테스트 작성자와 구현자를 모든 단위 테스트에서 분리하고, 작업 항목(W) 단위로 "최소 계약 기반 준비 → 준비된 W부터 독립 테스트·RED → 소유권 이관 → 구현-테스트 루프(구현 → 테스트 → 검증 → 다시 구현)"를 병렬로 진행한다(§4). 단위가 모두 통과해야 TEST로 넘어간다.
- **통합**: 단위로 검증된 기능들을 실제 흐름 순서대로 이어 실행해 연결에 문제가 없는지 증명한다. 화면 조작, API 순차 호출, 또는 둘의 혼합으로 실행한다. 시나리오에는 흐름·통과 기준·실행 방식·주체를 적고, TEST에서 수행한다. **필요한 경우에만** 둔다.
- **없음 / mock 대체**: 검증할 동작이 없거나, 실제 검증이 지금은 불가능한 경우다. 사유를 남기고, mock 대체는 조건부 완료로 보고한다.

전체 프로세스는 **설계(공통 부분·구현 순서) → 테스트 시나리오(통과 기준 잠금) → W별 구현-테스트 루프 → TEST(최종 검증)**다(§4.0). 설계가 W 사이의 기다림을 줄이고, 루프가 실패를 에이전트 안에서 빠르게 고치며, 작성자·구현자 분리와 독립 검증이 품질을 지킨다.

ECC(`affaan-m/ECC`)와 비교한 결과, ECC의 "모든 구현 작업은 테스트 작성을 거쳐야 완료" 규칙과 증거 대응표는 가져오고, OPAL의 "통과 기준은 구현자가 아닌 PM이 먼저 잠근다"와 독립 통합 검증은 유지한다. 전역 커버리지 목표와 Playwright 전제는 가져오지 않는다.

  - PLAN은 적립액 계산을 "단위 테스트"로 검증한다고 했지만(`PLAN.md:702` TS-017), TEST-SCENARIO에서 실행 관측으로 바뀌었다. 백엔드 저장소에는 해당 테스트 파일이 없다.
  - 백엔드 저장소에는 테스트 규칙(`workspace/backend/docs/claude/rules/testing.md` — Kotest 5.9·MockK, BehaviorSpec 권장)이 있었지만 PLAN·ANALYSIS·TEST-SCENARIO 어디에서도 참조되지 않았다.
- **stl 011·012**(프론트엔드): 시나리오 도구가 grep·lint·build·DOM 조회뿐이었고, 011 PLAN은 "신규 단위 테스트 없음"을 명시했다.
- **반대 사례 — mams 166·168·169**(Python 백엔드): 모두 실제 pytest 코드를 남겼다. 테스트 규칙이 프로젝트 안에 구체적으로 있었고(`docs/CONVENTIONS-BACKEND.md` — mock 단위 테스트 허용, 실 DB L3 검증 필수), pytest 인프라가 갖춰져 있었다.

### 2.2 OPAL 구조의 공백

1. **시나리오가 정적 확인으로 흐른다.** 목표 커버 게이트와 설계 게이트는 모든 AC/C/H가 시나리오에 연결됐는지를 보지만, 동작 요구가 실제 실행 테스트로 증명되는지는 판정 축에 없다. 167번 경제성 기준은 "가장 저렴한 계층"을 권하므로 로직 검증이 정적 확인으로 내려가도 막지 않는다.
2. **단위 테스트 코드의 담당이 비어 있다.** `opal-test-agent`는 "단위 테스트 = EXECUTE 단계(구현 워커 자가검증) — opal-test-agent의 책임이 아니다"라고 정의한다(`opal/agents/opal-test-agent/AGENT.md:69`). 그런데 구현 지침은 `test-tool unit` 실행만 지시하고 테스트를 쓰라는 지시가 없다(`opal/skills/op-dev-execute/references/execute-guide.md:64-66`). 테스트 코드는 RED 행에서만 생긴다(`AGENT.md:105-113`).
3. **RED 판정을 태스크 전체에 한 번 한다.** RED-first 규칙은 비즈니스 로직에 적용하고 혼합 작업은 작업 항목별로 판정하라고 하지만(`opal/core/references/harness/red-first.md` §1), 015는 태스크 전체를 "구현 후 검증"으로 정해 계산 로직까지 RED 대상에서 빠졌다.
4. **테스트 환경 판정이 틀린다.** `.opal/test-tools.yaml`은 만드는 단계가 없다. 그래서 `test-tool resolve`가 전역 템플릿(언어 `typescript` 고정)을 그대로 쓴다. pug에서 실행하면 `source: global`, `language: typescript`가 나온다. 범위도 `fe`·`be` 둘뿐이라 저장소가 6개인 프로젝트를 표현하지 못한다.
5. **테스트 규칙이 작성자에게 전달되지 않는다.** PM 주입 규칙의 TEST 단계 항목은 "관련 S, 변경 파일, 실행 환경, 기존 증거"뿐이다(`opal/core/references/pm/context-injection.md:27`). 컨벤션 검사는 허브 링크를 따라가는데, pug처럼 규칙을 저장소 안에 둔 프로젝트에서는 테스트 규칙까지 닿지 않는다.
6. **문서 모순**: `opal-test-agent` BE 모드는 "서비스 레이어 비즈니스 로직 단위 테스트"를 집중 영역으로 두는데(`AGENT.md:80`), 바로 위 절은 단위 테스트가 책임이 아니라고 한다.

## 3. 테스트 계층과 시나리오 계약

### 3.1 계층 정의

| 계층 | 증명 대상 | 시점 | 테스트 작성·실행 |
|---|---|---|---|
| 단위 | 기능 하나의 동작(계산·규칙·상태 전이·검증) | EXECUTE | test-agent가 테스트 코드, execute-agent가 구현 |
| 통합 | 기능들을 흐름대로 이은 결과(데이터 전달, 상태 연속, 실 DB·연동) | TEST | 주체(§3.3)가 흐름 실행, 판정은 test-agent |
| 없음 | 검증할 동작이 없는 변경 | — | 사유만 기록 |
| mock 대체 | 실제 검증이 지금 불가능한 흐름 | — | 사유·잔여 위험·후속 검증 시점 기록 |

- 단위 테스트 안에서 의존 대상(저장소 포트·외부 API 클라이언트)을 mock으로 대체하는 것은 단위 계층의 정상적인 작성 방식이다. "mock 대체" 계층은 통합 흐름 자체를 실제로 실행하지 못하는 경우만 뜻한다.
- 실제 연동을 요청받은 작업에서 mock으로 대신하고 완료를 주장하지 않는다(`opal/core/PRINCIPLES.md` §4). mock 대체 행이 있는 AC는 "조건부 완료"로 보고하고 사용자 확인을 받는다.

### 3.2 통합은 필요한 경우에만

- **통합 행이 필요한 AC**: 여러 기능을 잇는 흐름 — 사용자 흐름, 화면과 API, API와 DB 저장, 외부 연동, 배치 처리.
- **통합 행이 필요 없는 AC**: 기능 하나 안에서 끝나는 로직, 문서 태스크, 단위 테스트로 덮이는 내부 리팩터. 단위만으로 완료한다.
- 단위로 충분히 증명되는 내용을 통합으로 다시 검증하지 않는다. 같은 것을 두 번 증명하지 않는 것이 속도 개선의 한 축이다(§5).

### 3.3 통합 주체

| 주체 | 실행 | 판정 | `test-tool e2e` 실행 방식 |
|---|---|---|---|
| test-agent | test-agent | test-agent | browser · api · hybrid |
| test-agent + PM 승인 | test-agent, 사람 승인이 필요한 지점은 PM이 사용자 대신 승인 | test-agent | collaborative (사람 조치 응답자 = PM) |
| PM 대행 | PM이 사용자 대신 조작하고 증적 제출 | test-agent (verifier) | collaborative · manual (제출자 = PM) |
| PM + 사용자 | PM이 진행, 사용자가 확인·조작 | test-agent (verifier) | collaborative |
| 사용자 | 사용자가 직접 조작하고 증적 제출 | test-agent (verifier) | manual |

- PM이 실행한 경우에도 판정은 test-agent가 증적으로 한다. 시나리오를 쓰고 실행한 PM이 스스로 판정하지 않는다(`opal/core/references/harness/actor.md` §독립 검증 경계).
- **PM 대행의 경계**
  - 대행 여부는 시나리오에 미리 적고 설계 게이트가 확인한다. 실행 중에 즉석으로 정하지 않는다.
  - 대행 범위는 dev·테스트 환경의 되돌릴 수 있는 조작으로 한정한다. 운영 환경, 결제, 외부 시스템 쓰기, 인증 정보 입력은 사용자만 한다(`opal/core/references/harness/guards.md` §독립 검증 경계의 별도 승인 경계).
  - 보고에 "PM 대행"을 표시해 사용자가 직접 확인한 항목과 구분한다.

### 3.4 시나리오 행 형식 — 계층·검증 방식·완료 상태를 분리한다

시나리오 행은 서로 다른 세 축을 따로 적는다. 한 축의 예외가 다른 축의 의무를 풀어 주지 않게 하기 위해서다.

- **계층**: 단위 · 통합 · 없음 · mock 대체 (§3.1)
- **검증 방식**
  - 테스트 코드: 러너로 실행하는 단위·통합 테스트
  - 결정론 검사: 구조·형식·스키마·링크 같은 도구 검사(유형 `check`)
  - 흐름 실행: `test-tool e2e`로 흐름을 실행
  - 추론 검토: 독립 평가자의 내용 검토(§3.5)
- **완료 상태**: PASS · 조건부 완료 · BLOCKED (§3.6)

축 사이의 규칙:

- **동작 AC**(계산·규칙·상태 전이·흐름)는 검증 방식이 테스트 코드 또는 흐름 실행인 행이 1건 이상 있어야 PASS가 될 수 있다. 결정론 검사만으로는 동작 AC를 PASS시키지 않는다.
- **형식·구조 요구**(문서 구조, 설정 스키마, 머리말 규칙 등)는 결정론 검사로 PASS할 수 있다. 이런 행에는 테스트 파일·RED 의무가 없다.
- RED·테스트 파일 의무는 "계층 = 단위이고 검증 방식 = 테스트 코드"인 행에만 붙는다.
- RED 의무의 예외는 두 가지이고, 둘 다 RED만 면제하며 테스트 파일 의무는 면제하지 않는다.
  - 설계 단계에서 사용자가 승인한 탐색형 W의 행: §4.2 탐색형 경로(구현 전 소스 기준점 + 후속 테스트 GREEN + 조기 독립 단언 대조 + TEST 독립 판정)
  - EXECUTE 중 PM이 승인한 사후 검증 행: §4.2 사후 검증 행 절차

계층별 필수 항목:

- **단위**: 통과 기준, 검증 방식, 담당 작업 항목(W-ID). 검증 방식이 테스트 코드면 테스트 파일 경로(작업 항목의 변경 대상에 포함)를 적는다. 구체적인 테스트 케이스와 실행 명령은 적지 않는다 — test-agent가 테스트 코드로 쓴다(§4.2).
- **통합**: 흐름(단계 순서), 통과 기준, 실행 방식, 주체, 실행 환경 준비 여부.
- **없음**: 사유 한 줄.
- **mock 대체**: 사유, 실제로 검증하지 못한 범위(잔여 위험), 후속 검증 시점·주체.

지금의 `유형` 열(167, `unit`·`integration`·`contract`·`regression`·`e2e`·`check`)은 검증 방식 축으로 정리하고, 계층과 완료 상태는 별도 열로 둔다. 정확한 열 구성은 구현 태스크의 PLAN에서 정한다.

### 3.5 문서를 만드는 구현

- **기본은 결정론 검사**: 단위에 해당하는 검사(구조·필수 절·링크·인용 위치·머리말 규칙·매니페스트·스키마 — `event-loader static-check`, `code-scan validate`, `brain-tool lint` 등)를 구현 워커가 EXECUTE에서 통과시킨다. 대부분의 문서 태스크는 여기서 끝난다.
- **통합은 추론 검토**: 실행 흐름이나 계약을 바꾸는 문서(파일럿·하네스·에이전트 규칙 등)만 독립 평가자가 내용을 추론해 검토한다. 상류 문서와의 정합, 규칙 간 충돌, 빠진 경우를 본다.
- **추론 검토가 증명하는 범위**: 추론 검토는 형식·규범 내용 AC(문서가 무엇을 규정하는가, 규정끼리 충돌하지 않는가)만 증명한다. "파일럿이 실제로 X를 수행한다"처럼 실행 결과를 요구하는 AC는 실행 AC이므로, 흐름 실행(opst 등) 행이 있거나 예외 계획(§3.6)이어야 한다. 추론 검토로 실행 AC를 PASS시키지 않는다.
- opst 실제 실행은 의무가 아니라 merge 전 선택 검증으로 둔다.
- "없음"은 오탈자 수정처럼 의미가 바뀌지 않는 변경에만 쓴다.

### 3.6 완료 상태와 게이트 연결

- **PASS**: 행의 통과 기준이 해당 검증 방식의 증거로 충족됐다.
- **AC 처리 계획은 두 종류로 나눈다.**
  - **정상 계획**: AC를 PASS로 증명하는 것이 목표다. 동작 AC면 테스트 코드 또는 흐름 실행 행이 있어야 한다(§4 2단계의 정상 계획 검사).
  - **예외 계획**: 실제 검증이 지금 불가능해 mock 대체로 진행하는 AC다. 이 AC는 끝까지 "미충족"으로 남고, PASS로 바꾸지 않는다(가짜 PASS 금지). 예외 계획은 설계 단계에서 사용자가 미리 승인해야 성립한다(`state-tool design-decision --scope external` 기록 후 사용자 승인). 승인 기록이 없으면 설계 게이트가 거부한다.
- **조건부 완료**: 예외 계획 AC의 mock 대체 행에만 쓴다. 일반 PASS와 구분해 기록한다.
  - TEST PM Gate는 조건부 완료 행이 있으면 자동으로 통과하지 않고 `await_user`·`decision_request`로 사용자 결정을 요청한다. 결정 요청에는 잔여 위험과 후속 검증 시점·주체를 담는다.
  - 사용자가 잔여 위험을 승인하면(`owner=user` 기록) TEST를 통과하고, DONE.md에 잔여 위험 절로 남긴다. 승인 전에는 CLOSE로 넘어가지 않고 `close.final`도 막힌다.
  - 사용자가 거부하면 해당 행은 BLOCKED가 되어 실제 검증 수단을 마련할 때까지 대기한다.
- **BLOCKED**: 증거를 만들 수 없는 상태다(환경 없음, 러너 없음 + 대체 수단 없음, 사용자 거부 등). 통과로 간주하지 않는다.
- **러너 없는 요소의 동작 AC**: "check만 허용" 설정은 형식·구조 요구에만 적용된다. 동작 AC는 아래 순서로 증명 수단을 찾고, 어느 것도 없을 때만 BLOCKED다.
  1. 요소 선언에 적힌 러너
  2. 요소 루트 검사로 찾은 러너(§6.1)
  3. **런타임 내장 러너** — 순수 로직(계산·변환·검증 함수)의 단위 테스트에 한해, 설치 없이 런타임에 들어 있는 러너(`bun test`, `node --test`)를 쓴다. 예: pug `frontend`·`frontend_app`은 Bun을 쓰므로(`bun.lockb`·`bun.lock`) `bun test` 후보가 되고, stl `frontend_partners`는 이미 `node:test`로 테스트 파일을 돌리고 있다(`stl/tasks/011-*/PLAN.md:45`). lockfile·설정 파일은 후보를 찾는 단서일 뿐이다. 실제 사용 전에 바이너리 존재·버전, 대상 언어(TS 등)·모듈 형식·경로 별칭을 그 러너가 실제로 불러올 수 있는지 확인하고(예: 빈 테스트 1건 실행), 확인에 실패하면 다음 순서로 넘어간다. 화면 렌더링처럼 DOM 환경이 필요한 테스트는 대상이 아니다. 테스트 파일 위치·이름 규칙이 저장소에 없으면 opi의 `test-tools.yaml` 생성 때 사용자 확인으로 정한다.
  4. 통합 흐름 실행(`test-tool e2e`의 browser·api) — 화면 동작이나 흐름은 단위 러너 없이 이 경로로 증명한다.
  5. 러너 도입(저장소 구성 변경) 또는 예외 계획(mock 대체·조건부 완료) — 둘 다 사용자 결정이다. 결정 전에는 BLOCKED다.

## 4. 단계별 흐름

### 4.0 전체 프로세스 — 설계 → 시나리오 → 구현-테스트 루프

빠르게 진행하면서 품질을 유지하기 위해 세 단계가 각자 맡는 일을 나눈다.

```
설계(PLAN)            무엇을 어떤 순서로 만드는가
  공통 부분 설계 ─ 최소 계약 기반(타입·인터페이스·포트)과 공통 동작 W를 분리
  구현 순서 설계 ─ W 유형, 테스트 선행, 구현 선행, 파일 소유권
        │
        ▼
테스트 시나리오        무엇으로 통과를 판정하는가
  AC마다 계층(단위·통합·없음·mock 대체)과 통과 기준
  설계 게이트 통과 → 명세 잠금
        │
        ▼
구현-테스트 루프 (W마다, 준비된 W부터 병렬)
  테스트 작성 → RED → 구현 → 테스트 → 검증 → (실패 시) 다시 구현 → …
  통과 → 후행 사용 가능 → 다음 W가 이어서 시작
        │
        ▼
TEST                  태스크 최종 검증(통합 흐름·독립 단언 대조·전체 회귀)
```

| 단계 | 속도를 내는 장치 | 품질을 지키는 장치 |
|---|---|---|
| 설계 | 공통 부분을 먼저 고정해 W가 서로 기다리지 않게 함, 구현 순서를 선행 관계로 명시 | 공개 계약을 PLAN에 고정, 설계 게이트가 순환·충돌·누락을 거부 |
| 시나리오 | 단위 행은 통과 기준만 적음, 통합은 필요한 경우에만 | 통과 기준을 구현 전에 PM이 잠금, 평가자가 계층 분류 검사 |
| 구현-테스트 루프 | 준비된 W부터 병렬 시작, 내부 루프는 에이전트 호출 없이 빠르게 반복 | 작성자·구현자 분리, 유효한 RED, 테스트 불변, 매 반복 결정론 검증, 독립 단언 대조 |
| TEST | 단위 결함 대부분이 루프에서 해결돼 TEST 수정 반복이 줄어듦(보장은 아님 — 독립 대조를 TEST로 미룬 W의 테스트 결함·누락은 여기서 드러날 수 있음) | 태스크 PASS는 여기서만 선언 |

아래 1~6은 이 흐름을 단계별 규칙으로 적은 것이다.

1. **PLAN (PM)**: 작업 항목(W)과 선행 관계를 정할 때 **최소 계약 기반**을 함께 정한다(§4.1). W마다 유형, 테스트 작성 선행과 구현 선행, 파일 소유권 전환을 적는다 — PLAN 형식이 바뀐다(§4.5).
2. **TEST-SCENARIO (PM)**: AC마다 계층을 정하고 §3.4 형식으로 쓴다.
3. **설계 게이트**
   - 결정론 검사:
     - 정상 계획의 동작 AC마다 단위 또는 통합 행이 1건 이상 있다.
     - 정상 계획의 흐름형 AC에는 통합 행이 있다.
     - 정상 계획의 동작 AC마다 검증 방식이 테스트 코드 또는 흐름 실행인 행이 있다(결정론 검사만으로 덮인 동작 AC 거부).
     - 예외 계획 AC는 mock 대체 행, 잔여 위험, 후속 검증 시점·주체, 사용자 사전 승인 기록이 있다. 이 AC에는 "정상 계획의"로 시작하는 검사(단위·통합 행 존재, 흐름형 AC의 통합 행, 테스트 코드·흐름 실행 행, 통합 환경 준비)를 적용하지 않는다.
     - 검증 방식이 테스트 코드인 단위 행의 작업 항목 변경 대상에 테스트 파일이 있다.
     - 테스트 코드 단위 행이 있는 W는 `테스트 선행`(최소 계약 기반 중 그 W가 테스트를 작성·실행하는 데 필요한 것)이 지정돼 있다. 필요한 계약이 없으면 `없음`을 명시해야 하고, 빈칸은 거부한다.
     - W 유형·소유권 전환·선행 관계가 §4.5 형식을 따르고, 탐색형 W에는 사유와 사용자 승인 기록이 있다.
     - 정상 계획의 통합 행에 실행 방식과 주체가 있고, 실행 환경이 준비됐거나(`test-tool e2e env-check`) 사람 확인 방식이다.
     - PM 대행 행은 대행 경계(§3.3) 안에 있다.
     - 없음·mock 대체 행에 사유가 있고, mock 대체 행에 잔여 위험과 후속 검증 시점·주체가 있다.
   - 평가자 검사: 분류 자체가 맞는지 판정한다. 예: 흐름인데 단위로만 분류했거나, 계산 로직을 "없음"으로 분류했거나, 동작이 있는 공통 부분을 선언 전용 계약 기반으로 분류한 경우를 잡는다.
   - 게이트를 통과하면 **명세 잠금**(§4.3)이 걸린다.
4. **EXECUTE — W 단위 테스트 우선 파이프라인 (§4.2)**
   - 계약 기반 W를 먼저 처리하고, 각 기능 W는 **자기 선행 계약이 준비되는 즉시** 시작한다. 기반 전체 완료를 기다리지 않는다.
   - 기능 W마다: test-agent가 테스트와 W 내부 선언을 쓰고 RED를 기록 → 도구가 구현 디스패치 조건을 확인 → 소유권 이관 → execute-agent가 구현하고 GREEN을 기록한다.
   - 결정론 검사 행은 같은 W 안에서 도구 통과 증거를 기록한다.
   - 증거(테스트 파일, 테스트 이름, 명령, 출력, 소스·테스트·계약 해시)를 `test-tool`로 기록한다. "AC → 시나리오 → 테스트 → RED 증거 → GREEN 증거" 대응을 `test-scenario.json`에 남긴다.
   - 테스트 작성 기준은 §6.2의 우선순위를 따른다(test-agent와 execute-agent 모두에 주입).
5. **TEST (test-agent)** — 태스크 전체 PASS는 여기서만 선언한다. W의 GREEN은 그 작업 항목의 완료 증거일 뿐이다.
   - 진입 조건: EXECUTE에서 수행하는 행, 즉 단위 계층의 테스트 코드 행(GREEN 증거)과 결정론 검사 행(도구 통과 증거)에 증거가 모두 기록돼 있어야 하고, 하나라도 없으면 TEST에 들어가지 않는다. 통합 계층의 행은 검증 방식이 흐름 실행이든 통합 테스트 코드든 TEST에서 수행하므로 진입 조건에 포함하지 않는다.
   - 통합 행을 §3.3 주체·실행 방식대로 수행하고 판정한다.
   - 단위 테스트가 시나리오의 통과 기준을 실제로 단언하는지 대조한다(테스트 작성 test-agent와 다른 디스패치).
   - 통합 실패로 코드를 고치면 execute-agent가 fix 모드에서 영향받은 단위 테스트를 다시 통과시킨 뒤 통합을 다시 실행한다.
   - 최종 게이트에서 마지막 수정 기준으로 단위 전체 회귀를 한 번 실행한다(`opal/core/references/harness/test-cycle.md` §최종 TEST Gate).
6. **보고·CLOSE**: mock 대체 행은 조건부 완료와 잔여 위험으로, PM 대행 행은 대행 표시와 함께 보고한다.

### 4.1 최소 계약 기반

공통 기반은 "여러 W가 쓰는 것"이 아니라 **후속 W가 테스트를 작성·실행하기 위해 먼저 필요한 것**으로 정의한다. 소비자가 하나여도 선행 계약일 수 있고, 여러 곳에서 쓴다고 모두 먼저 구현할 필요는 없다.

- **계약 기반(선언 전용)**: 동작 없는 선언 — 타입, DTO, 인터페이스, 포트 시그니처. 먼저 만들고 컴파일·형식 검사(결정론 검사)로 확인한다. 테스트·RED 대상이 아니다.
- **공통 동작**: 동작이나 데이터 의미가 있는 공통 부분 — 유틸 함수, 검증 규칙, 기본값, 스키마·마이그레이션. 먼저 구현해 두는 예외가 아니라, 다른 기능 W와 똑같이 **독립 테스트 → RED → 구현 → GREEN**을 거치는 W다. 후속 W가 이 동작을 실제로 써야 하면 선행 관계로 지정하고, mock으로 충분하면 선행시키지 않는다.
- **선행 관계 두 가지와 실행 그룹의 역할 분리**
  - `테스트 선행`: 테스트 작성을 시작하려면 먼저 준비돼야 할 계약 W. 예: W-3이 계약 기반 W-1만 필요하면 W-2 완료를 기다리지 않고 테스트 작성을 시작한다.
  - `선행 작업`(구현 선행): 구현을 시작하려면 먼저 "후행 사용 가능" 상태(§4.2)가 돼야 할 W. 공통 동작 W를 mock이 아니라 실제로 써야 하는 경우 여기에 둔다. 테스트 선행은 항상 구현 선행에 포함된다.
  - `실행 그룹`: 변경 파일이 겹치는 W를 동시에 돌리지 않기 위한 충돌 방지 표시로만 쓴다. 순서를 정하지 않는다.
- **작은 태스크**: 최소 계약 기반이 필요 없으면(W 하나, 선행 계약 없음) 이 단계를 건너뛴다.

### 4.2 W 단위 테스트 우선 파이프라인 — 구현-테스트 루프

**구현-테스트 루프**

아래 상태도는 **RED 필수 일반 W의 기본 경로**다. 다른 W 유형과 행 경로는 아래 "경로별 분기"를 따른다. 이 절의 나머지 규칙(RED 유효성, 구현 디스패치 조건, 실패 처리, 테스트 리비전, W 상태)은 모두 이 루프의 상태와 전환에 붙는다. `state-tool`이 W의 현재 상태와 경로를 기록하고 그 경로에서 허용되지 않은 전환(예: RED 필수 행의 RED 없이 구현 시작, 테스트 수정 후 기존 GREEN 재사용)을 거부한다. 세션이 끊기면 기록된 상태와 카운터에서 재개한다.

```
[대기] ─ 테스트 선행 준비 ─▶ ① 테스트 작성 (test-agent)
                                   │
                           ② RED 확인 (도구)
                무효 RED → ①  ─────┤
                                   │ 유효 RED
                     ③ 구현 디스패치 조건 확인 (도구)
                                   │
         ┌─────────────────────────▼─────────────────────────┐
         │ 내부 루프 (execute-agent 디스패치 한 번 안에서)       │
         │   ④ 구현 → ⑤ 테스트 실행 → 실패 분류                │
         │     명백한 구현 결함만 ④로, 그 외는 루프 종료·제출    │
         │   유형별 상한(guards.md) 도달 시 종료·제출           │
         └─────────────────────────┬─────────────────────────┘
                                   ▼
                           ⑥ 검증 (도구 + 판정자)
          통과 │   구현 결함(결정론 판정) → ④ (외부 반복)
               │   테스트 문제 → PM 판정 → ① 테스트 리비전
               │   계약 충돌 → PLAN 재검토
               ▼   원인 불명·환경·상한 도달 → PM → 사용자
       [후행 사용 가능] ─────▶ TEST에서 최종 검증 완료
```

**경로별 분기**

모든 경로에 공통 조건(구현 선행 W의 후행 사용 가능, 배타적 파일 소유권, 현재 실행 입력 해시, TEST 최종 검증)은 그대로 적용된다. 경로마다 바뀌는 것은 진입 순서와 테스트 불변성의 기준 리비전뿐이다.

| 경로 | 진입 순서 | 불변성 기준 리비전 | 후행 사용 가능 조건 |
|---|---|---|---|
| RED 필수 일반 W | ① → ② → ③ → 내부 루프 → ⑥ | RED가 기록된 테스트 리비전 | 현재 리비전 GREEN (고위험이면 + 현재 리비전 조기 대조 PASS) |
| 선언·검사 W | 공통 조건 → 구현·검사 → ⑥(결정론만) | 해당 없음(테스트 없음) | 결정론 검사 통과 |
| 탐색형 W | 사용자 승인 + 소스 기준점 + 공통 조건 → 구현 → 테스트 작성(test-agent) → 실행 → ⑥ | 후속 테스트를 동결한 리비전 | 현재 리비전 GREEN + 현재 리비전 조기 대조 PASS |
| 일반 W 안의 사후 검증 행 | 승인된 리비전으로 그 행의 ②만 면제, 나머지는 일반 W와 같음 | 승인 기록의 테스트 리비전 | 일반 W와 같음 |

**실패 분류와 상한**

⑤ 실행이 실패하면 먼저 분류하고, 분류마다 다른 경로로 나간다. 내부 재구현은 명백한 구현 결함에만 열린다.

| 실패 분류 | 다음 상태 | 판정 주체 | 상한(SSOT `harness/guards.md` 자동 검증 루핑 제약) |
|---|---|---|---|
| 명백한 구현 결함(단언 실패, 자기 W 소스의 컴파일·타입 오류) | ④ 구현 | execute-agent(내부), 외부 반복은 결정론 검사 결과로만 도구가 판정 | unit/integration 3회, build/type 2회 |
| 테스트가 통과 기준과 다름, 단언 부적합 | ① 테스트 리비전 | 독립 판정자 또는 PM | 해당 없음(PM 판정 경로) |
| 계약 충돌 | PLAN 재검토 | PM | PLAN 재진입 2회 |
| 환경 오류·원인 불명 | 루프 이탈 | PM | 즉시 이탈 |

- 원인이 애매하면 구현 결함으로 보지 않고 PM 경로로 보낸다.
- 유형별 상한은 같은 실패(같은 행·같은 원인)에 누적한다. 내부·외부 루프를 오가거나 구현·테스트 수정을 번갈아 하거나 세션을 재개해도 초기화되지 않는다.
- **W 외부 반복 예산(2회)**: 실패 원인·테스트 리비전·재개와 무관하게 W 전체에 누적하는 별도 카운터다. 이 예산은 자동 재시도의 하드 상한이며, 넘으면 PM 조율로 넘긴다. 위 유형별 상한을 늘리지 않는다 — 둘 중 먼저 닿는 것이 적용된다.
- 유형별 상한을 넘으면 PM은 `await_user`·`decision_request`로 사용자에게 올린다. PM 승인만으로 추가 반복을 열지 않는다.
- 내부 루프에서 execute-agent는 테스트 파일을 고칠 수 없다. 도구가 ⑥에서 경로별 기준 리비전의 테스트 해시로 확인한다.

**⑥ 검증 두 층**

- **매 반복(도구, 결정론)**: 테스트 파일 해시가 경로별 기준 리비전과 같은가, W의 테스트 코드 행이 현재 리비전에서 모두 GREEN인가, 실행 입력 해시와 격리, 테스트·소스 컨벤션 검사.
- **조기 독립 단언 대조(판정자, 테스트 작성과 다른 디스패치)**: 단언이 통과 기준을 실제로 검증하는가.
  - 대상: 탐색형 W, 고위험 일반 W. 둘 다 현재 리비전의 대조 PASS가 후행 사용 가능 조건이다. 대조가 실패하거나 실행되지 않으면 후행 사용 가능이 되지 않는다.
  - 고위험 표시: 명세 잠금 전에 PM이 시나리오에 지정한다. 잠금 뒤에는 임의로 해제할 수 없다(요구 변경 경로로만).
  - 판정 기록은 W·S-ID·테스트 리비전·통과 기준에 묶인다. 리비전이나 통과 기준이 바뀌면 무효가 되고 다시 대조한다. "1회"는 리비전마다 1회다.
  - 그 밖의 일반 W는 TEST의 독립 대조로 미룬다. 이 경우 테스트 결함·누락은 TEST에서 발견될 수 있다.

**역할**

- test-agent: W의 테스트 코드와, 그 테스트가 컴파일·실행되는 데 필요한 W 내부 선언(시그니처만, 본문은 미구현 표지)을 쓰고 RED를 기록한다.
  - 선언은 PLAN이 허용한 경로와 공개 동작 경계 안에서만 만든다. 테스트는 공개 동작을 단언하고, 내부 private 구조(헬퍼 이름, 내부 호출 순서 등)를 강제하지 않는다.
  - 경계를 바꿔야 하는 선언(새 공개 API, 다른 W의 계약 변경)이 필요하면 쓰지 않고 PM에 올린다. PM은 PLAN 재검토 경로로 처리한다.
- execute-agent: 소유권을 이관받은 뒤 소스를 구현하고 테스트를 실행해 GREEN을 기록한다. 테스트 파일은 고칠 수 없다.
- PM: 조율이 필요한 경우(아래 실패 처리)에 집중한다. 모든 실패를 PM이 분석하지 않는다.

**RED의 유효성**

- 유효한 RED: 단언 실패, 또는 test-agent가 둔 미구현 표지(예: Kotlin `TODO()`, `NotImplementedError`)에서 나온 실패. 미구현 표지는 러너 출력에서 판별할 수 있도록 표지 종류를 요소 선언(`test-tools.yaml`)에 등록하고, 판별 규칙은 T3 PLAN에서 정한다.
- 무효: 실행 환경 오류, import·모듈 미발견, 컴파일·구문 오류(새 기능 내부 선언·fixture·의존성 누락 포함), 테스트 수집 실패.
- RED 기록에는 그 시점의 **소스 해시, 테스트 해시, 계약(선행 계약 W) 버전**을 함께 남긴다. 별도 골격 SHA를 관리하지 않더라도, RED가 어떤 코드·테스트·계약에서 나왔는지는 해시로 식별한다.

**구현 디스패치 조건 (도구가 확인)**

구현 디스패치 조건은 "테스트 작성 완료"가 아니다. 도구(`test-tool`·`state-tool`)가 W 유형별 조건을 확인하고, 충족될 때만 PM이 execute-agent를 디스패치할 수 있다. 공통 조건은 모든 경로의 필수 조건이다. RED 없는 경로는 RED 조건만 면제되고 공통 조건은 면제되지 않는다.

| 조건 | 일반 W (테스트 코드 행 있음) | 선언·검사 W (계약 기반, 문서·설정, 결정론 검사 행만) | 탐색형 W (사전 승인) |
|---|---|---|---|
| 공통 1. 구현 선행 W가 후행 사용 가능 | 필수 | 필수 | 필수 |
| 공통 2. 배타적 파일 소유권 | 필수 | 필수 | 필수 |
| 계약 버전 일치 | RED 기록(사후 검증 행은 승인 기록)에 묶인 선행 계약 버전 = 현재 | RED 기록 비교는 해당 없음. 실행 증거의 선행 계약·입력 해시가 최신이어야 함 | 같음(선언·검사 W와 동일) |
| 유효한 RED | 테스트 코드 행 전부, 현재 테스트 리비전 기준(승인된 사후 검증 행만 면제) | 면제 | 면제 |
| 테스트 동결 | 필수 | 해당 없음 | 테스트 작성 후 동결 |
| 소유권 이관 | test-agent 선언 파일 → execute-agent | 해당 없음 | 해당 없음(execute-agent가 먼저 씀) |
| 추가 기록 | — | — | 설계 승인 기록, 구현 전 소스 기준점 |

- 공통 1: PLAN `선행 작업`의 W가 모두 아래 "후행 사용 가능" 상태다. 테스트 작성 시작은 `테스트 선행`만 보지만, 구현 시작은 `선행 작업`을 본다.

**W 상태 두 단계 — 후행 사용 가능과 최종 검증 완료를 나눈다**

선행 W가 태스크 최종 검증(TEST)까지 끝나야 후행 W가 시작된다면, TEST는 모든 W의 GREEN을 기다리므로 교착된다. 그래서 W 상태를 둘로 나눈다.

| 상태 | 뜻 | 조건 | 쓰는 곳 |
|---|---|---|---|
| 후행 사용 가능 | 후행 W가 이 W에 기대 구현을 시작해도 된다 | 선언·검사 W(계약 기반, 문서·설정, 결정론 검사 행만): 결정론 검사 통과. 일반 W: 현재 테스트 리비전 GREEN(고위험 표시 W는 + 현재 리비전의 조기 독립 단언 대조 PASS). 탐색형 W: 현재 리비전 GREEN + EXECUTE 안의 조기 독립 단언 대조 통과 | 공통 1(선행 작업) |
| 최종 검증 완료 | 태스크 PASS의 일부로 판정됐다 | TEST의 독립 단언 대조·통합·전체 회귀 통과 | TEST·CLOSE |

- W의 GREEN은 후행 사용 가능까지만 뜻하고, 태스크 PASS는 여전히 TEST에서만 선언한다.
- 후행 사용 가능 뒤에 그 W의 테스트나 공개 계약이 바뀌면 상태가 풀리고, 후행 W는 §4.2 변경과 무효화 규칙을 따른다.
- 공통 2: W의 변경 대상 파일을 지금 쓰고 있는 다른 워커가 없다. 한 파일의 writer는 한 시점에 하나다.
- 소유권 이관 뒤에는 test-agent가 그 선언 파일을 고치지 않는다. test-agent와 execute-agent가 같은 파일을 동시에 수정하는 일은 없다.

**실행 격리**

- 테스트 실행을 줄 세우는 것만으로는 부족하다. 실행 중 다른 워커가 같은 모듈의 소스를 고치면 결과가 오염된다.
- 실행 대상 입력(소스·테스트·계약)을 실행 시점에 동결하거나 스냅샷으로 격리해 실행하고, 실행 증거에 입력 해시를 남긴다. 격리 방식(모듈 단위 잠금, 임시 작업 사본 등)은 T3 PLAN에서 정한다.

**실패 처리 — PM 개입 범위를 좁힌다**

- execute-agent가 실행 증거와 원인 후보를 제출한다.
- 명백한 구현 결함은 execute-agent가 허용된 범위(자기 W의 소스) 안에서 바로 고치고 다시 실행한다. 반복 상한은 위 "실패 분류와 상한"을 따른다.
- PM이 개입하는 경우: 테스트 수정이 필요해 보이는 경우, 계약 충돌, 원인 불명, 반복 상한 도달.
  - 테스트 수정은 PM이 통과 기준에 비춰 판정한다. 테스트가 기준과 다르면 test-agent가 고치고, 통과 기준에 연결된 단언을 약화하지 않는다. 수정 절차는 아래 "테스트 리비전"을 따른다.
- 반복 상한의 누적·초기화 금지와 W 외부 반복 예산은 위 "실패 분류와 상한"을 따른다.

**테스트 리비전 — 수정한 테스트는 새 테스트로 다룬다**

RED 뒤 테스트를 고치면, 기존 RED·GREEN 증거는 고치기 전 테스트에 대한 것이므로 새 테스트의 증거가 될 수 없다. 반례: 불완전한 테스트로 RED → 구현 GREEN → 빠진 단언 추가. 추가한 단언은 이미 구현된 코드에서 바로 통과하므로, 다시 돌려도 RED가 나오지 않는다.

- 증거는 테스트 리비전(테스트 파일 해시)마다 묶는다. 디스패치·완료 조건은 현재 리비전의 증거만 인정한다.
- 테스트를 고치면 그 테스트에 연결된 RED·GREEN 증거와 그에 기댄 판정·승인 기록을 한 번에(원자적으로) 무효화한다. 바뀌지 않은 테스트의 증거는 그대로 쓴다.
- 새 RED 관찰: 저장해 둔 구현 전 소스 기준점(또는 지정한 미구현 표지 상태)에서 수정한 테스트를 실행해 실패를 다시 관찰한다. 현재 구현에서 돌린 결과를 RED로 기록하지 않는다(거짓 RED 금지).
- 기준점에서 재관찰이 불가능하면 RED를 기록하지 않고, PM이 명시적으로 승인한 "사후 검증" 경로로 구분해 기록한다. 이 행은 TEST의 독립 단언 대조를 반드시 거친다.

**사후 검증 행 — RED 면제를 행 단위로만 연다**

탐색형 W(설계 단계에서 사용자가 W 전체를 승인)와 사후 검증 행(EXECUTE 중 PM이 행 단위로 승인)은 다른 경로다.

- 시나리오 행마다 검증 경로(`RED 필수` 기본값, 또는 `사후 검증`)를 둔다. `사후 검증`은 승인 기록이 있을 때만 성립한다.
- 승인 기록에는 대상 W·S-ID, 테스트 리비전(해시), 기준점 재관찰이 불가능한 사유, PM 승인이 들어간다. 도구는 이 기록을 읽어 일반 W의 디스패치 조건에서 **그 행의 RED만** 면제한다. 테스트가 다시 바뀌면 승인도 무효가 된다.
- 면제되지 않는 것: 구현 선행, 배타적 파일 소유권, 현재 리비전 GREEN, TEST 독립 판정.
- 권한과 범위: 명세 잠금 뒤 검증 경로를 `사후 검증`으로 바꾸는 권한은 PM만 있고, 테스트 리비전 절차에서 기준점 재관찰이 불가능한 경우에만 쓸 수 있다. 통과 기준·계층·주체는 바꿀 수 없다. 통과 기준을 바꿔야 하면 사후 검증이 아니라 PLAN 재검토(`requirement_change`)로 보낸다.
- 수정하는 동안 그 W의 execute-agent를 멈추고(pause), 수정과 무효화가 끝난 뒤 재개한다. 소스 writer는 계속 하나다.

**변경과 무효화**

- 공개 계약이나 통과 기준이 바뀌면: 영향받는 W를 멈추고 PLAN을 재검토한다(PLAN 재진입 상한 2회, `harness/guards.md`).
- 계약을 유지하는 내부 버그 수정이면: PLAN 재진입 없이 영향받는 테스트만 다시 실행한다.
- 증거 무효화는 영향받는 범위만 한다. 영향 범위가 불명확하면 전체를 다시 검증한다.

**탐색형 W**

구현하면서 설계가 바뀌는 탐색형 W는 테스트 우선이 맞지 않는다. 이런 W는 "execute-agent 구현 → test-agent가 테스트 작성 → GREEN" 경로로 둔다.

- PLAN에 W 유형을 탐색형으로 적고 사유를 남기며, 설계 단계에서 사용자 승인 기록이 있어야 한다. 설계 게이트 평가자가 남용 여부를 본다.
- 구현을 시작하기 전에 소스 기준점(해시)을 기록한다. 후속 테스트를 이 기준점에서 실행할 수 있으면 실패를 관찰해 함께 남긴다.
- 후행 사용 가능 상태가 되려면 후속 테스트의 현재 리비전 GREEN과 EXECUTE 안의 조기 독립 단언 대조(테스트 작성과 다른 test-agent 디스패치)가 모두 필요하다. 테스트가 구현 뒤에 쓰여 구현에 맞춘 테스트가 될 위험이 크므로, 대조를 TEST까지 미루지 않는다. 최종 검증 완료는 다른 W와 같이 TEST에서 판정한다.

**도입 방식**

처음부터 W 수만큼 test-agent를 띄우지 않는다. 작은 고정 풀(동시 test-agent 수 상한)로 시범 적용하고, §8의 전체 시간(기반 준비·에이전트 호출 비용·빌드 대기·재작업 포함)으로 확대 여부를 판단한다. 동시 실행 상한은 하네스 병렬 한도 안에서 정한다.

### 4.3 잠금 모델 — 명세 잠금과 행별 RED 증거를 분리한다

지금 `test-tool scenario-lock`은 RED 대상 행 전부의 실패 관찰이 끝나야 잠그고, 잠근 뒤에는 `scenario-red`를 거부한다(`opal/tools/test-tool/lib/scenario.py:411` `cmd_scenario_lock`, `:604` `cmd_scenario_red` — "locked==true 이후에는 spec존 변경을 거부"). 하나의 잠금이 "명세 동결"과 "RED 증거 완료"를 함께 뜻하므로, W별로 RED→GREEN이 진행되는 파이프라인을 표현할 수 없다. 잠금을 나눈다.

- **명세 잠금**: 설계 게이트 통과 시점에 행의 계층·검증 방식·통과 기준·주체를 동결한다. 이후 이 필드는 바꿀 수 없다(요구 변경은 기존 `requirement_change` 경로). RED 증거 기록은 명세 잠금 뒤에도 허용된다.
- **행별 RED 증거**: 테스트 코드 단위 행마다 RED 증거를 독립적으로 기록한다. W의 구현 디스패치는 §4.2의 W 유형별 조건을 충족할 때 열린다. 테스트 코드 단위 행이 없는 W(문서·설정만 바꾸는 W, 계약 기반 W)도 RED 조건만 면제될 뿐 구현 선행 W의 후행 사용 가능 상태와 배타적 파일 소유권은 확인한다. 선행 관계가 없는 다른 W의 진행과는 무관하다.
- **테스트 불변성 범위**: 어떤 행의 RED가 기록되면 그 행에 연결된 테스트 파일은 동결되고, 단언을 약화·삭제할 수 없다. 예외는 §4.2 실패 처리에서 PM이 판정한 테스트 수정뿐이며, §4.2 테스트 리비전 절차(증거 무효화·기준점 재관찰)를 따른다. fix 모드 불변성 검사는 해당 W의 테스트 파일로 범위를 한정한다.
- **구형 태스크**: 단일 `locked` 플래그를 쓰는 기존 `test-scenario.json`은 기존 계약 그대로 처리한다(§9.1 활성화 정책).

### 4.4 증거 기록의 동시성

여러 에이전트가 병렬로 RED·GREEN 증거를 기록하면 같은 `test-scenario.json`을 동시에 쓰게 된다. 지금 `_save_spec`은 파일 잠금 없이 덮어쓰므로(`scenario.py:206-209`) 증거가 유실될 수 있다.

- `test-tool`의 시나리오 기록 명령은 파일 잠금 아래에서 읽기-수정-원자 쓰기(임시 파일 → `os.replace`)를 한다. 같은 파일의 167번 게이트 이력 기록은 이미 원자 쓰기를 쓴다(`scenario.py:1221` `_atomic_write_json`).
- **쓰기 권한은 역할별로 나눈다.**
  - test-agent(테스트 작성): 담당 W의 테스트 코드 행 RED 증거만 기록한다.
  - execute-agent: 담당 W의 GREEN 증거와 결정론 검사 증거만 기록한다. RED 증거와 다른 W의 행에는 쓸 수 없다.
  - 조기 판정자(EXECUTE, 테스트 작성과 다른 test-agent 디스패치): 탐색형·고위험 W의 현재 리비전 조기 단언 대조 결과만 기록한다. 실패면 그 W의 후행 사용 가능을 막는다. 제출된 증거를 고치지 않는다.
  - TEST 판정자(test-agent, 테스트 작성과 다른 디스패치): 모든 행의 판정 결과를 기록한다. 제출된 증거를 고치지 않는다.
  - PM·도구: 명세 잠금, 소유권 이관, 예외 계획 승인, 조건부 완료 승인, 사후 검증 승인, 테스트 리비전 변경에 따른 증거 무효화, W의 후행 사용 가능 상태 갱신 같은 상태 기록을 소유한다.
- 하나의 시나리오 행이 여러 W에 연결되면, 단일 writer를 지정할지 증거를 덧붙이기만 하는 기록(append-only)으로 둘지 T3 PLAN에서 정한다.

### 4.5 설계(PLAN) 변경

## 5. 속도 개선과 품질 유지

### 5.1 속도 개선

- **단위를 개발 단계로 앞당긴다(가장 큰 효과)**: 로직 결함이 EXECUTE 루프 안에서 바로 고쳐져 TEST에 남는 결함이 주로 경계를 넘는 흐름 결함이 된다. 다만 독립 단언 대조를 TEST로 미룬 W의 테스트 결함·누락은 TEST에서 드러날 수 있다. TEST 수정 반복(fix → 재실행)이 줄어든다.
- **구현-테스트 내부 루프**: 구현 → 테스트 실행 → 재구현이 execute-agent 디스패치 한 번 안에서 반복되므로, 실패할 때마다 PM 판단과 새 디스패치를 거치지 않는다. PM 개입은 테스트 수정·계약 충돌·원인 불명·상한 도달로 한정된다(§4.2).
- **W 단위 병렬 파이프라인**: 선행 계약이 준비된 W부터 테스트 작성이 시작되고, 테스트 작성과 다른 W의 구현이 겹쳐 진행된다. 직렬 RED-first보다 벽시계 시간이 줄 것이라는 가설이며, 측정 전에는 확정하지 않는다. 대신 에이전트 호출과 빌드 대기가 늘 수 있으므로 효과는 §8 전체 시간으로 판단한다.
- **통합은 필요한 경우에만**: 단위로 증명되는 AC는 통합 행을 만들지 않아 시나리오 수와 TEST 시간이 준다.
- **시나리오 작성 분량 축소**: 단위 행은 통과 기준만 적는다. 계산·규칙 로직이 많은 태스크일수록 크게 줄고, 통합 흐름이 많은 태스크(예: pug 015)는 적게 준다. 문서가 짧아지면 설계 게이트 평가자의 판정 분량도 준다.
- **구조·형식 검사 전용 변경은 test-agent 생략**: 생략 자격은 PM이 아니라 도구가 판정한다. 자격 조건은 셋 다 충족해야 한다.
  - 모든 행의 검증 방식이 사전 허용된 구조·형식 검사(결정론 검사)이고 판정이 도구 종료 코드다.
  - 동작 테스트가 한 건도 없다. 단위 테스트 코드 행이 있으면 독립 단언 대조가 필요하므로 자격이 없다.
  - 이번 작업이 검사기 자체(검사 도구·검사 규칙)를 바꾸지 않았고, 실행 계약을 바꾸는 문서(파일럿·하네스·에이전트 규칙)를 바꾸지 않았다.
  - 자격이 있으면 도구 실행 기록을 증거로 TEST 행을 통과시킨다. 이는 "TEST 실행·판정은 서브에이전트"(`actor.md` §독립 검증 경계)를 바꾸는 일이므로, 자격 판정 도구와 함께 그 문서를 고친다.
- **이미 있는 장치의 효과가 커진다**: 사람 조치 일괄 선요청, 독립 시나리오 동시 실행, EXECUTE 증거 재사용(같은 커밋 SHA·명령·환경 서명·증거 경로이고, 작업본이 dirty면 변경 파일 해시까지 같을 때만 다시 돌리지 않음), 수정 영향 범위만 재실행(`test-cycle.md`)은 단위 증거가 확실해질수록 효과가 커진다.

### 5.2 품질 유지 장치

- 통과 기준은 구현자가 아닌 PM이 구현 전에 잠근다.
- 모든 단위 테스트는 test-agent가 쓰고 execute-agent가 구현한다. 작성자와 구현자를 분리해 구현에 맞춘 테스트가 생길 위험을 줄인다. 분리만으로 보장되지는 않으므로 TEST에서 통과 기준과의 독립 대조를 함께 둔다.
- `RED 필수` 행은 유효한 RED(단언 실패 또는 미구현 표지)와 그 시점 해시가 있어야 구현 디스패치가 열린다. 예외는 사전 승인된 탐색형 W와 PM 승인 사후 검증 행뿐이며(§4.2), 둘 다 TEST 독립 판정은 면제되지 않는다.
- RED 이후 테스트는 동결되고, 수정은 PM 판정과 테스트 리비전 절차(증거 무효화·구현 전 기준점에서 RED 재관찰)를 거친다.
- TEST에서 별도 디스패치된 test-agent가 단위 테스트의 단언과 통과 기준을 대조한다.
- 통합은 test-agent가 판정하며, PM이 실행한 경우에도 판정은 분리한다.
- mock 대체는 조건부 완료로만 보고한다.
- 테스트 파일도 컨벤션 검사 대상에 포함한다(§6.3).

## 6. 테스트 환경·규칙·교본

### 6.1 요소별 테스트 환경 (`.opal/test-tools.yaml`)

- **생성**: opi가 프로젝트를 초기화할 때 `docs/PROJECT.md` 프로젝트 구성 표의 요소(경로)마다 테스트 환경을 만든다. 각 저장소 루트를 검사해 후보를 채우고, 사용자 확인 후 기록한다. 검사 대상은 빌드 파일(Gradle·Maven·`package.json`·`pyproject`·Xcode), 테스트 의존성(Kotest·JUnit·vitest·jest·pytest), 잠금 파일(bun·pnpm·npm), test 스크립트다.
- **항목**: 요소 경로, 스택, 테스트 프레임워크, 단위·통합 실행 명령과 실행 위치, 테스트 규칙 문서 경로(`conventions`), 형식 규칙(테스트 위치·파일 이름 패턴), 참고 교본, "러너 없음" 명시.
- **사용**: `test-tool`이 요소 단위로 해석한다. 판정 순서는 요소 선언 → (없으면) 요소 루트 직접 검사(출처 "검사 추정" 표시) → 런타임 내장 러너 후보(`bun test`·`node --test`, 순수 로직 단위 테스트 전용으로 표시) → 러너 없음(`no_test_runner` 명시 반환)이다. 전역 템플릿은 판정 기준에서 빼고 도구 설치 안내용으로만 쓴다.
- **일치 검사**: 판정 결과가 PROJECT.md 구성 표의 스택과 다르면(예: Kotlin 요소에 vitest) 진행하지 않고 막는다.
- **러너 없는 요소**: pug `frontend`·`frontend_app`, mams 프론트 3종처럼 러너가 없는 요소는 "check만 허용" 여부를 프로젝트 설정으로 명시한다. 이 설정은 형식·구조 요구에만 적용되고, 동작 AC는 §3.6의 폴백 순서(내장 러너 → 통합 흐름 → 사용자 결정)를 따른다.
- 멀티 저장소 워크트리에서도 요소 경로가 허브 구조와 같으므로(`harness/worktree.md` §slot root 배치) 같은 상대 경로로 판정한다.

### 6.2 테스트 작성 기준 — 주변 스타일 우선

PM은 테스트를 쓰거나 테스트를 통과시키는 워커에게 대상 요소의 구성 표 행, 저장소 규칙 문서 경로, 언어 색인 경로(§6.4)를 디스패치 때 명시적으로 넘긴다. 워커는 §6.4의 "코드 작성 순서"를 따른다: 주변 코드 관찰·적용 → 저장소 규칙 문서와 안티패턴으로 문제 판정 → 문제일 때만 교본 참고.

### 6.3 테스트 코드 검사

- **결정론 검사**: 새 테스트 파일이 선언된 위치·이름 패턴·프레임워크를 따르는지, 단언이 없는 빈 테스트가 아닌지 확인한다.
- **독립 검사**: 컨벤션 검사(`op-gc-convention`) 대상에 테스트 파일을 넣고, 규칙 문서는 허브 링크 대신 요소 선언에서 직접 넘긴다. 최종 TEST Gate의 "Critical/High 0건"이 테스트 파일에도 적용된다.

### 6.4 언어별 교본

**코드 작성 순서 — 주변 스타일 먼저, 문제가 있을 때만 교본**

구현 워커와 test-agent는 코드·테스트를 쓸 때 아래 순서를 따른다.

1. **주변 관찰**: 같은 패키지·모듈의 소스와 같은 종류의 기존 테스트를 읽는다(권장 상한: 소스 2~3개, 테스트 1~2개. 같은 디스패치에서 이미 본 파일은 다시 읽지 않는다). 이름 짓기, 구조, 오류 처리, 의존성 주입, 테스트 프레임워크·스펙 형식, mock 사용법을 본다.
2. **대조 (항상)**: 적용하기 전에 저장소 규칙 문서와 언어 색인의 안티패턴 요약으로 주변 스타일을 대조한다. 이 둘은 문제가 있을 때만 읽는 교본 원문과 달리 매번 확인한다.
3. **적용 또는 문제 판정**: 문제가 없으면 주변 스타일 그대로 쓴다. 아래 중 하나면 "문제 있음"이다. 판정 기준은 주관이 아니라 문서와 목록이다.
   - 저장소 규칙 문서와 어긋난다(예: pug `backend/docs/claude/rules/*.md`). 규칙 문서 경로는 요소 선언(`test-tools.yaml`)의 `conventions`가 가리킨다.
   - 언어 색인의 안티패턴 목록에 해당한다.
   - 버그 위험이 있다(테스트의 sleep 대기, 테스트 간 공유 상태, 예외 삼킴).
   - 참고할 주변 코드가 없다(새 모듈, 첫 테스트).
4. **교본 참고**: 문제가 있을 때만 언어 색인에서 해당 절을 찾아 그 줄 범위만 읽고 적용한다. 적용 범위는 이번 변경 파일 안이다. 주변 기존 코드는 고치지 않고 결과에 "개선 후보"로 보고한다.
5. **출처 기록**: 결과에 적용한 스타일의 출처(주변 파일 경로, 규칙 문서, 교본 절)를 적는다. 독립 판정자가 확인한다(§4.2 조기 단언 대조, §4 5단계 TEST 단언 대조).

**언어별 교본과 색인 — 평소에는 색인만 읽는다**

교본 원문은 길다(예: ECC `kotlin-testing` 825줄, `python-testing` 817줄). 매번 읽지 않도록 스킬이 언어별 색인을 관리한다.

```
op-dev-execute/references/guides/
  INDEX.md            언어 → 색인 경로, 사용법 (1쪽)
  kotlin/INDEX.md     색인: 교본별 목차·줄 범위·언제 읽나·빼고 볼 절·안티패턴 요약
  kotlin/<교본>.md    원문 (ECC 커밋 고정본, MIT 고지)
  typescript/ …       같은 구성
  python/ …
  sql/ …
  common/ …           언어 무관
opal-test-agent/references/
  INDEX.md            판정용 교본 색인 (AI 회귀 패턴, 통합·E2E)
  <교본>.md
```

언어 색인 예시(`guides/kotlin/INDEX.md`):

```
# Kotlin 교본 색인
사용법: 평소에는 이 색인만 읽는다. 2단계(대조)는 아래 안티패턴 요약으로 매번 한다.
        4단계(교본 참고)에서만 표의 줄 범위를 Read(offset/limit)로 읽는다. "읽지 않음" 절은 읽지 않는다.
우선순위: 저장소 규칙 > 주변 코드 > 이 교본

| 교본 | 절 | 줄 | 언제 읽나 |
|---|---|---|---|
| kotlin-testing | Kotest 스펙 스타일 | 31-120 | 첫 테스트, 스펙 형식이 섞여 있을 때 |
| kotlin-testing | MockK | … | mock 방식이 규칙과 다를 때 |
| kotlin-testing | 코루틴 테스트 | … | runBlocking·sleep으로 기다릴 때 |
| kotlin-testing | Kover 커버리지 | … | 읽지 않음 (OPAL 소유) |
| kotlin-patterns | … | … | … |

안티패턴 요약 (3단계 판정 기준)
- 테스트에서 Thread.sleep·delay로 대기 → runTest·가상 시간
- …
```

- **색인은 도구가 만든다.** 교본 등록 때 원문 제목에서 절과 줄 범위를 뽑아 색인 뼈대를 만들고, 사람이 "언제 읽나"·"읽지 않음"·안티패턴 요약을 채운다. 원문은 커밋에 고정하므로 줄 범위가 바뀌지 않는다. 원문을 갱신하면 색인을 다시 만들고 메모를 다시 검토한다.
- **크기 상한**: 언어 색인은 2KB 안팎, 최상위 `INDEX.md`는 1KB 안팎. 넘으면 교본 수를 줄이거나 절을 묶는다.
- **연결**: 최상위 `INDEX.md`는 언어 색인과 `common/` 색인을 함께 가리키고, `opal-test-agent/references/INDEX.md`(판정용)는 test-agent 디스패치에만 주입한다.
- **선택**: 요소 선언(`test-tools.yaml`)의 언어로 색인을 고른다. PM은 디스패치할 때 요소의 언어 색인 경로만 넘기고, 원문 경로는 넘기지 않는다. 자동 활성화(트리거)에 기대지 않는다.
- **공유**: 구현 워커와 test-agent는 같은 사본을 쓴다. test-agent는 조기 단언 대조와 TEST 단언 대조에서 같은 색인으로 단언·스타일을 판정한다.
- **출처**: `affaan-m/ECC`(MIT). 로컬 확인본 커밋 `c70874fa`(2026-09-29). `ceo4ever/ECC` fork는 원본보다 커밋 221개 뒤처져 있으므로(2026-10-01 GitHub compare) 원본 커밋에 고정한다. 교본별 상단에 출처·커밋·라이선스 고지를 둔다.

## 7. ECC와의 비교 요약

- **가져오는 것**: 모든 동작 작업은 테스트 작성을 거쳐야 완료, 테스트 우선(실패 확인 후 구현 — 단 OPAL은 테스트 작성자와 구현자를 분리), 증거 대응표, 스택별 실행 정보, 언어별 교본.
- **OPAL이 유지하는 것**: 통과 기준은 PM이 구현 전에 잠금(ECC는 구현 에이전트가 직접 정함), 통합의 독립 실행·판정, 설계 게이트와 평가자의 분류 검사, 모든 단위 테스트의 작성자(test-agent)·구현자(execute-agent) 분리.
- **가져오지 않는 것**: 전역 커버리지 80% 목표, Playwright만 E2E로 보는 전제, 통합까지 같은 에이전트가 검증하는 방식, 모델 판단에 맡긴 교본 자동 활성화.

## 8. 측정

opst에 이미 있는 단계별 소요 시간(`phase_min`), 비용, 게이트 반복 수에 다음을 더해 적용 전후를 비교한다.

- **전체 소요 시간과 비용**(TEST만이 아니라 설계·EXECUTE·TEST·CLOSE 합계). EXECUTE에 테스트 우선 작성 비용이 새로 더해지므로, TEST 단축만으로 속도 개선을 판단하지 않는다.
- TEST 수정 반복 횟수
- 파이프라인 구성 시간: 계약 기반 준비 시간, 에이전트 호출 수·비용, 빌드·실행 대기 시간, 재작업(테스트 수정·계약 변경) 횟수 — 고정 풀 시범(§4.2 도입 방식)의 확대 판단 근거
- 동작 AC 중 실제 테스트 코드로 증명된 비율
- 설계 구간(TEST-SCENARIO 작성 + 설계 게이트) 소요 시간
- 구현-테스트 루프 지표: W당 내부·외부 반복 수, 실패 원인 분포(구현 결함·테스트 문제·계약 충돌·원인 불명), PM 개입 횟수, W별 대기(테스트 선행·구현 선행) 시간
- 숨은 인수 테스트 통과율(품질 유지 확인)

Kotlin 백엔드 시나리오는 opst 카탈로그에 없으므로, storelink6와 같은 구조(Gradle·Kotest·MockK)의 모의 저장소로 시나리오를 하나 추가한다.

## 9. 구현 단계 (태스크 분할)

이 범위는 하네스 규칙 4종(red-first·test-cycle·actor·design-gate), 도구 3종(test-tool·state-tool 설계 게이트·opst), 스킬·에이전트 6종 이상(op-dev-test-scenario·op-dev-execute·opal-test-agent·opi·op-scenario-gate·평가자)을 바꾸므로 **태스크 하나로는 크다**. 다음 4개로 나눈다.

1. **T1 시나리오·PLAN 계약과 게이트**: 계층 정의, 시나리오 행 형식, 통합 주체와 PM 대행 경계, 문서 구현 대응, PLAN Work items 형식 변경(§4.5: 유형·단계별 writer·테스트 선행·실행 그룹 의미 변경, `op-dev-plan`·`plan-guide`·`opal-plan-agent`), 설계 게이트 결정론 검사와 평가자 분류 축.
2. **T2 요소별 테스트 환경**: `test-tools.yaml` 요소 선언 스키마, opi 생성(검사 → 확인 → 기록), `test-tool` 요소 해석과 루트 검사 폴백, 스택 일치 차단, 러너 없음 정책.
3. **T3 단위 테스트 책임과 증거**: 최소 계약 기반 분류(§4.1), W 단위 테스트 우선 파이프라인(§4.2: test-agent 테스트·선언 작성, 미구현 표지 RED 판별, W 유형별 디스패치 조건표의 도구 확인, W 상태 두 단계(후행 사용 가능·최종 검증 완료), 사후 검증 행 승인 기록, 소유권 이관, 실행 격리, 실패 처리·테스트 리비전·무효화 규칙, 탐색형 W, 고정 풀 시범), 구현-테스트 루프의 경로별 상태 전이·실패 분류·유형별 상한과 W 외부 반복 카운터·고위험 조기 대조 게이트, `opal-pilot-dev` STEP 4의 준비 상태 기반 진행과 `state-tool` W 준비 상태·소유권·재개 계약(§4.5), `op-dev-execute`·`opal-test-agent`·RED-first 규칙 문서 개정(BE 모드 모순 해소 포함), TEST 진입 조건과 단언 대조, 검사만 있는 태스크의 test-agent 생략, 테스트 규칙 주입(§6.2)과 테스트 파일 컨벤션 검사. 회귀 검증에는 부정 테스트를 포함한다: 경로별 예외 진입(선언·검사, 탐색형, 사후 검증 행), 고위험 조기 대조 미실행·실패 시 후행 사용 가능 거부, 테스트 리비전 변경 시 증거·판정 무효화, 세션 재개 뒤 유형별 상한·외부 반복 카운터 보존.
4. **T4 교본 등록과 측정**: 언어별 교본 원문(커밋 고정본) 등록과 색인(목차·줄 범위·언제 읽나·읽지 않음·안티패턴 요약), 색인 뼈대 생성 도구, `coding-principles.md` §4의 코드 작성 순서(주변 스타일 우선), opi의 요소 언어 확정, opst 지표 추가와 Kotlin 시나리오.

순서는 T1 → T2 → T3 → T4를 권한다. T1과 T2는 서로 다른 파일을 고치므로 병행할 수 있다. T3는 T1(행 형식)과 T2(실행 환경)를 소비한다. 잠금 모델 분리와 증거 기록 동시성(§4.3·§4.4)은 `test-tool` 시나리오 계약을 바꾸므로 T3에 포함한다.

### 9.1 단계별 설치의 안전성 — 버전·구형 태스크·활성화 시점

T1~T4는 서로 다른 시점에 설치되므로, 중간 상태에서 진행 중인 태스크가 깨지지 않게 한다.

- **계약 버전**: 새 시나리오 계약(세 축 행 형식, 잠금 모델, 완료 상태)에 버전을 둔다. 태스크는 `state init` 시점의 계약 버전을 `state.json`에 기록하고, 재개할 때 그 버전을 상속한다.
- **구형 태스크**: 계약 버전이 없거나 구버전인 태스크는 기존 규칙(단일 `locked`, 기존 `유형` 열, 기존 TEST 판정)으로 끝까지 진행한다. 새 게이트 검사를 소급 적용하지 않는다.
- **도구의 이중 지원**: T1·T3가 바꾸는 도구(설계 게이트 검사, `test-tool` 시나리오 명령)는 전환 기간 동안 구버전과 신버전 계약을 모두 받는다. 형식은 기록된 계약 버전으로 가르며 추측하지 않는다.
- **버전 해석 규칙**: 계약 버전이 없으면 구버전(legacy)으로 처리한다. 설치본이 지원하지 않는 버전(알 수 없는 미래 버전 포함)은 legacy로 대신 처리하지 않고 명시적으로 거부한다.
- **활성화 시점**: 신규 태스크의 기본 계약 버전은 T1~T3가 모두 설치된 뒤에 신버전으로 바꾼다. 활성화는 날짜가 아니라 능력 확인으로 정한다. 설계 게이트·`test-tool`·관련 스킬과 에이전트(소비자)가 각자 지원하는 계약 버전을 보고하고, 모두 신버전을 지원할 때만 신규 기본값을 바꾼다. 그 전에는 신버전을 명시적으로 선택하더라도, 지원하지 않는 구성 요소가 있으면 시작 시점에 거부한다. T1만 설치된 상태에서 잠금·증거를 소비하는 T3 기능이 없는데 신버전으로 진행되는 일을 막기 위해서다.

## 10. 위험

- **PM 조율 부담**: W 수만큼 루프가 동시에 돈다. 구현 디스패치 조건을 도구가 확인하고, 명백한 구현 결함은 execute-agent가 스스로 고치게 해 PM 개입을 테스트 수정·계약 충돌·원인 불명으로 좁힌다. 고정 풀 시범으로 부담을 먼저 측정한다.
- **테스트 수정 뒤 거짓 증거**: 고친 테스트가 기존 RED·GREEN 증거를 이어받으면 관찰하지 않은 RED로 구현·완료가 열린다. 증거를 테스트 리비전에 묶고, 수정 시 원자 무효화와 구현 전 기준점 재관찰을 요구한다(§4.2).
- **계약 기반 설계 오류**: 계약이 틀리면 의존 W가 한꺼번에 영향을 받는다. 공개 계약 변경은 영향 W 중단과 PLAN 재검토로, 내부 수정은 영향 테스트 재실행으로 처리하고, 증거는 영향 범위만 무효화한다.
- **실행 간섭**: 병렬 실행 중 다른 워커의 소스 수정이 테스트 결과를 오염시킬 수 있다. 실행 입력 동결·스냅샷 격리와 입력 해시 기록으로 막는다.
- **비용 증가**: W마다 test-agent 호출이 더해진다. 벽시계 시간은 줄어도 토큰 비용은 늘 수 있으므로 §8 전체 비용으로 판단한다.
- **엄격한 게이트로 인한 차단**: 러너 없는 요소의 태스크가 막힐 수 있다. 형식·구조 요구는 요소별 "check만 허용" 설정으로, 동작 AC는 런타임 내장 러너와 통합 흐름 실행 폴백(§3.6)으로 차단을 줄이고, 그래도 수단이 없을 때만 사용자 결정으로 올린다.
- **PM 대행의 남용**: 대행 범위를 dev·되돌릴 수 있는 조작으로 한정하고, 시나리오 사전 선언과 보고 표시를 강제한다.
- **독립 검증 경계 변경**: test-agent 생략은 도구가 판정한 구조·형식 검사 전용 변경으로 한정한다. 동작 테스트가 있거나, 검사기 자체나 실행 계약 문서를 바꾼 작업은 제외한다(§5.1).
- **병렬 증거 기록의 유실**: 시나리오 기록을 파일 잠금 + 원자 쓰기로 바꾸고 역할별 쓰기 권한을 둔다(§4.4).
- **교본과 원본의 어긋남**: 커밋 고정본과 색인을 한 쌍으로 관리하고, 고정본을 갱신할 때 색인을 다시 만들고 메모를 다시 검토한다.
- **나쁜 주변 스타일 확산**: 주변 코드를 먼저 따르므로 나쁜 패턴이 퍼질 수 있다. 저장소 규칙 문서와 안티패턴 목록으로 문제를 판정하고, 적용 출처를 기록해 독립 판정에서 확인한다.
