# OPPL 빠른 프로젝트 완수 구조 개선 제안서

> 상태: 제안
> 작성: 알투(PM)
> 작성일: 2026-09-13
> 목적: 프로젝트 관리와 태스크 실행 관리를 하나의 지속 가능한 실행 구조로 결합하고, 공통 단계와 검증의 중복을 제거해 프로젝트 규모의 업무를 빠르고 안전하게 완수한다.

---

## 1. 결론

OPPL을 대화 안에서 하위 에이전트를 계속 깨우는 중첩 루프가 아니라, 저장된 상태를 기준으로
프로젝트 전체를 수렴시키는 외부 제어 루프로 개편한다. 각 태스크의 설계·구현·검증은 OPD가
사용하는 절차를 공용 태스크 실행 계약으로 분리해 담당한다.

OPPL이 OPD 파일럿을 명령 단위로 다시 호출하지는 않는다. 파일럿을 중첩하면 태스크 생성,
문서 로딩, 상태 초기화, 게이트와 전체 검증이 이중화되기 때문이다. 대신 단일 태스크용 `/opd`와
프로젝트용 실행기가 같은 태스크 실행 계약을 소비한다.

개편 후 역할은 다음과 같다.

| 계층 | 책임 | 하지 않는 일 |
|---|---|---|
| 프로젝트 제어 루프 | 목표·백로그·의존성·우선순위·전체 예산·배치·통합 완료 관리 | 개별 태스크의 구현 세부 지휘 |
| 공용 태스크 실행 | 한 태스크의 범위 확인·설계·구현·영향 검증·결과 반환 | 프로젝트 백로그와 다른 태스크 상태 변경 |
| 검증 조정 | 변경·태스크·배치·프로젝트 수준의 검사 시점 결정과 결과 재사용 | 같은 입력의 동일 검사를 반복 실행 |
| 실행 기록 | 작업·시도·대기·예산·검증·종료 상태의 기계 기록 | 수기 요약을 판정 원천으로 사용 |

이 구조는 “여러 태스크를 차례로 실행”하는 기능이 아니다. 프로젝트로 묶었기 때문에 공통 설계와
환경 준비를 한 번만 수행하고, 독립 작업을 함께 실행하며, 전체 회귀와 심층 보안 검사를 적절한
경계에서 한 번만 수행하는 것이 핵심이다.

## 2. 문제

### 2.1 현재 OPPL의 실행 단위가 지나치게 무겁다

현재 OPPL은 백로그의 모든 태스크에 동일한 T1~T5+G 파이프라인을 적용한다. 작은 변경도 계획,
테스트 시나리오, 명세 심사, 구현, 별도 테스트, 규칙 검사를 모두 거친다. 프로젝트 공통 맥락과
검증 기준도 각 태스크 프롬프트에 반복 주입된다.

태스크 123은 Phase 0~1C, 공용 기록 코어, 상태 도구, 10개 표준 파이프라인, 어댑터, 대시보드와
하네스를 하나의 상위 범위에 포함했다(`tasks/123-260912-oppl-태스크-실행로그-표준화/TASK.md`).
백로그 16개 중 초기 5개를 처리하는 데 약 11시간이 걸렸고, T03 구현 단계는 동일 컨텍스트로
여섯 번 재개됐다. 이는 개별 워커 성능보다 실행 구조와 범위 제어의 문제다.

### 2.2 대화 재개가 작업 스케줄러 역할을 대신한다

장시간 실행은 백그라운드 프로세스로 보내고 종료 파일을 나중에 확인한다. 명시적인 실행 중 상태,
자식 작업 수명주기와 완료 사건이 없으므로 PM이 대화를 재개해 진행을 확인한다. 재촉은 동일 감시
루프를 중복 생성할 수 있고, 긴 대화가 그대로 이어져 입력 컨텍스트가 계속 커진다.

### 2.3 결과 스트림과 프로세스 수명주기가 분리돼 있다

현재 비동기 결과 판정은 스트림의 마지막 줄이 결과인지 확인한다. 결과 뒤에 자식 작업 알림이 오면
정상 작업도 실패가 된다. 반대로 스트림 어디에든 결과가 있으면 성공으로 바꾸는 것도 중간 상태를
완료로 오인하므로 해결책이 아니다.

프로세스 종료, 살아 있는 자식 작업, 최종 결과와 종료 코드를 하나의 상태 전이로 다뤄야 한다.

### 2.4 검증과 보안 검사가 잘못된 경계에서 반복된다

구현 보정마다 영향 테스트와 전체 회귀가 함께 실행되고, 별도 테스트 단계에서 다시 실행된다.
보안 검사는 앞 태스크의 방어를 재사용하지 못한 새 경로를 찾아내는 데 효과가 있었지만, 모든
변경에 동일한 심층 검사를 반복하면 비용이 커진다.

검사를 뒤로 미루는 것이 아니라 검사 깊이와 실행 경계를 나눠야 한다.

### 2.5 문서상 상한이 실행 상한이 아니다

재시도, 무진전, 컨텍스트 압축과 예산 원칙이 문서에 있으나 실제 디스패치 차단으로 연결되지 않는다.
태스크 123에서는 동일 컨텍스트 재개 제한을 넘어서도 실행이 계속됐고, 대행 일지의 요약은 본문과
불일치했다. 사람이 기억해서 지키는 규칙은 프로젝트 규모에서 지속되지 않는다.

## 3. 목표와 제외 범위

### 3.1 목표

1. 프로젝트 목표부터 최종 통합 완료까지 하나의 상태로 복원 가능하게 관리한다.
2. 프로젝트 공통 분석·설계·환경·방어·검증 기준은 한 번만 확정한다.
3. 각 태스크에는 공통 맥락 전체가 아니라 해당 태스크의 차이와 필요한 참조만 전달한다.
4. 독립 태스크는 충돌 검증 후 같은 실행 배치에서 병렬 처리한다.
5. 수정 중에는 빠른 영향 검사를, 배치와 프로젝트 경계에서는 통합 검사를 수행한다.
6. 같은 입력과 환경에서 이미 통과한 검증은 다시 실행하지 않는다.
7. 대화 세션이 종료되거나 바뀌어도 저장된 상태만으로 정확히 재개한다.
8. 재시도·비용·시간·무진전 상한을 도구가 집행한다.
9. 워커 완료 선언이 아니라 프로세스와 자식 작업을 포함한 기계 증거로 완료를 판정한다.
10. 프로젝트 규모 업무의 속도와 품질을 단일 태스크 반복 실행보다 측정 가능하게 개선한다.

### 3.2 제외 범위

- 특정 모델의 응답 속도 자체 개선
- 무제한 병렬 실행
- 사용자 승인 없는 프로젝트 범위 변경
- 검증이나 보안 검사의 단순 생략
- `/opd`와 `/oppd`가 각각 별도의 태스크 실행 규칙을 유지하는 구조
- 태스크 123의 제품 기능과 남은 Phase 1B·1C 구현
- 대화 전문을 장기 실행 상태로 사용하는 방식

## 4. 제안 구조

### 4.1 전체 흐름

```text
프로젝트 요청
  ↓
프로젝트 계약 확정
목표 · 범위 · 완료조건 · 공통 제약 · 전체 예산
  ↓
백로그와 의존성 그래프
  ↓
실행 가능한 태스크 묶음 선택
  ↓
공용 태스크 실행 계약으로 순차·병렬 실행
  ↓
배치 통합 검증
  ├─ 태스크 내부 결함 → 해당 태스크만 재투입
  ├─ 태스크 경계 결함 → 백로그 재분할
  ├─ 프로젝트 계약 변경 → 사용자 결정
  └─ 통과 → 다음 실행 묶음
  ↓
프로젝트 전체 완료조건 검사
  ├─ 미충족 → 남은 작업 재투입
  └─ 충족 → 사용자 CLOSE 확인
```

### 4.2 프로젝트 제어 루프

프로젝트 제어 루프는 다음 정보만 소유한다.

- 프로젝트 목표와 최종 완료조건
- 백로그 항목, 의존성, 우선순위와 담당 표면
- 프로젝트 공통 컨텍스트 묶음
- 실행 준비가 끝난 태스크 목록
- 태스크 간 변경 충돌과 통합 순서
- 태스크·배치·프로젝트 예산
- 배치 통합 결과와 잔여 위험

한 회전은 “태스크 하나를 완주”가 아니라 “현재 실행 가능한 태스크 묶음을 실행하고 프로젝트
완료조건에 가까워졌는지 판정”하는 단위다. 완료조건에 기여한 변화가 없는 회전이 반복되면 더 큰
모델이나 추가 재촉이 아니라 태스크 분할 또는 사용자 에스컬레이션으로 전환한다.

### 4.3 공용 태스크 실행 계약

공용 태스크 실행 계약은 `/opd`의 단일 태스크 절차에서 추출한다. 프로젝트 제어 루프와 `/opd`가
같은 계약을 사용하며, 어느 쪽도 상대 파일럿을 명령으로 중첩 호출하지 않는다.

입력은 다음으로 제한한다.

- 태스크 목표와 수용 시나리오
- 허용된 변경 범위
- 관련 프로젝트 계약과 문서의 필요한 부분
- 선행 태스크가 확정한 인터페이스와 방어 목록
- 영향 검사와 종료 검증 명령
- 태스크 시간·비용·재시도 예산

결과는 다음 중 하나다.

| 결과 | 의미 | 프로젝트 제어 루프의 처리 |
|---|---|---|
| 완료 | 수용 시나리오와 영향 검증 통과 | 배치 통합 대상으로 편입 |
| 진행 중 | 프로세스 또는 자식 작업이 실행 중 | 재디스패치 없이 감시 |
| 대기 | 사람·외부 시스템·승인 필요 | 대기 이유와 재개 조건 노출 |
| 재분할 필요 | 태스크 범위 안에서 해결 불가 | 백로그 경계 재설계 |
| 실패 | 예산·재시도 초과 또는 복구 불가 | 원인과 마지막 증거를 보존하고 중단 |

태스크 실행기는 다른 태스크의 상태를 바꾸지 않으며, 프로젝트 제어 루프만 백로그 전이를 수행한다.

### 4.4 실행 수명주기

모든 워커 시도는 시작, 실행 중, 자식 대기, 완료, 실패, 시간 초과를 기계 상태로 가진다.

완료는 다음 세 조건의 결합으로만 인정한다.

1. 실행 프로세스가 종료됨
2. 추적 중인 자식 작업이 모두 종료됨
3. 최종 결과와 프로세스 종료 코드가 성공 계약을 만족함

결과가 있으나 자식 작업이 살아 있으면 진행 중이다. 자식 작업 알림이 결과 뒤에 도착해도 실패로
바뀌지 않는다. 출력이 전혀 없는 프로세스도 독립 watchdog이 제한 시간을 집행한다.

같은 컨텍스트의 비정상 재개는 한 번만 허용한다. 같은 지점에서 다시 실패하면 기존 산출물과 실패
증거를 요약해 새 컨텍스트에 남은 작업만 전달한다.

## 5. 빠른 실행 전략

### 5.1 프로젝트 공통 작업의 단일 수행

다음은 프로젝트 시작 또는 관련 계약 변경 시에만 수행한다.

- 목표·범위·완료조건 확정
- 프로젝트 구조와 표면 분석
- 공통 개발·검증 환경 확인
- 전체 테스트 기준선 수집
- 공통 보안 경계와 기존 방어 목록 확정
- 문서와 코드의 공통 참조 묶음 생성
- 태스크 의존성과 충돌 그래프 계산

각 태스크는 이 결과를 참조하고 자신의 차이만 설계한다. 태스크마다 PRD·TRD 전체를 다시 해석하거나
같은 기준선을 재수집하지 않는다.

### 5.2 적응형 태스크 깊이

| 등급 | 적용 조건 | 필수 과정 |
|---|---|---|
| 초소형 | 문서·상수·국소 수정, 계약 영향 없음 | 범위 확인 → 수정 → 영향 검사 |
| 소형 | 단일 모듈, 기존 패턴 확장 | 짧은 계획 → 구현 → 단위·회귀 검사 |
| 중형 | 다중 파일 또는 외부 계약 영향 | 설계 → 시나리오 → 구현 → 독립 검증 |
| 대형 | 여러 책임·모듈·수용 시나리오 | 실행 금지, 둘 이상의 태스크로 재분할 |

등급은 모델 크기가 아니라 작업 경계와 위험으로 정한다. 작은 태스크가 무조건 전체 설계 심사와
별도 테스트 에이전트를 거치지 않도록 한다.

### 5.3 실행 배치

의존성이 충족된 태스크 중 변경 파일·모듈·공유 설정·계약 표면이 겹치지 않는 항목을 같은 배치로
선택한다. 충돌 가능성이 있으면 순차 실행한다.

병렬 실행은 속도를 위한 독립 목표가 아니다. 올바른 태스크 분할의 결과로만 허용한다. 병렬 작업의
변경을 통합할 권한과 방식은 사용자 승인 및 Git 규칙을 따른다.

### 5.4 컨텍스트 전달

태스크 프롬프트는 다음 네 부분으로 구성한다.

1. 프로젝트 계약 요약의 고정 참조
2. 해당 태스크의 목표·범위·수용 시나리오
3. 직접 의존하는 선행 태스크의 인터페이스와 방어
4. 직전 시도의 실패 차이와 남은 작업

이전 대화 전문과 모든 프로젝트 문서를 반복 첨부하지 않는다. 각 입력 묶음의 hash를 기록해 어떤
근거로 실행했는지 재현한다.

---

## 6. 검증과 보안의 중복 제거

### 6.1 검증 경계

| 경계 | 검사 대상 | 실행 시점 |
|---|---|---|
| 변경 | 수정한 파일의 정적 검사와 직접 관련 테스트 | 매 수정 후 |
| 태스크 | 수용 시나리오와 영향 범위 회귀 | 태스크 완료 후보 시 1회 |
| 실행 배치 | 태스크 사이 계약·통합 검사 | 배치 결과 통합 후 1회 |
| 프로젝트 | 전체 회귀와 최종 완료조건 | 모든 필수 백로그 완료 후 1회 |

실패 수정 후에는 실패한 계층부터 다시 검사한다. 코드와 테스트 입력, 환경, 의존 버전이 동일하고
앞선 결과가 유효하면 결과를 재사용한다. 전체 회귀는 매 수정마다 실행하지 않는다.

### 6.2 보안 경계

| 수준 | 대상 | 검사 |
|---|---|---|
| 상시 | 모든 태스크 | 기존 보안 회귀·정적 규칙·공용 방어 사용 확인 |
| 위험 기반 | 새 I/O·인증·권한·명령 실행·외부 입력 경로 | 전문 보안 검사와 공격 입력 실증 |
| 프로젝트 | 배치 통합 후 또는 최종 완료 전 | 경계 간 우회와 방어 누락 통합 검사 |

앞 태스크가 만든 방어는 산문 목록만 전달하지 않는다. 공용 함수, 계약 검사와 회귀 테스트를 기본
전달 단위로 사용한다. 새 경로가 공용 방어를 사용하지 않으면 상시 검사에서 즉시 실패해야 한다.

## 7. 예산과 무진전 통제

예산은 프로젝트, 실행 배치, 태스크와 시도 네 수준으로 관리한다.

| 수준 | 관찰 대상 | 초과 시 처리 |
|---|---|---|
| 프로젝트 | 전체 시간·비용·완료율 | 새 배치 시작 중단, 사용자 보고 |
| 실행 배치 | 동시 작업 수·통합 실패 횟수 | 병렬 축소 또는 순차 전환 |
| 태스크 | 시간·비용·워커 호출 수 | 재분할 또는 차단 |
| 시도 | 제한 시간·무출력 시간·컨텍스트 크기 | 종료 후 증거 보존 |

진전은 다음 중 하나가 있을 때만 인정한다.

- 수용 시나리오가 실패에서 통과로 전이
- 미해결 blocker 감소
- 구현 또는 테스트 산출물의 검증 가능한 변화
- 프로젝트 완료조건의 미충족 항목 감소

같은 실패, 같은 산출물, 같은 검증 결과를 반복하면 진전이 아니다. 같은 지점에서 두 번 진전이
없으면 자동 재촉이나 동일 컨텍스트 재개를 중단한다.

---

## 8. 상태와 관측

판정 원천은 `backlog.json`, `state.json`, `test-scenario.json`과 표준 실행 로그다. 사람이 읽는
Markdown 표는 이 원천에서 생성하며, 수기 요약은 완료조건에 사용하지 않는다.

프로젝트 화면은 최소한 다음을 구분한다.

- 실행 준비 태스크
- 현재 실행 중인 태스크와 자식 작업 수
- 사람 또는 외부 조건을 기다리는 태스크
- 예산 또는 재시도 한도에 걸린 태스크
- 배치 통합 대기 태스크
- 프로젝트 완료조건의 충족률

PM은 실행 중인 작업을 재촉하지 않는다. 상태가 진행 중이면 감시하고, heartbeat 또는 종료 사건이
정해진 시간 동안 없을 때만 watchdog 결과에 따라 처리한다.

---

## 9. OPD·OPPD와의 관계

### 9.1 OPD

`/opd`는 단일 태스크를 수행하는 사용자 진입점으로 유지한다. 내부 설계·구현·검증 절차는 공용
태스크 실행 계약을 사용한다. 프로젝트 제어 기능은 갖지 않는다.

### 9.2 OPPD

OPPD의 재정의는 별도 제안으로 다룬다. 방향은 OPPL의 프로젝트 제어 루프와 공용 태스크 실행 계약을
소비하여 “프로젝트 요청부터 전체 완료까지”를 제공하는 사용자 진입점이다.

OPPL은 수렴과 실행 제어를 소유하는 기반이며, OPPD는 기획·WBS·사용자 게이트를 포함한 제품화된
프로젝트 완수 경험을 소유한다. 양쪽이 별도의 실행 루프를 복제하지 않는다.

### 9.3 기존 loop-action-agent

현재처럼 한 에이전트가 태스크의 전 단계를 디스패치하고 백그라운드 결과를 대화 재개로 수거하는
역할은 제거한다. 공용 태스크 실행 계약의 얇은 어댑터로 축소하거나 호환 기간 뒤 폐지한다.

---

## 10. 단계별 도입

### Phase A — 실행 기반 안정화

1. 프로세스·자식 작업·최종 결과를 결합한 종료 판정
2. 무출력 상황에서도 동작하는 watchdog
3. 진행 중·대기·완료·실패 상태 계약
4. 동일 컨텍스트 재개 상한과 새 컨텍스트 분리
5. 태스크·시도 예산의 기계 집행

Phase A가 끝나기 전에는 OPPL 자체로 나머지 개선을 장시간 자율 실행하지 않는다.

### Phase B — 공용 태스크 실행 계약

1. OPD의 태스크 절차에서 재사용 가능한 실행 계약 추출
2. 입력·결과·실패·재분할 계약 고정
3. 적응형 태스크 깊이 적용
4. 프로젝트 공통 컨텍스트와 태스크 차이 입력 분리

### Phase C — 프로젝트 제어 루프

1. 준비 태스크 묶음 선택
2. 변경 충돌을 고려한 실행 배치
3. 태스크 결과 수집과 프로젝트 상태 전이
4. 무진전·예산·범위 변경 라우팅
5. 배치와 프로젝트 완료조건 판정

### Phase D — 검증 최적화

1. 영향·태스크·배치·프로젝트 검사 분리
2. 동일 검증 결과 재사용
3. 보안 3단 구조 적용
4. 선행 방어의 공용 코드·테스트 승계

### Phase E — 제품 파일럿 연결

1. OPPD 재정의안에서 프로젝트 제어 루프 사용
2. 기존 OPPL과 OPPD의 중복 실행 규칙 제거
3. 실제 프로젝트 기준 성능·품질 비교
4. 호환 어댑터와 폐기 대상 확정

## 11. 수용기준

1. 장시간 태스크가 PM의 재촉 없이 진행 중·대기·완료·실패 중 하나로 관측된다.
2. 결과 뒤에 자식 알림이 도착해도 정상 작업이 실패로 바뀌지 않는다.
3. 자식 작업이 살아 있거나 프로세스가 종료되지 않았으면 완료로 판정되지 않는다.
4. stdout이 없는 워커도 정해진 제한 시간 안에 종료되고 원인이 기록된다.
5. 동일 컨텍스트의 비정상 재개가 한 번을 넘지 않는다.
6. 프로젝트 공통 분석·기준선·방어·환경 확인이 태스크마다 반복되지 않는다.
7. 대형 태스크는 실행 전에 둘 이상의 독립 태스크로 분할된다.
8. 독립 태스크는 충돌 검사 후 같은 배치에서 실행할 수 있다.
9. 같은 입력·코드·환경의 동일 검증이 중복 실행되지 않는다.
10. 전체 회귀는 태스크 수정마다가 아니라 정해진 태스크·배치·프로젝트 경계에서 실행된다.
11. 새 위험 경로는 태스크 단계에서 심층 보안 검사를 받고, 프로젝트 경계에서도 통합 검사를 받는다.
12. 태스크·배치·프로젝트 예산 초과가 추가 디스패치 전에 차단된다.
13. 실패 태스크만 재투입되며 이미 통과한 독립 태스크는 다시 실행되지 않는다.
14. 대화 세션을 바꾼 뒤에도 기계 상태만으로 같은 지점에서 재개된다.
15. 수기 요약이 없어도 프로젝트 진행률과 지연 원인을 재구성할 수 있다.
16. 모든 필수 태스크, 표면 수용 시나리오, 배치 통합, 전체 회귀와 보안 검사가 통과해야 프로젝트가 완료된다.
17. 대표 프로젝트 비교 실행에서 기존 OPPL보다 경과 시간과 모델 입력량이 각각 감소하고 검증 통과율은 낮아지지 않는다.
18. 태스크 123의 중복 감시, 스트림 오판, 과다 재개와 반복 전체 회귀 사례가 회귀 시나리오로 재현되고 수정 후 통과한다.

## 12. 성능 평가 기준

속도 개선은 “호출 수 감소”만으로 판정하지 않는다. 같은 요구사항과 동일한 최종 검증을 기준으로
기존 OPPL과 개선안을 비교한다.

| 지표 | 의미 |
|---|---|
| 전체 경과 시간 | 요청 확정부터 프로젝트 완료 후보까지 걸린 실제 시간 |
| 모델 입력량 | 공통 문서와 이전 대화의 중복 전달 정도 |
| 모델 호출 수 | 계획·재시도·검증·보안 호출 합계 |
| 중복 검증 시간 | 동일 입력과 환경에서 반복된 검사 시간 |
| 수동 개입 수 | 재촉·상태 확인·오탐 판정에 필요한 PM 개입 |
| 재작업 범위 | 실패 한 건으로 다시 실행된 태스크와 검증의 범위 |
| 품질 | 수용 시나리오·전체 회귀·보안 검사 통과율과 사후 결함 |

평가 표본은 작은 독립 태스크 묶음, 공유 모듈을 순차 변경하는 묶음, 외부 I/O와 보안 경계를 포함한
묶음의 세 종류로 구성한다. 태스크 123 기록은 결함 재현 근거로 사용하되 특정 worktree 경로를
평가 도구에 하드코딩하지 않는다.

## 13. 결정이 필요한 항목

1. 프로젝트 제어 루프를 OPPL의 최종 사용자 진입점으로 유지할지, OPPD 내부 기반으로 둘지 결정 필요
2. 공용 태스크 실행 계약의 구현 위치를 기존 OPD에서 추출할지, 별도 실행 컴포넌트로 둘지 결정 필요
3. 프로젝트·태스크별 기본 예산과 사용자가 조정할 수 있는 범위 결정 필요
4. 검증 결과 재사용의 유효 조건에 코드·테스트·환경 외 어떤 값을 포함할지 결정 필요
5. 기존 loop-action-agent의 호환 기간과 제거 조건 결정 필요

이 결정들은 구현 전에 별도 기술 설계에서 확정한다. 본 제안은 프로젝트 관리와 태스크 관리의
책임 경계, 중복 제거 원칙과 완료 판정 구조를 우선 확정한다.
