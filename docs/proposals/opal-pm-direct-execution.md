# OPAL PM 직접 수행 모델 설계 제안서

> 상태: 제안
> 작성일: 2026-09-10
> 범위: PM 직접 수행의 의미, 실행 유형, capability 호출 시점, 완료 후 지식 갱신 계약

---

## 1. 제안 요약

PM 직접 수행을 파일 수나 작업 난이도로 제한되는 경량 예외가 아니라, **PM이 작업의 실행 책임을 갖고 필요한 capability를 직접 선택·호출·검증하는 정식 실행 방식**으로 재정의한다.

직접 수행은 두 유형으로 나눈다.

1. **워크플로우 직접 수행(`direct-workflow`)**: PM이 선택된 pilot의 단계, 상태, 산출물, Gate를 유지하면서 작업을 직접 완주한다.
2. **대화형 직접 수행(`direct-adaptive`)**: PM이 사용자와 대화하며 필요한 분석·설계·구현·검증을 수행하고, 고정 파이프라인 없이 필요한 산출물과 지식을 갱신한다.

두 유형 모두 다음 책임을 공유한다.

- 작업 전 관련 도메인 지식을 선별 조회한다.
- 작업 시점에 맞는 작업 스킬, 범용 스킬, 도구, MCP, 서브에이전트를 호출한다.
- 필요한 capability가 없으면 탐색·설치하거나 스킬 위자드로 생성·등록할 수 있다.
- 실제 실행 증거로 결과를 검증한다.
- 변경된 동작·결정·설계·운영 지식을 docs, 기획·설계 문서, Project Brain, 프로젝트 메모리에 반영한다.

현재의 `L2 경량 트랙`과 파일 수·변경 종류·테스트 필요 여부에 따른 적격 조건은 폐기한다. 작업 규모는 직접 수행 가능 여부를 결정하지 않으며, 사용자에게 필요한 추적성·재현성·상태 관리 수준이 두 유형의 선택 기준이 된다.

## 2. 배경과 현재 계약의 한계

현행 PM 계약은 파일 수정이 없는 분석·설명은 PM이 직접 수행하고, 파일 수정이 수반되면 워커 디스패치와 Gate를 적용한다. 사용자가 “그냥 해” 또는 “직접 수행”이라고 요청한 경우에만 `L2 경량 트랙`으로 파이프라인을 우회한다. 이 경로는 파일 1~2개, 단순 수정, 동작 검증 불요라는 적격 조건을 갖는다(`opal/core/references/opal-pm.md` §12).

### 2.1 현행 L2 계약

이 제안이 대체하는 현행 계약은 다음과 같다. 새 모델로 전환할 때 폐기할 제한과 계속 지킬 품질 규칙을 구분하기 위한 AS-IS 기준선이다.

#### 진입 경로

| 경로 | 현행 동작 |
|---|---|
| 사용자 발화 | “그냥 해” 또는 “직접 수행”이면 즉시 L2에 진입하며, 해당 발화가 실행 허가를 포함한다. |
| PM 자동 감지 | PM이 L2 적격 작업으로 판단하면 경량 처리를 제안하고, 사용자가 수락해야 진입한다. 최종 선택은 사용자에게 있다. |

#### 적격성과 금지 경계

| 판정 | 현행 기준 |
|---|---|
| 적격 | 파일 1~2개, 단순 수정, 동작 검증 불요. 문서·문구·오타·주석·설정값 변경 등이 해당한다. |
| 부적격 | 코드 로직 변경, 파일 3개 이상, 구조·스키마·인터페이스 변경, 다중 영역 변경 |
| 강제 풀 파이프라인 | TEST, TEST-SCENARIO 또는 `verify`가 필요한 작업. 구현자 자체 판단만으로 통과하는 self-confirming 위험을 막기 위한 경계다. |

#### 하네스 적용 범위

| 구분 | 현행 항목 |
|---|---|
| 유지 | Guards, 코드 파일 `@header` 규칙과 갱신 검증, OPAL Tools 우선, Coding Principles |
| 미적용 | 태스크 파이프라인(`TASK → PLAN → EXECUTE`), `STATE.md`, QA·State·PM Gate, Observability, 워커 디스패치 |

“Gate 미적용”은 파이프라인 Gate 3종만 뜻한다. `@header` 갱신 검증은 별도 품질 축이므로 L2에서도 유지된다. L2 종료 선언 전 `git diff --name-only HEAD`와 untracked 파일로 변경 목록을 재구성하고, 코드 파일이 포함되면 `code-scan validate --changed <목록>`을 실행한다(`opal/core/references/harness/header-rules.md` §갱신 시점 (4단) (d)).

L2 직접 수행과 Dev pilot의 `opd↔opds` 트랙 라우팅은 별개 축이다. L2는 파이프라인 적용 여부와 실행 주체를 정하고, `opd↔opds`는 선택된 Dev 파이프라인 내부에서 분석·계약 복잡도에 따라 Full/Short 트랙을 조정한다.

### 2.2 현재 계약의 문제

이 모델에는 네 가지 문제가 있다.

1. **실행 주체와 작업 규모가 결합돼 있다.** PM이 직접 책임지는 방식과 작은 수정 여부는 서로 다른 결정인데 하나의 L2 조건으로 묶여 있다.
2. **워크플로우를 PM이 직접 수행하는 유형이 없다.** 현재 디스패치 의무는 워커 실행만 허용하므로 PM이 pilot 절차를 유지한 채 직접 수행하는 경로를 막는다(`opal/core/references/harness/guards.md` §디스패치 의무 원칙).
3. **capability 선택 계약이 워커 디스패치에 치우쳐 있다.** 런타임 capability 확인은 주로 워커 프롬프트 주입 시점에 정의돼 있고, PM 자신의 직접 실행을 위한 선택·호출·보강 절차는 독립된 계약이 아니다(`opal/core/references/harness/capability.md` §주입 계약, `opal/core/references/pm/dispatch-process.md` Step 6).
4. **완료 후 지식 동기화가 직접 수행의 공통 종료 조건으로 묶여 있지 않다.** 문서, brain, memory 관련 규칙은 존재하지만 직접 수행 유형을 관통하는 하나의 수명주기로 연결되지 않는다.

그 결과 “PM 직접 수행”이 작은 수정의 우회로로 읽히며, PM이 보유한 프로젝트 컨텍스트와 OPAL capability를 활용하는 정식 실행 모델이 되지 못한다.

## 3. 목표와 비목표

### 3.1 목표

- PM 직접 수행을 작업 규모와 무관한 정식 실행 방식으로 정의한다.
- 워크플로우형과 대화형을 명확히 분리한다.
- 어느 시점에 어떤 capability를 탐색·선택·호출하는지 규정한다.
- 작업 스킬(`op-*`), 범용 스킬, 도구, MCP, 서브에이전트, 스킬 생성·등록을 하나의 capability 모델로 다룬다.
- 두 유형 모두 완료 전에 실제 검증과 지식 동기화를 수행하도록 한다.
- PM이 최종 판단, 결과 통합, 완료 판정의 단일 책임자가 되게 한다.

### 3.2 비목표

- 모든 프로젝트 문서를 PM 컨텍스트에 상시 적재하지 않는다.
- 모든 작업에서 모든 종류의 capability를 호출하도록 강제하지 않는다.
- 기존 pilot별 단계와 Gate를 하나의 고정 파이프라인으로 통합하지 않는다.
- 서브에이전트 호출 결과만으로 완료를 선언하지 않는다.
- 필요한 근거 없이 신규 스킬을 만들거나 유사 스킬을 중복 등록하지 않는다.

## 4. 핵심 개념

### 4.1 PM 직접 수행

PM 직접 수행은 PM이 모든 명령과 파일 수정을 혼자 처리한다는 뜻이 아니다. PM이 다음 책임을 직접 소유한다는 뜻이다.

- 요청 해석과 실행 유형 결정
- 관련 도메인 컨텍스트 구성
- capability 선택과 호출 시점 결정
- 스킬·도구·서브에이전트 결과의 통합
- 실제 검증과 실패 처리
- 문서·지식·메모리 동기화
- 최종 완료 판정과 사용자 보고

서브에이전트가 구현하거나 독립 검증을 수행해도, PM이 위 책임을 유지하면 PM 직접 수행이다.

### 4.2 도메인 지식 준비 상태

PM이 도메인 지식을 “알고 있다”는 것은 모든 문서를 한 번에 읽어 상주시킨 상태가 아니다. 현재 작업에 필요한 지식을 최신 원천에서 조회해 **판단 가능한 컨텍스트를 준비한 상태**다.

| 지식 종류 | 우선 원천 | PM이 얻어야 할 내용 |
|---|---|---|
| 프로젝트 구조와 문서 경로 | `docs/PROJECT.md` | 관련 영역, 문서 레지스트리, 참조 시점 |
| 현재 코드 구조 | `code-scan`과 실제 파일 | 모듈, 의존, 소비자, 변경 후보 |
| 과거 결정과 설계 이유 | Project Brain | WHY/HOW, 채택·폐기 근거 |
| 운영 기억과 최근 맥락 | `.opal/MEMORY.json`과 memory 문서 | 활성 지식, 주의사항, 최근 결정 |
| 기획·설계·정책 | 레지스트리에서 선별한 docs | 요구사항, 제약, 인터페이스, 정책 |
| 외부 최신 사실 | 공식 문서·웹·MCP | 버전, API, 표준, 외부 제약 |

PM은 전체 폴더를 관성적으로 읽지 않고 작업 범위에 맞춰 선별한다. 현재 `dispatch-process` Steps 1~3의 실행 단위 확정, 지식·코드맵 선조회, PROJECT 레지스트리 기반 문서 선별을 PM 직접 수행의 공통 사전 절차로 일반화한다(`opal/core/references/pm/dispatch-process.md` Steps 1~3).

### 4.3 Capability

직접 수행에서 capability는 PM이 작업을 완수하기 위해 호출할 수 있는 모든 실행 수단이다.

| 종류 | 역할 | 예시 |
|---|---|---|
| 작업 스킬 | 단계별 표준 절차와 산출물 계약 실행 | `op-task`, `op-dev-plan`, `op-dev-execute` |
| pilot·오케스트레이터 스킬 | 전체 워크플로우와 상태 전이 실행 | `opal-pilot-*` |
| 범용 스킬 | 특정 결과물·도메인 작업 수행 | 문서, 데이터, 시각화, 웹 변환 스킬 |
| 도구 | 결정론적 조회·변경·검증 | `state-tool`, `code-scan`, `test-tool`, `brain-tool`, `memory-tool` |
| MCP·외부 조회 | 외부 시스템 또는 최신 지식 접근 | 공식 문서, 브라우저, 외부 서비스 |
| 서브에이전트 | 전문 작업, 독립 수집, 구현, 검증 | 계획·FE·BE·DB·테스트·평가 에이전트 |
| capability 생성·등록 | 현재 없는 재사용 능력 보강 | `opal-skill-manager`, `opal-skill-creator`, `skill-registry` |

정적 목록을 프롬프트에 복제하지 않는다. PM은 실행 시점의 실제 가용 capability를 확인하고 필요한 것만 선택한다. 이는 기존 런타임 capability 원칙을 PM 자신에게 확장한 것이다(`opal/core/references/harness/capability.md`).

## 5. 실행 유형

### 5.1 워크플로우 직접 수행 (`direct-workflow`)

PM이 선택된 pilot의 단계·산출물·상태·Gate 계약을 유지하면서 전체 작업을 책임지는 방식이다.

- 기준 흐름은 `TASK → PLAN → EXECUTE → TEST → CLOSE`다.
- ANALYSIS, TEST-SCENARIO, SPEC, QA 등 추가 단계는 선택한 pilot의 정의를 따른다.
- PM은 각 단계 스킬을 직접 적용하거나 필요한 전문 서브에이전트에 실행 단위를 맡길 수 있다.
- `state-tool`, 테스트 게이트, 승인 게이트 등 구조적으로 필수인 도구 호출은 그대로 유지한다.
- 워커 디스패치 여부는 단계 정의가 아니라 PM의 실행 전략이 결정한다.
- 기존 pilot의 반복 상한, 실제 검증, CLOSE 승인 계약은 유지한다.

워크플로우 직접 수행의 “직접”은 PM이 워크플로우 전체를 소유한다는 의미다. 단계 내부에서 스킬·도구·서브에이전트를 호출하는 것은 이 정의와 충돌하지 않는다.

### 5.2 대화형 직접 수행 (`direct-adaptive`)

PM이 사용자와 대화하며 문제를 구체화하고 필요한 행동을 그때그때 수행하는 방식이다.

- 태스크 폴더와 고정 단계 산출물을 기본으로 요구하지 않는다.
- 분석, 설계, 구현, 테스트 순서는 실제 의존관계에 따라 구성한다.
- 작업 규모, 파일 수, 코드 여부, 테스트 필요 여부를 진입 제한으로 사용하지 않는다.
- 코드 변경에는 사용자 실행 허가와 실제 검증이 필요하다.
- 작업 중 영속할 결정이나 설계가 생기면 해당 문서를 즉시 또는 완료 정리 시점에 갱신한다.
- 추적성과 단계별 Gate가 필요해지면 사용자 지시 또는 PM 제안으로 `direct-workflow`로 전환할 수 있다.

대화형이라는 이유로 검증을 생략하지 않는다. 고정 파이프라인을 생략할 뿐, 작업 성격에 맞는 검증과 완료 증거는 유지한다.

### 5.3 유형 선택

유형 선택에는 적격 조건을 두지 않는다. 다음 기준으로 사용자 의도를 해석한다.

| 사용자 표현 또는 상황 | 기본 유형 |
|---|---|
| “워크플로우로 직접 수행”, “pilot을 PM이 직접 수행” | `direct-workflow` |
| “직접 수행”, “그냥 해”, 대화 중 구체화하며 처리 | `direct-adaptive` |
| `//` pilot 명령과 PM 직접 수행 지시가 함께 있음 | 해당 pilot의 `direct-workflow` |
| 유형이 명확하지 않으나 상태·산출물 추적이 핵심 | PM이 `direct-workflow`를 제안 |
| 유형이 명확하지 않고 즉시 해결이 핵심 | PM이 `direct-adaptive`를 제안 |

파일 수, 변경량, 코드 로직 여부, 테스트 필요 여부는 유형 선택의 참고 정보일 수 있지만 직접 수행을 금지하는 조건은 아니다.

사용자가 유형을 명시하면 추가 적격성 심사 없이 해당 유형으로 진입한다. 유형이 명확하지 않으면 PM이 작업에 필요한 추적성과 상호작용 방식을 근거로 한 유형을 제안하고, 사용자가 수락한 뒤 진입한다. 현행 L2의 최종 사용자 결정권은 유지하되 파일 수·테스트 필요 여부에 따른 진입 제한은 폐기한다.

`direct-workflow`를 선택한 뒤 Dev pilot이 `opd`와 `opds` 중 어느 트랙을 사용할지는 해당 pilot의 `track-routing` 계약이 별도로 판단한다. 직접 수행 유형은 실행·관리 방식의 축이고, `opd↔opds`는 파이프라인 내부 트랙 축이다.

## 6. 공통 실행 수명주기와 capability 호출 시점

두 유형은 같은 수명주기를 공유한다. 워크플로우형은 이를 단계와 상태로 기록하고, 대화형은 실제 사건이 발생한 시점에 수행한다.

| 시점 | PM의 판단 | 우선 capability | 완료 조건 |
|---|---|---|---|
| 1. 요청 해석 | 목표, 범위, 실행 유형, 승인 범위가 충분한가 | 대화, TASK 스킬 | 성공 기준과 실행 유형 확정 |
| 2. 컨텍스트 준비 | 어떤 도메인 지식이 필요한가 | PROJECT 레지스트리, docs, brain, memory, `code-scan` | 결정에 필요한 근거 확보 |
| 3. capability 계획 | 어떤 절차·전문성·도구가 필요한가 | 스킬 레지스트리, tool 탐색, 가용 서브에이전트 | 호출 순서와 기대 결과 확정 |
| 4. 분석·설계 | 현재 상태와 목표 사이의 변경 계약은 무엇인가 | 분석·설계 스킬, 읽기 도구, 전문 에이전트 | 변경 대상·제약·검증 기준 확정 |
| 5. 실행 | 누가 어떤 단위를 어떤 도구로 수행하는가 | 실행 스킬, 편집·생성 도구, 전문 에이전트 | 요구 결과 생성 |
| 6. 검증 | 실제 요구가 충족됐는가 | 테스트 도구, 테스트 스킬·에이전트, lint/build/E2E | 실행 증거와 회귀 확인 |
| 7. 지식 동기화 | 어떤 원천이 이번 변경으로 낡았는가 | docs 편집, `brain-tool`, `memory-tool`, `code-scan` | 관련 원천 최신화 또는 불변 확인 |
| 8. 완료 판정 | 미해결 항목이나 미반영 지식이 남았는가 | diff·상태·검증 결과 조회 | 결과·증거·잔여 위험 보고 |

### 6.1 호출은 목적과 반환 계약을 가져야 한다

PM은 capability를 호출하기 전에 최소한 다음을 확정한다.

- **목적**: 이번 호출이 해결할 질문 또는 생성할 결과
- **입력**: 작업 범위, 관련 문서, 제약, 선행 결과
- **반환**: 산출물, 변경 파일, 검증 증거, blocker
- **후속 판단**: 결과를 채택·보완·폐기하는 기준

서브에이전트 호출은 특히 변경 범위와 완료 기준을 명시한다. PM은 반환 내용을 그대로 완료 선언에 사용하지 않고 실제 파일과 검증 결과를 확인한다.

### 6.2 capability 선택 순서

1. 선택한 workflow나 단계가 소유한 필수 스킬·도구를 먼저 적용한다.
2. 기존 등록 capability에서 현재 목적과 맞는 항목을 찾는다.
3. 기본 도구만으로 충분하면 별도 스킬을 추가하지 않는다.
4. 전문성, 독립 검증, 병렬 수집이 필요하면 서브에이전트를 호출한다.
5. 기존 capability로 반복 가능하게 해결할 수 없는 공백이 확인되면 설치 또는 신규 생성을 검토한다.

이 순서는 신규 스킬 생성을 금지하기 위한 것이 아니라 중복 등록과 일회성 추상화를 막기 위한 것이다.

## 7. 워크플로우 직접 수행의 단계 계약

선택한 pilot이 별도 단계를 정의하면 그 계약이 우선한다. 아래 표는 공통 기준이다.

| 단계 | PM 직접 책임 | 가능한 호출 | 단계 종료 시 확인 |
|---|---|---|---|
| TASK | 문제·목표·제약·수용 기준 확정 | `op-task`, 인터뷰·조사 도구 | 요구사항이 실행 가능한 수준으로 확정됨 |
| PLAN | 영향 분석, 작업 단위, 의존, 검증 설계 | PLAN 스킬, `code-scan`, brain, 설계·전문 에이전트 | 구현·검증 계약과 capability 계획 확정 |
| EXECUTE | 계획된 단위 실행과 통합 | 실행 스킬, 편집 도구, BE·FE·DB 등 전문 에이전트 | 계획된 변경과 단계별 자가검증 완료 |
| TEST | 실제 동작과 회귀 검증 | `test-tool`, 테스트 스킬·에이전트, 브라우저·외부 연동 | 요구사항 연결 증거와 실패 처리 완료 |
| CLOSE | 최종 일관성·지식 갱신·사용자 확인 | docs, brain, memory, `code-scan`, state 관련 도구 | 산출물·지식·상태가 일치하고 승인 게이트 통과 |

PM이 단계 스킬을 직접 적용하는 경우 해당 스킬의 절차와 출력 계약을 그대로 따른다. 스킬이 특정 단계를 워커 전용으로 제한한 현재 계약은 `direct-workflow` 컨텍스트에서는 “PM 또는 PM이 선택한 서브에이전트가 수행”으로 확장해야 한다.

검증 주체 분리가 품질 계약인 단계에서는 PM이 구현을 직접 했더라도 독립 테스트·평가 서브에이전트를 호출한다. 직접 수행은 검증 독립성을 제거하는 근거가 아니다.

코드 파일을 변경한 경우 CLOSE 전에 변경 파일 목록을 다시 구성해 `code-scan validate --changed <목록>`을 실행한다. 이는 pipeline Gate와 독립된 `@header` 품질 검증이므로 워크플로우 안에서도 생략하지 않는다.

## 8. 대화형 직접 수행의 사건 기반 계약

대화형 직접 수행은 단계 파일 대신 사건이 호출 시점을 만든다.

| 사건 | 필수 행동 |
|---|---|
| 새 요구나 제약이 등장함 | 영향 범위를 다시 확인하고 관련 문서를 추가 조회 |
| 설계 선택이 필요함 | 대안을 비교하고 채택 근거를 명시한 뒤 구현 |
| 코드·설정·데이터를 변경함 | 변경 전 관련 원천 확인, 변경 후 실제 검증 |
| 외부 API·라이브러리 사실이 필요함 | 최신 공식 원천을 조회하고 버전·시점을 확인 |
| 전문성이 필요한 하위 문제가 생김 | 관련 스킬 또는 전문 서브에이전트 호출 |
| 독립 검증이 필요한 위험이 생김 | 테스트·평가 서브에이전트 또는 별도 검증 도구 호출 |
| 반복 가능한 capability 공백이 확인됨 | 스킬 탐색·설치·생성·등록 절차 수행 |
| 기존 문서·지식이 낡아짐 | 완료 전에 해당 SSOT 갱신 |
| 범위와 추적 요구가 커짐 | `direct-workflow` 전환을 제안하거나 사용자 지시에 따라 전환 |

대화 기록은 실행 상태의 유일한 원천이 아니다. 장기 보존 가치가 있는 결정은 docs 또는 brain에, 운영 기억은 memory에 기록한다.

코드 파일을 변경한 경우 완료 보고 전에 `git diff --name-only HEAD`와 untracked 파일로 변경 목록을 다시 구성하고 `code-scan validate --changed <목록>`을 실행한다. 대화형 직접 수행에 파이프라인 Gate를 적용하지 않더라도 이 검증은 유지한다.

## 9. Capability 공백과 신규 스킬 등록

PM은 현재 작업에 필요한 capability가 없을 때 작업을 포기하거나 즉흥 절차를 반복하는 대신 capability를 보강할 수 있다.

### 9.1 처리 순서

1. `skill-registry` 또는 스킬 관리 기능으로 기존 작업 스킬과 범용 스킬을 검색한다.
2. 적합한 스킬이 있으면 현재 환경에서 실제 호출 가능한지 확인한다.
3. 외부 스킬이 적합하면 출처·권한·위험을 확인하고 설치 계약에 따라 등록한다.
4. 적합한 스킬이 없고 재사용 가치가 있으면 스킬 위자드인 `opal-skill-creator`를 호출한다.
5. 생성된 스킬을 OPAL 구조와 레지스트리에 등록한다.
6. 레지스트리 검증과 실제 매칭·호출 검증을 수행한다.
7. 검증된 신규 capability로 원래 작업을 재개한다.

OPAL 프레임워크 스킬의 생성·후처리·레지스트리 등록은 `opal-skill-creator`가 소유하고, 탐색·외부 설치·사용자 등록분 관리는 `opal-skill-manager`와 `skill-registry` 계약을 따른다(`opal/skills/opal-skill-creator/SKILL.md`, `opal/skills/opal-skill-manager/SKILL.md`).

### 9.2 신규 생성 판단

다음 조건을 모두 만족할 때 신규 스킬 생성을 우선한다.

- 기존 등록 스킬과 목적·입출력 계약이 겹치지 않는다.
- 현재 작업뿐 아니라 이후에도 반복 사용할 절차다.
- 자연어 지시만으로 반복하기보다 검증 가능한 실행 계약으로 보존할 가치가 있다.
- 생성·등록·호출 검증 비용이 현재 작업의 편익을 정당화한다.

일회성 변환이나 기본 도구 몇 번으로 끝나는 작업은 PM이 직접 처리한다.

## 10. 완료 후 문서·지식·메모리 동기화

두 직접 수행 유형 모두 완료 판정 전에 아래 원천의 영향 여부를 확인한다. 모든 저장소를 무조건 수정하는 것이 아니라, 변경 사실이 해당 원천을 낡게 만들었을 때 갱신한다.

| 변경으로 생긴 정보 | 갱신 대상 | 판단 기준 |
|---|---|---|
| 사용자 요구·정책·업무 흐름 | 기획·정책 문서 | 이후 구현·운영 판단에 영향을 주는가 |
| 구조·인터페이스·데이터 모델 | 설계·아키텍처 문서 | 현재 시스템 설명이나 계약이 달라졌는가 |
| 사용법·운영 절차·프로젝트 설명 | 관련 `docs/` | 사용자나 다음 작업자가 알아야 하는가 |
| 설계 이유·채택/폐기 결정·비자명한 해법 | Project Brain | 재사용할 WHY/HOW 지식인가 |
| 최근 작업 맥락·주의사항·후속 항목 | 프로젝트 memory | 다음 세션의 PM 판단에 필요한가 |
| 코드 구조·exports·depends | `code-scan` 원천 | 실제 코드 구조가 바뀌었는가 |
| 신규 또는 변경된 capability | 스킬·도구 레지스트리와 관련 문서 | 다음 호출에서 발견·사용 가능해야 하는가 |

워크플로우 직접 수행은 CLOSE 단계에서 이 확인을 Gate로 집행한다. 대화형 직접 수행은 완료 보고 전 같은 체크를 수행한다.

동일 사실을 여러 저장소에 복제하지 않는다. docs는 현재 계약, brain은 결정의 이유와 재사용 지식, memory는 운영 맥락과 최근 이력을 소유한다(`opal/core/references/opal-doc-standard.md` §2·§4, `opal/core/references/opal-pm.md` §14·§15).

## 11. 실패·전환·완료 판정

### 11.1 실패 처리

- 필수 capability가 없으면 추정으로 완료 처리하지 않는다.
- 기존 capability로 해결할 수 있으면 대체 경로를 선택한다.
- capability 보강이 필요하면 설치 또는 신규 생성 절차를 수행한다.
- 실제 검증 실패는 해당 실행 단위로 되돌려 수정하고 이전 통과 검증을 재실행한다.
- 반복 상한과 사용자 에스컬레이션은 `guards.md`의 계약을 유지한다.

### 11.2 유형 전환

- `direct-adaptive → direct-workflow`: 상태 추적, 다단계 산출물, 여러 Gate 또는 장기 작업 관리가 필요할 때 제안한다.
- `direct-workflow → direct-adaptive`: 사용자가 명시적으로 고정 워크플로우 해제를 요청할 때 전환한다.
- 전환 시 이미 확보한 근거와 산출물을 재사용하되, 새 유형의 필수 입력이 누락됐는지 확인한다.

전환은 실패나 강등을 의미하지 않는다. 사용자에게 필요한 운영 수준을 바꾸는 결정이다.

### 11.3 완료 조건

PM은 다음 항목이 모두 충족된 경우에만 직접 수행 완료를 선언한다.

1. 합의된 요구사항이 실제 결과에 반영됐다.
2. 필요한 검증이 실제 실행됐고 결과가 확인됐다.
3. 호출한 스킬·도구·서브에이전트의 결과를 PM이 통합·검토했다.
4. 변경으로 낡아진 docs·기획·설계·brain·memory·코드맵이 갱신됐다.
5. 미해결 blocker와 후속 항목이 명확히 보고됐다.
6. 적용되는 사용자 승인과 CLOSE 계약이 충족됐다.

| `opal/core/references/opal-pm.md` | PM 역할 전환을 두 직접 수행 유형으로 재작성하고 L2 적격 조건 제거 |

| `opal/core/references/pm/dispatch-process.md` | Steps 1~6을 워커 전용 디스패치 절차와 PM 직접 수행 공통 preflight로 분리 |
| `opal/core/references/harness/capability.md` | capability 확인·선택·보강 계약을 PM 직접 수행까지 확장 |
| pilot·단계 스킬 | 실행 주체를 PM 또는 PM이 선택한 서브에이전트로 해석할 수 있는 `direct-workflow` 분기 추가 |
| `harness/header-rules.md`·`harness/state.md` | L2 명칭과 전용 예외 제거, 각 직접 수행 유형의 완료 검증 시점으로 재배치 |
| `harness/pm-improvement-loop.md` | 대화·L2 트리거를 `direct-adaptive` 트리거로 교체 |
| 프로젝트 문서·도움말 | 사용자 명령과 두 유형의 차이, 전환 규칙 문서화 |

`worker.dispatch` 이벤트와 워커 컨텍스트 주입 계약은 서브에이전트를 실제 호출할 때 계속 적용한다. PM이 단계 스킬이나 도구를 직접 호출하는 경우에는 워커 receipt를 요구하지 않는다.

### 12.1 현행 L2 규칙 승계 판정

| 현행 L2 규칙 | `direct-workflow` | `direct-adaptive` | 판정 |
|---|---|---|---|
| 파일 수·단순 수정·동작 검증 불요 적격성 | 적용하지 않음 | 적용하지 않음 | 폐기. 작업 규모는 직접 수행 금지 조건이 아니다. |
| 사용자 발화가 실행 허가를 포함 | 적용되는 pilot 승인 계약 사용 | “직접 수행”·“그냥 해”에 유지 | 유형별 승인 계약으로 이관 |
| PM 자동 감지 후 사용자 수락 | 유형이 불명확할 때 적용 | 유형이 불명확할 때 적용 | 최종 사용자 결정권 유지 |
| Guards | 유지 | 유지 | 공통 불변 규칙 |
| Coding Principles | 코드 변경 시 유지 | 코드 변경 시 유지 | 공통 불변 규칙 |
| OPAL Tools 우선 | 유지 | 유지 | 공통 capability 선택 규칙 |
| `@header` 규칙 | 코드 변경 시 유지 | 코드 변경 시 유지 | 파이프라인과 독립된 공통 품질 축 |
| `code-scan validate --changed` | CLOSE 전 실행 | 완료 보고 전 실행 | 변경 파일 재구성 후 실행 |
| 태스크 파이프라인 | 선택한 pilot 정의대로 적용 | 미적용 | `direct-workflow` 전용 |
| `state.json`·`STATE.md` | 선택한 pilot 정의대로 적용 | 미적용 | `direct-workflow` 전용 |
| QA·State·PM Gate | 선택한 pilot 정의대로 적용 | 미적용 | `direct-workflow` 전용. 실제 검증 의무는 두 유형 모두 유지 |
| 파이프라인 Observability | 선택한 pilot 정의대로 적용 | 미적용 | 현행 L2 동작을 대화형 유형에 승계 |
| 워커 디스패치 의무 | 폐기 | 폐기 | 서브에이전트는 PM이 필요할 때 선택하는 capability로 전환 |
| 서브에이전트 사용 가능성 | 필요 시 호출 | 필요 시 호출 | 두 유형 모두 허용, PM이 결과 통합·검증 책임 유지 |

### 12.2 축 분리

직접 수행 유형과 pilot 내부 트랙은 서로 대체하거나 자동 변환하지 않는다.

| 축 | 결정 내용 | 예시 |
|---|---|---|
| 실행 유형 | PM이 워크플로우를 적용할지, 대화형으로 수행할지 | `direct-workflow` / `direct-adaptive` |
| pilot | 어떤 도메인 워크플로우를 사용할지 | `opd`, `opwt`, `opsdd` |
| pilot 내부 트랙 | 선택된 pilot 안에서 어떤 프로파일을 사용할지 | Dev의 `opd↔opds` |

따라서 `direct-workflow + opd`, `direct-workflow + opds`는 모두 가능하다. `direct-adaptive`는 Dev pipeline에 진입하지 않으므로 `opd↔opds` 라우팅 대상이 아니다.

## 13. 구현 수용 기준

- [ ] “직접 수행” 진입에 파일 수, 변경량, 코드 여부, 테스트 필요 여부 제한이 없다.
- [ ] `direct-workflow`와 `direct-adaptive`가 서로 다른 실행 계약으로 정의된다.
- [ ] 두 유형 모두 작업 전 도메인 컨텍스트 선별 절차를 수행한다.
- [ ] 단계 또는 사건별 capability 호출 시점이 정의된다.
- [ ] 작업 스킬, 범용 스킬, 도구, MCP, 서브에이전트를 같은 capability 판단 범위에서 선택할 수 있다.
- [ ] capability 공백 시 기존 스킬 탐색, 설치, 신규 생성·등록, 실제 호출 검증이 가능하다.
- [ ] `direct-workflow`가 선택된 pilot의 상태·Gate·검증 계약을 유지한다.
- [ ] `direct-adaptive`도 코드 변경 후 필요한 실제 테스트를 생략하지 않는다.
- [ ] Guards, Coding Principles, OPAL Tools 우선 규칙이 두 직접 수행 유형의 공통 불변 규칙으로 유지된다.
- [ ] 코드 파일 변경 시 두 유형 모두 변경 파일을 재구성하고 `code-scan validate --changed`를 실행한다.
- [ ] pipeline Gate 미적용과 `@header` 검증 유지가 서로 다른 축으로 명시된다.
- [ ] 두 유형 모두 완료 전에 관련 docs·기획·설계·brain·memory 영향 여부를 확인한다.
- [ ] 서브에이전트를 사용해도 PM이 통합·검증·완료 판정의 책임을 유지한다.
- [ ] 기존 워커 디스패치 방식은 PM이 워커 실행을 선택한 경우 그대로 동작한다.
- [ ] `direct-workflow/direct-adaptive`와 Dev의 `opd↔opds`가 서로 독립된 축으로 동작한다.
- [ ] L2 전용 문구와 참조가 하네스·스킬·도움말에서 제거되거나 새 모델로 치환된다.

## 14. 권고

이 제안을 채택하고 `L2 경량 트랙`을 두 종류의 PM 직접 수행 모델로 대체한다.

첫 구현은 공통 수명주기와 capability 라우팅을 단일 SSOT로 분리하는 것부터 시작한다. 이후 `opal-pm.md`와 guards를 연결하고, pilot별 `direct-workflow` 실행 주체 분기를 확산한다. 마지막으로 L2 참조를 제거하고 대화형 직접 수행의 완료 전 지식 동기화 검증을 연결한다.

이 순서는 PM 직접 수행의 의미를 먼저 고정하고, 각 pilot이 서로 다른 해석으로 분기되는 것을 막는다.
