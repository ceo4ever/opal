다음 단계의 근거가 되는가

각 문서는 같은 내용을 반복하지 않는다. TASK는 목표, ANALYSIS는 확인한 사실, PLAN은 구현 계약, TEST-SCENARIO는 판정 기준을 소유한다. 구현과 테스트는 그 계약을 코드와 실행 증거로 닫는다.

정확한 순서: TASK → ANALYSIS → PLAN → TEST-SCENARIO → EXECUTE → TEST. 시나리오는 PLAN 뒤에 작성하지만, 구현 전 RED로 지정된 항목은 EXECUTE 직전에 먼저 실패를 확인한다.

JOIN RULE

AC-N과 C-N은 TASK에서 시작해 PLAN의 W-N 및 시나리오의 S-N으로 연결된다. H-N은 PLAN에서 시작해 S-N으로 검증된다. ANALYSIS는 새 요구사항 ID를 만들기보다 이 연결을 결정할 사실과 근거를 제공한다.

03 / ownership

기준·상태·결과를 섞지 않는다

같은 사실을 여러 문서가 동시에 소유하면 어느 것이 최신인지 판단하기 어려워진다. 정보 종류마다 기록 위치를 하나로 고정한다.

SPECIFICATION / MARKDOWN

무엇을 만들고 어떻게 판정할지

사람과 구현자가 읽는 변경 계약이다. 실행 결과가 생겨도 기준 문장을 사후 수정하지 않는다.

  • TASK.md — 목표, AC-N, C-N
  • ANALYSIS.md — 사실, 근거, 변경 경계
  • PLAN.md — W-N, H-N, 순서와 파일 소유권
  • TEST-SCENARIO.md — S-N과 기대 결과
PIPELINE STATE / JSON

지금 어느 단계이며 누가 승인했는지

문서 본문에 진행률과 승인 상태를 반복하지 않는다. 파이프라인 상태는 도구가 갱신한다.

  • state.json — 단계 상태와 사용자 승인
  • state-tool — 전이·검증·조회
  • Work items 상태는 W-N 연결로 추적
  • CLOSE 완료 시 DONE.md 생성
TEST EVIDENCE / JSON

무엇을 실행했고 실제로 어떻게 끝났는지

시나리오 명세와 테스트 결과를 분리한다. 출력 증거가 없는 PASS는 기록할 수 없다.

  • test-scenario.json — PASS / FAIL / BLOCKED
  • 실제 명령, 출력, 관찰 증거
  • RED 확인과 명세 잠금
  • 코드 품질·보안·회귀 결과
RULE 01

다음 문서는 앞 문서를 복사하지 않고 ID와 근거로 연결한다.

RULE 02

PLAN 없는 시나리오는 H-N과 실제 구현 경계를 검증할 수 없다.

RULE 03

구현자는 W-N을 수행하고 검증 기준 S-N을 낮추지 않는다.

RULE 04

테스트는 실제 출력으로 끝나며 결과는 JSON SSOT에 기록한다.
