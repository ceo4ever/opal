# 실행 아키텍처 설계 상세 가이드

dtp-planner 에이전트가 TODO.md Part C(실행 아키텍처)를 설계할 때 참조하는 상세 가이드이다.

---

## 1. 에이전트 토폴로지 설계

### 1-1. DAG 구성

TODO Part A의 각 Step을 노드로, Step 간 의존성을 간선으로 하는 DAG를 구성한다.

```
예시:
Step 1 (DB 스키마) → Step 2 (모델 구현) → Step 5 (통합 테스트)
                   → Step 3 (API 라우트) → Step 5
Step 4 (UI 컴포넌트) ─────────────────────→ Step 5
```

### 1-2. 그룹핑 알고리즘

**우선순위 1: 파일 충돌 방지**
- 동일 파일을 수정하는 Step은 반드시 같은 에이전트에 배치
- 이 규칙은 다른 그룹핑 기준보다 우선

**우선순위 2: 모듈 응집도**
- 동일 모듈/레이어에 속하는 Step을 같은 에이전트에 그룹핑
- 예: DB 관련 Step (스키마 + 마이그레이션 + 시드) → 하나의 에이전트

**우선순위 3: 병렬 실행 극대화**
- 독립적인 모듈을 별도 에이전트로 분리하여 병렬 실행

### 1-3. 에이전트 크기 가이드

| 에이전트 당 Step 수 | 판단 |
|-------------------|------|
| 1~2개 | 적절 (집중도 높음) |
| 3~4개 | 적절 (관련 작업 묶음) |
| 5개 이상 | 분리 검토 (컨텍스트 과부하 위험) |

### 1-4. 배치(Batch) 결정

```
Batch 1: [의존성 없는 에이전트들 — 병렬 실행]
Batch 2: [Batch 1 완료 후 실행 가능한 에이전트들 — 병렬 실행]
...
Batch N: [최종 통합/테스트 에이전트]
```

## 2. 스킬 매칭 상세

### 2-1. 기존 스킬 카탈로그

에이전트 탐색 경로에서 사용 가능한 스킬을 확인한다:

```
탐색 경로 (우선순위):
1. {프로젝트}/.cursor/skills/
2. {프로젝트}/.claude/skills/
3. ~/.cursor/skills/
4. ~/.claude/skills/
```

| 스킬 | 트리거 조건 | 입출력 |
|------|-----------|-------|
| doc-writer | 기술 문서 작성 필요 | 프로젝트 컨벤션 → 표준 마크다운 문서 |
| api-analyzer | 외부 API 연동 필요 | API URL/문서 → 7단계 분석 명세서 |
| wireframe-builder | UI 프로토타입 필요 | 기획 문서 → 단일 HTML 와이어프레임 |
| version-mgr | 기존 산출물 수정 | 버전 체계 관리 |
| interview | 요구사항 불명확 | 구조화된 Q&A |

### 2-2. 스킬 갭 판별

각 에이전트의 작업 목록을 순회하며:

1. 위 카탈로그에서 매칭되는 스킬이 있는가?
2. 없다면, 해당 작업 패턴이 반복되는가?
   - 3개 이상의 Step에서 동일 패턴 → 스킬 후보
   - 1~2개 Step에서만 사용 → 인라인 지침

### 2-3. 신규 스킬 SKILL.md 초안

스킬 생성이 필요한 경우, 최소한의 SKILL.md 초안을 작성한다:

```markdown
---
name: {skill-name}
description: |
  {한 줄 설명}
---

# {스킬 제목}

## 입력
{입력 설명}

## 프로세스
{단계별 절차}

## 출력
{출력 형식}
```

저장 위치: `tasks/{NNN}/skills/{name}/SKILL.md`

## 3. 도구 탐색 상세

### 3-1. 도구 필요성 식별

각 Step의 작업 내용에서 도구가 필요한 패턴을 식별한다:

| 작업 패턴 | 필요 도구 유형 |
|----------|-------------|
| DB 스키마 변경/마이그레이션 | ORM CLI (prisma, typeorm, alembic 등) |
| 코드 린트/포맷 | 린터/포맷터 (eslint, prettier, black 등) |
| 테스트 실행 | 테스트 프레임워크 (vitest, jest, pytest 등) |
| 빌드/번들링 | 빌드 도구 (vite, webpack, esbuild 등) |
| API 테스트 | API 클라이언트 (httpie, curl) 또는 MCP 서버 |
| 브라우저 테스트 | E2E 도구 (playwright, cypress) |
| 타입 검사 | 타입 체커 (tsc, mypy, pyright 등) |

### 3-2. 환경 확인 명령

```bash
# Node.js 프로젝트
which node npm npx
npm ls --depth=0
cat package.json | jq '.scripts'

# Python 프로젝트
which python pip
pip list
cat pyproject.toml

# 공통
which git docker
```

### 3-3. 웹 검색 전략

미설치 도구가 있을 때:

1. **검색 키워드**: `"{기술스택} {작업유형} tool {현재연도}"`
2. **MCP 서버 검색**: `"MCP server {기능}"` — Smithery, npm 등에서 탐색
3. **비교 분석**: 2~3개 후보의 장단점 (성능, 커뮤니티, 유지보수 상태)
4. **추천 형식**:
   ```
   - **{tool-name}**: {설명} — {추천 이유} — {설치: `npm i -D {name}`}
   ```

## 4. 테스트 전략 구체화

> TEST-SCENARIO.md가 이미 작성된 경우, 시나리오(S-1~S-N)의 대상/조건/기대 결과를 기반으로 아래 테스트 전략을 구체화한다. TEST-SCENARIO.md의 시나리오가 "무엇을 검증할지"를 정의하고, 여기서는 "어떻게 검증할지"를 구체화한다.

### 4-1. B-1 기능 테스트 → 실행 가능한 형태로

Part B-1의 각 항목을:
- 테스트 파일 경로 (신규 작성 시)
- 실행 명령어
- 기대 결과 (성공 조건)

### 4-2. B-2 회귀 테스트

- 기존 테스트 스위트 경로 확인
- 전체 실행 명령어
- 커버리지 기준 (있는 경우)

### 4-3. B-3 코드 품질

- 린트: `{lint 명령} {변경 파일}`
- 타입 체크: `{type-check 명령}`
- 포맷: `{format-check 명령} {변경 파일}`

### 4-4. B-4 보안

- 하드코딩 시크릿 스캔: `grep -rn "(password|secret|token|api_key)\s*=" {변경 파일}`
- .gitignore 확인: `.env`, 인증 파일이 포함되어 있는지
- 민감 파일 노출: 변경 파일 중 .env, credentials 등이 없는지
