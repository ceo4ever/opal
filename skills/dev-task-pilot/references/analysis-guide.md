# ANALYSIS 단계 상세 가이드

> **Full Task 전용**: 이 가이드는 Full Task 모드의 ANALYSIS 단계에서 사용된다.
> Short Task에서는 이 단계가 없으며, `references/plan-guide.md`의 "Short Task 통합 PLAN" 섹션의 "코드 분석" 파트를 참조한다.

> **실행 컨텍스트**: 이 가이드는 워커 에이전트의 컨텍스트에서 실행된다.
> 오케스트레이터(알투)가 워커를 디스패치하면, 워커가 이 가이드를 읽고 프로세스를 따른다.
> 서브 에이전트 사용이 불가능한 플랫폼에서는 오케스트레이터가 직접 이 가이드를 따른다.
> 가이드의 프로세스 자체는 실행 주체와 무관하게 동일하다.

TASK.md의 요구사항을 바탕으로, 구현에 필요한 모든 정보를 수집하고 분석한다.
"충분히 조사하지 않고 코딩에 들어가는 것"이 가장 흔한 실패 원인이다.

## 분석 프로세스

### 0단계: 프로젝트 컨텍스트 로딩 (모든 작업 유형, 최우선)

코드 분석 전에 프로젝트 수준의 컨텍스트를 확보한다.

**프로젝트 문서 확인**:

1. `docs/` 디렉토리 존재 여부 확인 (opal-project-init이 생성한 프로젝트 문서)
   - **있으면**: 아래 문서를 Read하여 기술 스택, 아키텍처, 환경을 파악
     - `docs/INDEX.md` — 문서 인덱스 + 개발 워크플로우
     - `docs/server/README.md` — 백엔드 기술 스택, 구조, 실행 방법
     - `docs/client/README.md` — 프론트엔드 기술 스택, 구조
     - `docs/client/ARCHITECTURE.md` — Routing/View 분리 원칙, 컴포넌트 구조
     - `docs/server/PROJECT_STRUCTURE.md` — 백엔드 프로젝트 구조
   - **없으면**: 사용자에게 opal-project-init(opi) 실행을 제안
     > "프로젝트 문서(docs/)가 없습니다. opi를 실행하면 기술 스택/아키텍처 문서가 생성되어 분석 품질이 높아집니다. 진행할까요?"
2. `.opal/AGENT.md` 존재 시 Read — 프로젝트 규칙, 도메인 지식, 의사결정 원칙

**기술 스택 식별 + 추천 스킬/MCP 파악**:

3. 프로젝트 파일에서 기술 스택을 식별한다:
   - `CLAUDE.md` — 기술 스택 섹션
   - `package.json` — dependencies (React, Next.js, Express 등)
   - `pyproject.toml` — dependencies (FastAPI, Django 등)
   - `go.mod`, `pom.xml`, `build.gradle`, `Cargo.toml` — 기타 언어
   - `components.json`, `tailwind.config.*` — UI 라이브러리
4. `~/.opal/references/skills.md`의 "기술 스택별 추천 스킬" 섹션을 참조하여 해당 스택의 추천 스킬/MCP를 파악한다
5. `~/.opal/references/mcps.md`를 참조하여 사용 가능한 MCP 서버를 파악한다

### 1단계: 기존 코드베이스 분석 (모든 작업 유형)

현재 프로젝트 상태를 파악한다. 새로 만드는 것이든 수정하는 것이든, 기존 코드를 먼저 이해해야 한다.

**분석 항목:**

- **관련 파일 탐색**: Glob/Grep으로 관련 파일을 찾고 Read로 핵심 코드를 읽는다
- **기존 패턴 파악**: 같은 도메인의 기존 구현이 어떤 패턴을 따르는지 확인
- **의존성 맵**: 변경 대상 파일이 어디서 import되고, 어디를 import하는지
- **테스트 현황**: 관련 테스트 파일이 있는지, 커버리지는 어떤지

**분석 깊이 기준:**
```
신규 개발 → 동일 레이어의 기존 구현 전체를 읽는다
기능 개선 → 변경 대상 파일 + 직접 의존 파일을 읽는다
기능 수정 → 변경 대상 파일 + 영향 받는 파일을 읽는다
오류 수정 → 에러 발생 지점부터 호출 체인을 역추적한다
```

**데이터 파이프라인 작업 시 (추가)**:
- 입력 데이터의 첫 5행을 Read하여 실제 데이터 형식/타입/범위를 파악한다
- 날짜 필드가 float로 저장된 경우, ID 필드 타입 불일치 등 런타임 이슈를 사전에 감지한다
- 데이터 흐름 추적: 원본 → 변환 → 저장까지의 전체 경로를 확인한다

### 2단계: 외부 API / 라이브러리 조사 (신규 · 개선)

새로운 외부 연동이 필요한 경우:

- **공식 문서 확인**: API 엔드포인트, 인증 방식, 요청/응답 형식
- **SDK 확인**: 공식 SDK가 있는지, 버전, 의존성
- **Rate Limit**: 호출 제한, 재시도 정책
- **알려진 이슈**: 공식 문서에 명시된 제약사항, 커뮤니티 보고 이슈

**기술 조사 도구 활용 (의무)**:

- **context7 MCP**: 태스크에서 사용하는 핵심 라이브러리의 최신 문서를 조회한다
  - `resolve-library-id` → `query-docs`로 최신 API, 패턴, 주의사항 확인
  - deprecated 메서드 사용 방지, 버전별 API 변경 사항 확인
- **커뮤니티 검색** (WebSearch 도구): 기술적 이슈나 모르는 패턴이 있으면 검색한다
  - GitHub Issues: `"{라이브러리} {에러/패턴} site:github.com"`
  - Stack Overflow: `"{기술} {문제} site:stackoverflow.com"`
  - Reddit: `"{기술} best practice site:reddit.com"`

### 3단계: 유사 구현 패턴 참조 (신규)

프로젝트 내부 또는 외부에서 유사한 구현 패턴을 찾는다:

- **내부 패턴**: 프로젝트 내 다른 모듈의 기존 구현 방식
- **외부 패턴**: 오픈소스 프로젝트에서 비슷한 문제를 어떻게 풀었는지
- **Best Practice**: 공식 문서의 권장 패턴

**아키텍처 정합성 확인 (신규 기능 필수)**:
- 0단계에서 파악한 프로젝트 아키텍처(docs/, CLAUDE.md)에 맞는 구현 방식을 제안한다
- FE: 기존 컴포넌트 구조, 상태 관리 패턴, 라우팅 방식(App Router 등)에 맞출 것
- BE: 기존 레이어 구조(Model→DTO→Service→Router 등), ORM 패턴, API 설계 방식에 맞출 것
- 아키텍처와 다른 방식이 필요하면 근거와 함께 대안을 제시한다

### 4단계: 영향 범위 분석 (신규 · 개선 · 수정)

이 변경이 다른 부분에 미치는 영향을 파악한다:

- **직접 영향**: 변경 대상 파일을 import하는 다른 파일
- **간접 영향**: API 응답 형식 변경 → 프론트엔드 영향 등
- **DB 영향**: 테이블/컬럼 추가·수정 필요 여부
- **설정 영향**: 환경변수, 설정 파일, 패키지 추가 필요 여부

### 5단계: 원인 분석 — Root Cause (오류 수정 전용)

오류의 근본 원인을 찾는다:

- **재현 조건**: 어떤 입력/상태에서 에러가 발생하는지
- **에러 메시지 분석**: 스택 트레이스, 로그 확인
- **호출 체인 추적**: 에러 발생 지점 → 호출자 → 최초 진입점
- **가설 수립**: 가능한 원인 2~3개 나열, 각각의 검증 방법

## 분석 품질 체크리스트

ANALYSIS.md 작성 후, 아래 항목을 스스로 검증한다:

- [ ] TASK.md의 모든 요구사항에 대해 분석했는가?
- [ ] 기존 코드의 관련 파일을 실제로 읽었는가? (추측하지 않았는가?)
- [ ] 변경이 필요한 파일 목록이 완전한가?
- [ ] 영향 범위를 빠뜨린 곳이 없는가?
- [ ] 구현 불가능하거나 리스크가 높은 부분을 명시했는가?
- [ ] 프로젝트 컨텍스트(docs/, .opal/AGENT.md)를 확인했는가?
- [ ] 주요 라이브러리에 대해 context7 MCP로 최신 문서를 확인했는가?
- [ ] 기술 스택을 식별하고 추천 스킬/MCP를 파악했는가?

## QA 에이전트 호출 안내

ANALYSIS.md 작성이 완료되면, **오케스트레이터가 QA 에이전트를 호출**한다.

> **워커는 QA를 호출하지 않는다.** 워커는 ANALYSIS.md 경로와 요약을 오케스트레이터에 반환하고, 오케스트레이터가 QA 에이전트를 별도로 호출한다.
