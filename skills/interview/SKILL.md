# 요구사항 수집 인터뷰 스킬

사용자에게 효율적으로 질문하여 정확한 요구사항을 수집하고, 의사결정 사항을 체계적으로 기록합니다.

## 인터뷰 원칙

1. **한 번에 1개 질문**: AskUserQuestion 도구를 사용하여 **매 콜당 질문 1개**만 전달한다. 질문을 묶지 않는다 — 직전 답변이 다음 질문을 결정하기 때문이다.
2. **의사결정트리 기반**: 다음 질문은 항상 직전 답변에 의해 분기된다. 미리 정해진 고정 질문 목록을 순차 소진하는 것이 아니라, 답변에 따라 트리의 가지를 타고 내려가며 불필요한 가지는 잘라낸다.
3. **선택지 제공**: 가능하면 구체적인 선택지를 제시하여 의사결정 부담을 줄임
4. **맥락 설명**: 각 질문의 배경과 영향 범위를 간략히 설명
5. **누락 감지**: 답변을 받은 후 기존 산출물과 비교하여 누락된 항목 자동 감지
6. **완결까지 집요하게(relentless)**: 요구사항이 완전해질 때까지 트리를 끝까지 탄다. 다만 컨텍스트/기존 산출물에서 추론 가능한 가지는 질문 없이 스킵하고 1줄로 통지한다.

## 인터뷰 프로세스

### Step 1: 요구사항 초기 분석 및 의사결정트리 구성
```
사용자의 요청을 받으면:
1. 요청 내용에서 명시적 요구사항 추출
2. 기존 산출물(정책서, 설계서 등)이 있으면 Read로 확인
3. 요청과 기존 산출물 사이의 갭/충돌 식별
4. 불명확한 점을 의사결정트리로 구조화 — 루트(가장 상위 결정)부터
   리프(세부 결정)까지, 상위 답변이 하위 가지를 결정하도록 배치
```

### Step 2: 질문 1개 전달 (반복)
```
AskUserQuestion으로 트리의 현재 노드 1개만 질문한다:
- header: 12자 이내의 짧은 레이블 (예: "엔티티 관계", "인증 방식")
- question: 명확한 질문 + 배경 설명
- options: 2~4개 구체적 선택지 (장단점 포함)
- 매 콜당 질문 1개 — 절대 묶지 않는다
- 컨텍스트/기존 산출물에서 이미 답이 나오는 노드는 질문 없이
  "{항목}은 {추론값}으로 자동 결정. 변경하시려면 알려주세요." 1줄 통지 후 스킵
```

### Step 3: 답변 분석 및 다음 노드 결정
```
답변을 받으면:
1. 답변이 기존 규칙/산출물과 일관되는지 검증
2. 답변에 따라 트리에서 다음으로 탈 가지를 선택 (불필요한 가지는 가지치기)
3. 다음 노드가 있으면 Step 2로 돌아가 1개 더 질문
4. 트리를 끝까지 타서 미해결 노드가 없으면 결과 정리 후 다음 단계로 진행
```
### Step 4: 의사결정 기록
```
인터뷰 결과를 다음 형식으로 정리:

[결정 사항 요약]
1. {질문 주제}: {결정 내용} — {근거/맥락}
2. ...

[영향 범위]
- 영향받는 산출물: {목록}
- 필요한 업데이트: {목록}
```

## 질문 유형별 템플릿

### 엔티티/관계 질문
```
"{A}와 {B}의 관계는 어떻게 되나요?"
선택지:
- 1:1 (A 하나에 B 하나)
- 1:N (A 하나에 B 여러개)
- N:N (다대다 관계)
```

### 정책 결정 질문
```
"{기능}의 범위는 어떻게 할까요?"
선택지:
- A 방식: {설명} — 장점: {}, 단점: {}
- B 방식: {설명} — 장점: {}, 단점: {}
```

### 우선순위 질문
```
"다음 중 우선 포함할 항목은?"
선택지: (multiSelect: true)
- {항목A}: {설명}
- {항목B}: {설명}
```

## 기존 산출물과의 교차 검증

인터뷰 중 프로젝트에 관련 산출물이 있으면 반드시 교차 검증한다:

| 새 요구사항 영역 | 확인할 산출물 |
|-----------------|-------------|
| 엔티티 변경 | 정책서, DB 설계서, API 설계서 |
| 화면 변경 | 와이어프레임, 화면 정의서 |
| 데이터 처리 변경 | 정책서, 배치 설계서 |
| 지표 변경 | 프로젝트 표준 지표 정의, 필드 매핑 |
| 권한 변경 | 정책서 권한 섹션 |

## 인터뷰 주의사항

- 사용자가 간단히 답변하면, 해석한 내용을 요약하여 확인 요청
- 사용자가 새로운 개념을 제시하면, 기존 용어와의 관계를 반드시 질문
- 기술적 제약이 있는 요구사항이면, 제약 사항을 설명하고 대안 제시
- 모든 결정은 산출물에 반영될 때까지 추적
