# network-guide.md

기술 산출물 간 논리적 연결 관계와 워커 디스패치 규칙을 정의한다.

---

## 1. 산출물 유형 정의

### 필수 4종

| 유형 | 설명 | 수량 |
|------|------|------|
| **PRD** (Product Requirements Document) | 제품 목표, 타깃 유저, 핵심 요구사항 | 보통 1개 |
| **TRD** (Technical Requirements Document) | 기술 요구사항, 아키텍처 설계, 기술 스택 | 보통 1개 |
| **서비스 정책서** | 회원/결제/환불 등 비즈니스 정책. 도메인별 독립 문서로 관리 | 도메인별 복수 |
| **IA** (Information Architecture, 기능 포함) | 정보구조도 + 기능 정의 통합. JSON으로 작성 후 검토 시 xlsx 변환 | 보통 1개 |

### 선택 4종

| 유형 | 설명 |
|------|------|
| **기능도** | 시스템의 기능 구조를 다이어그램으로 표현 |
| **순서도** | 비즈니스 프로세스 또는 시스템 흐름 표현 |
| **운영 정책서** | 운영 기준, 권한, 처리 절차 등 내부 운영 규정 |
| **서비스 매뉴얼** | 사용자 또는 운영자 대상 사용 가이드 |

---

## 2. 논리적 연결 맵

### 유형 간 양방향 참조

```
PRD ↔ TRD
  PRD → TRD: 기능 요구사항 → 기술 구현 방식
  TRD → PRD: 기술 제약 → 요구사항 범위 조정

PRD ↔ 서비스 정책서
  PRD → 서비스 정책서: 핵심 요구사항 → 정책 상세화
  서비스 정책서 → PRD: 정책 결정 → 요구사항 보완

PRD ↔ IA
  PRD → IA: 기능 목록 → 정보 구조 설계
  IA → PRD: 구조 설계 → 요구사항 누락 발견

TRD ↔ IA
  TRD → IA: API/데이터 구조 → IA 기능 명세에 반영
  IA → TRD: 기능 명세 → 기술 구현 요건 도출

서비스 정책서 ↔ IA
  서비스 정책서 → IA: 정책 규칙 → IA 기능 조건/제약에 반영
  IA → 서비스 정책서: 화면/기능 구조 → 정책 보완 발견

서비스 정책서 ↔ 운영 정책서
  서비스 정책서 → 운영 정책서: 서비스 규정 → 운영 처리 절차 도출
  운영 정책서 → 서비스 정책서: 운영 기준 → 서비스 정책 보완
```

### 유형 내 연결 (복수 정책서 간)

동일 도메인 또는 연관 도메인의 서비스 정책서가 복수 존재할 때:

- **용어 통일**: 동일 개념에 대해 각 문서에서 동일한 용어를 사용한다
- **범위 중복 방지**: 정책 적용 범위가 겹치지 않도록 경계를 명확히 한다
- **상호 참조**: 연관 정책서를 `참조 문서` 섹션에 명시하고 연결 관계를 기록한다

### 각 연결의 참조 항목

| 소스 문서 | 참조 항목 | 대상 문서 |
|-----------|-----------|-----------|
| PRD > 기능 목록 | 기능별 구현 방식 결정 | TRD |
| PRD > 타깃 유저 | 정책 적용 대상 정의 | 서비스 정책서 |
| PRD > 핵심 요구사항 | 메뉴/기능 구조 설계 | IA |
| TRD > API 명세 | IA 기능 파라미터 정의 | IA |
| TRD > 데이터 모델 | IA 기능 조건 반영 | IA |
| 서비스 정책서 > 회원 정책 | 회원 관련 기능 제약 조건 | IA |
| 서비스 정책서 > 결제/환불 정책 | 결제 흐름 기능 정의 | IA |
| 서비스 정책서 > 서비스 규정 | 운영 처리 기준 도출 | 운영 정책서 |

## 3. 순서 체인

### 기본 흐름

```
PRD → TRD → 서비스 정책서 → IA
```

1. **PRD**: 제품 목표와 요구사항을 먼저 확립
2. **TRD**: PRD 기반으로 기술 구현 방식 설계
3. **서비스 정책서**: 요구사항 기반으로 도메인별 정책 상세화
4. **IA**: 앞선 세 문서를 종합하여 정보 구조와 기능을 정의

### 역방향 가능

어떤 문서든 먼저 작성할 수 있다. 프로젝트 상황에 따라 시작점이 달라질 수 있다:

- **TRD 선행**: 기술 스택이 먼저 결정된 경우
- **서비스 정책서 선행**: 규제/컴플라이언스 요건이 우선인 경우
- **IA 선행**: 화면 기획 중심으로 시작한 경우

### 역방향 처리 규칙

선행 문서가 나중에 작성될 경우, 정합성 재검증을 수행한다:

1. 이미 작성된 문서에서 선행 문서와 충돌하는 내용을 식별한다
2. 충돌 항목을 `diagnosis.json`의 `issues`에 기록한다
3. 영향 받는 문서를 보강(보강/재작성) 대상으로 재분류한다

## 4. 수정 시 영향 분석

### 절차

```
수정 대상 문서 식별
  └→ diagnosis.json에서 connected_to 문서 목록 조회
       └→ 각 연결 문서에 대해 영향 수준 판단
            └→ 연쇄 업데이트 범위 결정
```

### 영향 수준 판단

| 수준 | 기준 | 처리 |
|------|------|------|
| **직접** | 수정된 항목이 연결 문서의 특정 섹션에 직접 인용되거나 반영됨 | 해당 섹션 즉시 보강/재작성 |
| **간접** | 수정된 항목의 상위 개념이 연결 문서의 방향에 영향을 줌 | 정합성 검토 후 필요 시 보완 |
| **없음** | 수정 내용이 연결 문서와 실질적 관련이 없음 | 스킵 |

### 연쇄 업데이트 범위 결정

1. 직접 영향 문서: `status`를 `보강` 또는 `재작성`으로 갱신
2. 간접 영향 문서: `status`를 `OK`로 유지하되 `issues`에 검토 메모 추가
3. 변경된 diagnosis.json을 기반으로 배치를 재편성

## 5. diagnosis.json 스키마

Phase 2 PM 진단 산출물 JSON 구조.

```json
{
  "project": "프로젝트명",
  "scan_path": "기존 문서 경로",
  "documents": [
    {
      "id": "고유 식별자 (kebab-case)",
      "type": "PRD | TRD | 서비스 정책서 | IA | 기능도 | 순서도 | 운영 정책서 | 서비스 매뉴얼",
      "name": "문서명",
      "path": "기존 경로 (없으면 null)",
      "status": "보강 | 재작성 | 신규 | OK",
      "version": "현재 버전 (없으면 null)",
      "issues": ["이슈 목록"],
      "depends_on": ["의존 문서 id"],
      "connected_to": ["연결 문서 id"]
    }
  ],
  "batches": [
    {
      "batch": 1,
      "items": ["문서 id 목록"],
      "reason": "배치 사유 (독립/의존 설명)"
    }
  ]
}
```

### 필드 설명

| 필드 | 설명 |
|------|------|
| `id` | kebab-case 고유 식별자. 예: `prd-main`, `policy-member`, `ia-v1` |
| `type` | 산출물 유형 (섹션 1 정의 기준) |
| `name` | 문서 제목 (사람이 읽는 이름) |
| `path` | 파일 경로. 아직 없으면 `null` |
| `status` | 처리 방향: 보강(일부 수정), 재작성(전면 재작성), 신규(새로 생성), OK(변경 없음) |
| `version` | 현재 버전 문자열. 없으면 `null` |
| `issues` | 발견된 문제, 누락, 불일치 목록 |
| `depends_on` | 이 문서 작성 전에 완료되어야 하는 문서 id 목록 |
| `connected_to` | 논리적으로 연결된 문서 id 목록 (의존과 무관하게 정합성 체크 대상) |
| `batches` | 의존 관계 기반 병렬/순차 작업 그룹 |

## 6. Phase 1 워커 프롬프트 템플릿

문서 분석 워커에게 전달하는 표준 프롬프트.

```
## 작업 지시

당신은 기존 기술 문서를 분석하는 전문가입니다.

### 분석 대상
- 스캔 경로: {scan_path}
- 프로젝트: {project_name}

### 수행 작업

1. 지정 경로에서 기술 문서 목록을 파악한다.
2. 각 문서를 읽고 다음을 판단한다:
   - 문서 유형 (PRD / TRD / 서비스 정책서 / IA / 기능도 / 순서도 / 운영 정책서 / 서비스 매뉴얼)
   - 현재 품질 수준과 이슈
   - 처리 방향 (보강 / 재작성 / OK)
3. 문서 간 논리적 연결 관계를 파악한다 (connected_to).
4. 작성 순서 의존성을 파악한다 (depends_on).
5. 의존 관계를 바탕으로 배치를 편성한다 (batches).

### 출력 형식

아래 스키마를 따르는 diagnosis.json을 작성한다:

{diagnosis_json_schema}

### 주의 사항

- 존재하지 않는 문서는 status를 "신규"로 설정하고 path를 null로 한다.
- 이슈는 구체적으로 기술한다 ("내용 부족"보다 "결제 취소 정책 미정의" 형태로).
- 판단이 불확실한 경우 issues에 "확인 필요: {내용}" 형태로 기록한다.
```

## 8. 배치 편성 규칙

### 기본 원칙

`depends_on` 필드를 기준으로 배치를 자동 편성한다.

```
depends_on가 없는 문서  →  같은 배치 (병렬 처리 가능)
depends_on가 있는 문서  →  의존 문서 배치 완료 후 다음 배치
```

### 편성 알고리즘

1. `depends_on`이 비어 있거나 이미 완료된 항목만 참조하는 문서를 배치 1로 묶는다.
2. 배치 1 완료 후 새로 의존성이 해소되는 문서를 배치 2로 묶는다.
3. 모든 문서가 배치에 편성될 때까지 반복한다.
4. 각 배치의 `reason`에 독립/의존 관계를 명시한다.

### 예시

```json
{
  "batches": [
    {
      "batch": 1,
      "items": ["prd-main", "policy-member"],
      "reason": "의존 문서 없음. 병렬 처리 가능."
    },
    {
      "batch": 2,
      "items": ["trd-main", "policy-payment"],
      "reason": "trd-main은 prd-main에 의존. policy-payment는 policy-member에 의존."
    },
    {
      "batch": 3,
      "items": ["ia-v1"],
      "reason": "ia-v1은 prd-main, trd-main, policy-member, policy-payment 모두에 의존."
    }
  ]
}
```

### 순환 의존 감지

`depends_on`을 따라가다 자기 자신으로 돌아오는 경우 순환 의존으로 판단한다.

- 순환 의존 감지 시: 배치 편성을 중단하고 PM에게 판단을 요청한다
- 보고 형식: "순환 의존 감지: {문서 A} → {문서 B} → {문서 A}. 의존 방향을 재검토해주세요."

## 9. IA 형식 가이드

### IA JSON 스키마

IA는 메뉴 구조와 기능 정의를 통합한 JSON으로 작성한다.

```json
{
  "service": "서비스명",
  "version": "1.0",
  "menus": [
    {
      "id": "메뉴 고유 식별자 (kebab-case)",
      "name": "메뉴명",
      "depth": 1,
      "parent_id": null,
      "path": "URL 경로 (해당 시)",
      "access": "public | member | admin",
      "features": [
        {
          "id": "기능 고유 식별자",
          "name": "기능명",
          "description": "기능 설명",
          "conditions": ["조건 1", "조건 2"],
          "linked_policy": ["연관 정책서 id"]
        }
      ],
      "children": []
    }
  ]
}
```

#### 필드 설명

| 필드 | 설명 |
|------|------|
| `menus[].id` | kebab-case 고유 식별자. 예: `home`, `mypage-order` |
| `menus[].depth` | 메뉴 깊이. 최상위 = 1 |
| `menus[].parent_id` | 부모 메뉴 id. 최상위는 `null` |
| `menus[].access` | 접근 권한: `public`(비회원), `member`(로그인 필요), `admin`(관리자) |
| `features[].conditions` | 기능 실행 조건 또는 비즈니스 규칙 |
| `features[].linked_policy` | 이 기능과 관련된 서비스 정책서 id |

### JSON → xlsx 변환 프로세스

IA JSON이 확정된 후 xlsx로 변환한다.

1. **검토 완료 확인**: PM이 JSON 내용을 검토하고 승인한다.
2. **변환 실행**: JSON 구조를 xlsx 시트로 변환한다.
   - Sheet 1: 메뉴 구조 (id, name, depth, parent_id, path, access)
   - Sheet 2: 기능 정의 (menu_id, feature_id, name, description, conditions, linked_policy)
3. **경로**: JSON과 동일 경로에 같은 이름으로 저장. 예: `ia.json` → `ia.xlsx`

### .md 폴백

xlsx 변환이 불필요한 경우(스타트업 초기, 내부 팀 협업 등) `.md` 형태로 대체한다.

- 메뉴 구조: 계층형 목록(unordered list)으로 표현
- 기능 정의: 각 메뉴 섹션 하위에 테이블 형태로 작성
- 조건/정책 연결: 인라인 주석 또는 별도 "조건 및 정책 연결" 섹션으로 기술
