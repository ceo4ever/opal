# 분석 가이드 — analysis-guide.md

dtp-analysis 스킬의 핵심 분석 프로세스를 정의한다. 기술 컨텍스트 로딩은 `tech-context-guide.md`에서 별도로 수행한다.

## 분석 프로세스

### 1단계: 기존 코드베이스 분석

TASK.md의 요구사항을 기반으로 관련 코드를 탐색하고 구조를 파악한다.

#### 1.1 파일 탐색

1. **Glob**: 관련 디렉토리 구조 파악
   - 프로젝트 루트의 주요 디렉토리 확인
   - TASK.md에서 언급된 경로/모듈 우선 탐색
2. **Grep**: 키워드 기반 관련 파일 식별
   - TASK.md의 핵심 키워드 (함수명, 클래스명, 엔드포인트 등)
   - 에러 메시지, 로그 패턴 (오류 수정 태스크)
3. **Read**: 식별된 파일의 상세 분석
   - 파일 전체를 읽지 말고, 관련 섹션을 집중 분석한다
   - 200줄 이상 파일은 offset/limit으로 필요 부분만 Read

#### 1.2 패턴 파악

- 네이밍 컨벤션 (파일명, 변수명, 함수명)
- 디렉토리 구조 규약
- 에러 처리 패턴
- 로깅 패턴
- 설정 관리 방식
- 공통 유틸/헬퍼 존재 여부

#### 1.3 의존성 맵

- import/require 그래프: 변경 대상 → 직접 의존 → 간접 의존
- 외부 패키지 의존성 (package.json, requirements.txt 등)
- 내부 모듈 간 호출 관계
- 순환 의존성 여부

#### 1.4 테스트 현황

- 테스트 디렉토리/파일 존재 여부
- 테스트 프레임워크 (jest, pytest, go test 등)
- 변경 대상 관련 기존 테스트 유무
- 테스트 커버리지 수준 (측정 가능한 경우)

### 분석 깊이 기준

TASK.md의 `type` 또는 내용에 따라 분석 범위를 조절한다:

| 태스크 유형 | 분석 범위 | 설명 |
|-------------|----------|------|
| **신규 기능** | 전체 구조 | 삽입 지점, 기존 패턴과의 정합성, 전체 아키텍처 영향 |
| **기능 개선** | 변경 대상 + 직접 의존 | 변경 모듈과 이를 호출/참조하는 모듈 |
| **버그 수정** | 변경 대상 + 영향 범위 | 버그 발생 지점과 파급 경로 |
| **오류 수정** | 에러 역추적 | 에러 로그 → 호출 스택 → 원인 모듈 역추적 |

### 데이터 파이프라인 작업 추가 사항

데이터 흐름이 포함된 태스크의 경우 추가로 분석한다:

- **데이터 소스**: 입력 데이터의 출처, 형식, 볼륨
- **변환 단계**: ETL/ELT 파이프라인의 각 단계
- **데이터 스키마**: 테이블/컬렉션 구조, 필드 타입, 인덱스
- **데이터 무결성**: 제약 조건, 유효성 검사 규칙
- **성능 특성**: 쿼리 패턴, 배치 크기, 타임아웃

### 2단계: 외부 API/라이브러리 조사

TASK.md에서 외부 의존성이 식별된 경우 수행한다.

#### 2.1 context7 MCP 활용

```
1. resolve-library-id: 라이브러리명으로 ID 조회
2. get-library-docs: ID로 공식 문서 조회 (topic 파라미터로 범위 한정)
```

**활용 시점**:
- 새 라이브러리/프레임워크 도입 시
- 기존 라이브러리의 특정 API 사용법 확인 시
- 버전 업그레이드에 따른 breaking change 확인 시

#### 2.2 WebSearch 활용

context7에 없는 경우 또는 최신 정보가 필요한 경우:
- 공식 문서 사이트 검색
- GitHub Issues/Discussions
- 릴리스 노트, 마이그레이션 가이드
- Stack Overflow (검증된 답변만 참조)

#### 2.3 조사 결과 기록

- 확인된 API 시그니처, 사용 예시
- 버전 호환성 매트릭스
- 알려진 이슈/제한사항
- 대안 라이브러리 (필요 시)

### 3단계: 유사 구현 패턴 참조 + 아키텍처 정합성

#### 3.1 유사 패턴 검색

프로젝트 내에서 요구사항과 유사한 기존 구현을 찾는다:
- 동일 패턴의 다른 모듈 (예: 다른 CRUD 엔드포인트)
- 비슷한 기능의 컴포넌트 (예: 다른 폼 컴포넌트)
- 참조할 수 있는 테스트 패턴

#### 3.2 아키텍처 정합성 확인

- 새 코드가 기존 아키텍처 원칙에 부합하는가
- 레이어 간 의존성 방향이 올바른가
- 관심사 분리가 유지되는가
- 기존 공통 모듈/유틸을 활용할 수 있는가

### 4단계: 영향 범위 분석

#### 4.1 직접 영향

- 생성/수정/삭제 대상 파일 목록
- 변경되는 인터페이스 (API, 타입, 스키마)

#### 4.2 간접 영향

- 변경된 모듈을 import하는 파일 (Grep으로 확인)
- 변경된 API를 호출하는 클라이언트
- 영향받는 테스트 파일
- 설정/환경변수 변경에 의한 파급

#### 4.3 영향 범위 체크리스트

- [ ] DB 스키마 변경 → 마이그레이션 필요 여부
- [ ] API 인터페이스 변경 → 하위 호환성 유지 여부
- [ ] 설정/환경변수 변경 → .env.example 업데이트 필요 여부
- [ ] 빌드/배포 파이프라인 변경 → CI/CD 수정 필요 여부
- [ ] 공유 라이브러리 변경 → 다른 프로젝트 영향 여부

### 5단계: 원인 분석 Root Cause (오류 수정 전용)

버그/오류 수정 태스크에서만 수행한다:

1. **증상 정리**: 에러 메시지, 재현 조건, 발생 빈도
2. **역추적**: 에러 발생 지점 → 호출 스택 → 근본 원인
3. **근본 원인 식별**: 단순 증상이 아닌 구조적 원인 파악
4. **영향 확인**: 같은 원인에 의한 다른 잠재적 문제
5. **수정 방향**: 근본 원인 해결 vs 증상 완화의 트레이드오프

## 분석 품질 체크리스트

ANALYSIS.md 작성 완료 후 다음을 검증한다:

### 완전성
- [ ] TASK.md의 모든 요구사항이 분석에 반영되었는가
- [ ] 관련 파일 목록이 Glob/Grep으로 실제 확인되었는가 (추측 금지)
- [ ] 의존성 맵이 import/require 기반으로 작성되었는가

### 정확성
- [ ] 파일 경로가 실제 존재하는가
- [ ] 버전 정보가 실제 설정 파일에서 추출되었는가
- [ ] 외부 조사 결과가 공식 소스에서 확인되었는가

### 유용성
- [ ] 영향 범위가 직접+간접 모두 식별되었는가
- [ ] 제약/리스크가 구체적 근거와 함께 기술되었는가
- [ ] 다음 단계(PLAN)에서 바로 활용할 수 있는 수준인가
