# PLAN 단계 상세 가이드

이 가이드는 dtp-plan 스킬에서 참조된다. Full Task와 Short Task 모두에서 동일하게 사용된다.

> **실행 컨텍스트**: 이 가이드는 워커 에이전트의 컨텍스트에서 실행된다.
> 오케스트레이터가 워커를 디스패치하면, 워커가 이 가이드를 읽고 프로세스를 따른다.
> 서브 에이전트 사용이 불가능한 플랫폼에서는 오케스트레이터가 직접 이 가이드를 따른다.

---

## 0단계: 기술 컨텍스트 로딩 (의무)

ANALYSIS.md가 있으면 "6. 기술 컨텍스트" 섹션을, 없으면 TASK.md와 프로젝트 문서를 참조하여 기술 스택을 파악한다.

1. **기술 스택 확인**: 식별된 기술 스택 + 추천 스킬/MCP 목록 확인
2. **추천 스킬 Read**: 추천 스킬의 SKILL.md를 Read하여 설계 결정에 반영할 규칙/패턴을 파악
   - 예: react-best-practices -> dynamic import, 워터폴 제거 패턴
   - 예: modern-python -> uv, ruff, async session 패턴
   - 예: shadcn -> FieldGroup/Field 폼 구조, gap 레이아웃 규칙
3. **MCP 활용**: context7로 최신 API 문서 참조, shadcn MCP로 컴포넌트 조회
4. **FE 설계 시**: ui-designer SKILL.md의 "화면 유형별 구현 패턴"과 "shadcn Critical Rules"를 참조
   - 탐색: `{프로젝트}/.opal/skills/ui-designer/SKILL.md` -> `~/.opal/skills/ui-designer/SKILL.md`
5. 설계에 영향을 미친 스킬/MCP를 PLAN.md "기술 컨텍스트" 섹션에 기록

## 입력 기반 분기: 코드 분석

### ANALYSIS.md 존재 시

ANALYSIS.md의 분석 결과를 참조하여 "1. 코드 분석" 섹션을 간략 작성한다.
ANALYSIS.md에서 이미 파악한 코드 구조, 핵심 로직, 영향 범위를 요약 인용하고, 설계에 집중한다.

### ANALYSIS.md 미존재 시

직접 코드 분석을 수행한다. Full ANALYSIS 수준의 깊이로 실제 코드를 읽어야 한다.

> Short Task는 단계를 줄여 속도를 높이는 것이지, 분석 품질을 낮추는 것이 아니다.
> 충분한 분석 없이 계획을 세우면 구현 중 재작업이 발생한다.

**코드 분석은 반드시 실제 코드를 Read/Grep/Glob으로 읽어서 수행한다. 추측하지 않는다.**

#### 작업 유형별 분석 깊이

| 분석 영역 | 개선 | 수정 | 오류 |
|----------|------|------|------|
| 기존 코드 구조 파악 | ● | ● | ● |
| 핵심 로직 흐름 추적 | ● | ● | ● |
| 영향 범위 (호출자/피호출자) | ● | ● | ○ |
| 원인 분석 (Root Cause) | - | - | ● |
| 데이터 흐름 추적 | ○ | ○ | ● |

(● 필수 / ○ 선택 / - 불필요)

#### "현재 구현" 작성 시 포함할 내용

- 관련 함수/클래스의 시그니처와 역할
- 핵심 로직의 실행 흐름 (입력 -> 처리 -> 출력)
- 사용 중인 외부 라이브러리/API의 호출 방식
- 설정값이나 환경변수 의존성

#### "영향 범위" 작성 시 포함할 내용

- 변경 대상을 호출하는 코드 (상위 의존)
- 변경 대상이 호출하는 코드 (하위 의존)
- 공유 데이터 구조나 상태에 미치는 영향
- 관련 테스트 파일

## 1단계: 구현 범위 확정

ANALYSIS.md(있는 경우) 또는 직접 분석에서 파악한 변경 필요 파일 목록을 확정한다.

```markdown
## 파일 변경 계획

### 신규 생성
| # | 파일 경로 | 역할 |
|---|----------|------|

### 수정
| # | 파일 경로 | 변경 내용 |
|---|----------|----------|

### 영향 확인 (변경 없지만 테스트 필요)
| # | 파일 경로 | 확인 사항 |
|---|----------|----------|
```

## 2단계: 구현 순서 결정

의존성을 고려하여 순서를 정한다. 원칙: **의존 받는 쪽(하위 레이어)부터 구현한다.**

프로젝트의 아키텍처에 맞게 순서를 조정한다. 일반적으로:
1. 설정/인프라 모듈 -> 다른 모든 코드가 의존
2. 데이터 모델 -> 비즈니스 로직의 기반
3. 핵심 비즈니스 로직 -> 외부 인터페이스에서 호출
4. 외부 인터페이스 (API, UI) -> 최상위
5. 테스트 -> 각 단계별 검증

### 영역 태그 규칙 (FE + BE 작업 시)

FE + BE 모두 포함하는 작업에서는 각 구현 항목에 영역 태그를 부여한다:

- `[FE]` -- 프론트엔드 전용 (컴포넌트, 페이지, 스타일링)
- `[BE]` -- 백엔드 전용 (모델, 서비스, 라우터, DTO)
- `[공통]` -- FE/BE 공유 (타입 정의, 설정, 공유 DTO)

구현 순서 테이블에 영역 컬럼을 추가한다:

```markdown
| 순서 | 영역 | 작업 | 파일 | 예상 난이도 |
|------|------|------|------|-----------|
| 1 | [공통] | 공유 타입 정의 | shared/types.ts | 쉬움 |
| 2 | [BE] | 데이터 모델 | models/user.py | 보통 |
| 3 | [BE] | API 라우터 | routers/user.py | 보통 |
| 4 | [FE] | 사용자 목록 화면 | pages/users.tsx | 보통 |
```

영역 태그는 EXECUTE에서 FE/BE 병렬 디스패치의 기반이 된다.

## 3단계: 핵심 설계 명세

각 파일의 핵심 구현 내용을 명세한다. 전체 코드를 쓰는 것이 아니라, **클래스/함수 시그니처와 핵심 로직**을 정의한다.

작성해야 할 내용:
- **클래스 구조**: 상속 관계, 주요 메서드
- **함수 시그니처**: 파라미터, 반환 타입, 역할 설명
- **데이터 모델**: 모델/DTO의 필드 목록과 타입
- **쿼리**: 주요 SQL/쿼리문
- **설정값**: 환경변수 추가 항목

**FE 화면 설계 시** (0단계에서 ui-designer 참조한 경우):
- 각 화면의 유형(dashboard, crud, form, auth, detail, settings, report, monitor)을 명시
- 화면별 주요 shadcn 컴포넌트를 명시
- 화면별 action(new: 신규 생성 / modify: 기존 수정)을 명시
- 인터랙션(사용자 동작 -> 결과)을 정의

## 6단계: execution-plan.json 생성 (FE/BE 작업 시)

FE 또는 BE 작업이 포함된 태스크에서는 execution-plan.json을 생성한다.
이 파일은 EXECUTE 단계에서 FE/BE 병렬 디스패치의 입력으로 사용된다.

**저장 경로**: `tasks/{NNN}-{태스크명}/execution-plan.json`

**생성 조건**:
- FE 또는 BE 작업이 있으면 생성
- 문서 전용 작업이면 생성하지 않음
- Short Task에서도 FE/BE 작업이면 생성

**스키마**: dtp-plan SKILL.md의 "execution-plan.json 스키마" 섹션 참조.

**BE layers 순서 규칙**: model -> dto -> service -> router (하위 레이어부터)
**FE screens**: 화면별 독립 단위. 각 screen은 ui-designer plan-driven 모드의 입력으로 사용됨.
**common**: FE/BE 공유 타입, 설정 등. 반드시 먼저 실행.
**frontend/backend가 비어있으면**: 해당 키를 생략하거나 빈 배열로 둔다.

## 실행 체크리스트 작성

구현 순서를 바탕으로 실행 체크리스트를 작성한다.

```markdown

- [ ] Step 1: {제목} -- {파일} -- {작업 내용}
- [ ] Step 2: ...
```

## QA 에이전트 호출 안내

PLAN.md 작성이 완료되면, **오케스트레이터가 QA 에이전트를 호출**한다.

> **워커는 QA를 호출하지 않는다.** 워커는 PLAN.md 경로와 요약을 오케스트레이터에 반환하고, 오케스트레이터가 QA 에이전트를 별도로 호출한다.
