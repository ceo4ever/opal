# PLAN 단계 상세 가이드

이 가이드는 Full Task와 Short Task 모두에서 참조된다.

---

## Full Task PLAN

RESEARCH.md의 분석 결과를 바탕으로, "어떤 파일을 어떤 순서로 어떻게 구현할지" 구체적 계획을 세운다.
PLAN은 "설계서"가 아니라 "실행 가능한 구현 청사진"이다. 이 문서를 보고 바로 코딩에 들어갈 수 있어야 한다.

---

### 계획 수립 프로세스

#### 1단계: 구현 범위 확정

RESEARCH.md에서 파악한 변경 필요 파일 목록을 확정한다.

```markdown
## 파일 변경 계획

### 신규 생성
| # | 파일 경로 | 역할 |
|---|----------|------|

### 수정
| # | 파일 경로 | 변경 내용 |
|---|----------|----------|

### 영향 확인 (변경 없지만 테스트 필요)
| # | 파일 경로 | 확인 사항 |
|---|----------|----------|
```

#### 2단계: 구현 순서 결정

의존성을 고려하여 순서를 정한다. 원칙: **의존 받는 쪽(하위 레이어)부터 구현한다.**

프로젝트의 아키텍처에 맞게 순서를 조정한다. 일반적으로:
1. 설정/인프라 모듈 → 다른 모든 코드가 의존
2. 데이터 모델 → 비즈니스 로직의 기반
3. 핵심 비즈니스 로직 → 외부 인터페이스에서 호출
4. 외부 인터페이스 (API, UI) → 최상위
5. 테스트 → 각 단계별 검증

#### 3단계: 핵심 설계 명세

각 파일의 핵심 구현 내용을 명세한다. 전체 코드를 쓰는 것이 아니라, **클래스/함수 시그니처와 핵심 로직**을 정의한다.

작성해야 할 내용:
- **클래스 구조**: 상속 관계, 주요 메서드
- **함수 시그니처**: 파라미터, 반환 타입, 역할 설명
- **데이터 모델**: 모델/DTO의 필드 목록과 타입
- **쿼리**: 주요 SQL/쿼리문
- **설정값**: 환경변수 추가 항목

#### 4단계: 의존성 및 환경 변경

추가 패키지, 환경 설정 변경 사항을 정리한다.

#### 5단계: 테스트 전략

어떤 테스트를 작성할지, 각 테스트의 성공 기준을 정의한다.

---

### PLAN.md 출력 형식

```markdown
# PLAN: {태스크 제목}

> 작성일: YYYY-MM-DD | 참조: TASK.md, RESEARCH.md

## 1. 구현 범위
### 신규 생성 파일
### 수정 파일

## 2. 구현 순서
| 순서 | 작업 | 파일 | 예상 난이도 |
|------|------|------|-----------|

## 3. 핵심 설계
### 3.1 {컴포넌트명}
### 3.2 {컴포넌트명}

## 4. 의존성 및 환경 변경

## 5. 테스트 전략

## 6. 리스크 및 대응
| 리스크 | 영향 | 대응 방안 |
|--------|------|----------|
```

---

### 계획 품질 체크리스트

- [ ] 이 PLAN만 보고 바로 코딩에 들어갈 수 있는가?
- [ ] 구현 순서의 의존성이 올바른가? (하위 레이어 먼저)
- [ ] RESEARCH에서 발견한 제약/리스크가 PLAN에 반영되었는가?
- [ ] 테스트 전략이 TASK.md의 요구사항을 모두 커버하는가?
- [ ] 프로젝트 코드 컨벤션을 따르는가?

### QA 에이전트 호출 (필수)

이 가이드의 산출물 작성이 완료되면, 반드시 **QA 에이전트를 호출**해야 한다.
자체 품질 체크리스트 검증만으로는 불충분하며, QA 에이전트의 독립적 리뷰를 거쳐야 사용자에게 보고할 수 있다.

**호출 방법**: SKILL.md의 "QA 에이전트 호출 규칙" 섹션을 참조하여 서브 에이전트(Task 도구)로 실행한다.

## Short Task 통합 PLAN

Short Task에서는 RESEARCH, PLAN, TODO를 하나의 **PLAN.md**로 통합한다.
별도 단계를 분리하지 않고, 코드 분석부터 실행 체크리스트까지 한 문서에서 완결한다.

---

### 통합 PLAN 작성 프로세스

> ⚠️ **Short Task는 단계를 줄여 속도를 높이는 것이지, 분석 품질을 낮추는 것이 아니다.** 코드 분석은 Full Task의 RESEARCH와 동일한 깊이로 수행해야 한다. 충분한 분석 없이 계획을 세우면 구현 중 재작업이 발생한다.

1. **코드 분석** (Full Task RESEARCH 수준): 기존 코드를 실제로 읽고 구조·흐름·영향 범위를 파악한다.
2. **구현 계획**: 변경할 파일과 변경 내용을 구체적으로 정의한다.
3. **실행 체크리스트**: 구현 순서대로 Step을 나열한다 (5개 이하 권장).
4. **QA 체크리스트**: 기능 테스트, 회귀 테스트, 코드 품질 항목을 정의한다.

#### 코드 분석 상세 프로세스

코드 분석은 반드시 **실제 코드를 Read/Grep/Glob으로 읽어서** 수행한다. 추측하지 않는다.

**작업 유형별 분석 깊이:**

| 분석 영역 | 개선 | 수정 | 오류 |
|----------|------|------|------|
| 기존 코드 구조 파악 | ● | ● | ● |
| 핵심 로직 흐름 추적 | ● | ● | ● |
| 영향 범위 (호출자/피호출자) | ● | ● | ○ |
| 원인 분석 (Root Cause) | - | - | ● |
| 데이터 흐름 추적 | ○ | ○ | ● |

(● 필수 / ○ 선택 / - 불필요)

**"현재 구현" 작성 시 포함할 내용:**
- 관련 함수/클래스의 시그니처와 역할
- 핵심 로직의 실행 흐름 (입력 → 처리 → 출력)
- 사용 중인 외부 라이브러리/API의 호출 방식
- 설정값이나 환경변수 의존성

**"영향 범위" 작성 시 포함할 내용:**
- 변경 대상을 호출하는 코드 (상위 의존)
- 변경 대상이 호출하는 코드 (하위 의존)
- 공유 데이터 구조나 상태에 미치는 영향
- 관련 테스트 파일

---

### Short Task PLAN.md 출력 형식

```markdown
# PLAN: {태스크 제목}

> 작성일: YYYY-MM-DD | 모드: Short Task | 참조: TASK.md

## 1. 코드 분석
### 관련 파일
| 파일 | 역할 | 변경 필요 |
|------|------|----------|
### 현재 구현
{핵심 로직 흐름: 입력 → 처리 → 출력}
{관련 함수/클래스 시그니처와 역할}
{외부 라이브러리/API 호출 방식}
### 영향 범위
{호출자/피호출자 의존 관계}
{공유 데이터 구조/상태 영향}
{관련 테스트 파일}

## 2. 구현 계획
### 변경 파일
| # | 파일 경로 | 변경 내용 |
|---|----------|----------|
### 핵심 설계
{클래스/함수 시그니처, 변경 포인트 등}

## 3. 실행 체크리스트
- [ ] Step 1: {제목} — {파일} — {작업 내용}
- [ ] Step 2: ...

## 4. QA 체크리스트
### 기능 테스트
- [ ] {항목}
### 회귀 테스트
- [ ] {항목}
### 코드 품질
- [ ] {항목}
```

---

### Short Task 품질 체크리스트

- [ ] 관련 코드를 **실제로 읽고** 분석했는가? (추측 금지)
- [ ] 핵심 로직의 실행 흐름을 파악했는가?
- [ ] 변경의 영향 범위(호출자/피호출자)를 확인했는가?
- [ ] 구현 계획이 구체적인가? (파일별 변경 내용 명시)
- [ ] 실행 체크리스트가 TASK.md 요구사항을 모두 커버하는가?
- [ ] QA 항목이 기능/회귀/품질을 포함하는가?
- [ ] Step 수가 5개 이하인가? (초과 시 에스컬레이션 고려)

---

SKILL.md의 "QA 에이전트 호출 규칙"을 참조.
