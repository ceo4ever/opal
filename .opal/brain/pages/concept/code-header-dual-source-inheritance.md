## 개요

코드 헤더를 기록할 수 있는 자리가 소스 파일 안(인라인 주석)과 프로젝트 외부의 별도 지도, 두 곳으로 늘었다. 조회 시점에는 이 두 자리의 값을 필드 단위로 합쳐 하나의 헤더로 해석하되, 파일에 인라인 헤더가 있으면 그 파일에 대해서는 외부 지도의 값을 전혀 참고하지 않는다(근거: task:077 PLAN§3.2.2(G)).

## 결정 배경 (WHY)

소스를 고칠 수 없거나 수정 부담이 지나치게 큰 코드베이스는 그동안 헤더를 남길 방법 자체가 없었다(근거: task:077 DONE.md §1). 이를 해소하려면 외부에 별도 기록 공간을 두어야 했는데, 두 공간의 값을 필드마다 자유롭게 병합해 버리면 어떤 필드가 어느 자리에서 왔는지 추적할 수 없게 되어 신뢰가 무너진다는 점이 병합 방식을 기각한 이유였다(근거: task:077 DONE.md §3 결정2). 그래서 상속 순서를 다섯 단계로 서열화하되(파일 인라인 → 파일 단위 지도 항목 → 디렉토리 단위 지도 항목 → 레이어 규칙 → 도메인 규칙), 인라인이 하나라도 존재하는 파일은 인라인 값만 채택하고 나머지 네 단계는 아예 참조하지 않는다(근거: task:077 PLAN§3.2.2(G)3 "병합 없음, 파일 단독 승리").

## 결정 내용

외부 지도는 파일마다 흩어놓지 않고, 소스 트리와 같은 모양의 디렉토리(패키지) 단위 미러 트리 하나로 모은다. 값을 채울 때는 필드별로 가장 가까운 단계가 이긴다 — 예를 들어 노출 인터페이스나 설명 문구는 파일 단위 지도 항목이 디렉토리 단위 지도 항목보다 우선하고, 소속 레이어·도메인은 규칙 매칭 결과를 따른다(근거: task:077 PLAN§3.2.2(G)5 필드별 tier 표). 지도가 아예 없는 프로젝트에서는 이 전체 해석 로직이 즉시 우회되어, 지도 도입 이전과 완전히 동일한 조회 결과를 돌려준다 — 기존 여덟 가지 조회 동작의 결과를 하나도 바꾸지 않기 위한 제약이다(근거: task:077 PLAN§3.2.2(A),(H)3).

## 영향 범위

기존 여덟 가지 헤더 조회 동작 전체의 해석 경로, 신규 기록 위치 판정, 검증 동작의 위반 판정.
