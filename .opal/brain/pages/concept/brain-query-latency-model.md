## 개요

> **[정정 2026-08-20 — 소유자 확인]** 아래 원 진단("병목은 멀티턴 루프이고 프레임워크 로딩은 아니다")은 **오진이었다.** 실제 병목은 **헤드리스 호출 시 OPAL 부트스트랩이 전부 로딩되는 것**이었고, 브레인 검색(멀티턴) 자체는 문제가 아니었다. 해결은 부트스트랩 로드 범위를 캡하는 방식으로 이뤄졌다 — §해소 절 참조.

브레인 질의 콜드 지연의 병목은 **헤드리스 호출(`-p`)이 프로젝트 디렉토리에서 실행될 때 OPAL 부트스트랩 전체가 로딩되는 것**이다. 브레인 검색 자체는 소유자 확인상 현재 수준으로 충분하며, brain-tool의 키워드 검색·랭킹은 결정론적 파이썬 로직으로 0.15초 내 완료된다.

## 결정 배경 (WHY)

- 브레인 질의 콜드 시간 ≈69초, 웜 시간 ≈20초를 측정·분석한 결과, 대부분의 시간이 `claude -p` 서브프로세스 내 멀티턴 에이전트 루프(도구 호출 왕복 N회)에서 소모된다.
- brain-tool의 검색·랭킹(`pages/` 파일 스캔 + TF-IDF 유사 키워드 매칭)은 OPAL 프레임워크가 실행되는 파이썬 프로세스에서 결정론적으로 처리되어 ≈0.15초.
- "질문→검색어 변환"만 1턴 LLM으로 수행하고, 검색 자체는 brain-tool에 위임하면 멀티턴 루프를 "검색 밖+합성 1턴"(≈21초)으로 압축할 수 있다는 PoC가 완료됨.

> **[PoC 오진 경위 — 2026-08-20 기록]** PoC는 `claude -p "OK"` 바닥값(3.7~5.3초)을 근거로 "부트스트랩 로딩은 작다"고 결론했다. 그러나 그 측정은 **자명 프롬프트**여서 실제 질의 경로를 재현하지 못했다 — `//opbr` 진입은 PM tier 승격 + 프로젝트 정의·메모리·PM 컨텍스트 로드를 유발하는데 자명 프롬프트는 그 경로를 타지 않는다. **측정 대상이 실환경 경로를 재현하지 않아 병목 위치를 반대로 지목한 사례**다.

## 결정 내용 (HOW)

**현재 구조(037 기준)**:
- `claude -p` (in-agent) → 멀티턴 루프: 질문 이해 → brain-tool search → 페이지 fetch → 합성 (≈21~69초)
- 콜드 경로는 opbr 세션 초기화(≈5초) + 위 루프

**해소 — 부트스트랩 로드 범위 캡 (소유자 확인 2026-08-20)**:
- 당시 권고안(스킬에 경량 모드를 신설해 멀티턴을 2턴+도구로 압축, PoC 콜드 ≈21~26초)은 **폐기됐다.** 병목 지목 자체가 틀렸으므로 대책도 빗나갔다.
- **실제 해법**: 헤드리스 호출 프롬프트 첫 줄에 `[ASSISTANT]` 마커를 붙여 **비서 tier(Phase A)로 부트스트랩을 캡**한다 — 프로젝트 디렉토리에서 실행돼도 PM tier 승격을 억제해 프로젝트 정의·메모리·PM 컨텍스트 로드를 건너뛴다. 상세: [[bootstrap-marker-skip-ladder]]
- 브레인 검색(멀티턴) 자체는 손대지 않았고, 소유자 확인상 현재 수준으로 충분하다.
- **경량 모드 재제안 시 이 기록을 먼저 확인할 것** — 병목은 검색 루프가 아니라 부트스트랩 로드 범위였다.

**인사이트**: 헤드리스 호출은 실행 디렉토리에 따라 부트스트랩 로드 범위가 달라진다 — 같은 `-p` 호출이라도 프로젝트 안에서는 PM tier까지 로드된다. 지연을 논할 때는 **어느 tier까지 로드되는 경로인지**를 먼저 확정해야 하며, 자명 프롬프트 바닥값으로 대체 측정하면 병목을 놓친다.

## 영향 범위

- 037 기준 현재 구현: 비동기 잡+폴링으로 fetch 타임아웃 해소됨 (latency 자체는 동일)
- **해소 완료** — 부트스트랩 tier 캡(`[ASSISTANT]` 마커)으로 해결되어 후속 태스크 예약이 없다(2026-08-20). 경량 모드 방향과 대응 메모리는 정리됐다.
- `brain-tool search` 결정론성: `~/.opal/tools/brain-tool/` 파이썬 구현, 외부 LLM 호출 없음
