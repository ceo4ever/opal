## 개요

이름·서술만으로 항목을 의미 그룹으로 완전 자동 분류하는 것은 불가능하다는 실측 위에서, code-scan `split --plan`은 단일 규칙이 아니라 5단계 사다리로 후보를 제시하고, 사다리가 끝난 뒤에도 남는 항목은 임의로 배분하지 않고 "미분류"로 정직하게 남긴다.

## 결정 배경 (WHY)

파일명 접두사 하나로 자동 분류를 시도하면 상위 18개 토큰이 198건만 덮고 90건이 "기타"로 남는다는 것이 083 TASK 단계의 실측 근거다(근거: task:083 TASK.md 배경 분석 (6) "파일명 접두사로 분류하면 상위 18개 토큰이 198건만 덮고 90건이 '기타'로 남는다"). 단일 축 분류로는 커버리지가 구조적으로 부족하고, 그렇다고 남는 90건을 도구가 억지로 그룹에 밀어 넣으면 의미 없는 묶음이 생겨 사람이 나중에 다시 풀어야 한다. 도구의 역할은 후보 제시와 결정 집행까지이고, 경계 확정은 사람/워커의 몫이라는 것이 083의 명시적 전제다(근거: 같은 절 "도구의 역할은 후보 제시 + 결정 집행까지이며, 경계 확정은 사람/워커의 몫이다").

## 결정 내용

- 분류를 **5단계 사다리**(`SHARD_PLAN_LADDER`)로 수행한다 — S1(첫 토큰) → S2(첫 2토큰 결합) → S3(전체 토큰) → S4(마지막 토큰) → S5(`depends` 공유). 앞의 세 단계는 표준단어사전과 대조하고, 뒤의 두 단계는 사전 없이 이름·의존관계만으로 판단한다(근거: task:083 PLAN §3.4.2 (C) `SHARD_PLAN_LADDER` 정의, DONE.md §3.3).
- **각 단계는 직전 단계가 배정하지 못한 잔여만 입력으로 받고, 앞 단계의 배정은 후속 단계가 재배정하지 않는다.** 이 규칙 덕분에 같은 입력에 항상 같은 출력이 나온다(결정론) — 사다리 순서가 고정이므로 "이 그룹이 왜 S1이 아니라 S3에서 묶였는가"가 항상 재현 가능한 질문이 된다(근거: task:083 DONE.md §3.3 "각 단계는 직전 단계의 미분류분만 입력으로 받고, 앞 단계 배정은 후속 단계가 재배정하지 않는다").
- **잔여는 `unassigned`로 정직하게 남긴다. 도구는 임의 배분하지 않고 "기타" 그룹도 만들지 않는다.** 의미 경계를 확정하는 것은 사람의 몫이라는 원칙을 어기지 않기 위한 것이다(근거: task:083 DONE.md §3.3, TASK.md 배경 분석 (6)).
- 표준단어사전은 **읽기 전용·옵셔널** 대조다 — 부재·파싱 실패·매칭 0건 3분기 전부 비차단이며 명령을 막지 않는다. 이 사전 대조는 code-scan이 `.opal/` 밖의 문서를 읽는 첫 사례이고, 호출 지점은 `split --plan` 경로 1곳뿐이라 나머지 조회 8커맨드의 출력 바이트가 이 신설로 흔들리지 않는다(근거: task:083 DONE.md §3.3 "표준단어사전은 읽기 전용·옵셔널 대조다... 호출은 `split --plan` 경로 1곳뿐이라 조회 8커맨드의 출력 바이트가 흔들리지 않는다"; PLAN §리스크 가설 H-16·H-17).
- 제안 출력에는 각 단계가 무엇을 입력받아 몇 건을 배정하고 몇 건을 다음 단계로 넘겼는지 보여주는 `trace`, 특정 단계까지만 실행하는 `--stop-after`, 엔트리가 몇 단계에서 배정됐는지 보여주는 `assignments` 3종의 검토 장치가 딸려 있다 — 이 장치들을 켜고 꺼도 "제안 출력을 그대로 집행 입력으로 재사용할 수 있다"는 왕복 계약은 깨지지 않는다(근거: task:083 PLAN §3.4.2 (B) 왕복 불변식, 리스크 가설 H-18).

## 영향 범위

이름·서술 기반의 항목을 의미 그룹으로 나눠야 하는 모든 "제안형" 자동화 기능에 재사용 가능한 설계다 — 단일 축 분류의 커버리지 한계를 실측으로 확인했다면, 여러 신호를 순차 사다리로 배치하고 잔여를 정직하게 남기는 편이, 무리하게 커버리지 100%를 노리다 오분류를 만드는 것보다 안전하다.
