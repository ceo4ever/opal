## 개요

기존 서브명령에 분기 인자(`--kind`류)를 신설할 때, 기본값을 기존 동작으로 두면 기존 호출부·기존 테스트가 무변경으로 통과한다 — 하위호환은 코드 로직으로 별도 분기 처리를 해야 하는 문제가 아니라, **기본값 설계만으로 구조적으로 달성**할 수 있는 경우가 있다. (근거: task:079 DONE §2 R-1, PLAN §3.1.2)

## 결정 배경 (WHY)

`memory-tool update`에 `--kind {memory,history}`를 신설하면서, 기존 `update --title … --status …` 호출 계약과 기존 테스트 132건을 깨지 않아야 했다(task:079 PLAN H-1, P0 리스크). 신규 인자를 추가하는 모든 변경은 "기존 호출부가 이 인자를 모른다"는 사실과 공존해야 한다 — 신규 인자에 필수값을 요구하면 그 순간 모든 기존 호출부가 깨진다.

`cmd_append`가 이미 동일한 `kind` 분기 패턴을 쓰고 있었다는 선례도 이 설계를 검증했다(`memory_tool.py:924-926`) — 새 함수·새 분기 구조를 발명하지 않고 기존 패턴을 재사용하는 편이 회귀 위험이 낮다.

## 결정 내용

- **분기 인자의 기본값을 기존(레거시) 동작 값으로 설정한다.** `--kind`의 `default="memory"`가 곧 "이 인자를 모르는 기존 호출부가 그대로 통과한다"는 계약이 된다.
- **응답에 추가되는 신규 키는 additive(부가)로만 설계한다.** 응답 키 집합을 strict하게 단정하는 테스트가 없는 영역이라면(079에서는 `update` 응답이 해당), 기존 필드를 보존한 채 신규 필드(`kind` 등)를 얹어도 안전하다 — 다만 strict 단정 테스트가 있는 영역(예: `show`의 행 출력)에는 이 가정이 성립하지 않으므로 사전에 확인이 필요하다.
- **실증 기준**: 신규 케이스를 제외한 기존 테스트 전량(079에서는 132건)이 **무변경으로** GREEN이어야 하며, 회귀 스위트를 "일부 수정 후 통과"가 아니라 "그대로 통과"로 확인한다.

## 영향 범위

기존 CLI 서브명령·API 엔드포인트에 새로운 동작 분기를 추가하는 모든 확장 작업에 재사용 가능한 설계 규율이다. 새 파라미터를 도입할 때 "이 값을 아무도 지정하지 않으면 무슨 일이 일어나는가"를 먼저 확정하면, 하위호환 검증이 사후 테스트가 아니라 사전 설계 산출물이 된다.
