## 개요

파일 기반 SSOT를 사람이 직접 손으로 읽고 고쳐도 별 탈이 없던 느슨한 포맷(예: 마크다운 헤더 한 줄)에서, 파싱·검증이 엄격한 구조화 포맷(JSON + 스키마)으로 전환할 때는, 전환 대상 필드 중 **어떤 도구로도 게이트되지 않고 LLM이 직접 편집해 온 경로가 있는지**를 먼저 감사해야 한다. 그런 경로를 방치한 채 포맷만 바꾸면 손편집 위험(동시성 파손, 스키마 위반)이 오히려 커진다.

## 결정 배경 (WHY)

078에서 `MEMORY.md`를 JSON으로 전환하며 소스를 훑던 중, `last_task_number` 필드가 **어떤 서브명령으로도 게이트되지 않는 유일한 쓰기 경로**임을 발견했다 — 태스크 채번 시 PM(LLM)이 `MEMORY.md` 헤더를 직접 Read한 뒤 Edit으로 값을 올리는 절차가 문서(`task-process.md:19-22`)에 명문화되어 있었다. md 시절에는 read-then-write 왕복이 사실상 원자적이었지만(단일 `write_text` 호출), 이 필드를 JSON 스키마 필드로 그대로 옮기면 동시 실행 인스턴스 2개가 같은 번호를 읽고 같은 번호로 채번하는 TOCTOU 경쟁 조건이 그대로, 혹은 더 심하게 이전된다. (근거: task:078 PLAN.md §2, DONE §5 결함 #2)

## 결정 내용

- **선탐색 원칙**: SSOT 포맷 전환(md/텍스트 → JSON 등 구조화 포맷) 착수 시, 전환 대상 문서의 각 필드가 "도구 서브명령을 통해서만 쓰기가 발생하는지"를 먼저 표로 감사한다. 감사에서 비게이트 경로가 나오면, 포맷 전환과 **동시에** 그 경로를 tool-gated 서브명령으로 승격시켜야 한다(전환 후로 미루면 안 된다 — 구조화 포맷은 손편집에 더 취약하다).
- **078의 조치**: `task-number` 서브명령을 신설해 채번을 도구로 이관했다. 락(`memory_lock`, O_EXCL + stale 60s)으로 read-modify-write를 직렬화해, 20개 프로세스가 동시에 `--bump`해도 중복 없이 1..N이 배분됨을 실증했다(최종값 = 초기값+20). 채번 절차 문서 3곳을 "직접 Read+Edit" 지시에서 "도구 호출" 지시로 개정했다.

## 영향 범위

향후 다른 md/텍스트 SSOT(예: 다른 상태 파일)를 구조화 포맷으로 전환할 때도, 착수 전 체크리스트에 "이 문서의 모든 필드가 도구로만 쓰기되는가?"를 포함해야 한다.
