## 개요

`worktree-tool`의 슬롯·브랜치 판정 기준을 "디렉토리가 존재하는가"에서 "실제로 점유돼 있는가"로 바꾼 결정이다. 이 전환으로 "제거 후 재생성" 경로가 영구 차단되던 결함이 판정 기준 하나로 해소됐다.

## 결정 배경 (WHY)

- 단위 테스트 36건이 전건 GREEN인 상태에서 실환경(revup) 검증이 **차단성 결함**을 잡아냈다 — `remove` 성공 후 빈 슬롯 껍데기가 남고, 같은 태스크 번호로 재생성을 시도하면 슬롯 존재 오류로 영구 차단됐다. 슬롯 목록 조회는 "슬롯 없음"이라 답하는데 생성 명령은 "이미 존재한다"고 거부하는 내부 모순이었다(근거: task:092 DONE §5-(1)).
- 놓친 이유는 시나리오 설계의 구조적 공백이었다 — 기존 검증은 "레포별 경로가 맞는가"만 단언했고, 별도로 "살아 있는 슬롯의 중복 생성 거부"만 시험해 "제거된 슬롯을 재생성하는" 경로 자체를 밟지 않았다. 이 경위는 테스트 시나리오 문서에 증거로 남겼다(근거: task:092 DONE §5-(1), TEST-SCENARIO.md S-29 주석).
- 결함을 고치는 과정에서 담당 워커가 후속 공백을 임의로 넘기지 않고 블로커로 올렸다 — "슬롯 루트만 고치면 이번엔 브랜치 존재 검사에 막힌다"는 지적이었다. 슬롯 제거가 브랜치를 **의도적으로** 보존하기 때문이다(작업이 아직 살아 있을 수 있어 삭제하지 않는다는 원칙). PM이 임시 저장소에서 git 실동작을 직접 실측해 확정했다: ① 슬롯 제거 후 브랜치는 잔존한다 ② 그 브랜치로 새 worktree를 붙이는 명령은 성공한다(재사용) ③ 이미 다른 worktree가 체크아웃 중인 브랜치는 git 자체가 거부한다 ④ 점유 여부는 `git worktree list --porcelain`으로 판별 가능하다(근거: task:092 PLAN §1.4 DEC-7).

## 결정 내용

- 슬롯 존재 판정을 디렉토리 존재 검사에서 **실제 worktree 등록 여부**(`git worktree list`) 조회로 바꾼다.
- 브랜치 판정을 "존재하는가"에서 "다른 worktree에 점유(체크아웃) 중인가"로 바꾼다.
- 브랜치가 존재하지만 미점유이면 새로 만들지 않고 **재사용**한다(기존 브랜치를 그대로 붙이는 단일 명령).
- `remove`의 정리 범위를 레포별 worktree 경로에서 **슬롯 루트(`task_{NNN}/`)까지**로 넓혀 빈 디렉토리를 회수한다. 다만 `.opal-worktrees/` 자체와 메타 디렉토리는 다른 슬롯이 쓸 수 있으므로 남긴다.
- 살아 있는 슬롯의 중복 생성 거부는 이 전환으로도 **그대로 유지**된다 — 그 경우 브랜치가 점유 중이므로 git이 자체 거부하고, 도구는 그 신호를 동일한 에러 코드로 옮기기만 하면 된다. 즉 "재생성 허용"과 "중복 생성 거부"가 판정 기준 하나로 자연히 갈린다.

## 영향 범위

- `opal/tools/worktree-tool/worktree_tool.py` — 점유 판정 함수 3종 신설, `create` pre-flight·`remove` 정리 로직 교체.
- 이 전환이 없었다면 "제거 후 재작업"이라는 흔한 경로가 영구히 막혀, 워크트리 축 전체의 실사용성이 무너졌을 것이다.
