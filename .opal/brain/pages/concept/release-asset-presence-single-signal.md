## 개요

릴리즈 태그에 배포 자산이 실제로 올라와 있는지를 판정할 때, 별도 조회를 추가하지 않고 **체크섬 목록 파일의 다운로드 성공 여부 하나**만 신호로 쓴다. 성공하면 검증 모드, 실패하면 자동 아카이브 폴백 + 미검증 모드다.

## 결정 배경 (WHY)

- **존재가 동치다**: 발행 워크플로우가 배포 아카이브와 체크섬 목록을 같은 릴리즈 생성 스텝에서 함께 올리므로, 목록이 있으면 자산도 있다 (`.github/workflows/release.yml:53-56`, 근거: task:085 PLAN.md §3.0 D-B).
- **추가 왕복이 0이다**: 세 설치 경로 모두 이미 체크섬 목록을 받고 있었다. 받는 순서를 앞당기기만 하면 되므로 네트워크 비용이 늘지 않는다.
- **헤더 조회 프로브 기각 (실측)**: 존재하지 않는 릴리즈 자산을 헤더만 조회하면 HTTP 오류를 뜻하는 종료코드 22가 아니라 **56**이 돌아온다(리다이렉트 대상에서의 수신 실패). 네트워크 순단과 자산 부재를 종료코드로 구분할 수 없어 판정 신호로 쓸 수 없다.
- **릴리즈 조회 API 기각**: 왕복이 1회 늘고 비인증 호출 빈도 제한의 영향을 받는다.

## 결정 내용

- 태그 설치·업데이트는 체크섬 목록을 먼저 받아본다. 수신 성공이 곧 검증 모드 진입 조건이다.
- 수신 실패는 자동 아카이브 폴백으로 강등하되, 폴백은 무조건 통과가 아니라 기존 3분기(환경변수 옵트인 / 대화형 동의 / 비대화형 거부)로 수렴한다 — 실패 시 닫히는 방향을 유지한다.
- 남는 위험은 **네트워크 순단을 자산 부재로 오판**해 검증 가능한 설치가 미검증으로 강등되는 경우다. 이 강등은 배너와 동의 절차를 거치고 비대화형에서는 거부로 귀결되므로, 검증이 조용히 사라지는 형태는 아니다 (근거: task:085 PLAN.md §리스크 가설 H-1, TEST.md §2.2 실측).
- 목록 파일에서 자산명을 파생하지 못하는 형식 이상도 같은 폴백 경로로 처리한다.

## 영향 범위

설치 경로 3종의 다운로드 계획 수립 지점(`scripts/install.sh:234`, `opal/tools/opal-cli/lib/update.sh:84`, `scripts/install.ps1:213`). 이 판정은 네트워크를 사용하므로, 네트워크 접근 0을 계약으로 하는 예행 실행 흐름에서는 조기 반환해야 한다.
