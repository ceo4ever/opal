## 개요

설치·업데이트 스크립트를 실제로 돌려 검증하려면 두 가지가 걸린다 — 실행하면 운영 중인 설치본을 파괴적으로 덮어쓴다는 것, 그리고 자산 부재·다운로드 실패·손상 파일 같은 결함 상황을 재발행 없이 만들 수 없다는 것. 태스크 085는 소스를 한 줄도 바꾸지 않고 **프로세스 경계 두 지점만** 실행 경로 선행 스텁으로 가로채 두 문제를 함께 해결했다.

## 결정 배경 (WHY)

- **봉인 1 — 플랫폼 설치 스크립트 호출 지점**: 해당 인자로 호출될 때만 인자와 환경을 기록하고 정상 종료하며, 그 외 모든 호출은 실제 셸에 위임한다. 그 결과 다운로드 → 검증 → 추출 → 버전 각인까지 전 구간이 실제로 실행되고, 마지막 설치 호출만 기록으로 대체된다. 이 호출을 그대로 두면 실사용 설치본을 파괴적으로 재설치한다.
- **봉인 2 — 네트워크 클라이언트**: 호출 주소를 전부 기록하고, 지정 패턴에만 404 등가 종료코드를 돌려주며, 지정 패턴은 로컬 픽스처로 응답을 대체한다. 결함을 주입하지 않은 칸은 실제 네트워크·실제 릴리즈 자산으로 실행된다.
- 두 봉인 모두 검증 대상 로직의 **바깥**이며, 시스템 설정을 바꾸지 않는다.
- 격리 결과는 사실로 확인했다 — 홈 디렉토리 배포본은 전 구간 무변경이고 검증 세션 전후 변경 시각이 동일하다 (근거: task:085 TEST.md §0.1).
- 배포본 대신 프로젝트 사본을 직접 구동해도 등가다. 업데이트 로직은 호출 스크립트 위치를 기준으로 라이브러리를 읽어들이므로 재배포본과 동일 바이트의 코드가 실행된다.

실측에서 드러난 함정 두 가지도 함께 남긴다.

- 스텁 셸의 실행기 선언을 환경 조회 형태로 두면 스텁 자신을 재귀 호출한다 — 절대경로로 고정해야 한다.
- 스크립트 내부의 명령 치환 서브셸은 실행 경로 조회를 거치지 않으므로 셸 스텁의 영향을 받지 않는다. 봉인 범위를 실제보다 넓게 오해하지 않도록 기록에 남긴다.

대조군 선택에서도 실측이 판단을 바꿨다. 자산이 없는 과거 태그를 폴백 대조군으로 쓰려 했으나, 그 태그 트리에는 버전 파일 자체가 없어 규약과 무관한 이유로 실패한다 — 대조군으로 부적합하다. 그래서 현행 태그에 선택적 실패를 주입하는 방식을 택했다 (근거: task:085 TEST.md §0.4).

## 결정 내용

- 파괴적 부작용을 가진 실행 경계는 소스 수정이 아니라 **프로세스 경계 스텁**으로 봉인한다. 검증 대상 코드는 실물 그대로 돌린다.
- 봉인 지점은 검증 대상 바깥이어야 하고, 무엇을 왜 가로챘는지와 그로 인해 실행되지 않은 구간을 검증 기록에 명시한다.
- 결함 주입은 시스템 설정·실 데이터를 바꾸지 않는 방식을 우선한다.
- 픽스처는 가능한 한 실제 배포본을 내려받아 쓰고, 손상본·형식 이상본만 그로부터 파생시킨다.
- 실행 환경이 없어 돌려보지 못한 칸은 통과로 표기하지 않는다. 정적 검사로 대체했다면 대체 수단과 함께 실행 증거가 없다는 사실을 그대로 남긴다.

## 영향 범위

설치기·업데이트기처럼 실행 자체가 환경을 바꾸는 스크립트의 검증 전략 전반. 네트워크 의존 경로의 결함 주입에도 같은 형태를 재사용할 수 있다.
