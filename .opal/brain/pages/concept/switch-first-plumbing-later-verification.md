## 개요

기계장치를 먼저 깔고 스위치를 나중에 켜는 2단계 전환에서, 스위치를 켜기 전까지는 앞 단계가 만든 계약이 **전혀 검증되지 않는다**. 태스크 118이 만든 루트 소유권 장치 전부가 설정 키 하나에 걸려 있었고, 그 키가 비어 있는 동안에는 모든 장치가 종전과 동일하게 동작해 무엇이 맞고 무엇이 빠졌는지 드러나지 않았다.

## 결정 배경 (WHY)

- 태스크 캡슐을 워크트리에 실체화할 범위를 선언하는 설정 키는 118이 신설했지만 값은 빈 목록이 기본이었고, 허브 설정에는 키 자체가 없었다. 같은 픽스처에서 값을 넣은 경우와 비운 경우를 대조하니, 값이 있으면 태스크 해석 루트가 워크트리 자신에 착지하고 비어 있으면 같은 경로에서 허브로 탈출했다 — 워크트리에 메모리 앵커 파일이 실체화되지 않아 조상 탐색이 허브까지 올라가기 때문이다(근거: task:119 ANALYSIS Q4 실측, `opal/tools/state-tool/state_tool.py:730`).
- 따라서 "태스크 캡슐이 워크트리에 생성된다"는 완료 조건과 "두 프로세스가 같은 정규 경로를 관측한다"는 완료 조건은 같은 변경의 두 관측면이며 분리 구현할 수 없다(근거: 같은 항목).
- 스위치가 꺼져 있는 동안 118의 계약은 실행된 적이 없었고, 그래서 병합 이후 차단 연쇄(→ [[state-aware-path-resolution-unblocks-merge]])도, 생성 순서가 뒤집혀야 한다는 사실도 발견되지 않았다. 119가 스위치를 켜자 세 결함이 한꺼번에 드러났다 — 채번 명령의 상대 경로가 워크트리 사본을 가리켜 즉시 거부되는 문제(근거: ANALYSIS Q1), 워크트리 생성 명령이 태스크 폴더를 만들지 않으므로 별도 생성 단계가 필요한 문제(근거: ANALYSIS Q2), 그리고 폴더 생성 순서를 바꾸지 않으면 실패 시 폴더가 두 곳에 남는 문제(근거: ANALYSIS Q7).
- 스위치를 켜는 것이 회귀가 아니라 **정상 동작의 전제**인 경우도 있었다. 브레인 도구와 이벤트 로더는 워크트리에 설정 디렉터리가 실체화되지 않으면 애초에 오동작하므로, 스위치 활성화가 그 오동작을 해소한다(근거: task:119 ANALYSIS Q8).

## 결정 내용

- 스위치 값을 허브 운영 설정에 넣고, 규범 문서에서 그 값의 지위를 "다음 단계 활성화 예정값"에서 **현행 운영값**으로 승격했다(근거: task:119 PLAN D-9).
- 워크트리에 내려온 설정 사본은 읽기 전용 스냅샷으로 못 박고, 워크트리 도구 호출은 언제나 허브 루트를 명시해 수행한다는 문장을 계약에 추가했다 — 명시하지 않으면 워크트리가 자기를 허브로 오인할 여지가 남는다(근거: 같은 결정, ANALYSIS Q4 중첩 설정 위험).
- 되돌림 경로를 실측으로 확보했다. 키를 제거하면 실체화 범위가 코드 디렉터리 목록과 동일해져 즉시 전환 전 동작으로 돌아간다(근거: task:119 FIXTURE-EVIDENCE §3 S-6).

## 실측

스위치가 켜진 슬롯에서는 설정 디렉터리와 태스크 디렉터리가 워크트리에 실재했고(브레인 개념 페이지 317건, 태스크 22항목), 키를 제거한 슬롯에서는 두 디렉터리 모두 실체화되지 않았다(근거: task:119 FIXTURE-EVIDENCE §3). 실환경 파일럿에서 신규 슬롯이 이 활성값을 그대로 적용받아, 태스크 폴더와 상태 파일이 워크트리 안에만 생성되고 허브는 생성 전 구간에서 오염되지 않았다(근거: task:119 PILOT-EVIDENCE §1).

## 영향 범위

- 배관을 까는 태스크와 스위치를 켜는 태스크를 나눌 때, 앞 태스크의 완료 조건은 "장치가 존재한다"까지만 증명할 수 있고 "계약이 성립한다"는 증명하지 못한다. 뒤 태스크의 범위 산정에 앞 태스크가 남긴 미검증 계약의 결함 수정이 포함돼야 한다 — 119는 실제로 차단급 결함 하나와 계약 정정 하나를 추가로 떠안았다.
- 스위치 하나가 여러 완료 조건을 동시에 켜는 구조에서는 그 조건들을 개별 작업 단위로 쪼개지 않는다. 쪼개면 앞 조각이 관측 불가능해진다.
