## 개요

파이프라인 실행 중 "사용자 확인"이라는 이름의 행이 거치는 상태는 미확인(`pending`) 하나에서 출발해, 자동 승인(`done/auto`) 또는 소유자 승인(`done/user`) 둘 중 하나로만 끝나는 단일 축으로 확정됐다(근거: task:093 DONE.md §2 "설계 후 불변식"). 두 종결 상태 모두 승인 시각(`timestamp`)이 반드시 남는다.

## 결정 배경 (WHY)

- (근거: task:093 DONE.md §1 착수 배경 표 #1~#5) 착수 전에는 이 행에 진입 경로가 세 갈래(초기화 시점의 `agentic` 자동 `na` 마킹 / 소유자의 명시적 승인 호출 / 캡틴의 직접 확인)로 나뉘어 있었고, 서로 전제조건을 공유하지 않아 무검증 덮어쓰기와 승인 이력 누락(시각이 `null`로 남는 문제)이 발생했다.
- (근거: task:093 DONE.md §1 #2) 자동 승인을 표현하려고 `na`(해당 없음) 상태를 전용했는데, 이는 애초에 스키마가 뜻하던 "해당 없음"이 아니라 다음 단계 진입을 막는 가드를 우회하기 위한 임시방편이었다. `na`로 표시된 행은 소유자가 실제로 확인했는지 알 수 있는 흔적(시각)이 없었다.
- (추론: 코드패턴) 상태가 세 갈래로 나뉘어 있으면 "이 행이 승인됐는가"를 판정하는 로직도 갈래마다 따로 존재해야 하고, 그중 하나만 고쳐도 나머지 갈래에서 같은 결함이 재발한다.

## 결정 내용

- 초기화 시점에는 사용자 확인 행을 모드에 관계없이 항상 `pending`(미확인)으로 만든다. `agentic` 모드라고 해서 초기화 시점에 다른 상태를 부여하지 않는다(근거: task:093 DONE.md §2 F-1, PLAN.md §3.1.2 "삭제 후 세 빌더의 사용자 확인 행은 각 빌더의 기본 행 딕셔너리를 그대로 사용한다").
- 이 행이 `pending`에서 벗어나는 경로는 두 가지뿐이다. 하나는 다음 단계로 넘어가는 시점에 도구가 자동으로 승인하는 경로(`done/auto`), 다른 하나는 소유자가 직접 확인해 승인하는 경로(`done/user`)다. 어느 경로든 승인 시각을 반드시 기록한다.
- 기존에 `na`로 저장된 값을 스키마에서 제거하지 않고 하위호환으로 남겨둔다. 이미 진행 중인 태스크의 상태 파일이 갑자기 스키마 검증에 걸리는 것을 막기 위한 것이며, 신규로 `na`를 생성하는 경로는 더 이상 없다(근거: task:093 DONE.md §2 F-6, PLAN.md §3.1.2 "데이터 모델(변경 없음)").

## 영향 범위

파이프라인 상태 도구(`opal/tools/state-tool/state_tool.py`)의 행 생성(빌더 3종)과 단계 전이 검증 경로 전체. 사용자 확인 행을 다루는 모든 파일럿(`opal-pilot-*`)이 이 계약을 참조한다.
