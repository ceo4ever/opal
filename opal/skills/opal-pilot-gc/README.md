# opal-pilot-gc

커밋 전 코드 보안·컨벤션 문제를 진단하는 경량 스킬. 별칭 `opgc`.

## 개요

`//opgc`를 호출하면 대상 파일의 보안 취약점과 컨벤션 위반을 진단하여 보고서로 정리해 줍니다. **코드를 직접 수정하지는 않습니다** — 진단 전담 스킬이며, 수정이 필요한 이슈가 있으면 마지막에 `opds`(짧은 개발 태스크) 체인으로 넘길지 안내받습니다.

## 언제 쓰나

- 커밋하기 전에 지금까지 변경한 코드를 보안·컨벤션 관점에서 점검하고 싶을 때
- 프로젝트 전체를 대상으로 일괄 진단하고 싶을 때
- 보안만, 또는 컨벤션만 골라서 점검하고 싶을 때

## 사용법

```
//opgc                                    # 기본: staged 변경 파일, 보안+컨벤션 둘 다
//opgc --security                         # 보안 진단만
//opgc --convention                       # 컨벤션 진단만
//opgc --scope all                        # 프로젝트 전체 파일 대상
//opgc --agentic --convention             # 컨벤션만, 결과 확인 단계까지 자동 진행
```

| 옵션 | 기본값 | 설명 |
|---|---|---|
| `--security` | — | 보안 진단만 실행 (미지정 시 컨벤션과 함께 둘 다 실행) |
| `--convention` | — | 컨벤션 진단만 실행 (미지정 시 보안과 함께 둘 다 실행) |
| `--scope staged` | 기본값 | git에 스테이징된 변경 파일만 대상 |
| `--scope all` | — | 프로젝트 전체 추적 파일 대상 |
| `--agentic` | — | 중간 확인 단계를 건너뛰고 자동으로 진행 (완료 승인만 사용자가 함) |

대상 범위는 `staged`(기본) 외에 `all`(전체), `untracked`(신규 미추적 파일), `commit`/`commit:<ref>`(특정 커밋)로도 지정할 수 있습니다.

## 파이프라인

1. **SCAN** — 대상 파일을 확정하고, 기술 스택을 감지하고, 프로젝트에 `docs/SECURITY.md`·`docs/CONVENTIONS.md`가 있으면 기준 문서로 사용합니다. 프로젝트가 프론트엔드/백엔드처럼 여러 요소로 구성되어 있으면 요소별로 나눠서 진단을 준비합니다.
2. **CHECK** — 보안 검사와 컨벤션 검사를 (요소 × 검사 종류) 조합으로 병렬 수행합니다.
3. **REPORT** — 검사 결과를 하나로 통합하고, 이전 실행 결과와 비교(delta)하여 신규/재발/해소 이슈를 구분합니다. 결과를 보고받고 다음 단계 진행을 확인합니다.
4. **CLOSE** — 완료 문서를 만들고, 수정이 필요한 이슈가 있으면 `//opds` 체인으로 이관할지 안내합니다.

## 산출물

```
tasks/{번호}-{날짜}-opgc-{요약}/
├── STATE.md                       # 진행 상황·의사결정 기록
├── GC-SECURITY-{시각}[-{요소}].md   # 보안 보고서 (요소별로 여러 개 생길 수 있음)
├── GC-CONVENTION-{시각}[-{요소}].md # 컨벤션 보고서
├── GC-REPORT-{시각}.md             # 통합 판정 보고서
└── DONE.md                        # 완료 문서
```

각 보고서에는 발견된 이슈가 심각도(Critical/High/Medium/Low/Info)별로 정리되고, 자동 수정 가능 여부와 확인이 필요한 항목이 표시됩니다.

## 관련 스킬

- **opds (opal-pilot-dev-short)** — opgc가 진단한 이슈 중 수정이 필요한 것을 실제로 반영할 때 이어서 호출합니다.
- **opal-brain (opbr)** — 프로젝트에 브레인이 설정되어 있으면, opgc 완료 시 진단 결과가 자동으로 브레인에 누적됩니다.

## FAQ

### 코드를 직접 고쳐주지는 않나요?
네, opgc는 진단 전담입니다. 보고서에서 이슈를 확인한 뒤 `//opds "..."` 명령으로 별도 태스크를 시작해 수정을 반영해야 합니다.

### 프로젝트가 프론트엔드/백엔드로 나뉘어 있으면 어떻게 되나요?
`docs/PROJECT.md`에 프로젝트 구성이 등록되어 있으면 요소별로 나눠서 각각 진단하고, 보고서도 요소별로 분리되어 생성됩니다. 구성 정보가 없으면 프로젝트 전체를 하나로 진단합니다.

### `docs/SECURITY.md`나 `docs/CONVENTIONS.md`가 없어도 되나요?
네, 없어도 진단은 진행됩니다. 다만 있으면 그 기준 문서를 참조해 더 정확하게 진단합니다.

### 이전 실행과 비교가 되나요?
네, 직전 opgc 실행 결과가 있으면 자동으로 비교 기준(baseline)으로 삼아 이번 실행에서 새로 생긴 이슈, 반복되는 이슈, 해소된 이슈를 구분해 보여줍니다.
