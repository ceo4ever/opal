# SDD 태스크 분해 (TASKS)

## 실행 컨텍스트

이 스킬은 워커 에이전트의 컨텍스트에서 실행된다.
오케스트레이터(opal-pilot-sdd)가 워커를 디스패치하면, 워커가 이 스킬을 읽고 프로세스를 따른다.
서브 에이전트 사용이 불가능한 플랫폼에서는 오케스트레이터가 직접 이 스킬을 따른다.

- **워커 에이전트**: opal-task-agent
- **model**: advanced

---

## 페르소나

`personas/task-decomposer.md`를 Read하여 분해 원칙과 행동 규칙을 적용한다.

---

## 입력/출력

| 항목 | 설명 |
|------|------|
| **필수 입력** | SPEC.md, SPEC-PLAN.md, TEST-SCENARIOS.md |
| **선택 입력** | 프로젝트 컨텍스트 (docs/ARCHITECTURE.md, docs/CONVENTIONS.md) |
| **보장 출력** | specs/{NNN}-{feature}/TASKS.md |

### 입력 파일 역할

| 파일 | 역할 |
|------|------|
| SPEC.md | SSOT — AC/FR/EC 정의, 추적 매트릭스의 원천 |
| SPEC-PLAN.md | 아키텍처/설계 — 컴포넌트 구조가 태스크 분해의 기반 |
| TEST-SCENARIOS.md | TS 목록 — AC↔TS 매핑, 태스크별 완료 기준 |

---

## 프로세스

### Step 1: 입력 파일 로딩

1. 디스패치 프롬프트에 명시된 `spec_path`에서 아래 파일을 Read한다:
   - `specs/{NNN}-{feature}/SPEC.md`
   - `specs/{NNN}-{feature}/SPEC-PLAN.md`
   - `specs/{NNN}-{feature}/tests/TEST-SCENARIOS.md`
2. 프로젝트 컨텍스트가 필요하면 `docs/ARCHITECTURE.md`, `docs/CONVENTIONS.md`를 Read한다.

### Step 2: AC/FR 분석

SPEC.md에서 아래 정보를 추출한다:

1. **FR 목록**: `[FR-01]`, `[FR-02]`, ... — 기능 요구사항 전체
2. **AC 목록**: `AC-01`, `AC-02`, ... — GIVEN/WHEN/THEN 형식의 수용 기준 전체
3. **EC 목록**: `[EC-01]`, ... — 엣지 케이스 (태스크에 명시적으로 포함 필요)
4. **NFR 목록**: `[NFR-01]`, ... — 비기능 요구사항 (횡단 관심사로 별도 태스크 또는 기존 태스크에 통합)

**검증**: AC가 3개 미만이면 SPEC.md 불완전 — 에스컬레이션한다.

### Step 3: 설계 기반 태스크 분해

SPEC-PLAN.md의 아키텍처 컴포넌트를 기반으로 태스크를 도출한다.

**분해 원칙**:

1. **컴포넌트 → 태스크 매핑**: SPEC-PLAN.md의 각 컴포넌트/모듈이 태스크 후보
2. **응집도 우선**: 하나의 태스크는 단일 컴포넌트 또는 밀접한 컴포넌트 그룹
3. **단일 워커 완결**: 각 태스크는 워커 1명이 한 세션에 완료할 수 있는 크기
4. **SPEC-PLAN.md에 없는 태스크 금지**: 설계 문서에 근거 없는 태스크를 생성하지 않는다

**분해 단위 기준**:

| 단위 | 태스크 분리 여부 |
|------|-----------------|
| 독립 컴포넌트 (모델, 서비스 등) | 별도 태스크 |
| 밀접 연관 컴포넌트 (모델+DTO 등) | 하나의 태스크로 통합 |
| 횡단 관심사 (로깅, 인증 등) | NFR에 따라 별도 태스크 또는 기존 태스크에 포함 |
| UI 화면 | 화면 단위로 태스크 분리 |
| API 엔드포인트 | 관련 서비스와 함께 하나의 태스크 |

**태스크 ID**: `T{N}` — 1부터 순차 부여. ID는 의존관계 그래프에서 사용.

### Step 4: 추적 매트릭스 작성

모든 AC가 하나 이상의 태스크에 매핑되어야 한다. 빈틈이 있으면 태스크를 추가한다.

| AC | FR | TS | 담당 태스크 | 커버리지 |
|----|----|----|-----------|----------|

**작성 규칙**:

1. SPEC.md의 모든 AC를 나열한다
2. 각 AC에 관련 FR을 매핑한다
3. TEST-SCENARIOS.md에서 해당 AC의 TS를 매핑한다
4. Step 3에서 도출한 태스크 중 해당 AC를 구현하는 태스크를 매핑한다
5. **커버리지 컬럼**: 매핑이 완전하면 `완료`, 부분이면 `부분 — {사유}`

**검증**: 커버리지가 `부분`인 행이 있으면 태스크를 추가하거나 기존 태스크 범위를 확장한다.

### Step 5: 의존관계 그래프 결정

태스크 간 의존관계를 설계 문서에서 도출한다.

**의존관계 도출 기준**:

| 관계 유형 | 예시 | 의존 방향 |
|----------|------|----------|
| 데이터 모델 → 서비스 | 모델 정의 후 서비스 구현 | T(모델) → T(서비스) |
| 서비스 → API | 비즈니스 로직 후 라우터 | T(서비스) → T(API) |
| API → UI | 엔드포인트 후 화면 연동 | T(API) → T(UI) |
| 공통 모듈 → 의존 모듈 | 공유 타입/유틸 먼저 | T(공통) → T(의존) |

**표기 형식**: 방향 그래프 (ASCII)

```
T1 → T2 → T4
T1 → T3 → T4
```

**검증**:
- 순환 의존이 없어야 한다 (A → B → A 금지)
- 모든 태스크가 그래프에 포함되어야 한다 (고립 태스크도 명시)

### Step 6: 태스크별 적정 스킬 추천

각 태스크의 복잡도와 범위에 따라 실행 스킬을 추천한다.

#### 스킬 추천 기준

| 기준 | opds (경량) | opd (풀스펙) | opp (비코드) |
|------|------------|-------------|-------------|
| 변경 파일 수 | 1~3개 | 4개 이상 | - |
| 모듈 범위 | 단일 모듈 | 다중 모듈 | - |
| 분석 필요성 | 낮음 (구조 명확) | 높음 (코드 분석 필요) | - |
| 테스트 범위 | unit 위주 | unit + integration | - |
| 작업 유형 | 코드 구현 | 코드 구현 | 문서/설정/비코드 |

#### 추천 결정 프로세스

1. **비코드 작업** (문서, 설정, 마이그레이션 스크립트 등) → `opp`
2. **코드 작업 + 파일 1~3개 + 단일 모듈** → `opds`
3. **코드 작업 + 파일 4개 이상 또는 다중 모듈 또는 분석 필요** → `opd`

각 태스크에 추천 스킬과 근거를 기록한다.

### Step 7: 병렬 실행 그룹 식별

의존관계 그래프에서 동시 실행 가능한 태스크 그룹을 식별한다.

**그룹핑 규칙**:
- 의존관계가 없는 태스크끼리 같은 그룹
- 모든 선행 태스크가 완료된 후 실행 가능한 태스크끼리 같은 그룹
- 그룹 번호는 실행 순서를 나타냄

**표기 형식**:

```
Group 1 (병렬): T1, T5
Group 2 (병렬): T2, T3    ← T1 완료 후
Group 3 (순차): T4         ← T2, T3 완료 후
```

### Step 8: 상태 필드 초기화

모든 태스크의 상태를 `⬜ 대기`로 초기화한다.

**상태 열거형**:

| 상태 | 의미 |
|------|------|
| ⬜ 대기 | 아직 시작 안 함 |
| 🔄 진행 중 | EXECUTE-LOOP에서 실행 중 |
| ✅ 완료 | 모든 TS Green |
| ❌ 실패 | 에스컬레이션 필요 |

### Step 9: TASKS.md 작성

아래 출력 형식에 따라 TASKS.md를 작성한다.

### Step 10: 결과 반환

워커는 TASKS.md 경로와 요약을 오케스트레이터에 반환한다.
워커는 QA를 호출하지 않는다. 오케스트레이터가 다음 Phase(TASKS-VERIFY)에서 검증한다.

## TASKS.md 출력 형식

```markdown
# Tasks: {기능명}

> SPEC.md v{X.Y} 기준 | 총 태스크: {N}개

## 추적 매트릭스 (Requirements Traceability Matrix)

| AC | FR | TS | 담당 태스크 | 커버리지 |
|----|----|----|-----------|----------|
| AC-01 | FR-01, FR-02 | TS-01, TS-02 | T1, T2 | 완료 |
| AC-02 | FR-03 | TS-03 | T3 | 완료 |

## 의존관계 그래프

T1 → T2 → T4
T1 → T3 → T4

## 실행 그룹

Group 1 (병렬): T1, T5
Group 2 (병렬): T2, T3    ← T1 완료 후
Group 3 (순차): T4         ← T2, T3 완료 후

## 태스크 목록

### T1: {태스크명}
- **범위**: {변경 대상 파일/모듈}
- **AC 매핑**: AC-01, AC-02
- **FR 매핑**: FR-01, FR-02
- **TS 매핑**: TS-01, TS-02
- **의존**: 없음
- **예상 규모**: Small (→ opds)
- **추천 근거**: 파일 2개, 단일 모듈, 구조 명확
- **완료 기준**: TS-01, TS-02 Green
- **상태**: ⬜ 대기

### T2: {태스크명}
- ...
```

## 스킬 추천 기준 요약

| 조건 | 추천 스킬 | 파이프라인 |
|------|----------|----------|
| 비코드 작업 (문서, 설정) | opp | TASK → PLAN → EXECUTE |
| 코드, 파일 1~3개, 단일 모듈 | opds | TASK → PLAN+TEST-SCENARIO → EXECUTE |
| 코드, 파일 4개+, 다중 모듈, 분석 필요 | opd | TASK → ANALYSIS → PLAN+TEST-SCENARIO → EXECUTE |

## 품질 체크리스트

- [ ] 모든 AC가 추적 매트릭스에 포함되어 있는가? (누락 AC = 구현 누락)
- [ ] 모든 TS가 하나 이상의 태스크에 매핑되어 있는가?
- [ ] 의존관계 그래프에 순환이 없는가?
- [ ] 모든 태스크가 의존관계 그래프에 포함되어 있는가?
- [ ] 각 태스크가 단일 워커 1세션 완결 크기인가?
- [ ] 각 태스크에 스킬 추천과 근거가 포함되어 있는가?
- [ ] SPEC-PLAN.md에 없는 태스크를 생성하지 않았는가?
- [ ] 병렬 실행 그룹이 식별되어 있는가?
- [ ] 모든 태스크 상태가 `⬜ 대기`로 초기화되어 있는가?
- [ ] 한국어 본문 + 영어 코드/필드명 규칙을 따르는가?
