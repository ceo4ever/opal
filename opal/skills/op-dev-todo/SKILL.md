# 실행 체크리스트 확장 (TODO)

> **Full Task 전용**: 이 스킬은 Full Task 모드의 TODO 단계에서 사용된다.
> Short Task에서는 TODO 단계가 없으며, 실행 체크리스트는 PLAN.md에 통합된다.

## 실행 컨텍스트

이 스킬은 워커 에이전트의 컨텍스트에서 실행된다.
오케스트레이터가 워커를 디스패치하면, 워커가 이 스킬을 읽고 프로세스를 따른다.
서브 에이전트 사용이 불가능한 플랫폼에서는 오케스트레이터가 직접 이 스킬을 따른다.

---

## 페르소나

`personas/software-architect.md`를 Read하여 설계 원칙과 행동 규칙을 적용한다.

---

## 입력/출력

| 항목 | 설명 |
|------|------|
| **필수 입력** | PLAN.md |
| **선택 입력** | ANALYSIS.md |
| **보장 출력** | TODO.md (Part A + Part B + Part C) |

---

## 프로세스

### Step 1: 가이드 로딩

`references/todo-guide.md`를 Read한다.

### Step 2: Part A -- 실행 체크리스트 상세 분해

PLAN.md의 구현 순서를 따라, 각 항목을 파일 단위 작업으로 상세 분해한다.

**작업 분해 원칙**:
- 하나의 작업 = 하나의 파일 또는 하나의 논리적 단위
- 각 작업은 독립적으로 테스트 가능해야 한다
- 작업 간 의존성 순서를 명시한다
- 각 작업에 "완료 기준"을 달아서, 끝났는지 모호하지 않게 한다

**Step 형식**:

```markdown
### Step {N}: {작업 제목}
- [ ] 완료
- **파일**: {대상 파일 경로}
- **작업 내용**: {무엇을 할지 구체적으로}
- **완료 기준**: {이것이 되면 완료}
- **테스트**: {어떻게 검증할지}
- **실행 방법**: {direct | sub-agent}
- **의존**: {선행 Step}
```

### Step 3: Part B -- QA 체크리스트

구현이 완료된 후 품질을 검증하는 체크리스트를 작성한다.

- **B-1. 기능 테스트**: TASK.md의 요구사항 충족 확인
- **B-2. 회귀 테스트**: 기존 기능 비파괴 확인
- **B-3. 코드 품질**: 프로젝트 코드 컨벤션 준수 (타입 힌트, 주석, 포매터, 네이밍)
- **B-4. 보안**: 민감 정보 노출 방지 (.env, 하드코딩 토큰/시크릿)

### Step 4: 복잡도 판별

Part A 작성 완료 후, 아래 기준으로 실행 모드를 결정한다:

| 기준 | 단순 모드 | 복잡 모드 |
|------|----------|----------|
| Step 수 | 5개 이하 | 6개 이상 |
| 변경 파일 수 | 3개 이하 | 4개 이상 |
| 모듈 범위 | 단일 모듈 | 다중 모듈/레이어 |
| 작업 유형 | 오류 수정, 단순 기능 수정 | 신규 개발, 대규모 개선 |
| 외부 의존성 | 없음 | 새 API, 새 패키지, 새 도구 필요 |

**하나라도 "복잡 모드" 기준에 해당하면 복잡 모드를 적용한다.**

- 단순 모드: 모든 Step의 실행 방법을 `direct`로 설정
- 복잡 모드: Step 5(Part C)로 진행하여 실행 아키텍처를 설계

### Step 5: Part C -- 실행 아키텍처 설계 (복잡 모드 전용)

**이 파트는 복잡 모드에서만 생성된다.**

`references/execute-plan-guide.md`를 Read하여 다음을 설계한다:

- **C-1. 에이전트 토폴로지**: Step 간 의존성 DAG 기반 에이전트 그룹핑 및 실행 순서
- **C-2. 스킬 요구사항**: 기존 스킬 매칭 + 신규 스킬 필요 여부
- **C-3. 도구 요구사항**: CLI, MCP, 패키지 설치/설정 필요 사항
- **C-4. 테스트 전략**: op-dev-test-agent 에이전트의 실행 계획

> 이 파트는 기존 dtp-action-plan-agent(레거시)의 역할을 흡수한다.
> 별도 에이전트를 호출하지 않고, 워커가 직접 Part C를 생성한다.

### Step 6: 결과 반환

워커는 TODO.md 경로, 요약, 복잡도 판별 결과를 오케스트레이터에 반환한다.
오케스트레이터가 사용자에게 보고하고, 승인을 받으면 EXECUTE 단계로 진행한다.

> **TODO 단계 검증 없음**. TODO 단계는 별도 문서 QA 단계를 두지 않는다 (문서 QA는 PLAN 등 상위 산출물에 대해 PM이 PM Gate에서 직접 수행).

## TODO.md 출력 형식

```markdown
# TODO: {태스크 제목}

> 작성일: YYYY-MM-DD | 참조: TASK.md, ANALYSIS.md, PLAN.md

## Part A: 실행 체크리스트

> 총 {N}개 Step | 실행 모드: {단순 / 복잡}

### Step 1: {제목}
- [ ] 완료
- **파일**: {경로}
- **작업 내용**: {설명}
- **완료 기준**: {기준}
- **테스트**: {명령어}
- **실행 방법**: {direct / sub-agent}
- **의존**: 없음

---

## Part B: QA 체크리스트

### B-1. 기능 테스트
- [ ] {항목}

### B-2. 회귀 테스트
- [ ] {항목}

### B-3. 코드 품질
- [ ] {항목}

### B-4. 보안
- [ ] {항목}

---

## Part C: 실행 아키텍처 (복잡 모드 시)

{복잡 모드일 때만 이 섹션이 추가된다}

### C-1. 에이전트 토폴로지
{DAG 기반 에이전트 그룹핑, 배치 실행 순서}

### C-2. 스킬 요구사항
{기존 스킬 매칭, 신규 스킬 필요 여부}

### C-3. 도구 요구사항
{CLI, MCP, 패키지 설치/설정}

### C-4. 테스트 전략
{op-dev-test-agent 실행 계획}

---

## 승인 요청

> 위 TODO가 사용자의 승인을 받으면 EXECUTE 단계를 시작합니다.
> 단순 모드: 워커가 Step 순서대로 직접 실행합니다.
> 복잡 모드: 워커가 Part C 토폴로지에 따라 내부 서브 에이전트를 병렬 실행합니다.
```

---

## 상태 표시 규칙

체크박스로 완료 상태를 관리한다:
- `- [ ] 완료` -- 미완료
- `- [x] 완료` -- 완료

블로커 발생 시:
- 체크박스는 미완료 상태로 유지
- Step 아래에 `> 블로커: {설명}` 인라인 메모 추가
- 즉시 사용자에게 보고

---

## 실행 방법 필드 규칙

- `direct` -- 메인 에이전트가 직접 실행 (단순 모드 기본값)
- `sub-agent` -- 복잡 모드에서 워커 내부의 서브 에이전트에 위임 (Part C 토폴로지에 따라 결정)
- 단순 모드에서는 모든 Step이 `direct`
- 복잡 모드에서는 Part C의 에이전트 토폴로지가 각 Step의 실행 방법을 결정

## 품질 체크리스트

- [ ] PLAN.md의 모든 구현 항목이 Step으로 분해되었는가?
- [ ] 각 Step의 완료 기준이 명확하고 검증 가능한가?
- [ ] Step 간 의존성 순서가 올바른가?
- [ ] 각 Step의 실행 방법(direct/sub-agent)이 지정되었는가?
- [ ] QA 체크리스트가 TASK.md의 모든 요구사항을 커버하는가?
- [ ] 회귀 테스트와 보안 체크가 포함되어 있는가?
- [ ] 복잡도 판별 기준에 따라 실행 모드가 올바르게 결정되었는가?
- [ ] 복잡 모드일 경우 Part C가 포함되어 있는가?
