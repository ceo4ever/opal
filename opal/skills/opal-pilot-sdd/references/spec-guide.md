# spec.md 작성 가이드

> opal-pilot-sdd Phase 1: SPEC에서 spec.md를 작성할 때 참조하는 상세 지침.
> op-sdd-spec 스킬과 연동된다.

---

## 1. spec.md 개요

spec.md는 SDD 파이프라인의 **SSOT(Single Source of Truth)** 이다. 기능의 WHAT/WHY를 정의하며, 이후 모든 단계(검증, 설계, 태스크 분해, 구현)의 근거가 된다.

**핵심 원칙**:
- WHAT(무엇을 할 것인가)을 기술한다. HOW(어떻게 구현할 것인가)는 SPEC-PLAN.md의 영역이다.
- 검증 가능한 명세를 작성한다. 모호한 표현은 테스트 시나리오 도출을 방해한다.
- 살아있는 문서 -- 구현 중 발견된 통찰은 즉시 반영하되, 변경 이력을 기록한다.

---

## 2. 10섹션 표준 구조

spec.md는 반드시 아래 10개 섹션을 모두 포함해야 한다. 섹션 누락 시 SPEC-VERIFY에서 구조적 검증 Fail 처리된다.

```markdown
# SPEC: {기능명}

> 버전: 1.0 | 작성일: YYYY-MM-DD | 상태: Draft
> TASK: tasks/{NNN}-{태스크명}/TASK.md

## 1. Background (배경)
## 2. Goals (목표)
## 3. Non-goals (비목표)
## 4. User Stories (사용자 스토리)
## 5. Functional Requirements (기능 요구사항)
## 6. Acceptance Criteria (수용 기준)
## 7. Edge Cases (엣지 케이스)
## 8. Non-functional Requirements (비기능 요구사항)
## 9. Constraints (제약)
## 10. Open Questions (미결 사항)
```

---

## 3. 섹션별 작성 지침

### 3-1. Background (배경)

왜 이 기능이 필요한지 비즈니스 맥락을 기술한다.

**작성 기준**:
- TASK.md의 배경 정보를 기반으로 하되, 프로젝트 컨텍스트를 반영하여 보강한다
- 현재 상태(AS-IS)와 목표 상태(TO-BE)를 구분하면 명확해진다
- 기술적 배경보다 비즈니스/사용자 맥락을 우선한다

**좋은 예**:
> 현재 사용자 인증은 세션 기반이며, 모바일 앱에서 세션 만료 후 재로그인 요구로 이탈률이 15%에 달한다. JWT 기반 인증으로 전환하여 세션 유지와 멀티 디바이스 지원을 개선한다.

**나쁜 예**:
> JWT 토큰을 구현한다. (WHY가 없음)

### 3-2. Goals (목표)

이 기능이 달성해야 할 것을 명확히 나열한다.

**작성 기준**:
- 검증 가능한 목표를 우선한다
- 불릿 포인트로 나열한다
- "~를 지원한다", "~를 제공한다" 형태로 결과를 명시한다

### 3-3. Non-goals (비목표)

명시적으로 범위 밖인 것을 정의하여 범위 크리프를 방지한다.

**작성 기준**:
- "이번에 하지 않는 것"을 분명히 한다
- 왜 범위 밖인지 간략하게 설명한다
- Goals와 모순되면 안 된다 (SPEC-VERIFY에서 의미적 검증 대상)

**좋은 예**:
> - 소셜 로그인 (OAuth) -- 별도 기능으로 후속 개발 예정
> - 2FA(이중 인증) -- 보안 강화 페이즈에서 다룰 예정

### 3-4. User Stories (사용자 스토리)

`As a {역할}, I want {기능}, so that {가치}` 형식으로 작성한다.

**작성 기준**:
- 주요 사용자 유형별로 최소 1개 이상
- {가치} 부분을 생략하지 않는다 -- WHY가 명확해야 한다

### 3-5. Functional Requirements (기능 요구사항)

**넘버링 규칙**: `[FR-NN]` (01부터 순차, 2자리 zero-padded)

**작성 기준**:
- 각 FR은 하나의 검증 가능한 요구사항을 기술한다
- TASK.md의 모든 요구사항이 FR로 매핑되어야 한다
- 구현 방법(HOW)이 아닌 동작(WHAT)을 기술한다

**좋은 예**:
> - [FR-01] 시스템은 이메일/비밀번호로 사용자를 인증한다
> - [FR-02] 인증 성공 시 JWT 액세스 토큰과 리프레시 토큰을 발급한다

**나쁜 예**:
> - [FR-01] bcrypt로 비밀번호를 해싱하고 PostgreSQL에서 조회한다 (HOW가 섞임)

### 3-6. Acceptance Criteria (수용 기준)

**넘버링 규칙**: `AC-NN` (01부터 순차, 2자리 zero-padded)

**형식 규칙** -- 반드시 **GIVEN/WHEN/THEN** 형식:

```markdown
### AC-01: {시나리오명}
> 대응 FR: FR-01

- **GIVEN**: {사전 조건}
- **WHEN**: {행위}
- **THEN**: {기대 결과}
```

**최소 개수**: 3개 이상

**FR-AC 양방향 추적성**: 모든 FR에 대응하는 AC가 1개 이상 있어야 하며, AC 상단에 대응 FR ID를 명시한다.

**좋은 AC 예**:

```markdown
### AC-01: 유효한 자격 증명으로 로그인
> 대응 FR: FR-01, FR-02

- **GIVEN**: 등록된 사용자 계정이 존재하고 비밀번호가 올바를 때
- **WHEN**: POST /auth/login에 이메일과 비밀번호를 전송하면
- **THEN**: 200 OK와 함께 JWT 액세스 토큰(만료 1시간)과 리프레시 토큰(만료 7일)이 반환된다
```

**나쁜 AC 예**:

```markdown
### AC-01: 로그인 동작
- 사용자가 로그인하면 토큰을 받는다
```
(GIVEN/WHEN/THEN 형식 위반, 구체성 부족)

**AC 작성 팁**:
- GIVEN은 전제 조건만 기술한다 (시스템 상태, 데이터 존재 여부)
- WHEN은 사용자/시스템의 단일 행위만 기술한다
- THEN은 검증 가능한 기대 결과를 기술한다 (HTTP 코드, 반환 데이터, 상태 변경)
- 하나의 AC에 복수의 THEN이 있으면 AC를 분할하는 것을 고려한다

### 3-7. Edge Cases (엣지 케이스)

**넘버링 규칙**: `[EC-NN]` (01부터 순차, 2자리 zero-padded)

**작성 기준**:
- 예외 상황과 기대 동작을 함께 기술한다
- 정상 경로만 기술된 spec은 불완전하다 -- 적극적으로 엣지 케이스를 도출한다
- EC 항목은 SPEC-VERIFY에서 추가 테스트 시나리오로 도출된다

**예시**:
> - [EC-01] 5회 연속 로그인 실패 시 -- 계정을 30분간 잠금하고 429 응답 반환
> - [EC-02] 만료된 리프레시 토큰으로 갱신 요청 시 -- 401 응답 + 재로그인 안내

### 3-8. Non-functional Requirements (비기능 요구사항)

**넘버링 규칙**: `[NFR-NN]` (01부터 순차, 2자리 zero-padded)

**작성 기준**:
- 성능, 보안, 접근성, 확장성 등을 고려한다
- **생략하지 않는다** -- 비기능 요구사항이 없는 기능은 드물다
- 가능한 한 정량적 기준을 포함한다 (SPEC-VERIFY에서 NFR 측정 가능성 검증)

**좋은 예**:
> - [NFR-01] 로그인 API 응답 시간 p95 < 200ms
> - [NFR-02] 비밀번호는 bcrypt(cost 12 이상)로 해싱하여 저장

**나쁜 예**:
> - [NFR-01] 빠르게 동작해야 한다 (정량 기준 없음)

### 3-9. Constraints (제약)

기술적, 정책적 제약을 기술한다.

**작성 기준**:
- 프레임워크, 언어, 호환성 등 기술적 제약
- 보안 정책, 라이선스 등 정책적 제약
- 프로젝트 컨텍스트(docs/PROJECT.md, ARCHITECTURE.md)에서 도출된 제약
- 기존 시스템과의 통합 포인트도 제약으로 기록

### 3-10. Open Questions (미결 사항)

spec 작성 과정에서 발생한 미해결 질문을 기록한다.

**핵심 규칙**:
- **"없음"이 SPEC-VERIFY 진행 조건** -- OQ가 하나라도 남아있으면 SPEC-VERIFY로 진행 불가
- 코드베이스, 문서, 프로젝트 컨텍스트에서 해소 가능한 OQ는 작성 중 해소한다
- 해소 불가능한 OQ는 `[OQ-UNRESOLVED]` 태그와 함께 오케스트레이터에 반환한다
- 소유자 판단이 필요한 OQ만 남긴다

## 4. FR/AC/EC 넘버링 규칙 종합

| 요소 | 형식 | 시작 번호 | 예시 |
|------|------|----------|------|
| Functional Requirements | `[FR-NN]` | 01 | [FR-01], [FR-02] |
| Acceptance Criteria | `AC-NN` | 01 | AC-01, AC-02 |
| Edge Cases | `[EC-NN]` | 01 | [EC-01], [EC-02] |
| Non-functional Requirements | `[NFR-NN]` | 01 | [NFR-01], [NFR-02] |
| Open Questions | `[OQ-NN]` (미해소 시) | 01 | [OQ-01] |

**규칙**:
- 2자리 zero-padded (01, 02, ..., 10, 11, ...)
- 삭제된 번호는 재사용하지 않는다 (추적성 유지)
- 교차 참조 시 해당 ID를 그대로 사용한다 (예: AC 상단에 `대응 FR: FR-01`)

## 5. 기능 분할 기준

spec.md가 너무 크면 Spec Theater 함정에 빠진다. 아래 기준으로 분할을 판별한다.

**분할 신호**:
- TASK.md의 요구사항이 3개 이상의 독립적 기능을 포함
- AC가 10개를 초과
- 서로 다른 도메인 모듈에 걸치는 요구사항이 혼재
- 한눈에 읽을 수 없는 분량 (스크롤 없이 파악 불가)

**분할 제안 형식**:
```
[SCOPE-SPLIT] {기능A}, {기능B}, {기능C}로 분할을 제안합니다.
각각 독립된 spec.md로 작성하면 검증/구현이 용이합니다.
계속 진행할까요?
```

**주의**: 오케스트레이터(또는 소유자)의 승인 없이 임의 분할 금지.

## 6. 버전 관리

spec.md는 살아있는 문서로서 구현 중 변경이 허용된다. 단, 변경 이력을 기록해야 한다.

**상태 전이**:
```
Draft → Verified (SPEC-VERIFY 통과) → Implemented (DONE)
```

**변경 시 규칙**:
1. 버전 번호를 증가시킨다 (1.0 → 1.1)
2. 헤더의 작성일과 버전을 갱신한다
3. 문서 하단에 변경 이력 섹션을 추가한다:

```markdown
## 변경이력

| 버전 | 날짜 | 변경내용 | 사유 |
|------|------|---------|------|
| 1.0 | 2026-04-05 | 초기 작성 | - |
| 1.1 | 2026-04-07 | AC-04 추가, FR-03 수정 | T2 구현 중 인증 흐름 보완 필요 발견 |
```

**에스컬레이션 대상 변경** (agentic 모드):
- Goals / Non-goals 변경 -- 스코프 변경이므로 사용자 에스컬레이션
- 기존 AC 삭제/대폭 수정 -- 추적성 훼손 위험이므로 사용자 에스컬레이션
