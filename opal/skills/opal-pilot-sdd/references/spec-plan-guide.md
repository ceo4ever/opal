# SPEC-PLAN.md 작성 가이드

> opal-pilot-sdd Phase 3: SPEC-PLAN에서 SPEC-PLAN.md를 작성할 때 참조하는 상세 지침.
> op-sdd-plan 스킬과 연동된다.

---

## 1. SPEC-PLAN.md 개요

SPEC-PLAN.md는 spec.md의 WHAT를 HOW로 변환하는 **기능 수준 아키텍처 설계** 문서이다. 컴포넌트 구성, 데이터 모델, API 설계, 기술 결정을 수립하여 태스크 분해(op-sdd-tasks)의 입력이 된다.

**핵심 원칙**:
- spec.md(WHAT)를 기반으로 설계(HOW)를 수립한다
- 기존 아키텍처를 존중하고, 신규 컴포넌트는 기존 패턴에 맞춘다
- 모든 기술 결정에 근거와 대안을 기록한다
- SPEC-PLAN.md만 보고 태스크 분해에 들어갈 수 있어야 한다

---

## 2. SPEC-PLAN.md vs T{N}/PLAN.md

이 두 문서는 이름이 비슷하지만 역할이 완전히 다르다.

| 항목 | SPEC-PLAN.md | T{N}/PLAN.md |
|------|-------------|-------------|
| **범위** | 기능 전체 | 개별 태스크 1개 |
| **수준** | 설계 레벨 (아키텍처) | 구현 레벨 (코드) |
| **내용** | 컴포넌트, 데이터 모델, API, 기술 결정 | 파일별 변경 계획, 구현 순서, 체크리스트 |
| **생성 스킬** | op-sdd-plan | op-dev-plan |
| **소비자** | op-sdd-tasks (태스크 분해의 입력) | op-task-execute (코드 구현의 입력) |
| **타이밍** | EXECUTE-LOOP 이전 (Phase 3) | EXECUTE-LOOP 내부 (각 태스크 실행 시) |

**관계**: SPEC-PLAN.md가 기능 전체의 설계 청사진이고, T{N}/PLAN.md는 개별 태스크의 구현 상세 계획이다.

## 3. 7섹션 표준 구조

SPEC-PLAN.md는 아래 7개 섹션으로 구성된다.

```markdown
# SPEC-PLAN: {기능명}

> 버전: 1.0 | 작성일: YYYY-MM-DD | spec.md v{X.Y} 기준

## 1. 아키텍처 설계
## 2. 데이터 모델
## 3. API 설계
## 4. 기술 결정
## 5. 보안 고려사항
## 6. 에러 핸들링
## 7. 제약 반영
```

---

## 4. 섹션별 작성 지침

### 4-1. 아키텍처 설계

spec.md의 요구사항을 아키텍처 컴포넌트에 매핑한다.

**포함 내용**:

1. **컴포넌트 구성 테이블**:

| 컴포넌트 | 역할 | 신규/수정 | 레이어 |
|----------|------|----------|--------|
| UserService | 사용자 인증/관리 비즈니스 로직 | 신규 | Service |
| AuthMiddleware | JWT 토큰 검증 미들웨어 | 신규 | Middleware |
| UserModel | 사용자 데이터 엔티티 | 수정 | Model |

2. **의존관계**: 컴포넌트 간 의존 방향을 텍스트 다이어그램으로 표현한다.

```
Controller → Service → Repository → Model
           → Middleware
```

3. **변경 영향 범위**: 기존 시스템에서 영향받는 컴포넌트를 식별한다.

| 영향받는 컴포넌트 | 영향 내용 | 수준 |
|------------------|----------|------|
| 기존 SessionManager | JWT 전환으로 세션 관리 방식 변경 | 높음 |

**작성 기준**:
- 신규 컴포넌트는 기존 아키텍처 패턴(레이어링, 네이밍, 디렉토리 구조)을 따른다
- 기존 ARCHITECTURE.md와 충돌하면 안 된다
- 순환 의존이 없어야 한다

### 4-2. 데이터 모델

spec.md의 도메인 모델과 요구사항을 기반으로 데이터 모델을 설계한다.

**포함 내용**:

1. **엔티티 정의**:

| 엔티티 | 속성 | 타입 | 제약 |
|--------|------|------|------|
| User | id | UUID | PK |
| User | email | VARCHAR(255) | UNIQUE, NOT NULL |
| User | password_hash | VARCHAR(60) | NOT NULL |
| RefreshToken | token | VARCHAR(512) | UNIQUE |

2. **관계 설계**:

| 관계 | 타입 | 설명 |
|------|------|------|
| User -> RefreshToken | 1:N | 사용자당 복수 리프레시 토큰 |

3. **스키마**: 테이블/컬렉션 정의 (프로젝트 기술 스택에 맞는 형식)

4. **인덱싱 전략**: 쿼리 패턴 기반 인덱스 설계

| 인덱스 | 대상 | 근거 |
|--------|------|------|
| idx_user_email | User.email | 로그인 시 이메일 조회 |

5. **마이그레이션 고려**: 기존 데이터가 있을 경우 마이그레이션 전략

### 4-3. API 설계

spec.md의 FR과 AC를 기반으로 API를 설계한다.

**포함 내용**:

1. **엔드포인트 목록**:

| # | 메서드 | 경로 | 설명 | 인증 |
|---|--------|------|------|------|
| 1 | POST | /auth/login | 사용자 로그인 | 불필요 |
| 2 | POST | /auth/refresh | 토큰 갱신 | 리프레시 토큰 |
| 3 | POST | /auth/logout | 로그아웃 | 필요 |

2. **요청/응답 스키마**: 각 엔드포인트의 입출력 타입 정의

3. **에러 응답**: 각 엔드포인트의 에러 케이스와 응답 형식

4. **내부 인터페이스**: 서비스 간 인터페이스 (함수 시그니처, 이벤트)

**작성 기준**:
- 프로젝트의 기존 API 패턴(인증 방식, 응답 형식, 에러 코드)을 따른다
- spec.md의 AC와 직접 대응되는 엔드포인트가 있어야 한다
- Edge Cases(EC)에 대한 에러 응답이 포함되어야 한다

### 4-4. 기술 결정

설계에 필요한 기술 결정을 내리고 근거를 기록한다.

**기록 형식**:

```markdown
#### TD-{N}: {결정 제목}
- **결정**: {선택한 옵션}
- **근거**: {선택 이유}
- **대안**: {고려한 대안과 포기 이유}
- **영향**: {이 결정이 영향을 미치는 컴포넌트/모듈}
```

**예시**:

```markdown
#### TD-1: JWT 라이브러리 선택
- **결정**: jose
- **근거**: ESM 네이티브, 타입 안전, 표준 준수, 프로젝트 기존 의존성과 충돌 없음
- **대안**: jsonwebtoken (CJS 중심, ESM 호환 이슈), passport-jwt (Express 전용, 프레임워크 종속)
- **영향**: AuthService, AuthMiddleware
```

**작성 기준**:
- 모든 결정에 반드시 근거와 대안을 기록한다
- 프로젝트 기존 기술 스택과의 호환성을 최우선으로 고려한다
- 새 라이브러리 도입 시 번들 크기, 유지보수 상태, 라이선스를 확인한다

### 4-5. 보안 고려사항

spec.md의 Constraints와 NFR에서 보안 관련 요구사항을 추출하여 설계에 반영한다.

**포함 내용**:

1. **인증/인가**: 리소스별 접근 제어 방식

| 리소스 | 접근 제어 | 방식 |
|--------|----------|------|
| /auth/login | 공개 | 없음 |
| /api/users | 인증 필요 | JWT Bearer |
| /admin/* | 관리자 전용 | JWT + Role 검사 |

2. **데이터 보호**: 민감 데이터 식별 및 보호 전략

| 데이터 | 보호 수준 | 방식 |
|--------|----------|------|
| 비밀번호 | 높음 | bcrypt 해싱, 원문 저장 금지 |
| 토큰 | 높음 | HttpOnly 쿠키 또는 Authorization 헤더 |

3. **입력 검증**: 사용자 입력 검증 전략 (위치, 규칙)

### 4-6. 에러 핸들링

기능 전체에 대한 에러 핸들링 전략을 수립한다.

**포함 내용**:

1. **에러 분류**: 비즈니스 에러, 시스템 에러, 외부 연동 에러

| 분류 | 예시 | 처리 방식 | HTTP 코드 |
|------|------|----------|-----------|
| 비즈니스 | 잘못된 비밀번호 | 사용자 메시지 반환 | 401 |
| 비즈니스 | 계정 잠금 | 잠금 해제 시간 안내 | 429 |
| 시스템 | DB 연결 실패 | 재시도 + 로깅 | 503 |

2. **실패 시나리오**: test-scenarios.md의 부정 시나리오 기반 주요 실패 경로

3. **복구 전략**: 재시도, 폴백, 서킷브레이커 등

### 4-7. 제약 반영

spec.md의 Constraints 섹션의 모든 항목이 설계에 반영되었는지 확인한다.

**기록 형식**:

| # | 제약 조건 (spec.md) | 설계 반영 위치 | 반영 방식 |
|---|-------------------|--------------|----------|
| 1 | 기존 PostgreSQL 사용 | 2. 데이터 모델 | 기존 DB에 테이블 추가 |
| 2 | Next.js API Routes | 3. API 설계 | API Routes 패턴 사용 |

**작성 기준**:
- spec.md Constraints를 하나씩 읽고 매핑한다
- 반영되지 않은 제약이 있으면 설계를 수정한다
- 매핑이 불가능한 제약은 사유를 기록한다

## 5. 작성 전 필수 분석

SPEC-PLAN.md 작성 전에 반드시 아래를 수행한다:

1. **spec.md**: 요구사항(FR/NFR), 수용 기준(AC), 제약 조건(Constraints) 파악
2. **test-scenarios.md**: 테스트 시나리오와 AC 매핑 파악
3. **verify.md**: SPEC-VERIFY에서 발견된 경고/이슈 확인
4. **docs/ARCHITECTURE.md**: 기존 시스템 구조, 레이어, 컴포넌트 관계
5. **docs/PROJECT.md**: 기술 스택, 프로젝트 구조
6. **docs/CONVENTIONS.md**: 네이밍 규칙, 코드 패턴, 디렉토리 구조
7. **코드베이스**: 기존 컴포넌트 구조, 데이터 모델, API 패턴, 에러 핸들링 패턴

**추측하지 말고 실제로 읽어서 파악한다.**
