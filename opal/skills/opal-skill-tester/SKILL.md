# opal-skill-tester

단위 테스트를 통과해도 실제 Pilot 실행에서만 드러나는 결함이 있다(예: run-log 사건 형식 오류로 기록이 멈춤, 결정론 검사 오탐). 이 스킬은 같은 모의 과업을 격리된 저장소에서 헤드리스 세션으로 끝까지 돌리고, 세션에 보여주지 않은 숨은 인수 테스트와 표준 지표로 결과를 채점한다.

## 실행 비용을 먼저 알린다

실행 1회는 실제 Pilot 세션 하나다. 기능 모드 시나리오 1회에 약 20~35분, $10~15가 든다(참고: `function-stockctl-multiloc` 실측). 실행 전에 시나리오 메타의 예상 시간·비용 × 변형 수 × 반복 수를 사용자에게 알리고, 사용자가 실행을 요청한 경우에만 `run`을 호출한다.

## 명령

실행기는 `scripts/skill_tester.py`다. 설치본에서는 `~/.opal/skills/opal-skill-tester/scripts/skill_tester.py`를 `python3`로 실행한다.

| 명령 | 용도 |
|---|---|
| `list [--mode smoke\|function\|judgment]` | 시나리오 목록과 모드·예상 비용 |
| `validate [<id> \| --all]` | 시나리오 규격 검사(`references/scenario-spec.md`) |
| `run <id> [--variant V ...] [--repeat N] [--out DIR]` | 실행 → 수집 → 판정 → 보고서 |
| `report <out-dir>` | 이미 끝난 실행 폴더로 REPORT.md 재생성 |
| `record <out-dir> [--task-dir D]` | 실행 결과를 `tasks/`에 기록(`run`은 끝나면 자동 기록, `--no-record`로 끔) |
| `refresh [--project-root R]` | 모든 기록의 `report.html`을 다시 만든다. `record`(run 자동 기록 포함)도 끝에 같은 갱신을 하므로, 아카이브 직후 바로 링크를 고칠 때만 쓴다 |

- `--variant`를 주지 않으면 시나리오의 `default_variant` 하나로 **단일 실행**한다. 기본값이다.
- `--variant`를 두 번 이상 주면 같은 조건에서 나란히 돌리는 **비교 실행**이 된다. 예: `--variant "//opd --no-pm" --variant "//opd"`.
- `--repeat N`은 변형마다 N회 반복한다. 한 번의 결과로는 우연과 차이를 구분할 수 없으므로, 판단을 내릴 비교는 2회 이상을 권한다.
- 실행 결과 폴더(모의 저장소 포함) 기본값은 `/tmp/opal-skill-tester/<id>-<시각>/`이다.
- `run`이 끝나면 보고서·지표·실행별 세션 결과·모의 태스크 핵심 산출물을 프로젝트 `tasks/` 아래 `YYMMDD-opst-{대상 스킬}-{모드}-{시나리오 제목}` 폴더에 기록한다. 번호는 채번하지 않는다. 기록 폴더에는 `record.json`과 대시보드 `report.html`이 생긴다. 단일 실행은 `요약`+`이력: <변형>` 탭, 비교 실행은 `비교`+`상세: <변형>`+`이력: <변형>` 탭이다. 이력 탭은 `tasks/`와 `tasks/backup/` 아래 같은 스킬의 과거 기록을 모아 추세 차트와 표로 보여주고, 각 행에서 과거 실행 상세를 페이지 안에 펼치거나(모든 뷰어) 과거 대시보드를 새 탭으로 연다. 오래된 태스크가 `tasks/backup/`으로 옮겨져 경로가 바뀌어도, 기록할 때마다 모든 대시보드를 다시 만들어 링크를 현재 위치로 고친다. 현재 세션이 작업 중인 태스크가 있으면 `--task-dir <그 태스크 폴더>`를 넘겨 `skill-tests/` 아래에 기록한다. 넘기지 않으면 진행 중 태스크가 정확히 하나일 때만 그 아래에, 아니면 `tasks/` 바로 아래에 기록한다.

## 절차

### 1. 인터뷰로 실행 조건을 정한다

실행 조건은 사용자가 정한다. 무엇을 검증할지(모드)와 비용(시나리오·변형·반복)이 사용자 목적에 달려 있기 때문이다. 먼저 `list`로 현재 카탈로그를 읽고, 요청에 이미 담긴 답은 다시 묻지 않고 빠진 항목만 묻는다.

| 항목 | 요청에서 읽는 예 | 없을 때 묻는 선택지(첫 번째가 권장) |
|---|---|---|
| 대상 스킬(변형) | `//opst opds` → `//opds` | 시나리오 `target_pilots`에 있는 커맨드 |
| 실행 방식 | "비교", "A랑 B" → 비교 | 단일 실행 / 비교 실행(두 번째 변형도 묻는다) |
| 모드 | "스모크", "기능 테스트", "판단" | 스모크 / 기능 / 판단 — 각 선택지에 검증 질문 한 줄을 붙인다 |
| 시나리오 | id 또는 제목 | 고른 모드의 시나리오가 둘 이상일 때만 목록에서 묻는다 |
| 반복 | "2번씩" | 단일은 1회, 비교는 2회를 권장 |

- 가능하면 선택지형 질문 도구로 묻고, 한 번에 여러 항목을 묶어 **최대 2라운드**로 끝낸다. 1라운드는 대상·방식·모드·반복이고, 2라운드는 시나리오 선택이 필요할 때만 둔다.
- 모드 선택지 설명은 다음을 쓴다.
  - 스모크: 파이프라인이 끝까지 규칙대로 도는지만 본다. 가장 싸다.
  - 기능: 명세대로 제대로 만드는지 숨은 테스트로 채점한다.
  - 판단: 모호·충돌 요구를 사용자 결정으로 올리는지 본다.
- 요청한 스킬을 대상으로 하는 시나리오가 카탈로그에 없으면 실행하지 않는다. 시나리오를 새로 만들지 묻는다(아래 "시나리오 추가").

### 2. 실행 전 최종 확인

정해진 조건을 한 번에 요약해 확인받는다. 사용자가 "바로 돌려"처럼 실행을 명시했어도 이 확인은 생략하지 않는다. 실행 1회가 실제 비용을 쓰기 때문이다.

```text
시나리오: <id> (<모드>) — <제목>
변형: <V1>[, <V2>] × 반복 <N>회 = 세션 <K>개(병렬)
예상: 약 <분>분, $<합계> (시나리오 estimate × 세션 수)
진행할까요?
```

### 3. 사전 점검과 실행

- `validate <id>`가 통과해야 한다. 실행기는 run 시작 전에 같은 검사를 다시 하고, 설치본 `~/.opal`이 테스트하려는 소스와 다르면 경고한다. 스킬 소스를 고쳤다면 먼저 install한다.
- 확인을 받은 조건 그대로 `run`을 호출한다. 실행은 오래 걸리므로 백그라운드로 돌리고 끝날 때까지 기다린다.

### 4. 보고

`tasks/` 기록 폴더(응답의 `record`)의 `REPORT.md`를 읽어 판정과 핵심 지표를 요약하고, 사용자에게 `report.html` 경로를 알려 브라우저로 열게 한다. 불합격 항목은 원인이 스킬 결함인지, 시나리오·환경 문제인지 구분해 보고한다. 환경 문제(예: 설정 누락)로 실행이 초기에 멈췄다면 그 실행은 비교에서 제외한다.

## 테스트 모드와 판정

| 모드 | 검증 질문 | 합격 조건 |
|---|---|---|
| `smoke` | 파이프라인이 끝까지 규칙대로 도는가 | 준수 범주 전부 |
| `function` | 명세대로 제대로 만드는가 | 결과 범주 + 준수 범주 |
| `judgment` | 모호·충돌 요구를 사용자 결정으로 올리는가 | 결정 지점 적중 + 준수(상태 검증·run-log) |

지표 정의·임계값·기준 대비 추세 규칙은 `references/metrics.md`를 읽는다. 효율·재작업 범주는 합격 조건이 아니라 같은 변형·시나리오 과거 기록의 최근 3회 중앙값 대비 경고다. 과거 기록이 없으면 추세 판정은 생략된다(첫 기록).

## 시나리오 추가

새 시나리오는 `scenarios/<id>/`에 만든다. 규격·필수 파일·숨은 테스트 작성 규칙·판단 모드의 결정 지점 정의는 `references/scenario-spec.md`를 읽고 따른 뒤 `validate <id>`로 확인한다. 여러 시나리오가 같은 기반 저장소를 쓰면 `scenarios/_bases/`에 두고 `scenario.json`의 `base`로 참조한다.

## 격리와 주의

- 실행기는 기반 저장소를 결과 폴더로 복사해 새 git 저장소로 만들고 그 안에서만 세션을 돌린다. 원본 시나리오·프로젝트 저장소는 바뀌지 않는다.
- 모의 저장소는 `tasks/` 기록에 복사하지 않는다. 그 안의 `.git`과 `.opal/AGENT.md`가 실제 저장소에 중첩 저장소와 가짜 OPAL 프로젝트를 만들기 때문이다.
- 요구서는 저장소 밖(`<run>/REQUEST.md`)에 두고, 숨은 테스트는 저장소로 복사하지 않는다. 세션에 숨은 테스트 경로를 알려 주지 않는다.
- 세션은 `claude -p --permission-mode auto`로 실행된다. Pilot이 merge·push를 사용자 결정으로 남긴다. OPPB 시나리오가 격리 저장소 내 local merge를 명시 승인해도 결과 저장소 밖 push·배포로는 확장되지 않는다.
- 설치본을 바꾸는 install은 실행 중에 돌리지 않는다. 실행 중인 세션 아래에서 도구가 바뀌면 비교가 오염된다.
