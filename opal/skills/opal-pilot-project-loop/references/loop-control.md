# 루프 제어 가이드 (Loop Control Guide)

> opal-pilot-project-loop(oppl)의 2-루프(설계 수렴 루프 / 실행 수렴 루프) + 태스크 내부 파이프라인 공통 종료·안전 제어 지침.
> SKILL.md `## 루프 제어` 절에서 인라인 참조한다.
> 근거: `tasks/056-260710-opd-oppl-루프-오케스트레이터/SPEC.html` §07 "루프 제어 — 종료·안전".

---

## 1. 개요

oppl은 선형 Phase가 아니라 **종료조건이 있는 수렴 루프**로 구동한다 — Loop 1(설계 수렴: 인터뷰~Evaluator 검토, 4요소 잠김+미해결 0까지 반복), Loop 2(실행 수렴: 태스크 선택~종료 판정, 전 수용기준 GREEN+회귀 0까지 반복), 태스크 내부 파이프라인(T1~T5, 명세→구현→검증)이 그것이다. 세 계층 모두 "무한히 돌지 않는다"를 보장하기 위해 아래 8개 안전 요소를 갖춘다 (SPEC §07 표 전 항목).

**8개 안전 요소** (SPEC §07):

| # | 요소 | 요약 |
|---|------|------|
| 1 | [반복 상한](#2-반복-상한-루프별-hard-cap) | 루프별 hard iteration cap |
| 2 | [토큰/비용 예산](#3-토큰비용-예산) | run 단위 budget |
| 3 | [무진전 감지](#4-무진전-감지) | 목표에 가까워지지 않으면 중단 |
| 4 | [목표 달성 체크](#5-목표-달성-체크-수용-테스트-기반) | 검증가능 기준(수용 테스트)으로 판정 |
| 5 | [경로 분리](#6-경로-분리-성공실패에스컬레이션) | 성공 / 실패 / 에스컬레이션 |
| 6 | [에러 처리](#7-에러-처리-복구가능-vs-하드블로커) | 복구가능 vs 하드블로커 구분, 유형별 전략 |
| 7 | [컨텍스트 관리](#8-컨텍스트-관리-압축-작업기억) | 이전 반복을 압축 작업기억으로 요약 + 실행 로그 |
| 8 | [사람 게이트](#9-사람-게이트-비가역-행동-전) | 비가역 행동(배포·DB·TRD/PRD·외부계약) 전 사용자 승인 |

> TEST-SCENARIO.md S-055가 검사하는 "종료조건 5종"(반복상한·예산·무진전·목표체크·사람게이트)은 위 8요소 중 **직접 종료를 판정하는 5요소**(#1·#2·#3·#4·#8)다. 나머지 3요소(경로 분리·에러 처리·컨텍스트 관리)는 종료조건 자체가 아니라 종료조건을 안전하게 운용하기 위한 보조 장치다.

## 2. 반복 상한 (루프별 hard cap)

각 루프·서브루프는 **hard iteration cap**을 가진다. 초과 시 무조건 중단하고 에스컬레이션한다(자율 재시도 없음).

| 루프 | 상한 대상 |
|------|----------|
| Loop 1 설계 수렴 루프 | D1~D7 전체 회전 수 |
| Loop 2 실행 수렴 루프 | L0~L✓ 전체 회전 수 (= 백로그 태스크 처리 회전) |
| 태스크 내부 파이프라인 | T1~T5 + G 재작업 회전 수 (drift 재콜백 포함) |
| Evaluator 피드백 루프 (optimizer loop) | G 게이트 루브릭 미달 재작업 회전 수 |

> [MUST] **구체적 재시도 횟수·최대 반복 수는 여기서 새로 정의하지 않는다.** `opal/core/references/opal-harness.md` §1 "자동 루핑 제약(Verification Loop Guards)" 표를 **참조**하고 수치를 **복제하지 않는다** (opal-harness.md §1 "본 표를 참조" 원칙). 구현 수준 실패(L1 lint~L3b E2E)는 하네스 §1 표의 기존 재시도 한도를 그대로 따르며, 설계 수준 실패(G 게이트 루브릭 미달·PLAN 재진입)는 하네스 §1 "PLAN 재진입" 행의 상한을 따른다.
> oppl 고유 추가 상한(Loop 1/Loop 2 전체 회전 수)은 하네스 §1에 대응 행이 없으므로 **태스크 단위로 backlog.json `goal`(목표 요약) 대비 진행률을 관찰하며 무진전 감지(§4)와 결합해 판단**한다 — 별도 고정 수치를 SKILL 본문에 하드코딩하지 않는다.

## 3. 토큰/비용 예산

run(설계 루프 1회 진입 ~ 실행 루프 종료까지) 단위로 비용 예산을 관찰한다.

- PM은 각 태스크 파이프라인 완주(T1~T5)를 하나의 비용 단위로 취급하고, 디스패치 하이브리드 C(생성자 1회 + Evaluator 1회, 태스크당 ~2~3 디스패치 — SPEC §03 note)를 초과하는 재디스패치가 반복되면 예산 소진 신호로 간주한다.
- 저위험 슬라이스는 생성자·Evaluator 인라인 경량화(디스패치 생략)로 예산을 절약한다 (SPEC §03 note).
- 예산 소진이 감지되면 **경로 분리(§6)**의 에스컬레이션 경로로 전환한다 — 남은 예산 내 강행하지 않는다.
- 절대 토큰 수·달러 한도는 프로젝트/사용자 협의로 결정하는 가변 값이며, oppl SKILL 본문에 고정 수치를 하드코딩하지 않는다(플랫폼·모델별 상이 — 하드코딩 금지 원칙 준용).

## 4. 무진전 감지

**무진전(no-progress)** = 반복을 거듭해도 목표(backlog.json `goal`, 또는 태스크 수용기준)에 가까워지지 않는 상태. 아래 신호 중 하나 이상이 관찰되면 무진전으로 판정하고 루프를 중단한다.

| 신호 | 관찰 대상 |
|------|----------|
| 백로그 정체 | `backlog-tool done-check` 결과 `remaining[]`이 연속 회전에서 동일하거나 증가 |
| 동일 실패 반복 | 같은 시나리오(S-ID)·같은 게이트(G)에서 동일 사유로 반복 FAIL |
| 검증 왕복 | Evaluator verdict가 fail↔pass를 오가지 않고 fail에 고정된 채 회전 소진 |
| drift 반복 재콜백 | Evaluator drift 재콜백(§04 "구현/테스트 중 계약 drift 발견 시에만")이 동일 계약 항목에 대해 반복 발생 |

무진전 판정 시 **경로 분리(§6)**의 "실패" 또는 "에스컬레이션" 경로로 즉시 전환한다 — 동일 방식으로 재시도를 늘리지 않는다.

---

## 5. 목표 달성 체크 (수용 테스트 기반)

목표 달성 여부는 **검증가능 기준(수용 테스트)**으로만 판정한다 — 주관적 "충분히 됐다" 판단을 배제한다.

| 루프 | 종료(목표 달성) 판정 기준 |
|------|------------------------|
| Loop 1 설계 수렴 루프 | 4요소(PRD/TRD/CONTRACT/BACKLOG) 잠김 + Evaluator D6 미해결 이슈 0 |
| Loop 2 실행 수렴 루프 | `backlog-tool done-check` → `all_done:true` (전 태스크 수용기준 GREEN) + 회귀 0 |
| 태스크 내부 파이프라인 | test-scenario.json 전 시나리오 `result:pass` (T4a) + T4b 규칙검사 통과 |

판정은 항상 도구 호출 결과(backlog-tool `done-check`, test-tool `scenario-status`)를 근거로 하며, PM이 도구 결과 없이 "완료로 보인다"고 임의 판단하지 않는다 ([MUST] 도구 우선 원칙 — `docs/CONVENTIONS.md` §도구 우선 원칙).

---

## 6. 경로 분리 (성공/실패/에스컬레이션)

세 경로는 서로 배타적이며, 매 루프 회전(라운드) 끝에 정확히 하나로 분기한다.

| 경로 | 트리거 | 처리 |
|------|--------|------|
| 성공 | §5 목표 달성 체크 충족 | 다음 단계 진행 (Loop 종료 → 다음 Loop, 또는 T5 마무리 → BACKLOG 갱신) |
| 실패 (복구가능) | §7 "복구가능" 에러 유형, 반복 상한(§2) 미도달 | 하네스 §1 재시도 한도 내 재작업 루프 |
| 에스컬레이션 | §2 반복 상한 초과 / §3 예산 소진 / §4 무진전 감지 / §7 "하드블로커" | 즉시 사용자 보고, 자율 재시도 중단 |

> 에스컬레이션 경로는 "실패"의 하위가 아니라 독립 경로다 — 복구가능 실패의 재시도 누적이 상한을 넘으면 실패 경로에서 에스컬레이션 경로로 전환되지만, 하드블로커나 사람 게이트(§9) 대상 행동은 처음부터 에스컬레이션 경로로 직행한다.

---

## 7. 에러 처리 (복구가능 vs 하드블로커)

| 구분 | 정의 | 예 | 처리 |
|------|------|-----|------|
| 복구가능 (recoverable) | 재작업으로 해결 가능, 계약/설계를 부정하지 않음 | lint/format, build/type, unit/integration test FAIL, RED 미확인(`red_not_confirmed`) | 하네스 §1 재시도 한도 내 자동 fix 루프 |
| 하드블로커 (hard blocker) | 재작업 불가, 계약/설계 자체가 부정되거나 헌법 위반 | Evaluator readonly 계약 위반(H-4), 검증 2원화 순서 역전(H-9), backlog.json/test-scenario.json 손상, 사람 게이트 대상 행동을 승인 없이 진행 시도 | 즉시 중단 + 사용자 에스컬레이션 (0회 재시도) |

- 도구 결과 계약 위반(H-5 — 단일라인 JSON·exit code 불일치)은 도구 자체 버그로 간주해 **하드블로커**로 취급한다 — 파싱 실패를 추측으로 넘기지 않는다.
- 설계 수준 실패(G 게이트에서 Evaluator가 명세 자체의 결함을 지적)는 `opal/core/references/opal-harness.md` §1 "PLAN 재진입" 행의 scope별 분기(action→에이전트 자율 재설계 / wbs→PM 에스컬레이션 / trd→즉시 사용자 에스컬레이션)를 따른다.

## 8. 컨텍스트 관리 (압축 작업기억)

루프가 여러 회전을 거치며 컨텍스트가 누적되므로, 매 회전 종료 시 이전 반복을 **압축 작업기억**으로 요약한다.

- **압축 대상**: 각 회전의 {대상, 결과(PASS/FAIL), 사유, 시점} — verification.md §5 결과 계약과 동일 스키마.
- **저장 위치**: STATE.md(파이프라인 진행 요약) + 도구 SSOT(backlog.json/test-scenario.json)에 자연히 누적되는 상태값 — 별도 요약 파일을 신규로 만들지 않는다(3-SSOT 축 분리 원칙 준수).
- **실행 로그**: 각 도구 호출·디스패치 결과는 해당 산출물(QA-SPEC.md, DONE.md, GC-*.md)에 자기완결적으로 기록되며, PM은 다음 회전 진입 시 이 요약만 참조하고 이전 회전의 전체 대화·중간 산출물을 컨텍스트에 재로드하지 않는다.
- 세션이 재개될 때는 STATE.md·backlog.json·test-scenario.json 3-SSOT를 다시 읽어 압축된 상태에서 이어간다 — 처음부터 재추론하지 않는다.

## 9. 사람 게이트 (비가역 행동 전)

**비가역(irreversible) 행동**을 시도하기 전에는 항상 사용자 승인을 받는다 — agentic 모드에서도 예외 없다.

| 비가역 행동 범주 | 예 |
|-----------------|-----|
| 배포 | install-mac.sh 실행, 실 서비스 배포 |
| DB | 마이그레이션 적용, 스키마 변경 |
| TRD/PRD 확정 | D7 사용자 게이트 — 설계 산출물의 `docs/` 승격 |
| 외부 계약 | 외부 API 연동, 타 시스템에 영향을 주는 인터페이스 변경(§4 contract.md 오너십 계층 "외부 노출" 행) |

사람 게이트는 3-way 모드(interactive/semi-agentic/agentic) 승계와 별개로 항상 적용된다 — semi-agentic·agentic 모드가 EXECUTE 이전 auto-pass를 허용하지 않는 경계(TASK.md/SPEC 제약)와 동일한 정신으로, 비가역 행동은 모드에 관계없이 사용자 승인을 거친다.
