## 1. 개요

USER_JOURNEY.md와 USER_FLOW.md는 **조건부 산출물**이다 — 모든 oppl 프로젝트가 아니라 **user-facing 프로젝트에서만** 생성된다. 둘은 계층이 다르다.

| 산출물 | 소속 루프 | 계층 | 다루는 것 |
|--------|---------|------|----------|
| `USER_JOURNEY.md` | Loop 1 (설계 수렴 루프) — D1.5 | **거시** | 단계·행동·시스템 반응 (프로젝트 전체 여정) |
| `USER_FLOW.md` | 태스크 파이프라인 — T1 | **미시** | 분기·상태·에러경로 (개별 슬라이스 내부) |

이 둘은 계층 · 핵심 개념(SPEC §02)에서 정의한 "프로젝트 > 태스크(슬라이스) > 단계" 위계와 정확히 대응한다 — JOURNEY는 프로젝트 수준, FLOW는 태스크(슬라이스) 수준이다.

---

## 2. 트리거 조건 — user-facing 프로젝트만

**생성 조건**: 프로젝트가 사람이 직접 상호작용하는 화면·인터페이스를 가질 때만 트리거한다.

| 프로젝트 유형 | 트리거 |
|-------------|--------|
| 웹/앱 UI, 대화형 봇, 사용자 대면 CLI 인터랙션 | 트리거 (생성) |
| 인프라(배포·모니터링 도구) | 스킵 |
| 라이브러리/SDK (내부 API만 노출) | 스킵 |
| CLI 내부 로직 (사람이 매 단계 관찰하지 않는 배치/도구) | 스킵 |

판단은 Loop 1 D1 인터뷰에서 명확화된 목표·범위를 근거로 한다 — 인터뷰 결과 프로젝트가 인프라/라이브러리/CLI 내부용으로 확인되면 D1.5·T1의 UX 산출물 단계를 건너뛰고 다음 단계(D2 PRD, 또는 T2 테스트시나리오)로 직행한다. 스킵 여부와 근거는 STATE.md 또는 PLAN.md에 1줄로 기록한다(왜 생성하지 않았는지 추적 가능하게).

> **oppl 자신도 이 규칙의 적용 대상이다** — oppl 스킬/도구/에이전트 자체는 CLI 내부 자산이므로 이번 태스크(056)에서 USER_JOURNEY.md/USER_FLOW.md를 생성하지 않는다(스킵 사례의 자기참조 예시).

## 3. USER_JOURNEY.md (Loop1 거시)

**시점**: 인터뷰 중 ~ PRD 전 (D1.5), Loop 1 명확화 4요소가 슬라이싱(D5 백로그 분해)의 원천이 되기 전.

**작성자**: Planner.

**내용 — 단계·행동·시스템 반응**:

| 열 | 설명 |
|----|------|
| 단계 | 사용자 여정의 거시 마디 (예: 가입 → 온보딩 → 첫 사용 → 재방문) |
| 행동 | 그 단계에서 사용자가 하는 행동 |
| 시스템 반응 | 그 행동에 시스템이 보여주는 반응/결과 |

**용도**: D5 백로그 분해 시 "여정 단계 → 슬라이스" 매핑의 입력이 된다 (SPEC §03 D5 "어떻게" 열 "의존성 그래프(여정 단계 → 슬라이스)"). USER_JOURNEY.md 없이는 백로그 태스크 분해가 임의 기준으로 흐를 위험이 있다.

**형식**: Mermaid `flowchart` 또는 `sequenceDiagram`으로 여정을 시각화한다. 예:

```mermaid
flowchart LR
  A[가입] --> B[온보딩]
  B --> C[첫 사용]
  C --> D[재방문]
```

## 4. USER_FLOW.md (Loop2 미시)

**시점**: 태스크 파이프라인 T1 (명세·설계 단계), 해당 슬라이스가 인터랙션을 가질 때만.

**작성자**: 생성자(도메인 resolve — be/fe-agent 등).

**내용 — 분기·상태·에러경로**: 해당 슬라이스 내부의 상세 흐름 — 조건 분기, 화면/상태 전이, 에러 발생 시 경로. USER_JOURNEY.md의 거시 마디 하나를 미시적으로 펼친 것에 해당한다.

**형식**: Mermaid `flowchart`(상태·분기 중심) 또는 `sequenceDiagram`(컴포넌트 간 상호작용 중심) — 슬라이스 성격에 맞게 선택한다.

**Flow는 인터랙션 슬라이스만**: 순수 API/BE 슬라이스(사람이 직접 화면으로 상호작용하지 않는 계층)는 USER_FLOW.md를 생성하지 않고 **계약 테스트로 대체**한다 — CONTRACT.md 기계검증절(`contract.md` §2.2)의 계약 conformance 테스트가 그 역할을 한다.

## 5. G 게이트·검증과의 관계

- G 게이트(명세 리뷰, 구현 전)에서 Evaluator는 USER_FLOW.md가 존재하는 슬라이스에 대해 test-scenario.json의 시나리오가 Flow의 분기·에러경로를 빠짐없이 커버하는지 확인한다.
- USER_JOURNEY.md/USER_FLOW.md 자체는 Evaluator의 루브릭 판정 대상이 아니라(CONTRACT.md 루브릭절이 판정 대상), **테스트 시나리오 완전성의 참조 입력**으로 쓰인다.
