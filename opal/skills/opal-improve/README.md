# opal-improve

OPAL 사용 중 떠오른 개선 아이디어를 관찰→분류→기록→보고→승인 5단계로 처리해, 이 프로젝트만의 개선인지 프레임워크 전체의 개선인지를 가려 저장하는 스킬입니다.

## 개요

"이 부분 이렇게 바꾸면 좋겠다"는 생각이 들 때마다 어디에 적어야 할지 고민하지 않아도 되도록 만든 스킬입니다. 개선 아이디어를 말하면, 그것이 지금 진행 중인 **이 프로젝트에만 해당하는 개선**인지 아니면 **OPAL 프레임워크 자체의 개선**인지를 판단해 각각 알맞은 곳에 기록합니다.

- 판단(어디에 속하는가)은 이 스킬이 직접 수행합니다.
- 실제 기록(파일 쓰기)은 `improve-tool`이라는 별도 도구가 담당합니다. 스킬이 임의로 파일을 건드리지 않고, 항상 도구를 통해 결정론적으로 기록합니다.

## 트리거

- `//opim` 또는 `//opal-improve` 명시 호출
- "개선 제안", "프레임워크 개선", "개선 기록", "회고" 등의 발화
- PM이 판단이 애매하거나 같은 유형의 문제가 반복되는 것을 감지했을 때도 스스로 이 흐름을 따릅니다.

## 사용법

```
//opim
```

호출 뒤 개선하고 싶은 내용을 자유롭게 말하면 됩니다. 별도 인자 형식은 없습니다.

## 동작 흐름

1. **관찰**: 대화 중 나온 피드백이나, 지금까지의 작업 과정(재시도·재지시·반복된 문제)에서 개선 후보를 찾습니다. 후보가 없으면 "개선후보 0건"으로 끝냅니다 — 이 역시 정상 종료입니다.
2. **분류**: 이 개선이 프레임워크 소스(`opal/`, 스킬, 도구, 하네스 등)에 속하는지, 아니면 이 프로젝트 고유의 규칙·코드에 속하는지 가립니다.
   - 대상이 명확하면 바로 확정합니다.
   - 애매한 경계 사례만 "다른 프로젝트에서도 유효한가?", "특정 코드에 의존하는가?", "반영될 문서가 프레임워크 문서인가 프로젝트 문서인가?" 세 기준으로 다시 판단합니다.
   - 그래도 판단이 갈리면 임의로 정하지 않고 사용자에게 선택지를 제시해 묻습니다.
3. **기록**: 확정된 분류에 따라 `improve-tool`을 호출합니다.
   - **로컬(이 프로젝트 개선)** → 프로젝트 `.opal/MEMORY.json`에 후보로 추가됩니다. `MEMORY.json`이 아직 없는 프로젝트라면 조용히 건너뜁니다(오류 아님).
   - **FW(프레임워크 개선)** → `~/.opal/fw-inbox/`에 제안 파일로 쌓입니다. 이후 소유자 검토를 거쳐 프레임워크에 반영됩니다.
4. **보고**: 몇 건이 어떤 분류로 기록되었는지 짧게 알립니다.
5. **승인**: 사용자 이의가 없으면 확정합니다. 단, 이미 확정된 기준을 고치거나 지우는 일, 새 금지사항을 추가하는 일은 항상 사용자 승인이 필요합니다. 프레임워크 에이전트 정의 자체는 이 스킬로 수정하지 않습니다.

## 산출물

- 로컬 개선: 프로젝트의 `.opal/MEMORY.json`에 개선 후보(`type: improvement`, `status: candidate`)로 추가됨
- FW 개선: `~/.opal/fw-inbox/{일시}-{호스트}-{제목}.md` 파일 신규 생성 (출처 정보 포함)
- 둘 다 개선 후보로만 쌓이며, 즉시 코드나 문서를 고치지는 않습니다. 실제 반영은 별도 검토·승인 절차를 거칩니다.

## FAQ

### 이 스킬을 쓰면 바로 코드가 바뀌나요?
아니요. 이 스킬은 개선 아이디어를 정리해서 알맞은 위치에 "기록"만 합니다. 실제 반영(코드 수정, 규칙 확정)은 별도로 검토·승인하는 절차를 거칩니다.

### 로컬 개선과 프레임워크 개선을 헷갈리면 어떻게 하나요?
스킬이 자체 기준으로 먼저 판단하고, 판단이 애매한 경우에만 사용자에게 물어봅니다. 직접 어느 쪽인지 지정해서 요청해도 됩니다.

### `.opal/MEMORY.json`이 없는 프로젝트에서 로컬 개선을 시도하면 어떻게 되나요?
오류 없이 조용히 건너뜁니다(no-op). 아무 파일도 생기지 않습니다.
