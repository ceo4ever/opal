# PLAN 단계 상세 가이드 (범용)

이 가이드는 op-task-plan 스킬에서 참조된다. 도메인 무관 범용 태스크에서 사용한다.

> **실행 컨텍스트**: 이 가이드는 워커 에이전트의 컨텍스트에서 실행된다.
> 오케스트레이터가 워커를 디스패치하면, 워커가 이 가이드를 읽고 프로세스를 따른다.

---

## 현황 조사 원칙

현황 조사는 **모든 수단을 동원**하여 수행한다. 추측 금지. 실제로 읽고 확인한다.

### 활용 수단 (상황에 따라 선택)

| 수단 | 활용 상황 | 예시 |
|------|----------|------|
| Glob/Grep/Read | 파일 구조 파악, 기존 코드/문서 확인 | `Glob skills/**/*.md` |
| WebSearch | 최신 정보, 외부 레퍼런스, 라이브러리 문서 | 최신 API 변경 사항 |
| 스킬 SKILL.md Read | 기존 OPAL 스킬 패턴/프로세스 파악 | 유사 스킬 구조 참고 |
| 프로젝트 문서 Read | CONVENTIONS.md, ARCHITECTURE.md, PROJECT.md | 네이밍 규칙, 아키텍처 방향 |
| context7 MCP | 라이브러리 최신 문서 | 외부 패키지 API |

### 조사 항목

1. **관련 파일**: 태스크에 영향을 받거나 참조해야 하는 파일 목록
2. **현재 상태**: 관련 파일/시스템의 현재 구현 상태
3. **영향 범위**: 변경 시 영향을 받는 파일/시스템

---

## 1단계: 구현 범위 확정

현황 조사에서 파악한 변경 필요 파일 목록을 확정한다.

```markdown
### 파일 변경 계획

#### 신규 생성
| # | 파일 경로 | 역할 |
|---|----------|------|

#### 수정
| # | 파일 경로 | 변경 내용 |
|---|----------|----------|

#### 삭제
| # | 파일 경로 | 사유 |
|---|----------|------|
```

---

## 2단계: 구현 순서 결정

의존성을 고려하여 순서를 정한다. 원칙: **의존 받는 쪽(하위 레이어)부터 구현한다.**

일반적인 순서 원칙:
1. 공유 기반 파일 (다른 파일들이 의존) → 먼저
2. 독립적인 파일들 → 이후 (순서 자유)
3. 통합/검증 파일 → 마지막

구현 순서 테이블:
```markdown
| 순서 | 작업 | 파일 | 예상 난이도 |
|------|------|------|-----------|
```

---

## 3단계: 핵심 설계

각 파일의 핵심 변경 내용을 명세한다. 전체 내용을 쓰는 것이 아니라, **핵심 변경 사항과 설계 결정**을 정의한다.

작성해야 할 내용 (도메인에 따라 선택):
- **구조 변경**: 섹션 추가/삭제, 형식 변경
- **내용 명세**: 추가할 주요 내용의 개요
- **규칙/패턴**: 적용할 규칙이나 패턴
- **치환**: 기존 내용에서 변경할 항목

## 실행 체크리스트 작성

구현 순서를 바탕으로 실행 체크리스트를 작성한다.

### 분해 규칙

- **1파일 = 1 Step 권장**: 하나의 Step은 하나의 파일 또는 논리적 단위를 대상으로 한다
- **독립 완료 가능**: 각 Step은 완료 기준이 명확해야 한다
- **의존성 순서**: Step 간 의존성 순서를 명시한다
- **완료 기준 명확**: 각 Step에 "완료 기준"을 달아서, 끝났는지 모호하지 않게 한다

### Step 형식

```markdown
### Step N: {작업 제목}
- [ ] 완료
- **파일**: {대상 파일 경로}
- **작업 내용**: {무엇을 할지 구체적으로}
- **완료 기준**: {이것이 되면 완료}
- **테스트**: {어떻게 검증할지}
- **의존**: {선행 Step 번호 또는 "없음"}
```

### Phase 그룹핑 (병렬 판별)

하네스 §7 병렬 처리 원칙에 따라, 실행 체크리스트의 Step을 Phase로 그룹핑한다.

**그룹핑 규칙**:
1. `의존: "없음"` 이고 서로 다른 파일을 대상으로 하는 Step들 → **같은 Phase** (병렬 실행 가능)
2. 선행 의존이 있는 Step → 선행 Step의 Phase 이후 Phase에 배치
3. 동일 파일을 수정하는 Step → **반드시 순차** (같은 Phase에 넣지 않음)

**표기 방법**: 실행 체크리스트 상단의 요약 줄에 Phase 정보를 추가한다:

    > 총 {N}개 Step | Phase {M}개
    >
    > | Phase | Step | 실행 | 비고 |
    > |-------|------|------|------|
    > | 1     | 1, 2 | 병렬 | 독립 파일 |
    > | 2     | 3    | 순차 | Step 1 의존 |
    > | 3     | 4, 5 | 병렬 | 독립 파일 |

**적용 원칙**: op-task-plan은 항상 direct 실행이지만, 오케스트레이터가 Phase 정보를 기반으로 병렬 툴콜을 판단한다.

**Phase가 1개인 경우**: 모든 Step이 순차 의존이면 Phase 요약 테이블의 실행 컬럼을 모두 "순차"로 표기한다.

## QA 체크리스트 작성

```markdown
## 4. QA 체크리스트
### 기능 테스트
- [ ] {TASK.md 요구사항에 대응하는 검증 항목}
### 일관성 테스트
- [ ] {기존 파일/시스템과의 일관성 확인}
### 문서 품질
- [ ] 한국어 본문 + 영어 코드/필드명 규칙을 따르는가
- [ ] kebab-case 파일/폴더 네이밍을 따르는가
- [ ] YAML frontmatter가 올바른가 (해당 시)
```

## 품질 체크리스트

- [ ] 이 PLAN만 보고 바로 실행에 들어갈 수 있는가?
- [ ] 구현 순서의 의존성이 올바른가?
- [ ] 현황 조사를 실제 파일/문서/정보를 읽고 수행했는가? (추측 금지)
- [ ] 실행 체크리스트가 TASK.md 요구사항을 모두 커버하는가?
- [ ] QA 항목이 기능/일관성/품질을 포함하는가?
- [ ] 각 Step의 완료 기준이 명확하고 검증 가능한가?

---

## QA 에이전트 호출 안내

PLAN.md 작성이 완료되면, **오케스트레이터가 QA 에이전트를 호출**한다.

> **워커는 QA를 호출하지 않는다.** 워커는 PLAN.md 경로와 요약을 오케스트레이터에 반환하고, 오케스트레이터가 QA 에이전트를 별도로 호출한다.
