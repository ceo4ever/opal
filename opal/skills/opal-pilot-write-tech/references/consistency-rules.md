# 정합성 검증 규칙 (Consistency Rules)

otp-write-tech 스킬이 생성하는 산출물 간 일관성을 보장하기 위한 검증 규칙 정의서.

---

## 1. 유형 간 검증 (Cross-Type Validation)

산출물 유형 쌍별 체크 항목을 정의한다. 각 쌍은 양방향으로 검증한다.

### PRD ↔ TRD

| 체크 항목 | 방향 | 기준 |
|-----------|------|------|
| PRD의 모든 Must/Should 기능이 TRD에 기술적으로 커버되는가 | PRD → TRD | 누락 0건 |
| TRD의 기술 스택이 PRD의 비기능 요구사항(성능, 보안)을 충족하는가 | TRD → PRD | 충족 명시 필요 |
| 동일 개념에 동일 용어를 사용하는가 | 양방향 | 용어 매핑 테이블 기준 |

### PRD ↔ 서비스 정책서

| 체크 항목 | 방향 | 기준 |
|-----------|------|------|
| PRD의 비즈니스 규칙이 정책서에 상세화되었는가 | PRD → 정책서 | 각 규칙별 대응 정책 존재 |
| 정책서의 용어가 PRD와 일치하는가 | 정책서 → PRD | 용어 매핑 테이블 기준 |
| PRD 범위 내 정책이 모두 커버되었는가 | PRD → 정책서 | 누락 0건 |

### PRD ↔ IA

| 체크 항목 | 방향 | 기준 |
|-----------|------|------|
| PRD 기능 요구사항이 IA 기능 목록에 전수 매핑되는가 | PRD → IA | 누락 0건 (기능 매핑 테이블 사용) |
| IA의 메뉴 구조가 PRD 사용자 시나리오와 부합하는가 | IA → PRD | 시나리오별 탐색 경로 검증 |

### TRD ↔ IA

| 체크 항목 | 방향 | 기준 |
|-----------|------|------|
| TRD 아키텍처가 IA 기능을 기술적으로 지원하는가 | TRD → IA | 각 IA 기능에 대응하는 기술 컴포넌트 존재 |
| IA 데이터 I/O가 TRD 데이터 모델과 일치하는가 | IA → TRD | 입력/출력 필드 일치 |

### 서비스 정책서 ↔ IA

| 체크 항목 | 방향 | 기준 |
|-----------|------|------|
| 정책서 규칙이 IA 기능 동작에 반영되었는가 | 정책서 → IA | 각 정책 규칙이 IA 동작 설명에 언급 |
| IA에서 정책 관련 예외 처리가 명시되었는가 | IA → 정책서 | 예외 케이스 커버리지 |

### 외부 API 명세서 ↔ TRD (외부 API 연동 프로젝트 한정)

> 외부 API 명세서가 opwt 관리 산출물로 존재하는 경우에만 적용한다.

| 체크 항목 | 방향 | 기준 |
|-----------|------|------|
| 외부 API 명세서의 주요 엔드포인트가 TRD 기술 요구사항에 반영되었는가 | API명세서 → TRD | 활용 엔드포인트 전수 커버 |
| API 인증 방식(OAuth, API Key 등)이 TRD 보안 요구사항에 명시되었는가 | API명세서 → TRD | 인증 방식 정합 |
| TRD의 외부 API 연동 기술 요구사항이 명세서 스펙과 일치하는가 | TRD → API명세서 | 한도/제약 수용 여부 명시 |

### 외부 API 명세서 ↔ 서비스 정책서 (외부 API 연동 프로젝트 한정)

> 외부 API 명세서가 opwt 관리 산출물로 존재하는 경우에만 적용한다.

| 체크 항목 | 방향 | 기준 |
|-----------|------|------|
| API Rate limit/한도 제약이 서비스 정책에 반영되었는가 | API명세서 → 정책서 | 한도 초과 시 처리 정책 존재 |
| API 데이터 보존 기간/삭제 정책이 서비스 정책과 일치하는가 | API명세서 → 정책서 | 정책 충돌 0건 |
| 정책에서 활용하는 API 데이터 항목이 명세서에 존재하는가 | 정책서 → API명세서 | 누락 필드 0건 |

### 외부 API 명세서 ↔ IA (외부 API 연동 프로젝트 한정)

> 외부 API 명세서가 opwt 관리 산출물로 존재하는 경우에만 적용한다.

| 체크 항목 | 방향 | 기준 |
|-----------|------|------|
| IA 기능 정의에서 표시하는 데이터 항목이 API 응답 필드에 존재하는가 | IA → API명세서 | 표시 항목 전수 커버 |
| API 응답 구조 변경 시 IA 기능 정의에 영향 받는 항목이 반영되었는가 | API명세서 → IA | 영향 항목 누락 0건 |

### 기능 시나리오 다이어그램 ↔ 서비스 정책서

| 체크 항목 | 방향 | 기준 |
|-----------|------|------|
| 시나리오 예외/실패 케이스 분기가 정책서 비즈니스 규칙과 일치하는가 | 시나리오 → 정책서 | 예외 분기 1:1 매핑 |
| 정책서 규칙이 시나리오 정상·예외 경로 모두에 반영되었는가 | 정책서 → 시나리오 | 규칙 누락 0건 |
| 시나리오의 분기 결정 조건이 정책서 조건과 동일 표기되어 있는가 | 양방향 | 용어 일관성 |

### 기능 시나리오 다이어그램 ↔ TRD

| 체크 항목 | 방향 | 기준 |
|-----------|------|------|
| 시나리오 sequenceDiagram의 API 호출이 TRD API 명세 엔드포인트와 일치 | 시나리오 → TRD | 호출 1:1 매핑 |
| TRD 보안/인증 요구사항이 시나리오 인증 분기에 반영 | TRD → 시나리오 | 인증 분기 누락 0건 |
| 시나리오 DB 상호작용이 TRD 데이터 모델 테이블 정의와 일치 | 시나리오 → TRD | 데이터 흐름 정합 |

### 기능 시나리오 다이어그램 ↔ IA

| 체크 항목 | 방향 | 기준 |
|-----------|------|------|
| 시나리오 화면 진입점이 IA 메뉴 id와 1:1 매핑 | 시나리오 → IA | 진입점 누락 0건 |
| IA 기능 정의 description이 시나리오 정상 경로에 반영 | IA → 시나리오 | 동작 흐름 일치 |
| 시나리오의 access 분기가 IA access 권한(public/member/admin)과 정합 | 양방향 | 권한 분기 일치 |

### 화면 흐름도 ↔ IA

| 체크 항목 | 방향 | 기준 |
|-----------|------|------|
| 화면 흐름도의 화면 노드가 IA 메뉴 id와 1:1 매핑 | 화면 흐름도 → IA | 화면 노드 누락 0건 |
| IA depth 구조가 화면 흐름도의 화면 그룹화와 정합 | IA → 화면 흐름도 | 그룹화 일치 |
| 시나리오 다이어그램과 범위 중복 없음 (화면 흐름도 = 화면 단위 / 시나리오 = 기능 단위) | 양방향 | 범위 중복 0건 |

## 2. 유형 내 검증 (Intra-Type Validation)

동일 유형의 산출물이 복수인 경우(예: 여러 정책서) 적용한다.

### 복수 정책서 간 검증

| 체크 항목 | 기준 |
|-----------|------|
| 동일 개념에 동일 용어 사용 | 예: 회원정책서 "프리미엄 회원" = 결제정책서 "프리미엄 회원" |
| 범위 중복/누락 없음 | 각 정책서의 적용 범위가 명확히 구분되고, 공백 없음 |
| 상호 참조 정합성 | 타 정책서를 참조할 때 해당 정책서의 실제 정의와 일치 |

---

## 3. 용어 일관성 (Term Consistency)

모든 산출물에서 동일 개념은 동일 용어로 표현해야 한다.

### 용어 매핑 테이블

검증 시 아래 형식으로 테이블을 작성하고, 불일치 항목을 식별한다.

```
| 개념 | PRD 용어 | TRD 용어 | 정책서 용어 | IA 용어 | 불일치 |
|------|----------|----------|-------------|---------|--------|
| (예) 등급제 회원 | 프리미엄 회원 | premium_user | 프리미엄 회원 | 프리미엄 | IA 용어 불일치 |
```

**불일치 발견 시 처리:**
1. 테이블에 불일치 항목 기록
2. PM이 통일 기준 결정
3. 결정된 용어를 전체 산출물에 반영

---

## 4. 범위 일관성 (Scope Consistency)

산출물 간 다루는 범위(scope)의 포함 관계를 검증한다.

| 규칙 | 설명 |
|------|------|
| PRD 범위 ⊇ TRD 범위 | TRD가 PRD에 없는 기능을 정의하면 안 된다 |
| PRD 기능 목록 = IA 기능 목록 | 전수 매핑, 누락 0건 |
| 정책서 범위 ⊆ PRD 범위 | 정책서는 PRD에 명시된 기능/규칙의 상세화만 다룬다 |

**위반 시 처리:**
- TRD에 PRD 외 기능 존재 → TRD에서 제거하거나 PRD 범위 확장 결정
- IA에 PRD 외 기능 존재 → IA에서 제거하거나 PRD 범위 확장 결정
- 정책서에 PRD 외 규칙 존재 → PM 검토 후 PRD 업데이트 또는 정책서 삭제

## 5. 기능 매핑 (Feature Mapping)

PRD 요구사항과 IA 기능 간 1:1 매핑을 추적한다.

### 기능 매핑 테이블

```
| PRD 요구사항 ID | 요구사항 | IA 기능 ID | 기능명 | 매핑 상태 |
|-----------------|----------|------------|--------|-----------|
| REQ-001 | 회원가입 | IA-F-001 | 회원가입 화면 | 매핑됨 |
| REQ-002 | 소셜 로그인 | IA-F-002 | 소셜 로그인 버튼 | 부분매핑 |
| REQ-003 | 비밀번호 찾기 | — | — | 누락 |
```

**매핑 상태 정의:**
- `매핑됨` — PRD 요구사항이 IA 기능으로 완전히 커버됨
- `누락` — IA에 대응 기능 없음 (추가 필요)
- `부분매핑` — 일부만 커버됨 (상세 기술 필요)

## 6. QA 워커 프롬프트 템플릿 (QA Worker Prompt)

정합성 검증 워커에게 전달할 표준 프롬프트다.

```
## 정합성 검증 요청

### 검증 대상
- diagnosis.json 경로: {diagnosis_json_path}
- 검증 범위: {scope} (예: PRD ↔ TRD, 전체 등)

### 수행 절차

1. diagnosis.json을 읽어 생성된 산출물 목록과 경로를 파악한다
2. 각 산출물 파일을 Read한다
3. consistency-rules.md의 유형 간 검증(1절) 체크 항목을 순회한다
4. 복수 산출물이 있는 경우 유형 내 검증(2절) 체크 항목을 순회한다
5. 용어 매핑 테이블(3절)을 작성하고 불일치를 식별한다

   a. 각 참조 산출물 파일을 Read한다
   b. 외부 참조 산출물 검증(8절) 체크 항목을 순회한다
   c. 검증 결과를 external_reference 배열에 기록한다
```

## 7. 대규모 네트워크 처리 (Large Network Handling)

산출물이 10개 이상인 경우, 한 번에 모든 검증을 수행하면 컨텍스트 초과 위험이 있다.

### 배치 분할 전략

| 원칙 | 내용 |
|------|------|
| 배치 크기 | 한 번에 검증하는 산출물 쌍은 최대 4쌍으로 제한 |
| 배치 단위 | 핵심 산출물(PRD, TRD) 포함 쌍을 먼저 배치 구성 |
| 상태 유지 | 각 배치 완료 후 중간 결과를 파일로 저장 (`consistency-result-batch-{n}.json`) |

### 우선순위 기반 검증

검증 순서를 아래와 같이 정의한다:

1. **Tier 1 (필수)** — PRD ↔ TRD, PRD ↔ IA
2. **Tier 2 (중요)** — PRD ↔ 서비스 정책서, TRD ↔ IA
3. **Tier 3 (선택)** — 서비스 정책서 ↔ IA, 유형 내 검증, 기능 시나리오 다이어그램 ↔ 정책서/TRD/IA (시나리오 산출물 존재 시), 화면 흐름도 ↔ IA (화면 흐름도 산출물 존재 시)
4. **Tier 4 (외부 API 명세서)** — 외부 API 명세서↔TRD, 외부 API 명세서↔서비스 정책서, 외부 API 명세서↔IA (외부 API 명세서 관리 산출물 존재 시만)
5. **Tier 5 (외부 참조)** — 와이어프레임↔IA, ERD↔서비스 정책서, api-spec↔TRD, 화면 흐름도↔와이어프레임 (reference_artifacts 존재 시만)

자원이 부족하면 Tier 1만 완료하고 중단할 수 있다. 이 경우 Tier 2/3/4는 별도 배치로 처리한다.

### 점진적 검증

```
배치 1 완료 → 중간 보고 → PM 검토
배치 2 완료 → 중간 보고 → PM 검토
...
전체 완료 → 최종 통합 보고
```

중간 보고 형식:
```
배치 {n}/{total} 완료
- 검증 쌍: {pair_list}
- Pass: {n}건 / Fail: {n}건
- 즉시 조치 필요: {n}건 (있으면 목록 포함)
```

## 8. 외부 참조 산출물 검증 (External Reference Validation)

> **구분**: 이 섹션은 `diagnosis.json`의 `reference_artifacts` (읽기 전용 참조 문서)에 대한 검증이다.
> **외부 API 명세서 (opwt 관리 타입)**의 검증은 §1에 정의된 크로스 체크 규칙을 따른다.

diagnosis.json에 reference_artifacts가 존재하는 경우, 해당 참조 산출물과 opwt 산출물 간 정합성을 검증한다.
reference_artifacts가 없으면 이 섹션의 모든 체크 항목을 skip 처리한다.

### 와이어프레임 ↔ IA

| 체크 항목 | 방향 | 기준 |
|-----------|------|------|
| 와이어프레임 화면이 IA 메뉴 구조에 매핑되는가 | WF → IA | 각 화면에 대응하는 IA 메뉴 존재 |
| 와이어프레임 기능 동작이 IA 기능 정의에 반영되었는가 | WF → IA | 주요 기능 누락 0건 |
| IA 기능의 화면 경로가 와이어프레임 URL과 일치하는가 | IA → WF | path 불일치 0건 |

### 와이어프레임 ↔ 서비스 정책서

| 체크 항목 | 방향 | 기준 |
|-----------|------|------|
| 와이어프레임 입력 필드의 검증 규칙이 정책서에 정의되었는가 | WF → 정책서 | 주요 입력 필드의 검증 규칙 커버 |
| 와이어프레임 기능 조건이 정책서 비즈니스 규칙과 일치하는가 | WF → 정책서 | 조건 불일치 0건 |

### ERD ↔ 서비스 정책서

| 체크 항목 | 방향 | 기준 |
|-----------|------|------|
| 정책서 데이터 규칙이 ERD 엔티티/속성과 정합하는가 | 정책서 → ERD | 정책에서 언급하는 데이터 항목이 ERD에 존재 |
| ERD 제약조건(NOT NULL, FK 등)이 정책 규칙을 반영하는가 | ERD → 정책서 | 필수 필드, 참조 무결성 일치 |
| 코드성 컬럼의 값 범위가 정책서 정의와 일치하는가 | ERD → 정책서 | 코드값 매핑 일치 |

### ERD ↔ TRD

| 체크 항목 | 방향 | 기준 |
|-----------|------|------|
| TRD 데이터 모델 기술이 ERD 구조와 일치하는가 | TRD → ERD | 테이블/컬럼 구조 정합 |
| ERD 인덱스/제약조건이 TRD 성능 요구사항을 충족하는가 | ERD → TRD | 주요 쿼리 대상 인덱스 존재 |

### API 명세서 ↔ TRD

| 체크 항목 | 방향 | 기준 |
|-----------|------|------|
| TRD API 설계가 API 명세서와 일치하는가 | TRD → API | 엔드포인트/메서드/파라미터 일치 |
| API 인증/권한 규칙이 TRD 보안 요구사항과 일치하는가 | API → TRD | 인증 방식 정합 |

### API 명세서 ↔ 서비스 정책서

| 체크 항목 | 방향 | 기준 |
|-----------|------|------|
| API 응답의 에러 코드/메시지가 정책서 예외 처리와 일치하는가 | API → 정책서 | 주요 에러 시나리오 커버 |
| 정책서 비즈니스 규칙이 API 파라미터 검증에 반영되었는가 | 정책서 → API | 검증 규칙 정합 |

### 화면 흐름도 ↔ 와이어프레임

| 체크 항목 | 방향 | 기준 |
|-----------|------|------|
| 화면 흐름도 화면 노드가 와이어프레임에 대응 화면이 존재 | 흐름도 → 와이어프레임 | 화면 노드 누락 0건 |
| 와이어프레임의 화면 간 링크가 화면 흐름도 전환 화살표에 반영 | 와이어프레임 → 흐름도 | 전환 누락 0건 |
| 화면 흐름도 분기 조건이 와이어프레임 인터랙션 정의와 정합 | 양방향 | 분기 일치 |
