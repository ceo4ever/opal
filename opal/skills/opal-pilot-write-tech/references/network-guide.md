# network-guide.md

기술 산출물 간 논리적 연결 관계와 워커 디스패치 규칙을 정의한다.

---

## 1. 산출물 유형 정의

### 필수 4종

| 유형 | 설명 | 수량 |
|------|------|------|
| **PRD** (Product Requirements Document) | 제품 목표, 타깃 유저, 핵심 요구사항 | 보통 1개 |
| **TRD** (Technical Requirements Document) | 기술 요구사항, 아키텍처 설계, 기술 스택 | 보통 1개 |
| **서비스 정책서** | 회원/결제/환불 등 비즈니스 정책. 도메인별 독립 문서로 관리 | 도메인별 복수 |
| **IA** (Information Architecture, 기능 포함) | 정보구조도 + 기능 정의 통합. JSON으로 작성 후 검토 시 xlsx 변환 | 보통 1개 |

### 선택 4종

| 유형 | 설명 |
|------|------|
| **기능도** | 시스템의 기능 구조를 다이어그램으로 표현 |
| **순서도** | 비즈니스 프로세스 또는 시스템 흐름 표현 |
| **운영 정책서** | 운영 기준, 권한, 처리 절차 등 내부 운영 규정 |
| **서비스 매뉴얼** | 사용자 또는 운영자 대상 사용 가이드 |

### 프로젝트 특화 선택 타입

> 모든 프로젝트에 해당하지 않으며, 프로젝트 특성에 따라 선택적으로 추가한다.

| 유형 | 설명 | 수량 | 적용 조건 |
|------|------|------|----------|
| **외부 API 명세서** | 서드파티 API 스펙 분석·활용 정책 기획 산출물. 메타, 구글광고, 카카오 등 외부 API를 연동하는 기획 단계에서 작성한다. API 제공 데이터 구조, 한도/제약, 인증 방식, 활용 범위를 정리하고 정책서·IA·TRD와 논리적으로 연결한다. | API 공급자별 또는 도메인별 | 외부(서드파티) API 연동 프로젝트 |

> **내부 API와의 구분**: 외부 API 명세서는 기획 단계 산출물이다. 시스템 자체 API 설계(내부 API)는 개발 단계에서 별도로 처리하며 opwt 관리 대상이 아니다.

## 2. 논리적 연결 맵

### 유형 간 양방향 참조

```
PRD ↔ TRD
  PRD → TRD: 기능 요구사항 → 기술 구현 방식
  TRD → PRD: 기술 제약 → 요구사항 범위 조정

PRD ↔ 서비스 정책서
  PRD → 서비스 정책서: 핵심 요구사항 → 정책 상세화
  서비스 정책서 → PRD: 정책 결정 → 요구사항 보완

PRD ↔ IA
  PRD → IA: 기능 목록 → 정보 구조 설계
  IA → PRD: 구조 설계 → 요구사항 누락 발견

TRD ↔ IA
  TRD → IA: API/데이터 구조 → IA 기능 명세에 반영
  IA → TRD: 기능 명세 → 기술 구현 요건 도출

서비스 정책서 ↔ IA
  서비스 정책서 → IA: 정책 규칙 → IA 기능 조건/제약에 반영
  IA → 서비스 정책서: 화면/기능 구조 → 정책 보완 발견

서비스 정책서 ↔ 운영 정책서
  서비스 정책서 → 운영 정책서: 서비스 규정 → 운영 처리 절차 도출
  운영 정책서 → 서비스 정책서: 운영 기준 → 서비스 정책 보완

외부 API 명세서 ↔ TRD (외부 API 연동 프로젝트 한정)
  외부 API 명세서 → TRD: API 엔드포인트/파라미터/응답 스펙 → 기술 요구사항 도출
  TRD → 외부 API 명세서: 기술 제약(인증, 한도) → 명세서 보완

외부 API 명세서 ↔ 서비스 정책서 (외부 API 연동 프로젝트 한정)
  외부 API 명세서 → 서비스 정책서: API 한도/제약/정책 → 서비스 정책 규칙 반영
  서비스 정책서 → 외부 API 명세서: 서비스 정책 결정 → API 활용 범위 재검토

외부 API 명세서 ↔ IA (외부 API 연동 프로젝트 한정)
  외부 API 명세서 → IA: API 제공 데이터 필드 → 기능 정의 및 표시 항목 설계
  IA → 외부 API 명세서: 기능 요구 데이터 → 필요 API 필드 보완 확인

외부 API 명세서 ↔ 와이어프레임 (외부 API 연동 프로젝트 한정)
  외부 API 명세서 → 와이어프레임: API 응답 데이터 구조 → 화면 구성요소 설계 검증
  와이어프레임 → 외부 API 명세서: 화면 표시 항목 → API 필드 커버리지 확인
```

### 유형 내 연결 (복수 정책서 간)

동일 도메인 또는 연관 도메인의 서비스 정책서가 복수 존재할 때:

- **용어 통일**: 동일 개념에 대해 각 문서에서 동일한 용어를 사용한다
- **범위 중복 방지**: 정책 적용 범위가 겹치지 않도록 경계를 명확히 한다
- **상호 참조**: 연관 정책서를 `참조 문서` 섹션에 명시하고 연결 관계를 기록한다

### 각 연결의 참조 항목

| 소스 문서 | 참조 항목 | 대상 문서 |
|-----------|-----------|-----------|
| PRD > 기능 목록 | 기능별 구현 방식 결정 | TRD |
| PRD > 타깃 유저 | 정책 적용 대상 정의 | 서비스 정책서 |
| PRD > 핵심 요구사항 | 메뉴/기능 구조 설계 | IA |
| TRD > API 명세 | IA 기능 파라미터 정의 | IA |
| TRD > 데이터 모델 | IA 기능 조건 반영 | IA |
| 서비스 정책서 > 회원 정책 | 회원 관련 기능 제약 조건 | IA |
| 서비스 정책서 > 결제/환불 정책 | 결제 흐름 기능 정의 | IA |
| 서비스 정책서 > 서비스 규정 | 운영 처리 기준 도출 | 운영 정책서 |

## 3. 순서 체인

### 기본 흐름

```
PRD → TRD → 서비스 정책서 → IA
```

1. **PRD**: 제품 목표와 요구사항을 먼저 확립
2. **TRD**: PRD 기반으로 기술 구현 방식 설계
3. **서비스 정책서**: 요구사항 기반으로 도메인별 정책 상세화
4. **IA**: 앞선 세 문서를 종합하여 정보 구조와 기능을 정의

### 역방향 가능

어떤 문서든 먼저 작성할 수 있다. 프로젝트 상황에 따라 시작점이 달라질 수 있다:

- **TRD 선행**: 기술 스택이 먼저 결정된 경우
- **서비스 정책서 선행**: 규제/컴플라이언스 요건이 우선인 경우
- **IA 선행**: 화면 기획 중심으로 시작한 경우

### 역방향 처리 규칙

선행 문서가 나중에 작성될 경우, 정합성 재검증을 수행한다:

1. 이미 작성된 문서에서 선행 문서와 충돌하는 내용을 식별한다
2. 충돌 항목을 `diagnosis.json`의 `issues`에 기록한다
3. 영향 받는 문서를 보강(보강/재작성) 대상으로 재분류한다

## 4. 수정 시 영향 분석

### 절차

```
수정 대상 문서 식별
  └→ diagnosis.json에서 connected_to 문서 목록 조회
       └→ 각 연결 문서에 대해 영향 수준 판단
            └→ 연쇄 업데이트 범위 결정
```

### 영향 수준 판단

| 수준 | 기준 | 처리 |
|------|------|------|
| **직접** | 수정된 항목이 연결 문서의 특정 섹션에 직접 인용되거나 반영됨 | 해당 섹션 즉시 보강/재작성 |
| **간접** | 수정된 항목의 상위 개념이 연결 문서의 방향에 영향을 줌 | 정합성 검토 후 필요 시 보완 |
| **없음** | 수정 내용이 연결 문서와 실질적 관련이 없음 | 스킵 |

### 연쇄 업데이트 범위 결정

1. 직접 영향 문서: `status`를 `보강` 또는 `재작성`으로 갱신
2. 간접 영향 문서: `status`를 `OK`로 유지하되 `issues`에 검토 메모 추가
3. 변경된 diagnosis.json을 기반으로 배치를 재편성

## 5. diagnosis.json 스키마

Phase 2 PM 진단 산출물 JSON 구조.

```json
{
  "project": "프로젝트명",
  "scan_path": "기존 문서 경로",
  "reference_artifacts": [
    {
      "id": "고유 식별자 (kebab-case)",
      "type": "wireframe | erd | api-spec",
      "name": "산출물명",
      "path": "파일 경로",
      "scope": "커버하는 범위 설명 (예: 로그인 화면, 회원 도메인 ERD)"
    }
  ],
  "documents": [
    {
      "id": "고유 식별자 (kebab-case)",
      "type": "PRD | TRD | 서비스 정책서 | IA | 기능도 | 순서도 | 운영 정책서 | 서비스 매뉴얼 | 외부 API 명세서",
      "name": "문서명",
      "path": "기존 경로 (없으면 null)",
      "status": "보강 | 재작성 | 신규 | OK",
      "version": "현재 버전 (없으면 null)",
      "issues": ["이슈 목록"],
      "depends_on": ["의존 문서 id"],
      "connected_to": ["연결 문서 id"]
    }
  ],
  "batches": [
    {
      "batch": 1,
      "items": ["문서 id 목록"],
      "reason": "배치 사유 (독립/의존 설명)"
    }
  ]
}
```

### 필드 설명

| 필드 | 설명 |
|------|------|
| `id` | kebab-case 고유 식별자. 예: `prd-main`, `policy-member`, `ia-v1` |
| `type` | 산출물 유형 (섹션 1 정의 기준) |
| `name` | 문서 제목 (사람이 읽는 이름) |
| `path` | 파일 경로. 아직 없으면 `null` |
| `status` | 처리 방향: 보강(일부 수정), 재작성(전면 재작성), 신규(새로 생성), OK(변경 없음) |
| `version` | 현재 버전 문자열. 없으면 `null` |
| `issues` | 발견된 문제, 누락, 불일치 목록 |
| `depends_on` | 이 문서 작성 전에 완료되어야 하는 문서 id 목록 |
| `connected_to` | 논리적으로 연결된 문서 id 목록 (의존과 무관하게 정합성 체크 대상) |
| `batches` | 의존 관계 기반 병렬/순차 작업 그룹 |
| `reference_artifacts` | 외부 참조 산출물 목록. opwt가 관리하지 않지만 작성 시 참조하는 문서 |
| `reference_artifacts[].type` | 참조 유형: `wireframe`, `erd`, `api-spec` |
| `reference_artifacts[].scope` | 커버 범위 (어떤 도메인/화면을 다루는지) |

## 6. Phase 1 워커 프롬프트 템플릿

문서 분석 워커에게 전달하는 표준 프롬프트.

```
## 작업 지시

당신은 기존 기술 문서를 분석하는 전문가입니다.

### 분석 대상
- 스캔 경로: {scan_path}
- 프로젝트: {project_name}

### 수행 작업

1. 지정 경로에서 기술 문서 목록을 파악한다.
2. 각 문서를 읽고 다음을 판단한다:
   - 문서 유형 (PRD / TRD / 서비스 정책서 / IA / 기능도 / 순서도 / 운영 정책서 / 서비스 매뉴얼)
   - 현재 품질 수준과 이슈
   - 처리 방향 (보강 / 재작성 / OK)
3. 문서 간 논리적 연결 관계를 파악한다 (connected_to).
4. 작성 순서 의존성을 파악한다 (depends_on).
5. 의존 관계를 바탕으로 배치를 편성한다 (batches).
6. 프로젝트에 외부 참조 산출물(와이어프레임, ERD, API 명세서 등)이 있는지 확인한다.
   - docs/wireframes/, docs/erd/, docs/api-spec/ 경로 스캔
   - PROJECT.md 문서 테이블에서 관련 문서 탐색
   - 발견된 참조 산출물은 reference_artifacts에 기록한다.

### 출력 형식

아래 스키마를 따르는 diagnosis.json을 작성한다:

{diagnosis_json_schema}

### 주의 사항

- 존재하지 않는 문서는 status를 "신규"로 설정하고 path를 null로 한다.
- 이슈는 구체적으로 기술한다 ("내용 부족"보다 "결제 취소 정책 미정의" 형태로).
- 판단이 불확실한 경우 issues에 "확인 필요: {내용}" 형태로 기록한다.
```

## 7. Phase 3 워커 프롬프트 템플릿

문서 작성/수정 워커에게 전달하는 표준 프롬프트.

### 7-1. 보강 (일부 수정)

```
## 작업 지시

당신은 기술 문서 작성 전문가입니다. 기존 문서를 보강합니다.

### 대상 문서
- 문서명: {name}
- 유형: {type}
- 현재 경로: {path}
- 식별된 이슈: {issues}

### 참조 문서
{depends_on 문서 목록과 경로}

### 외부 참조 산출물
{reference_artifacts 목록과 경로 — 해당하는 것만}
- 와이어프레임: {경로} — 화면 구성요소/기능 동작 참조
- ERD: {경로} — 엔티티/속성/관계 참조
- API 명세서: {경로} — 엔드포인트/파라미터 참조

### 수행 작업

1. 현재 문서를 읽고 전체 구조를 파악한다.
2. 이슈 목록의 항목을 순서대로 해결한다.
3. 참조 문서와 정합성을 확인하고 불일치 항목을 수정한다.
4. 기존 문서의 구조와 톤을 유지하면서 수정한다.
5. 외부 참조 산출물이 제공된 경우, 해당 내용을 참조하여 작성한다.
   - 와이어프레임: 화면 구성요소와 기능 동작을 정책서/IA에 반영
   - ERD: 엔티티/속성 정의를 정책서 데이터 규칙에 반영
   - API 명세서: API 엔드포인트/파라미터를 TRD/정책서에 반영

### 출력

보강된 문서를 원래 경로에 저장한다.
변경 내용을 요약하여 보고한다.
```

### 7-2. 재작성 (전면 재작성)

```
## 작업 지시

당신은 기술 문서 작성 전문가입니다. 문서를 전면 재작성합니다.

### 대상 문서
- 문서명: {name}
- 유형: {type}
- 현재 경로: {path} (기존 내용은 참고용)
- 식별된 이슈: {issues}
```

## 8. 배치 편성 규칙

### 기본 원칙

`depends_on` 필드를 기준으로 배치를 자동 편성한다. 하네스 §7.4 리소스 관리 원칙에 따라 고부하 작업 시 배치를 제한한다.

```
depends_on가 없는 문서  →  같은 배치 (병렬 처리 가능)
depends_on가 있는 문서  →  의존 문서 배치 완료 후 다음 배치
```

### 리소스 기반 제한 (Concurrency Limit)

배치 내 문서들의 크기를 합산하여 병렬 개수를 조절한다.

| 배치 총합 크기 | 병렬 제한 (Max) | 비고 |
|---------------|----------------|------|
| 200KB 이상 | 순차 (Sequential) | 매우 큰 문서 세트 |
| 100KB ~ 200KB | 2개 | 대용량 문서 포함 시 |
| 100KB 미만 | 제한 없음 (Full Parallel) | 일반적인 경우 |

- **단일 파일 제한**: 특정 문서가 50KB를 초과하는 경우, 해당 문서는 단독 배치 또는 Max 2개로 편성 권장.
- **오케스트레이터 판단**: PM이 `diagnosis.json` 생성 시 `reason`에 리소스 기반 제한 사유를 명시한다.

### 편성 알고리즘

1. `depends_on`이 비어 있거나 이미 완료된 항목만 참조하는 문서를 배치 1로 묶는다.
2. 배치 1 완료 후 새로 의존성이 해소되는 문서를 배치 2로 묶는다.
3. 모든 문서가 배치에 편성될 때까지 반복한다.
4. 각 배치의 `reason`에 독립/의존 관계를 명시한다.

### 예시

```json
{
  "batches": [
    {
      "batch": 1,
      "items": ["prd-main", "policy-member"],
      "reason": "의존 문서 없음. 병렬 처리 가능."
    },
    {
      "batch": 2,
      "items": ["trd-main", "policy-payment"],
      "reason": "trd-main은 prd-main에 의존. policy-payment는 policy-member에 의존."
    },
    {
      "batch": 3,
      "items": ["ia-v1"],
      "reason": "ia-v1은 prd-main, trd-main, policy-member, policy-payment 모두에 의존."
    }
  ]
}
```

### 순환 의존 감지

`depends_on`을 따라가다 자기 자신으로 돌아오는 경우 순환 의존으로 판단한다.

- 순환 의존 감지 시: 배치 편성을 중단하고 PM에게 판단을 요청한다
- 보고 형식: "순환 의존 감지: {문서 A} → {문서 B} → {문서 A}. 의존 방향을 재검토해주세요."

## 9. IA 형식 가이드

### 산출물 구성

IA는 **JSON + Mermaid 사이트맵** 이중 출력을 기본으로 한다.

| 파일 | 역할 | 필수 여부 |
|------|------|----------|
| `ia.json` | 구조 데이터 — 기능 정의, 정책 연결, 조건 등 전체 스펙 | 필수 |
| `ia-sitemap.md` | Mermaid 시각화 — 계층 구조 사이트맵, 기획 검토용 | 필수 |
| `ia.xlsx` | 스프레드시트 내보내기 — 외부 공유, 비개발자 협업 시 | 선택 |

### IA JSON 스키마

```json
{
  "service": "서비스명",
  "version": "1.0",
  "menus": [
    {
      "id": "메뉴 고유 식별자 (kebab-case)",
      "name": "메뉴명",
      "type": "html | app | popup | batch | external-api",
      "depth": 1,
      "parent_id": null,
      "description": "화면 설명",
      "path": "URL 경로 (해당 시)",
      "access": "public | member | admin",
      "features": [
        {
          "id": "기능 고유 식별자",
          "name": "기능명",
          "description": "기능 설명 (조건/규칙 포함)",
          "linked_policy": ["연관 정책서 id"]
        }
      ],
      "children": []
    }
  ]
}
```

#### 필드 설명

| 필드 | 설명 |
|------|------|
| `menus[].id` | kebab-case 고유 식별자. 예: `home`, `mypage-order` |
| `menus[].type` | 화면 타입: `html`(웹 페이지), `app`(앱 화면), `popup`(팝업), `batch`(배치), `external-api`(외부 API 연동) |
| `menus[].depth` | 메뉴 깊이. 최상위 = 1 |
| `menus[].parent_id` | 부모 메뉴 id. 최상위는 `null` |
| `menus[].description` | 화면 설명 — 화면의 목적과 주요 내용 |
| `menus[].access` | 접근 권한: `public`(비회원), `member`(로그인 필요), `admin`(관리자) |
| `features[].description` | 기능 설명 — 동작 방식, 조건, 비즈니스 규칙 통합 기술 |
| `features[].linked_policy` | 이 기능과 관련된 서비스 정책서 id |

### Mermaid 사이트맵 변환 스펙

IA JSON을 `flowchart TD` Mermaid 다이어그램으로 변환한다.

#### JSON 필드 → Mermaid 매핑

| JSON 필드 | Mermaid 대응 |
|-----------|-------------|
| `id` | 노드 ID |
| `name` | 노드 레이블 (`["name"]`) |
| `depth` | `classDef depth{N}` 스타일 |
| `parent_id` | `parent_id --> id` 엣지 |
| `access: admin` | `classDef admin` 스타일 오버라이드 |

#### classDef 스타일 기준

```
classDef root    fill:#1a1a1a,color:#fff,stroke:none       ← 루트 (depth 0)
classDef depth1  fill:#555,color:#fff,stroke:none,rx:6     ← 1depth
classDef depth2  fill:#999,color:#fff,stroke:none          ← 2depth
classDef depth3  fill:#ccc,color:#333,stroke:none          ← 3depth
classDef admin   fill:#4a6fa5,color:#fff,stroke:none       ← 관리자 전용 메뉴
classDef member  fill:#5a9a6a,color:#fff,stroke:none       ← 로그인 필요 메뉴
```

> `access`가 `admin` 또는 `member`이면 depth 스타일 대신 access 스타일을 적용한다.

#### 파일명 및 저장 경로

- JSON과 동일 경로에 저장: `ia.json` → `ia-sitemap.md`
- Mermaid 코드 블록(` ```mermaid `)으로 래핑하여 .md 파일로 저장

#### 대규모 IA 분리 기준

| 노드 수 | 처리 방식 |
|---------|----------|
| 50개 이하 | 단일 파일 (`ia-sitemap.md`) |
| 50개 초과 | 도메인(1depth 기준)별 분리 (`ia-sitemap-{domain}.md`) + 전체 개요 (`ia-sitemap.md`에 1depth만 표시) |

### 검토 도구 내보내기 (선택)

xlsx가 필요한 경우(외부 공유, 비개발자 협업 등) JSON 확정 후 단일 시트로 변환한다.
저장 경로: JSON과 동일 경로. 예: `ia.json` → `ia.xlsx`

#### 단일 시트 컬럼 정의

| # | 컬럼명 | JSON 매핑 | 설명 |
|---|--------|-----------|------|
| 1 | 번호 | 자동 순번 | 행 번호 |
| 2 | 1Depth | depth=1 `name` | 최상위 메뉴명 |
| 3 | 2Depth | depth=2 `name` | 2단계 메뉴명 |
| 4 | 3Depth | depth=3 `name` | 3단계 메뉴명 |
| 5 | 4Depth | depth=4 `name` | 4단계 메뉴명 |
| 6 | 타입 | `type` | html/App/Popup/Batch/외부Api |
| 7 | 화면ID | `id` | kebab-case 고유 식별자 |
| 8 | 화면명 | `name` | 현재 depth의 메뉴명 |
| 9 | 화면 설명 | `description` | 화면 목적 및 주요 내용 |
| 10 | URL | `path` | URL 경로 |
| 11 | 접근권한 | `access` | public/member/admin |
| 12 | 기능 | `features[].name` | 기능명 (복수 시 행 반복) |
| 13 | 기능 설명 | `features[].description` | 기능 동작, 조건, 규칙 |
| 14 | 비고 | `features[].linked_policy` + 메모 | 정책서 연관 id, 이슈 등 |

#### 행 구성 규칙

- **기능이 없는 메뉴**: 기능/기능 설명/비고 컬럼 공란, 메뉴 행 1개
- **기능이 복수인 메뉴**: 기능별로 행 반복, 메뉴 정보(1~11번 컬럼) 셀 병합
- **Depth 컬럼**: 해당 depth 컬럼만 채우고 하위 depth 컬럼은 공란

## 10. 외부 참조 산출물

참조 산출물은 opwt가 직접 생성/관리하지 않으며, "읽기 전용"으로 활용한다.

### 참조 산출물 유형

### 참조 산출물 획득

PM이 Phase 2 진단 시 프로젝트에서 참조 산출물을 스캔한다:
1. `docs/PROJECT.md` 문서 테이블에서 참조 산출물 경로 탐색
2. 사용자가 직접 경로를 제공
3. 프로젝트 내 일반적 경로 스캔 (`docs/wireframes/`, `docs/erd/`, `docs/api-spec/`)

### 주의 사항

- opwt는 참조 산출물의 존재를 "문서 경로"로만 인지한다 (스킬 의존 없음)
- 참조 산출물이 없어도 opwt는 정상 동작한다 (선택적 보강)
- 참조 산출물의 생성/수정은 각 전담 스킬 또는 PM 오케스트레이션으로 해결
