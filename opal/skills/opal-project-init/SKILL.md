# opal-project-init

프로젝트 환경을 초기화하거나 최신화하는 스킬.

## 설계 원칙

프로젝트는 **WHAT**(무엇을)과 **WHY**(왜)를 정의하는 것이다. HOW(어떻게)는 다양할 수 있다.
opi가 만든 프로젝트 환경(`docs/`, `.opal/`)은 모든 스킬(opal-pilot-dev, opal-pilot-write-tech 등)의 컨텍스트가 된다.

**핵심 규칙**:
- 모든 문서는 알투가 프로젝트를 분석한 후 **직접 작성**한다. 플레이스홀더 치환이 아니다.
- 작성 후 반드시 **사용자 검토 → 피드백 → 반영** 사이클을 거친다.
- 문서 작성 시 반드시 참조 가이드를 Read한다:
  - `~/.opal/skills/opal-project-init/references/docs-guide.md` — docs 문서 구조/내용 지침
  - `~/.opal/skills/opal-project-init/references/agent-guide.md` — AGENT.md 구조/내용 지침

## 모드 판별

프로젝트 루트에서 `.opal/AGENT.md` 존재 여부로 자동 판별한다.

| 조건 | 모드 |
|------|------|
| `.opal/AGENT.md` 미존재 | **초기화 모드** — 처음부터 환경 구축 |
| `.opal/AGENT.md` 존재 | **최신화 모드** — 기존 환경을 현재 상태에 맞게 갱신 |

## 초기화 모드

`.opal/AGENT.md`가 없는 프로젝트에서 실행한다. 5개 Phase로 진행한다.

### Phase 0: 태스크 폴더 생성

모든 Phase 시작 전에 먼저 태스크 폴더와 TASK.md를 생성한다.

1. `tasks/` 폴더에서 기존 태스크 번호를 확인하여 다음 번호를 결정한다.
2. `tasks/{NNN}-opi-{프로젝트명}/TASK.md`를 생성한다:

```markdown
# TASK: opi 프로젝트 초기화

- 모드: 초기화
- 시작일시: YYYY-MM-DD HH:mm
- 상태: 진행 중
```

3. 완료 시 DONE.md는 Phase 4에서 추가한다.

---

### Phase 1: 프로젝트 이해

소스 분석과 사용자 대화를 통해 프로젝트를 파악한다.

**1-1. 프로젝트 분석**

2단계로 프로젝트를 분석한다.

**Step A. 프로젝트 레이아웃 탐색**

프로젝트 루트의 디렉토리 트리를 depth 2~3으로 스캔하여 실제 구조를 발견한다.

발견된 디렉토리를 아래 기준으로 분류한다 (판별 우선순위 순):

| 우선순위 | 판별 기준 | 분류 |
|---------|----------|------|
| 1 | config 파일 존재 | **코드 디렉토리** |
| 2 | 문서 파일 존재 (.md, .docx, .pdf 등) | **문서 디렉토리** |
| 3 | `tasks/` 패턴 | **태스크 디렉토리** |
| 4 | 위 어디에도 해당 안 됨 | **미분류** (인터뷰에서 사용자에게 확인) |

코드 디렉토리 판별 config 파일:

| config 파일 | 기술 |
|------------|------|
| `package.json` | Node.js (React, Next.js, Vue.js, Express 등) |
| `pyproject.toml` / `requirements.txt` | Python (FastAPI, Django, Flask 등) |
| `go.mod` | Go |
| `pom.xml` | Java + Maven (Spring Boot 등) |
| `build.gradle` / `build.gradle.kts` | Java/Kotlin + Gradle |
| `Cargo.toml` | Rust |

폴더명(`frontend/`, `server/`, `back/` 등)은 **보조 힌트**로만 사용한다. 최종 판별은 config 파일 존재 여부가 우선이다.

루트에 config 파일이 있으면 루트 자체가 코드 디렉토리로 분류된다 (표준 구조 하위 호환).

레이아웃 탐색 결과를 내부 참조용으로 정리한다:
```
[레이아웃 탐색 결과]
코드: frontend/ (package.json), backend/ (pyproject.toml)
문서: docs/, 100.기획/
태스크: tasks/
미분류: assets/, scripts/
```

**Step B. 기술 스택 분석**

Step A에서 발견된 **모든 코드 디렉토리**에서 config 파일을 탐색한다. 코드 디렉토리가 0개면 이 단계를 건너뛴다.

코드 디렉토리별 분석:

| 분석 대상 | 추출 정보 |
|----------|----------|
| `package.json` | 프로젝트명, 설명, FE 스택 (next→Next.js, react→React, vue→Vue.js) |
| `pyproject.toml` / `requirements.txt` | BE 스택 (fastapi→FastAPI, django→Django, flask→Flask) |
| `go.mod` / `Cargo.toml` / `pom.xml` / `build.gradle` | BE 스택 (Go, Rust, Java 등) |
| `.env`, `docker-compose.yml` | 포트, DB 타입, 외부 서비스 |

프로젝트 전체 분석:

| 분석 대상 | 추출 정보 |
|----------|----------|
| `README.md` | 프로젝트 설명, 설치 방법 |
| `CLAUDE.md`, `.cursorrules`, `GEMINI.md` | 기존 컨벤션, 아키텍처 규칙 |
| 발견된 문서 디렉토리 | 기존 문서 목록 (docs/ 외 포함) |

**1-2. 프로젝트 카테고리 판별**

Step A 레이아웃 탐색 결과를 바탕으로 카테고리를 자동 제안한다.

**개발 프로젝트** (코드 디렉토리가 1개 이상 발견):

| 서브 카테고리 | 판별 기준 |
|--------------|----------|
| FE 단독 | FE config만 발견 (package.json + FE 프레임워크) |
| BE 단독 | BE config만 발견 (pyproject.toml, go.mod, pom.xml 등) |
| 풀스택 | FE + BE config 모두 발견 (모노레포 포함) |
| 기획+개발 | 코드 디렉토리 + 문서 디렉토리 모두 발견 |

**일반 프로젝트** (코드 디렉토리 0개):

기획만, 문서만, 빈 프로젝트 모두 포함. 있는 것만 docs/에 기록하고, 없으면 빈 상태로 시작하여 최신화로 채워간다.

사용자에게 분석 결과를 보여주고 확인받는다:

```
[프로젝트 분석 결과]

프로젝트 구조를 분석했습니다.

{레이아웃 탐색 결과 요약}
  코드: {발견된 코드 디렉토리 + 기술 스택}
  문서: {발견된 문서 디렉토리}
  미분류: {미분류 디렉토리 — 있으면}

프로젝트 카테고리:
  1. 개발 프로젝트 — {서브 카테고리} ({근거})
  2. 일반 프로젝트

추천: {자동 판별 결과}. 맞나요?
{미분류 디렉토리가 있으면} "{폴더명}"은 어떤 용도인가요?
```

빈 프로젝트인 경우:

```
[프로젝트 분석 결과]

프로젝트 루트가 비어있습니다.
인터뷰를 통해 프로젝트를 파악하고 docs/를 생성하겠습니다.

어떤 프로젝트를 시작하시나요?
  1. 개발 프로젝트 — 코드를 작성할 프로젝트
  2. 일반 프로젝트 — 기획, 문서 등 비개발 프로젝트
```

**1-3. 사용자 인터뷰**

사용자은 전문가가 아닐 수 있다. **객관식 중심으로 쉽게 답할 수 있게** 하고, 맞는 것이 없으면 직접 입력하게 한다.

**진행 방식**:
1. 기본 질문 세트(7개)를 **한 번에 하나씩** 진행한다
2. 시작 시 "7개 질문을 드리겠습니다" 안내한다
3. 이전 답변을 기반으로 다음 질문의 선택지를 맞춤 생성한다
4. 기본 질문 완료 후, 추가 질문이 필요하면 "N개 더 여쭤볼게요" 안내 후 진행

**시작 안내**:

```
프로젝트를 파악하기 위해 7개 질문을 드리겠습니다.
객관식으로 준비했으니 편하게 답해주세요. 없으면 직접 입력하시면 됩니다.
```

**기본 질문 (7개, 한 번에 하나씩)**:

```
Q1/7. 프로젝트명
      분석 결과: {소스에서 추출한 이름 (있으면)}
      → 맞으면 그대로, 수정하려면 알려주세요.
      (분석 결과 없으면: "프로젝트 이름을 알려주세요.")

Q2/7. 이 프로젝트를 한 줄로 설명하면?
      → 직접 입력

Q3/7. 어떤 분야의 프로젝트인가요?
      a) 웹 서비스 (이커머스, SaaS, 커뮤니티 등)
      b) 모바일 앱
      c) AI/ML (에이전트, 데이터 분석, 자동화 등)
      d) 인프라/DevOps
      e) 기획/문서 (비개발)
      f) 프레임워크/라이브러리
      g) 기타: 직접 입력해주세요

Q4/7. 지금 어느 단계에 있나요?
      a) 아이디어 단계 (구상 중)
      b) 초기 설계 (기획/설계 진행 중)
      c) 개발 중 (MVP 또는 기능 개발)
      d) 안정화 (버그 수정, 최적화)
      e) 운영 중 (유지보수)
      f) 기타: 직접 입력해주세요

Q5/7. 알투가 이 프로젝트의 PM으로서 어떤 관점으로 검토하면 좋을까요?
      {Q3 도메인 답변을 기반으로 맞춤 제안 2~3개 생성}
      a) {도메인 맞춤 제안 1}
      b) {도메인 맞춤 제안 2}
      c) 잘 모르겠어요 (알투가 제안할게요)
      d) 직접 입력

Q6/7. 이 프로젝트에서 가장 중요한 원칙이 있나요?
      {Q3 도메인 기반으로 예시 제안}
      a) {예: "UX 단순성 최우선"}
      b) {예: "데이터 정합성 최우선"}
      c) 아직 없어요 (나중에 정할게요)
      d) 직접 입력

Q7/7. 추가로 만들고 싶은 문서가 있나요?
      a) PRD (제품 요구사항 정의서)
      b) 기능명세서
      c) 기획서
      d) 지금은 없어요
      e) 기타: 직접 입력해주세요
```

**추가 질문** (기본 질문 완료 후, 필요 시):

개발 프로젝트인 경우, 기술적 질문이 추가로 필요할 수 있다.

```
기본 질문 끝났습니다! {N}개만 더 여쭤볼게요.

Q8. 기술 스택을 알려주세요 (분석에서 파악한 것이 있으면 확인)
    분석 결과: {파악된 스택}
    → 맞으면 그대로, 수정/추가하려면 알려주세요.

Q9. ...
```

**규칙**:
- **반드시 한 번에 하나씩** 질문한다. 한꺼번에 여러 개 묻지 않는다.
- 질문 번호에 **전체 개수를 표시**한다 (Q1/7, Q2/7...)
- 소스 분석에서 이미 파악한 것은 **기본값으로 제시**하고 확인만 받는다
- 이전 답변을 기반으로 다음 질문의 **선택지를 맞춤 생성**한다 (특히 Q5, Q6)
- **"잘 모르겠어요"** 선택지를 항상 포함한다 — 알투가 대신 제안
- 추가 질문 시작 전에 반드시 **"N개 더 여쭤볼게요"** 안내

### Phase 2: 공통 문서 작성 + 검토

참조 가이드를 Read한 후 문서를 직접 작성한다.

**사전 준비**: 아래 가이드를 반드시 Read한다.
- `~/.opal/skills/opal-project-init/references/docs-guide.md`
- `~/.opal/skills/opal-project-init/references/agent-guide.md`

**2-1. 작성 대상**

| 순서 | 파일 | 설명 | 참조 가이드 |
|------|------|------|------------|
| 1 | `docs/PROJECT.md` | 프로젝트 정의 (SSOT) | docs-guide.md |
| 2 | `.opal/AGENT.md` | PM 프로필 (역할, 검토 기준, 업무 지침) | agent-guide.md |
| 3 | `.opal/MEMORY.md` | 메모리 인덱스 (빈 상태로 생성) | - |
| 4 | 사용자 요청 문서 | PRD, 기획서 등 사용자이 추가 요청한 문서 | docs-guide.md |

**2-2. 작성 프로세스**

각 문서를 순서대로 작성한다:

1. 참조 가이드의 구조에 맞춰 초안을 작성한다
2. 사용자에게 초안을 제시한다
3. 사용자 피드백을 받아 반영한다
4. 사용자 승인 후 확정한다

**2-3. 문서 등록 프로토콜**

사용자 요청 문서를 포함하여 새 문서를 생성할 때마다:

1. 사용자에게 확인: "이 문서를 프로젝트 문서로 등록할까요?"
2. 용도 인터뷰: "이 문서의 용도는 무엇인가요? 어떤 작업에서 참조하면 좋을까요?"
3. 사용자 승인 시 `docs/PROJECT.md`의 프로젝트 문서 테이블에 등록
4. 등록되지 않은 문서는 다른 스킬이 참조하지 않는다

**2-4. MEMORY.md 형식**

```markdown
# {프로젝트명} 프로젝트 Memory Index

## 프로젝트
{빈 상태 — 프로젝트 진행하며 축적}
```

### Phase 3: 개발 문서 (개발 프로젝트만)

일반 프로젝트는 이 Phase를 건너뛰고 Phase 4로 간다.

**3-1. 추가 분석**

Phase 1-1에서 발견된 **코드 디렉토리**를 기반으로 심화 분석한다 (루트 고정 아님). 코드 디렉토리가 여러 개이면 각각 분석한다.

- 분석 경로: Phase 1-1 Step A에서 발견된 코드 디렉토리
- 기술 스택 상세 (버전, 설정, 의존성 관계)
- 아키텍처 (레이어 구조, 모듈 분리, 데이터 흐름)
- 코드 구조 (디렉토리 레이아웃, 네이밍 패턴, 공통 모듈)
- 개발 환경 (포트, 환경 변수, 빌드 도구)

기술적 결정사항이 불명확하면 사용자에게 추가 질문한다.

**3-2. 작성 대상**

| 문서 | 조건 | 참조 가이드 |
|------|------|------------|
| `docs/ARCHITECTURE.md` | 항상 | docs-guide.md |
| `docs/CONVENTIONS.md` | 항상 | docs-guide.md |
| `docs/BACKEND.md` | BE 코드 디렉토리 발견 시 | docs-guide.md |
| `docs/FRONTEND.md` | FE 코드 디렉토리 발견 시 | docs-guide.md |

**3-3. 작성 프로세스**

Phase 2와 동일한 프로세스를 따른다:

### Phase 4: 플랫폼 파일 + 완료

**4-1. 플랫폼 파일 생성**

`apply.js` 스크립트로 플랫폼 부트스트래퍼를 생성한다.

```bash
node ~/.opal/skills/opal-project-init/scripts/apply.js --project-root {프로젝트 경로}
```

생성 대상:

| 템플릿 소스 | 생성 위치 | 내용 |
|------------|----------|------|
| `templates/common/platform/CLAUDE.md` | `{프로젝트}/CLAUDE.md` | OPAL 부트스트래퍼 |
| `templates/common/platform/GEMINI.md` | `{프로젝트}/GEMINI.md` | OPAL 부트스트래퍼 |
| `templates/common/platform/.cursorrules` | `{프로젝트}/.cursorrules` | OPAL 부트스트래퍼 |

기존 파일 처리:
- `CLAUDE.md`: OPAL 마커(`# === OPAL START ===`) 기반 병합. 기존 사용자 내용 보존 + 부트스트래퍼 갱신
- `GEMINI.md`, `.cursorrules`: 기존 파일 `.bak` 백업 후 부트스트래퍼 추가
- 이미 OPAL 마커가 있으면 갱신만 수행

Node.js가 없는 환경에서는 알투가 직접 부트스트래퍼를 삽입한다.

**4-2. 프로젝트 메모리 갱신**

`.opal/MEMORY.md`가 존재하면 (초기화 모드에서 방금 생성했으면) 작업 히스토리에 opi 완료를 기록한다.

```markdown
| # | 작업 | 단계 | 경로 | 시작일시 | 완료일시 |
|---|------|------|------|---------|---------|
| {N} | opi 프로젝트 초기화 | 완료 | docs/, .opal/ | YYYY-MM-DD HH:mm | YYYY-MM-DD HH:mm |
```

최신화 모드에서도 동일하게 기록한다:
```markdown
| {N} | opi 프로젝트 최신화 | 완료 | docs/, .opal/ | YYYY-MM-DD HH:mm | YYYY-MM-DD HH:mm |
```

**4-3. tasks/ DONE.md 기록**

Phase 0에서 생성한 `tasks/{NNN}-opi-{프로젝트명}/` 폴더에 완료 기록을 추가한다.

- **TASK.md**: Phase 1 분석 결과(프로젝트 카테고리, 기술 스택, 인터뷰 요약) + 업데이트 대상 목록으로 내용을 보완하고, 상태를 `완료`로 갱신한다.
- **DONE.md**: 생성/변경된 문서 목록 + 핵심 결정 사항

> STATE.md, PLAN.md 등 복잡한 산출물은 생략한다 (세션 복원이 필요한 장기 작업이 아님).

**4-4. 완료 보고 + 원래 요청으로 복귀**

opi는 프로젝트 셋업이 목적이지만, 사용자의 **원래 요청**이 있었다면 자연스럽게 다음 단계로 이어간다.

사용자의 원래 요청을 분석하여:
- **개발 요청** ("만들어줘", "개발해줘") → otp 스킬로 이어가기 제안
- **문서 요청** ("PRD 작성해줘", "기획서 만들어줘") → 문서 작업으로 이어가기 제안
- **셋업만 요청** ("프로젝트 초기화해줘") → 완료 보고만

```
---
opi 완료

프로젝트: {프로젝트명}
카테고리: {개발/일반} 프로젝트

생성된 문서:
- {생성된 문서 목록}

플랫폼 파일:
- CLAUDE.md, GEMINI.md, .cursorrules (부트스트래퍼)
---
```

**원래 요청으로 자동 복귀**:

opi는 프로젝트 셋업 수단이지 목적이 아니다. 사용자의 원래 요청을 기억하고, 셋업 완료 즉시 다음 단계로 넘어간다.

```
[원래 요청이 개발인 경우] → 셋업 완료 보고 후 바로 otp 실행
알투: "프로젝트 셋업 완료했습니다. {원래 요청}에 맞춰 개발을 시작합니다."
  → opal-pilot-dev 또는 opal-pilot-dev-short를 자동 판단하여 바로 TASK 단계 진입

[원래 요청이 문서인 경우] → 셋업 완료 후 바로 문서 작성 시작
알투: "프로젝트 셋업 완료했습니다. {요청한 문서} 작성을 시작합니다."

[셋업만 요청한 경우] → 완료 보고만
알투: "프로젝트 셋업 완료했습니다. 무엇을 도와드릴까요?"
```

**자동 판단 기준**:
- 전체 앱/서비스 개발 ("만들어줘", "개발해줘") → `//oppd` opal-pilot-project-dev (opwt로 PRD/TRD → 로드맵 → opd/opds 태스크 순차 실행)
- 단일 기능 추가/수정 → opal-pilot-dev 또는 opal-pilot-dev-short
- 문서 작업 → 해당 문서 작성 시작
- 판단 불확실 → 사용자에게 간단히 확인

사용자에게 "어떤 스킬로 할래요?"라고 묻지 않는다. 알투가 PM으로서 판단하고 바로 진행한다.

> oppd 스킬 미존재 시 opal-pilot-dev로 폴백한다.

### Phase 2: 프로젝트 유형별 분석

**병렬 처리 원칙** (하네스 §7 준수):
독립적인 분석 항목은 병렬로 수행한다. 의존관계 있는 분석만 순차로 실행한다.

**개발 프로젝트** (코드가 있는 프로젝트):

Step A~C를 병렬로 수행한 후, Step D를 순차 실행한다.

| Step | 분석 항목 | 병렬 가능 | 비고 |
|------|----------|----------|------|
| A. 프로젝트 레이아웃 재스캔 | 디렉토리 트리 + config 파일 | ✅ | 초기화 모드 Step A와 동일 |
| B. 기술 스택 분석 | config 파일 파싱 | ✅ | 초기화 모드 Step B와 동일 |
| C. 코드 구조 심층 분석 | 코드 레벨 탐색 | ✅ | **신규** (아래 상세) |
| D. 구조적 요소 1:1 비교 | 문서 vs 실제 대조 | ❌ (A/B/C 의존) | **신규** (아래 상세) |

**Step C. 코드 구조 심층 분석** (개발 프로젝트 전용)

코드 디렉토리별로 아래 항목을 탐색하여 설계 사상을 파악한다:

| 분석 대상 | 탐색 패턴 | 추출 정보 |
|----------|----------|----------|
| 엔트리포인트 | `main.*`, `index.*`, `app.*` 파일 탐색 | 앱 시작점, 초기화 흐름 |
| 베이스 클래스/상속 체계 | `class.*Base`, `extends`, `implements` 패턴 검색 + 주요 클래스 상속 관계 | 공통 패턴, 추상화 수준 |
| 미들웨어/인터셉터 | `middleware/`, `interceptor/` 디렉토리 탐색 | 요청 처리 파이프라인 |
| 설정 로더 | `config.*`, `settings.*` 파일 탐색 | 환경 설정 구조, 프로파일 |
| 라우터/컨트롤러 | `routes/`, `controllers/`, `router.*` 탐색 | API 엔드포인트 구조 |
| 공유 유틸리티 | `utils/`, `shared/`, `common/` 디렉토리 탐색 | 재사용 모듈 |

> **플랫폼 독립**: 탐색 방법은 도구명이 아닌 행위(파일 탐색, 패턴 검색)로 기술한다. 각 플랫폼의 에이전트가 자기 도구로 실행한다.
> 코드 디렉토리가 여러 개이면 각각 분석한다.
> Phase 1-0에서 수집한 변경 맥락을 기반으로 변경 가능성 높은 영역을 우선 탐색한다.

**Step D. 구조적 요소 1:1 비교** (Step A/B/C 완료 후)

각 문서의 구조 관련 섹션을 실제 코드와 1:1 대조한다:

| 문서 | 비교 섹션 | 비교 대상 (실제) | 비교 방법 |
|------|----------|----------------|----------|
| ARCHITECTURE.md | 디렉토리 구조 | Step A 레이아웃 결과 | 경로 diff |
| ARCHITECTURE.md | 기술 스택 상세 | Step B 스택 분석 결과 | 버전/의존성 diff |
| ARCHITECTURE.md | 시스템 구성 | Step C 엔트리포인트/미들웨어 | 컴포넌트 존재 여부 diff |
| CONVENTIONS.md | 네이밍 규칙 | Step C 실제 네이밍 패턴 | 패턴 일치 여부 |
| CONVENTIONS.md | 파일 구조 | Step A 디렉토리 레이아웃 | 규칙 vs 실제 diff |
| BACKEND.md | 서버 구조 | Step C BE 분석 결과 | 레이어/모듈 diff |
| BACKEND.md | 도메인 패턴 | Step C 베이스 클래스/상속 | 패턴 일치 여부 |
| FRONTEND.md | 클라이언트 구조 | Step C FE 분석 결과 | 라우팅/컴포넌트 diff |

비교 결과를 **4가지로 분류**한다:
- **일치**: 문서와 실제가 동일
- **불일치**: 문서 기재 내용과 실제가 다름
- **문서에 없음**: 실제에는 있지만 문서에 기재되지 않은 항목
- **실제에 없음**: 문서에 기재되어 있지만 실제로는 삭제/이동된 항목

> 해당 문서가 없는 경우 (예: BACKEND.md 미존재) → 아래 "새 문서 필요성 판단"에서 처리

**Step E. 새 문서 필요성 판단** (Step D 완료 후)

Step D의 "문서에 없음" 항목을 기반으로 새 문서 후보를 도출한다.

| 조건 | 제안 문서 |
|------|----------|
| BE 코드 디렉토리 발견 + BACKEND.md 미존재 | docs/BACKEND.md 생성 권장 |
| FE 코드 디렉토리 발견 + FRONTEND.md 미존재 | docs/FRONTEND.md 생성 권장 |
| ARCHITECTURE.md 미존재 | docs/ARCHITECTURE.md 생성 권장 |
| CONVENTIONS.md 미존재 | docs/CONVENTIONS.md 생성 권장 |
| 신규 도메인/프레임워크가 독립 문서 수준으로 큰 경우 | 도메인별 가이드 생성 제안 |
| "문서에 없음" 항목이 기존 문서 어디에도 자연스럽게 포함되지 않는 경우 | 해당 주제의 독립 문서 제안 |

> 후보 목록은 Phase 2.5에서 사용자에게 보고하고, 사용자 확정 후 Phase 3에서 생성한다.
> 새 문서 생성 시 docs-guide.md를 참조하고, 문서 등록 프로토콜을 따른다.

**일반/문서 프로젝트** (코드가 없는 프로젝트):

Step A~B를 병렬로 수행한 후, Step C를 순차 실행한다.

| Step | 분석 항목 | 병렬 가능 |
|------|----------|----------|
| A. 문서 전체 스캔 | ✅ |
| B. 문서 간 정합성 검증 | ✅ |
| C. 변경점 정리 | ❌ (A/B 의존) |

**Step A. docs/ 하위 문서 전체 스캔**

1. `docs/` 하위 문서 전체를 스캔한다
2. 문서 정리 상태를 점검한다:
   - 문서 테이블에 미등록된 문서가 있는가
   - 등록된 문서 중 삭제/이동된 것이 있는가
   - 설명/용도가 비어있거나 오래된 것이 있는가

**Step B. 문서 간 정합성 검증**

docs/ 하위 문서들 간의 정합성을 검증한다:

| 검증 항목 | 방법 |
|----------|------|
| 상호 참조 유효성 | 문서 내 링크/참조가 실제 존재하는 문서를 가리키는지 확인 |
| 용어 일관성 | 동일 개념을 다른 문서에서 다른 이름으로 부르고 있지 않은지 확인 |
| 정보 충돌 | 동일 사실에 대해 문서 간 상이한 기술이 없는지 확인 |
| 날짜/버전 정합성 | Phase, 버전, 날짜 정보가 문서 간 일치하는지 확인 |

**Step C. 변경점 정리 + 새 문서 필요성 판단** (Step A/B 완료 후)

Step A/B 결과를 종합하여 변경 필요 항목을 정리한다.

| 조건 | 제안 문서 |
|------|----------|
| docs/ 내 문서가 10개 이상이고 인덱스 없음 | docs/INDEX.md 또는 분류 체계 제안 |
| 동일 주제 문서가 3개 이상 분산 | 통합 문서 제안 |

> 후보 목록은 Phase 2.5에서 사용자에게 보고하고, 사용자 확정 후 Phase 3에서 생성한다.
> 새 문서 생성 시 docs-guide.md를 참조하고, 문서 등록 프로토콜을 따른다.

| 판정 | 조건 | Phase 2.5 동작 |
|------|------|---------------|
| **경미** | 기존 문서 갱신만 필요, 신규 문서 후보 없음, 구조 변경 소규모 | 보고 후 즉시 Phase 3 진행 |
| **대규모** | 아래 조건 중 1개 이상 해당 | 사용자 인터뷰 발동 |

**대규모 변화 트리거** (1개 이상 해당 시):
- 신규 문서 생성이 필요한 경우 (Phase 2 "새 문서 필요성 판단" 해당)
- 기존 문서 범위 밖의 도메인/프레임워크가 발견된 경우
- 디렉토리 구조가 대폭 변경된 경우 (엔트리포인트 이동, 레이어 추가 등)
- 사용자가 직접 방향 협의를 요청한 경우

**경미한 변화 — 즉시 진행**:

```
[프로젝트 최신화 분석 요약]

■ 변경 맥락
  최근 태스크 {N}개 완료. 주요 변화: {핵심 변화 1~3줄}

■ 분석 결과
  업데이트 필요: {N}건 ({문서별 건수})
  정합성 이슈: {N}건 ({있으면})

{N}건 업데이트를 반영합니다.
```

보고 후 Phase 3으로 바로 진행한다.

**대규모 변화 — 사용자 인터뷰**:

```
[프로젝트 최신화 분석 요약]

■ 변경 맥락
  최근 태스크 {N}개 완료. 주요 변화: {핵심 변화 1~3줄}

■ 분석 결과 요약
  업데이트 필요: {N}건 ({문서별 건수})
  신규 문서 후보: {N}건 ({후보 목록})
  정합성 이슈: {N}건 ({대표 이슈})

■ 방향 확인
  1. 전체 업데이트 (위 항목 모두 반영)
  2. 핵심만 업데이트 ({가장 중요한 N건}만)
  3. 특정 문서만 지정
  4. 기타 (직접 입력)

어떤 방향으로 정리할까요?
```

> **규칙**: 대규모 변화 시, 사용자가 방향을 확정하기 전까지 Phase 3으로 넘어가지 않는다.

### Phase 3: 변경 사항 정리 + 사용자 검토

**절대 규칙**: 자동으로 문서를 덮어쓰지 않는다. 사용자 승인 후에만 업데이트한다.

Phase 2.5에서 확정된 방향에 따라, 해당 범위의 변경 사항을 **섹션(§) 단위**로 상세 보고한다.

1. 사용자에게 섹션별 변경 내용을 보고한다:

   **개발 프로젝트 보고 형식**:
   ```
   [프로젝트 최신화 상세]

   사용자 선택 방향: {Phase 2.5에서 확정된 방향}

   ■ docs/ARCHITECTURE.md
     § 디렉토리 구조: src/services/notification/ 추가 반영 필요
     § 기술 스택 상세: React 18 → 19 버전 갱신
     § 시스템 구성: notification-service 추가 필요 (Step C에서 발견)
     § 미들웨어 체계: 변경 없음

   ■ docs/FRONTEND.md
     § 아키텍처 원칙: 신규 상태 관리 패턴 반영
     § API 연동: 새 API 클라이언트 구조 반영

   ■ docs/CONVENTIONS.md
     § 변경 없음

   ■ 새 문서 제안
     docs/BACKEND.md — BE 코드 디렉토리 발견됨 (backend/). 생성 권장.

   업데이트를 진행할까요? (§ 단위로 개별 승인/거부 가능)
   ```

   **일반/문서 프로젝트 보고 형식**:
   ```
   [프로젝트 최신화 상세]

   사용자 선택 방향: {Phase 2.5에서 확정된 방향}

   ■ docs/PROJECT.md
     § 프로젝트 개요: Phase 2 → 3 변경 반영
     § 프로젝트 문서 테이블: 미등록 문서 2건 추가

   ■ 정합성 이슈
     § docs/roadmap.md ↔ docs/PROJECT.md: Phase 정보 불일치
     § docs/meeting-notes.md 내 "v2 API" 참조 → 관련 문서 없음

   ■ 새 문서 제안
     없음

   정리를 진행할까요? (§ 단위로 개별 승인/거부 가능)
   ```

2. 미등록 문서 → 사용자에게 용도 인터뷰 → 등록 여부 결정
3. Phase 2.5에서 확정된 새 문서 후보가 있으면 docs-guide.md를 참조하여 생성
4. 사용자 승인 → 해당 섹션만 업데이트
5. 업데이트 시 docs-guide.md, agent-guide.md를 참조하여 구조 일관성 유지

### Phase 4: 플랫폼 파일 갱신 + 완료

**4-1. 플랫폼 파일 갱신**

부트스트래퍼가 최신인지 확인하고, 필요 시 갱신한다.

1. `CLAUDE.md`, `GEMINI.md`, `.cursorrules`의 OPAL 마커 확인
2. 마커가 없거나 구버전이면 갱신 (기존 사용자 내용 보존)
3. 변경이 없으면 스킵

**4-2. 프로젝트 메모리 갱신**

`.opal/MEMORY.md` 작업 히스토리에 opi 최신화 완료를 기록한다.

```markdown
| {N} | opi 프로젝트 최신화 | 완료 | docs/, .opal/ | YYYY-MM-DD HH:mm | YYYY-MM-DD HH:mm |
```

**4-3. tasks/ DONE.md 기록**

Phase 0에서 생성한 `tasks/{NNN}-opi-{프로젝트명}/` 폴더에 완료 기록을 추가한다.

- **TASK.md**: Phase 1 분석 결과(변경 감지 항목, 문서 상태) + 업데이트 대상 목록으로 내용을 보완하고, 상태를 `완료`로 갱신한다.
- **DONE.md**: 변경된 문서 목록 + 핵심 결정 사항

> STATE.md, PLAN.md 등 복잡한 산출물은 생략한다 (세션 복원이 필요한 장기 작업이 아님).

**4-4. 완료 보고**

```
---
opi 최신화 완료

프로젝트: {프로젝트명}

업데이트된 문서:
- {변경된 파일 목록}

새로 등록된 문서:
- {있으면 목록}

변경 없음:
- {변경 없는 파일 목록}

태스크 기록: tasks/{NNN}-opi-{프로젝트명}/
---
```
