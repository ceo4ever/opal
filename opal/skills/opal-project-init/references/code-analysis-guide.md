# 코드 심층 분석 가이드

> opi 스킬의 초기화·최신화 모드에서 공통으로 참조하는 심층 코드 분석 방법론.
> SKILL.md 본문에서 "어떻게 탐색하는가"를 분리한 단일 진실 원천(SSOT).

## 블록 1 — 심층 탐색 패턴 표

코드 디렉토리별로 아래 항목을 탐색하여 설계 사상과 HOW를 파악한다.
코드 디렉토리가 여러 개(또는 서비스가 여럿)이면 각각 적용한다.

> **[MUST] 플랫폼 독립**: 모든 탐색은 도구명이 아닌 **행위**(파일 탐색·패턴 검색)로 기술한다.
> 각 플랫폼의 에이전트가 자기 도구로 실행한다.

| 분석 대상 | 탐색 행위 | 추출 정보 | docs 슬롯 매핑 |
|----------|----------|----------|--------------|
| 엔트리포인트 | `main.*`, `index.*`, `app.*` 파일 탐색 | 앱 시작점, 초기화 흐름, 미들웨어 체인 적재 순서 | ARCHITECTURE § 데이터 흐름 |
| 베이스 클래스·상속 체계 | `Base`, `extends`, `implements`, `Abstract` 패턴 검색 + 주요 클래스 상속 관계 | 공통 패턴, 추상화 수준, 도메인 계층 정의 | ARCHITECTURE § 레이어 규칙, BACKEND § 도메인 패턴 |
| 미들웨어·인터셉터 | `middleware/`, `interceptor/`, `filter/` 디렉토리·파일 탐색 | 요청 처리 파이프라인, 횡단 관심사 적용 순서 | ARCHITECTURE § 데이터 흐름 |
| 설정 로더 | `config.*`, `settings.*`, `properties`, `yaml` 파일 탐색 | 환경 설정 구조, 프로파일, 멀티 DB 설정 | ARCHITECTURE § 기술 스택 상세 |
| 라우터·컨트롤러 | `routes/`, `controllers/`, `router.*`, `@Controller`, `@RestController` 탐색 | API 엔드포인트 구조, HTTP 메서드 패턴 | ARCHITECTURE § 시스템 구성 |
| 공유 유틸리티 | `utils/`, `shared/`, `common/`, `helpers/` 디렉토리 탐색 | 재사용 모듈, 횡단 관심사 공통 처리 | BACKEND § 도메인 패턴 |
| 레이어 경계·의존 방향 | 패키지·모듈 구조 + 각 레이어가 import하는 대상 패턴 검색 | 레이어 정의, 허용/금지 의존 방향, 인터페이스 분리 위치 | ARCHITECTURE § 레이어 규칙 및 의존 방향 |
| 트랜잭션 경계 | `@Transactional`, `transactionManager`, `TransactionalOperator` 패턴 검색 | 트랜잭션 매니저 종류·적용 범위·혼용 금지 규칙 | ARCHITECTURE § 트랜잭션·상태 전이 |
| 상태 전이·열거형 | `enum`, `sealed class`, `Status`, `State` 패턴 검색 + 사용 위치 탐색 | 도메인 상태 enum 목록, 전이 가능 경로 | ARCHITECTURE § 트랜잭션·상태 전이, BACKEND § 도메인 패턴 |
| 도메인 패턴 | 서비스 클래스·포트 인터페이스·어댑터 구현체 파일 탐색 | 아키텍처 패턴(레이어드/헥사고날/CQRS 등), 포트·어댑터 위치 | BACKEND § 도메인 패턴 |
| 새 기능 추가 경로 | 기존 도메인/API/화면 추가 커밋 또는 예제 파일 탐색 → 관련 파일 경로·어노테이션·인터페이스 파악 | 신규 도메인·API·화면 추가 시 실제 수정 파일 목록·순서 | ARCHITECTURE § 새 기능 추가 절차, BACKEND § 새 기능 추가 가이드 |

## 블록 2 — BE/FE 스택별 탐색 체크리스트

블록 1 표 완료 후, 스택 유형에 맞는 체크리스트를 추가로 적용한다.

> **[MUST] 플랫폼 독립**: 도구명·특정 CLI 명령을 기술하지 않는다. 행위로만 기술한다.

### BE 체크리스트

- [ ] **레이어·포트-어댑터 구조 확인**: 코드 디렉토리 최상위 패키지가 레이어를 반영하는지, 포트(인터페이스)와 어댑터(구현체)가 분리되었는지 확인
  - 확인 행위: 최상위 패키지 목록 탐색 → domain/application/infrastructure/external 등 레이어 분리 여부
  - 추출 정보: 레이어 정의 + 패키지 위치 + 금지 의존 방향(예: "domain에서 Spring 어노테이션 금지")
- [ ] **트랜잭션 매니저 파악**: 사용 중인 트랜잭션 매니저 이름·방식·DB 대응 관계 확인
  - 확인 행위: `@Transactional` 어노테이션 + `transactionManager` 속성값 + Config 파일에서 Bean 등록 탐색
  - 추출 정보: 매니저명-방식-DB-사용 모듈 표 (예: `| storelinkR2dbcTransactionManager | R2DBC | stl | storelink6-api |`)
- [ ] **도메인 경계 파악**: 서비스 경계(bounded context)를 확인하고 서비스 간 의존 방향 파악
  - 확인 행위: 서비스별 패키지 분리 구조 탐색 + 서비스 간 호출 패턴(직접 호출/이벤트/API) 검색
  - 추출 정보: 서비스 목록 + 경계 정의 + 허용 통신 방식
- [ ] **예외 체계 확인**: 도메인 예외 계층 + 에러 코드 패턴 파악
  - 확인 행위: `exception/`, `error/` 디렉토리 탐색 + `@ExceptionHandler`, `ControllerAdvice` 탐색
  - 추출 정보: 예외 계층 구조 + 에러 코드 enum 위치 + HTTP 상태 코드 매핑 규칙
- [ ] **새 기능 추가 경로 실증**: 기존 도메인/API 추가 예제를 따라 실제 수정 파일 목록 도출
  - 확인 행위: 가장 단순한 기존 도메인/API를 기준으로 관련 파일 경로 목록화
  - 추출 정보: "새 API 추가 시 생성·수정 파일 순서 목록" (→ ARCHITECTURE § 새 기능 추가 절차)

### FE 체크리스트

- [ ] **라우팅 구조 확인**: 라우터 파일·디렉토리 기반 라우팅(Next.js App Router/Pages Router 등) 구조 파악
  - 확인 행위: `app/`, `pages/`, `routes/` 디렉토리 탐색 + 라우터 설정 파일 탐색
  - 추출 정보: 라우팅 방식 + 레이아웃 계층 + 동적 라우트 패턴
- [ ] **상태 관리 파악**: 전역 상태·서버 상태·폼 상태 관리 도구 및 패턴 확인
  - 확인 행위: `store/`, `context/`, `hooks/` 디렉토리 탐색 + 상태 관리 라이브러리 import 패턴 검색
  - 추출 정보: 상태 관리 분류(전역/서버/폼) + 사용 라이브러리 + 패턴 (예: `useQuery`/`zustand` 분리 기준)
- [ ] **컴포넌트 분리 규칙 파악**: 페이지·레이아웃·공통 컴포넌트 분리 패턴 확인
  - 확인 행위: `components/`, `ui/`, `features/` 디렉토리 구조 탐색 + 임포트 패턴 검색
  - 추출 정보: 컴포넌트 분류 기준 + 디렉토리 규칙 + 재사용 vs 페이지 전용 구분
- [ ] **API 클라이언트 패턴 파악**: 서버 통신 방식·클라이언트 구조 확인
  - 확인 행위: `api/`, `services/`, `lib/` 디렉토리 탐색 + fetch/axios/SDK import 패턴 검색
  - 추출 정보: API 클라이언트 구조 + 에러 처리 방식 + 타입 생성 도구
- [ ] **새 기능 추가 경로 실증**: 기존 페이지/컴포넌트 추가 예제 기준 실제 수정 파일 목록 도출
  - 확인 행위: 가장 단순한 기존 화면·컴포넌트를 기준으로 관련 파일 경로 목록화
  - 추출 정보: "새 화면 추가 시 생성·수정 파일 순서 목록" (→ ARCHITECTURE § 새 기능 추가 절차)

## 블록 3 — 작성 후 코드 1:1 재대조 절차

docs를 작성한 후, 반드시 아래 표에 따라 실제 코드와 1:1 재대조한다.
이 단계는 초기화·최신화 양쪽 모두에서 필수이다.

> **목적**: HOW 섹션이 코드 근거 없이 추측으로 채워지지 않았는지 검증한다 (헌법 §4 동작 증거 — HOW도 실측 기반).

| 문서 | 비교 섹션 | 비교 대상 (실제 코드) | 비교 방법 |
|------|----------|---------------------|----------|
| ARCHITECTURE.md | 디렉토리 구조 | 레이아웃 탐색 결과 | 경로 diff |
| ARCHITECTURE.md | 기술 스택 상세 | config 파일 스택 분석 결과 | 버전/의존성 diff |
| ARCHITECTURE.md | 시스템 구성 | 엔트리포인트·미들웨어 탐색 결과 | 컴포넌트 존재 여부 diff |
| ARCHITECTURE.md | 레이어 규칙·의존 방향 | 실제 패키지 구조 + import 패턴 | 레이어 정의·금지 방향 일치 여부 |
| ARCHITECTURE.md | 트랜잭션·상태 전이 | `@Transactional` 패턴·상태 enum 탐색 결과 | 매니저·enum 목록 diff |
| ARCHITECTURE.md | 새 기능 추가 절차 | 기존 도메인/API 추가 예제 파일 목록 | 절차 단계·파일 경로 일치 여부 |
| CONVENTIONS.md | 네이밍 규칙 | 실제 파일·클래스·함수 네이밍 패턴 | 패턴 일치 여부 |
| CONVENTIONS.md | 파일 구조 | 레이아웃 탐색 디렉토리 결과 | 규칙 vs 실제 diff |
| BACKEND.md | 서버 구조 | BE 레이아웃·레이어 탐색 결과 | 레이어·모듈 diff |
| BACKEND.md | 도메인 패턴 | 베이스 클래스·포트 인터페이스·어댑터 탐색 결과 | 패턴 일치 여부 |
| FRONTEND.md | 클라이언트 구조 | FE 라우팅·컴포넌트 탐색 결과 | 라우팅·컴포넌트 diff |

재대조 결과를 **4가지로 분류**한다:

| 분류 | 의미 | 조치 |
|------|------|------|
| **일치** | 문서와 실제가 동일 | 통과 |
| **불일치** | 문서 기재 내용과 실제가 다름 | 문서 수정 |
| **문서에 없음** | 실제에는 있지만 문서에 기재되지 않은 항목 | 문서에 추가 |
| **실제에 없음** | 문서에 기재되어 있지만 실제로는 삭제/이동된 항목 | 문서에서 제거 |

> HOW 섹션(레이어 규칙·의존 방향·트랜잭션·새 기능 추가 절차 등)이 추측이나 일반론으로 채워진 경우에도 **"불일치"** 처리한다. 코드 근거 없이 작성된 HOW는 재작성한다.

## 블록 4 — 레포 구조 판별 + 자체 docs 흡수

### 4-1. 레포 구조 판별

Phase 1-1 Step A 레이아웃 탐색에서 아래 기준으로 구조를 판별한다.

| 구조 유형 | 판별 기준 (행위) | 문서 세트 분기 |
|----------|----------------|--------------|
| **단일레포·단일서비스** | 코드 디렉토리 1벌, 멀티모듈 빌드 파일(`settings.gradle.kts`, `nx.json`, `pnpm-workspace.yaml` 등) 없음 | 기존대로 단일 ARCHITECTURE/BACKEND/FRONTEND |
| **멀티레포 (우산)** | 프로젝트 루트 하위에 독립 버전관리 디렉토리(`.git`)가 N개 존재 | 레포별 문서 세트 분기 (`docs/{레포명}/` 또는 레포별 `docs/`) |
| **멀티서비스 (단일레포)** | 단일 버전관리 + 멀티모듈 빌드 파일 존재 → 빌드 모듈 목록에서 서비스 경계 식별 | 공통 ARCHITECTURE + 서비스별 `docs/services/{서비스명}/` 세트 |

#### 멀티레포 판별 행위

1. 프로젝트 루트의 depth 2~3 스캔에서 하위 버전관리 디렉토리(`.git`) 존재 여부 탐색
2. 발견 시 → 멀티레포(우산) 구조로 판정, 각 하위 레포를 독립 분석 단위로 처리
3. 미발견 시 → 단일레포로 판정, 빌드 파일 기반 멀티서비스 판별로 진행

#### 멀티서비스 판별 행위 (단일레포)

1. 빌드 파일 탐색: `settings.gradle.kts` / `nx.json` / `pnpm-workspace.yaml` / `turbo.json` 등 존재 여부 확인
2. 발견 시 → 파일 내 모듈·프로젝트 목록 탐색하여 서비스 경계 식별
   - Gradle: `include(...)` 목록에서 `application/` 계열 모듈 추출
   - Nx/pnpm workspace: `apps/` 또는 `packages/` 목록 확인
3. 서비스 수 ≥ 2이면 → 멀티서비스로 판정

**대형 임계 기준** (디스패치 분기 M-7과 연동):
- 코드 디렉토리(영역) 수 ≥ 2, **또는**
- 단일 영역이라도 빌드 모듈·하위 디렉토리가 대규모: 빌드 모듈 수 ≥ 10 (예: pointail/backend는 50+ Gradle 모듈)

> 하위호환: 단일레포·단일서비스이면 기존 단일 문서 세트 동작 유지.

### 4-2. 자체 docs 흡수

코드 디렉토리 분석 전에, 해당 코드베이스가 이미 아키텍처/도메인 문서를 보유하는지 탐색한다.

#### 탐색 대상 경로 (행위)

- `docs/architecture/`, `docs/domain/`, `docs/adr/` 디렉토리 존재 여부 탐색
- 루트 레벨 `ARCHITECTURE.md`, `ARCHITECTURE_*.md` 파일 탐색
- 루트 레벨 `ADR/`, `decisions/` 디렉토리 탐색

#### 분기 처리

```
자체 docs 탐색 결과
├─ 발견됨 (성숙 레포: ARCHITECTURE/ADR/docs/) → 정제·흡수 경로
│   1. 자체 docs 파일을 Read하여 HOW 정보 추출
│      (레이어 규칙·트랜잭션·상태 전이·도메인 패턴·새 기능 절차 우선)
│   2. docs-guide.md 템플릿 슬롯에 매핑·정제
│      (추상 서술은 제거, 코드 근거 있는 규칙만 선별)
│   3. [MUST] 출처 추적 보존: 흡수한 내용에 원본 docs 경로·섹션 기재
│      예: "출처: {레포}/docs/architecture/layer-rules.md §Domain 레이어"
│   4. 블록 3 재대조로 자체 docs가 실제 코드와 일치하는지 검증
│      (stale 문서 맹신 금지 — 헌법 §4)
└─ 빈약/없음 → 직접 생성 경로
    블록 1~2 탐색 패턴으로 코드에서 직접 분석·추출하여 생성
```
