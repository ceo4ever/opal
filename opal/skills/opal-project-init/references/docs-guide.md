# docs 문서 작성 가이드

> opi 스킬에서 프로젝트 문서를 작성할 때 참조하는 구조/내용 지침.
> 이 가이드는 템플릿이 아니다. 에이전트가 프로젝트를 분석하고 이 구조에 맞춰 직접 작성한다.

---

## docs/PROJECT.md — 프로젝트 정의 (모든 프로젝트 필수)

프로젝트의 WHAT(무엇을)과 WHY(왜)를 정의하는 단일 진실 원천(SSOT).
프로젝트 문서 테이블을 통해 모든 문서의 허브 역할을 한다.

### 구조

```markdown
# {프로젝트명}

> {프로젝트 한 줄 설명}

## 프로젝트 개요

| 항목 | 값 |
|------|-----|
| 프로젝트명 | {프로젝트명} |
| 도메인 | {도메인} |
| 현재 Phase | {현재 진행 단계} |

## 프로젝트 원칙

{이 프로젝트에서 모든 작업이 지켜야 할 핵심 원칙}
{사용자과 대화에서 도출. 3~5개 권장}

예:
- 소상공인이 5분 안에 첫 결과를 받을 수 있어야 한다
- 크롤링 실패해도 사용자 경험이 끊기면 안 된다
- 모든 컴포넌트는 프로젝트 간 재사용 가능해야 한다

## 프로젝트 기준

{품질, 우선순위, 의사결정 기준}

예:
- UX 단순성 > 기능 풍부함
- 데이터 정합성 > 처리 속도
- 코드 가독성 > 성능 최적화

## 기술 스택 (개발 프로젝트만)

| 레이어 | 기술 |
|--------|------|
| Backend | {예: FastAPI 0.115, Python 3.12} |
| Frontend | {예: Next.js 15, React 19, shadcn/ui} |
| Database | {예: PostgreSQL 16} |
| 기타 | {예: Claude API, Crawl4AI} |

## 프로젝트 설정

프로젝트별 커스텀 경로 등을 정의한다. 생략 시 기본값 적용.
에이전트(PM)가 부트스트랩에서 이 설정을 읽고 모든 작업에 적용한다.

| 항목 | 경로 | 기본값 |
|------|------|--------|
| 태스크 폴더 | {예: `work/tasks/`} | `tasks/` |

- 사용자이 별도 지정하지 않으면 이 섹션을 생략한다 (기본값 적용)
- 에이전트가 opi 인터뷰에서 "특별한 폴더 설정이 있나요?" 같이 묻지 않는다 — 사용자이 직접 요청할 때만 설정

## 프로젝트 문서

| 문서 | 설명 | 용도 | 참조 시점 |
|------|------|------|----------|
| `.opal/AGENT.md` | PM 프로필 | PM 역할 및 검토 기준 | 부트스트랩 시 자동 |
```

### 작성 규칙

- **프로젝트 개요**: 사실 기반으로 작성. 추측 금지.
- **프로젝트 원칙**: 사용자과 대화에서 명시적으로 도출된 것만. 에이전트가 임의로 추가하지 않는다.
- **프로젝트 기준**: 트레이드오프 상황에서의 판단 기준. "A > B" 형식 권장.
- **기술 스택**: 일반 프로젝트에서는 이 섹션을 생략한다.
- **프로젝트 문서 테이블**: 프로젝트 허브. 모든 등록된 문서의 레지스트리.

### 문서 등록 프로토콜

문서를 생성하는 모든 스킬(opi, otp-doc 등)은 작성 완료 후:

1. 사용자에게 확인: "이 문서를 프로젝트 문서로 등록할까요?"
2. 용도 인터뷰: "이 문서의 용도는 무엇인가요? 어떤 작업에서 참조하면 좋을까요?"
3. 사용자 승인 시 PROJECT.md 문서 테이블에 등록
4. 등록되지 않은 문서는 다른 스킬이 참조하지 않음

**참조 시점 표준값**:

| 값 | 의미 |
|---|------|
| 부트스트랩 시 자동 | 매 세션 시작 시 에이전트가 자동 Read |
| 개발 작업 시 항상 | otp 디스패치 시 항상 워커에게 전달 |
| 개발 작업 시 | otp 디스패치 시 관련 있으면 워커에게 전달 |
| BE 작업 시 | 백엔드 관련 작업에서 워커에게 전달 |
| FE 작업 시 | 프론트엔드 관련 작업에서 워커에게 전달 |
| 요청 시 | 사용자이나 스킬이 명시적으로 요청할 때만 |

## docs/ARCHITECTURE.md — 아키텍처 (개발 프로젝트)

시스템 전체 구조와 기술적 결정을 기술한다.

### 구조

```markdown
# 아키텍처

> {프로젝트명} 시스템 아키텍처

## 시스템 구성

{전체 시스템 아키텍처 — 서버, 클라이언트, DB, 외부 서비스 관계}
{다이어그램 또는 텍스트로 표현}

## 기술 스택 상세

| 레이어 | 기술 | 버전 | 선택 이유 |
|--------|------|------|----------|

## 개발 환경

| 항목 | 값 |
|------|-----|
| 서버 | http://localhost:{포트} |
| 클라이언트 | http://localhost:{포트} |
| DB | {연결 정보} |

## 디렉토리 구조

{프로젝트 전체 디렉토리 트리}
```

### 작성 규칙

- 실제 코드베이스를 분석하여 작성 (추측 금지)
- 기술 선택 이유를 명시 (나중에 왜 이걸 골랐는지 알 수 있도록)
- 신규 프로젝트는 사용자 대화 기반, 기존 프로젝트는 코드 분석 기반

## docs/CONVENTIONS.md — 코드 컨벤션 (개발 프로젝트)

코드 작성 시 따라야 할 규칙. 워커가 코드를 쓸 때 직접 참조한다.

### 구조

```markdown
# 코드 컨벤션

> {프로젝트명} 코드 작성 규칙

## 언어 규칙

{문서 언어, 코드 언어, 주석 언어}

## 네이밍 규칙

{변수, 함수, 클래스, 파일, 디렉토리 네이밍}

## 파일 구조

{디렉토리 레이아웃 규칙}

## 브랜치 전략

{브랜치 네이밍, 워크플로우}

## 커밋 규칙

{커밋 메시지 형식, 단위}
```

### 작성 규칙

- 기존 프로젝트: 코드에서 패턴을 추출하여 정리
- 신규 프로젝트: 사용자 대화 + 기술 스택 베스트 프랙티스 기반
- 구체적으로 작성 (예: "함수명은 camelCase" ✅, "적절한 네이밍" ❌)

## docs/BACKEND.md — 서버 가이드 (BE 있을 때)

백엔드 개발에 필요한 모든 정보를 하나의 문서에 통합한다.

### 구조

```markdown
# 백엔드 가이드

> {프로젝트명} 서버 개발 가이드

## 서버 구조

{디렉토리 레이아웃, 레이어 구조}

## 환경 설정

{환경 변수, 설정 파일, 시크릿 관리}

## 도메인 패턴

{Controller-Service-Repository, Agent-Tool 등 프로젝트에 맞는 패턴}

## 새 기능 추가 가이드

{새 도메인/서비스/API 추가 시 따라야 할 절차}

## 패키지 관리

{uv, pip, npm 등 프로젝트의 패키지 관리 방법}
```

### 작성 규칙

- 기존 코드 구조를 실제로 분석하여 작성
- "이 프로젝트에서 새 기능을 추가하려면?" 질문에 답할 수 있는 수준

## docs/FRONTEND.md — 클라이언트 가이드 (FE 있을 때)

프론트엔드 개발에 필요한 모든 정보를 하나의 문서에 통합한다.

### 구조

```markdown
# 프론트엔드 가이드

> {프로젝트명} 클라이언트 개발 가이드

## 클라이언트 구조

{디렉토리 레이아웃, 라우팅 구조}

## 아키텍처 원칙

{상태 관리, 컴포넌트 분리, Routing/View 분리 등}

## 환경 설정

{환경 변수, 빌드 설정}

## API 연동

{API 클라이언트, 타입 생성, 에러 처리}

## 트러블슈팅

{자주 발생하는 문제와 해결법}
```

### 작성 규칙

- BACKEND.md와 동일 원칙
- UI 프레임워크(React, Vue 등)별 베스트 프랙티스 반영
- 컴포넌트 구조가 있으면 명시
