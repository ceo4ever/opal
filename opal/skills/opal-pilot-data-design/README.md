# opal-pilot-data-design

기획서·기존 DB를 바탕으로 표준 데이터 사전 확립부터 ERD 설계, DDL 생성까지 완주하는 DB 설계 스킬. 별칭 `opdd`.

## 개요

`//opdd`를 호출하면 표준 단어사전·도메인사전·코드사전을 먼저 확정한 뒤, 그 사전을 근거로 개념·논리·물리 ERD를 순서대로 설계하고, 최종적으로 DDL/마이그레이션 스크립트까지 생성합니다. 신규 설계(백지에서 시작)와 역공학(기존 DB·ORM에서 역추적)을 모두 지원합니다.

## 언제 쓰나

- 새 서비스의 데이터 모델을 처음부터 설계할 때
- 기존 DB·ORM 코드에서 물리 스키마를 역추적해 문서화하고 싶을 때
- 표준 용어사전을 먼저 세우고 그 위에서 논리/물리 설계를 진행하고 싶을 때
- 단순히 ERD 하나만 그리는 정도가 아니라 사전→모델링→DDL까지 전체 파이프라인이 필요할 때

> 단계 스킬만 단독으로 쓰고 싶다면(예: ERD만 그리기) 이 스킬 대신 해당 단계 스킬을 직접 호출하세요.

## 사용법

```
//opdd {작업 설명}                 # 기본 — 자동 감지 트랙(신규/역공학)
//opdd --greenfield {작업 설명}    # 신규 설계 트랙 강제
//opdd --reverse {작업 설명}       # 역공학 트랙 강제
//opdd --agentic {작업 설명}       # DDL·QA 단계를 자동으로 진행
```

트랙을 명시하지 않으면, 기존 ORM 모델·DDL 스크립트·물리 DBML이 있는지 자동으로 감지해 역공학 여부를 확인받습니다. 아무 것도 없으면 신규 설계로 진행합니다.

## 파이프라인

1. **TASK** — 설계 산출물을 저장할 경로(기본: `200.설계/`)를 정하고, 기획서·기존 ERD·기존 사전·기존 ORM 코드 등 참고할 입력을 자동으로 찾아 확인합니다. 신규/역공학 트랙도 이 단계에서 확정합니다.
2. **DICT** — 표준 단어사전·도메인사전·코드사전 3종을 작성합니다. 이후 모든 모델링 단계는 이 사전에 등록된 용어만 사용합니다.
3. **MODEL** — 확정된 트랙에 따라 순서대로 ERD를 작성합니다.
   - 신규: 개념 ERD → 논리 ERD → 물리 ERD(DBML) 순서
   - 역공학: 물리 ERD(DBML)에서 시작해 논리 ERD로 역산 (개념 ERD는 만들지 않음)
4. **DDL/MIGRATION** — 확정된 물리 ERD(DBML)를 바탕으로 대상 DBMS에 맞는 DDL 스크립트와 마이그레이션을 생성합니다.
5. **QA** — 사전-모델-DDL 간 정합성(용어 일치, 엔티티 누락 여부, 명명규칙 준수 등)을 검증합니다.
6. **CLOSE** — 완료 문서를 작성하고 관련 문서를 최신화합니다.

각 단계 완료 시 결과를 확인받고, 승인 후 다음 단계로 넘어갑니다. (DICT·MODEL 확정 이후 DDL·QA 단계는 자동으로 진행됩니다.)

## 산출물

```
200.설계/                      (기본 경로 — docs/PROJECT.md에 다른 경로가 등록되어 있으면 그 경로 사용)
├── 210.사전/                  # 표준단어사전·도메인사전·코드사전 (md + 필요 시 xlsx)
├── 220.개념모델링/             # 개념 ERD (mermaid + 설명, 신규 트랙만)
├── 230.논리모델링/             # 논리 ERD (mermaid + 설명)
├── 240.물리모델링/             # 물리 ERD (DBML)
└── 250.DDL/                   # DDL 스크립트 + 마이그레이션

tasks/{번호}-{작업명}/
├── TASK.md · STATE.md · DONE.md
```

## 관련 스킬

- **op-data-dictionary / op-data-model / op-data-ddl** — 각 단계를 실제로 수행하는 단계 스킬입니다. opdd가 이들을 순서대로 디스패치합니다.
- **opal-brain (opbr)** — 프로젝트에 브레인이 설정되어 있으면, 완료 시 사전·ERD·DDL 결정이 브레인에 누적됩니다.

## FAQ

### 기존 ERD나 사전이 이미 있으면 어떻게 되나요?
있으면 자동으로 감지해 이번 설계의 베이스라인(증분 설계 기준)으로 사용합니다. 처음부터 다시 만들지 않습니다.

### 신규/역공학은 어떻게 정해지나요?
`--reverse`/`--greenfield` 플래그로 직접 지정할 수 있고, 지정하지 않으면 기존 ORM 코드·DDL·물리 DBML의 존재 여부를 자동 감지한 뒤 사용자에게 확인받아 확정합니다. 아무 근거도 없으면 신규 설계로 진행됩니다.

### 표준사전이 왜 모델링보다 먼저인가요?
논리/물리 모델링에서 사용할 속성명과 타입의 기준(SSOT)이 표준사전이기 때문입니다. 사전이 먼저 확정돼야 이후 단계의 명명이 일관됩니다.

### 대상 DBMS는 어떻게 정하나요?
TASK 단계 인터뷰에서 확정합니다(MySQL/PostgreSQL/MSSQL 등). DDL 생성 시 이 값을 기준으로 스크립트를 작성합니다.
