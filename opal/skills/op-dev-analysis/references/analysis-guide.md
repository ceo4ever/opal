# 분석 가이드 — analysis-guide.md

op-dev-analysis 스킬의 핵심 분석 프로세스를 정의한다. 기술 컨텍스트 로딩은 `tech-context-guide.md`에서 별도로 수행한다.

## 분석 프로세스

### 1단계: 기존 코드베이스 분석

TASK.md의 요구사항을 기반으로 관련 코드를 탐색하고 구조를 파악한다.

#### 1.1 파일 탐색

→ `opal/core/references/harness/analysis-core.md` §1. 지식 선조회 3단 참조.
→ 선조회 결과에 없는 신규 요소를 Glob/Grep/Read로 **보조 탐색**하는 규율은 같은 문서 §3. 델타 탐색 규율이 소유한다. §1이 금지하는 것은 선조회 없는 **직행**이며 보조 사용은 허용된다(허용 3층은 §1 말미 표 참조).

#### 1.2 패턴 파악

- 네이밍 컨벤션 (파일명, 변수명, 함수명)
- 디렉토리 구조 규약
- 에러 처리 패턴
- 로깅 패턴
- 설정 관리 방식
- 공통 유틸/헬퍼 존재 여부

#### 1.3 의존성 맵

→ `opal/core/references/harness/analysis-core.md` §6. 의존성·영향 범위 도출 참조.

#### 1.4 테스트 현황

- 테스트 디렉토리/파일 존재 여부
- 테스트 프레임워크 (jest, pytest, go test 등)
- 변경 대상 관련 기존 테스트 유무
- 테스트 커버리지 수준 (측정 가능한 경우)

### 분석 깊이 기준

→ `opal/core/references/harness/analysis-core.md` §4. 분석 깊이 기준 참조 (데이터 파이프라인 작업 추가 사항 포함).

### 2단계: 외부 API/라이브러리 조사

TASK.md에서 외부 의존성이 식별된 경우 수행한다.

#### 2.1 context7 MCP 활용

```
1. resolve-library-id: 라이브러리명으로 ID 조회
2. get-library-docs: ID로 공식 문서 조회 (topic 파라미터로 범위 한정)
```

**활용 시점**:
- 새 라이브러리/프레임워크 도입 시
- 기존 라이브러리의 특정 API 사용법 확인 시
- 버전 업그레이드에 따른 breaking change 확인 시

#### 2.2 WebSearch 활용

context7에 없는 경우 또는 최신 정보가 필요한 경우:
- 공식 문서 사이트 검색
- GitHub Issues/Discussions
- 릴리스 노트, 마이그레이션 가이드
- Stack Overflow (검증된 답변만 참조)

#### 2.3 조사 결과 기록

- 확인된 API 시그니처, 사용 예시
- 버전 호환성 매트릭스
- 알려진 이슈/제한사항
- 대안 라이브러리 (필요 시)

### 3단계: 유사 구현 패턴 참조 + 아키텍처 정합성

#### 3.1 유사 패턴 검색

프로젝트 내에서 요구사항과 유사한 기존 구현을 찾는다:
- 동일 패턴의 다른 모듈 (예: 다른 CRUD 엔드포인트)
- 비슷한 기능의 컴포넌트 (예: 다른 폼 컴포넌트)
- 참조할 수 있는 테스트 패턴

#### 3.2 아키텍처 정합성 확인

- 새 코드가 기존 아키텍처 원칙에 부합하는가
- 레이어 간 의존성 방향이 올바른가
- 관심사 분리가 유지되는가
- 기존 공통 모듈/유틸을 활용할 수 있는가

### 4단계: 영향 범위 분석

→ `opal/core/references/harness/analysis-core.md` §6. 의존성·영향 범위 도출 참조 (직접/간접 영향·체크리스트 포함).

### 5단계: 원인 분석 Root Cause (오류 수정 전용)

버그/오류 수정 태스크에서만 수행한다:

1. **증상 정리**: 에러 메시지, 재현 조건, 발생 빈도
2. **역추적**: 에러 발생 지점 → 호출 스택 → 근본 원인
3. **근본 원인 식별**: 단순 증상이 아닌 구조적 원인 파악
4. **영향 확인**: 같은 원인에 의한 다른 잠재적 문제
5. **수정 방향**: 근본 원인 해결 vs 증상 완화의 트레이드오프
