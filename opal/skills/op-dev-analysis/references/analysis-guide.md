# sdlc-v2 ANALYSIS 작성 가이드

> TASK 첫 frontmatter가 `template: sdlc-v2`일 때만 읽는다.

## 1. 질문 선택

다음 중 PLAN의 변경 대상·계약·검증 방법을 바꿀 질문만 조사한다.

- TASK `Open questions`
- AC/C 충족 여부를 좌우하는 현재 동작
- 변경 대상의 실제 소비자·호출자·파서·gate
- 틀리면 실제 연동이나 배포가 실패하는 권한·데이터·환경 가정

질문이 없으면 새 질문을 만들지 않는다. 추가 조사 불요 사실과 근거만 `Findings`에 남긴다.

## 2. 필요한 근거만 확인

- `opal/core/references/harness/analysis-core.md`의 지식 선조회와 델타 탐색 규칙을 따른다.
- PM이 주입한 프로젝트 문서와 코드 범위에서 필요한 구간만 읽는다.
- 외부 API·라이브러리 현재 사양이 설계를 바꿀 때만, PM이 주입한 runtime capability로 확인한다.
- 관련 파일 전체 목록, 기술 스택 표, 도구 추천표를 만들지 않는다.

버그 태스크는 증상 → 재현 조건 → 발생 지점과 호출자 → 근본 원인 → 같은 원인의 영향 순으로 확인한다. 결과는 별도 root-cause 절을 만들지 않고 아래 네 절에 배치한다.

## 3. 소비자와 경계 확정

- 문서 형식 변경: 생성자, 소비자, 결정론 parser/gate, 설치본 경계를 확인한다.
- 코드 변경: 공개 인터페이스, 직접 호출자, 관련 테스트, 설정·배포 경계를 확인한다.
- 데이터·외부 연동: 쓰기·발신·권한 변화와 실제 환경 검증 지점을 확인한다.
- 구현으로 내용이 달라질 프로젝트·기획·설계 문서만 변경 후보로 둔다.

## 4. 핵심 가정 확인

읽기 전용 명령, 기존 로그, fixture, 설치본 비교처럼 승인된 범위의 최소 프로브를 우선한다. 실제 발신·운영 데이터 변경·사용자 세션 조작이 필요하면 확인했다고 쓰지 말고 `Critical assumptions` 또는 `Handoff`에 남긴다.

## 5. 출력

```markdown
---
template: sdlc-v2
---
# ANALYSIS: {제목}

> 입력: [TASK.md](TASK.md) | 조사 기준: {리비전·워킹트리·확인 시점}

## Findings

| 질문 | 확인한 사실 | 근거 | 설계에 미치는 영향 |
|---|---|---|---|
| {PLAN을 바꿀 질문} | {관측 사실} | {경로:줄, 문서 절, 실행 증거} | {계약·가능성·제약} |

## Change boundary

| 경로·인터페이스 | 역할 | 변경 영향 |
|---|---|---|
| {직접 변경 후보 또는 회귀 경계} | {관련 이유} | {변경·호출자·검증 영향} |

## Critical assumptions

| 가정 | 확인 방법·결과 | 남은 한계 |
|---|---|---|
| {틀리면 실패하는 가정} | {프로브 또는 기존 증거} | {미확인 경계} |

## Handoff

- PLAN에서 결정할 것: {사실 확인 뒤 남은 구현 선택}
- 착수 차단: {없음 | 확인 전 시작할 수 없는 작업}
```

각 사실은 한 곳에만 쓴다. `Findings`는 관측, `Change boundary`는 PLAN 파일·회귀 범위, `Critical assumptions`는 검증 한계, `Handoff`는 남은 결정만 소유한다.

## 완료 검사

- 질문마다 PLAN에 미치는 영향이 있다.
- 변경 후보와 회귀 확인 대상이 구분된다.
- 미실행 프로브를 확인 사실로 쓰지 않았다.
- PM이 주입한 프로젝트 문서의 제약과 갱신 후보가 필요한 위치에 반영됐다.
- 네 절 외 구형 독립 표·기술 컨텍스트·QA 절을 만들지 않았다.
