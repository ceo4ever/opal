# sdlc-v2 PLAN 작성 가이드

> TASK 첫 frontmatter가 `template: sdlc-v2`일 때 읽는다. PLAN은 실행 순서와 구현 계약만 소유한다.

## 1. 입력 소비

TASK의 AC/C와 영향 범위, ANALYSIS의 Findings/Change boundary/Critical assumptions/Handoff를 그대로 사용한다. 요구를 다시 설명하거나 코드베이스 조사 내용을 복제하지 않는다.

## 2. 결정과 계약

`Decisions and contracts`에는 구현자가 선택할 필요가 없도록 확정된 결정, 변경 후 계약, 근거만 적는다. 폐기한 대안은 현재 구현·복구 판단에 영향을 줄 때만 한 문장으로 남긴다.

## 3. Work items

EXECUTE와 PM Gate는 이 표를 공식 입력으로 읽는다.

| 열 | 계약 |
|---|---|
| 작업 | 고유한 `W-N. 제목` |
| 담당 | 실제 실행 주체와 파일 소유권 |
| 변경 대상 | 수정·생성할 코드·문서 경로 |
| 구체적 변경 | 구현자가 추가 설계 없이 수행할 변경 |
| 선행 작업 | `없음` 또는 먼저 끝나야 할 W-ID |
| 실행 그룹 | `P1`, `P2` 순서의 실행 배치 |
| 완료 기준 연결 | 하나 이상의 `AC-N` 또는 `C-N` |

병렬 판단:

- 같은 실행 그룹의 W는 선행 관계가 없고 변경 대상이 겹치지 않아야 한다.
- 같은 파일을 바꾸는 작업은 하나의 W로 합치거나 후행 W와 다음 실행 그룹으로 분리한다.
- 더 앞선 W에 의존하면 더 뒤 실행 그룹에 둔다.
- 병렬화 이점이 없으면 불필요하게 W를 쪼개지 않는다.

문서 판단:

- ANALYSIS `Change boundary`와 `docs/PROJECT.md` 레지스트리에서 구현 결과로 내용이 달라질 문서만 변경 대상에 포함한다.
- 참조만 한 문서는 Work item으로 만들지 않는다.
- 문서 전문을 PLAN에 옮기지 않고, 경로와 바뀔 계약·절만 적는다.

## 4. Risks

`Risks` 절은 유지하되 실제로 틀리면 구현·검증·배포가 실패하는 가정만 `H-N`으로 적는다. 그런 위험이 없으면 `추가 검증이 필요한 위험 없음.` 한 문장으로 닫고 H를 만들지 않는다.

위험이 있으면 다음 열을 사용한다.

| 위험 | 깨질 수 있는 동작·계약 | 영향 | 설계 대응 |
|---|---|---|---|
| H-1. {가정} | {계약} | {사용자·운영·배포 영향} | {Work item 또는 시나리오 대응} |

## 5. Release and recovery

실제 적용에 필요한 항목만 적는다.

- 적용 순서: 실행 그룹, 통합, 설치·배포 순서
- 검증 범위: 결정론·회귀·실제 연동 구분
- 실측 경계: 시간·품질 목표가 있을 때 시작·종료·대기·재작업 기준
- 실패 시: 설치·배포 전후 복구 방법

배포나 설치가 없는 작업은 그 사실과 검증 종료 지점만 한 문장으로 적는다.

## 출력 형식

```markdown
---
template: sdlc-v2
---
# PLAN: {제목}

> 입력: [TASK.md](TASK.md), [ANALYSIS.md](ANALYSIS.md)

## Approach
{접근과 범위}

## Decisions and contracts

| 결정 | 변경 후 계약 | 선택 이유·근거 |
|---|---|---|
| {결정} | {계약} | {근거} |

## Work items

| 작업 | 담당 | 변경 대상 | 구체적 변경 | 선행 작업 | 실행 그룹 | 완료 기준 연결 |
|---|---|---|---|---|---|---|
| W-1. {작업명} | {담당} | `{경로}` | {변경} | 없음 | P1 | AC-1, C-1 |

## Risks
{H 표 또는 위험 없음 문장}

## Release and recovery
- 적용 순서: {순서}
- 검증 범위: {검증}
- 실측 경계: {해당 시}
- 실패 시: {복구}
```

## 완료 검사

- 모든 W가 변경 대상·구체적 변경·소유권·순서·AC/C 연결을 가진다.
- 같은 실행 그룹의 파일 충돌과 선행 작업 역행이 없다.
- 실제 위험만 H로 만들었고, 위험이 없으면 명시적으로 닫았다.
- 구현으로 달라질 프로젝트 문서가 빠지지 않았다.
- 단계 상태·시나리오·QA·실행 증거를 복제하지 않았다.

## Legacy 호환

legacy TASK에 기존 PLAN이 없을 때만 기존 프로젝트의 PLAN 형식을 사용한다. 기존 PLAN이 있으면 재작성하지 않으며, 신규 sdlc-v2 PLAN에 legacy 기능표·§4.2 체크리스트·QA 체크리스트를 만들지 않는다.
