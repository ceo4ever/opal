# PLAN 단계 상세 가이드 v2.0

이 가이드는 op-dev-plan 스킬에서 참조된다. Full Task와 Short Task 모두에서 동일하게 사용된다.

> **실행 컨텍스트**: 이 가이드는 워커 에이전트의 컨텍스트에서 실행된다.
> 오케스트레이터가 워커를 디스패치하면, 워커가 이 가이드를 읽고 프로세스를 따른다.
> 서브 에이전트 사용이 불가능한 플랫폼에서는 오케스트레이터가 직접 이 가이드를 따른다.

## 0단계: 기술 컨텍스트 로딩 (의무)

ANALYSIS.md가 있으면 "기술 컨텍스트" 섹션을, 없으면 TASK.md와 프로젝트 문서를 참조하여 기술 스택을 파악한다.

1. **기술 스택 확인**: 식별된 기술 스택 + 추천 스킬/MCP 목록 확인
2. **추천 스킬 Read**: 추천 스킬의 SKILL.md를 Read하여 설계 결정에 반영할 규칙/패턴을 파악
   - 예: react-best-practices → dynamic import, 워터폴 제거 패턴
   - 예: modern-python → uv, ruff, async session 패턴
   - 예: shadcn → FieldGroup/Field 폼 구조, gap 레이아웃 규칙
3. **MCP 활용**: context7로 최신 API 문서 참조, shadcn MCP로 컴포넌트 조회
4. **FE 설계 시**: ui-designer SKILL.md의 "화면 유형별 구현 패턴"과 "shadcn Critical Rules"를 참조
   - 탐색: `{프로젝트}/.opal/skills/ui-designer/SKILL.md` → `~/.opal/skills/ui-designer/SKILL.md`
5. 설계에 영향을 미친 스킬/MCP를 PLAN.md "기술 컨텍스트" 섹션에 기록

## 1단계: 기능 식별 (신설)

### F-ID 부여 규칙

TASK.md 요구사항을 기능(F-NNN) 단위로 그룹핑한다.

- **F-ID 포맷**: `F-{NNN}` (3자리 zero-padded, 예: F-001, F-002, F-010)
- **그룹핑 기준**: 논리적으로 함께 테스트 가능한 요구사항 묶음
- **R 매핑**: 각 F에 포함된 요구사항(R-번호) 명시

### 기능 목록 테이블 작성

```markdown
| F-ID | 기능명 | 포함 요구사항 | 우선순위 | 의존 |
|------|--------|-------------|---------|------|
| F-001 | {기능명} | R1 | P0 | 없음 |
| F-002 | {기능명} | R2, R3 | P0 | F-001 |
```

### 기능 의존 그래프 작성

```
F-001 ─ F-002 ─┬─ F-003
               └─ F-004
```

### Flat/Multi-Feature 모드 판정

| 조건 | 모드 | 동작 |
|------|------|------|
| 기능 >= 2개 | **Multi-Feature** | F-NNN 하위 섹션 전개 (§2·§3 반복) |
| 기능 = 1개 | **Flat** | §2·§3의 F 하위 섹션 생략, 평면 구조 |
| ANALYSIS.md에 `features[]` 명시 | Multi 강제 | 상류 결과 존중 |

**Flat 모드 PLAN.md 구조 예시**:
- §1.2 기능 목록: 단일 행 (F-001)
- §1.3 의존 그래프: 생략
- §2: 관련 파일 맵 / 현재 구현 / 영향 범위 (F 하위 구조 없이 평면)
- §3: 파일 변경 계획 / 설계 / 환경 / 배치 / 테스트 시나리오 (평면)
- §4 이후: 동일

## 2단계: 기능별 분석 (기능 루프)

각 F-NNN에 대해 아래 3개 항목을 작성한다. **Multi-Feature 모드**에서는 `### F-NNN: {기능명}` H3 헤딩 하위에 작성한다. **Flat 모드**에서는 F 헤딩 없이 직접 작성한다.

### 2.N.1 관련 파일 맵

6영역 분류 축으로 파일을 정리한다:

| 영역 | 경로 | 역할 | 변경 유형 |
|------|------|------|----------|
| FE / BE / DB / 환경 / 배치 / 공통 | 경로 | 역할 설명 | 신규 / 수정 |

> **6영역 라벨**: `FE` (프론트엔드) / `BE` (백엔드) / `DB` (데이터베이스) / `환경` (설정·패키지) / `배치` (배치·크론·마이그레이션) / `공통` (FE/BE 공유)
>
> 프레임워크 문서·스킬 태스크에서는: **스킬 / 가이드 / 오케스트레이터 / 에이전트 / 문서 / 환경 / 배치** 축 사용.

### 2.N.2 현재 구현

ANALYSIS.md 존재 여부에 따라 분석 깊이를 조절한다:

**ANALYSIS.md 있음**: ANALYSIS.md의 해당 기능 분석 결과를 참조하여 간략 작성.

**ANALYSIS.md 없음**: 직접 코드 분석 수행 (Full ANALYSIS 수준):
- Glob/Grep/Read로 관련 코드를 실제로 읽는다 (추측 금지)
- 기존 코드 구조, 핵심 로직 흐름 파악
- 관련 함수/클래스 시그니처와 역할
- 외부 라이브러리/API 호출 방식
- 영향 범위 (호출자/피호출자 의존 관계)
- 공유 데이터 구조/상태 영향
- 관련 테스트 파일

### 2.N.3 영향 범위

- 변경 대상을 호출하는 코드 (상위 의존)
- 변경 대상이 호출하는 코드 (하위 의존)
- 공유 데이터 구조나 상태에 미치는 영향
- 관련 테스트 파일

## 3단계: 기능별 설계 (기능 루프)

각 F-NNN에 대해 아래 5개 항목을 작성한다. Multi-Feature 모드에서는 `### F-NNN: {기능명}` H3 헤딩 하위에 작성.

### 3.N.1 파일 변경 계획 (신규/수정, 6영역)

```markdown
**신규 생성**
| # | 경로 | 영역 | 역할 | 근거 |
|---|------|------|------|------|

**수정**
| # | 경로 | 영역 | 변경 내용 요약 | 근거 |
|---|------|------|--------------|------|
```

> 근거: `(→ D-N §N)` 단축 인용 또는 `` `경로:줄번호` `` 또는 `-`. 포맷 규정: `opal/core/references/harness/citation-rules.md` §2·§3.2.

### 3.N.2 API·데이터 모델·화면 설계

각 설계 결정(클래스 구조, 함수 시그니처, 데이터 모델, API) 뒤에 인라인 인용 기재.
- 로컬 문서: `(→ D-N §N)` 단축 또는 `` `경로 §N` ``
- 소스 코드: `` `경로:줄번호` ``
- 외부 사이트: `[사이트명](URL)`
- 필수 제약: `[MUST]` 포맷 (citation-rules.md §2.4)
- 포맷 규정: `opal/core/references/harness/citation-rules.md §2`

각 파일의 핵심 구현 내용을 명세한다. 전체 코드를 쓰는 것이 아니라, **클래스/함수 시그니처와 핵심 로직**을 정의한다.

작성해야 할 내용:
- **클래스 구조**: 상속 관계, 주요 메서드
- **함수 시그니처**: 파라미터, 반환 타입, 역할 설명
- **데이터 모델**: 모델/DTO의 필드 목록과 타입
- **API 설계**: 엔드포인트, 요청/응답 스키마

**FE 화면 설계** (ui-designer plan-driven 모드 입력 포맷):

FE 화면이 있으면 아래 서브섹션 포맷으로 기재한다. 이 포맷이 op-dev-execute가 ui-designer plan-driven 모드에 전달하는 계약이다.

```markdown
##### 화면: {화면명}
- **ID**: FE-{N}
- **유형**: {dashboard | crud | form | auth | detail | settings | report | monitor}
- **action**: {new | modify}
- **경로**: {route}
- **파일**: {파일 경로 목록}
- **shadcn 컴포넌트**: {컴포넌트 목록}
- **UI 작업**: {설명 + 생성/수정 컴포넌트}
- **API 연동**: {엔드포인트 + 설명}
```

### 3.N.3 환경 변경

추가 패키지, 환경 설정 변경 사항. 없으면 "해당 없음".

### 3.N.4 배치/마이그레이션

배치 작업, DB 마이그레이션, 크론 작업. 없으면 "해당 없음".

### 3.N.5 테스트 시나리오 (AC ↔ TS 매핑)

```markdown
| TS-ID | AC 매핑 | 유형 | 기대 결과 |
|-------|---------|------|----------|
| TS-001 | R1 AC | 산출물 검사 / 기능 테스트 | {구체적 기대 결과} |
```

- **TS-ID**: `TS-{NNN}` 형식, 태스크 내 전역 고유
- **유형**: 산출물 검사 / 기능 테스트 / 통합 테스트 / 보안 테스트 / 회귀 테스트

## 4단계: 통합 실행 계획 (기능 의존 기반)

### 4.1 Phase 그룹핑

기능 의존 그래프(§1.3)를 기반으로 Phase를 구성한다:

```markdown
| Phase | 기능 | Step | agent | 실행 | 비고 |
|-------|------|------|-------|------|------|
| 1 | F-001 | 1, 2 | opal-be-agent | 병렬 가능 | 독립 파일 |
| 2 | F-002 | 3 | opal-fe-agent | 순차 | F-001 완료 후 |
```

### 4.2 실행 체크리스트 (기능-Step 매핑)

각 Step에 소속 F-ID를 필수 명시한다.

**분해 규칙**:
- 논리적 단위 = 1 Step (1파일 = 1 Step이 기본, 관련 파일이 묶이면 같이 처리)
- 독립 테스트 가능: 각 Step은 독립적으로 검증 가능해야 한다
- 의존성 순서: 하위 레이어 먼저
- 완료 기준 명확: 끝났는지 모호하지 않게

**Step 형식**:

```markdown
#### Step N: {작업 제목}
- [ ] 완료
- **소속 기능**: F-NNN
- **영역**: {FE / BE / DB / 환경 / 배치 / 공통 / 문서}
- **agent**: {에이전트명}
- **파일**: {대상 파일 경로}
- **작업 내용**: {구체적 구현 내용}
- **완료 기준**: {검증 가능한 완료 조건}
- **테스트**: {TS-ID 또는 검증 방법}
- **실행 방법**: {direct / sub-agent}
- **의존**: {선행 Step 번호 또는 "없음"}
```

**실행 방법 규칙**:
- `direct` — 메인 에이전트가 직접 실행 (단순 모드 기본값)
- `sub-agent` — 복잡 모드에서 워커 내부 서브 에이전트에 위임

**Short Task**: 5개 이하 Step 권장. 초과 시 Full Task 에스컬레이션 고려.

### agent 필드 배정 규칙

PM이 디스패치 시 전문 에이전트 매핑 테이블(agents.md)을 주입하면, 이를 참조하여 각 Step의 영역에 맞는 agent를 배정한다. 매핑 테이블이 없으면 agent 필드를 생략한다 (폴백: PM이 직접 판단).

| 영역 | 기본 agent | 비고 |
|------|-----------|------|
| FE | opal-fe-agent | 프론트엔드 전문 |
| BE | opal-be-agent | 백엔드 전문 |
| DB | opal-db-agent | DB 모델 설계+구현 전문 |
| 환경 | opal-task-agent | 범용 |
| 배치 | opal-task-agent | 범용 |
| 공통 | opal-task-agent | 범용 (PM이 영향 범위에 따라 오버라이드 가능) |
| 문서 | PM 직접 | docs/ 갱신 Step |

### docs/ 갱신 Step 자동 생성 규칙

코드 변경이 docs/ 문서 내용에 영향을 미치는 경우, 실행 체크리스트에 docs/ 갱신 Step을 자동으로 추가한다.

- **영역**: 문서
- **agent**: PM 직접
- **의존**: 해당 코드 변경 Step 완료 후

갱신 대상 판단 기준:
| 코드 변경 | 갱신 대상 docs/ |
|----------|----------------|
| 새 API 엔드포인트 추가 | BACKEND.md |
| 새 컴포넌트/페이지 추가 | FRONTEND.md |
| 시스템 구조 변경 | ARCHITECTURE.md |
| 새 패턴/규칙 도입 | CONVENTIONS.md |

### 4.3 병렬/순차 판별 근거

```markdown
| 관계 | 근거 |
|------|------|
| Step 1 → Step 2 | 동일 파일 순차 수정 |
| Step 3 ∥ Step 4 | 독립 파일, 독립 기능 |
```

## 5단계: 복잡도 판별

실행 체크리스트 작성 완료 후, 아래 기준으로 실행 모드를 결정한다:

| 기준 | 단순 모드 | 복잡 모드 |
|------|----------|----------|
| Step 수 | 5개 이하 | 6개 이상 |
| 변경 파일 수 | 3개 이하 | 4개 이상 |
| 모듈 범위 | 단일 모듈 | 다중 모듈/레이어 |
| 작업 유형 | 오류 수정, 단순 기능 수정 | 신규 개발, 대규모 개선 |
| 외부 의존성 | 없음 | 새 API, 새 패키지, 새 도구 필요 |

**하나라도 "복잡 모드" 기준에 해당하면 복잡 모드를 적용한다.**

- 단순 모드: 모든 Step의 실행 방법을 `direct`로 설정. 실행 아키텍처 섹션 생략.
- 복잡 모드: 실행 아키텍처 섹션(§7)을 포함.

## 6단계: 실행 아키텍처 (복잡 모드 전용)

복잡 모드로 판정된 경우에만 이 섹션을 PLAN.md §7에 포함한다.

### C-1. 에이전트 토폴로지

Step 간 의존성 DAG를 구성하고, 에이전트를 그룹핑한다:

**그룹핑 우선순위**:
1. **파일 충돌 방지**: 동일 파일을 수정하는 Step은 반드시 같은 에이전트에 배치
2. **모듈 응집도**: 동일 모듈/레이어에 속하는 Step을 같은 에이전트에 그룹핑
3. **병렬 극대화**: 독립적인 모듈을 별도 에이전트로 분리

**배치(Batch) 구성**:
- Batch 1: 의존성 없는 에이전트들 (병렬 실행)
- Batch 2: Batch 1 완료 후 실행 가능한 에이전트들
- Batch N: 최종 통합/테스트 에이전트

### C-2. 스킬 요구사항

각 에이전트의 작업에 필요한 스킬을 매칭한다:
- 기존 스킬 매칭 (탐색 경로: 프로젝트 → ~/.opal/skills/)
- 갭 판별: 3개 이상 Step에서 동일 패턴 → 스킬 후보, 1~2개 → 인라인 지침

### C-3. 도구 요구사항

CLI, MCP, 패키지 설치/설정 필요 사항을 정리한다.

### C-4. 테스트 전략

op-dev-test-agent 에이전트의 실행 계획을 정리한다:
- 기능 테스트: 테스트 파일 경로, 실행 명령어, 기대 결과
- 회귀 테스트: 기존 테스트 스위트 실행 명령어
- 코드 품질: 린트/타입 체크/포맷 명령어
- 보안: 하드코딩 시크릿 스캔, .gitignore 확인

## PLAN.md 파싱 규칙 (후속 소비자용)

op-dev-execute, ui-designer, op-dev-qa가 PLAN.md에서 기능·설계·테스트 정보를 추출할 때 사용하는 형식 계약.

| 관련 파일 맵 컬럼 | `영역 \| 경로 \| 역할 \| 변경유형` | §2.N.1 하위 테이블 |
| 테스트 시나리오 컬럼 | `TS-ID \| AC 매핑 \| 유형 \| 기대결과` | §3.N.5 하위 테이블 |

| QA 매트릭스 | `F-ID \| QA 항목 \| TS-ID \| Pass 조건` | §5.1 하위 테이블 |

## QA 체크리스트 작성 가이드

### 5.1 기능-QA 매트릭스 (Multi-Feature 모드 필수)

Multi-Feature 모드에서는 §5.1에 기능-QA 매트릭스를 반드시 작성한다. 모든 F-NNN이 최소 1개 QA 항목으로 커버되어야 한다.

```markdown
### 5.1 기능별 QA
| F-ID | QA 항목 | TS-ID | Pass 조건 |
|------|---------|-------|----------|
| F-001 | {기능 1의 검증 항목} | TS-001 | {Pass 조건} |
| F-002 | {기능 2의 검증 항목} | TS-002 | {Pass 조건} |
```

**매핑 규칙**:
- TS-ID는 §3.N.5 테스트 시나리오의 TS-ID와 일치해야 한다
- F-NNN에 대응하는 QA 항목이 없으면 Flat 모드로 전환하거나 테스트 시나리오를 보완한다

### 5.2~5.4 공통 QA 항목

```markdown
### 5.2 회귀 테스트
- [ ] {기존 기능 비파괴 확인 항목}

### 5.3 코드/문서 품질
- [ ] 프로젝트 컨벤션 준수
- [ ] 변경이력 기록 (버전, KST 일시, 변경내용)

### 5.4 보안
- [ ] .env, 인증 파일이 .gitignore에 포함되어 있는가
- [ ] 코드에 하드코딩된 토큰/시크릿이 없는가
```
