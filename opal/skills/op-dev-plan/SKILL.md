# 구현 계획 수립 (PLAN)

## 실행 컨텍스트

이 스킬은 워커 에이전트의 컨텍스트에서 실행된다.
오케스트레이터가 워커를 디스패치하면, 워커가 이 스킬을 읽고 프로세스를 따른다.
서브 에이전트 사용이 불가능한 플랫폼에서는 오케스트레이터가 직접 이 스킬을 따른다.

---

## 페르소나

`personas/software-architect.md`를 Read하여 설계 원칙과 행동 규칙을 적용한다.

---

## 입력/출력

| 항목 | 설명 |
|------|------|
| **필수 입력** | TASK.md |
| **선택 입력** | ANALYSIS.md |
| **보장 출력** | PLAN.md (기능 중심 구조 §1~§9, 기능-QA 매트릭스 포함) |

---

## 입력 분기 — ANALYSIS.md 유무

ANALYSIS.md 존재 여부에 따라 기능별 분석(Step 4) 깊이가 조절된다:

| 조건 | 기능별 분석 방식 | 설계 집중도 |
|------|----------------|-----------|
| ANALYSIS.md **있음** | ANALYSIS.md 참조하여 F-NNN별 분석 간략 작성 | 설계/구현 계획에 집중 |
| ANALYSIS.md **없음** | F-NNN별 직접 코드 분석 (Full ANALYSIS 수준) | 코드 분석 + 설계를 통합 수행 |

ANALYSIS.md에 `features[]` 필드가 명시된 경우: **Multi-Feature 모드 강제** (상류 결과 존중).

---

## 모드 판별 — Flat vs Multi-Feature

| 조건 | 모드 | 동작 |
|------|------|------|
| 기능 >= 2개 | **Multi-Feature** | F-NNN 하위 섹션 전개 (§2·§3 반복) |
| 기능 = 1개 | **Flat** | §2·§3의 F 하위 섹션 생략, 평면 구조 |
| ANALYSIS.md에 `features[]` 명시 | Multi 강제 | 상류 결과 존중 |

## 프로세스

### Step 1: 가이드 로딩

`references/plan-guide.md`를 Read한다.

### Step 2: 기술 컨텍스트 로딩

plan-guide.md의 0단계를 따른다. 기술 스택에 따라 아래 스킬/MCP를 활용한다.

#### 활용 스킬 (기술 스택에 따라 선택적 Read)

| 기술 스택 | 스킬 | 탐색 경로 |
|----------|------|----------|
| React | `vercel-labs/react-best-practices` | `~/.opal/community-skills/vercel-labs/` |
| React | `vercel-labs/composition-patterns` | `~/.opal/community-skills/vercel-labs/` |
| Next.js | `vercel-labs/next-best-practices` | `~/.opal/community-skills/vercel-labs/` |
| shadcn/ui | `vercel-labs/shadcn` | `~/.opal/community-skills/vercel-labs/` |
| Python | `trailofbits/modern-python` | `~/.opal/community-skills/trailofbits/` |
| FE 설계 | `anthropics/frontend-design` | `~/.opal/community-skills/anthropics/` |
| FE 화면 | `ui-designer/SKILL.md` | `{프로젝트}/.opal/skills/` → `~/.opal/skills/` |

#### 활용 MCP (필요 시)

| MCP | 용도 |
|-----|------|
| context7 | 최신 라이브러리 API 문서 참조 |
| shadcn MCP | shadcn/ui 컴포넌트 조회 및 사용법 확인 |

### Step 3: 기능 식별

plan-guide.md의 1단계를 따른다.

- TASK.md 요구사항을 F-NNN 단위로 그룹핑
- F-ID 포맷: `F-{NNN}` (3자리 zero-padded, 예: F-001, F-002)
- 기능 목록 테이블 작성 (F-ID | 기능명 | 포함 요구사항 | 우선순위 | 의존)
- 기능 의존 그래프 작성 (ASCII)
- Flat/Multi-Feature 모드 판정

### Step 4: 기능별 분석 (기능 루프)

plan-guide.md의 2단계를 따른다. 각 F-NNN에 대해:

- **관련 파일 맵** (영역 | 경로 | 역할 | 변경유형) — 6영역: FE/BE/DB/환경/배치/공통
- **현재 구현** — ANALYSIS.md 유무에 따라 깊이 조절
- **영향 범위** — 직접/간접 의존 관계

**Flat 모드**: F 하위 섹션 없이 평면으로 작성.

### Step 5: 기능별 설계 (기능 루프)

plan-guide.md의 3단계를 따른다. 각 F-NNN에 대해:

- **파일 변경 계획** (신규/수정, 6영역)
- **API·데이터 모델·화면 설계** — FE 화면 설계는 §3.N.2 FE 화면 설계 서브섹션 포맷으로 작성
- **환경 변경**
- **배치/마이그레이션**
- **테스트 시나리오** (TS-ID | AC 매핑 | 유형 | 기대결과)

**Flat 모드**: F 하위 섹션 없이 평면으로 작성.

### Step 6: 통합 실행 계획

plan-guide.md의 4단계를 따른다:

- Phase 그룹핑 (기능 의존 기반)
- 실행 체크리스트 (Step별 소속 F-ID 필수 명시)
- 병렬/순차 판별 근거

### Step 7: 복잡도 판별

plan-guide.md의 "복잡도 판별" 섹션을 따라 실행 모드를 결정한다.

### Step 8: 실행 아키텍처 설계 (복잡 모드 전용)

복잡 모드로 판정된 경우, plan-guide.md의 "실행 아키텍처 (복잡 모드 전용)" 섹션을 따라 C-1~C-4를 작성한다.
단순 모드이면 이 Step을 스킵한다.

### Step 9: PLAN.md 작성

아래 기능 중심 출력 형식으로 PLAN.md를 작성한다.

### Step 10: 결과 반환

워커는 PLAN.md 경로와 요약을 오케스트레이터에 반환한다.
워커는 QA를 호출하지 않는다. 오케스트레이터가 QA 에이전트를 별도로 호출한다.

## 영역 태그 규칙

파일 맵의 "영역" 컬럼과 파일 변경 계획의 "영역" 컬럼에 사용하는 분류 축:

| 영역 | 적용 대상 |
|------|----------|
| `FE` | 프론트엔드 (컴포넌트, 페이지, 스타일링) |
| `BE` | 백엔드 (모델, 서비스, 라우터, DTO) |
| `DB` | 데이터베이스 (마이그레이션, 스키마) |
| `환경` | 환경 설정 (.env, 빌드 설정, 패키지) |
| `배치` | 배치 작업, 크론, 마이그레이션 스크립트 |
| `공통` | FE/BE 공유 (타입 정의, 설정, 공유 DTO) |

> 프레임워크 문서·스킬 태스크에서는 **스킬 / 가이드 / 오케스트레이터 / 에이전트 / 문서 / 환경 / 배치** 축을 사용한다.
> 일반 개발 태스크에서는 위 6영역(FE/BE/DB/환경/배치/공통)을 사용한다.

영역 태그는 EXECUTE에서 FE/BE 병렬 디스패치의 기반이 된다.
