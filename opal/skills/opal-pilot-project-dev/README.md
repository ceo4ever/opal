# opal-pilot-project-dev

아이디어부터 제품 완성까지 기획→설계→구현을 하나의 파이프라인으로 이어가는 프로젝트 개발 스킬. 별칭 `oppd`.

## 개요

`//oppd`를 호출하면 제품 요구사항(PRD)·기술 요구사항(TRD) 작성부터, 작업을 나눠 실행 순서를 정하는 WBS 수립, 그리고 각 작업을 실제 코드로 구현하는 단계까지 이어서 진행합니다. 기획 산출물 작성은 `opwt`에, 코드 구현은 실행 에이전트에 맡기고, 이 스킬은 전체를 조율합니다.

## 언제 쓰나

- 제품 명세(PRD·TRD) 작성부터 시작해서 실제 구현까지 한 번에 진행하고 싶을 때
- 이미 프로젝트 문서(`docs/PROJECT.md`)는 있고, 여기서부터 기획→개발까지 이어갈 때
- 여러 개의 독립적인 작업(액션)으로 나눠 순차/병렬로 진행할 규모의 개발일 때

> 목표·계약이 실행 중에 자주 바뀌는 프로젝트라면 `oppl`을, 확정된 실행 계약을 무인으로 소화하고 싶다면 `oppb`를 고려하세요.

## 사용법

```
//oppd {요청 내용}                  # 기본 — PRD/TRD 작성부터 구현까지
//oppd --wbs {요청 내용}            # PRD/TRD + WBS까지만 하고 종료 (구현 없음)
//oppd --agentic {요청 내용}        # 전 단계를 자동으로 진행 (완료 승인만 사용자가 함)
```

`docs/PROJECT.md`가 아직 없는 프로젝트에서 호출하면, 프로젝트 초기 설정을 먼저 자동으로 실행한 뒤 원래 요청으로 복귀합니다.

## 파이프라인

1. **Phase 1 (기획)** — `opwt`를 호출해 PRD·TRD를 작성합니다. 이어서 명세 완성도를 자동 검증하고, 문제가 있으면 최대 2회까지 자동으로 다듬습니다. 사용자가 확정하면 `docs/PRD.md`·`docs/TRD.md`로 승격됩니다.
2. **Phase 2 (WBS)** — PRD/TRD를 바탕으로 작업을 독립적으로 실행 가능한 "액션" 단위로 나누고 실행 순서(의존성)를 정합니다. 각 액션마다 적합한 개발 스킬(`opd`/`opds`/`opdw`)을 판단해 배정합니다. 사용자가 WBS를 확인하고 승인합니다.
3. **Phase 3 (실행)** — 확정된 WBS의 의존성 그래프에 따라 액션을 순차 또는 병렬로 자율 실행합니다. 각 액션은 설계→테스트 시나리오→구현→검증까지 자동으로 완주하며, 실패 시 원인에 따라 자체 재작업하거나 사용자에게 판단을 요청합니다.

`--wbs` 플래그를 쓰면 Phase 1~2까지만 진행하고 구현 단계(Phase 3) 없이 종료합니다.

## 산출물

```
tasks/{번호}-oppd-{프로젝트명}/
├── TASK.md · STATE.md · DONE.md
├── PRD.md · TRD.md              # 작업본 → 확정 후 docs/로 승격
├── WBS.md                       # 액션 목록·의존성·담당 스킬 (태스크 폴더 전용)
└── actions/
    ├── A01-{액션명}/            # 액션별 설계·구현·완료 기록
    └── A02-{액션명}/ ...

docs/PRD.md · docs/TRD.md         # Phase 1 확정 후 승격
```

## 관련 스킬

- **opwt (opal-pilot-write-tech)** — Phase 1의 PRD/TRD 작성을 실제로 수행합니다.
- **opd / opds / opdw** — Phase 3에서 각 액션에 배정되는 실제 구현 스킬(전체 개발/짧은 개발/와이어프레임)입니다.
- **opal-brain (opbr)** — 프로젝트에 브레인이 설정되어 있으면, 전체 완료 시 산출물이 브레인에 누적됩니다.

## FAQ

### PRD/TRD가 이미 있으면 어떻게 되나요?
`docs/PRD.md`가 이미 있으면 새로 작성하는 대신 기존 문서에 변경 내용만 델타로 병합합니다.

### 액션 실행 중 문제가 생기면 어떻게 되나요?
문제의 성격에 따라 처리됩니다. 액션 내부 설계 문제는 자체적으로 재설계해 해결하고, WBS 범위나 인터페이스에 영향을 주는 문제는 그 성격(구현 방식 조정 vs 기능 범위 변경)에 따라 자동 조정하거나 사용자에게 확인을 요청합니다. TRD/PRD 자체를 바꿔야 하는 문제는 항상 사용자에게 확인을 요청합니다.

### 여러 액션을 동시에 진행할 수 있나요?
네, 서로 의존하지 않는 액션은 격리된 작업 공간(worktree)에서 병렬로 실행한 뒤 순서대로 병합하고 통합 테스트를 수행합니다.

### `--wbs`와 `--agentic`을 같이 쓸 수 있나요?
네, `//oppd --wbs --agentic {요청}`처럼 조합할 수 있습니다.
