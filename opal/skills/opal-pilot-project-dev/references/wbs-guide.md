# WBS 수립 가이드

> opal-pilot-project-dev Phase 2에서 WBS(Work Breakdown Structure)를 수립할 때 참조하는 구조/내용 지침.
> PRD/TRD 확정 후, 프로젝트를 실행 가능한 태스크로 분할한다.

---

## 작성 전 준비

다음 문서를 반드시 Read한다:
- `docs/PRD.md` — 우선순위 매트릭스, 기능 목록
- `docs/TRD.md` — 기술 의존성, API/데이터 모델
- `docs/ARCHITECTURE.md` — 시스템 구조
- `docs/PROJECT.md` — 프로젝트 원칙, 기준

## 태스크 분할 원칙

1. **독립 실행 가능한 단위**로 분할한다 — 각 태스크가 완료되면 동작하는 결과가 있어야 함
2. **의존성 방향**: 하위 레이어 → 상위 레이어 (DB 스키마 → API → UI)
3. **병렬 가능한 태스크를 식별**한다 — 의존성이 없는 태스크는 동시 실행
4. **Must 우선순위**부터 배치한다 (PRD 우선순위 매트릭스 따름)
5. **하나의 태스크는 1~3일 분량**이 적정 (너무 크면 분할, 너무 작으면 합침)
6. **각 태스크에 적합한 otp 스킬을 판단**한다 (아래 기준)
7. **자동 테스트 가능성** — 각 태스크의 성공/실패를 lint/build/test로 기계적으로 판정할 수 있는 단위로 분할한다

## 액션(Action) 구조

분할된 태스크를 **"액션(action)"**으로 명명하고, oppd 태스크 스코프 내에서 관리한다.

### 채번 규칙

- 형식: `A{NN}-{name}` (2자리 순번 + kebab-case 이름)
- 스코프: oppd 태스크 내에서만 유효 (글로벌 채번 불필요)
- 예시: `A01-db-schema`, `A02-auth-api`, `A03-core-ui`

### 디렉토리 구조

```
tasks/{NNN}-oppd-{프로젝트명}/
├── TASK.md
├── STATE.md
├── DONE.md
└── actions/
    ├── A01-{액션명}/
    │   ├── TASK.md
    │   ├── PLAN.md
    │   ├── TEST-SCENARIO.md
    │   └── DONE.md
    ├── A02-{액션명}/
    └── ...
```

각 액션 폴더는 opd/opds가 사용하는 태스크 폴더로 직접 전달된다.

---

## 스킬 판단 기준

| 조건 | 스킬 | 근거 |
|------|------|------|
| 코드 변경 10+ 파일, 다중 모듈 연쇄 영향 | `//opd` (Full Task) | ANALYSIS + TODO 단계가 필요한 규모 |
| 코드 변경 <10 파일, 단일 모듈 | `//opds` (Short Task) | PLAN 통합 분석으로 충분 |
| 와이어프레임 + UI 구현 | `//opdw` (Wireframe) | wireframe-builder + ui-designer 활용 |
| 프로젝트 초기 구조 셋업 (보일러플레이트) | `//opds` | 단순 구조 생성 |
| DB 마이그레이션 + API + UI 통합 | `//opd` | 다중 레이어 영향 |

## Work Package 구조

액션은 **Work Package(WP) → Action 2단계 계층**으로 조직한다. WP는 마일스톤과 1:1이 아닌 **작업 분류** 단위이며, 관련된 액션들을 의미 있는 묶음으로 그룹화한다.

> **소규모 프로젝트 예외**: 액션이 5개 미만인 경우 WP 계층을 생략하고 플랫 액션 목록만 사용할 수 있다.

### WP 테이블 예시

| WP | Work Package | 설명 | 포함 액션 |
|----|-------------|------|----------|
| WP1 | 기본 구조 | 프로젝트 초기 셋업 | A01 |
| WP2 | 데이터 레이어 | DB 스키마 + 모델 + 인증 | A02, A03 |
| WP3 | API 레이어 | 핵심 API + 비즈니스 로직 | A04, A05 |
| WP4 | UI 레이어 | 메인 화면 + UX | A06 |

### WP 정의 기준

- **동일 레이어/모듈**에 속하는 액션을 같은 WP로 묶는다
- **의존성 방향**과 일치하도록 WP를 정렬한다 (WP1 → WP2 → ...)
- WP는 병렬 실행 단위가 아니다 — 병렬 그룹은 액션 테이블의 "실행" 컬럼이 담당한다

| # | WP | 액션 | 설명 | 스킬 | 의존성 | 실행 | 우선순위 | 검증 명령 | PRD 매핑 | 상태 | 완료일시 |

| ... | ... | ... | ... | ... | ... | ... | ... | ... | ... | ... | ... |

- **실행 컬럼**: `순차` = 앞 액션 완료 후 실행, `▶ 병렬 X` = 같은 그룹은 동시 실행 가능
- **검증 명령 컬럼**: 액션 완료 후 자동으로 실행되는 기계적 검증 명령. 프로젝트 기술 스택에 맞게 조정한다
- **상태 컬럼**: `미시작` / `진행 중` / `완료` / `실패` / `스킵`
- **완료일시 컬럼**: `YYYY-MM-DD HH:mm` (KST) 형식. 미완료 시 `-`

## 실행 순서

```
Phase 1: A01 (기본 구조) ─── 순차

Phase 2: ┌─ A02 (DB)     ─┐
         └─ A03 (인증)    ─┘ 병렬 A (A01 완료 후 동시 시작)

Phase 3: A04 (API) ─── 순차 (A02 완료 후)

Phase 4: ┌─ A05 (비즈니스) ─┐
         └─ A06 (UI)       ─┘ 병렬 B (A04 완료 후 동시 시작)
```

## 의존성 그래프 (DAG)

액션 목록 작성 후, 텍스트 기반 DAG를 작성하여 의존성을 시각화한다.

```
A01 (기본 구조)
 ├──▶ A02 (DB 스키마)
 │     └──▶ A04 (핵심 API)
 │           ├──▶ A05 (비즈니스 로직)
 │           └──▶ A06 (UI 메인 화면)
 └──▶ A03 (인증/인가)
```

### DAG 작성 규칙

- 루트 노드(의존성 없음)에서 시작하여 리프 노드까지 전개
- 동일 레벨에 있으면서 서로 의존하지 않는 노드 → **병렬 그룹** 후보
- 병렬 그룹은 `▶ 병렬 X`로 표기하여 실행 순서 테이블과 일치시킨다
- 순환 의존(cycle)이 발견되면 분할이 잘못된 것 → 재분할 필요

## 병렬 실행 전략

의존성 그래프에서 **동일 선행 조건**을 가진 태스크를 병렬 그룹으로 묶는다.

**병렬 판단 기준**:
- 동일한 선행 액션에 의존하면서 서로 의존하지 않는 액션 → 병렬 가능
- FE와 BE가 독립적인 경우 → 병렬 가능 (API 인터페이스만 합의되면)
- 같은 파일/모듈을 수정하는 액션 → 병렬 불가 (충돌 위험)
- **worktree 충돌 가능성**: 공유 설정 파일(package.json, tsconfig.json 등), 공통 유틸리티, 공유 타입 정의를 동시에 수정하는 액션 → 병렬 불가. 병렬 실행 시 각 액션은 별도 worktree에서 격리되므로, 머지 시점에 충돌이 발생할 수 있는 파일 변경을 사전에 식별한다

**Phase 4 실행 시 병렬 처리**:
- 병렬 그룹의 액션은 각각 별도 otp로 디스패치 (worktree 격리)
- 모든 병렬 액션 완료 후 다음 순차/병렬 그룹으로 진행
- 병렬 액션 간 충돌 발생 시 PM이 조정
- 상세 전략은 `parallel-execution-guide.md` 참조

## 태스크 분할 프로세스

1. **PRD Must 기능 나열** — 구현해야 할 기능 전체 목록
2. **TRD 기술 레이어 매핑** — 각 기능이 어떤 레이어(DB, API, UI)에 걸치는지
3. **의존성 그래프 작성** — 어떤 것이 먼저 되어야 하는지
4. **병렬 그룹 식별** — 의존성이 없는 태스크끼리 병렬 그룹으로 묶기
5. **태스크 그룹핑** — 같은 레이어/모듈에 속하는 작업을 묶기
6. **크기 조정** — 1~3일 분량 기준으로 분할/합침
7. **스킬 판단** — 각 태스크에 적합한 otp 스킬 배정
8. **마일스톤 설정** — MVP, Beta, Release 등 의미 있는 중간 지점
9. **Work Package 그룹핑** — 관련 액션을 WP로 묶기 (액션 5개 이상인 경우)

## PM 검수 체크리스트

WBS 작성 후 사용자에게 넘기기 전, 아래를 1:1 대조한다:

- [ ] PRD의 모든 Must 기능이 태스크로 분할되었는가
- [ ] PRD의 Should 기능이 태스크에 포함되거나 "향후" 명시되었는가
- [ ] 의존성 순서가 올바른가 (하위 레이어 먼저)
- [ ] 병렬 가능한 태스크가 식별되고 그룹핑되었는가
- [ ] 병렬 태스크 간 파일/모듈 충돌이 없는가
- [ ] 각 태스크의 스킬 판단이 적절한가
- [ ] 태스크 크기가 적정한가 (1~3일 분량)
- [ ] 마일스톤이 현실적이고 의미 있는가
- [ ] 모든 태스크에 PRD 기능 매핑(F-XXX)이 있는가
- [ ] 리스크가 식별되었는가
- [ ] 각 액션에 기계적 검증 가능한 완료 기준(검증 명령)이 있는가
- [ ] 액션 테이블에 `WP`, `상태`, `완료일시` 컬럼이 포함되어 있는가
- [ ] Work Package 계층이 정의되어 있는가 (액션 5개 이상인 경우)
