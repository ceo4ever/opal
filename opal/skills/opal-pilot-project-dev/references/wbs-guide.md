# WBS 수립 가이드

> opal-pilot-project-dev Phase 2에서 WBS(Work Breakdown Structure)를 수립할 때 참조하는 구조/내용 지침.
> PRD/TRD 확정 후, 프로젝트를 실행 가능한 태스크로 분할한다.

---

## 작성 전 준비

다음 문서를 반드시 Read한다:
- `docs/PRD.md` — 우선순위 매트릭스, 기능 목록
- `docs/TRD.md` — 기술 의존성, API/데이터 모델
- `docs/ARCHITECTURE.md` — 시스템 구조
- `docs/PROJECT.md` — 프로젝트 원칙, 기준

## 태스크 분할 원칙

1. **독립 실행 가능한 단위**로 분할한다 — 각 태스크가 완료되면 동작하는 결과가 있어야 함
2. **의존성 방향**: 하위 레이어 → 상위 레이어 (DB 스키마 → API → UI)
3. **병렬은 세분화의 산출**이다 — 단일 책임으로 잘게 나누면 충돌 표면이 줄어 자연히 병렬 가능 단위가 드러난다. 세분화↑ → 충돌↓ → 병렬↑ 인과로 속도가 따라온다
4. **Must 우선순위**부터 배치한다 (PRD 우선순위 매트릭스 따름)
5. **하나의 액션은 단일 책임 + 단일 수용 시나리오로 독립 검증 가능한 단위로 분할한다. 둘 이상의 독립 책임/수용 기준이 섞이면 재분할하고, 관찰 가능한 동작이 없는 헬퍼·타입 단독이면 소비 단위에 흡수한다.**

   **너무 큼 신호 → 재분할**:
   - ① 독립 책임이 2개 이상
   - ② 독립 수용 기준이 2개 이상
   - ③ 단일 수용 시나리오 작성 불가

   **너무 작음 신호 → 흡수**:
   - 관찰 가능한 동작이 없는 헬퍼·타입 단독 (소비하는 액션에 흡수)

6. **각 태스크에 적합한 otp 스킬을 판단**한다 (아래 기준)
7. **자동 테스트 가능성** — 각 태스크의 성공/실패를 lint/build/test로 기계적으로 판정할 수 있는 단위로 분할한다

## 수용 시나리오 용어 계층

WBS 액션을 정의할 때 다음 계층으로 완료 기준을 서술한다:

- **수용 시나리오 (상위 개념)**: 자연어 완료 기준 + 기계적 검증 명령(구체)을 포함하는 단위 검증 정의. 이것이 해당 액션의 `TEST-SCENARIO.md`(RED-first) 씨앗이 된다.
- **완료 기준 / 검증 명령 (하위)**: 수용 시나리오의 기계적 부분. 수용 시나리오 없이 단독 존재해서는 안 된다.

**[MUST] generic 명령 금지**: `npm run lint && npm test` 같은 포괄 명령은 수용 시나리오로 허용하지 않는다. 액션별 구체 명령(대상 파일/모듈/엔드포인트 특정)을 필수 기재한다.

## 액션(Action) 구조

분할된 태스크를 **"액션(action)"**으로 명명하고, oppd 태스크 스코프 내에서 관리한다.

### 액션 타입

액션은 다음 세 가지 타입 중 하나를 가진다:

| 타입 | 정의 | 작성 규칙 |
|------|------|----------|
| BE | 백엔드 레이어(모델·API·서비스·연동·인증) 구현 | BE 원자 단위 1종 = 1 액션 |
| FE | 프론트엔드 레이어(컴포넌트·화면 모듈) 구현 | FE 3계층 기준 1단위 = 1 액션 |
| 통합(integration) | 병렬군 머지 후 "합쳐서 E2E 통과"를 책임지는 별도 테스트된 액션 | 병렬 그룹마다 1개 필수. 통합 액션은 별도 채번 대상이며, 병렬은 실행 방식이다 |

**통합 액션 작성 규칙**:
- **언제 두는가**: 병렬 그룹(BE 병렬 또는 BE/FE 병렬)이 완료될 때마다 1개 통합 액션을 후속 배치
- **통합 수용 시나리오**: 머지된 결과의 E2E/계약 통과를 검증하는 구체 명령을 필수 기재

### 채번 규칙

- 형식: `A{NN}-{name}` (2자리 순번 + kebab-case 이름)
- 스코프: oppd 태스크 내에서만 유효 (글로벌 채번 불필요)
- 예시: `A01-db-schema`, `A02-auth-api`, `A03-core-ui`

### 디렉토리 구조

```
tasks/{NNN}-oppd-{프로젝트명}/
├── TASK.md
├── STATE.md
├── DONE.md
└── actions/
    ├── A01-{액션명}/
    │   ├── TASK.md
    │   ├── PLAN.md
    │   ├── TEST-SCENARIO.md
    │   └── DONE.md
    ├── A02-{액션명}/
    └── ...
```

각 액션 폴더는 opd/opds가 사용하는 태스크 폴더로 직접 전달된다.

## 스킬 판단 기준

| 조건 | 스킬 | 근거 |
|------|------|------|
| 코드 변경 10+ 파일, 다중 모듈 연쇄 영향 | `//opd` (Full Task) | ANALYSIS + TODO 단계가 필요한 규모 |
| 코드 변경 <10 파일, 단일 모듈 | `//opds` (Short Task) | PLAN 통합 분석으로 충분 |
| 와이어프레임 + UI 구현 | `//opdw` (Wireframe) | wireframe-builder + ui-designer 활용 |
| 프로젝트 초기 구조 셋업 (보일러플레이트) | `//opds` | 단순 구조 생성 |
| DB 마이그레이션 + API + UI 통합 | `//opd` | 다중 레이어 영향 |

## Work Package 구조

액션은 **Work Package(WP) → Action 2단계 계층**으로 조직한다. WP는 마일스톤과 1:1이 아닌 **작업 분류** 단위이며, 관련된 액션들을 의미 있는 묶음으로 그룹화한다.

> **소규모 프로젝트 예외**: 액션이 5개 미만인 경우 WP 계층을 생략하고 플랫 액션 목록만 사용할 수 있다.

### WP 테이블 예시

| WP | Work Package | 설명 | 포함 액션 |
|----|-------------|------|----------|
| WP1 | 기본 구조 | 프로젝트 초기 셋업 | A01 |
| WP2 | 데이터 레이어 | DB 스키마 + 모델 + 인증 | A02, A03 |
| WP3 | API 레이어 | 핵심 API + 비즈니스 로직 | A04, A05 |
| WP4 | UI 레이어 | 메인 화면 + UX | A06 |

### WP 정의 기준

- **동일 레이어/모듈**에 속하는 액션을 같은 WP로 묶는다
- **의존성 방향**과 일치하도록 WP를 정렬한다 (WP1 → WP2 → ...)
- WP는 병렬 실행 단위가 아니다 — 병렬 그룹은 액션 테이블의 "실행" 컬럼이 담당한다

## 실행 순서

```
Phase 1: A01 (기본 구조) ─── 순차

Phase 2: ┌─ A02 (DB)     ─┐
         └─ A03 (인증)    ─┘ 병렬 A (A01 완료 후 동시 시작)

Phase 3: A04 (API) ─── 순차 (A02 완료 후)

Phase 4: ┌─ A05 (비즈니스) ─┐
         └─ A06 (UI)       ─┘ 병렬 B (A04 완료 후 동시 시작)
```

## 의존성 그래프 (DAG)

액션 목록 작성 후, 텍스트 기반 DAG를 작성하여 의존성을 시각화한다.

```
A01 (기본 구조)
 ├──▶ A02 (DB 스키마)
 │     └──▶ A04 (핵심 API)
 │           ├──▶ A05 (비즈니스 로직)
 │           └──▶ A06 (UI 메인 화면)
 └──▶ A03 (인증/인가)
```

### DAG 작성 규칙

- 루트 노드(의존성 없음)에서 시작하여 리프 노드까지 전개
- 동일 레벨에 있으면서 서로 의존하지 않는 노드 → **병렬 그룹** 후보
- 병렬 그룹은 `▶ 병렬 X`로 표기하여 실행 순서 테이블과 일치시킨다
- 순환 의존(cycle)이 발견되면 분할이 잘못된 것 → 재분할 필요

## 병렬 실행 전략

병렬은 1차 목표가 아니라 **세분화의 파생 효과**다. 단일 책임으로 잘게 나눌수록 파일·모듈 겹침이 줄어(충돌↓) 동시 실행 가능 액션이 늘어난다. **세분화↑ → 충돌↓ → 병렬↑**

의존성 그래프에서 **동일 선행 조건**을 가진 태스크를 병렬 그룹으로 묶는다.

**병렬 판단 기준**:
- 동일한 선행 액션에 의존하면서 서로 의존하지 않는 액션 → 병렬 가능
- FE와 BE가 독립적인 경우 → 병렬 가능 (API 계약이 합의된 경우. 미합의 시 계약 정의 액션 선행)
- 같은 파일/모듈을 수정하는 액션 → 병렬 불가 (충돌 위험)
- **worktree 충돌 가능성**: 공유 설정 파일(package.json, tsconfig.json 등), 공통 유틸리티, 공유 타입 정의를 동시에 수정하는 액션 → 병렬 불가. 병렬 실행 시 각 액션은 별도 worktree에서 격리되므로, 머지 시점에 충돌이 발생할 수 있는 파일 변경을 사전에 식별한다

**Phase 4 실행 시 병렬 처리**:
- 병렬 그룹의 액션은 각각 별도 otp로 디스패치 (worktree 격리)
- 모든 병렬 액션 완료 후 다음 순차/병렬 그룹으로 진행
- 병렬 액션 간 충돌 발생 시 PM이 조정
- 상세 전략은 `parallel-execution-guide.md` 참조

## 태스크 분할 프로세스

1. **PRD Must 기능 나열** — 구현해야 할 기능 전체 목록
2. **TRD 기술 레이어 매핑** — 각 기능이 어떤 레이어(DB, API, UI)에 걸치는지
3. **의존성 그래프 작성** — 어떤 것이 먼저 되어야 하는지
4. **병렬 그룹 식별** — 의존성이 없는 태스크끼리 병렬 그룹으로 묶기
5. **태스크 그룹핑** — 같은 레이어/모듈에 속하는 작업을 묶기
6. **크기 조정** — 단일 책임/수용 시나리오 기준으로 재분할/흡수 (너무 큼: 독립 책임 2+ 또는 독립 수용 기준 2+ → 재분할, 너무 작음: 관찰 동작 없는 헬퍼·타입 단독 → 흡수)
7. **스킬 판단** — 각 태스크에 적합한 otp 스킬 배정
8. **마일스톤 설정** — MVP, Beta, Release 등 의미 있는 중간 지점
9. **Work Package 그룹핑** — 관련 액션을 WP로 묶기 (액션 5개 이상인 경우)

## PM 검수 체크리스트

WBS 작성 후 사용자에게 넘기기 전, 아래를 1:1 대조한다:

- [ ] PRD의 모든 Must 기능이 태스크로 분할되었는가
- [ ] PRD의 Should 기능이 태스크에 포함되거나 "향후" 명시되었는가
- [ ] 의존성 순서가 올바른가 (하위 레이어 먼저)
- [ ] 병렬 가능한 태스크가 식별되고 그룹핑되었는가
- [ ] 병렬 태스크 간 파일/모듈 충돌이 없는가
- [ ] 각 태스크의 스킬 판단이 적절한가
- [ ] 각 액션이 **단일 책임**인가 (화면 1개 / 엔드포인트 1개 / 서비스 1개 수준)
- [ ] 각 액션에 **구체 수용 시나리오**가 있고 generic 검증 명령(예: `npm run lint && npm test`)이 아닌가
- [ ] 병렬 그룹마다 **통합 액션**이 존재하는가
- [ ] **너무 큼/작음** 판정 신호에 걸리는 액션이 없는가 (독립 책임 2+ 또는 독립 수용 기준 2+ → 재분할, 헬퍼·타입 단독 → 흡수)
- [ ] 마일스톤이 현실적이고 의미 있는가
- [ ] 모든 태스크에 PRD 기능 매핑(F-XXX)이 있는가
- [ ] 리스크가 식별되었는가
- [ ] 각 액션에 수용 시나리오(자연어 완료 기준 + 구체 검증 명령)가 있는가
- [ ] 액션 테이블에 `WP`, `타입`, `상태`, `완료일시` 컬럼이 포함되어 있는가
- [ ] Work Package 계층이 정의되어 있는가 (액션 5개 이상인 경우)

## BE 액션 분할 기준

BE 액션은 아래 **원자 단위 5종** 중 하나를 책임 단위로 삼는다. 하나의 액션 = 하나의 원자 단위.

| BE 원자 단위 | 책임 | 수용 시나리오 예 | 너무 큼 신호 | 너무 작음 신호 |
|-------------|------|----------------|------------|--------------|
| 모델·마이그레이션 | 스키마/ORM 모델 정의 | 마이그레이션 적용 후 지정 테이블·제약 생성 확인, `npx prisma migrate dev --name <name>` 오류 0건 + `npm test -- --run src/**/<model>*` 통과 | 2개 이상의 독립 모델 스키마 포함 | 인덱스 1개 추가만인 경우 → 관련 모델 액션에 흡수 |
| 엔드포인트 | 라우트 + 요청/응답 계약 | 해당 엔드포인트가 계약대로 응답(상태코드·스키마), `npm test -- --run src/**/api/<endpoint>*` 통과 | 2개 이상의 독립 라우트 그룹 포함 | 관찰 동작 없는 미들웨어 헬퍼 단독 → 관련 엔드포인트 액션에 흡수 |
| 도메인 서비스 | 비즈니스 로직 단위 | 입력→출력 단위 테스트 통과, `npm test -- --run src/**/service/<name>*` 통과 | 독립 비즈니스 규칙 2개 이상 | 유틸 함수 단독(서비스 없이) → 소비 서비스 액션에 흡수 |
| 외부연동 | 외부 API/큐/메시지 어댑터 | 연동 mock/통합 테스트 통과, `npm test -- --run src/**/integration/<adapter>*` 통과 | 독립 외부 시스템 2개 이상 | 어댑터 타입 정의만 → 연동 구현 액션에 흡수 |
| 인증 | 인증/인가 | 토큰 발급·검증·권한 시나리오 통과, `npm test -- --run src/**/auth/<scenario>*` 통과 | 인증 + 별도 인가 권한 로직이 혼재 → 재분할 | 토큰 검증 헬퍼 단독 → 인증 구현 액션에 흡수 |

**공통 너무 큼 신호**: ① 독립 책임 2+ ② 독립 수용 기준 2+ ③ 단일 수용 시나리오 작성 불가 → 재분할
**공통 너무 작음 신호**: 관찰 가능한 동작이 없는 헬퍼·타입 단독 → 소비 단위에 흡수

## FE 액션 분할 기준

FE 액션은 아래 **3계층** 구조로 분할한다. 계층 간 순서를 지키고, 소규모 예외 시 T0/T1 생략 가능.

| 계층 | 단위 | 실행 | 추출/생략 기준 | 수용 시나리오 예 |
|------|------|------|--------------|----------------|
| T0 | 컴포넌트 설계(공통 컴포넌트 식별) | 선행(순차) | 화면 ≤3인 소규모 시 생략 가능 | 공통 컴포넌트 목록 + 컴포넌트 API 계약(props/emits) 문서화 완료 |
| T1 | 공통 컴포넌트 구현 (컴포넌트1 = 액션1, 병렬) | 병렬 | 기존 UI킷(shadcn 등) 우선 사용. 프로젝트 고유 컴포넌트는 2개 이상 화면에서 실사용되는 경우만 추출. 단일 화면 전용은 T2 화면 액션에 흡수 | 컴포넌트 렌더 + props 시나리오 통과, `npm test -- --run src/**/component/<name>*` 통과 |
| T2 | 화면 모듈 구현 (화면1 = 액션1, 병렬) | 병렬 | T1 컴포넌트 API 계약 합의 후 병렬 시작. 각 화면은 독립 액션 | 화면 렌더 + 인터랙션 시나리오 통과, `npm run build` 오류 0건 + `npm test -- --run src/**/screen/<name>*` 통과 |

**소규모 예외**: 화면 수 ≤3이고 공유 컴포넌트가 적은 경우 → T0/T1 생략, 평면 화면 액션(T2만) 운용.

**컴포넌트 API 계약** = T1↔T2 간 인터페이스 계약(props/emits/slots 정의). 계약 합의 완료 시 T2 병렬 시작 가능.

## BE/FE 분할 매트릭스

| 규칙 | 내용 |
|------|------|
| 레이어 경계 = 액션 경계 | BE 액션과 FE 액션을 동일 액션에 혼합하지 않는다. BE ≠ FE = 각각 별도 액션 |
| API 계약(BE) | BE 엔드포인트의 요청/응답 스키마. 액션 간 인터페이스 계약 |
| 컴포넌트 API 계약(FE) | FE 컴포넌트의 props/emits 정의. 액션 간 인터페이스 계약 |
| 병렬 조건 | API 계약 합의 완료 시 BE/FE 병렬 실행 가능 |
| 순차 조건 | API 계약 미합의 시 계약 정의 액션이 선행(순차)되어야 한다 |
| 공유 모델 선행 | 공유 타입/모델(DTO 등)은 BE/FE 모두가 의존하므로 별도 선행 액션으로 분리 |
| 통합 액션 필수 | BE/FE 병렬군 머지 후 반드시 통합 액션(integration 타입)으로 E2E 검증 ("조각은 완벽한데 합치면 깨지는 함정" 방어) |
