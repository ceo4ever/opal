# 로드맵 수립 가이드

> opal-pilot-project-dev Phase 2에서 로드맵을 수립할 때 참조하는 구조/내용 지침.
> PRD/TRD 확정 후, 프로젝트를 실행 가능한 태스크로 분할한다.

## 작성 전 준비

다음 문서를 반드시 Read한다:
- `docs/PRD.md` — 우선순위 매트릭스, 기능 목록
- `docs/TRD.md` — 기술 의존성, API/데이터 모델
- `docs/ARCHITECTURE.md` — 시스템 구조
- `docs/PROJECT.md` — 프로젝트 원칙, 기준

## 태스크 분할 원칙

1. **독립 실행 가능한 단위**로 분할한다 — 각 태스크가 완료되면 동작하는 결과가 있어야 함
2. **의존성 방향**: 하위 레이어 → 상위 레이어 (DB 스키마 → API → UI)
3. **병렬 가능한 태스크를 식별**한다 — 의존성이 없는 태스크는 동시 실행
4. **Must 우선순위**부터 배치한다 (PRD 우선순위 매트릭스 따름)
5. **하나의 태스크는 1~3일 분량**이 적정 (너무 크면 분할, 너무 작으면 합침)
6. **각 태스크에 적합한 otp 스킬을 판단**한다 (아래 기준)

---

## 스킬 판단 기준

| 조건 | 스킬 | 근거 |
|------|------|------|
| 코드 변경 10+ 파일, 다중 모듈 연쇄 영향 | `//opd` (Full Task) | ANALYSIS + TODO 단계가 필요한 규모 |
| 코드 변경 <10 파일, 단일 모듈 | `//opds` (Short Task) | PLAN 통합 분석으로 충분 |
| 와이어프레임 + UI 구현 | `//opdw` (Wireframe) | wireframe-builder + ui-designer 활용 |
| 프로젝트 초기 구조 셋업 (보일러플레이트) | `//opds` | 단순 구조 생성 |
| DB 마이그레이션 + API + UI 통합 | `//opd` | 다중 레이어 영향 |

## 로드맵 구조 (docs/ROADMAP.md)

```markdown
# ROADMAP: {프로젝트명}

> 작성일: YYYY-MM-DD | 상태: 초안 / PM 검수 완료 / 사용자 확정
> 기반: PRD vX.X, TRD vX.X

## 개요

총 {N}개 태스크, {M}개 마일스톤으로 구성.

## 마일스톤

| # | 마일스톤 | 포함 태스크 | 목표 |
|---|---------|-----------|------|
| M1 | MVP | T1~T5 | 핵심 기능 동작 |
| M2 | Beta | T6~T8 | UI 완성 + 테스트 |
| M3 | Release | T9~T10 | 배포 준비 |

## 태스크 목록

| # | 태스크 | 설명 | 스킬 | 의존성 | 실행 | 우선순위 | PRD 매핑 |
|---|--------|------|------|--------|------|---------|----------|
| T1 | 프로젝트 기본 구조 | 디렉토리, 설정, 의존성 | //opds | - | 순차 | Must | - |
| T2 | DB 스키마 + 모델 | 데이터 모델 구현 | //opds | T1 | ▶ 병렬 A | Must | F-001~003 |
| T4 | 인증/인가 | JWT + RBAC | //opds | T1 | ▶ 병렬 A | Must | F-010 |
| T3 | 핵심 API | CRUD 엔드포인트 | //opds | T2 | 순차 | Must | F-001~003 |
| T5 | 핵심 비즈니스 로직 | 도메인 서비스 | //opd | T2,T3 | ▶ 병렬 B | Must | F-004~006 |
| T6 | UI 메인 화면 | 와이어프레임 + 구현 | //opdw | T3 | ▶ 병렬 B | Must | F-001 |
| ... | ... | ... | ... | ... | ... | ... | ... |

- **실행 컬럼**: `순차` = 앞 태스크 완료 후 실행, `▶ 병렬 X` = 같은 그룹은 동시 실행 가능

## 실행 순서

```
Phase 1: T1 (기본 구조) ─── 순차

Phase 2: ┌─ T2 (DB)     ─┐
         └─ T4 (인증)    ─┘ 병렬 A (T1 완료 후 동시 시작)

Phase 3: T3 (API) ─── 순차 (T2 완료 후)

Phase 4: ┌─ T5 (비즈니스) ─┐
         └─ T6 (UI)       ─┘ 병렬 B (T3 완료 후 동시 시작)
```

## 병렬 실행 전략

의존성 그래프에서 **동일 선행 조건**을 가진 태스크를 병렬 그룹으로 묶는다.

**병렬 판단 기준**:
- 동일한 선행 태스크에 의존하면서 서로 의존하지 않는 태스크 → 병렬 가능
- FE와 BE가 독립적인 경우 → 병렬 가능 (API 인터페이스만 합의되면)
- 같은 파일/모듈을 수정하는 태스크 → 병렬 불가 (충돌 위험)

**Phase 4 실행 시 병렬 처리**:
- 병렬 그룹의 태스크는 각각 별도 otp로 디스패치
- 모든 병렬 태스크 완료 후 다음 순차/병렬 그룹으로 진행
- 병렬 태스크 간 충돌 발생 시 PM이 조정
```

## 태스크 분할 프로세스

1. **PRD Must 기능 나열** — 구현해야 할 기능 전체 목록
2. **TRD 기술 레이어 매핑** — 각 기능이 어떤 레이어(DB, API, UI)에 걸치는지
3. **의존성 그래프 작성** — 어떤 것이 먼저 되어야 하는지
4. **병렬 그룹 식별** — 의존성이 없는 태스크끼리 병렬 그룹으로 묶기
5. **태스크 그룹핑** — 같은 레이어/모듈에 속하는 작업을 묶기
6. **크기 조정** — 1~3일 분량 기준으로 분할/합침
7. **스킬 판단** — 각 태스크에 적합한 otp 스킬 배정
8. **마일스톤 설정** — MVP, Beta, Release 등 의미 있는 중간 지점

## PM 검수 체크리스트

로드맵 작성 후 사용자에게 넘기기 전, 아래를 1:1 대조한다:

- [ ] PRD의 모든 Must 기능이 태스크로 분할되었는가
- [ ] PRD의 Should 기능이 태스크에 포함되거나 "향후" 명시되었는가
- [ ] 의존성 순서가 올바른가 (하위 레이어 먼저)
- [ ] 병렬 가능한 태스크가 식별되고 그룹핑되었는가
- [ ] 병렬 태스크 간 파일/모듈 충돌이 없는가
- [ ] 각 태스크의 스킬 판단이 적절한가
- [ ] 태스크 크기가 적정한가 (1~3일 분량)
- [ ] 마일스톤이 현실적이고 의미 있는가
- [ ] 모든 태스크에 PRD 기능 매핑(F-XXX)이 있는가
- [ ] 리스크가 식별되었는가
