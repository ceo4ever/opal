# knowledge-sync — 완료 직전 8영역 판정

> 소유: `opal-self-pm/SKILL.md` §7.

**[MUST] 무근거 생략 금지** — 8영역 전부를 판정한다. "관련 없어 보임"만으로 항목을 건너뛰지 않는다. 영향이 있으면 `update`, 없으면 반드시 근거를 댄 `no-op + 근거`로 닫는다. 판정되지 않은 영역이 하나라도 남아 있으면 §8 사용자 최종 확인으로 넘어가지 않는다(`opal-self-pm/SKILL.md` §7).

## 영향 후보의 수명주기

**[MUST]** 수정 범위를 찾는 진입·질문 단계에서 작업 중인 프로젝트의 `PROJECT.md`(기본 `docs/PROJECT.md`, 프로젝트 지침이 지정한 위치 우선)를 읽고 문서 목록·구성·적용 범위·참조 시점으로 관련 지식·문서를 선별한다. 결과는 TASK.md에 `대상 / 선별 근거 / 예상 영향 / 상태(pending)`인 영향 후보 집합으로 남긴다. 별도 문서는 복잡할 때만 만들며, 문서 생성을 새 단계나 게이트로 만들지 않는다.

영향 후보는 다음 수명주기를 가진다.

1. **초기 수집** — PROJECT·brain·memory·코드맵·TASK 직접 지목·관련 코드 조사에서 후보를 한 번 수집한다.
2. **실행 중 증분** — 새 결정, 실제 변경 파일, 새 소비자·참조자, 범위 변경이 초기 후보 밖으로 나갈 때만 해당 후보와 근거를 추가한다.
3. **종료 정합** — 초기 후보와 증분을 최종 `changed_files`·결정·테스트 결과에 대조해 `update` 또는 `no-op + 근거`로 닫는다. 초기 검색을 처음부터 반복하지 않는다.

현재 세션에서 읽은 원천이 최신이면 재사용한다. PROJECT나 원천 자체가 변경됐거나, 새 범위·새 용어·새 소비자·경로 불일치가 생긴 경우에만 해당 부분을 다시 조회한다. OPAL 프레임워크 저장소의 문서 경로나 구성을 대상 프로젝트에 가정하지 않는다.

`PROJECT.md`는 관련 문서를 찾는 **라우팅 인덱스**이지 관련 문서가 하나도 빠지지 않았다는 증거가 아니다. 오래되거나 불완전한 레지스트리를 그 자체로 신뢰하면 누락을 발견할 수 없으므로, 초기 수집과 실행 중 증분에서 다음 후보 집합을 함께 관리한다.

1. TASK·계약·사용자 지시가 직접 지목한 문서와 지식 저장소를 후보에 넣는다.
2. 변경·추가·삭제 파일을 PROJECT의 프로젝트 구성과 문서 레지스트리에 대조해 영역과 owner 후보를 넣는다. 이때 선별된 레지스트리 경로·패턴이 실제로 해석되는지 확인하고, 코드 경로와 문서 폴더의 별칭이 다르면 그 매핑 근거를 기록한다. 존재하지 않는 경로나 해석 불가능한 패턴은 `no-op` 근거가 아니라 PROJECT 보정 신호다.
3. 변경하려는 규칙·인터페이스·경로·명칭의 직접 소비자와 참조자를 수정 범위 조사 때 제한적으로 역검색한다. 문서 링크, import·호출, 생성·설치 스크립트, README·PROJECT 요약이 대상이며 `rg`·기존 code-scan 등 프로젝트에 있는 조회 수단을 사용한다. 재현할 수 있도록 검색 범위·검색어와 결과를 함께 남긴다. 종료 시에는 실행 중 새로 생긴 이름·경로·소비자만 추가 검색한다.
4. 레지스트리의 용도·적용 범위·참조 시점이 맞는 기획·설계·운영·컨벤션·테스트 문서와, 선별 문서가 필수로 가리키는 종속 원문을 후보에 넣는다. 고정 파일명 목록이나 `docs/` 전량 읽기로 대체하지 않는다.
5. 종료 정합에서 각 후보를 `경로 / 선별 근거 / 이번 변경의 의미 영향 / update 또는 no-op / 확인 결과`로 TASK·DONE 또는 검증 문서에 확정한다. 경로 단위 후보가 모두 닫혀야 8영역 판정을 닫을 수 있다.
6. 관련 owner가 레지스트리에서 누락됐거나 레지스트리 설명이 현재 역할과 어긋나면 owner 문서와 PROJECT를 함께 보완한다. PROJECT 자체가 없을 때만 프로젝트 지침·요청과 실제 구성에서 최소 대상을 탐색하고 탐색 근거를 남긴다. 문서가 없다는 이유로 OPAL 전용 경로를 새로 만들지 않는다.

`PROJECT.md를 읽음`, `레지스트리에 없음`, `기존 등재로 충분함`만 적은 판정은 위 역추적 증거가 없으면 `no-op` 근거가 아니다.

의미적으로만 연결되고 텍스트·코드·레지스트리에 드러나지 않는 외부 관계까지 완전 탐지한다고 주장하지 않는다. 검색할 수 없는 외부 시스템이나 미등록 지식이 의심되면 미확인 한계로 기록하고, 완료 조건을 좌우하면 사용자에게 확인하기 전 최종 확인 단계로 넘어가지 않는다.

## 실제 동기화와 증거

- 변경 파일·확정 결정과 PROJECT 레지스트리를 대조하고 영향 있는 기획서·설계서·docs·brain을 실제 갱신한다. 필요한 현재 문서가 없으면 적절한 owner 위치에 추가하고 PROJECT 레지스트리에 연결한다. 문서 부재만으로 필요한 지식 반영을 생략하지 않는다.
- `update`는 쓰기와 확인이 끝났다는 뜻이다. 변경 경로·반영 내용·검증 결과를 `knowledge_impact`와 DONE.md에서 추적 가능하게 남긴다. 실패·미해결 사항을 `no-op`으로 바꾸지 않고 해결하거나 사용자에게 보고한다.
- 기존 brain 페이지는 `brain-tool update-page`, 새 페이지는 `add-page`로 반영한다. 현재 사실은 docs, 결정 이유는 brain, 후속 주의사항은 memory에 둔다.
- 동기화가 승인 범위 안이면 수행을 이어간다. 새로운 정책 결정이나 범위 밖 변경이면 §6으로 복귀한다.

## 규범 변경의 brain 판정

스킬·하네스·agent·참조 문서에서 규칙, gate, workflow, 수용 기준, 예외 또는 선택 원칙의 의미가 달라졌다면 재사용할 결정 이유가 생긴 것으로 우선 판정한다. brain이 초기화돼 있으면 관련 페이지를 검색한 뒤 다음 중 하나로 닫는다.

- `update`: 기존 페이지에 WHY를 보강하거나 새 페이지를 추가하고 검색·링크·lint 결과를 확인한다.
- `no-op`: (a) 문구·오탈자·링크만 고친 비의미 편집, (b) 기존 brain 페이지가 같은 WHY를 이미 담아 경로와 확인 결과를 제시함, (c) 실험 변경이 폐기·원복되어 유지할 결정이 없음 중 하나를 구체적으로 입증한다.

owner 문서가 현재 규범의 SSOT라는 사실은 brain `no-op`의 단독 근거가 될 수 없다. owner는 WHAT, brain은 WHY를 소유하므로 중복 없이 함께 갱신할 수 있다.

## 기록 형식

각 영역 판정은 아래 형식 문자열 8건을 만든 뒤 `self-pm-tool --set-field knowledge_impact '[...]'`로 **현재 스냅샷 전체를 한 번에 교체**한다(`opal-self-pm/SKILL.md` §7 명령 참조).

```
<영역명>: update - <무엇을 갱신했는지 1줄>
<영역명>: no-op - <근거 1줄>
```

예:
```
기획: no-op - 이번 변경은 기존 정책 범위 내 구현 세부이며 정책 문서 서술과 불일치 없음
brain: update - pages/concept/self-pm-tool.md 신규 등록 (add-page 완료)
```

초기 판정 뒤 사용자 피드백·범위 변경·새 증거로 하나라도 재판정하면 영향받은 항목만 append하지 않는다. 8영역을 다시 확인하고 전체 배열을 교체해 `brain: no-op`과 `brain: update`처럼 상충하는 현재 판정이 함께 남지 않게 한다. 과거 오판과 보정 과정은 run-log 사건이 보존한다.

## 중복 기록 금지

각 owner 문서·도구에 현재 사실만 반영한다. 이미 다른 영역에서 기록한 내용을 다른 영역에 다시 옮겨 적지 않는다 — 예: brain에 남긴 WHY를 프로젝트 문서에 다시 쓰지 않는다(각 owner는 제안서 §6.5의 정보 유형 표대로 단일 책임을 갖는다).
