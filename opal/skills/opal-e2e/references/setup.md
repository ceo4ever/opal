# opal-e2e — setup 참고

`//e2e setup`이 인터뷰·확인·기록 과정에서 따르는 세부 계약이다. 스키마 필드 자체는
여기 복제하지 않고 `opal/tools/test-tool/lib/e2e/environment.py`(`load`/`validate`/
`normalize`/`service_order`/`render_service`/`select_surface`)를 가리킨다.

## 인터뷰 항목

`env-inspect`(+ 후보 부족 시 PROJECT.md 폴백)로 확정하지 못한 항목은 아래를 사용자에게
직접 묻는다.

- 대상 표면: 어떤 서비스·표면(web/api/desktop)을 이번 E2E 대상으로 삼는지, 여러 후보가
  있으면 어느 것을 `surface_ref`로 쓸지.
- 로컬 기동 또는 기존 URL: 설정이 서비스를 직접 기동해야 하는지, 이미 떠 있는 URL을
  가리켜야 하는지.
- 계정·비밀 환경 변수 이름: 로그인·API 키 등 비밀이 필요하면 그 변수 이름(`from_env`).
  실제 비밀 값은 인터뷰에서도 받지 않는다.
- 데이터 준비·복원: 테스트 전후 데이터 초기화·복원이 필요한지, 필요하면 어떤 절차인지.
- 외부 연동 정책: 외부 서비스 실제 호출을 허용할지, 격리·모킹이 필요한지.

## PROJECT.md 추정 규칙

- `env-inspect` 결과의 `surface_candidates`가 없거나 특정 표면 종류가 비어 있을 때만
  이 폴백을 쓴다. 후보가 이미 충분하면 추정하지 않는다.
- 읽는 절: `docs/PROJECT.md`의 "프로젝트 구성"(요소·경로·기술 스택) 절과 그 절이 가리키는 관련 설계 문서
  (예: `docs/ARCHITECTURE.md`의 해당 컴포넌트 절)로 한정한다. 문서가 없으면 이 단계를
  건너뛰고 인터뷰로 넘어간다.
- 추정 표시: 결과에 각 추정 항목마다 "추정"이라는 표시와 근거 위치(문서 경로 + 절 제목
  또는 표 행)를 함께 남긴다. 표시 없이 추정값을 확정값처럼 제시하지 않는다.
- 추정값은 사용자 확인 전에는 `.opal/e2e/environment.json`은 물론 어떤 설정 파일에도
  쓰지 않는다. 인터뷰로 사용자가 확인한 뒤에만 초안에 반영한다.
- 사용자가 확인한 추정값이라도 그 자체로 `ready`가 되지 않는다. `env-check`가 실제
  기동·health·executor 확인을 통과해야만 `ready`다.
- `env-inspect`는 이 추정 로직을 갖지 않는다. 파일 구조만 훑는 결정론 도구로 유지되며,
  추정·해석은 이 스킬 층에서만 수행한다.

## 사용자 확인 체크리스트

`env-validate --file`이 통과한 초안을 `.opal/e2e/environment.json`에 기록하기 전에
아래를 모두 사용자에게 확인받는다.

- [ ] 대상 표면과 `surface_ref`(복수 후보가 있는 경우)가 의도한 것과 같다.
- [ ] 서비스 기동 방식(직접 기동 vs 기존 URL 가리킴)이 맞다.
- [ ] 비밀 환경 변수 이름이 실제 프로젝트 관례와 일치하고, 값 자체는 설정에 없다.
- [ ] PROJECT.md 폴백으로 추정한 항목이 있다면 그 추정이 맞는지 확인했다.
- [ ] 데이터 준비·복원 절차와 외부 연동 정책에 동의했다.

## 표면별 제약

- 데스크톱(`desktop`) 표면은 `env-check`의 준비 검증(기동·존재 확인)까지만 지원한다.
  이 스킬과 test-tool 어느 쪽도 데스크톱 표면 전용 실행기(executor)를 갖지 않는다.
