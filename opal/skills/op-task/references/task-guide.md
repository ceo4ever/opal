# TASK.md 작성 상세 가이드

> op-task가 신규 `template: sdlc-v2` TASK를 작성할 때만 읽는다.

## 필드 계약

| 절 | 소유 정보 | 작성 기준 |
|---|---|---|
| `Problem` | 현재 문제와 비용 | 사용자·운영 관점에서 왜 필요한지 적는다. 해결책을 섞지 않는다. |
| `Proposed outcome` | 완료 후 상태 | 사용자가 관찰할 결과를 적는다. 구현 목록으로 바꾸지 않는다. |
| `Affected users and systems` | 영향 경계 | 영향받는 사용자·팀·시스템과 포함/제외 범위를 짧게 적는다. |
| `Constraints` | 보존해야 할 조건 | 구현·검증에서 반드시 지킬 조건만 `C-N`으로 적는다. |
| `Acceptance criteria` | 핵심 수용 요구사항 | 완료 후 결과를 수용할지 독립적으로 결정하는 핵심 요구사항만 `AC-N`으로 적는다. 구현 방법과 검증 절차는 적지 않는다. |
| `Open questions` | 착수 전 미확정 | 목표·범위·제약·완료 기준을 바꾸는 질문만 남기며 없으면 절을 생략한다. |

## 질문 기준

다음 중 하나라도 목표·범위·제약·완료 기준을 바꾸고 현재 맥락에서 답을 추론할 수 없을 때만 질문한다.

- 포함·제외 범위가 둘 이상으로 해석된다.
- 외부 시스템·권한·데이터 정책 선택에 따라 결과가 달라진다.
- 완료 판정에 필요한 수치나 관찰 지점이 없다.

구현 라이브러리, 파일 구조, 내부 API 형태, 대안 비교는 ANALYSIS/PLAN 입력이다. TASK 질문으로 앞당기지 않는다.

## AC 작성 기준

신규 sdlc-v2는 별도 Requirements 절을 두지 않으므로 AC가 검증 가능한 핵심 요구사항 역할을
함께 맡는다. **하나의 AC는 다른 AC와 겹치지 않는 하나의 독립적인 수용 결정을 표현한다.**
관찰 지점이나 assertion 개수를 기준으로 잘게 나누지 않는다. 하나의 수용 결정을 구성하는
성공 동작과 불가분한 거부·보존 경계는 같은 AC에 함께 둘 수 있다.

AC 후보는 아래 다섯 조건을 모두 만족할 때만 채택한다.

| 조건 | 판정 질문 |
|---|---|
| 출처성 | `Proposed outcome` 또는 명시된 포함 범위에서 직접 도출되는가? |
| 필수성 | 실패하면 사용자가 결과물을 수용할 수 없는가? |
| 관찰성 | 내부 구현을 보지 않고 실제 동작이나 산출물로 Pass/Fail을 판정할 수 있는가? |
| 해법 독립성 | 특정 파일·함수·도구·명령·테스트 방법·배포 절차를 구현 해법으로 강제하지 않는가? |
| 비중복성 | 다른 AC와 구별되는 수용 결과이며, 동일 요구를 환경·검증 단계만 바꿔 반복하지 않는가? |

작성 후 각 AC를 `Proposed outcome`의 문장 또는 명시된 포함 범위에 역으로 연결한다. 연결할 수
없으면 새 요구를 임의로 추가한 것이므로 제거하거나 사용자 결정으로 돌린다. 어떤 AC를 제거해도
독립적인 수용 결과가 사라지지 않으면 그 AC는 다른 항목과 겹치므로 병합하거나 제거한다.

- `적절히`, `효율적으로`, `빠르게` 같은 표현은 판정 가능한 동작·상태·경계로 바꾼다.
- 같은 요구를 unit·integration·실측·설치본·배포본 확인처럼 검증 환경별 AC로 나누지 않는다.
- 교체형 목표는 신형 채택과 구형 비채택이 하나의 수용 결정이면 같은 AC에 함께 기술한다.
- 서로 독립적인 수용 결정에만 고유하고 연속된 `AC-N`을 부여한다.
- 문서 형식 자체보다 사용자가 얻는 결과와 회귀 방지를 우선한다.

중복 여부는 문장의 차이가 아니라 **수용 결정의 차이**로 판정한다.

| 잘못된 분리 | 올바른 처리 |
|---|---|
| 같은 동작을 단위 테스트·통합 테스트·설치본에서 확인하는 AC 3개 | 동작 요구 AC 1개 + 환경별 TEST-SCENARIO |
| 공통 helper 사용과 모든 소비자의 동일 동작을 각각 AC로 등록 | 동일 동작만 AC로 두고 helper 선택은 PLAN에 기록 |
| 신형 채택과 구형 비채택이 함께 성립해야 전환이 완료되는데 별도 AC로 분리 | 전환 완료라는 하나의 수용 결정 안에 두 관찰 경계를 함께 기록 |

### AC가 아닌 정보의 위치

| 후보 내용 | 기록 위치 |
|---|---|
| 파일·함수·공통 helper·내부 API 등 구현 방법 | PLAN의 결정·Work item |
| unit·integration·실측·설치본 재확인 등 검증 방법과 환경 | TEST-SCENARIO의 시나리오 |
| 문서 갱신·install·배포 같은 수행 절차 | PLAN Work item 또는 Release 절 |
| 프로젝트 전체에 이미 적용되는 공통 금지·품질 규칙 | 프로젝트 규칙을 참조하고 TASK에 복제하지 않음 |
| 결과와 무관한 영향 파일·소비자 목록 | `Affected users and systems` 또는 PLAN Findings |

## Constraints 작성 기준

- 어떤 구현안을 선택해도 반드시 보존해야 하는 비협상 조건만 적는다.
- 프로젝트 공통 규칙, 수행 절차, 검증 환경을 태스크별 Constraint로 복제하지 않는다.
- 태스크 고유 Constraint가 없으면 현재 태스크에 직접 적용되는 프로젝트 강제 계약을 한 항목으로 참조하되 원문을 복제하지 않는다.
- 서로 다른 항목은 고유하고 연속된 `C-N`을 쓴다.

## 출력 형식

```markdown
---
template: sdlc-v2
---
# TASK: {제목}

## Problem
{현재 문제}

## Proposed outcome
{완료 후 관찰 가능한 상태}

## Affected users and systems
{사용자·팀·시스템과 범위}

## Constraints
- C-1: {반드시 지킬 조건}

## Acceptance criteria
- AC-1: {Pass/Fail 판정 기준}

## Open questions
- {필요할 때만}
```

## 완료 검사

- 필수 다섯 절이 존재하고 비어 있지 않다.
- 모든 Constraints와 Acceptance criteria에 고유 C/AC ID가 있다.
- 각 AC가 다섯 채택 조건을 모두 만족하고 `Proposed outcome` 또는 포함 범위에 연결된다.
- 같은 요구를 구현 방법·검증 환경·단계만 달리해 여러 AC로 반복하지 않았다.
- Open questions에는 착수 판단을 바꾸는 질문만 있다.
- 기술 스택·스킬/MCP·관련 문서 카탈로그·단계 상태를 만들지 않았다.
- op-task의 계약 검사가 통과한다.
