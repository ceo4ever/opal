# TASK.md 작성 상세 가이드

> op-task가 신규 `template: sdlc-v2` TASK를 작성할 때만 읽는다.

## 필드 계약

| 절 | 소유 정보 | 작성 기준 |
|---|---|---|
| `Problem` | 현재 문제와 비용 | 사용자·운영 관점에서 왜 필요한지 적는다. 해결책을 섞지 않는다. |
| `Proposed outcome` | 완료 후 상태 | 사용자가 관찰할 결과를 적는다. 구현 목록으로 바꾸지 않는다. |
| `Affected users and systems` | 영향 경계 | 영향받는 사용자·팀·시스템과 포함/제외 범위를 짧게 적는다. |
| `Constraints` | 보존해야 할 조건 | 구현·검증에서 반드시 지킬 조건만 `C-N`으로 적는다. |
| `Acceptance criteria` | 완료 판정 | 실제 동작이나 산출물로 Pass/Fail을 판정할 기준만 `AC-N`으로 적는다. |
| `Open questions` | 착수 전 미확정 | 목표·범위·제약·완료 기준을 바꾸는 질문만 남기며 없으면 절을 생략한다. |

## 질문 기준

다음 중 하나라도 목표·범위·제약·완료 기준을 바꾸고 현재 맥락에서 답을 추론할 수 없을 때만 질문한다.

- 포함·제외 범위가 둘 이상으로 해석된다.
- 외부 시스템·권한·데이터 정책 선택에 따라 결과가 달라진다.
- 완료 판정에 필요한 수치나 관찰 지점이 없다.

구현 라이브러리, 파일 구조, 내부 API 형태, 대안 비교는 ANALYSIS/PLAN 입력이다. TASK 질문으로 앞당기지 않는다.

## AC/C 작성 기준

- 한 항목에는 하나의 판정 가능한 조건만 둔다.
- `적절히`, `효율적으로`, `빠르게` 같은 표현은 관찰값으로 바꾼다.
- 서로 다른 항목은 고유하고 연속된 `AC-N` 또는 `C-N`을 쓴다.
- 교체형 목표는 구형 잔존 0과 신형 채택을 각각 확인할 수 있어야 한다.
- 문서 형식 자체보다 사용자가 얻는 결과와 회귀 방지를 우선한다.

## 출력 형식

```markdown
---
template: sdlc-v2
---
# TASK: {제목}

## Problem
{현재 문제}

## Proposed outcome
{완료 후 관찰 가능한 상태}

## Affected users and systems
{사용자·팀·시스템과 범위}

## Constraints
- C-1: {반드시 지킬 조건}

## Acceptance criteria
- AC-1: {Pass/Fail 판정 기준}

## Open questions
- {필요할 때만}
```

## 완료 검사

- 필수 다섯 절이 존재하고 비어 있지 않다.
- 모든 Constraints와 Acceptance criteria에 고유 C/AC ID가 있다.
- Open questions에는 착수 판단을 바꾸는 질문만 있다.
- 기술 스택·스킬/MCP·관련 문서 카탈로그·단계 상태를 만들지 않았다.
- op-task의 계약 검사가 통과한다.
