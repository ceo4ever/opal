# TASK.md 작성 상세 가이드

op-task 스킬의 참조 문서. TASK.md 작성 시 구체적인 판별 기준과 규칙을 제공한다.

## 작업 유형 판별 기준

사용자 요청을 분석하여 다음 5가지 유형 중 하나를 선택한다.

| 유형 | 판별 기준 | 예시 |
|------|----------|------|
| **신규** | 기존에 없는 기능/모듈/서비스를 처음부터 만드는 경우 | "결제 모듈 만들어줘", "새 API 엔드포인트 추가" |
| **개선** | 기존 기능이 동작하지만 확장/리팩토링/성능 개선이 필요한 경우 | "검색 속도 개선", "기존 API에 필터 추가" |
| **수정** | 기존 기능의 동작 방식을 변경하는 경우 (버그 아님) | "정렬 순서를 변경", "입력 필드 유효성 검사 규칙 변경" |
| **오류** | 기존 기능이 의도대로 동작하지 않아 수정이 필요한 경우 | "로그인 시 500 에러", "데이터가 저장되지 않음" |
| **Wireframe UI** | UI 화면의 설계와 구현을 포함하는 경우 | "대시보드 화면 만들어줘", "이 디자인대로 구현" |

### 복합 유형 처리

- 하나의 요청이 여러 유형에 걸칠 수 있다 (예: 신규 기능 + UI)
- **주된 작업**의 유형을 선택한다
- UI가 핵심이면 `Wireframe UI`, 로직이 핵심이면 해당 유형을 선택한다

## 요구사항 작성 규칙

### 명확성

- 하나의 항목이 하나의 기능/변경만 표현한다
- "~하고, ~하며, ~한다" 식의 복합 문장을 피한다
- 모호한 표현을 구체화한다:
  - (X) "빠르게 로딩되어야 한다"
  - (O) "첫 페이지 로딩 시간이 3초 이내여야 한다"

### 검증 가능성

- 각 항목이 완료 여부를 판단할 수 있어야 한다
- 체크박스(`- [ ]`)로 작성하여 추적 가능하게 한다
- 수치, 조건, 동작을 구체적으로 명시한다:
  - (X) "사용자 경험을 개선한다"
  - (O) "목록에서 항목을 클릭하면 상세 페이지로 이동한다"

### 독립성

- 각 항목이 가능한 한 독립적으로 구현/검증 가능해야 한다
- 의존 관계가 있으면 순서를 명시하거나 그룹으로 묶는다

## 기술 스택 사전 판별 프로세스

프로젝트 루트에서 설정 파일을 탐색하고, 의존성을 분석하여 기술 스택을 판별한다.

### Node.js / JavaScript 생태계

**`package.json`** 확인:

| dependencies/devDependencies 키 | 판별 결과 |
|------|----------|
| `next` | Next.js (App Router vs Pages Router — `app/` 디렉토리 유무로 판별) |
| `react`, `react-dom` | React |
| `vue` | Vue.js |
| `express` | Express.js |
| `fastify` | Fastify |
| `@nestjs/core` | NestJS |
| `typescript` | TypeScript 사용 |

### Python 생태계

**`pyproject.toml`** 또는 **`requirements.txt`** 확인:

| 패키지명 | 판별 결과 |
|----------|----------|
| `fastapi` | FastAPI |
| `django` | Django |
| `flask` | Flask |
| `sqlalchemy` | SQLAlchemy ORM |
| `pydantic` | Pydantic 모델 |

### 기타 언어

| 설정 파일 | 판별 결과 |
|----------|----------|
| `go.mod` | Go (모듈명에서 프레임워크 판별: `gin`, `echo`, `fiber` 등) |
| `pom.xml` | Java + Maven (Spring Boot 여부: `spring-boot-starter-*` 의존성) |
| `build.gradle` / `build.gradle.kts` | Java/Kotlin + Gradle |
| `Cargo.toml` | Rust (주요 크레이트에서 프레임워크 판별: `actix-web`, `axum` 등) |

### UI 라이브러리 판별

| 설정 파일 | 판별 결과 |
|----------|----------|
| `components.json` | shadcn/ui |
| `tailwind.config.js` / `tailwind.config.ts` | Tailwind CSS |
| `styled-components` in package.json | styled-components |
| `.storybook/` 디렉토리 | Storybook |
| `@mui/material` in package.json | Material UI |
| `@chakra-ui/react` in package.json | Chakra UI |

### 판별 결과 기재

기술 스택 섹션에 다음 형식으로 기재한다:

```markdown
## 기술 스택

- **Runtime**: Node.js 20+
- **Framework**: Next.js 14 (App Router)
- **Language**: TypeScript
- **UI**: React 18 + shadcn/ui + Tailwind CSS
- **State**: Zustand
- **DB**: PostgreSQL + Prisma
```

항목이 판별되지 않으면 "미확인"으로 기재하고, 사용자에게 확인한다.

## Wireframe UI TASK 특화 규칙

작업 유형이 `Wireframe UI`인 경우 추가 규칙을 적용한다.

### 입력물 처리

Wireframe UI 작업의 입력물은 다음 중 하나 이상이다:

| 입력물 유형 | 처리 방법 |
|------------|----------|
| **정책서/기획서** (.md, .docx, .pdf) | 핵심 요구사항과 화면 목록을 추출하여 요구사항에 반영 |
| **디자인 이미지** (.png, .jpg, .fig) | 화면 구성 요소를 식별하여 요구사항에 반영. 이미지 경로를 관련 문서에 기재 |
| **구두 요청** | interview 스킬로 화면 구성, 인터랙션, 데이터 흐름을 확인 |
| **기존 코드** | 현재 UI 구조를 분석하여 변경 범위를 특정 |

### 추가 필수 항목

Wireframe UI TASK.md에는 다음 항목을 반드시 포함한다:

```markdown
## 요구사항

### 화면 목록
- [ ] {화면명}: {주요 기능 설명}

### 공통 요구사항
- [ ] 반응형 레이아웃 (모바일/태블릿/데스크톱)
- [ ] 접근성 기본 준수 (시맨틱 HTML, 키보드 내비게이션)

### 화면별 요구사항
#### {화면명}
- [ ] {구성 요소와 인터랙션}
```

## TASK.md 품질 체크리스트

최종 검토 시 다음 항목을 모두 확인한다:

### 구조 완전성
- [ ] 모든 필수 섹션(작업 목표, 배경, 요구사항, 제약 조건, 기술 스택)이 존재하는가
- [ ] 메타데이터(작성일, 작업 유형)가 정확한가

### 작업 목표
- [ ] 1-2문장으로 핵심 목표가 명확히 표현되었는가
- [ ] 읽는 사람이 "무엇을 만드는지" 즉시 이해할 수 있는가

### 요구사항
- [ ] 각 항목이 하나의 기능/변경만 표현하는가
- [ ] 각 항목이 완료 여부를 판단할 수 있는가
- [ ] 모호한 표현(적절히, 효율적으로, 빠르게 등)이 없는가
- [ ] 빠진 요구사항이 없는가 (사용자 요청 대비)

### 기술 스택
- [ ] 프로젝트의 실제 설정 파일과 일치하는가
- [ ] 버전 정보가 포함되어 있는가 (확인 가능한 경우)

### 제약 조건
- [ ] 기술적 제약이 명시되었는가 (호환성, 의존성 등)
- [ ] 비기능 요구사항이 해당되면 포함되었는가 (성능, 보안 등)
