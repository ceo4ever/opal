# op-task — TASK.md 작성

## 실행 컨텍스트

이 스킬은 **오케스트레이터가 직접 수행**한다. 서브에이전트를 생성하지 않는다.
사용자와 대화하며 요구사항을 확인하고, 결과물(TASK.md)을 작성한다.

> **[MUST]** 산출물 작성·검증 시 `opal/core/references/harness/citation-rules.md`를 Read하여 규칙(근거 제시 원칙 / 트랙별 매트릭스 / [MUST] 토큰 / 영역 간 용어 일관성 / decision_required 계약)을 준수한다.

## 페르소나

`personas/service-planner.md`를 Read하여 페르소나를 로드한다.
파일이 없으면 기본 페르소나로 동작한다: **서비스 기획자** — 사용자 요청의 의도를 파악하고, 누락된 정보를 식별하며, 실행 가능한 수준으로 구조화하는 역할.

## 프로세스

### STEP 1. 사용자 요청 파악

사용자의 요청 텍스트를 분석한다:

- **무엇을** 만들거나 변경하려는지 핵심 목표를 추출한다
- **왜** 필요한지 배경과 동기를 파악한다
- **어디까지** 해야 하는지 범위를 특정한다

### STEP 2. 요구사항 명확화

모호하거나 누락된 정보가 있으면 **interview 스킬**을 연동하여 사용자에게 질문한다.

**interview 스킬 탐색 경로** (우선순위):
1. `{프로젝트}/.opal/skills/interview/SKILL.md`
2. `~/.opal/skills/interview/SKILL.md`

다음 항목이 불명확하면 질문한다:
- 작업 범위가 광범위하여 세부 범위 특정이 필요한 경우
- 기존 시스템과의 연동 방식이 불분명한 경우
- 비기능 요구사항(성능, 보안, 접근성)이 언급되지 않은 경우
- 사용자가 원하는 최종 산출물 형태가 불확실한 경우

**질문하지 않는 경우**:
- 요청이 이미 구체적이고 명확한 경우
- 단순 수정/오류 해결로 범위가 자명한 경우

#### 인터뷰 결과 분류

인터뷰 결과를 다음과 같이 분류한다:
- **확정**: 소유자과 합의된 설계 방향 → TASK.md "확정된 설계 방향" 섹션에 기록
- **미확정**: 추가 논의 또는 조사 필요 → TASK.md "미확정 사항 (PLAN에서 결정)" 섹션에 기록

미확정 사항은 PLAN 단계에서 워커가 조사 후 결정한다.

### STEP 3. 기술 스택 사전 판별

프로젝트 루트의 설정 파일을 탐색하여 기술 스택을 자동 판별한다.
상세 판별 기준은 `references/task-guide.md`를 참조한다.

탐색 대상:
- `package.json` — Node.js 생태계 (React, Next.js, Express 등)
- `pyproject.toml`, `requirements.txt` — Python 생태계 (FastAPI, Django 등)
- `go.mod` — Go
- `pom.xml`, `build.gradle` — Java/Kotlin
- `Cargo.toml` — Rust
- `components.json`, `tailwind.config.*` — UI 라이브러리

### STEP 4. TASK.md 작성

아래 통일 형식으로 TASK.md를 작성한다.

#### 대화 내용 반영

스킬 호출 전에 소유자과 관련 대화가 있었을 경우, 해당 내용을 TASK.md에 기록한다.

**배경 분석 (대화에서 도출)** — 대화에서 분석/조사/현황 파악이 먼저 수행된 경우:
- TASK.md 템플릿 "배경" 아래에 "배경 분석 (대화에서 도출)" 섹션을 추가한다
- 분석 결과, 조사 결과, 현황 파악 내용, 파일별 현재 상태 등을 기록한다
- 목적: 워커가 TASK.md만으로 컨텍스트를 독립적으로 파악할 수 있어야 한다

**확정된 설계 방향 (대화에서 합의)** — 대화에서 설계 방향이 합의된 경우:
- TASK.md 템플릿 "배경 분석" 아래(또는 "요구사항" 앞)에 "확정된 설계 방향 (대화에서 합의)" 섹션을 추가한다
- 대화 없이 바로 스킬 호출된 경우 두 섹션 모두 생략

#### 요구사항 작성 기준

각 요구사항 항목은 다음 4가지를 포함한다:

| 필드 | 설명 | 예시 |
|------|------|------|
| **무엇을** | 변경/생성할 내용 (구체적 행위) | "전환 테이블을 섹션으로 추가" |
| **어디에** | 반영 대상 문서/파일 + 섹션 | "`AGENT.md` → 행동 규칙 하위" |
| **왜** | 근거 (확정 방향 참조 또는 문제 설명) | "확정 방향 §2" |
| **AC** | QA Gate에서 Pass/Fail 판정 가능한 수용 기준 | 아래 참조 |

**AC 작성 가이드**: "QA Gate에서 Pass/Fail 판정 가능한 문장"으로 작성한다.

| Bad (모호) | Good (검증 가능) |
|-----------|-----------------|
| "역할 전환을 정의해라" | "5가지 케이스가 테이블에 모두 존재하고, 각 케이스에 조건/역할/동작 컬럼이 채워져 있다" |

## 저장 경로

```
tasks/{NNN}-{YYMMDD}-{스킬약어}-{태스크명}/TASK.md
```

- `{NNN}`: 3자리 순번 — `.opal/MEMORY.md`의 `last_task_number` + 1로 채번 (harness §4 참조)
- `{YYMMDD}`: TASK 단계 시작일 (KST) — `node ~/.opal/tools/date/date.js yymmdd` 실행하여 취득
- `{스킬약어}`: STEP 5에서 결정된 오케스트레이터 약어 (예: `opp`, `opd`, `opds`, `opdw`, `opwt`)
- `{태스크명}`: kebab-case (예: `user-auth-implementation`)
- `tasks/` 폴더가 없으면 생성한다

### STEP 5. 오케스트레이터 선택

작업 유형을 기반으로 적합한 오케스트레이터 스킬을 추천하고 사용자에게 확인한다.

#### 추천 테이블

| 작업 유형 | 추천 스킬 | 설명 |
|----------|----------|------|
| 프레임워크 문서/스킬/설정 변경 | `opp` | 범용 프로젝트 작업 |
| 기획 산출물 세트 (PRD/TRD/정책서/IA) | `opwt` | 기획 문서 네트워크 |
| 기능 개발 — 전체 파이프라인 | `opd` | dev 전체 (분석→계획→실행→테스트) |
| 기능 개발 — 간략 | `opds` | dev 간략 (계획→실행→테스트) |
| 와이어프레임 UI | `opdw` | 와이어프레임 전용 |

#### 절차

1. 작업 유형에 맞는 스킬을 위 테이블에서 선택하여 추천한다
2. 사용자에게 확인: "적용 스킬: `{추천 스킬}`로 진행할까요?"
3. **승인**: 해당 스킬약어로 폴더 생성 및 TASK.md 헤더 기재
4. **변경 요청**: 사용자가 지정한 스킬로 적용
5. **불명확한 경우**: 선택지와 각 스킬 한 줄 설명을 제시하고 사용자가 선택

#### STATE.md 리마인더

> **[오케스트레이터 후처리]** op-task 프로세스 완료 후, 오케스트레이터는 하네스 §4 "오케스트레이터 공통 영역"을 수행해야 한다. 특히 **STATE.md 생성**을 잊지 않는다.
>
> **[MUST] STATE.md는 `state-tool`로만 생성한다. LLM이 직접 작성하는 것은 금지된다.** (`harness/state-template.md` §[MUST] 블록 — TASK F-16 / PLAN §1.5 M-18)
>
> `state init`을 호출하여 STATE.md를 생성한다 (PLAN §3 Step 5 / §2.11 G-8):
>
> ```bash
> ~/.opal/tools/state-tool/run.sh init <task-path> \
>   --skill <opp|opd|opds|opdw|opwt|opgc|oppd|opsdd> \
>   --mode <interactive|agentic> \
>   [--task-title <태스크 제목>] \
>   [--next-action <첫 액션 텍스트>]
> ```
>
> - `--task-title`: STATE.md 1행 제목 (생략 시 `<task-path>` 마지막 디렉토리명 — PLAN §2.19.1)
> - `--next-action`: `## 다음 액션` 초기값 (생략 시 `"PLAN 단계 진입"` — PLAN §2.11 G-8)
> - 행 구성(`--rows-spec`/`--rows-from`)은 오케스트레이터 SKILL.md "STATE.md 도메인 치환값" 참조 (PLAN §2.3)

## 작성 체크리스트

TASK.md 완성 전에 다음을 확인한다:

- [ ] 모드(interactive/agentic)가 헤더에 기록되었는가
- [ ] 작업 유형이 정확히 판별되었는가
- [ ] 작업 목표가 1-2문장으로 명확한가
- [ ] 스킬 호출 전 대화에서 분석/조사가 선행되었다면 "배경 분석 (대화에서 도출)" 섹션을 포함했는가 (없으면 생략)
- [ ] 스킬 호출 전 대화에서 설계 방향이 합의되었다면 "확정된 설계 방향 (대화에서 합의)" 섹션을 포함했는가 (없으면 생략)
- [ ] 인터뷰 결과가 있다면 확정/미확정으로 분류했는가
- [ ] 요구사항이 검증 가능한 단위로 분리되었는가 (무엇을/어디에/왜/AC 포함)
- [ ] AC가 "QA Gate에서 Pass/Fail 판정 가능한 문장"으로 작성되었는가
- [ ] 기술 스택이 프로젝트 실제 구성과 일치하는가
- [ ] 제약 조건이 누락 없이 기재되었는가
- [ ] 관련 문서가 있으면 경로와 함께 명시되었는가
- [ ] 관련 문서를 참조했다면 "관련 문서" 테이블에 유형/경로(URL)/참조 이유가 기재되었는가 (citation-rules.md §3.1 참조)
