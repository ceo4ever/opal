# op-task — TASK.md 작성

## 실행 컨텍스트

이 스킬은 **오케스트레이터가 직접 수행**한다. 서브에이전트를 생성하지 않는다.
사용자와 대화하며 요구사항을 확인하고, 결과물(TASK.md)을 작성한다.

## 페르소나

`personas/service-planner.md`를 Read하여 페르소나를 로드한다.
파일이 없으면 기본 페르소나로 동작한다: **서비스 기획자** — 사용자 요청의 의도를 파악하고, 누락된 정보를 식별하며, 실행 가능한 수준으로 구조화하는 역할.

## 프로세스

### STEP 1. 사용자 요청 파악

사용자의 요청 텍스트를 분석한다:

- **무엇을** 만들거나 변경하려는지 핵심 목표를 추출한다
- **왜** 필요한지 배경과 동기를 파악한다
- **어디까지** 해야 하는지 범위를 특정한다

### STEP 2. 요구사항 명확화

모호하거나 누락된 정보가 있으면 **interview 스킬**을 연동하여 사용자에게 질문한다.

**interview 스킬 탐색 경로** (우선순위):
1. `{프로젝트}/.opal/skills/interview/SKILL.md`
2. `~/.opal/skills/interview/SKILL.md`

다음 항목이 불명확하면 질문한다:
- 작업 범위가 광범위하여 세부 범위 특정이 필요한 경우
- 기존 시스템과의 연동 방식이 불분명한 경우
- 비기능 요구사항(성능, 보안, 접근성)이 언급되지 않은 경우
- 사용자가 원하는 최종 산출물 형태가 불확실한 경우

**질문하지 않는 경우**:
- 요청이 이미 구체적이고 명확한 경우
- 단순 수정/오류 해결로 범위가 자명한 경우

### STEP 3. 기술 스택 사전 판별

프로젝트 루트의 설정 파일을 탐색하여 기술 스택을 자동 판별한다.
상세 판별 기준은 `references/task-guide.md`를 참조한다.

탐색 대상:
- `package.json` — Node.js 생태계 (React, Next.js, Express 등)
- `pyproject.toml`, `requirements.txt` — Python 생태계 (FastAPI, Django 등)
- `go.mod` — Go
- `pom.xml`, `build.gradle` — Java/Kotlin
- `Cargo.toml` — Rust
- `components.json`, `tailwind.config.*` — UI 라이브러리

### STEP 4. TASK.md 작성

아래 통일 형식으로 TASK.md를 작성한다.

```markdown
# TASK: {제목}

> 작성일: YYYY-MM-DD | 작업 유형: {신규/개선/수정/오류/Wireframe UI} | 적용 스킬: {약어}
> 입력: 사용자 요청
> 출력: TASK.md

## 작업 목표

{1-2문장으로 핵심 목표를 명시}

## 배경

{왜 이 작업이 필요한지, 현재 상태와 문제점}

## 요구사항

- [ ] {검증 가능한 단위로 작성}
- [ ] {하나의 항목 = 하나의 기능/변경}

## 제약 조건

- {기술적 제약, 호환성, 성능 요구 등}

## 기술 스택

- {STEP 3에서 판별한 기술 스택 목록}

## 관련 문서

- {참고할 기존 문서, API 명세, 디자인 파일 등}
```

## 저장 경로

```
tasks/{NNN}-{스킬약어}-{태스크명}/TASK.md
```

- `{NNN}`: 3자리 순번 (001, 002, ...)
- `{스킬약어}`: STEP 5에서 결정된 오케스트레이터 약어 (예: `opp`, `opd`, `opds`, `opdw`, `opwt`)
- `{태스크명}`: kebab-case (예: `user-auth-implementation`)
- 기존 `tasks/` 폴더의 최대 번호 + 1로 자동 채번한다
- `tasks/` 폴더가 없으면 생성한다

### STEP 5. 오케스트레이터 선택

작업 유형을 기반으로 적합한 오케스트레이터 스킬을 추천하고 사용자에게 확인한다.

#### 추천 테이블

| 작업 유형 | 추천 스킬 | 설명 |
|----------|----------|------|
| 프레임워크 문서/스킬/설정 변경 | `opp` | 범용 프로젝트 작업 |
| 기획 산출물 세트 (PRD/TRD/정책서/IA) | `opwt` | 기획 문서 네트워크 |
| 기능 개발 — 전체 파이프라인 | `opd` | dev 전체 (분석→계획→실행→테스트) |
| 기능 개발 — 간략 | `opds` | dev 간략 (계획→실행→테스트) |
| 와이어프레임 UI | `opdw` | 와이어프레임 전용 |

#### 절차

1. 작업 유형에 맞는 스킬을 위 테이블에서 선택하여 추천한다
2. 사용자에게 확인: "적용 스킬: `{추천 스킬}`로 진행할까요?"
3. **승인**: 해당 스킬약어로 폴더 생성 및 TASK.md 헤더 기재
4. **변경 요청**: 사용자가 지정한 스킬로 적용
5. **불명확한 경우**: 선택지와 각 스킬 한 줄 설명을 제시하고 사용자가 선택

#### 완료 보고 형식

```
📋 [TASK] 완료 보고
📎 산출물: tasks/{NNN}-{스킬약어}-{태스크명}/TASK.md
적용 스킬: {약어}
다음 단계({다음 단계명})로 넘어갈까요?
```

## 작성 체크리스트

TASK.md 완성 전에 다음을 확인한다:

- [ ] 작업 유형이 정확히 판별되었는가
- [ ] 작업 목표가 1-2문장으로 명확한가
- [ ] 요구사항이 검증 가능한 단위로 분리되었는가
- [ ] 기술 스택이 프로젝트 실제 구성과 일치하는가
- [ ] 제약 조건이 누락 없이 기재되었는가
- [ ] 관련 문서가 있으면 경로와 함께 명시되었는가
