# OPAL 문서 표준 (opal-doc-standard)

> 작성일: 2026-03-29 | 버전: v2.0
> 참조 전용 — 다른 스킬이 문서 산출물 작성/수정 시 이 규칙을 따른다.
> 탐색 경로: ~/.opal/references/opal-doc-standard.md

## 1. 언어 규칙

- 프로젝트의 CLAUDE.md 또는 코드 컨벤션 문서에 정의된 언어 규칙을 **우선** 따른다.
- 별도 규칙이 없으면: 본문 한국어, 코드/변수/필드명 영어.
- 파일명: 프로젝트 규칙 우선. 별도 규칙이 없으면 `{내용}_{버전}.{확장자}` 형식.
- 문서 형식: Markdown(.md) 기본, 필요 시 .docx/.xlsx/.pptx.
- 저장 위치: 프로젝트 구조에 맞춰 저장한다.

## 2. 문서 헤더 템플릿

모든 기술 문서는 반드시 아래 구조로 시작한다:

```markdown
# [문서 제목]

> 작성일: YYYY-MM-DD | 작성자: [작성자명] | 버전: v{X.Y}

---

## 1. 개요
[문서 목적, 대상, 범위]

## 2. 상세 내용
[본문]

## 3. 참고사항
[관련 문서, 제약사항]

---

변경이력:

| 버전 | 일시 | 작성자 | 변경내용 |
|------|------|--------|---------|
| v1.0 | YYYY-MM-DD HH:mm | [작성자명] | 초기 작성 |
```

## 3. 문서 유형별 필수 섹션

### 범용

| 문서 유형 | 필수 섹션 | 비고 |
|-----------|----------|------|
| **분석서** | 개요, 분석 대상, 분석 결과, 종합 평가 | 데이터 기반 |
| **명세서** | 개요, 인증, 엔드포인트, 요청/응답, 에러, 제한사항 | API 중심 |
| **정책서** | 개요, 용어정의, 각 정책 영역, 변경이력 | 비즈니스 규칙 — 본문은 비즈니스 용어 우선 (코드 식별자 본문 주어 금지: `citation-rules.md` §8) |
| **설계서** | 개요, 아키텍처, 상세 설계, 인터페이스, 제약사항 | 기술 중심 |
| **계획서** | 개요, 목표, 범위, 일정, 산출물, 리스크 | 작업 계획 |
| **보고서** | 개요, 배경/목적, 조사 방법, 결과/분석, 결론/제안 | 데이터 기반 |
| **가이드/매뉴얼** | 개요, 사전 조건, 단계별 절차, 트러블슈팅, FAQ | 절차 중심 |
| **기획/제안서** | 개요, 현황/문제 분석, 제안 내용, 기대 효과, 일정/리소스 | 의사결정용 |

### 기획 산출물 (opwt)

| 문서 유형 | 필수 섹션 | 비고 |
|-----------|----------|------|
| **PRD** | 개요, 목표/배경, 타깃 사용자, 핵심 요구사항, 비기능 요구사항, 우선순위, 성공 지표 | 제품 정의 |
| **TRD** | 개요, 시스템 아키텍처, 기술 스택, API 설계, 데이터 모델, 인프라/배포, 보안, 제약사항 | 기술 설계 |
| **IA** | 개요, 메뉴/화면 구조, 기능 정의, 접근 권한, 정책 연결 | 아래 IA 작성 가이드 참조 |

> **IA 작성 가이드**: md는 구조 개요 정리용으로 사용하고, 실질 내용(메뉴 구조 + 기능 정의)은 JSON으로 작성을 추천한다. 상세 JSON 스키마는 opwt의 `references/network-guide.md` 섹션 9 "IA 형식 가이드"를 참조한다.

## 4. 테이블 작성 규칙

- 모든 테이블에는 헤더 행과 구분선이 있어야 한다.
- 테이블 내 데이터는 좌측 정렬 기본.
- 빈 셀은 `-` 또는 `N/A`로 표시.
- 테이블이 5개 컬럼을 초과하면 분리 검토.

## 5. 버전 넘버링 규칙

### 형식: `v{Major}.{Minor}`

| 변경 수준 | 버전 변경 | 예시 | 기준 |
|-----------|----------|------|------|
| **구조적 변경** | Major 증가 | v1.0 → v2.0 | 섹션 추가/삭제, 엔티티 신규, 아키텍처 변경 |
| **내용 수정** | Minor 증가 | v1.0 → v1.1 | 기존 섹션 내용 수정, 오류 수정, 보강 |

**Major 변경** (v1.x → v2.0):
- 새로운 주요 개념이나 구조가 추가될 때
- 문서 구조(섹션) 자체가 추가되거나 대폭 변경될 때
- 기존 규칙이 근본적으로 바뀔 때

**Minor 변경** (v1.0 → v1.1):
- 기존 섹션 내 설명 보강, 테이블 데이터 추가
- 오탈자, 수치 수정
- 기존 규칙의 세부 조정

## 6. 파일 관리 프로세스

1. **기존 버전 확인** — 해당 폴더에서 동일 문서의 최신 버전을 확인한다.
2. **새 파일 생성** — 기존 파일을 절대 덮어쓰지 않는다. 새 버전은 새 파일로 생성한다.
3. **변경이력 업데이트** — 문서 하단의 변경이력 테이블에 새 버전 항목을 추가한다. 이전 버전의 변경이력도 모두 포함해야 한다.
4. **헤더 메타정보 갱신** — `> 작성일: {오늘 일시 YYYY-MM-DD HH:mm KST} | 작성자: {에이전트명} | 버전: v{새 버전}`

산출물 업데이트 요청 시 주의사항:
- 반드시 최신 버전 파일을 Read로 먼저 확인
- 변경 범위를 파악하여 Major/Minor 결정
- 이전 버전의 모든 내용을 새 버전에 계승 (누락 방지)
- 변경된 부분만 정확히 수정 (관련 없는 부분 변경 금지)

## 7. 변경이력 테이블 형식

```markdown
| 버전 | 일시 | 작성자 | 변경내용 |
|------|------|--------|---------|
| v1.0 | YYYY-MM-DD | {작성자} | 초기 작성 |
| v1.1 | YYYY-MM-DD HH:mm | {작성자} | {핵심 변경 1줄 요약} |
```

변경내용은 1줄로 핵심만 기술한다. 상세 내용은 문서 본문에서 확인한다.

## 8. HTML/바이너리 파일 버전 관리

코드 내부에 변경이력 섹션이 없는 파일(HTML, 바이너리 등):
- 파일명으로 버전 관리 (예: `wireframe_v3.0.html`)
- 부분 수정은 기존 파일을 직접 Edit (Minor: 파일명 유지)
- 대규모 변경은 새 파일 생성 (Major: 새 파일명)

## 9. 작업 보고 규칙

문서 작성 완료 시 반드시 다음을 제공한다:
- 산출물 파일 경로
- 주요 변경 사항 요약 (3줄 이내)
- 관련 문서 영향 분석 (다른 문서에 영향이 있는지)

## 10. 출력 형식 규칙

기본 출력은 `.md`(Markdown)이다. 다른 형식으로 변환 시 아래 규칙을 따른다.

| 형식 | 용도 | 주의사항 |
|------|------|---------|
| `.md` | 기본 출력. 모든 문서의 원본 형식 | - |
| `.docx` | 공유/인쇄용 | 이미지는 상대 경로 대신 인라인 삽입. 복잡한 마크다운 테이블(중첩, 5컬럼 초과)은 단순화 |
| `.pdf` | 배포/아카이브용 | 페이지 나눔 고려. 목차(TOC) 포함 권장. 코드 블록은 고정폭 폰트 유지 |
| `.xlsx` | 구조화 데이터 (IA 등) | JSON → xlsx 변환 시 시트별 데이터 매핑을 명시. 원본 JSON과 동일 경로에 저장 |

변환 시 원본 `.md`(또는 `.json`)를 항상 함께 유지한다. 변환본만 단독으로 관리하지 않는다.
