# 분석 코어

ANALYSIS는 PLAN의 변경 대상·계약·검증 방법을 정하는 데 필요한 사실만 확인한다.
산출물 형식은 분석 스킬이 소유한다.

## 1. 근거를 읽는 순서

분석 시작 전에 PM이 다음 순서로 컨텍스트를 준비한다.

1. 프로젝트 지식이 있으면 작업 키워드로 관련 항목을 조회하고 선별한다.
2. 기존 코드맵이 있으면 변경 후보의 구조·의존·소비자를 조회한다.
3. `docs/PROJECT.md`를 읽고, 레지스트리의 용도·참조 시점·경로 규칙으로 이번 작업에 필요한
   기획·설계·개발·운영 문서를 선별한다.
4. TASK와 이전 단계 산출물에서 직접 지목한 문서를 추가한다.

프로젝트 지식이나 코드맵이 없으면 그 단계만 건너뛴다. 분석을 시작하기 위해 새 지식 저장소나
코드맵을 만들지 않는다. 조회 결과와 선별 문서 경로는 디스패치 입력으로 전달한다.

분석 워커는 주입된 근거를 같은 순서로 소비하며 이미 확인된 내용을 다시 탐색하지 않는다.
추가 탐색은 §3의 남은 차이에만 수행한다. PM이 직접 분석하는 경우에도 같은 순서를 적용한다.

## 2. 조사할 질문

다음 중 답이 PLAN을 바꾸는 질문만 조사한다.

- TASK의 Open questions
- AC/C 충족 여부를 좌우하는 현재 동작
- 변경 대상의 생성자, 소비자, 호출자, parser, gate
- 틀리면 구현·실제 연동·설치·배포가 실패하는 권한·데이터·환경 가정
- 구현 뒤 사실이 달라져 갱신해야 할 프로젝트 문서

질문이 없으면 새 질문을 만들지 않는다.

## 3. 델타 조사

프로젝트 지식, 코드맵, PROJECT 선별 문서가 답하지 못한 항목만 확인한다.

- 코드: 공개 인터페이스, 직접 호출자, 관련 테스트와 설정
- 문서 형식: 생성자, 소비자, parser, gate, 설치본
- 데이터·외부 연동: 읽기·쓰기 경계, 권한, 실제 환경 검증 지점
- 버그: 재현 조건, 발생 지점, 근본 원인, 같은 원인의 영향 범위

PM이 주입한 runtime capability만 사용한다. 필요한 capability가 없으면 기본 읽기 도구로 확인 가능한
범위까지만 조사하고 한계를 남긴다. 특정 도구·MCP의 존재를 가정하지 않는다.

## 4. 기록과 승계

- 사실은 근거 위치와 PLAN에 미치는 영향을 함께 기록한다.
- 소스 원문을 복제하지 않고 `경로:줄번호`, 문서 절, 실행 결과를 사용한다.
- TASK에서 확정된 문제·결과·AC/C를 다시 정의하지 않는다. 충돌이 있으면 근거와 함께 보고한다.
- 실제로 실행하지 않은 연동·권한·데이터 프로브는 확인 사실로 쓰지 않는다.
- PLAN은 ANALYSIS를 재조사하지 않고 소비한다. 새로운 충돌이나 누락이 발견된 경우에만 해당 항목을 보완한다.

## 5. 종료 기준

다음 조건을 만족하면 분석을 끝낸다.

- PLAN을 바꾸는 각 질문에 확인 사실 또는 명시된 미확인 한계가 있음
- 직접 변경 후보와 회귀 확인 경계가 구분됨
- 갱신할 프로젝트 문서 후보가 빠지지 않음
- 다음 단계가 다시 전체 탐색하지 않고 설계를 시작할 수 있음
