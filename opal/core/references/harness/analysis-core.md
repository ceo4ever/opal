# 분석 코어 — ANALYSIS·PLAN 공유 SSOT

> ANALYSIS·PLAN 두 단계가 공유하는 분석 절차의 단일 원천이다. 절차는 이 문서가 소유하고, 산출물 형식(ANALYSIS.md/PLAN.md 템플릿)은 각 스킬이 소유한다 — 역할이 분리되어 있으므로 이 문서에 산출물 템플릿을 신설하지 않는다.

---

## 1. 지식 선조회 3단

ANALYSIS 단계 진입 시 · PLAN 단계 2단계(기능별 분석) 진입 시, 코드/문서 재탐색에 앞서 아래 순서로 지식을 선조회한다.

```bash
# 1단 brain — 과거 결정·교훈 (E5이므로 E1~E4 동반 인용 필수)
~/.opal/tools/brain-tool/run.sh search "<키워드>"
# 2단 code-scan — 구조·@header 검색
~/.opal/tools/code-scan/run.sh scan <scope> ; ~/.opal/tools/code-scan/run.sh search "<키워드>"
# 3단 docs 레지스트리(docs/PROJECT.md 문서 표) → 과거 태스크 산출물(tasks/**/ANALYSIS.md·DONE.md)
```

- **1단 brain**: 동일·유사 태스크의 과거 결정·교훈을 검색한다. brain은 파생 스냅샷(E5)이므로 단독 인용을 금지하며, E1~E4 근거를 동반 인용한다(`citation-rules.md` §9 (e) E5 단독 인용 금지).
- **2단 code-scan**: 구조·@header 기반으로 관련 코드를 검색한다. 결과가 불충분한 경우의 분기 판정은 `header-rules.md` §빈 결과 폴백이 소유한다(본 문서는 분기 조건·수치를 복제하지 않는다).
- **3단 docs 레지스트리**: `docs/PROJECT.md` 문서 표를 조회해 이번 작업과 관련된 문서를 선별한다. 이 단계는 항상 수행한다(비용이 표 1개 조회다).
- **3단-B 과거 태스크 산출물 — [MUST] 조건부**: 과거 산출물(`tasks/**/ANALYSIS.md` · `DONE.md`) 조회는 **무조건 수행하지 않는다.** 아래 트리거 중 **하나 이상**이 참일 때만 수행한다.

| # | 트리거 | 판정 방법 |
|---|--------|----------|
| T1 | 1단 brain이 0건이거나 관련도가 낮다 | 1단 결과로 판정(추가 비용 0) |
| T2 | 대상 파일을 건드린 과거 태스크가 있다 | `git log --oneline -- <대상경로>`에 태스크 번호 존재 |
| T3 | TASK.md가 선행 태스크를 인용한다 | `task:NNN` 또는 `tasks/NNN-` 참조 존재 |
| T4 | 회귀·재발·이전 결정 번복 성격이다 | 작업 유형이 `오류`·`수정`이거나 배경에 재발 서술 존재 |

  - **근거**: brain은 선별·stale 가능한 파생 스냅샷이라 과거 산출물을 전량 대체하지 못한다(`opal/core/references/opal-pm.md` §13). 그러나 태스크 산출물은 프로젝트가 커질수록 누적되므로, 무조건 조회는 결과 0건이 예정된 호출을 규범이 강제하는 형태가 된다 — 절차 충족이 커버리지 착시를 만든다.
  - **[MUST] 스킵을 침묵하지 않는다**: T1~T4 전건 미해당으로 건너뛰면 산출물 §0 참조 문서에 `과거 산출물 미조회 — 트리거 T1~T4 전건 미해당` 1줄을 남긴다. 축소 실행은 허용하되 결측은 명시한다.

**[MUST] 코드/문서 작업 판별 승계**: code-scan 사전 범위 파악 기준은 `opal/core/references/pm/dispatch-process.md` §code-scan 사전 범위 파악이 소유한다. 문서·규범 전용 태스크에서는 2단이 0건을 반환할 수 있다 — 이 경우 `header-rules.md` §빈 결과 폴백 판정에 따르고, 0건이면 즉시 이탈한다(무의미한 재호출 금지).

**[MUST] Glob/Grep/Read의 3층 위치**: 이 도구들은 금지가 아니라 **위치가 정해져** 있다.

| 층 | 상황 | 허용 |
|----|------|------|
| 직행 | 선조회 없이 첫 동작으로 사용 | **금지** (`opal/core/references/pm/dispatch-process.md` §code-scan 사전 범위 파악) |
| 델타 보조 | 선조회 결과에 없는 신규 요소 탐색 | **허용** — §3 델타 탐색 규율 |
| 폴백 병행 | code-scan 매칭 0건·저커버리지 | **허용** — 분기 판정은 `opal/core/references/harness/header-rules.md` §빈 결과 폴백이 소유 |

**[MUST] 플랫폼 조건문 금지**: 위 3단은 도구 래퍼(`~/.opal/tools/*/run.sh`) 호출로만 기술한다 — 스킬·에이전트 본문에 플랫폼 조건문을 추가하지 않는다(`docs/CONVENTIONS.md` §플랫폼 분기 격리).

## 2. 증분 소비 규율

§1 선조회 3단 중 하나라도 결과를 반환하면, 해당 결과를 **재도출하지 않고 그대로 소비**한다.

- **선조회 결과 존재**: brain·code-scan·docs 레지스트리·과거 산출물 중 하나라도 답을 제공하면 그 정보를 그대로 인용하고, 나머지는 §3 델타 탐색으로 넘긴다. 동일 정보를 다시 코드 탐색·재작성하지 않는다.
- **확정 입력 승계**: TASK.md `[결정]` 항목과 ANALYSIS.md의 2원 확정 원천 — §1.1 「관련 파일 목록」(파일 맵: 영역·경로·역할·변경 유형 4필드, §5 축 적용) + §다음 단계 입력(§8 「PLAN이 재조사 없이 쓸 수 있는 확정값」, 결정형 확정값 3열) — 은 재조사 없이 그대로 승계한다. **[MUST] 재도출 금지** — 승계 항목의 근거를 후속 단계가 다시 찾아 검증하지 않는다. 미결 항목만 「PLAN 결정 필요」 표에서 소비한다.
- **선조회 결과 완전 부재**: §1의 수행한 단계가 모두 0건이면 본 절 대신 신규(Full) 분석으로 전환한다 — 판정은 `opal/core/references/harness/header-rules.md` §빈 결과 폴백을 따른다. 3단-B를 트리거 미해당으로 수행하지 않은 경우는 '0건'이 아니라 '미조회'이며, 위 스킵 명시 규칙을 따른다.

---

## 3. 델타 탐색 규율

§1 선조회 결과가 존재하면, 이후 탐색은 **선조회 결과와 이번 태스크 요구사항의 차분(delta)만** 대상으로 한다.

- 선조회 결과가 이미 커버하는 파일·함수·의존 관계는 재확인 대상에서 제외한다.
- TASK.md 요구사항 중 선조회 결과에 없는 신규 요소만 Glob/Grep/Read로 추가 탐색한다.
- 델타가 없으면(선조회 결과가 요구사항을 전부 커버하면) 추가 탐색 없이 §4 이하 절차로 진행한다.
- 델타 탐색 결과에도 근거 등급(E1~E5)을 병기한다(`citation-rules.md` §9).

## 4. 분석 깊이 기준

TASK.md의 `type` 또는 내용에 따라 분석 범위를 조절한다.

| 태스크 유형 | 분석 범위 | 설명 |
|-------------|----------|------|
| **신규 기능** | 전체 구조 | 삽입 지점, 기존 패턴과의 정합성, 전체 아키텍처 영향 |
| **기능 개선** | 변경 대상 + 직접 의존 | 변경 모듈과 이를 호출/참조하는 모듈 |
| **버그 수정** | 변경 대상 + 영향 범위 | 버그 발생 지점과 파급 경로 |
| **오류 수정** | 에러 역추적 | 에러 로그 → 호출 스택 → 원인 모듈 역추적 |

### 데이터 파이프라인 작업 추가 사항

데이터 흐름이 포함된 태스크의 경우 추가로 분석한다.

- **데이터 소스**: 입력 데이터의 출처, 형식, 볼륨
- **변환 단계**: ETL/ELT 파이프라인의 각 단계
- **데이터 스키마**: 테이블/컬렉션 구조, 필드 타입, 인덱스
- **데이터 무결성**: 제약 조건, 유효성 검사 규칙
- **성능 특성**: 쿼리 패턴, 배치 크기, 타임아웃

## 5. 관련 파일 맵 6영역 축

파일을 아래 6영역 분류 축으로 정리한다.

| 영역 | 경로 | 역할 | 변경 유형 |
|------|------|------|----------|
| FE / BE / DB / 환경 / 배치 / 공통 | 경로 | 역할 설명 | 신규 / 수정 |

> **6영역 라벨**: `FE`(프론트엔드) / `BE`(백엔드) / `DB`(데이터베이스) / `환경`(설정·패키지) / `배치`(배치·크론·마이그레이션) / `공통`(FE/BE 공유)
>
> **프레임워크 문서·스킬 태스크 축**: 위 6영역 대신 **스킬 / 가이드 / 오케스트레이터 / 에이전트 / 문서 / 환경 / 배치** 축을 사용한다.

## 6. 의존성·영향 범위 도출

### 6.1 의존성 맵

- import/require 그래프: 변경 대상 → 직접 의존 → 간접 의존
- 외부 패키지 의존성 (package.json, requirements.txt 등)
- 내부 모듈 간 호출 관계(호출자/피호출자)
- 순환 의존성 여부

### 6.2 직접 영향

- 생성/수정/삭제 대상 파일 목록
- 변경되는 인터페이스 (API, 타입, 스키마)

### 6.3 간접 영향

- 변경된 모듈을 import하는 파일 (Grep으로 확인)
- 변경된 API를 호출하는 클라이언트
- 공유 데이터 구조·상태에 미치는 영향
- 영향받는 테스트 파일
- 설정/환경변수 변경에 의한 파급

### 6.4 영향 범위 체크리스트

- [ ] DB 스키마 변경 → 마이그레이션 필요 여부
- [ ] API 인터페이스 변경 → 하위 호환성 유지 여부
- [ ] 설정/환경변수 변경 → .env.example 업데이트 필요 여부
- [ ] 빌드/배포 파이프라인 변경 → CI/CD 수정 필요 여부
- [ ] 공유 라이브러리 변경 → 다른 프로젝트 영향 여부

## 7. 분석 품질 체크리스트

ANALYSIS.md(및 PLAN.md 기능별 분석) 작성 완료 후 아래 통합 체크리스트로 자체 검증한다. 이 문서가 체크리스트의 단일 원천(SSOT)이다 — 다른 문서는 이 목록을 복제하지 않고 포인터로 참조한다.

### 완전성
- [ ] TASK.md의 모든 요구사항이 분석에 반영되었는가
- [ ] 관련 파일 목록이 §1 선조회(code-scan) 또는 Glob/Grep으로 실제 확인되었는가 (추측 금지)
- [ ] 의존성 맵이 import/require 기반으로 작성되었는가 (§6.1)
- [ ] §0 참조 문서 테이블이 작성되어 있는가 (유형/경로(URL)/참조 이유 포함)

### 정확성
- [ ] 파일 경로가 실제 존재하는가
- [ ] 버전 정보가 실제 설정 파일에서 추출되었는가
- [ ] 외부 조사 결과가 공식 소스(context7/WebSearch)에서 확인되었는가

### 유용성
- [ ] 영향 범위가 직접+간접 모두 식별되었는가 (§6.2, §6.3)
- [ ] 제약/리스크가 구체적 근거와 함께 기술되었는가
- [ ] 다음 단계(PLAN)에서 재조사 없이 바로 활용할 수 있는 수준인가

### 근거 표기
- [ ] §1.1 관련 파일 목록에 근거(줄번호) 컬럼이 채워져 있는가 (없으면 "-" 표기)
- [ ] 제약/리스크에 근거(§N, 줄번호, 또는 외부 URL)가 기재되어 있는가
- [ ] 소스코드 원문 블록이 0건인가 — 코드펜스는 실행 명령·시그니처로 한정한다(`citation-rules.md` §2.2 소스코드 원문 블록 금지)

### dedup 판정 비대상 (중복으로 세지 않는 것)

체크리스트·본문 중복 계수 시 아래 3종은 중복으로 세지 않는다.

1. 마크다운 표 구분선·공통 참조표 헤더 — 규범이 요구하는 필수 반복 구조
2. `citation-rules.md` 트리거 문구 등 SSOT+Trigger 관용구 — 제거하면 로드 경로가 끊긴다
3. 각 문서가 자기 산출물 형식을 정의하는 템플릿 블록
