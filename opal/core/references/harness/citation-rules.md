# 인용 규칙 (Citation Rules)

> 출처: opal-harness.md §2
> 로드 시점: TASK/ANALYSIS/PLAN 산출물 작성 시
> 역할: 산출물 인용 포맷(문서/코드/외부/MUST) + 적용 방식(테이블+인라인) + 단계별 의무 수준 + 예외 규칙 + 사람/AI 탐색 가이드

## §0. 근거 제시 원칙

> **[MUST]** 상상·추정·기억 기반 기재 금지 — 모든 분석·설계 결정은 문서 근거(경로/URL + 섹션/줄번호)를 인용해야 한다. 단, "**사실 주장**"(코드베이스·문서·실행 결과에 대한 서술)과 "**결정**"(소유자·PM의 권한 행사)은 구분한다 — 결정은 근거 인용 의무의 판정 대상이 아니다(§9 (f)).

이 원칙은 모든 pilot(오케스트레이터)과 PLAN·TASK·ANALYSIS·QA 스킬 전반에 강제 적용된다. 근거 없는 설계 결정은 해당 내용이 "상상 또는 추정"으로 간주되어 무효 처리될 수 있다.

## 1. 적용 범위 및 목적

### 적용 범위

TASK / ANALYSIS / PLAN 3단계 산출물에 설계 결정·분석 결과의 **근거 문서 + 위치**를 추적한다. 워커가 산출물을 작성할 때 이 규칙을 필수 하네스로 적용한다.

| 대상 산출물 | 적용 스킬 |
|-----------|---------|
| TASK.md | `op-task` |
| ANALYSIS.md | `op-dev-analysis` |
| PLAN.md (dev) | `op-dev-plan` + `references/plan-guide.md` |
| PLAN.md (범용) | `op-task-plan` + `references/plan-guide.md` |

### 목적

1. **사람의 원본 접근 즉시성** — 경로/URL이 그대로 기재되어 에디터 이동 또는 브라우저 클릭으로 즉시 원본 문서에 도달한다
2. **AI의 재탐색 비용 절감** — 다음 단계 워커가 이미 식별된 근거 경로를 그대로 Read/WebFetch에 주입하여 반복 탐색을 제거한다
3. **재해석 방지** — 핵심 제약·금지사항은 원문 인용으로 해석 여지를 제거한다 (`opal-pm.md` §3 Step 3 인용 의무 규칙과 통일)

## §1.5. 개발/비개발 트랙별 근거 매트릭스

산출물 작성 트랙에 따라 필수 근거 유형이 달라진다.

| 트랙 | 문서 | 웹 | 기획 산출물 | 설계 산출물 | 소스 코드 |
|------|------|-----|-----------|-----------|---------|
| **비개발 트랙** | 필수 | 필수 | 선택 | 선택 | 선택 |
| **개발 트랙** | 필수 | 선택 | 필수 | 필수 | 필수 |

트랙 판별은 산출물 유형으로 한다 — 기획 문서(PRD/TRD/정책서/IA) = 비개발 / 코드·설계 산출물(ANALYSIS/PLAN/EXECUTE 관련) = 개발.

## 2. 인용 포맷

산출물에 근거를 기록할 때는 아래 4종의 포맷 중 하나를 사용한다.

### 2.1 문서 근거 (기획/설계 문서)

로컬 파일 중 사람이 읽는 Markdown 문서(기획서, 설계서, 컨벤션, 하네스 문서 등).

**표준 포맷**:

```
`경로` §{N} {섹션명}
```

원문 인용이 필요한 경우:

```
`경로` §{N}: "<원문>"
```

**예시**:

- `` `opal/core/references/opal-harness.md` §2 모듈 구조 ``
- `` `docs/CONVENTIONS.md` §3.1: "API 응답은 camelCase를 사용한다" ``

### 2.2 코드 근거 (소스 코드)

로컬 파일 중 코드 파일(.py, .ts, .js 등). 줄번호를 명시하여 AI가 Read 도구의 `offset`/`limit`에 매핑할 수 있게 한다.

**표준 포맷**:

```
`경로:줄번호`
```

줄 범위:

```
`경로:N-M`
```

**예시**:

- `` `opal/skills/op-dev-plan/SKILL.md:134` ``
- `` `src/models/user.py:45-78` ``

**[MUST] 산출물 분량 규칙**: ANALYSIS·PLAN 등 산출물에 **소스코드 원문 블록을 기재하지 않는다**. 대체: `경로:줄번호` 인용 + 필요 시 **1~3줄 약식 발췌**까지만 허용한다. 이유: 코드가 SSOT인데 산출물에 원문을 복제하면 토큰을 2중 지불하고 그 복제본은 즉시 stale이 된다.

### 2.3 외부 사이트

외부 URL(공식 문서, 라이브러리 레퍼런스, 블로그 등). 사람은 클릭, AI는 WebFetch로 접근한다.

**표준 포맷**:

```
[사이트명/문서명](URL)
```

**예시**:

- `[FastAPI 공식 문서 — 미들웨어](https://fastapi.tiangolo.com/tutorial/middleware/)`
- `[shadcn/ui Button](https://ui.shadcn.com/docs/components/button)`

### 2.4 필수 제약 인용 ([MUST])

재해석 여지가 있는 금지사항·강제 규칙은 `[MUST]` 접두사 + 원문 인용으로 기재한다. `opal-pm.md` §3 Step 3 포맷과 통일한다.

**표준 포맷** (로컬 문서):

```
[MUST] `경로` §{N}: <원문>
```

**표준 포맷** (외부 사이트):

```
[MUST] [사이트명](URL): <원문>
```

**예시**:

- `` [MUST] `opal/core/references/opal-harness.md` §1 Guards: "사용자가 명시적으로 '승인', '진행해', '구현해' 등의 실행 허가를 내릴 때까지 코드를 작성하거나 파일을 생성/수정하지 않는다." ``
- `` [MUST] `docs/CONVENTIONS.md` §3.1: "API 응답은 camelCase를 사용한다" ``

### 2.5 개발 트랙 [MUST] 토큰 대상

개발 트랙에서 `[MUST]` 인용이 반드시 필요한 구체 토큰 유형 6종:

#### (1) 필드명

- **Good**: `` [MUST] `docs/CONVENTIONS.md` §3.1: "API 응답은 camelCase" ``
- **Bad**: `"API 응답은 camelCase다 (컨벤션 문서 참고)"`

#### (2) 함수 시그니처

- **Good**: `` [MUST] `src/user.py:45`: "def create_user(email: str) -> User" ``
- **Bad**: `"create_user는 email 받는다"`

#### (3) 타입명

- **Good**: `` [MUST] `src/types/user.ts:12`: "type UserRole = 'admin' | 'member'" ``
- **Bad**: `"UserRole은 admin 또는 member"`

#### (4) ERD 컬럼명

- **Good**: `` [MUST] `docs/ERD.md` §2.3: "users.deleted_at TIMESTAMP NULL" ``
- **Bad**: `"users 테이블에 deleted_at 있음"`

#### (5) IA 화면 ID/라우트

- **Good**: `` [MUST] `docs/IA.md` §4.1: "SCREEN-U001 /settings/profile" ``
- **Bad**: `"설정 페이지 경로"`

#### (6) 정책 조항 번호

- **Good**: `` [MUST] `docs/policy.md` §5.2.1: "만 14세 미만 가입 불가" ``
- **Bad**: `"14세 제한 정책"`

## 3. 적용 방식 (참조 테이블 + 인라인)

인용은 **참조 문서 테이블**(개요)과 **인라인 인용**(구체 근거)을 혼합하여 적용한다.

| 방식 | 적용 위치 | 목적 |
|------|---------|------|
| **참조 문서 테이블** | 산출물 상단(TASK §관련 문서 / ANALYSIS §0 / PLAN §1 또는 §8.3) | 전체 참조 문서 개요 — 사람 탐색용 + 인라인 단축 참조용 |
| **인라인 인용** | 설계 결정·분석 결과 문장 끝 | 구체 근거 — 어느 문장이 어느 문서의 어느 섹션/줄에서 왔는지 |

### 3.1 참조 문서 테이블

모든 산출물의 참조 문서 테이블은 아래 공통 컬럼 스키마를 사용한다.

```markdown
| # | 유형 | 문서/사이트 | 경로/URL | 참조 이유 |
|---|------|-----------|---------|----------|
| D-1 | 설계 | CONVENTIONS.md | `docs/CONVENTIONS.md` | API 응답 규칙 |
| D-2 | 소스 | user.py | `src/models/user.py` | 현재 모델 구조 |
| D-3 | 외부 | FastAPI 공식 문서 | [FastAPI Middleware](https://fastapi.tiangolo.com/tutorial/middleware/) | 미들웨어 패턴 |
```

**컬럼 규정**:

| 컬럼 | 값 규정 |
|------|--------|
| `#` | 태스크 내 고유 ID. 포맷 `D-{N}` (D-1, D-2, ...) — 인라인 인용에서 단축 참조에 사용 |
| `유형` | `기획` / `설계` / `소스` / `외부` 중 1택 |
| `문서/사이트` | 문서명 또는 사이트명 (식별용 이름) |
| `경로/URL` | 로컬은 백틱 경로(`` `경로` ``), 외부는 Markdown 링크(`[사이트명](URL)`) |
| `참조 이유` | 이 문서를 참조한 이유 한 줄 요약 |

### 3.2 인라인 인용 (단축 참조)

본문 문장에서 참조 테이블의 항목을 인용할 때는 `D-{N}` 단축 참조를 사용한다.

**표준 포맷**:

```
{설계 결정 문장} (→ D-N §N)
```

**예시**:

- "API 응답은 camelCase를 적용한다 (→ D-1 §3.1)"
- "User 모델에 `deleted_at` 필드 추가 (→ D-2:45-78)"
- "미들웨어는 Starlette 베이스 (→ D-3)"

참조 테이블을 거치지 않고 직접 인라인 인용하는 것도 허용된다 (§2의 풀 포맷 그대로 기재).

## 4. 단계별 의무 수준

단계가 뒤로 갈수록(TASK → ANALYSIS → PLAN) 설계 결정이 구체화되므로 인용 의무도 단계적으로 강화된다.

| 단계 | 참조 문서 테이블 | 인라인 인용 | `[MUST]` 포맷 |
|------|----------------|-----------|--------------|
| **TASK** | 필수 (관련 문서 섹션) | **사실 주장 필수 / 결정 선택** — §9 (f) 참조 | 선택 |
| **ANALYSIS** | 필수 (§0 참조 문서) | **필수** — 관련 파일 맵에 `경로:줄번호`, 제약/리스크에 `경로 §N` 또는 `[사이트명](URL)` | 선택 |
| **PLAN** | 필수 (§1 또는 §8.3) | **필수** — 설계 결정 뒤에 `(→ D-N §N)` 단축 또는 풀 포맷 | 필수 — 핵심 설계 중 금지/강제 규칙 |

**PM → 워커 주입 포맷과의 통일**: `opal-pm.md` §3 Step 3 "인용 의무 규칙"의 `[MUST] <문서명> §N: <원문>` 포맷을 §2.4에서 재사용한다. PM이 주입한 `[MUST]` 제약은 워커가 산출물에 그대로 옮겨 적어 정합성을 유지한다.

## 5. 예외 규칙

### 인용 생략 허용

- **결정(권한 행사)**: 소유자·PM이 선택한 방향(예: 경험·일반 원리에 근거한 결정)은 인용 생략 허용 — 결정은 근거가 없어도 확정이다(§9 (f) 참조). 단, 문서 근거가 명백히 있는 경우에는 필수.
- **사실 주장**: 코드베이스·문서·실행 결과에 대한 서술은 인용 생략을 **허용하지 않는다**. 근거가 없으면 그것은 사실 주장이 아니라 가설이므로, 가설로서 리스크 가설(H-N)로 강등해 기재한다.
- **자명한 내용**: 프로젝트 내에서 반복 사용되는 자명한 컨벤션(예: 파일 네이밍)은 매번 인용하지 않아도 된다.

### 레거시 호환

- **기존 산출물 소급 변경 불필요**: 이 규칙 도입 이전에 작성된 TASK.md/ANALYSIS.md/PLAN.md는 소급 변경하지 않는다. 신규 태스크부터 적용한다.

### 결합도 완화

- 외부 URL이 빈번히 변경되는 경우(베타 문서 등), 참조 문서 테이블의 `참조 이유` 컬럼에 "변경 가능성" 표기를 추가할 수 있다.

## 6. 사람/AI 탐색 가이드

참조 테이블과 인라인 인용을 사람과 AI가 각각 어떻게 활용하는지.

### 사람 (소유자·리뷰어)

| 인용 유형 | 탐색 방법 |
|---------|---------|
| `` `경로` §N `` (문서) | 경로 컬럼 복사 → 에디터에서 파일 열기 → §N 섹션 이동 |
| `` `경로:줄번호` `` (코드) | 경로 복사 → 에디터 이동 → 해당 줄로 점프 |
| `[사이트명](URL)` (외부) | 렌더된 Markdown에서 링크 클릭 |
| `D-N §N` (단축 참조) | 참조 문서 테이블에서 D-N 행 확인 → 위 방법으로 원본 접근 |

### AI (후속 워커)

| 인용 유형 | 탐색 방법 |
|---------|---------|
| `` `경로` `` / `` `경로` §N `` | Read 도구의 `file_path`에 경로를 그대로 주입 |
| `` `경로:N` `` / `` `경로:N-M` `` | Read 도구의 `offset`=N, `limit`=M-N+1로 변환하여 해당 구간만 읽기 |
| `[사이트명](URL)` | WebFetch 도구에 URL을 그대로 주입 |
| `D-N §N` | 참조 문서 테이블에서 D-N 행 조회 → 경로/URL 추출 → 위 방법으로 접근 |
| `[MUST] ...` | 재해석 금지. 원문을 그대로 준수하며 하위 결정에 반영 |

## 7. 영역 간 용어 일관성 검토 + decision_required 계약

### §7.1 검출 대상 영역 쌍

워커는 다음 영역 쌍에서 동일 개념이 다른 토큰으로 사용되는지 능동 감시한다:

- FE ↔ BE (타입/필드/API 필드명 불일치)
- 정책서 ↔ 코드 (정책 용어 ↔ 변수/함수명)
- ERD ↔ 코드 (DB 컬럼명 ↔ ORM 모델 필드)
- IA ↔ FE 라우트 (화면 ID ↔ 라우트 path)

### §7.2 검출 의무

워커는 산출물 작성 중 §7.1 영역 쌍에서 **동일 개념이 다른 토큰으로 나타나는 경우** 능동 검출하여 산출물 §리스크 섹션에 기재해야 한다. "다름의 발견"은 리스크 성격으로 간주한다.

### §7.3 산출물 §리스크 기재 포맷 예시

```
| # | 리스크 | 영향 | 대응 |
|---|--------|------|------|
| R-T1 | 용어 불일치 — FE `userType` ↔ BE `subType` | API 직렬화 실패 위험 | decision_required 에스컬레이션 |
```

### §7.4 decision_required JSON 스키마

워커 반환 페이로드에 다음 형식으로 포함한다:

```json
{
  "decision_required": [
    {
      "type": "terminology_mismatch",
      "summary": "FE userType vs BE subType",
      "tokens": ["userType", "subType"],
      "areas": ["FE", "BE"],
      "source_refs": ["src/fe/types.ts:12", "src/be/models/user.py:45"],
      "suggested_resolution": "하나로 통일 (도메인 결정 필요)"
    }
  ]
}
```

### §7.5 에스컬레이션 원칙

> **[MUST]** 결정성 이슈(`type: "terminology_mismatch"` 등)는 **agentic 모드에서도 사용자 에스컬레이션 필수**이며, PM이 자율 결정하지 않는다.

## 8. 비즈니스 용어 우선 원칙 (기획 산출물)

> **[MUST]** 정책서·PRD·TRD·IA·외부 API 명세서 등 기획 산출물과 brain 페이지의 **본문은 비즈니스 용어/자연어로 서술**한다. 코드 변수·enum·식별자를 본문 서술의 주어로 나열하는 것을 금지한다.

핵심 명제: **"코드는 SSOT 근거이지 본문 서술의 주어가 아니다."**

### 8.1 적용 대상

기획/지식 산출물(비개발 트랙, §1.5) — 정책서, PRD, TRD, IA, 외부 API 명세서, 기능 시나리오/화면 흐름도, brain concept/entity/synthesis 페이지.

> ANALYSIS/PLAN/EXECUTE 등 개발 트랙 산출물은 코드 토큰을 [MUST] 포맷(§2.5)으로 직접 인용하는 것이 정상이므로 이 원칙의 강제 대상이 아니다.

### 8.2 작성 규칙

1. **코드 식별자 본문 나열 금지** — 변수·enum·컬럼·함수명을 본문 문장의 주어/서술 대상으로 쓰지 않는다.
2. **비즈니스 용어 우선** — 의미를 자연어로 서술하고, 코드 식별자는 **괄호 + 근거 인용**(`경로:줄번호`, §2.2)으로만 병기한다.
3. **조건·상태군 풀어쓰기** — enum/플래그 비교식은 의미를 풀어 쓴다.

### 8.3 자연어 변환 예시

| 코드 조건 (Bad — 본문 주어로 사용) | 비즈니스 용어 변환 (Good) | 코드 근거 병기 |
|----------------------------------|--------------------------|---------------|
| `autoSelCancelYn ≠ N` | 자동취소가 켜져 있고 | (`path/to/file:line`) |
| `basicPugCpMsnBscId ≠ null` | 기본 미션이 지정되어 있으며 | (`path/to/file:line`) |
| `AUTO_SELECT_CANCELABLE` 상태 | 자동 선택 취소가 가능한 상태 | (`path/to/file:line`) |

- **Bad**: "`autoSelCancelYn`가 N이 아니고 `basicPugCpMsnBscId`가 null이 아니면 자동 취소된다."
- **Good**: "자동취소가 켜져 있고(`a.java:120`) 기본 미션이 지정되어 있으면(`b.java:88`) 자동으로 취소된다."

### 8.4 표 작성 권장 — "조건(용어)" + "코드 근거" 분리

조건/규칙을 표로 정리할 때는 **의미 컬럼**과 **코드 근거 컬럼**을 분리한다. 코드 식별자를 의미 컬럼에 섞지 않는다.

| 조건 (비즈니스 용어) | 처리 | 코드 근거 |
|---------------------|------|----------|
| 자동취소가 켜져 있고 기본 미션이 지정됨 | 자동 취소 실행 | `path:120`, `path:88` |

- opwt 작성 워커: `opal/skills/opal-pilot-write-tech/references/network-guide.md` §7 공통 작성 원칙이 이 §8을 참조한다.
- opwt QA 워커: `opal/skills/opal-pilot-write-tech/references/consistency-rules.md` §3.1이 이 §8 위반을 검출한다.
- brain ingest 워커: `opal/skills/op-brain-ingest/SKILL.md` STEP 4 entity 작성 규칙이 §8.2(코드 식별자 본문 주어 금지)·§8.8(부록 분리)을 명문화한다.
- brain init 시드: `opal/skills/opal-brain/SKILL.md` 핵심 엔티티 시드 entity 작성 규칙이 §8.2·§8.8을 명문화한다 (소스 커버리지 부록 분리).

### 8.6 다층 근거 원칙

비즈니스 용어·결정의 근거는 코드 단층만으로 충분하지 않다. 코드(SSOT)·정책서·IA·설계 문서를 **다층 병기**한다.

**언제 적용하는가:**

- brain term 페이지 `sources` 키: 해당 용어가 정의된 근거 문서가 복수 계층(코드+정책+IA)에 걸쳐 있을 때 모두 병기한다.
- PLAN·ANALYSIS 산출물에서 비즈니스 결정을 기술할 때: 코드 참조 외에 정책 조항·화면 근거가 있으면 함께 기재한다.
- 기획 산출물(정책서·TRD·PRD) 작성 시: 동일 개념이 코드·정책·IA 세 계층에서 동시에 정의되면 세 계층 모두 `sources`에 포함한다.

**토큰 형식(SSOT):** `opal/tools/brain-tool/templates/schema-template.md` §4 링크 규칙 — `POL-{번호}` (정책참조), `ia:{system}:{screen}` (IA참조). 형식 변경은 해당 SCHEMA §4를 수정한다.

### 8.7 업무 표면(business-surface) 명명

업무 표면(surface)은 비즈니스 용어가 실제로 등장하는 화면·프로세스·접점을 가리킨다. brain term 페이지의 `surfaces` 키와 정합한다.

**명명 규칙:**

- 형식: `{system}:{screen-id}` — system은 서비스 시스템 식별자(소문자 kebab), screen-id는 IA의 화면 ID 또는 약어.
- 예시: `store-admin:order-list`, `buyer-app:checkout`, `ops-dashboard:settlement`.
- IA 문서가 있으면 해당 화면 ID를 그대로 사용한다. IA 미정 시 업무 맥락에서 의미 있는 식별자를 임시 사용하고, IA 확정 후 갱신한다.
- `ia:{system}:{screen}` 토큰(§4 IA참조)과 동일 식별자 체계를 공유한다.

### 8.8 개발자 부록 분리

기획 산출물(비개발 트랙, §1.5)에서 코드 식별자·enum·API path·레포명은 본문 주어로 사용하지 않는다(§8.2 재확인).

**강등 배치 원칙:**

- 본문에서 코드 식별자가 필요한 경우, 해당 내용을 "소스 커버리지" 또는 "개발자 부록" 섹션으로 분리하여 배치한다.
- 본문 서술 계층(의미)과 코드 참조 계층(식별자)을 문서 구조적으로 분리한다.
- brain term 페이지에서 코드 식별자를 언급해야 한다면 `sources` 키 또는 별도 "개발자 부록" 하위 섹션에만 기재한다.

### 8.9 5W1H 사고 프레임

5W1H(누가·언제·어디서·무엇을·왜·어떻게)는 ingest/query 품질을 점검하는 **사고 틀**로 사용한다.

**[MUST] 5W1H를 페이지 섹션 구조 템플릿으로 강제하는 것을 금지한다.** brain 페이지나 기획 산출물의 섹션 헤딩으로 `## 누가`, `## 왜`, `## 어떻게` 등을 배치하지 않는다.

**올바른 사용:**

- ingest 전 품질 점검: "이 용어 정의에 who(행위자)/what(의미)/why(목적)가 충분히 담겼는가?" 내부 검토 질문으로 사용.
- query 품질 점검: brain search 결과가 질문의 5W1H 요소를 충족하는지 확인하는 틀로 사용.
- 산출물 섹션 구조는 해당 스킬 SKILL.md의 섹션 템플릿을 따른다.

## 9. 근거 등급과 관할

### (a) AS-IS 근거 등급 5단계

| 등급 | 원천 |
|------|------|
| E1 | 실행 관측 — 실 DB 스키마·실제 응답·로그·테스트 실행 결과 |
| E2 | 현행 소스코드 · 통과 중인 테스트 |
| E3 | 생성 코드 — 스키마 파생(jOOQ·ORM 생성물 등) |
| E4 | 프로젝트 문서 (`docs/` 등) |
| E5 | brain · code-map — 파생 스냅샷 |

**[MUST] E1을 인용할 때는 관측 스코프와 실행 명령을 함께 기재한다.** 같은 시점의 같은 대상도 스코프가 다르면 수치가 달라지므로(예: 단일 파일 실행 vs 디렉토리 실행), 스코프 없는 실행 관측 인용은 E1로 인정하지 않는다. 근거: 본 규칙 신설 태스크에서 통과 수 스코프 누락 오류가 워커·PM·평가자 3개 층에서 독립 재발했다(098).

### (b) 관할 2축

같은 "권위 서열" 질문도 AS-IS(지금 어떻게 동작하는가)와 TO-BE(무엇이어야 하는가·왜)는 원천이 다르다. **[MUST] 소스코드는 TO-BE 근거로 최하위다** — 코드에 TO-BE를 물으면 "현행이 정답"이라는 답밖에 나오지 않아 개선·정책변경 태스크가 구조적으로 불가능해진다.

| 질문 유형 | 1순위 | 2순위 | 근거 아님 |
|-----------|-------|-------|----------|
| **AS-IS** (지금 어떻게 동작하는가) | E1 → E2 | E3 → E4 | 기억·추정 |
| **TO-BE** (무엇이어야 하는가·왜) | 소유자 결정 → 정책·요구사항 문서 | 설계 문서 | **소스코드(최하위)** |

### (c) 충돌 해소 규칙

같은 사실에 두 원천이 충돌하면 **그 사실이 생성된 지점에 가까운 쪽이 이긴다**. 스키마·타입 사실은 실 DB·생성 코드(E1·E3)가 수기 도메인 모델(E2)을 이긴다.

### (d) [MUST] 등급 외 목록

빌드 산출물·고아 화석(소스 없는 컴파일 산출물)·사람의 기억·에이전트의 추정은 근거로 인정하지 않는다.

### (e) [MUST] E5 단독 인용 금지

brain·code-map은 원천으로의 포인터이므로 E1~E4 동반 인용을 강제한다. brain은 "stale 가능 — ingest/sync 시점 스냅샷"이다(`opal/core/references/opal-pm.md` §13).

### (f) [MUST] 결정은 등급 판정 대상이 아니다

소유자의 결정은 근거가 없어도 확정이다(요구사항의 원천이므로). 단 소유자가 **사실을 진술**하면 그것은 기억이므로 E1~E4 확인 대상이다.

### (g) [MUST] 도구 자동 부여 범위 경계

도구가 경로 패턴으로 자동 부여하는 등급은 E2·E4·E5에 한정된다. E1(실행 관측)·E3(생성 코드)은 경로 패턴으로 판별 불가하므로 `unknown`으로 반환되어 PM 판단에 위임된다. 프로젝트별 매핑 설정 파일은 신설하지 않는다.

### (h) §8.6과의 경계

§8.6은 병기 *대상 선정*, §9는 병기된 원천 간 *충돌 해소* — §8.6으로 병기한 각 원천에 §9 등급을 부여한다.

### (i) 관련 문서 (중복 방지)

- 코드=SSOT 원칙: `opal/core/references/opal-pm.md` §7.
- 문서/코드 불일치 판정 절차: `opal/core/references/harness/doc-code-mismatch.md`.

**[MUST] 본 절이 근거 서열의 유일 SSOT다** — 위 문서들에 서열 규정을 복제하지 않는다.
