# Coding Principles — 코딩 행동 원칙 SSOT

OPAL 파이프라인 4단계(TASK / PLAN / TEST-SCENARIO / EXECUTE)와 QA Gate에 적용하는 코딩 행동 원칙. 코드를 작성·수정하는 모든 주체가 따른다.

---

## §1 TASK 단계 — 사전 사고

TASK 단계는 요구사항을 명확히 하고 AC(수용 기준)를 수립하는 단계다. 이 단계의 사고 규율이 하류의 재작업을 줄인다.

### 원칙

- 코드 작성 전에 전체 접근법을 계획한다.
- 모호함을 표면화한다. 추측으로 진행하지 않고 소유자에게 확인한다.
- AC는 EXECUTE **전에** 확정한다. 나중에 추가되는 AC는 사후 합리화에 불과하다.
- 인터뷰 기법으로 누락된 요구사항을 발굴한다.

### 체크

- [ ] 각 요구사항이 검증 가능한 단위(무엇을 / 어디에 / 왜 / AC)로 분해되었는가
- [ ] 각 AC가 Pass/Fail 판정 가능한 문장으로 작성되었는가
- [ ] 모호한 사항을 추측이 아닌 소유자 확인으로 해소했는가

---

## §2 PLAN 단계 — 단순성 우선

PLAN 단계는 구현 계획을 수립한다. 현재 요구사항을 만족하는 **가장 단순한 설계**여야 한다 — 그 이상은 안 된다.

### 원칙

- 영리한 설계보다 단순한 설계를 우선한다.
- 현재 요구사항이 강제할 때만 복잡성을 추가한다. 사전 추상화·미래 대비·불필요한 레이어 금지.
- 새 패턴을 도입하기 전에 중복되는 기존 패턴을 먼저 제거한다.
- PLAN은 TASK 범위를 초과하지 않는다.

### 체크

- [ ] 설계가 현재 요구사항만 해결하는가 (over-engineering 없음)
- [ ] 기존 패턴과의 일관성이 유지되는가
- [ ] 새 패턴 도입 시 중복되는 기존 패턴을 제거했는가

---

## §3 TEST-SCENARIO 단계 — 희박 케이스 분류

검증 시나리오는 발생 가능성과 영향도를 기준으로 선정한다. 발생 불가능한 케이스 방어는 금지한다.

### 희박 케이스 분류 매트릭스

| 발생 가능성 | 영향도 | 처리 |
|----------|--------|------|
| 높음 | 높음 | 시나리오 필수 (Golden Path) |
| 높음 | 낮음 | 시나리오 작성 |
| 낮음 | 높음 | 시나리오 작성 + 정당화 명시 |
| 낮음 | 낮음 | 시나리오 제외 또는 Known Issue 기록 |
| 불가능 | — | 작성 금지 (위반 시 QA Fail) |

### 체크

- [ ] 불가능한 케이스를 다루는 시나리오가 없는가
- [ ] 낮음/낮음 케이스가 무분별하게 추가되지 않았는가
- [ ] 낮음/높음 케이스에 정당화 근거가 명시되었는가
- [ ] TASK.md의 각 AC가 어느 시나리오(S-N)에 대응하는지 매핑 표가 작성되었는가

---

## §4 EXECUTE 단계 — 외과적 변경

EXECUTE 단계는 실제 파일을 생성·수정한다. 지시된 것만 건드린다.

### 원칙

- PLAN.md에 명시된 범위만 변경한다. 범위 밖 파일·구간은 수정하지 않는다.
- 인접 코드를 "개선"하지 않는다. 범위 밖에 고칠 것이 보이면 별도 태스크로 표면화한다.
- 사변적 추가를 금한다. "나중에 쓸 것 같아서" 추가하는 코드는 금지다.
- 새 패턴을 도입하기 전에 중복되는 기존 패턴을 먼저 제거한다.
- 발생 불가능한 케이스를 방어하는 코드를 추가하지 않는다.

### 체크

- [ ] PLAN.md에 명시된 파일만 변경되었는가
- [ ] 인접 코드를 개선 명목으로 수정하지 않았는가
- [ ] 사변적 추가가 없는가
- [ ] 불가능한 케이스 방어 분기가 없는가

---

## §5 QA Gate — 사후 검증

QA Gate는 EXECUTE 산출물을 위 원칙에 따라 사후 검증한다.

### 단순성 검증 (§2)

- 불필요한 추상화 레이어가 추가되지 않았는가
- 현재 요구사항 범위를 초과한 구현이 없는가
- 발생 불가능한 시나리오를 방어하는 코드가 없는가

### 외과적 검증 (§4)

- PLAN.md 범위 밖 파일이 변경되지 않았는가
- 인접 코드가 "개선" 명목으로 수정되지 않았는가
- 사변적 추가가 없는가

### 목표 지향 검증

- 모든 AC가 통과되었는가
- AC와 실제 구현 결과가 정확히 대응하는가
- AC 외 추가 clarification 없이 검증 가능했는가

각 원칙이 OPAL 단계별로 어떻게 적용되는가.

| 원칙 | TASK | PLAN | TEST-SCENARIO | EXECUTE | QA Gate |
|------|:----:|:----:|:-------------:|:-------:|:-------:|
| 사전 사고 (Think Before Acting) | ✅ 주 | ✅ 주 | — | — | — |
| 단순성 우선 (Simplicity First) | — | ✅ 설계 | ✅ 시나리오 (희박 케이스) | ✅ 구현 | ✅ 검증 |
| 외과적 변경 (Surgical Changes) | — | — | — | ✅ 주 | ✅ 검증 |
| 목표 지향 (Goal-Driven · 검증 가능 AC) | ✅ success criteria | — | ✅ verify check | ✅ verify loop | — |
