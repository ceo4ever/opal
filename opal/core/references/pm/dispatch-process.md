# PM 디스패치 전 프로세스

> 출처: opal-pm.md §3
> Lazy 트리거: 워커 디스패치 직전
> 탐색 경로: `opal/core/references/pm/dispatch-process.md`

워커에게 작업을 디스패치하기 전에 **매번** 다음 5단계를 동적으로 수행한다. 프로젝트 문서는 opi 최신화 등으로 수시로 변경되므로, 캐시하지 않고 매번 최신 상태를 확인한다.

## Step 0. 전문 에이전트 선택

`.opal/AGENT.md`의 "전문 에이전트" 섹션과 `agents.md` 매핑 테이블을 확인하여, 현재 단계+영역에 맞는 에이전트를 선택한다.

1. `.opal/AGENT.md`의 "전문 에이전트" 테이블 확인 (부트스트랩 Eager에서 이미 로드됨)
   - 테이블 있음 → 이 프로젝트에서 사용하는 에이전트와 경로를 파악
   - 테이블 없음 → agents.md 매핑 테이블로 폴백
2. 현재 단계(PLAN/EXECUTE/TEST) + 영역(FE/BE/DB/기획/공통) → 에이전트 선택
3. 프로젝트 에이전트 경로가 명시되어 있으면 → 프로젝트 에이전트 사용 (프레임워크 상속)
4. "(프레임워크 기본)"이면 → `~/.opal/agents/{에이전트명}/AGENT.md` 사용
5. 매핑 없음 → opal-task-agent (폴백)
6. PLAN 에이전트 디스패치 시: 매핑 테이블을 워커 프롬프트에 함께 주입하여 agent 필드 배정을 위임

**폴백 규칙**:
1. agents.md에 전문 에이전트 섹션 없음 → 기존 방식 (opal-task-agent + Step 1~5 전체 수행)
2. 매핑 테이블에 해당 단계/영역 없음 → 해당 단계는 기존 방식
3. 매핑 있음 → 전문 에이전트 사용

**Codex tool-backed 세션 특이사항**: Codex tool-backed 세션(모델이 도구로 자율 구동)에서 워커를 디스패치할 때는 `agents.md §Codex tool-backed 인라인 주입` 규칙에 따라 AGENT.md 본문을 `spawn_agent`의 message에 인라인 주입한다. tool-backed 세션에서는 커스텀 에이전트 이름호출이 노출되지 않으므로(이름호출 불가 — [#15250](https://github.com/openai/codex/issues/15250)) generic spawn을 사용하며, PM이 런타임에 AGENT.md 본문을 직접 주입하는 방식으로 워커를 구동한다.

전문 에이전트가 선택된 경우, Step 1~5의 문서 선별/제약 추출 범위가 해당 에이전트의 도메인으로 한정된다.

## Step 1. 문서 테이블 확인

`docs/PROJECT.md`의 프로젝트 문서 테이블을 Read하여 현재 등록된 문서 전체를 파악한다.

## Step 2. 관련 문서 선별

현재 작업과 관련된 문서를 선별한다:
- 문서 테이블의 "참조 시점" 컬럼이 현재 작업과 매칭되는 문서
- 작업 도메인(FE/BE/인프라 등)에 따른 추가 선별

## Step 3. 문서 Read + 핵심 제약 추출

선별된 문서를 직접 Read하여 핵심 제약을 추출한다.

예:
- "BaseMedia를 반드시 상속하라" (BE-FRAMEWORK.md)
- "미들웨어 체계를 준수하라" (ARCHITECTURE.md)
- "shadcn/ui 컴포넌트를 사용하라" (FRONTEND.md)

### 인용 의무 규칙

핵심 제약을 워커에게 주입할 때 다음 기준으로 **원문 인용 vs 요약**을 구분한다:

| 구분 | 기준 | 처리 방법 |
|------|------|----------|
| 원문 인용 필수 | 금지사항, 아키텍처 강제 규칙, 재해석 여지가 있는 정책·명세·도메인 규칙, **코드 컨벤션의 [MUST]/금지/네이밍 규칙 (`docs/CONVENTIONS.md` 등)** | `[MUST] <문서명> §N: <규칙 원문>` 형식으로 직접 인용 |
| 요약 허용 | 선호사항, 가이드라인, 스타일 가이드 | 요약 형태로 전달 가능 |

**인용 포맷**: `[MUST] <문서명> §N: <규칙 원문>`

예:
- `[MUST] BE-FRAMEWORK.md §3: BaseMedia를 반드시 상속하라. 직접 Model 상속 금지.`
- `[MUST] ARCHITECTURE.md §2: 미들웨어 체계를 준수하라. 커스텀 미들웨어 삽입 금지.`
- `[MUST] CONVENTIONS.md §3.1: API 응답은 camelCase를 사용한다. 직렬화 시 snake_case 금지.`

> **이유**: 경로 나열과 요약 수준의 제약 전달은 워커가 자체 판단으로 규칙을 우회할 수 있다.
> 원문을 직접 인용해야 워커가 동일한 기준을 적용한다.

## Step 4. 문서 간 종속 관계 확인

문서 내에서 다른 문서를 필수 참조하는 관계를 파악한다.

예: BACKEND.md → BE-FRAMEWORK.md (필수 참조)

종속 문서도 Step 3에서 함께 Read한다.

## Step 5. 영구 기준 판단

핵심 제약 중 일회성이 아닌 영구적 기준으로 추가해야 할 사항이 있으면, `.opal/AGENT.md` 확정 기준 추가를 소유자에게 제안한다.

## 워커 컨텍스트 주입 템플릿

위 5단계 결과를 바탕으로 워커 디스패치 프롬프트에 다음을 포함한다:

```markdown
## 참조 문서
- `docs/ARCHITECTURE.md` — 시스템 아키텍처
- `docs/CONVENTIONS.md` — 코드 컨벤션
- (추가 선별 문서...)

## 핵심 제약
- [MUST] <문서명> §N: <규칙 원문>  ← 원문 인용 필수 항목
- [MUST] CONVENTIONS.md §N: <컨벤션 강제 규칙 원문>  ← 컨벤션 [MUST]/금지/네이밍 (해당 시)
- [MUST] 증분 저장: 산출물 1개를 완결 저장한 뒤 다음 산출물로 이동한다. 말미 일괄 저장 금지.  ← 전 워커 공통 고정
- [MUST] 입력 축소: 대상 파일 전체 통독 금지. grep으로 위치를 특정한 뒤 해당 구간만 Read하고 부분 편집(Edit)한다.  ← 전 워커 공통 고정
- {선호사항 또는 가이드라인}: {설명}  ← 요약 허용 항목

## 종속 문서
- {문서 A} → {문서 B} (필수 참조)

## 문서/코드 불일치 규칙
문서와 실제 코드가 다를 경우 **코드(실질적 문서) 기준**으로 작업하고, 불일치 사항을 PM에게 보고한다.
```

> `docs/CONVENTIONS.md` 부재 시 본 항목은 자연 스킵 (Step 2 문서 선별에서 제외됨)

> **전 워커 공통 고정 2항목**(증분 저장 · 입력 축소)은 Step 2 문서 선별 결과와 무관하게 **모든 워커 디스패치에 항상 포함**한다 — 문서에서 추출한 [MUST]와 달리 근거 문서가 없는 운영 규율이다. 워커가 중단되더라도 직전 완결 산출물까지 보존되게 하는 것이 목적이며, 단계 스킬은 이 문언을 복제하지 않고 본 템플릿을 참조한다. 근거: `tasks/078-260728-opd-메모리-json전환/DONE.md` §8(완화 조합 도출 후 전량 성공), `tasks/079-260730-opds-히스토리-정정명령/DONE.md` §8(선제 적용 → 인프라 실패 0건).

## code-scan 사전 범위 파악

**코드/문서 작업 판별**: 변경·탐색 대상에 code-scan 지원 확장자(코드 파일) 또는 코드 구조 이해가 포함되면 **코드 작업**, 순수 .md 문서·기획·정책만이면 **문서 작업**.

**코드 변경·코드 탐색이 필요한 작업이면 디스패치 전 code-scan을 무조건 호출한다.** 순수 문서 작업은 이 단계를 명시적으로 스킵할 수 있다.

- `code-scan scan <scope>` 로 변경 대상 도메인/레이어 파악
- 변경 대상 파일의 domain/layer/depends 파악 → 워커 컨텍스트 주입에 활용
- scan.json 부재면 `pm/code-scan-management.md §생성 시점`에 따라 즉석 자동 생성 후 진행 (Glob/Grep 직행 금지)
- 결과 해석·폴백은 `harness/header-rules.md §code-scan 활용 가이드 §빈 결과 폴백`의 3분기를 따른다

## Step 1.5 brain 사전 지식 참조

`.opal/brain/`이 존재하는 프로젝트에서, 아래 **3시점**에 brain에서 관련 지식을 조회한다. `.opal/brain/` 없으면 각 시점을 자연 스킵 (기존 파이프라인 그대로 진행).

### 조회 시점

| 시점 | 언제 | 목적 |
|------|------|------|
| ① 작업·분석·설계 전 | PLAN 착수 전 / 구현 설계 시작 전 | 과거 아키텍처 결정·반복 패턴·설계 근거를 사전 확인하여 중복 설계 방지 |
| ② 워커 디스패치 시 | 각 Step 워커 프롬프트 작성 직전 | 해당 Step 키워드로 관련 페이지를 조회해 워커 컨텍스트에 주입 |
| ③ 사용자 질의 | 캡틴/사용자의 구체적 질문 수신 즉시 | 과거 결정·맥락을 근거로 답변 품질 향상 |

### 흐름 (3시점 공통)

1. `brain-tool search <키워드>` 실행 — 반환값은 **후보 목록**(page 경로·title·score·snippet)이며 본문은 포함되지 않는다.
2. PM이 score 상위 후보를 선별한다. 관련성이 불확실하면 사용자에게 확인 후 진행한다.
3. **선별된 페이지만** `Read`하여 본문을 워커 컨텍스트에 주입한다.
   - RAG식 전량 로드 금지 — index.md 전체 자동 로드 안 함, 선택된 페이지만 주입.
   - 워커 프롬프트의 "brain 참조" 항목 또는 "참조 문서" 항목에 포함한다.

> **원칙**: code-scan이 "무엇이 있나"를 파악하듯, brain은 "왜·어떻게 그렇게 되었나"를 파악한다. 두 단계는 독립이며 순서는 brain → code-scan (과거 맥락 먼저, 현재 구조 파악 후).
> brain `analyze`(init 동적 제안 입력)는 code-scan @header 정량 집계에 의존하므로, code-scan 보급률이 brain 지식 품질의 상한이다 (brain → code-scan 순서 유지).

## 디스패치 전 선언

워커 디스패치 직전, Observability 선언을 수행한다 (하네스 §5 참조):

> `⚙️ 워커 디스패치:` {단계명} — {워커 역할 한 줄 요약}

## Step 6. 실행 라우팅

PLAN.md §4 실행 체크리스트의 agent 필드를 참조하여 에이전트별 배치(Batch)를 구성한다.

1. PLAN.md §4 실행 체크리스트에서 각 Step의 agent 필드를 확인
2. 동일 agent의 독립 Step → 같은 Batch (병렬 가능)
3. 의존 관계가 있는 Step → 순차 배치
4. agent 필드가 없는 Step → opal-task-agent (기존 방식)
5. **산출량 상한** — 단일 디스패치가 생성·수정하는 **산출 파일이 3개를 초과하면** 파일 집합을 비중첩(non-overlapping)으로 분할하여 별도 디스패치로 배치한다. 반대로 **동일 파일을 2개 이상 Step이 변경하면 분할하지 않고 같은 디스패치에 묶어 순차 편집한다**(동시 편집 시 후행 저장이 선행 편집을 덮어쓰는 충돌 방지).
   - 임계값 3은 **관측 기반 잠정치**다 — 산출 2~3파일 배치는 완주하고 10파일 단일 디스패치는 중단된 관측에 근거하며, **4~9 구간은 미검증**이다. 확정치로 취급하지 말고, 새 관측이 쌓이면 이 수치를 갱신한다.
   - 산출 파일 수는 PLAN.md §4.2 각 Step의 `**파일**` 항목을 합집합으로 세되, 같은 경로는 1개로 계수한다.
   - 워커가 중단된 뒤의 산출물 판정·재배치 절차는 `harness/pm-review-gate.md` §워커 중단 시 산출물 실측 판정을, 동일 컨텍스트 재개 횟수 상한은 `opal-harness.md` §1 자동 루핑 제약 표를 따른다(본 항목은 산출량 기준만 소유한다).
   - StepCount ≥ 10 구간의 조건부 분할 배치 규칙은 `harness/parallel-execution.md`가 소유한다(본 절은 산출량 상한만 소유하며 배치 크기를 재서술하지 않는다).

## Step 7. 컨텍스트 슬라이싱

에이전트별로 필요한 컨텍스트만 추출하여 디스패치 프롬프트에 주입한다.

- PLAN.md §3 해당 F-NNN 섹션만 (전체 PLAN이 아닌 해당 기능 설계만)
- 도메인 문서 (에이전트별 문서 매핑 테이블 §6 참조)
- TEST-SCENARIO 해당 TS-ID만
- 선행 Batch의 changed_files (통합 Step용)
