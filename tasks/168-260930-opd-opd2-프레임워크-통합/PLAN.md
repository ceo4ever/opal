# PLAN: opd2 프레임워크 통합 — state-tool 단일 상태와 FW 공통 계약 연결

> 입력: [TASK.md](TASK.md)

## Approach

opd2(`opal-pilot-dev2`)는 자체 아티팩트 결합 해시·범위·증거·역할 분리 게이트(`opal/skills/opal-pilot-dev2/scripts/lifecycle.py:109-277`, 이하 D-11)를 이미 갖춘 독립 생명주기 엔진이다. 이 게이트 판정 로직(`Store.chain`·`fingerprint`·`scope`·`evidence`·`approvals`·`advance`, D-11:173-277)은 손대지 않는다. 바꾸는 것은 **그 판정 결과를 어디에 영속화하는가**다 — 지금은 `<task>/.sdlc/events.jsonl`(append-only journal, D-11:123-160)과 `.sdlc/state.json`(조회 사본)에만 쓰는데, 이를 FW 공통 `state-tool`의 `<task>/state.json`(D-1 `opal/tools/state-tool/state_tool.py`)이 소유하는 단일 SSOT로 옮긴다.

병행해서 (1) `state-tool`에 `opd2`를 신규 식별자로 등록하고(§2.2), (2) `opal-skills-registry.json`에 등재해 `//opd2` 트리거를 가능하게 하며(§2.2), (3) opd2 전용 `references/pipeline.json`을 신설해 기존 `STAGE_ENUM`에 매핑하고(§2.3), (4) opd2의 Coordinator/Builder/Verifier/Reviewer 호출을 FW `worker.dispatch` 이벤트 게이트를 거쳐 등록된 FW 워커에게 디스패치하도록 바꾼다(§2.4). actor 축(PM 조율)은 `opal-pilot-dev`(`opd`·`opds`) 전용 폐쇄 목록이므로(D-4 `harness/actor.md` §지원 Pilot 폐쇄 목록) opd2는 그 목록에 들어가지 않으며, Coordinator/Builder/Verifier/Reviewer라는 opd2 자체 역할 분리 구조를 FW 이벤트 게이트 밑에서 그대로 유지한다.

배포·관측(RELEASE/OBSERVE)과 actor 축 확장은 범위 밖이다(TASK §Affected users and systems 제외 항목).

## Decisions and contracts

| 결정 | 변경 후 계약 | 선택 이유·근거 |
|---|---|---|
| 상태 SSOT는 `state-tool`(A안) | opd2 태스크의 단계 상태는 `<task>/state.json`(`state-tool`) 한 곳에만 존재한다. `.sdlc/events.jsonl`·`.sdlc/state.json`·`STATE.md`(sdlc 버전)·`AGENTIC-LOG.md`(sdlc 버전)를 생성하지 않는다 | 캡틴 결정(AGENTIC-LOG.md #1). `harness/worktree.md` §실행 소유권(lease) 계약(D-5)·`harness/guards.md` §커밋 규칙(D-6)이 lease·checkpoint 판정 입력으로 `state.json`을 전제한다 |
| opd2의 기계 게이트 로직은 유지, 영속 위치만 이전 | `lifecycle.py`의 `chain`/`fingerprint`/`scope`/`evidence`/`approvals`/`advance` 판정 로직(D-11:173-277)은 바꾸지 않는다. 아티팩트 결합 해시·evidence 로그·approvals·reviews·baseline snapshot·retries 카운터는 `.sdlc/` 밖의 태스크 전용 경로(`<task>/run/opd2-ledger.json` + `<task>/run/opd2-evidence-*.log`)로 옮긴다 | AC-3가 이 게이트를 "PM이 검사를 건너뛰고 행을 완료할 수 없다"로 명시하므로 판정 자체는 재구현하지 않는다. `<task>/run/`은 이미 워크트리 태스크가 쓰는 실행 로그 캡슐(이 태스크 자신의 `run/run-log-run_*.jsonl`이 실례)이라 새 최상위 디렉토리를 만들지 않는다 |
| `Store.save()`가 매 전이마다 `state-tool mark`를 호출 | lifecycle.py 내부 전이(`INTENT→DESIGN→PLAN→BUILD→VERIFY→REVIEW→CLOSED`)가 성공할 때만 대응하는 pipeline.json 행을 `state-tool mark --task-step <key> --done`으로 완료 처리한다. `state-tool` 호출이 실패하면 lifecycle.py 쪽 전이도 커밋하지 않는다(원장 우선 커밋 후 state-tool 실패로 어긋나는 순서를 두지 않는다) | 두 저장소가 아니라 하나의 SSOT를 만드는 것이 목적이므로, 원장(게이트 증거)과 행 상태(state-tool)가 항상 같은 트랜잭션 경계 안에서 맞아떨어져야 한다. H-1 참조 |
| pipeline.json stage는 opd2 내부 6단계로 압축, `REVIEW`는 `VERIFY` stage 안의 별도 행 | `meta.stages = ["TASK","DESIGN","PLAN","EXECUTE","VERIFY","CLOSE"]`. lifecycle.py `INTENT→TASK`, `DESIGN→DESIGN`, `PLAN→PLAN`, `BUILD→EXECUTE`, `VERIFY→VERIFY`(빌더/검증자 evidence 행), `REVIEW→VERIFY`(리뷰 행), `CLOSED→CLOSE`로 매핑한다 | 캡틴 결정(AGENTIC-LOG.md #2). `STAGE_ENUM`에 `REVIEW`가 이미 있지만 `MODE_BOUNDARY_STAGES`(D-1:90-97)에도 속해 있어, 행 stage를 `REVIEW`로 두면 semi-agentic에서 리뷰 단계까지 사용자 확인 경계로 강제된다. opd2 자체 설계는 "semi-agentic: intent/spec/plan까지 사용자 검토, 이후 자율"(D-10 SKILL.md §진행 계약)이므로 리뷰를 `MODE_BOUNDARY_STAGES` 밖(`VERIFY` stage의 행)에 두어야 기존 설계와 맞는다 |
| RELEASE/OBSERVE 미지원 명시 | `delivery=release` 요청은 SKILL.md 진입 절차에서 "미지원"으로 명시 거부한다. `lifecycle.py`의 기존 `--delivery release` 경로 자체는 그대로 남겨두되(C-4, 이미 커밋된 아티팩트 계약 유지), state-tool 연동(§pipeline.json, checkpoint, CLOSE)은 build만 대상으로 한다 | TASK §Affected 제외 범위와 AC-6이 배포·관측 경로를 이번 통합에서 제외한다. 기존 SKILL.md는 "별도 배포 요청이 없으면 delivery=build로 한다"(D-10:17-18)고만 할 뿐 release 요청 시 동작을 정하지 않아 침묵을 메운다 |
| Coordinator/Builder/Verifier/Reviewer는 등록 FW 워커로 디스패치, 특화 매핑 없으면 `opal-task-agent` | 각 역할 호출 직전 `worker.dispatch` 이벤트를 load·verify하고, `opal-task-agent`(D-8 `AGENTS.md` §폴백 규칙 1 "매핑에 해당 단계/영역 없음 → 기존 방식")를 Agent 도구로 매번 새로 호출하며 `agents/*.md` 역할 문서를 프롬프트에 그대로 주입한다. 같은 역할을 위해 이전 호출의 컨텍스트를 재사용하지 않는다(Builder≠Verifier≠Reviewer 독립성, D-11:232-233 기존 게이트와 정합) | opd2는 FE/BE/DB 도메인 분화가 없는 범용 변경 파일럿이라 `AGENTS.md`의 전문 에이전트 매핑 테이블에 해당 조합이 없다(D-8). AC-5가 "등록된 FW 워커"·"같은 워커가 구현과 검증·리뷰를 겸하지 않는다"를 요구하므로 매번 새 Agent 호출로 독립성을 물리적으로 보장한다 |
| actor 축 미지원 유지 | `state-tool`의 `NEW_TASK_DEFAULTS["opd2"].actor`는 `None`(키 부재와 동일 의미, `oppd`/`oppl`/`oppb`와 같은 형태, D-1:106-108)으로 둔다. `ACTOR_SKILLS`·`harness/actor.md` §지원 Pilot 폐쇄 목록은 건드리지 않는다 | TASK §Affected users and systems가 "actor 축 지원 Pilot 목록 확장"을 명시적으로 제외했고, `harness/actor.md`(D-4) 스스로 "지원 범위를 넓히려면 별도 태스크가 필요하다"고 명시한다. opd2는 이미 자체 Coordinator/Builder/Verifier/Reviewer 역할 분리를 가지므로 actor=coordinator 대체가 필요 없다 |
| C-1을 opd2 전용 mark 가드로 확장(사용자 승인) | `state_tool.py`에 `apply_scenario_gate_mark_guard()`(D-1:6658)와 같은 위치·호출 규약의 `apply_opd2_gate_mark_guard()`를 추가해, `skill=="opd2"`이고 대상 `row.key`가 opd2 gate 키 집합(`task.intent_md`·`design.spec_md`·`plan.plan_md`·`execute.implement`·`verify.verifier_evidence`·`verify.review`)일 때 `cmd_mark`가 완료 처리 직전 형제 스크립트 `lifecycle.py verify-mark`를 호출해 통과하지 못하면 신규 오류 코드로 거부한다(`--force`·`--auto-pass`·`--as-worker` 우회 불가, 저장 전이므로 실패해도 state.json 불변). 다른 Pilot의 `NEW_TASK_DEFAULTS`·enum·행 구성·전이 동작에는 어떤 조건 분기도 추가하지 않는다 | 독립 평가자 design-rubric i2 completeness/AC-3 gap — PLAN이 게이트 판정을 `lifecycle.py` 내부로만 두면 PM이 `lifecycle.py`를 거치지 않고 `state-tool mark ... --force`를 직접 호출해 그대로 통과된다(AC-3 "PM이 검사를 건너뛰고 행을 완료할 수 없다"·"force나 auto-pass로도 우회할 수 없다" 위반). opd/opds의 `test_scenario.scenario_gate`·`plan.scenario_gate` 키에 이미 같은 패턴(형제 CLI를 호출해 실패 시 `--force`로도 못 뚫는 `scenario_gate_record_required`)이 있어(D-1:6658-6699) 신규 메커니즘이 아니라 기존 패턴의 pilot-scoped 확장이다. 이 확장은 C-1의 문자 그대로의 범위("opd2 식별자·신규 기본값 등록")를 넘어서므로 이 세션에서 사용자에게 직접 확인했고, 사용자가 "C-1을 확장해 opd2 전용 mark 가드 추가"를 선택했다(AskUserQuestion 응답, 2026-09-30) |
| lifecycle.py 전이 ↔ state.json 행 매핑을 명시 | 아래 표를 W-4·W-5 구현의 단일 기준으로 삼는다. `task.user_confirm`·`design.user_confirm`·`plan.user_confirm`은 `lifecycle.py`가 직접 mark하지 않는다 — agentic은 state-tool의 `auto_approve_prior_user_confirmations()`가 다음 행 mark 시 자동 승인하고, semi-agentic은 이 세 행이 `MODE_BOUNDARY_STAGES`에 속해 자동 승인이 거부되므로 Coordinator가 사용자 검토를 받은 뒤 `state-tool mark ... --owner user --done`으로 명시 완료한다. `close.docs_sync`~`close.final`은 `lifecycle.py`가 아니라 opd/opds CLOSE 단계와 동일하게 Coordinator가 직접 수행·mark한다.<br>`INTENT→DESIGN`→`task.intent_md`, `DESIGN→PLAN`→`design.spec_md`, `PLAN→BUILD`→`plan.plan_md`, `BUILD→VERIFY`→`execute.implement`, `VERIFY→REVIEW`→`verify.verifier_evidence`, `REVIEW→CLOSED`→`verify.review`(+`close.done_md`, DONE.md 존재 확인과 함께) | 독립 평가자 design-rubric i2 decision_clarity/row mapping gap — 기존 PLAN은 "매 전이마다 대응 행을 mark한다"고만 하고 다대다 관계(TASK 단계 2행, CLOSE 단계 6행)의 실제 대응과 확인 행 소유 주체를 정하지 않아 구현자가 임의로 골라야 했다 |
| VERIFY stage 이벤트는 `stage.test`를 재사용 | opd2의 VERIFY stage 행(`verify.verifier_evidence`, `verify.review`) 진입 시 `events.json`에 없는 `stage.verify`를 새로 만들지 않고 기존 `stage.test`(test-cycle.md 등)를 load·verify한다 | 독립 평가자 design-rubric i2 decision_clarity/stage events gap — W-5가 "해당 `stage.*` 이벤트"라고만 하고 VERIFY stage에 대응하는 이벤트가 `events.json`에 없다는 사실을 다루지 않았다. 새 이벤트 신설은 이벤트 매니페스트 소유자(`opal/core/references/events.json`) 변경이라 이 태스크 범위(§Affected 제외 목록에 명시되지 않았으나 opd2 전용 신규 이벤트 신설도 범위 확대이므로 지양) 밖이다 |

- 실패 시: 이 태스크는 신규 브랜치 작업이라 배포·설치 롤백 대상이 없다. state-tool 연동이 실패하면 해당 커밋을 포함하지 않고 재작업한다. 이미 병합된 뒤 결함이 발견되면 `opd2` 식별자·registry 항목·pipeline.json은 additive라 제거해도 다른 Pilot에 영향을 주지 않는다(C-1).
