# PLAN: 검증 시간 단축 — 실호출 최소화·컨벤션 검사 경량화·판정 병렬화

> 입력: [TASK.md](TASK.md)

## Approach

검증 시간을 쓰는 곳 아홉 군데를 네 갈래로 나누어 처리한다. 각 갈래는 모델 판단이 필요한 부분과 결정론으로 고정할 수 있는 부분을 분리하는 방식이다.

1. **실호출 최소화(AC-1·AC-2)** — 시나리오 가이드가 에이전트 실호출을 "모델 판단 자체가 수용 기준"인 경우로 한정하고, evaluator는 기록된 결과 파일로 같은 계약을 증명할 수 있는 실호출 시나리오를 `cheaper_layer` 권고로 지적한다.
2. **설계 게이트 결정론화와 병렬화(AC-3·AC-8)** — 이전 회차 지적 조립을 `state-tool design-gate start`가 수행하고, evaluator를 설계 판정·시나리오 판정 두 호출로 나눠 한 메시지에서 동시에 디스패치한다. 두 부분 결과는 신규 `design-gate combine`이 결정론 규칙으로 기존 단일 판정과 같은 형식의 결과 파일 하나로 결합한다. `design-gate record`는 바꾸지 않는다.
3. **컨벤션 검사 경량화(AC-4·AC-5)** — 신규 도구 `convention-precheck`가 기준 커밋 대비 변경 구간을 계산하고 기계 규칙 4종을 같은 finding 스키마로 판정한다. checker는 변경 구간만 읽고 기계 규칙은 건너뛴다. 모델 finding의 변경 구간 밖 항목 제거와 최종 결합도 같은 도구가 맡는다.
4. **측정 기반 설정과 TEST 병렬(AC-6·AC-7·AC-9)** — 호출 세션과 무관한 model·effort를 평가 세트 측정 뒤 캡틴이 결정하고, 표시용 `effort: default`는 없애며 재발을 막는 시험을 둔다. TEST 병렬 실행은 실측으로 판정한다.

170에서 철회된 병렬 분리가 실패한 원인은 결합 규칙과 이전 지적 처리를 문서 산문에 흩어 두었기 때문이다. 이번에는 이 두 가지를 `state_tool.py`의 결정론 코드로 고정하고, 분리 단위·부분 결과 형식·결합 규칙을 아래 Decisions에서 먼저 확정한 뒤 문서를 쓴다.

에이전트 실호출 시험(AC-2·AC-8)은 TEST 에이전트가 Bash로 `claude -p --agent <이름>`을 실행해 수행한다. 사전 프로브에서 `claude -p --agent opal-evaluator-agent`가 이 환경에서 8초에 응답했다(설치 전에는 `--agents`로 저장소 정의를 지정한다). 따라서 서브에이전트 디스패치 권한이 없는 TEST 에이전트도 PM의 직접 수행 없이 실호출을 수행할 수 있다(C-4).

## Decisions and contracts

| 결정 | 변경 후 계약 | 선택 이유·근거 |
|---|---|---|
| D-1. 이전 지적 조립은 `design-gate start`가 한다 | `start` 성공 응답에 `previous_gaps`(문자열 배열: 설계 gaps 다음 시나리오 gaps 순서), `previous_gaps_by_scope`(`{"design": [...], "scenario": [...]}`), `previous_gaps_iteration`(선택된 회차 정수 또는 `null`)를 항상 싣는다. 선택 규칙은 `op-scenario-gate` SKILL의 기존 조회 규칙 그대로다: `design_gate.history`를 최신부터 역순 순회해 `verdict`가 `deterministic_fail`·`input_error`·`superseded`가 아닌 첫 회차 k를 고르고 `<task>/run/design-gate-i{k}.json`의 `design.gaps`와 `scenario.gaps`(문자열 항목만)를 읽는다. 그 파일이 없거나 읽을 수 없으면 더 이전 회차로 계속 간다. 파일을 읽었는데 gaps가 모두 비어 있으면 순회를 멈추고 세 필드를 `previous_gaps: []`, `previous_gaps_by_scope: {"design": [], "scenario": []}`, `previous_gaps_iteration: <그 파일의 회차 k>`로 반환한다. 끝까지 읽을 파일이 없으면 `[]`·빈 scope 둘·`previous_gaps_iteration: null`이다. 즉 `previous_gaps_iteration`은 gaps를 실제로 읽은 마지막 회차이며 읽지 못했으면 `null`이다. 같은 상태·같은 파일이면 항상 같은 응답이다 | 170이 "산문 규칙이라 PM이 매 회차 추론한다"를 문제로 지목했다(TASK Problem). 응답에 항목만 더하므로 `start`의 거부 순서·오류 코드는 그대로다(C-1) |
| D-2. gaps 항목 id 정의를 도구가 소유한다 | id = 문자열에서 첫 번째 `: ` 앞부분 전체이며 `: `가 없으면 전체 문자열이다(`opal/agents/opal-evaluator-agent/AGENT.md:124`의 정의와 같다). `state_tool.py`의 헬퍼 하나가 이 정의를 구현하고 `combine`이 사용한다 | id 정의가 evaluator 문서와 SKILL에 따로 복사되어 있던 것이 170 철회의 한 원인이었다. 도구에 하나만 둔다 |
| D-3. 판정을 `scope`로 나눈다 | evaluator `design-rubric` 입력에 `scope`를 추가한다. 값은 `design`·`scenario`·`all`이며 생략하면 `all`로 현행 단일 호출 동작과 같다. `scope: design`은 설계 4축만, `scope: scenario`는 시나리오 3축과 `advisories[]`만 채점한다. `design` 호출도 완전성 판정을 위해 `scenario_source`를 읽을 수 있으나 시나리오 축은 채점하지 않는다. 입력 `previous_gaps`는 `previous_gaps_by_scope[scope]`가 비어 있지 않을 때만 보낸다 | 설계 4축과 시나리오 3축은 서로의 점수에 의존하지 않는다(`opal/agents/opal-evaluator-agent/AGENT.md:109-126`). 이전 지적을 축 목록에서 이미 `design.gaps`와 `scenario.gaps`로 분리해 기록하므로 id 접두 해석 없이 나눌 수 있다 |
| D-4. 부분 결과 형식 | 두 호출 모두 최상위에 `input_bundle_hash`·`iteration`·`scope`·`status`를 반환한다. `scope: design` 결과는 `design: {axes: {4축 PASS|FAIL}, gaps: []}`, `resolved_gaps: []`, `advisories: []`를 가진다. `scope: scenario` 결과는 `scenario: {scores: {goal, adoption, boundary}, average, gaps: []}`, `resolved_gaps: []`, `advisories: []`를 가진다. `resolved_gaps`는 그 호출이 받은 `previous_gaps`의 id마다 `{id, status: resolved|unresolved, reason}` 한 원소씩이다. 부분 결과의 `verdict`·`rewrite_target`은 있어도 쓰지 않는다 | verdict 계산을 evaluator에서 도구로 옮겨 두 호출이 서로의 결과를 알 필요가 없게 한다 |
| D-5. 결합은 `design-gate combine`이 결정론으로 한다 | `state-tool design-gate combine <task> --iteration N --design-result <json> --scenario-result <json> --output <json>`. `state.json`을 쓰지 않는다. 검사 순서: ① 열린 시도 없음 또는 `--iteration`이 열린 시도 번호와 다름 → `design_gate_iteration_invalid` ② 각 부분 결과의 `input_bundle_hash`·`iteration`이 열린 시도와 다름·없음 → `design_gate_result_stale` ③ `scope` 값 불일치, 필수 축·점수 누락, 점수가 숫자가 아님, `resolved_gaps`의 `status`가 두 값이 아님, `resolved_gaps` id 집합이 해당 scope의 `previous_gaps_by_scope`(D-1을 현재 상태에서 다시 계산)의 id 집합과 다름 → `design_gate_partial_invalid`(신규 코드, `detail`에 사유). 통과하면 출력 파일에 단일 `design-rubric` 결과와 같은 형식을 쓴다: `input_bundle_hash`, `iteration`, `design`(설계 부분 결과의 `axes`·`gaps`), `scenario`(`scores`, `average`는 세 점수 평균을 소수 셋째 자리까지 반올림한 값, `gaps`), `resolved_gaps`(설계 쪽 다음 시나리오 쪽 순서로 이어 붙임), `advisories`(시나리오 부분 결과의 것만, 열린 시도가 refinement면 빈 배열), `verdict`, `rewrite_target`. `verdict`는 설계 4축이 모두 `PASS`(대소문자 무시)이고 세 점수가 모두 1 이상이며 평균이 1.5 이상일 때만 `pass`다. `rewrite_target`은 `pass`면 `null`, 설계 축만 미달이면 `plan`, 시나리오 점수만 미달이면 `scenario`, 둘 다면 `both`다. 표준 출력은 `{ok, output_path, verdict, rewrite_target, resolved_gaps_count}`다 | 판정 기준은 `opal/agents/opal-evaluator-agent/AGENT.md:109-126`의 Phase 1-D 규칙을 코드로 옮긴 것이라 기준은 바뀌지 않는다(C-1). `record`는 이 출력 파일을 평소처럼 읽고 자체 재계산 안전판(`state_tool.py:7285`)을 그대로 적용한다 |

## Release and recovery

- 적용 순서: P1(W-1~W-6, 서로 다른 파일이라 병렬) → P2(W-7·W-8·W-9, 서로 다른 파일이라 병렬) → P3(W-10, 측정 후 캡틴 보고) → 캡틴 결정 → P4(W-11, 결정값 기입과 배포 1회).
- 검증 범위: 결정론(`unittest` 시험 4종과 `scripts/tests` 시험 2종, 정적 문서 검사), 회귀(기존 `test_design_gate.py` 전체·`test_agent_adapter_fields.sh`), 실제 연동(실호출 시나리오 3회 — evaluator `cheaper_layer` 1회, 병렬 판정 한 쌍 1회). 측정(W-10)은 TEST가 아니라 EXECUTE의 증거이며 TEST는 보고서의 형식과 채택 판정 일관성을 확인한다.
- 실측 경계: W-10의 후보×사례 호출은 1회 실행 상한이며 실패한 호출은 결과 없음으로 기록하고 재실행하지 않는다. 소요 시간은 호출 시작부터 응답 JSON 수신까지의 벽시계다. 병렬 실호출 시나리오의 시간 기준은 두 호출의 개별 소요 합보다 전체 소요가 작은지다.
- 실패 시: W-11에서 캡틴이 후보를 모두 거부하면 두 에이전트의 `effort`는 미선언으로 두고 AC-6은 미충족으로 보고한다(C-3). 배포가 실패하면 `scripts/install-mac.sh`는 재실행이 안전하며 소스는 git에 있다. `combine`·`convention-precheck`는 새 명령이라 기존 흐름을 바꾸지 않으므로 문제 시 W-8·W-7의 문서 변경을 되돌려 기존 절차(단일 호출·전체 파일 검사)로 돌아갈 수 있다.
