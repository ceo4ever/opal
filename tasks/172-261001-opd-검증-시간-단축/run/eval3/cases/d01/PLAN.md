# PLAN: 워크트리 CLOSE에서 문서·brain·산출물 지식 반영

> 입력: [TASK.md](TASK.md)

## Approach

CLOSE 파이프라인(op-brain-ingest 디스패치 → 회고 → `worktree-tool finalize`(merge 전) → 사용자 merge 안내)은 이미 "워크트리에서 쓰고 merge 전에 귀속 커밋으로 확정"하는 순서로 올바르게 배선돼 있다. 유일하게 이 순서를 막는 지점은 `brain_tool.py`의 `require_write_root`가 명시 `--allocator-root` 없이 워크트리 cwd에서의 기본 쓰기를 전면 거부하는 가드다. 이 가드는 `harness/worktree.md` §task root와 allocator root 계약(이미 `.opal`을 task_root 쓰기 대상으로 규정)과 모순되며, task 118에서 memory-tool의 허브 전용 MEMORY 쓰기 패턴을 brain-tool에 과잉 일반화해 생긴 것으로 판단된다.

접근은 최소 침습 수정이다: `require_write_root`가 `--allocator-root` 미지정 시 워크트리 여부와 무관하게 조회(`require_brain`)와 같은 cwd 자신(task_root) 해석으로 쓰기를 허용하도록 바꾸고, `--allocator-root` 명시 경로(현재 161/162/167 백필과 oppb P5에서 쓰는 명시적 타 루트 쓰기)는 그대로 유지한다. 나머지 Work item은 이 결정을 반영하도록 문서·테스트·merge 후 안내·log/index 파일 merge 전략을 정합시키고, 이미 누락된 161/162/167 후보를 허브에 직접 백필한다. 코드 아키텍처 변경은 없다 — 가드 한 곳의 조건 축소, 문서 6건 정정(done-template.md·op-oppb-knowledge-finalize/SKILL.md·opal-pilot-dev/SKILL.md·op-brain-ingest/SKILL.md·worktree_tool.py·README.md), `.gitattributes` 1건 추가, 데이터 백필 1건이다.

`code-scan scan opal/tools/brain-tool/brain_tool.py --json` 결과: `domain: opal-brain`, `layer: util`, `exports`에 `require_write_root`·`finalize_brain_root` 포함. 같은 결과의 inline @header 설명 자체가 "회고적 학습 쓰기(add-page·update-page)는 require_write_root/finalize_brain_root가 명시 allocator_root(허브 절대 경로)만 받고 cwd 추론을 거부한다"고 현재(수정 전) 동작을 서술하고 있어, W-1에서 코드를 바꾸면 이 inline @header 설명도 같은 파일에서 함께 갱신해야 한다(`harness/header-rules.md` §갱신 시점 — 코드 변경 시 @header가 현재 사실과 어긋나면 안 된다).

## Findings

- `opal/core/references/harness/memory-learning.md` — MEMORY 전용 `--allocator-root` 계약 문구가 이번 변경과 무관하게 그대로 유효한지 확인한다.
- `docs/CONVENTIONS.md` — §266 `allocator_root 명시 전달` 규칙이 MEMORY 전용 서술이며 brain-tool을 지칭하지 않는지 확인한다.
- .opal/brain/pages/concept/worktree-task-root-allocator-root-split.md (:39 "명시 인자 없는 쓰기를 전용 오류로 막는다") — 파생 지식 스냅샷이다. 이 태스크의 Work item이 직접 고치지 않으며 CLOSE의 op-brain-ingest가 갱신 여부를 판단한다(W-5 백필 대상이 아님).

### 미확인 가정
- H-1 (oppb P5 `p5.knowledge_batch`의 pre-finalize guard(pipeline id 18)가 `.opal/brain/**` diff-0을 검사하는 구현이 `brain_tool.py`의 write-root 가드와 독립적인 별도 검사인지는 `op-oppb-knowledge-finalize/SKILL.md` 문구로만 확인했고, 그 guard의 실제 구현 코드는 이번 PLAN 조사에서 직접 열람하지 않았다.)
- H-4 (같은 brain page의 같은 구간을 두 브랜치가 서로 다른 내용으로 고치면 git이 표준 conflict marker를 낸다고 판단했지만, 실제 merge 실행 결과가 항상 그렇게 되는지는 S-12로 실측 전까지는 추정이다 — 단순 날짜 bump처럼 두 브랜치가 우연히 같은 결과로 수렴하면 git은 오히려 충돌 없이 자동 병합한다는 점은 iteration 4 실측으로 이미 확인했다.)
