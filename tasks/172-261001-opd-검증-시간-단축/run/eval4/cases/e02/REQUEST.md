# 검증 정확성 복구와 GC 효율 개선 — TASK 초안 묶음

> 상태: 제안
> 용도: 합의된 요구사항을 독립 개발 태스크로 인계하기 위한 입력. 정식 태스크 채번·실행·설계 게이트 통과를 의미하지 않는다.

## 공통 목표와 경계

실제 검사를 하지 않은 통과 판정을 제거하고, 컨벤션 체커의 불필요한 탐색·중복 검증·전체 재검사를 줄인다. 기존 실행기와 영역별 LLM 병렬 구조를 활용한다.

- 기존 검사 실행은 test-tool, 문맥 판단은 LLM 체커, 결과 통합·판정은 공통 스키마에 따른 도구가 담당한다.
- 범용 캐시, 자연어 규칙의 검사 코드 자동 변환, 파일별 규칙 메타데이터, LLM 추가 분할은 제외한다.
- 검증 요구와 제외 근거는 기존 TEST-SCENARIO 검증 계약 및 test-scenario.json의 소유 경계를 활용한다. PLAN Work items에 검증 명령 열을 신설하지 않는다. 문서와 기계 실행 증거의 연결 방식은 후속 설계 대상이다.
- 코드 변경 없이 문서만 검토한 상태다. 아래 내용은 구현 완료나 검증 완료를 주장하지 않는다.

### 결과 상태의 소유권

- test-tool 실행 결과 상태·사유 코드·의미의 정의는 A1이 한 번만 확정하고 test-tool의 계약 원문에서 관리한다. B·C·D는 이를 참조하며 자체 상태 값을 만들지 않는다. 이 초안의 미실행·설정 미완료·설치 확인 실패 등은 구분할 상황을 뜻하며 확정된 enum이 아니다.
- GC check envelope 및 최종 판정(PASS/PASS_WITH_ADVISORIES/FAIL/INCOMPLETE), test-tool 결과와 GC 판정의 대응은 `opal/core/references/harness/gc-finding-schema.md`가 소유한다. A2는 기존 판정 불일치를 수정하고, A1 결과 계약 확정 후 필요한 대응은 C·D에서 같은 원문에 반영한다.
- C는 증거의 최신성·대상 대응 조건을 소유한다. 오래된 증거는 이 조건을 만족하지 않는 사유이며 별도 실행 상태가 아니다. B의 검사 축소는 범위 기록이지 판정 값이 아니다.

### 공통 배포 완료 조건

- 배포 자산을 변경하는 각 태스크는 프로젝트 소스를 수정한 뒤 정식 install 경로로 재배포하고 배포본으로 공개 진입점을 검증한다. 소스 테스트만으로 완료하지 않는다.
- A1은 배포된 실행기·스키마·전역 템플릿과 신규 셸에서의 환경변수/설정 해석 경로를 검증한다. B는 배포된 GC 스킬을 프레임워크 소스가 없는 외부 프로젝트 환경에서 검증한다.
- 배포 명령·검증한 버전 또는 파일 식별 정보·실행 결과를 태스크 증거로 보존한다. 병렬 태스크의 공유 설치·배포는 조율한다.

## A1 TASK — test-tool 실행 정확성 복구

### 문제와 근거

- test_tool.py의 cmd_unit은 changed-files를 실행기에 전달하지 않는다 (`opal/tools/test-tool/test_tool.py:163`).
- runner는 설치 확인용 check를 실제 검사로 실행하며, 빈 실행도 ok=true가 될 수 있다 (`opal/tools/test-tool/lib/runner.py:133`).
- check의 원래 의미는 설치 확인이다 (`opal/core/references/test-tools-schema.yaml:61`). 기본 템플릿에 --version 명령이 있다 (`opal/templates/test-tools.yaml:49`).
- Python 추론 명령 ruff .은 현재 설치 도구에서 잘못된 명령이다 (`opal/tools/test-tool/lib/resolver.py:142`).

### 요구사항

0. 첫 단계에서 test-tool의 코드 및 스킬·에이전트·하위 참조 문서 소비자 목록을 확정한다. op-dev-execute, op-scenario-gate, opal-pilot-sdd, opal-pilot-project-loop, opal-evaluator-agent 등을 포함하되 이름 목록을 폐쇄 목록으로 가정하지 않는다. 소비자별 사용 서브명령·입력/출력 의존·수정 필요/영향 없음과 근거를 기록하여 이번 이관 범위를 닫는다. 문자열 참조 수를 실제 영향 소비자 수로 간주하지 않는다.
1. check=설치 확인, install=설치, run=실제 검사로 구분한다. run 누락 시 check로 대체하지 않는다.
2. 전역 템플릿·추론 출력·스키마·소비자·테스트를 함께 이관한다. 기존 사용자 설정의 check를 임의로 run으로 복사하지 않는다.
3. 요청 변경 파일과 실제 검사 범위를 구분한다. 파일 단위 검사를 지원하지 않는 도구는 실제 범위와 사유를 기록한다.
4. 미실행·설정 미완료·설치 확인 실패·검사 실패·검사 통과를 구분한다. 명시적으로 적용할 검사가 없는 경우도 근거 없이 통과시키지 않는다.
5. 명령·실행 디렉터리·설정 출처·실제 검사 범위·결과를 기록한다. 후속 증거 연결에 필요한 식별 정보는 기존 증거 체계와 중복 없이 설계한다.

### 완료 기준

- 버전 확인 성공과 빈 실행이 실제 검사 통과로 소비되지 않는다.
- 고정된 정상/위반 사례에 실제 지원 도구의 run 명령을 실행해 성공·실패 양쪽을 관측한다. mock이나 문자열 검사만으로 완료하지 않는다.
- 추론 Python lint 경로도 실제 도구로 검사한다. 검증한 도구 버전과 명령을 보존한다.
- 기존 설정·run 누락·파일 범위 지원/미지원·선행 검사 실패를 실제 공개 CLI 경로로 검증한다.
- 유효한 직접 실행 명령을 이미 check에 저장한 기존 설정의 이관 경로를 설명하고 검증한다.
- 확정한 소비자 목록 전건에 이관 또는 영향 없음 근거가 있고, 영향 있는 공개 호출 경로에서 새 결과 계약을 확인한다.

## A2 TASK — GC 판정과 프로젝트 레지스트리 정합

### 요구사항

1. PM Gate §13, conventions-hub-model, 컨벤션 검사 스킬 op-gc-convention 및 보안 검사 스킬 op-gc-security의 기준 문서 부재 동작과 판정을 gc-finding-schema에 맞춘다. 통합 보고 op-gc-report의 소비도 확인한다.
2. INCOMPLETE와 호출 파이프라인의 진행 허용을 구분한다. 기준 문서 부재로 검사를 생략하고 PASS를 만들지 않는다.
3. docs/PROJECT.md의 op-dev-plan 설명에서 현재 Work items 계약에 없는 검증 명령 정의 주장을 바로잡는다. PLAN 스키마 확장으로 문서를 맞추지 않는다.

### 근거와 완료 기준

- 근거: `opal/core/references/harness/pm-review-gate.md:99`, `opal/core/references/conventions-hub-model.md:43`, `opal/core/references/harness/gc-finding-schema.md` §6 최종 판정, `docs/PROJECT.md:90`, `opal/skills/op-dev-plan/references/plan-guide.md:26`.
- 컨벤션·보안 각각 문서 부재·advisory만 존재·blocking 존재·검사 실패 사례에서 호출자와 검사 스킬의 판정이 일치한다.
- 특히 severity=High이면서 disposition=advisory인 finding은 심각도만으로 차단하지 않는다. 검사가 완전하면 PASS_WITH_ADVISORIES, 결측이 있으면 INCOMPLETE로 구분한다.
- 레지스트리 설명이 실제 PLAN/TEST-SCENARIO 책임과 일치한다.

## B TASK — GC 빠른 완화와 전환기 계약

### 요구사항

1. 첫 단계에서 GC 스킬 3종(op-gc-security/op-gc-convention/op-gc-report), opal-pilot-gc, 두 체커 에이전트(opal-security-checker/opal-convention-checker), 이들이 실행 중 읽는 종속 참조의 후보 목록을 확정한다. 각 참조를 실행 시 읽기 / 소스 수정 지시 / 근거 인용으로 분류하고 수정 또는 유지 근거를 기록한다. 실행 참조는 배포 환경에서 읽을 수 있도록 고치고 소스 수정 지시와 근거 인용은 보존한다.
2. 누락 참조를 찾기 위한 디스크 전체 탐색, 대상 재선별, 불필요한 git 이력 조회, 임의 테스트 재실행을 금지한다.
3. 전환기 기계 검사 명령은 프로젝트가 선언한 package scripts·명시적 프로젝트 문서·프로젝트 실행 설정 등 추적 가능한 출처에서만 취한다. 충돌하거나 실행 디렉터리·범위가 불명확하면 실행하지 않고 사유를 기록한다.
4. 전환기에는 호출자가 명령·검사 범위·결과를 함께 넘긴 증거만 재사용한다. 알려진 후속 수정이나 대상 불일치가 있으면 재사용하지 않는다. 이 규칙은 C의 해시 기반 최신성 판정이 이미 구현됐다는 뜻이 아니다. 재사용할 증거가 없는 경우 3번 출처 조건을 만족하는 독립된 동일 검사 실행은 한 번으로 제한하되, 수정 후 재검사와 실패 복구는 별도 실행으로 기록한다.
5. 기계 검사가 선언되지 않았다는 이유만으로 GC 전체를 자동 INCOMPLETE로 만들지 않는다. 실제로 적용되는 필수 기준의 미검증은 숨기지 않는다. 기준 문서 부재에 대한 기존 INCOMPLETE 규칙은 유지한다.
6. 기계 검사 축소·미실행 범위와 이유를 보고한다. LLM 문맥 검사는 적용 가능한 원문 기준으로 계속한다.
7. 영역별 LLM 병렬을 유지한다. 기계 실행과 규칙 책임이 겹치지 않는 LLM 판단은 호출자가 병렬 조율한다.

### 완료 기준

- 프레임워크 소스가 없는 외부 프로젝트 환경에서 GC 실행 참조가 해석된다.
- 기록상 디스크 전체 경로 탐색, 대상 재선별, B-4의 전환기 재사용 조건을 충족한 증거의 중복 기계 실행이 없다.
- 명령 선언 있음/없음/충돌, 실제 필수 기준 미검증, 기준 문서 부재 사례를 구분한다.
- 이 단계는 행동 지침 기반 완화이며, Bash 권한 제한까지 구현하지 않았다면 실행 금지를 기계적으로 보장한다고 보고하지 않는다.

## C TASK — 검증 증거 도입과 게이트 연결

### 요구사항

- A1의 실행 계약을 기반으로 생산·보존·반환·소비를 연결한다. 기존 TEST-SCENARIO/test-scenario.json 계약을 우선 사용한다.
- 게이트는 test-tool 호출 흔적이 아니라 선언된 필수 검증과 실제 증거의 대응·완전성·현재 코드에 대한 유효성을 확인한다.
- 코드·관련 설정의 식별 정보와 검사 도중 변경 처리, 실행 제외의 사전 선언 및 검토된 변경 절차를 정의한다.
- 신규 프로젝트 초기화와 기존 프로젝트 설정 이관, 이관 전 B 동작을 명시한다. 전역/프로젝트 파일 위치만으로 증거를 인정하거나 배제하지 않는다.
- PLAN/TEST-SCENARIO가 없는 독립 GC 호출의 적용 기준도 정의한다.

### 완료 기준

- 필수 검증 누락·오래된 증거·설치 확인 출력은 게이트를 통과하지 않는다.
- 신규/기존/미이관 프로젝트의 공개 진입점에서 생산된 증거가 실제 소비된다.
- 미이관 프로젝트가 침묵한 통과나 설명 없는 일괄 차단 상태가 되지 않는다.

## D TASK — GC 결과 통합과 증분 재검사

### 요구사항과 완료 기준

- C 증거와 LLM 결과를 공통 스키마로 통합하고, 미실행과 통과를 구분한다.
- 최초 범위, 직전 검사 이후 변경 파일, 사전 선언한 추가 영향 범위와 근거, 실제 검사 범위를 기록한다.
- 실제 범위는 변경 파일과 선언 영향 범위 안에 있어야 한다. 영역 전체로 확대하면 검사 전에 사유를 남긴다.
- 변경 파일은 적용 규칙 전체를 검사하고, 미검사 파일의 이전 미해결 finding을 보존한다. 추가·삭제·이동·규칙 변경을 다룬다.
- 고정 정상/위반/수정 후 신규 위반 사례에서 finding 소실과 미완료 통과 오판이 없다.
- 재검사 대상 집합과 중복 기계 실행을 필수 지표로 삼는다. LLM 호출 수·토큰·총비용·경과 시간은 반복 측정 지표다.
- 동일 구성별 최소 5회 전후 비교를 초기 측정으로 사용하고 편차를 함께 보고한다. 30% 단축이나 +10% 시간 상한을 근거 없이 통과 기준으로 고정하지 않는다.
- 부록의 과거 관측 요약을 참고 기준선으로 보존한다. 실제 전후 평가는 동일 사례·도구 버전·실행 조건으로 새 기준선을 확보하며, 과거 집계와 직접 대응하지 않는 개선율을 계산하지 않는다. 최초 변경 전 원본 기록·추출 절차·실행별 표를 확보하고, 확보하지 못한 항목은 미확인으로 남긴다.

## 독립 읽기 전용 조사 — 과거 호출 후보 12건

- 12건은 사용자가 Claude 세션 기록에서 `test-tool/run.sh unit` 문자열을 매칭한 후보 수이며 실제 호출 수가 아니다. 원본에서 단순 언급과 중복을 제거해 실제 호출 수를 확정한다. 다른 호출 표기도 조사하여 문자열 매칭의 누락 가능성을 기록한다.
- 당시 설정·실제 명령·원본 출력·태스크 판정에 사용된 위치·별도 직접 검증을 확인한다.
- 실제 검사 / 설치 확인·빈 실행의 통과 오인 / 명시적 실패와 별도 검증 / 근거 부족으로 분류한다.

## 순서와 설계 인계

- A1, A2, B, 읽기 전용 조사는 독립 착수 가능하다. 변경 파일이 겹치면 분리하거나 순차 진행하고, 공유 설치·배포는 조율한다.
- C는 A1 실행·증거 계약 안정화 뒤 진행한다. D는 C에 의존한다.
- 프레임워크 전체의 실행 참조 경로 표준화는 별도 후속 작업이며 B를 막지 않는다.
- 각 개발 태스크는 TASK·PLAN·TEST-SCENARIO와 독립 설계 게이트로 구체화한다. 필드 이름·게이트 연결 지점·호환 처리의 세부는 설계에서 결정하며 이 초안을 구현 명세로 취급하지 않는다.

### 전달된 추출 방법과 재현 한계

- 대상은 하위 에이전트 기록 파일 중 첫 3줄에 `op-gc-convention` 문자열이 있는 파일이다. 시작과 종료는 각 파일의 첫 타임스탬프와 마지막 타임스탬프다.
- 작업 시간은 인접 이벤트의 시간 간격 중 600초 미만인 간격만 합산한다. 정확히 600초인 간격도 제외된다. 이는 사용자 제공 추출 규칙이며 원본 스크립트와 대조할 예정이다.
- 수집 기간은 보존된 기록 전체이며 가장 이른 실행은 08-30이다. 정확한 연도·마지막 기록 시각은 원본 목록에서 확인한다.
- mams는 필터를 넓혀 후보 7건을 얻었고, Edit을 10회 사용한 1건을 체커가 아닌 수정 워커로 추정해 제외하여 6건이다. 제외 판단은 확정된 역할 분류가 아니다. 원본 보존 시 확대 필터의 구체 조건, 제외 파일과 근거를 함께 보존하고 7건 포함/6건 제외의 집계 차이를 확인한다.
- 도구 호출과 반복 실행을 같은 세션 기록 및 보고서에서 집계했다. 재시도·중복·중첩 호출의 집계 규칙은 스크립트에서 확인할 항목이다.
- 이 방식으로는 Codex·Cursor 실행을 측정할 수 없다. 다른 플랫폼에는 별도 기록 어댑터 또는 공통 실행 로그가 필요하며, 플랫폼 간 수치를 직접 비교하지 않는다.
- 이 시간은 긴 중단 구간을 제외한 작업 시간 추정이다. 중단을 포함한 전체 경과 시간이나 병렬 작업 시간 합계와 혼용하지 않는다. 병렬 영역의 시간은 태스크 경과 시간 계산에서 단순 합산하지 않는다.
- D의 전후 실험 전에 개인정보·비밀값을 제외한 원본 증거와 추출 절차를 태스크에 보존하고, 실행별로 프로젝트/태스크/영역/최초·재검사 구분/시간 구간/제외 구간/도구 호출 수/검사 파일 수를 기록한다. 과거 원본을 확보하지 못하면 새 실험 기준선을 사용하고 역사적 수치에 대한 정밀 개선율 주장은 하지 않는다.
