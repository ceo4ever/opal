# PLAN: 이벤트 로딩 경량화 1차

> 입력: [TASK.md](TASK.md) | 근거: [제안서](../../docs/proposals/opal-event-loading-economy.md)

## Approach

`event-loader`가 소유하는 `worker.dispatch` 계약을 둘로 나눈다. 새 계약(버전 2)은 호출자가 대상 에이전트·역할·디스패치 식별자·계약 버전을 모두 넘길 때만 성립하며, 응답 본문에서 대상과 무관한 에이전트 항목을 제거하고 receipt를 호출에 묶는다. 구형 계약(인자 없음)은 전환 기간 동안 전체 전송·경고·구형 검증 표시로만 남는다. 모든 이벤트의 load 응답은 본문을 `documents`에 한 번만 싣는다.

구현은 네 덩어리다. (1) 절 경계를 코드 펜스 바깥 헤딩으로만 판정하는 선별 모듈, (2) 매니페스트의 계약·선별 선언, (3) `event_loader.py`의 load·verify·측정·정적 검사·구형 추적, (4) 인자를 전달하는 소비자(state-tool, 에이전트 16종, PM·파일럿·README 문서). 호환 종료 자체(구형 호출을 거부로 바꾸는 매니페스트 한 줄)는 이 태스크가 만드는 판정 도구로 이후 수행하며 이번 범위에서 실행하지 않는다.

## Findings

### 직접 변경
`event-loader`의 load·verify 흐름(`opal/tools/event-loader/event_loader.py`)이 본문을 `documents`와 `required_documents`·`optional_documents`에 중복 담고(272-313행), verify는 문서 경로·해시·합계만 대조한다(332-391행). 이 둘과 새 선별 모듈(`opal/tools/event-loader/agent_sections.py`), 매니페스트(`opal/core/references/events.json`)의 `worker.dispatch` 선언, `state-tool event-verify` 위임부(`opal/tools/state-tool/state_tool_parts/gates.py`, 인자 선언은 `opal/tools/state-tool/state_tool_parts/cli.py`)와 그 표면 고정 파일(`opal/tools/state-tool/tests/fixtures/state_tool_surface.json`)이 바뀐다. `worker.dispatch` 진입 게이트를 가진 에이전트 16종(`opal/agents/*/AGENT.md`)의 verify 줄과 하위 디스패치 3종의 load 줄이 바뀐다.

code-scan 결과(`code-scan scan --json`) 인용: `opal/tools/event-loader/event_loader.py`는 module `event_loader`, layer `util`, domain `opal-tools`, exports `main`·`load_event`·`verify_receipt`·`static_check`·`measure_event`·`compose_project_brief`·`project_brief`다. `opal/tools/state-tool/state_tool_parts/gates.py`는 module `state_tool_parts.gates`, layer `util`, domain `opal-pipeline`, exports `cmd_verify`·`cmd_event_verify`·`cmd_design_gate_start`·`cmd_design_gate_combine`이며 `cmd_event_verify`가 loader를 서브프로세스로 호출한다(depends: event-loader). 새 모듈 `agent_sections`는 domain `opal-tools`·layer `util`로 표준 라이브러리만 쓰고 `event_loader`가 이를 import한다.

### 회귀 확인
`session.*`·`pm.activate`·`stage.*`·`pilot.start` 이벤트의 load는 본문 중복 제거 외에는 같아야 한다(`opal/tools/event-loader/run.sh`가 호출하는 경로). `state-tool`의 다른 서브명령과 `design-gate`는 건드리지 않는다(`opal/tools/state-tool/state_tool_parts/commands_core.py`의 `is_worker_dispatch_row`는 이벤트 로딩과 무관한 상태 행 판정이다). 설치 스크립트(`scripts/install-mac.sh`)는 도구 디렉터리를 통째로 배포하므로 새 모듈 파일 추가에 별도 변경이 없는지만 확인한다.

### 문서 갱신
호출 형식이 서술된 곳만 바꾼다: `opal/core/references/pm/dispatch-process.md`(Step 0 순서와 `[WORKER]` 템플릿), `opal/core/references/agents.md`(머리말의 전문 적용 문장), `opal/core/references/opal-pm.md`(§3 디스패치 전 프로세스 문장), `opal/skills/opal-pilot-dev2/SKILL.md`(§worker.dispatch 이벤트 게이트), `opal/tools/event-loader/README.md`, `opal/tools/opal-agent/README.md`(헤드리스 워커 receipt 문장). 컨텍스트 주입·관측성·시나리오 게이트·actor 문서는 `worker.dispatch`를 이름으로만 언급하고 호출 형식을 서술하지 않아 변경하지 않는다.

## Decisions and contracts

| 결정 | 변경 후 계약 | 선택 이유·근거 |
|---|---|---|
| D-1. 응답 형식 | 모든 이벤트의 load 응답은 최상위 `response_version: 2`를 갖고, 본문은 `documents[].content`에만 담는다. `required_documents`·`optional_documents`는 `id`·`token`·`path`·`sha256`·`bytes`만 담는다. 이벤트별 receipt의 `schema_version`은 `worker.dispatch` 새 계약만 2이고 나머지는 1을 유지한다 | 저장소에서 두 배열의 본문을 읽는 소비자는 event-loader 자신뿐이다(제안서 §2.2). 부트·단계 소비자는 `documents[].content`만 읽는다 |
| D-2. 계약 버전 선언 | 매니페스트의 `worker.dispatch` 선언에 `contract: {"current": 2, "supported": [2], "legacy_accepted": true}`를 둔다. 소비자는 호출마다 `--contract-version 2`를 넘기고 loader가 `supported` 포함 여부를 판정한다. 호환 종료는 `legacy_accepted`를 `false`로 바꾸는 한 줄이다 | 선언이 매니페스트 한 곳이라 종료 시점이 코드 수정 없이 결정론으로 바뀐다. 파일럿 SKILL 본문에는 선언하지 않고 호출 예시에서 인자로만 전달한다 |
| D-3. 새 계약의 필수 인자 | `load`·`verify` 모두 `--contract-version`·`--agent`·`--role`·`--dispatch-id` 네 개가 필요하다. 하나라도 없으면 `contract_args_missing`으로 거부하고 구형으로 전환하지 않는다. `--role-doc <경로>`는 선택이며 주면 receipt에 경로·해시가 기록되고 verify에서도 같은 값을 받아야 한다. `--role`은 `^[a-z][a-z0-9_-]*$`, `--dispatch-id`는 `^[A-Za-z0-9][A-Za-z0-9._-]{7,63}$`를 따른다 | 제안서 §4.1·§4.2. 형식 위반은 `contract_arg_invalid`로 거부한다 |
| D-4. 디스패치 식별자 발급 | 호출하는 쪽(PM 또는 하위 디스패치 에이전트)이 워커 호출마다 새 불투명 문자열을 만들어 load·verify·`[WORKER]` 프롬프트에 같은 값을 넣는다. loader는 값을 저장하거나 유일성을 보장하지 않고 receipt 기록과 verify 인자의 일치만 판정한다 | run-log의 `worker_run_id`는 Agent 호출 뒤에 생기므로 load 시점에 쓸 수 없다. state-tool 발급은 하위 디스패치(headless) 경로가 상태 파일 없이도 동작해야 한다는 제약과 충돌한다 |
| D-5. 에이전트 문서 해석 | `--agent`는 `{프로젝트}/.opal/agents/<이름>/AGENT.md`를 먼저, 없으면 프레임워크 문서를 쓴다. 프레임워크 문서는 소스 실행 시 `{source_root}/opal/agents/`, 설치본 실행 시 `{deployed_root}/agents/`다. 어느 쪽에도 없으면 `agent_not_found`다. receipt의 `agent`에 `name`·`path`·`sha256`·`origin`(`project` 또는 `framework`)을 기록하고, verify는 같은 규칙으로 다시 해석해 경로·해시·출처 중 하나라도 다르면 `agent_changed`로 거부한다 | 제안서 §4.1, `agents.md` 탐색 경로 |
| D-6. 선별 선언 | 매니페스트의 `worker.dispatch` 선언에 `selection`을 둔다: 대상 문서 id `agent-registry`, 모드 `agent_entries`, 제외 절 제목 `에이전트 추가 가이드`·`향후 추가 에이전트`, 전체 항목 제공 에이전트 `opal-plan-agent`·`opal-task-action-agent`·`opal-sdd-action-agent`·`opal-loop-action-agent`. 에이전트 항목은 코드 펜스 바깥의 H3 헤딩 중 첫 토큰이 `^[a-z][a-z0-9]*(-[a-z0-9]+)*-(agent|checker)$`인 것이다. 대상 항목은 첫 토큰이 `--agent` 값과 같은 항목이다. 대상 항목이 레지스트리에 없는 에이전트(프로젝트 전용)는 항목 0개로 처리하고 `selection.target_entry`를 `absent`로 응답에 표시하되 거부하지 않는다 | C-2·C-3. 담당 배정 역할은 매핑 테이블 선택이 필요하고, 하위 디스패치 3종은 자기가 부를 에이전트를 고르므로 전체 항목을 받는다 |
| D-7. 절 경계 | 헤딩은 줄 시작의 `#{1,6} `이며, 줄 시작이 ```로 시작하는 줄 사이(여는 펜스 이후 같은 길이 이상의 닫는 펜스까지)에 있는 줄은 헤딩이 아니라 본문으로 취급한다. 절은 다음 같은 수준 이하 헤딩(펜스 바깥)에서 끝난다. 제외 절은 해당 H2 제목과 하위 전체를 뺀다 | C-3. `agents.md` §프로젝트 전문 에이전트 생성의 예시 블록과 §향후 추가 에이전트의 템플릿 블록 안 헤딩이 절로 유출되지 않는다 |
| D-8. receipt 새 필드(계약 2) | `schema_version: 2`, `contract_version`, `load_id`(load마다 새 32자리 16진수), `dispatch_id`, `agent`(D-5), `role`, `role_doc`(없으면 `null`), `selection`(제외·유지 절 id와 바이트), `body_sha256`, `payload_bytes`(실제 전달 본문 합계), `source_payload_bytes`(선별 전 전체), `response_bytes`. 문서 항목은 `sha256`·`bytes`를 **전달한 내용**의 값으로, `source_sha256`·`source_bytes`를 원본 파일의 값으로 기록한다. `body_sha256`은 `documents` 순서대로 `<id>`+NUL+`<전달 내용>`+NUL을 이어 붙인 UTF-8의 sha256이다. `response_bytes`는 `response_bytes` 필드를 0으로 둔 응답 JSON의 UTF-8 길이다 | 제안서 §4.1, AC-3·AC-5 |
| D-9. 새 계약 verify | `--receipt`는 load 응답 전체 파일이어야 한다(`documents[].content` 없으면 `response_body_missing`). verify는 (a) 필수 인자 네 개 유무 (b) 인자와 receipt의 대상·역할·역할 문서·식별자·계약 버전 일치 (c) 응답 파일의 각 `content`가 receipt의 `sha256`과 일치하고 `body_sha256`이 재계산 값과 같음 (d) 같은 규칙으로 선별을 다시 수행한 전달 내용과 receipt 해시 일치 (e) 에이전트 문서 재해석(D-5) (f) 기존 매니페스트·문서 최신성 검사 순으로 수행하며 첫 실패에서 거부한다. 오류 코드: `contract_args_missing`·`contract_arg_invalid`·`unsupported_contract_version`·`contract_mismatch`·`dispatch_target_mismatch`·`dispatch_role_mismatch`·`dispatch_id_mismatch`·`body_hash_mismatch`·`agent_changed`·`response_body_missing`·`agent_not_found` | AC-3 |
| D-10. 구형 호환 | 계약 인자 네 개가 모두 없고 `legacy_accepted`가 `true`일 때만 구형이다. load는 전체 문서(선별 없음)와 `schema_version: 1` receipt를 돌려주고 응답에 `warnings: [{"code": "legacy_dispatch_contract", ...}]`와 `contract: "legacy"`를 넣는다. verify는 `schema_version: 1`이고 계약 인자가 없으면 기존 규칙으로만 검증하고 결과에 `contract: "legacy"`·`legacy_verified: true`·같은 경고를 낸다. 일부 인자만 있으면 `contract_args_missing`이다. 계약 인자가 있는데 receipt가 1이면 `contract_mismatch`, 인자가 없는데 receipt가 2면 `contract_args_missing`이다. `--contract-version`이 `supported` 밖이면 `unsupported_contract_version`(설치 후 재로드 안내 포함). `legacy_accepted`가 `false`면 구형 load는 `legacy_dispatch_rejected`, 구형 receipt verify는 `legacy_receipt_rejected`로 거부한다 | AC-4, C-4. 실행 중이던 세션은 읽어 둔 구형 지시로 계속 호출하므로 전환 기간에는 막지 않는다 |
| D-11. 구형 호출 추적 | 구형 load·verify마다 `{ts(ISO8601, UTC), op, event, project_root}` 한 줄을 JSONL에 추가한다. `ts`는 환경변수 `OPAL_EVENT_LOADER_NOW`(ISO8601)가 있으면 그 값, 없으면 현재 UTC 시각이다(시험이 시각을 고정하는 용도). 경로는 환경변수 `OPAL_EVENT_LOADER_LEDGER`가 있으면 그 값, 없으면 `{deployed_root}/state/event-loader/legacy-dispatch.jsonl`이다. 쓰기 실패는 호출을 막지 않고 응답 `warnings`에 `ledger_write_failed`를 더한다. 새 서브명령 `legacy-report [--since <ISO8601>] [--until <ISO8601>]`가 구간 내 건수·첫/마지막 시각·op별 건수를 출력한다 | AC-4. receipt는 호출자가 보관하는 파일이라 집계할 수 없으므로 loader가 직접 남긴다 |
| D-12. 호환 종료 판정 구간 | 전환 기준 시점은 이 변경이 `~/.opal`에 설치된 시각이다(설치 후 운영 기록에 남긴다). 종료 조건 3(제안서 §4.2)의 "구형 호출 0건"은 `legacy-report --since <전환 기준 시점>`의 건수가 0이고 기준 시점부터 판정 시점까지 연속 168시간(7일) 이상 경과한 경우다. 조건 1(소스 구형 호출 0건)은 `static-check`, 조건 2(직접·하위 검증 시나리오 통과)는 이 태스크의 시나리오 결과가 증거다 | C-4. 누적 총량이 아니라 기준 시점 이후 관측 구간으로 판정한다 |
| D-13. 측정 | `measure`는 `--agent --role --dispatch-id --contract-version`을 받으면 그 호출의 `payload_bytes`·`source_payload_bytes`·`response_bytes`를 따로 출력한다. 새 서브명령 `load-report --receipt <경로>...`는 receipt 파일들을 읽어 `load_id` 기준으로 중복을 제거한 뒤 `payload_bytes`와 `response_bytes` 합계를 각각 출력하고 verify 결과 파일(`command: verify`)은 건너뛴다. 비용·시간은 loader가 만들지 않고 opst·run-log 결과를 결과 자료의 별도 열에 둔다 | AC-5. 재검증은 `load_id`가 같아 한 번만 센다 |
| D-14. 정적 검사 | `static-check`는 `worker.dispatch` 소비자 파일에서 `--event worker.dispatch`와 `load` 또는 `verify`가 함께 있는 줄이 `--contract-version`·`--agent`·`--role`·`--dispatch-id`를 모두 담지 않으면 `dispatch_contract_args_missing`(누락 인자 목록 포함)을 낸다. `opal/agents/<이름>/AGENT.md`의 verify 줄에서 `--agent` 값이 `<`로 시작하지 않는데 폴더 이름과 다르면 `dispatch_gate_agent_mismatch`를 낸다. 코드 펜스 안 헤딩이 절로 선별되지 않는지는 `static-check`가 아니라 테스트가 소유한다. `worker.dispatch` 소비자 경로에 `opal/core/references/pm/dispatch-process.md`를 추가한다 | 제안서 §3.2·§4.2. 16종 게이트 문장은 에이전트가 다른 문서를 읽기 전에 실행해야 하므로 공통 문서 참조로 줄이지 않고 인라인을 유지하며 드리프트를 이 검사로 막는다 |

## Release and recovery

- 적용 순서: P1(W-1, W-2) → P2(W-3) → P3(W-4, W-5, W-6). 소스 상태에서 단위 테스트와 `event-loader static-check`(매니페스트 전체·`worker.dispatch` 소비자)를 통과시킨 뒤 `scripts/install-mac.sh`로 배포한다. 배포는 TEST 단계 실호출과 설치본 측정에 필요하며, 배포 시각을 전환 기준 시점(D-12)으로 기록한다.
- 검증 범위: 결정론(선별·receipt·오류 코드·원장·정적 검사 단위 테스트), 소비자(state-tool 전달, 에이전트 문서 정적 검사), 회귀(기존 event-loader·state-tool 테스트 전체), 실제 연동(설치본 loader로 대상 2종 이상 load·verify, 하위 디스패치 경로 1회). 로드량은 문서 본문 합계·실제 응답 바이트(`response_bytes`)를 따로 출력하고, 비용·시간은 opst·run-log 값을 결과 자료의 별도 열에 둔다. 측정 시작·종료는 load 호출 시작부터 verify 통과까지로 하고 재검증은 `load_id`로 한 번만 센다.
- 설치본 loader 결함 복구: 배포 직후 `session.assistant`·`pm.activate`·`stage.plan` load와 `static-check`를 설치본에서 먼저 실행하고, 하나라도 실패하면 즉시 이 변경 커밋을 `git revert`한 뒤 `scripts/install-mac.sh`로 재설치한다. 재설치 후 같은 세 load와 `static-check`가 성공하는지 확인한다. 배포 전 설치본 디렉터리(`~/.opal/tools/event-loader`)는 `.bak` 사본으로 보존해 재설치 실패 시 복원 수단으로 쓴다. 이 복구는 사용자가 설치를 승인한 시점에만 수행한다.
- 실패 시: 배포 전에는 소스 변경을 되돌린다. 배포 후 문제는 매니페스트의 `legacy_accepted`가 `true`인 채이므로 인자 없는 구형 호출이 계속 동작하며, 새 계약 소비자 문서만 되돌리면 복구된다. 구형 거부(호환 종료)는 이번 범위에서 켜지 않는다.
