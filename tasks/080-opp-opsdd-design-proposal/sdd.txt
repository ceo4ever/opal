- 광고비 현황 진행중

2) 개발

SDD는 **Spec-Driven Development**, 즉 **명세 중심 개발 방법론**입니다. 코드를 먼저 쓰는 대신, 먼저 요구사항과 설계를 명확한 명세로 정리하고 그 명세를 기준으로 구현과 검증을 진행합니다. [goddaehee.tistory](https://goddaehee.tistory.com/405)

## 핵심 흐름
보통 SDD는 다음 순서로 진행됩니다:  
1. **Requirements / Spec**: 사용자 스토리와 수용 기준을 정리합니다.  
2. **Design**: 아키텍처, 데이터 모델, 구현 방식을 설계합니다.  
3. **Tasks**: 실제 작업 단위로 분해해 실행합니다. [yozm.wishket](https://yozm.wishket.com/magazine/detail/3477/)

## 왜 쓰나
SDD의 목적은 “무엇을 왜 만드는지”가 코드에 묻히는 문제를 줄이고, 명세를 **단일 진실 소스**로 삼아 일관성과 추적성을 높이는 데 있습니다. AI 코딩 환경에서는 환각이나 즉흥적인 구현을 줄이고, 요구사항 범위 안에서 개발을 통제하는 데 특히 유용합니다. [news.hada](https://news.hada.io/topic?id=27675)

## TDD와 차이
- **TDD**: 테스트를 먼저 작성하고, 테스트를 통과하는 코드를 만듭니다.  
- **SDD**: 명세를 먼저 작성하고, 그 명세를 만족하는 코드를 만듭니다. [tsyang.tistory](https://tsyang.tistory.com/224)

## 한 줄로 정리
SDD는 **“코드보다 먼저 명세를 만든다”** 는 개발 방식입니다. [palms](https://palms.blog/beyo/ssd-spec-driven-development)

원하시면 제가 이어서 **SDD와 TDD 차이**, **SDD 실제 적용 예시**, 또는 **GitHub Spec Kit/Kiro 기준 워크플로우**까지 한국어로 쉽게 정리해드릴게요.



SDD에서 `spec.md`는 **“무엇을 만들지”를 가장 먼저 고정하는 핵심 문서**입니다. 보통 **요구사항, 사용자 시나리오, 수용 기준**을 중심으로 작성하고, 구현 방법보다는 의도와 동작을 명확히 적습니다. [javaexpert.tistory](https://javaexpert.tistory.com/1425)

## 일반적인 구성 항목
보편적으로 `spec.md`에는 다음 항목이 들어갑니다. [genon](https://www.genon.ai/resources/blog/spec-kit-%EB%AA%85%EC%84%B8-%EA%B8%B0%EB%B0%98-%EA%B0%9C%EB%B0%9C%EC%9D%84-%ED%99%9C%EC%9A%A9%ED%95%9C-%EB%B0%94%EC%9D%B4%EB%B8%8C-%EC%BD%94%EB%94%A9)

- **기능 개요**
- **목표 / 비목표**
- **사용자 스토리**
- **요구사항**
- **수용 기준**
- **예외 / 에러 처리**
- **보안 / 권한**
- **성능 / 제약 조건**
- **검증 기준 또는 Done 기준**

## 많이 쓰는 구조
실무나 Spec Kit 계열 워크플로우에서는 `spec.md`를 아래처럼 쓰는 경우가 많습니다. [github](https://github.com/github/spec-kit/blob/main/spec-driven.md)

1. **Background / Context**
   - 왜 이 기능이 필요한지
2. **User Stories**
   - `As a ... I want ... so that ...`
3. **Functional Requirements**
   - 반드시 동작해야 하는 기능
4. **Acceptance Criteria**
   - `GIVEN / WHEN / THEN` 형태
5. **Edge Cases**
   - 예외 상황, 실패 케이스
6. **Non-functional Requirements**
   - 성능, 보안, 접근성, 확장성
7. **Constraints**
   - 기술적/정책적 제한
8. **Open Questions**
   - 아직 결정되지 않은 사항

## 예시
예를 들어 “실시간 채팅” 기능의 `spec.md`라면, 다음처럼 적습니다. [yozm.wishket](https://yozm.wishket.com/magazine/detail/3477/)

- 사용자는 채팅방에 입장할 수 있어야 한다.
- 사용자는 메시지를 실시간으로 전송하고 수신할 수 있어야 한다.
- 메시지 전송 실패 시 재시도 또는 오류 안내가 표시되어야 한다.
- 채팅 기록은 새로고침 후에도 유지되어야 한다.

## 작성 팁
`spec.md`는 **코드 설명서가 아니라 제품의 의도 문서**에 가깝습니다. 그래서 클래스명, 함수명, DB 테이블 같은 구현 세부사항보다, **사용자가 무엇을 경험해야 하는지**와 **성공이 어떻게 판정되는지**를 쓰는 게 좋습니다. [ykss.netlify](https://ykss.netlify.app/translation/2026/how-to-write-a-good-spec-for-ai-agents/)

원하시면 제가 바로 **`spec.md` 템플릿**을 한국어 마크다운 형식으로 만들어드릴게요.


아래처럼 `spec.md`를 **실제 문서처럼 바로 쓸 수 있는 예시 코드**로 작성하면 됩니다. `spec.md`는 보통 **무엇을 만들지, 어떤 조건을 만족해야 하는지**를 적고, 구현 세부는 뒤 단계에서 다룹니다. [genon](https://www.genon.ai/resources/blog/spec-kit-%EB%AA%85%EC%84%B8-%EA%B8%B0%EB%B0%98-%EA%B0%9C%EB%B0%9C%EC%9D%84-%ED%99%9C%EC%9A%A9%ED%95%9C-%EB%B0%94%EC%9D%B4%EB%B8%8C-%EC%BD%94%EB%94%A9)

```md
# Chat Room Feature Spec

## Background
사용자는 여러 명이 동시에 대화할 수 있는 실시간 채팅 기능이 필요하다.

## Goals
- 사용자가 채팅방에 입장할 수 있어야 한다.
- 사용자가 메시지를 보내고 받을 수 있어야 한다.
- 새로고침 후에도 채팅 기록이 유지되어야 한다.

## Non-goals
- 음성/영상 통화는 지원하지 않는다.
- 파일 업로드는 이번 범위에 포함하지 않는다.

## User Stories
- 사용자는 채팅방 목록을 보고 원하는 방에 들어갈 수 있다.
- 사용자는 입력창에 메시지를 작성해 전송할 수 있다.
- 사용자는 다른 사람이 보낸 메시지를 실시간으로 확인할 수 있다.

## Functional Requirements
1. 사용자는 인증 후 채팅방에 입장할 수 있어야 한다.
2. 메시지는 전송 즉시 화면에 반영되어야 한다.
3. 메시지 전송 실패 시 오류 안내가 표시되어야 한다.
4. 채팅 기록은 서버에 저장되어야 한다.
5. 사용자는 이전 메시지를 스크롤로 불러올 수 있어야 한다.

## Acceptance Criteria
- GIVEN 사용자가 채팅방에 입장했을 때
  WHEN 메시지를 입력하고 전송하면
  THEN 메시지가 본인 화면과 다른 사용자 화면에 표시되어야 한다.

- GIVEN 네트워크 오류가 발생했을 때
  WHEN 사용자가 메시지를 전송하면
  THEN 실패 메시지 또는 재시도 안내가 보여야 한다.

- GIVEN 사용자가 페이지를 새로고침했을 때
  WHEN 채팅방으로 다시 들어오면
  THEN 이전 대화 내역이 유지되어야 한다.

## Edge Cases
- 빈 메시지는 전송할 수 없다.
- 너무 긴 메시지는 제한한다.
- 동시에 같은 방에 여러 사용자가 입장할 수 있다.
- 메시지 전송 순서가 꼬이지 않도록 처리한다.

## Constraints
- 반응 속도는 1초 이내를 목표로 한다.
- 모바일 화면에서도 정상 동작해야 한다.
- 접근성 기본 기준을 만족해야 한다.

## Open Questions
- 메시지 수정/삭제를 지원할 것인가?
- 읽음 표시가 필요한가?
- 익명 채팅을 허용할 것인가?
```

## 작성 포인트
이런 형태가 좋은 이유는 `spec.md`가 **사용자 스토리와 기능 요구사항 중심**으로 구성되기 때문입니다. 또 Spec Kit류 워크플로우에서는 `spec.md`를 기준으로 이후 `plan.md`, `tasks.md`를 만들기 때문에, 명세가 모호하면 뒤 단계도 흔들립니다. [aspdotnet.tistory](https://aspdotnet.tistory.com/3454)

## 더 실무적으로 쓰는 버전
프로젝트에 따라 아래 항목을 추가하면 더 좋습니다.

- **API 계약**
- **데이터 모델**
- **보안 요구사항**
- **로그/모니터링**
- **테스트 기준**

원하시면 제가 다음 답변에서 바로 **“로그인 기능용 spec.md 예시”** 또는 **“웹서비스용 spec.md 템플릿”**으로 바꿔드릴게요.


아래처럼 `spec.md`를 만든 뒤, **체크리스트 기반으로 검증하는 스크립트**를 둘 수 있습니다. Spec Kit 계열 문서에서는 `spec.md`가 준비된 뒤 체크리스트를 통해 요구사항 완성도와 준비 상태를 확인하는 흐름이 소개됩니다. [deepwiki](https://deepwiki.com/github/spec-kit/4-spec-driven-development-workflow)

## 예시 검증 스크립트
```python
#!/usr/bin/env python3
import re
import sys
from pathlib import Path

SPEC_PATH = Path("spec.md")
REQUIRED_SECTIONS = [
    "Background",
    "Goals",
    "Non-goals",
    "User Stories",
    "Functional Requirements",
    "Acceptance Criteria",
    "Edge Cases",
    "Constraints",
    "Open Questions",
]

def load_spec():
    if not SPEC_PATH.exists():
        print(f"ERROR: {SPEC_PATH} not found")
        sys.exit(1)
    return SPEC_PATH.read_text(encoding="utf-8")

def check_sections(text):
    missing = []
    for section in REQUIRED_SECTIONS:
        pattern = rf"^##\s+{re.escape(section)}\s*$"
        if not re.search(pattern, text, flags=re.MULTILINE):
            missing.append(section)
    return missing

def check_minimum_content(text):
    issues = []

    if "NEEDS CLARIFICATION" in text:
        issues.append("Spec still contains NEEDS CLARIFICATION markers.")

    if len(re.findall(r"^-\s+", text, flags=re.MULTILINE)) < 5:
        issues.append("Not enough bullet-point requirements found.")

    ac_count = len(re.findall(r"^\s*-\s*GIVEN\s+", text, flags=re.MULTILINE))
    if ac_count < 1:
        issues.append("No Acceptance Criteria in GIVEN/WHEN/THEN format found.")

    return issues

def main():
    text = load_spec()
    missing = check_sections(text)
    issues = check_minimum_content(text)

    if missing or issues:
        print("SPEC VALIDATION FAILED")
        if missing:
            print("Missing sections:")
            for s in missing:
                print(f"- {s}")
        if issues:
            print("Issues:")
            for i in issues:
                print(f"- {i}")
        sys.exit(1)

    print("SPEC VALIDATION PASSED")

if __name__ == "__main__":
    main()
```

## 이 스크립트가 하는 일
이 예시는 `spec.md`에 **필수 섹션이 있는지**, **명확화가 덜 된 문구가 남아 있는지**, **수용 기준이 최소한 있는지**를 빠르게 검사합니다. 즉, 구현 전에 스펙이 너무 비어 있거나 애매한 상태로 넘어가는 것을 막는 용도입니다. [wikidocs](https://wikidocs.net/blog/@jaehong/9653/)

## 실무에서 자주 추가하는 검증
실제 프로젝트에서는 아래도 자주 넣습니다.

- `plan.md`, `tasks.md` 존재 여부 확인.
- `Functional Requirements`와 `Acceptance Criteria` 간 개수 불일치 검사.
- `Open Questions`가 남아 있으면 실패 처리.
- 특정 키워드가 있어야 하는지 검사, 예: `security`, `testing`, `performance`.
- `spec.md`의 변경이 있으면 테스트 파일 생성 여부까지 확인.

## 간단한 셸 버전
원하면 더 단순하게 이렇게도 시작할 수 있습니다.

```bash
#!/usr/bin/env bash
set -euo pipefail

test -f spec.md
grep -q "^## Background" spec.md
grep -q "^## Functional Requirements" spec.md
grep -q "GIVEN" spec.md
grep -q "WHEN" spec.md
grep -q "THEN" spec.md

echo "SPEC VALIDATION PASSED"
```

원하시면 다음 답변에서 **`spec.md + plan.md + tasks.md`까지 함께 검증하는 버전**이나 **JSON Schema 방식 검증 예시**로 확장해드릴게요.


`spec.md` 검증이 실패하면, **문서를 바로 수정하지 말고 실패 원인을 분류해서 단계적으로 고치는 것**이 좋습니다. Spec Kit 계열 흐름에서는 스펙, 계획, 작업, 구현을 구분해 보고, 각 단계가 요구사항과 맞는지 다시 점검하는 방식이 권장됩니다. [github](https://github.com/github/spec-kit/issues/1450)

## 우선 할 일
먼저 실패 원인이 **형식 문제인지, 내용 문제인지, 아직 미정인 요구사항인지** 나눠보세요. 구현 단계의 오류처럼 보이더라도, 실제로는 `spec.md`의 목표나 수용 기준이 불명확해서 생긴 경우가 많습니다. [linkedin](https://www.linkedin.com/posts/itmschristophermckenna_prompt-code-is-breaking-your-team-here-activity-7374240507046072320-kYf4)

## 자주 쓰는 대응
- **누락된 섹션 추가**: Background, Goals, Acceptance Criteria 같은 필수 항목을 채웁니다. [deepwiki](https://deepwiki.com/github/spec-kit/4-spec-driven-development-workflow)
- **애매한 문구 수정**: “빠르게”, “적절히”, “가능하면” 같은 표현을 구체화합니다. [ykss.netlify](https://ykss.netlify.app/translation/2026/how-to-write-a-good-spec-for-ai-agents/)
- **미정 항목 분리**: 결정되지 않은 내용은 `Open Questions`로 옮깁니다. [deepwiki](https://deepwiki.com/github/spec-kit/4-spec-driven-development-workflow)
- **수용 기준 보강**: GIVEN / WHEN / THEN 형태로 성공 조건을 명확히 씁니다. [github.github](https://github.github.com/spec-kit/quickstart.html)
- **범위 축소**: 한 번에 너무 많은 기능을 넣었다면, MVP 범위로 줄입니다. [reddit](https://www.reddit.com/r/GithubCopilot/comments/1nbc11u/whos_using_spec_kit_whats_your_experience_so_far/)

## 실무 팁
검증 실패 시에는 `spec.md`를 고친 뒤 다시 검증하고, 그래도 실패하면 `plan.md`와 `tasks.md`가 스펙을 제대로 반영하는지 함께 확인하는 편이 좋습니다. 만약 팀 작업이라면, 개발자가 아니라 **기획자/PO/도메인 담당자와 먼저 합의**해서 스펙을 확정하는 게 재작업을 줄입니다. [github](https://github.com/github/spec-kit/issues/1450)

원하시면 제가 바로 **“검증 실패 메시지별 대응표”**나 **“실패한 spec.md를 고치는 예시”**로 이어서 정리해드릴게요.


SDD 프로젝트에서 pytest와 ruff를 통합하면 **명세 검증 → 코드 품질 → 단위 테스트**까지 자동화된 품질 게이트를 만들 수 있습니다. SDD 워크플로우에서는 `spec.md` 검증 후 `implement` 단계에서 코드 생성 품질을 ruff/pytest로 보장하는 게 핵심입니다. [news.hada](https://news.hada.io/topic?id=15837)

## pyproject.toml 설정
```toml
[project]
name = "sdd-project"

[tool.ruff]

[tool.ruff.lint]
select = ["E", "F", "I", "UP"]

[tool.ruff.format]

[tool.pytest.ini_options]
testpaths = ["tests"]

python_functions = "test_*"
addopts = "-v --cov=src --cov-report=term-missing"
```

## 1. pre-commit 통합 (가장 중요)
`.pre-commit-config.yaml`:
```yaml
repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.6.9
    hooks:
      - id: ruff
        args: [--fix]
      - id: ruff-format
      
  - repo: local
    hooks:
      - id: validate-spec
        name: Validate spec.md
        entry: python scripts/validate-spec.py
        language: system
        files: ^spec.md$
        stages: [commit]
```

## 2. pytest로 QA 테스트 만들기
`tests/test_qa.py`:
```python
import subprocess
import sys
from pathlib import Path

REPO_ROOT = Path(__file__).parent.parent

def test_spec_validation():
    """spec.md가 완전한지 확인"""
    result = subprocess.run(
        [sys.executable, "scripts/validate-spec.py"],
        cwd=REPO_ROOT, capture_output=True
    )
    assert result.returncode == 0, result.stderr.decode()

def test_ruff_lint():
    subprocess.run(
        ["ruff", "check", "."], cwd=REPO_ROOT, check=True
    )

def test_ruff_format():
    subprocess.run(
        ["ruff", "format", "--check"], cwd=REPO_ROOT, check=True
    )
```

## 3. GitHub Actions CI/CD
`.github/workflows/sdd-ci.yml`:
```yaml
name: SDD Quality Gate
on: [pull_request, push]

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      
      - uses: astral-sh/setup-uv@v5
        with:
          enable-cache: true
          
      - run: uv sync --dev
      
      - name: Validate Spec
        run: uv run python scripts/validate-spec.py
        
      - name: Lint & Format
        run: |
          uv run ruff check --fix .
          uv run ruff format --check .
          
      - name: Test
        run: uv run pytest
```

## 4. Makefile 워크플로우
```makefile
validate-spec:
	uv run python scripts/validate-spec.py

lint:
	uv run ruff check --fix .
	uv run ruff format .

test:
	uv run pytest tests/

ci: validate-spec lint test
	@echo "✅ SDD Quality Gate PASSED"

dev: validate-spec lint test implement
```

## 5. SDD 워크플로우 통합 순서
```
1. spec.md 작성 → validate-spec.py ✅
2. plan.md, tasks.md → validate-all ✅  
3. implement → ruff + pytest ✅
4. PR → CI Quality Gate ✅
```
