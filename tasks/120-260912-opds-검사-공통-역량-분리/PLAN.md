# PLAN: GC 검사 역량의 공통 스킬 분리

> 입력: [TASK.md](TASK.md) — ANALYSIS 없음(Short Task). 아래 근거는 본 PLAN 작성 시 직접 조사한 현행 자산이다.

## Approach

`docs/proposals/opal-gc-capability-refactor.md` §11 마이그레이션 1~5·8단계만 구현한다. 6단계(`opal-self-pm` 연결)와 7단계(reference registry)는 PM 결정으로 제외됐다.

검사 절차의 SSOT를 `opal-pilot-gc`에서 신설 단계 스킬로 옮기고, 세 곳에 흩어진 규칙을 한 곳으로 수렴한다. 현재 규칙 원본은 (a) `opal/skills/opal-pilot-gc/references/base-security-checklist.md`·`base-convention-checklist.md`, (b) 두 checker AGENT.md의 Phase 절차(`opal/agents/opal-security-checker/AGENT.md:95-176`, `opal/agents/opal-convention-checker/AGENT.md:104-182`), (c) pilot SKILL.md의 fingerprint·트리거 절(`opal/skills/opal-pilot-gc/SKILL.md:282-300`, `:493-509`) 세 군데에 중복돼 있다.

대상 자산은 전부 Markdown·JSON 문서다. `.opal/code-scan.json`은 존재하지만 `code-scan search gc`가 0건이므로 code-map coverage 대상이 아니며, 구조 파악과 영향 분석은 Read/Grep 실측으로 수행했다. 따라서 본 태스크의 변경은 코드 심볼이 아니라 문서 계약의 이동·정리다.

`opal-pilot-gc`는 범위 확정·상태·Gate·CLOSE만 소유하는 thin wrapper가 되고, `references/pipeline.json`은 한 글자도 바꾸지 않는다 — 이것이 AC-2 회귀 판정의 결정론 기준이다.

## Release and recovery

- 적용 순서: P1(schema SSOT) → P2(세 스킬 신설·규칙 이관) → P3(에이전트 thin role·pilot wrapper) → P4(프레임워크 레퍼런스·프로젝트 문서) → P5(회귀·범위 검증). P4 완료 후 `scripts/install-mac.sh`를 실행해 `~/.opal/`에 배포한다.
- 검증 범위: W-9 ①~⑧은 결정론 회귀(테스트·감사·grep·git diff)다. ⑨ 범위 시나리오와 배포 후 `//opgc --scope staged` 1회 실행은 실제 연동 검증이며, 후자가 이 태스크의 검증 종료 지점이다.
- 실패 시: 모든 변경이 Markdown·JSON 소스이고 런타임 상태 마이그레이션이 없다. `git revert` 또는 해당 W의 파일 되돌리기로 복구하고, 배포본은 `scripts/install-mac.sh` 재실행으로 이전 상태와 일치시킨다. `references/pipeline.json`과 진행 중 태스크의 `state.json`은 이 작업이 건드리지 않으므로 실행 중인 opgc 태스크의 상태 손실은 없다.
