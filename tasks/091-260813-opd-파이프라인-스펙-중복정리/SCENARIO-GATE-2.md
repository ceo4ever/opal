#### 1-2. G-1 검증 — **구멍을 실제로 닫았다** (통과용 형식 아님)

디스패치 [MUST] 1의 질문("S-35가 정말 검출하는 구조인가, 통과용 형식인가")에 대한 판정 근거:

1. **기준선이 워커 산출물과 독립적이다.** S-35 조건은 편집 전 실측 상수 6개(opdd 0 / opwt 0 / opsdd 0 / oppl 0 / opgc 0 / oppd 1)를 문서에 고정 기재했다. 평가자가 §0-1에서 전량 재현했다. 워커가 무엇을 제출하든 이 상수는 변하지 않으므로 self-confirming 경로가 없다.
2. **검출 대상이 실재하는 실패 모드다.** 5종(opdd·opwt·opsdd·oppl·opgc)은 현재 `--task-step`이 **0건**이다. 070 방식(구형 삭제만)으로 작업하면 이 5종은 편집 후에도 0건으로 남고 S-35가 FAIL을 낸다. 즉 기대 결과가 참이려면 워커가 실제로 신형 주소를 넣어야만 한다 — 회피 경로가 grep 상수 대비로 막혀 있다.
3. **판정 문구가 명시적이다.** "어느 pilot이든 편집 후에도 0건이면 **'구형을 지우기만 하고 신형을 넣지 않았다'**로 판정하여 FAIL" — 통과 조건이 아니라 실패 조건이 문서화되어 있다.
4. **070 대조군이 참조축으로 기재되었다.** 전환 완료된 4종의 현재값(opd 12 / opds 10 / opdw 9 / opp 8)이 병기되어 "전환 완료 상태가 어떤 모양인지"의 비교 기준이 있다. 이 4개 값도 실측과 일치한다.
5. **가설 계보가 연결되었다.** H-13("삭제만 하고 채택 안 함", P0)이 §1 표에 신설되고 §4 R-4 AC(b) 행에 `H-7, H-13 → S-35, S-21`로 매핑되었다. 커버리지 입력의 `hypotheses`도 13건으로 갱신되어 도구 계층과 정합한다.

iter1이 "S-20은 `--row N`을 그냥 삭제해도 통과한다"고 지목한 지점에 **역방향 카운터가 생겼다**. 이것이 상향의 1차 근거다.

#### 1-3. G-2 검증 — **self-confirming 경로가 닫혔다**

S-21의 검증 입력 출처가 두 곳에서 동일하게 재정의되었다.

- §2.2 Given: "**SKILL.md에서 `--task-step\s+(\S+)` 정규식으로 추출한 key 전량** (워커 제출 목록 금지)"
- §3 조건: "**검증 입력은 SKILL.md에서 `--task-step\s+(\S+)` 정규식으로 직접 추출한다 — 워커가 제출한 key 목록을 입력으로 쓰지 않는다(self-confirming 차단)**"

iter1이 지적한 "워커가 놓친 지점은 목록에 없으므로 영원히 검증되지 않는다"는 구조가 제거되었다. 검증 대상이 워커의 **주장**에서 문서의 **실제 텍스트**로 이동했다 — 070 실패 계열과 동일 구조였던 부분이 해소되었다. 이것이 상향의 2차 근거다.

실호출 표본도 3종 → 4종으로 opwt가 추가되었다. opwt는 `--row` 보유 2위(11건)이자 H-8(동적 key 규약 신설) 대상으로, iter1이 "신규 규약 리스크가 가장 높다"고 지목한 pilot이다. 표본 커버 `--row` 건수는 27건 → **38건 / 45건**(84%)으로 확대되었다.

#### 1-4. G-3 검증 — **부분 반영, 관측률 3배**

#### 1-5. 2점을 준 근거와 그 한계

`scenario-gate.md` §2 ⑤축 정의는 "교체형 목표=구형 잔존0·**신형 채택 검증 시나리오 존재**"이며, 앵커 2는 "구형 잔존0·신형 채택 **모두 검증**"이다. 존재 기준이다.

### G-4. S-35 임계가 `≥1건`이라 부분 미채택을 통과시킨다 (S-35 강화)

- **무엇이 남았는가**: S-35 기대 결과가 "6종 전부 `--task-step` **≥1건**으로 증가"다. opdd는 `--row`가 14건인데 삭제 후 `--task-step`을 **1건만** 넣어도 통과한다. 나머지 13개 지점이 주소 없는 산문으로 남아도 S-20(0건)·S-21(추출된 key만 검사)·S-35(≥1) 전부 통과한다.
- **iter1 G-1이 제안했던 원문**: "Then=`--row` 보유 6종에서 `--task-step` 증가 ≥1 **& 합계 대응**". 반영본에서 **합계 대응 조항이 빠졌다**.
- **TASK.md AC와의 괴리**: `TASK.md` R-4 AC(b)는 "**교체된 key 46건이 전부** 해당 pipeline.json `task_steps[].key`에 실재"로 **개수를 앵커**한다. S-21은 "추출된 key가 전부 실재"로 바뀌어 개수 앵커가 사라졌다(정규식 추출로 출처는 얻고 개수는 잃은 트레이드오프). 결과적으로 **46건이라는 AC의 수량 조건을 검증하는 시나리오가 어디에도 없다**.
- **어떻게 고치는가**: S-35 기대 결과에 pilot별 하한을 추가한다 — 예: `--task-step` 증가분이 해당 pilot의 `--row` 감소분의 일정 비율(또는 동수) 이상. 최소한 opdd 14 / opwt 11 / opsdd 9처럼 두 자릿수 pilot에는 `≥1`이 아닌 실질 하한을 건다. 또는 S-21 기대 결과에 "추출 key 총량 ≥ 기준선 `--row` 45건 대비 대응 수량"을 명시한다.

### G-5. 쌍 2(산문 `행 N`)에 자동 채택 검증이 여전히 0건 (S-22/R-5 보강)

## 4. 판정 요약

**상향의 근거는 두 가지이며 모두 평가자가 직접 재현했다.**

첫째, **S-35는 통과용 형식이 아니다.** 기준선 6개 값과 070 대조군 4개 값을 레포에서 독립 재측정한 결과 **10개 전량이 문서 기재와 일치**했다. 이 기준선은 워커 산출물과 무관한 고정 상수이므로, "구형만 지우고 신형을 안 넣는" 070 실패 모드를 실행하면 5개 pilot이 0건으로 남아 결정론으로 FAIL이 뜬다. iter1에서 "잔존 0과 채택 사이에 치환 대응 검증이 없다"고 지목한 자리에 역방향 카운터가 실제로 생겼다.

둘째, **S-21의 self-confirming 경로가 닫혔다.** 검증 입력이 "워커가 제출한 key 목록"에서 "SKILL.md 본문에서 정규식으로 직접 추출한 key 전량"으로 §2.2와 §3 양쪽에서 재정의되었고, 워커 제출 목록 사용 금지가 명문화되었다. 검증 대상이 주장에서 텍스트로 이동한 것이 핵심이다. 실호출 표본도 `--row` 2위·H-8 대상인 opwt를 포함해 45건 중 38건(84%)을 덮는다.

**남은 비대칭은 성격이 달라졌다.** iter1의 문제는 "채택 검증이 성립하지 않는다"(구조적)였고, iter2의 잔여는 "채택 검증이 성립하되 임계가 느슨하다"(정도)다 — G-4의 `≥1건` 임계와 G-5의 쌍 2 자동 백업 부재가 그것이다. 둘 다 verdict를 뒤집지 않으나, EXECUTE 단계에서 "opdd 14건을 지우고 1건만 넣어도 전 시나리오 통과"가 물리적으로 가능하다는 점은 PM이 인지한 상태로 진입해야 한다.

①과 ⑥은 신규 추가에 의해 약화되지 않았음을 매핑·플래그·본문 3중으로 확인했다. 커버리지 hard gate도 평가자가 도구를 직접 재실행해 exit 0을 재현했다.
