**쌍 1의 결함 — 채택 검증 입력의 출처 미정의**

S-21의 Given은 §2.2에서 "**교체된 key 목록**"이다. 이 목록이 어떻게 산출되는지 시나리오가 규정하지 않는다. EXECUTE 워커가 "내가 교체한 key"를 제출한 목록을 검증한다면 self-confirming이다 — 워커가 놓친 지점은 목록에 없으므로 영원히 검증되지 않는다. 070의 실패 계열(문서에 실제로 무엇이 적혀 있는지가 아니라 워커 주장을 검증)과 동일 구조다.

더 근본적으로, **S-20(`--row ` 0건)은 `--row N`을 그냥 삭제하거나 "해당 단계"류 산문으로 바꿔도 통과한다.** 잔존 0과 채택 사이에 **치환 대응 검증**이 없다. 평가자 실측상 opdd·opwt·opsdd·oppl·opgc 5종은 현재 `--task-step`이 0건이므로, 이 5종의 전후 델타(0 → N)를 기준선 대비 결정론으로 확인할 수 있음에도 그 시나리오가 없다.

또한 S-21 실호출 표본 3종(opdd 14 + opsdd 9 + oppl 4 = 27건)에서 **opwt 11건 · oppd 5건 · opgc 2건 = 18건이 빠진다**. 특히 opwt는 `--row` 보유 2위이면서 H-8(동적 행 key 규약 신설) 대상이라 신규 규약 리스크가 가장 높은 pilot이다.

**쌍 2의 결함 — 채택 검증이 편중된 사람 표본 단독**

R-5 AC는 "`행 [0-9]+` grep이 0건**이거나** 잔존분이 pipeline.json key를 병기"로 되어 있어 **36건을 전부 삭제만 해도 AC가 통과**한다. 자동 채택 검증이 전무하고, 유일한 채택 검증은 S-34(사람 통독)다.

그런데 S-34의 PM 요청 양식은 표본을 `opal-pilot-dev`(행 N 6건)와 `opal-pilot-sdd`(행 N 2건)로 지정한다 — **사람 시야에 들어오는 것은 36건 중 8건뿐이고, 최다 2종인 opds 9건과 opp 8건(합 17건)은 표본에서 빠진다.** 나머지 28건이 해석 불능 산문으로 남아도 이 시나리오 집합에서는 아무도 관측하지 않는다. 디스패치가 경계하라고 지목한 "grep으로 없어졌다만 확인하고 사람·운영 계층에서 목표 달성 여부는 아무도 안 보는 구조"가 이 쌍에 정확히 해당한다.

**0점이 아닌 이유**: 쌍 3·4·5는 잔존과 채택이 모두 견고하며, 특히 쌍 4·5는 S-28(stdout 실출력)·S-33(세션 노출)으로 신형이 **실제로 동작하는 지점까지** 관통한다. 쌍 1·2도 채택 시나리오 자체는 존재한다(070은 존재조차 하지 않았다). 잔존·채택 라벨이 시나리오 제목에 명시("구형 잔존 검증" / "신형 채택 검증")되어 설계 의도도 확인된다.

## 3. gaps — 비차단 권고

아래 3건은 verdict를 pass에서 뒤집지 않는다(⑤가 통과선 1점을 충족). 다만 ⑤가 만점이 아닌 실질 사유이며, 반영하면 이 태스크가 노출된 070 실패 모드가 구조적으로 닫힌다. **반영 여부 판단과 실제 반영은 PM 책임이다** — 평가자는 TEST-SCENARIO.md를 수정하지 않았다.

### G-1. `--row` → `--task-step` 치환 대응 검증 시나리오 부재 (L1, 신규)

- **무엇이 없는가**: S-20은 `--row ` 0건만 본다. `--row N`을 삭제만 해도 통과하므로, 그 자리에 신형 주소가 들어갔다는 보장이 없다.
- **어디에 무엇을 추가하는가**: §3 L1에 신규 시나리오(예: S-35) — pilot별 비-변경이력 구간 `--task-step` 출현 건수를 편집 전후로 측정하여, `--row` 감소분에 대응하는 증가가 발생했는지 확인한다. 기준선은 이미 결정론으로 확정 가능하다: **opdd 0 / opwt 0 / opsdd 0 / oppl 0 / opgc 0 / oppd 1** (평가자 실측). 이 5종에서 편집 후 `--task-step`이 0건으로 남으면 "삭제만 하고 채택 안 함"이 자동 검출된다.
- **§2.2·§4 반영**: Given=편집 전 `--task-step` 카운트 10종, When=Step 10~13, Then=`--row` 보유 6종에서 `--task-step` 증가 ≥1 & 합계 대응. §4 매핑 표 `R-4 AC(b)` 행에 S-21과 병기.

### G-2. S-21의 검증 입력 출처가 미정의 — self-confirming 경로 (S-21 수정)

- **무엇이 문제인가**: §2.2 S-21의 Given이 "교체된 key 목록"으로만 적혀 있다. 이 목록이 EXECUTE 워커가 제출한 것이면, 워커가 누락한 지점은 목록에 없으므로 영원히 검증되지 않는다.
- **어떻게 고치는가**: Given을 "**SKILL.md 10종에서 `--task-step\s+(\S+)` 정규식으로 추출한 key 전량**"으로 명시 고정한다(워커 제출 목록 금지). 기대 결과에 "추출된 key 전량이 해당 pipeline.json `task_steps[].key`에 실재 — 1건이라도 불일치 시 FAIL"을 추가한다.
- **실호출 표본 보강**: 대표 3종(opdd·opsdd·oppl = 27건)에서 **opwt 11건 · oppd 5건 · opgc 2건이 빠진다**. opwt는 `--row` 2위이자 H-8 동적 key 규약 신설 대상이므로 실호출 표본에 **opwt를 추가**한다(3종 → 4종).

### G-3. S-34 사람 표본이 산문 `행 N` 최다 2종을 배제 (S-34 수정)

- **무엇이 문제인가**: 산문 `행 N` 36건의 채택(= key/항목명 참조로 바뀌어 해석 가능한가)을 검증하는 유일한 시나리오가 S-34인데, PM 요청 양식이 표본을 `opal-pilot-dev`(6건)·`opal-pilot-sdd`(2건)로 지정한다. **36건 중 8건만 관측되고, 최다 2종인 opds 9건·opp 8건(합 17건)은 시야 밖이다.** R-5 AC 자체가 "grep 0건이거나 잔존분이 key 병기"라 전량 삭제로도 통과하므로, 자동 백업도 없다.
- **어떻게 고치는가**: S-34 PM 요청 양식의 통독 대상을 **`opal-pilot-dev-short`(9건) + `opal-pilot-project`(8건)를 포함하도록 확장**한다. 현행 opd·opsdd는 "표준/비표준 구조 양극단" 표본이므로 유지하되, `행 N` 밀도 상위 2종을 추가해 4종으로 만든다(총 관측 25건 / 36건).
- **대안(자동 백업)**: 산문에서 삭제된 36개 지점이 key 또는 항목명 참조로 치환되었는지 L1에서 확인하는 시나리오를 추가한다 — 예: 편집 전 `행 N` 출현 라인을 기록해 두고, 편집 후 동일 라인이 `task_steps[].key` 문자열 또는 항목명을 포함하는지 대조.

## 4. 판정 요약

070의 직접 후속이라는 위험 조건에서, 이 시나리오 집합은 **목표 달성(①)과 경계/부정(⑥)에서 만점**이다. S-33이 배포본·새 세션·운영 계층에서 목표를 관통 검증하고, S-14가 과잉 차단 실패 모드를 명시 배제하며, S-16이 보안 경계까지 포함한다. 070이 노출했던 "목표 검증 시나리오 부재"는 재현되지 않았다.

**⑤에서 1점에 그친 것은 070과 동일 계열의 잔재가 정확히 `--row`·`행 N` 두 쌍에 남아 있기 때문이다** — 두 쌍 모두 잔존 0은 10종 전수 자동 검증이면서, 채택은 Producer 주장 목록(S-21) 또는 편중된 2종 사람 표본(S-34)에 의존한다. G-1~G-3은 이 비대칭을 닫는 최소 변경이며, 특히 G-1은 기준선이 이미 확정되어 있어 즉시 작성 가능하다.
