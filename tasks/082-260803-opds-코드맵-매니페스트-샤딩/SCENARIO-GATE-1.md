## 2. gaps[] — 이 시나리오 집합으로도 놓칠 수 있는 것

> 세 축 모두 임계를 넘었으므로 **verdict를 좌우하지 않는 개선 제안**이다. 다만 G-1은 목표(재발 방지)와 직결되므로 반영을 강권한다.

### G-1 [강권] 샤드 파일 **자신**의 상한 초과가 검출되는지 검증하는 시나리오가 없다

- 상한 픽스처 `oversize/`의 조건은 "**베이스**가 200바이트 초과"뿐이다(`TEST-SCENARIO.md:56`, S-15 `:226`). S-16도 동일 자산의 설정값만 바꾼다.
- 그런데 이 태스크의 상한 도입 근거는 정확히 "**상한 없으면 샤드 재비대로 동일 사고 재발**"이다(TASK 확정 방향 #4, `TASK.md:59`). PLAN은 상한 검사를 "베이스·샤드 공통"으로 설계했다(`PLAN.md` §3.5.2 (B) "구조 패스에서 순회 중인 매니페스트마다(베이스·샤드 공통)").
- 즉 **샤드가 상한 검사 대상에서 누락되어도 현재 시나리오 집합은 전량 GREEN**이며, 누락 시 열리는 구멍이 바로 태스크가 막으려는 재발 경로 그 자체다. S-23 ①("분산 후 oversize 0건")은 분산 후 전부 상한 이하라는 정상 상태만 보므로 이 결손을 잡지 못한다.
- 제안: `oversize/` 픽스처에 **샤드 1개가 상한을 초과하는 변형**을 추가하고, `manifest_oversize`의 `manifest` 필드가 **샤드 경로**를 가리키는지 단언하라(S-10의 "침범 귀속" 패턴 준용). S-15 또는 S-23에 1항 추가로 족하다.

### G-2 [권장] `validate --changed` 모드가 샤드 자산에서 검증되지 않는다

- `--changed`는 파일 목록 구성 경로가 full 스캔과 완전히 다르다(`code-scan.js:1809-1834` — csv/stdin 파싱 + `hasExcludedSegment`/`matchesAnyPattern`/`isFilteredOutOfScope` 4단 필터). 구조 패스만 "full scope regardless of `--changed`"이고(`code-scan.js:1899`), **커버 판정 파일 루프는 두 모드가 공유**한다 — PLAN §3.3.2 (A)가 고치는 `fe`/`ownerRel` 지점(`code-scan.js:1851`)이 정확히 그 공유 지점이다.
- 그런데 PLAN·TEST-SCENARIO 어디에도 `--changed` 문자열이 없다(grep 확인 — PLAN은 scaffold의 `changed` 변수 1건만, TEST-SCENARIO는 0건).
- 실무 위험: `--changed`는 CLOSE 게이트·hook 연동에서 가장 자주 쓰이는 경로다. 샤드 소유 키를 `--changed`로 넘겼을 때 `uncovered:no_entry` 오탐이 나도 현재 시나리오는 전부 통과한다.
- 제안: S-7에 "동일 자산에서 `validate --changed <샤드소유파일>`도 위반 0건" 1항을 추가하라. 픽스처 신규 없이 실행 1줄 추가로 덮인다.

### G-3 [권장] 분산 **작업 도중의 중간 상태**에서 조회·기록이 어떻게 동작하는지 미검증

- S-23은 **손으로 만든 "분산 전" 트리와 "분산 후" 트리 2개를 대조**한다(`:440`). 즉 검증 대상이 "두 정적 상태"이고, 베이스에서 샤드로 엔트리를 옮기는 **전이 과정**은 어떤 시나리오도 통과하지 않는다.
- 실제 마이그레이션은 소유자의 다단계 수작업이며(TASK 확정 방향 #10 — 자산 분할은 적용 프로젝트 별도 작업), 그 사이 중간 상태가 필연적으로 발생한다:
  - (a) 샤드 파일 생성 + `shards` 선언 완료, **베이스에서 엔트리 미제거** → 중복. validate 측은 S-8이 덮지만, **그 상태에서 `scan`/`target`이 first-wins 승자로 정상 동작하는지**(U-4 전제 "조회는 계속 동작해야 한다", `TASK.md:74`)를 단언하는 시나리오가 없다. S-14는 `scaffold` 무쓰기만 본다.
  - (b) 베이스에서 엔트리 제거 + `shards` 선언 완료, **샤드 파일 미생성** → S-8이 `orphan:shard_missing`을 잡지만, 그 상태에서 `scan`이 해당 파일을 어떻게 분류하는지(uncovered? 무응답?) 미정의.
  - (c) 샤드 파일 생성 + 엔트리 이동 완료, **`shards` 선언 미추가** → S-8이 `shard_undeclared`를 잡지만, 조회는 그 파일을 놓친 채 조용히 통과한다(베이스에도 샤드에도 안 잡힘 → 사실상 서술 유실). 이 조용한 유실이 검증되지 않는다.
  - (d) 샤드 파일 존재 + `files{}` 빈 객체 → `scaffold`가 이 샤드를 `pruned`/삭제하지 않는지 미검증(PLAN은 "존재하지 않는 샤드는 버킷을 만들지 않는다"만 규정).
- 제안: 최소 (a)와 (c)에 대해 **`scan --json` 동작을 1항씩 추가**하라 — (a)는 승자 엔트리로 정상 해석, (c)는 그 파일이 `uncovered`로 **드러나야 함**(조용한 유실 금지). 둘 다 기존 `duplicate-key/`·`undeclared/` 픽스처 재사용으로 가능하다.
- 추가 제안(픽스처 무결성): S-23의 "분산 후" 트리를 손으로 쓰지 말고 **"분산 전"에서 엔트리를 라벨별로 옮기는 스크립트로 생성**하라. 현 설계에서는 두 트리를 사람이 각각 작성하므로, ②의 "헤더 값 완전 동일" 단언이 도구가 아니라 **픽스처 작성자의 정확성**을 시험하게 된다.

### G-4 [권장] 여러 스코프가 동시에 샤드를 쓸 때의 상호작용이 미검증

### G-5 [선택] 상한의 **정확한 경계값**(size == limit)이 단언되지 않는다
