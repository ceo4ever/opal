# PLAN: E2E profile·verdict 계약 도입

> 입력: [TASK.md](TASK.md), [ANALYSIS.md](ANALYSIS.md)

## Approach

이번 PLAN은 제안서의 9개 독립 태스크 중 1번인 "E2E profile·verdict 계약"만 구현 대상으로 삼는다. Runtime Manager, 실제 Browser/API/Human executor, Playwright 기본 설치 제거, server/port/session lifecycle은 제외하고, `test-tool`의 profile·status·evidence 판정 owner와 그 소비자 이전까지만 설계한다 (→ D-1:12-22, D-3:846-860).

실행은 RED-first로 진행한다. 먼저 기존 fallback/escalation/pass 허용 테스트를 새 계약 기준으로 실패하게 뒤집고, 그 다음 단일 owner 모듈과 thin consumer를 구현한다. source suite 통과 뒤에는 사용자 전역 `~/.opal/`을 직접 수정하지 않고 격리 설치본으로 계약 일치를 확인한다 (→ D-2:47-51, D-7:797-805, D-8:253-254).

| D-C3. executor matrix | `EXECUTOR_MATRIX`는 `browser: required=("browser",), allowed=("browser",)`, `api: required=("api",), allowed=("api",)`, `hybrid: required=("api", "browser"), allowed=("api", "browser")`, `collaborative: required=("human",), allowed=("browser", "api", "human")`, `manual: required=("human",), allowed=("human",)`로 고정한다. `collaborative`는 human 전후에 자동 step이 있으면 browser/api를 허용하지만 human을 생략하면 불일치다. | 공개 표면별 허용 profile과 금지 대체가 제안서 표에 정리돼 있고, 각 step은 `executor=browser|api|human`을 명시해야 한다 (→ D-3:341-380). |
| D-C4. public function signatures | `resolve_profile(surface: Mapping[str, Any] | None, requirement_text: str = "", actors: Sequence[str] = ()) -> dict[str, Any]`; `executor_contract(profile: str) -> dict[str, tuple[str, ...]]`; `validate_surface_match(profile: str, surface_kind: str | None, actors: Sequence[str]) -> dict[str, Any]`; `normalize_legacy_verdict(payload: Mapping[str, Any]) -> dict[str, Any]`; `can_try_next_provider(candidate_result: Mapping[str, Any]) -> bool`; `build_verdict(run_result: Mapping[str, Any]) -> dict[str, Any]`; `validate_pass_requirements(scenario: Mapping[str, Any], result: Mapping[str, Any]) -> dict[str, Any]`; `validate_scenario_contract(spec: Mapping[str, Any], *, legacy_defaults: bool = True) -> dict[str, Any]`; `status_to_exit(status: str) -> int`; `status_to_error(status: str) -> str | None`를 공개한다. 모든 반환 dict는 `ok`, `status`, `error`, `detail`, `normalized` 키만 사용하고 legacy `fallback`, `escalated`, `escalate` 키를 신규 출력하지 않는다. | ANALYSIS Handoff가 함수 시그니처와 schema version 확정을 PLAN 결정 항목으로 넘겼다 (→ D-2:47-50). 제안서는 JSON 입출력 계약 우선을 요구한다 (→ D-3:425-438). |
| D-C5. profile resolve 입력 우선순위 | profile은 `surface_ref`가 가리키는 IR의 `kind`가 있으면 그것을 1순위로 사용하고, 없으면 scenario의 `surface_kind`, `actors`, `requirement_text`를 사용한다. 도구 가용성·runner availability는 profile 입력이 아니다. | D-C6. legacy migration | `normalize_legacy_verdict`는 입력 호환만 제공한다. `fallback+not_in_cmux`와 `fallback+cmux_not_installed`는 Browser 후보 내부 `provider_unavailable`로 변환한다. `fallback+open_failed`, `fallback+surface_parse_failed`, `has_cmux=false`, `escalated+usage/invalid_surface/goto_failed/eval_failed`, 알 수 없는 error, reason 없는 `fallback`은 `infra_error`다. `wait_failed`는 `wait_kind=="assertion_condition"`일 때만 `fail`, `navigation_ready/transport/None`은 `infra_error`다. 신규 출력에는 `fallback`, `escalated`, `escalate`, `escalation`을 쓰지 않는다. | [MUST] `tasks/125-260912-opd-E2E-프로필-판정-계약/TASK.md` §Constraints: "기존 상태·오류 입력은 명시적인 이행기 변환을 제공하되 신규 결과에서 generic `fallback`, `escalated`, `escalate`를 생성하지 않는다." 현행 adapter가 해당 legacy 값을 생성한다 (→ D-5:119-134, D-5:172-223). 제안서 migration 표와 wait_kind 분기를 그대로 승계한다 (→ D-3:479-510, D-2:17, D-2:44). |
| D-C7. Browser 후보 전환 | `provider_unavailable`은 final status가 아니라 Browser 후보 내부 결과다. `can_try_next_provider()`는 오직 `{"status": "provider_unavailable"}` 또는 legacy에서 그 상태로 변환된 `not_in_cmux/cmux_not_installed`에만 true를 반환한다. 후보 소진 시 final `executor_unavailable`/exit 18이 된다. assertion 실패, 제품 실패, 인증·데이터·증적 실패, open/parse/navigation/runtime 실패는 다른 후보 성공으로 덮지 않는다. | TASK AC-4와 C-3이 후보 전환 한계를 고정한다 (→ D-1:18, D-1:28). 제안서도 provider_unavailable과 final executor_unavailable의 경계를 분리한다 (→ D-3:461-477, D-3:735-755). |
| D-C8. pass와 real-usage gate | `build_verdict()`와 `validate_pass_requirements()`는 `pass` 또는 `fidelity="real-usage"` 승격 전 모든 assertion에 `expected`와 `actual`이 있고, profile/시나리오가 요구한 `required_evidence`가 `observed_evidence`에 충족됐는지 검사한다. ## Release and recovery

- 적용 순서: P1 RED-first 테스트 → P2 contract owner → P3 resolver/schema/template → P4 adapter/CLI와 scenario validator 병렬 → P5 agent 소비자 → P6 pilot/docs 소비자 → P7 source suite와 격리 설치본 검증.
- 검증 범위: contract unit tests, public `test-tool run.sh integration/scenario-*` exit/output tests, legacy migration fixture, scenario schema/runtime validation fixture, pilot/agent 문서 소비자 grep 회귀, source unittest suite, 격리 installed CLI smoke를 구분한다.
- 실측 경계: source suite는 `opal/tools/test-tool/tests/test_*.py` 전체가 기준이다. installed 검증은 임시 `OPAL_HOME` 또는 동등한 격리 설치 경로의 `tools/test-tool/run.sh`로 status→exit와 legacy 출력 금지를 확인한 시점에 종료한다.
- 실패 시: P1~P6 실패는 해당 W 파일 소유자에게 되돌려 재작업한다. P7 source 실패는 release 금지다. P7 격리 설치 실패가 환경 문제라면 사용자 전역 설치본을 직접 수정하지 않고 실패 명령·stderr·격리 경로를 기록해 AC-9 미완료로 보고한다.
