# PLAN: 하네스 병렬 실행 제한 및 리소스 관리 원칙 추가

## 1. 분석 및 설계 방향

현재 하네스는 "독립 작업은 무조건 병렬"이라는 성능 중심의 원칙을 가지고 있으나, 대용량 애셋 처리 시 안정성(Stability) 문제가 확인됨. 이를 해결하기 위해 **예방(Prevention) - 제어(Control) - 복구(Recovery)** 3단계 전략을 도입함.

### 예방 (Pre-check)
- 디스패치 전 대상 파일들의 크기(Size)를 체크함.
- 텍스트 파일 기준 특정 임계치(예: 50KB)를 넘는 파일이 다수일 경우 고부하 작업으로 분류.

### 제어 (Concurrency Limit)
- **Safe Mode**: 고부하 작업 시 병렬 개수를 제한 (기본 Max 2 또는 순차).
- **Adaptive Batching**: 파일 크기의 총합을 고려하여 배치를 유연하게 편성.

### 복구 (Runtime Fallback)
- 병렬 실행 중 오류(메모리, 리소스 부족, 타임아웃) 발생 시:
  1. 현재 배치를 즉시 중단.
  2. 실패한 항목들을 **순차(Sequential)** 또는 **N/2 배치**로 재편성.
  3. 재시도 수행 및 이력 기록.

## 3. QA 체크리스트

- [x] **병렬 원칙과 제한 원칙이 상충되지 않고 조건부로 잘 연결되는가**: §7의 기본 병렬 기조를 유지하면서, §7.4에서 특정 리소스 임계치(50KB/200KB) 조건 시에만 제한이 발동되도록 논리적으로 잘 연결됨.
- [x] **폴백(Fallback) 프로세스가 무한 루프에 빠지지 않도록 설계되었는가**: 실패 시 배치를 1/2로 줄이거나 순차로 전환하여 '작아진 배치'로 재시도하므로, 최종적으로는 순차 실행에 도달하여 완료됨을 보장함.
- [x] **파일 크기 기반의 판단 기준이 실제 리소스 부하와 유의미한 상관관계를 갖는가**: 텍스트 파일(md, js 등) 기준 50KB는 상당한 양의 토큰을 포함하므로 에이전트의 컨텍스트 점유 및 메모리 부하와 밀접한 관련이 있음. (타당함)
- [x] **`AGENTIC-LOG.md`에 리소스 이슈 발생 및 복구 이력이 명확히 기록되는가**: 하네스 §7.5-5번에 기록 의무를 명시함. (본 태스크는 interactive 모드이므로 실제 로그 생성은 N/A이나 원칙에는 반영됨)
