# PLAN: PM 보고·활동 이벤트·정지 판정 관측 배선

> 입력: [TASK.md](TASK.md) (ANALYSIS 없음 — opds Short profile)

## Approach

세 가지를 서로 다른 표준 사건으로 분리해 기록하고, 기존 관측 축(상태 전이·보관함·검증 라우트)에 접합한다.

1. **사건 어휘 확장.** `docs/run-log/CONTRACT.md` §1.2 사건 12종에 `pm.report`·`stop.decision` 2종을 더해 14종으로 닫는다. `activity`는 4종 그대로 두고 어떤 축도 얹지 않는다(C-1). 폐쇄 집행 지점은 기존과 동일하게 기록 코어 `run_log_core.validate_event()` 한 곳이며, `state-tool` 앞단 검증은 같은 규칙의 중복 방어로 유지한다.
2. **판정 입력의 영속화.** Stop hook은 별도 프로세스여서 `transition_action`/`report_type`을 알 방법이 현재 없다 — 이 셋은 stdout 계약이고 `state.json`에 남지 않는다(`opal/core/references/harness/state.md:15`). 그래서 hook은 `current_status`만 보고 전이를 추정한다(`opal/tools/ownership-tool/ownership_tool/stop_evaluator.py:31-36` `_STATUS_TRANSITION`). `pm.report` 사건과 `state.json.run_log.last_report` 포인터가 이 빈틈을 메운다.
3. **집행과 기록의 분리.** Stop hook은 run-log에 직접 쓰지 않는다. 자기 receipt에 판정을 적재하고, `state-tool`이 다음 호출에서 기존 outbox/drain 경로로 `stop.decision`을 커밋한다. hook의 fail-safe exit 0 불변식과 `.opal-task.lock` 30초 상한이 Stop 임계 경로에 들어가지 않는다.
4. **판정 원천의 배선.** Phase 0이 `pm-agent-tool` 채널을 `observed_trajectory`로 등급 배정해 두었으나(`tasks/123-260912-oppl-태스크-실행로그-표준화/archive/tasks/T01-채널-관측-능력-실측/profiles.json`) 변환기가 런타임에 배선돼 있지 않아 이 태스크 run-log의 `worker.started`는 0건이다. 배정 전제를 먼저 재실측한 뒤 변환기를 배선한다.
5. **읽기 판정.** `state-tool verify --run-log-completeness-check`에 축을 추가해 AC-5의 4분류를 기록만으로 가른다. 기존 4축(`missing_state_changed`/`missing_pm_activity`/`missing_gate_event`/`unobserved_worker_boundary`)과 같은 비차단 응답에 합류시킨다.

범위 밖: active 모드 승격, `profiles.json`의 프로젝트 소스 승격, 완료 게이트 참여, Phase 1A 정량 게이트(채널별 표본 20건), 교차 태스크 집계.

변경 후보 탐색은 `code-scan scan <경로> --header-source inline`으로 수행했다 — `opal/tools/ownership-tool` 14파일 전건 layer=util, `opal/tools/run-log-tool` 3파일(util 2 + test 1), `opal/tools/state-tool` 11파일(util 2 + test 9). 아래 Work items의 파일 경로는 그 결과에서 고른 것이다.

## Release and recovery

- **적용 순서**: P1(실측·캡처·계약) → P2(기록 코어) → P3(state-tool 표면·변환기) → P4(receipt·훅) → P5(판정 축) → P6(E2E) → P7(문서). 배포는 `docs/run-log/TRD.md` §배포 순서가 정한 "기록 코어·기록 CLI 설치·검증 후 상태 도구의 새 스키마 활성화" 순서를 그대로 따른다 — ① W-4 머지 후 install, 배포본에서 `run-log-tool append`로 새 사건 2종 수용을 확인, ② 그 뒤 W-5·W-7·W-9의 state-tool 개정을 머지하고 다시 install, ③ W-6·W-8의 훅·어댑터 변경은 `claude-hooks.json` 배포(`scripts/install-mac.sh:1501-1509`, `scripts/merge-hooks.py` 멱등 upsert)를 통해 마지막에 내린다. [MUST] `.opal/AGENT.md` §금지사항: "`~/.opal/` 직접 편집 금지 — 항상 프로젝트 소스를 수정한 후 install로 배포한다."
- **검증 범위**: 결정론 — W-4·W-5·W-7·W-9의 단위·계약 테스트(subprocess 실호출 + 디스크 산출물 검사, mock 금지). 회귀 — `opal/tools/run-log-tool/tests/` 전체, `opal/tools/state-tool/tests/` 전체, `opal/tools/ownership-tool/tests/` 전체. **이 3개 디렉터리 전건 통과(TEST-SCENARIO S-14) 판정은 W-12 적용 후를 기준으로 한다** — W-12 이전에는 이 태스크와 무관한 선점 실패 2건이 이미 존재한다. 실제 연동 — W-10의 실제 훅 프로세스 E2E 5시나리오가 유일한 AC-4·AC-6 근거다. **AC-1은 install 후 TEST-SCENARIO S-19를 Claude Code 2.1.278의 실제 `PostToolUse:Agent` 봉투로 재실행해** 해당 태스크 조각에 `worker.started` 1건 이상·`activity` 1건 이상·terminal 1건이 남고 세 종류 전건이 A1 조합임을 확인해야 인도된다. legacy `Task` fixture 통과만으로 S-19를 대체하지 않는다. AC-7은 W-6 성립 여부와 **독립적으로** 판정한다 — 1차 근거는 W-4(기록 코어의 `pm.report`·`stop.decision` `data` 폐쇄 거부 + `redact()` 통과)·W-5(`pm.report` 경로의 조각·`pending_events`·`last_report` 평문 0건)·W-7(`stop.decision` 커밋 경로의 평문 0건)의 조각 파일 실검사이고, W-6의 변환기 원본 검사는 A1 경로가 인도될 때 더해지는 2차 근거다. W-1이 불성립을 내 W-6이 빠져도 AC-7의 검증 수단은 남는다.
- **구조적 차단 게이트**: W-5는 TEST-SCENARIO S-4·S-5와 CONTRACT MV-33을 실제 `run-log-tool append`·`state-tool log-event`·조각 파일로 증명하기 전에 완료로 보지 않는다. 원문 `summary`·`reason`·`refs`·여분 `data`는 저장 0건이고, 정상 사건은 D-16 템플릿과 바이트 동일해야 한다. 기존 `redact()` 4종은 별도 회귀로 평문 0건을 유지하며 자연어 탐지 regex는 검증·구현 범위에 없다. 배포는 W-4 renderer·코어 문지기를 먼저 install·검증한 뒤 W-5·W-7 state-tool 조립기를 배포하고, 실패 시에는 둘을 함께 되돌려 renderer/조립기 drift를 남기지 않는다.
- **모드 경계**: 검증은 전부 `shadow`에서 수행한다. `mode=active` 전환과 `profiles.json`의 `opal/core/` 승격은 이번 범위에 넣지 않는다 — 승격은 사람 승인 게이트를 거치는 2단 소유 절차이고(`docs/run-log/CONTRACT.md` §3.3), active의 유일한 추가 효과인 완료 게이트 집행은 Phase 1B 인도물이다(`docs/run-log/PRD.md` §Phase 1B). Phase 1A→1B의 정량 게이트(채널별 정상 완료 표본 20건 이상, 포착률 100%)는 이 태스크가 떠안지 않는다.
