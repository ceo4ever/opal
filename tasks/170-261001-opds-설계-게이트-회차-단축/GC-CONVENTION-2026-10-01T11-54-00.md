- [ ] GC-C002 [opal/tools/state-tool/state_tool.py:7511-7527] `--design-gate-check` 라우트가 `state.json` 로드 시 예외 처리 없이 직접 `json.load()`를 호출해, 같은 파일의 인접 비차단 진단 라우트와 견고성 패턴이 다름
  - 카테고리: 코드 품질 (예외 처리 일관성)
  - 위반 기준: 인접 코드에서 관측한 패턴 — `_run_log_completeness_check()`(동일 파일 1832행대)는 `state.json`을 읽을 때 `try: ... except (OSError, ValueError): return result`로 손상된 JSON을 graceful skip 처리하는 반면, 신규 `design_gate_check` 분기는 `with open(state_file, encoding="utf-8") as f: dgc_state = json.load(f)`를 예외 처리 없이 호출한다. `docs/CONVENTIONS.md`에는 이 패턴을 직접 규정하는 조항이 없어 **advisory**로만 보고한다(카테고리 8 코드 품질 규칙에 따름).
  - 설명: 이 라우트는 자신의 `--help` 문구("design-gate ①~⑦ 결정론 검사 + decision_clarity 유보 어휘 후보 린트를 회차·상태 소비 없이 실행한다(**비차단, exit 0 유지**)")와 진입 주석("무차단 사전점검")에서 비차단을 명시적으로 약속한다. 그러나 `state.json`이 존재하되(`state_file.exists()`는 통과) 파싱 불가능한 손상 JSON이면 `json.load()`가 `json.JSONDecodeError`를 던져 처리되지 않은 예외로 `verify` 명령 전체가 스택트레이스와 함께 비정상 종료(exit 1)하며, 같은 비차단 계열 라우트인 `_run_log_completeness_check` 및 다른 5개 게이트 라우트가 공유하는 "손상 상태에서도 exit 0 유지" 기대와 어긋난다. `_is_pm_design_path(dgc_state)`도 `dgc_state`가 dict가 아닌 경우(예: 최상위가 리스트인 JSON) 동일하게 처리되지 않은 예외로 이어진다.
  - 해결 방안: `_run_log_completeness_check`와 동일하게 `state.json` 읽기를 `try/except (OSError, ValueError)`로 감싸 파싱 실패 시 기존 `state_file.exists()` 분기와 같은 형태의 `"design_gate_check": "skipped"` 응답(exit 0)으로 graceful degrade 시킨다.
