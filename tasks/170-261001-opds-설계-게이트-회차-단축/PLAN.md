# PLAN: 설계 게이트 회차 단축 — 결정론 사전 검사·사전 점검 절차·evaluator 설정 최적화

> 입력: [TASK.md](TASK.md)

## Approach

설계 게이트의 흐름을 "결정론 검사(값싸고 빠름)"와 "evaluator 판정(비싸고 느림, 회차 소비)" 두 티어로 명확히 나누고, 결정론 티어를 evaluator 호출 **이전**에 한 번에 몰아서 실행하는 사전검사 배치로 재구성한다. evaluator 판정 자체(설계 4축·시나리오 3축·pass 조건·반복 상한 3회)는 바꾸지 않는다(C-1). 이번 태스크가 손대는 것은:

1. 결정론 검사(`_design_gate_deterministic_check`)를 `design-gate start` 밖에서도 회차·상태 소비 없이 호출할 수 있게 노출한다(AC-1).
2. decision_clarity FAIL의 재발을 줄이기 위해, 같은 사전검사 응답에 "판정이 아닌 후보 목록"으로 유보 어휘 린트를 동봉하고, PM 경로 절차에 이 사전점검과 TEST-SCENARIO 동시 갱신을 명문화한다(AC-2, AC-3).
3. evaluator의 rewrite 지적을 축-위치-남은선택 구조로 의무화하고, 다음 회차가 이전 지적의 해소 여부를 명시적으로 보고하게 한다(AC-4).
4. 과거 18회차 실측 이력(161·162·163·164·167·168, 근거: `state.json` `design_gate.history`)과 진행 중인 169의 이력을 평가 세트로 삼아 evaluator model·effort 후보 3개 이하를 측정하고(AC-5), 캡틴이 고른 값을 설치 프론트매터에 고정한다(AC-6).

내부 결정론 검사 ①~⑦(`opal/tools/state-tool/state_tool.py:6787-6853`)을 스레드로 병렬화하는 안은 검토 후 기각한다 — 실측 병목은 evaluator 왕복(회차당 4~6분, TASK.md 근거)이지 내부 검사 순서가 아니므로 복잡도 대비 실익이 없다(PRINCIPLES.md §2 단순성).

**scope 병렬 분리는 이번 PLAN에서 제외한다.** 설계 게이트 1~3회차 중 캡틴 지시로 `design-rubric`을 `scope: design`/`scope: scenario` 병렬 2콜로 나누는 안을 시도했으나, 3회 전부 rewrite(both)로 끝나 반복 상한(retry_limit)에 도달했다. 3회차 지적 중 Critical 2건(executability — 워커가 서브에이전트를 디스패치할 도구가 없는데 W-5/S-6을 워커에게 맡김, recoverability — install-mac.sh 전체 재배포 범위 불명확)과 Medium 1건(completeness — 161 pass 사례 bundle hash 불일치)은 scope 분리 여부와 무관하게 실재하는 문제였고 이번 PLAN에서 수정한다. 반면 나머지 지적(옛 "1회 디스패치" 문구가 저장소 곳곳에 남음, previous_gaps/resolved_gaps의 id·echo·측정단위 관련 모순 다수)은 scope 분리라는 단일 기능이 만들어낸 부수 복잡도였다 — 패치를 반복할수록 새 모순이 났고(1회차 11건→2회차 11건→3회차 5건, 매번 scope 분리 주변에서 재발), 이는 "거의 다 됐다"는 신호가 아니라 "이 기능이 이 태스크 범위에 비해 과설계됐다"는 신호로 판단해 캡틴과 함께 범위에서 제외하기로 결정했다(AGENTIC-LOG #9). scope 분리 자체는 폐기가 아니라 **이 태스크 CLOSE 후 별도 후속 태스크로 재검토**한다(§범위 밖 제안 참조) — AC-4(이전 회차 지적의 축-위치-남은선택 구조화 + 해소 여부 보고)는 scope 분리 없이 기존 단일 `design-rubric` 호출 안에서 그대로 구현한다.

## Release and recovery

- 적용 순서: W-1·W-2·W-3 (P1, 서로 다른 파일이라 병렬) → W-4 (P2, W-3 완료 필요) → W-5 (P3, PM 직접 수행, W-3·W-4 완료 필요) → W-6 (P4, W-5 완료·캡틴 결정 필요) → 배포는 `scripts/install-mac.sh`(Claude 어댑터 대상)로 일괄 재실행.
- 검증 범위: W-1은 `verify --design-gate-check`를 기존 `design-gate start`의 결정론 실패 이력이 재현된 전용 fixture에 실행해 같은 `missing` 목록이 나오는지, 그리고 state.json `design_gate` 블록이 실행 전후 불변인지로 결정론 확인. W-3·W-4는 TEST 단계에서 새로 만드는 전용 fixture 태스크로 PM이 직접 evaluator를 재디스패치해 `resolved_gaps` 계약이 지켜지는지 실제 연동 검증한다(170 자신은 이미 pass 시도 중이라 재사용하지 않는다). W-5는 측정 자체가 검증 대상(실행 증거 = `EVAL-RESULT.md`).
- 실측 경계: W-5의 24회 디스패치는 1회 실행 상한(C-3)이며 재시도하지 않는다 — 실패한 디스패치는 결과 없음으로 `EVAL-RESULT.md`에 기록하고 재실행하지 않는다.
- 실패 시: W-6 설치가 실패하거나 캡틴이 후보 3개 모두를 거부하면 effort 필드를 추가하지 않고 현행(미지정) 상태를 유지한다 — AC-6은 미충족으로 남기고 별도 후속 태스크로 이월한다. install 실패 시 `scripts/install-mac.sh`는 기존 폴백 리터럴(바이트 동일 유지, `:544`)로 자가완결 동작하므로 배포 중단 위험은 없다.

## 범위 밖 제안 (캡틴 결정 필요, 이번 PLAN에 포함하지 않음)

TASK.md 조사 중 발견했으나 C-1(판정 기준·반복 상한 불변)에 저촉되거나 이번 Proposed outcome 범위를 벗어나 Work items에 넣지 않은 항목이다.

1. **`design-rubric`의 `scope: design`/`scope: scenario` 병렬 디스패치** — 캡틴이 이번 PLAN 작성 세션 중 직접 지시해 1~3회차에 시도했으나(AGENTIC-LOG #4·#9), 3회 전부 rewrite로 끝나 retry_limit에 도달했다. 지적 대부분(previous_gaps/resolved_gaps의 id·echo·측정단위 관련 모순, 저장소 전역의 옛 문구 치환 범위)이 scope 분리 자체가 만든 부수 복잡도였다. **이 태스크 CLOSE 후 별도 후속 태스크로 재검토한다** — 재검토 시 이번 3회차 이력(`run/design-gate-i1.json`~`i3.json`)을 설계 입력으로 재사용할 것. AC-4(이전 지적 해소 보고)는 이번 PLAN에서 scope 분리 없이 먼저 구현한다.
2. **decision_clarity 축에 Likert형 앵커 예시 추가** — 현재 `opal-evaluator-agent/AGENT.md:114`는 5개 카테고리를 한 줄 이진 판정으로 묶어 평가자 간 판단 편차가 클 수 있다. 축 정의·앵커를 바꾸는 것이라 C-1 위반 — 별도 태스크로 검토 제안.
3. **completeness 축과 결정론 검사 ②의 중복 축소** — 결정론 검사가 이미 AC/C→Work item 연결을 기계적으로 확인하는데 evaluator의 `completeness` 축이 같은 사실을 다시 주관 판정한다. 축 재정의라 C-1 밖.
4. **design-rubric 루브릭에 advisory 채널 부재** — 시나리오 3축에는 `advisories[]`(subsumed/mergeable 등 비차단 권고)가 있는데 설계 4축에는 없다. 이번 scope 분리 시도에서 "옛 문구 잔존"(cosmetic) 같은 경미한 지적과 "워커가 서브에이전트를 디스패치할 수 없음"(치명) 같은 지적이 똑같이 `FAIL` 한 줄로 묶여, 심각도 구분 없이 매 회차 전체 rewrite를 요구했다. 설계 축에도 advisory 채널을 두면 경미한 지적은 회차를 소비하지 않고 누적 보고될 수 있다. 축 판정 계약 자체를 바꾸는 것이라 C-1 위반 — evaluator-agent/design-gate.md를 다루는 별도 태스크로 제안.
5. **design-rubric 판정 커버리지의 비결정성** — 본 태스크 1~3회차에서, 1회차부터 존재했던 "W-5를 워커에게 맡기면 안 된다"(executability)는 3회차에야 처음 지적됐다. 매 회차 같은 체크리스트를 전수 순회하는 결정론적 커버리지 보장이 없다는 뜻으로 보인다 — "이번 회차 통과"가 "문제 없음"을 보장하지 않는다. design-rubric phase의 탐색 범위·완전성 계약을 명문화하는 별도 태스크로 제안(이 역시 평가 기준 자체를 다루므로 C-1과의 경계를 먼저 검토해야 한다).
