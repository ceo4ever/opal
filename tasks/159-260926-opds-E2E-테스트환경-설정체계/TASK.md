# TASK: E2E 테스트 환경 설정 체계 — 환경 검토·인터뷰·설정·준비 검증 후 시나리오 실행

## Problem

E2E 테스트는 대상 환경(웹 브라우저, API, macOS·Windows·Linux 데스크톱 앱, 사람 참여, 이들의 혼합)마다 실행 방법·기동 명령·계정·데이터·드라이버 준비가 다르다. 그런데 현재 OPAL에는 프로젝트별 E2E 환경을 검토하고 설정하는 단계가 없다.

- `opal-e2e` 스킬은 `author`·`run`·`status` 3모드뿐이고 환경 설정 모드가 없다 (`opal/skills/opal-e2e/SKILL.md:25-27`).
- `test-tool e2e` 하위 명령은 `run`·`resume`·`status`·`clean`·`driver-verify`·`promote-check`뿐이다 (`opal/tools/test-tool/test_tool.py:349-401`).
- 테스트 대상 앱 기동이 이 저장소 구조에 고정돼 있다. backend는 `dashboard.backend.main:app`, frontend는 `dashboard/frontend` 경로다 (`opal/tools/test-tool/lib/e2e/runtime.py:105`, `:155`). 그래서 다른 프로젝트에서는 시나리오와 드라이버가 준비돼 있어도 앱 기동 단계에서 실패한다.
- 실행 profile은 `browser`·`api`·`hybrid`·`collaborative`·`manual`만 있고 데스크톱 앱 표면은 없다 (`opal/tools/test-tool/lib/e2e_contract.py:57-86`).

결과적으로 사용자는 E2E를 시작하기 전에 무엇을 준비해야 하는지 안내받지 못한다. 설정이 부족하면 원인이 분명하지 않은 `blocked`·`infra_error`만 받게 되고, 프레임워크의 재사용성 원칙(다른 프로젝트에서 그대로 동작)도 깨진다.

## Proposed outcome

사용자가 어느 프로젝트에서든 다음 순서로 E2E를 준비하고 실행할 수 있다.

1. **환경 검토**: 저장소를 읽기 전용으로 살펴 테스트 표면 후보, 기동 방법, health 확인 지점, 설치된 드라이버를 제시받는다.
2. **인터뷰**: 탐지로 알 수 없는 항목만 질문받아 확정한다. 대상 표면, 로컬 기동 또는 기존 URL, 계정·비밀값 환경 변수 이름, 데이터 준비·복원, 외부 연동 정책이 여기에 해당한다.
3. **환경 설정 확정**: 확정 내용이 프로젝트의 E2E 환경 설정 파일로 남는다. 파일 형식은 스키마로 검증된다.
4. **준비 검증**: 설정대로 실제로 기동·확인해서 표면별 준비 완료·미비를 판정받는다. 미비 항목에는 원인과 조치가 붙는다.
5. **시나리오 작성·실행**: 확정된 환경을 전제로 여정을 작성하고, `run`은 고정 경로가 아니라 이 설정으로 웹·API 대상을 기동해 실행한다.

데스크톱 앱(macOS·Windows·Linux)은 이번 태스크에서 설정과 준비 검증까지 지원한다. 실행기가 없다는 사실은 준비 검증이 명시적으로 보고하며, 실행을 성공으로 가장하지 않는다.

## Affected users and systems

- 사용자: OPAL로 프로젝트를 개발하면서 E2E 검증을 하는 소유자, 그리고 E2E를 소비하는 PM·테스트 워커.
- 포함:
  - `opal/skills/opal-e2e/` (환경 설정 흐름 추가)
  - `opal/tools/test-tool/` (E2E 환경 설정 스키마·검증·준비 검증 명령, `run`의 설정 기반 기동)
  - 관련 README·PROJECT.md 레지스트리
  - 이 저장소 자체의 E2E 환경 설정 (기존 `dashboard` 동작을 설정으로 표현)
- 제외:
  - 데스크톱 앱 실행기(드라이버) 구현 — 후속 태스크
  - 모바일 앱
  - 기존 여정·조각 계약 변경
  - 외부 서비스 계정 생성
  - 실제 배포 환경 쓰기

## Constraints

- C-1: 실행 판정(`pass`·`fail`·`blocked`·`infra_error`·`executor_unavailable`)과 exit code의 소유자는 계속 `test-tool`이다. 스킬은 명령을 호출하고 구조화 결과를 해석만 한다 (`opal/skills/opal-e2e/SKILL.md` §판정 소유 경계).
- C-2: 준비 완료 판정은 실제 기동·확인 결과로만 한다. 설정 파일이 있다는 것이나 사람의 진술만으로 준비 완료로 올리지 않는다.
- C-3: 비밀번호·토큰 같은 비밀값은 설정·산출물에 원문으로 저장하지 않고 환경 변수 이름으로만 선언한다 (`opal/skills/opal-e2e/references/authoring.md` §조각).
- C-4: 프로젝트 전용 경로·명령을 test-tool 코드에 하드코딩하지 않는다. 프로젝트별 차이는 프로젝트 설정 파일이 소유한다 (`.opal/AGENT.md` §PM 검토 기준 "프로젝트 의존 하드코딩 없음").
- C-5: 이 저장소에서 기존 `test-tool e2e` 회귀 테스트와 기존 여정 실행 동작이 유지된다. 설정 파일이 없는 프로젝트에서도 기존 기본 동작을 깨지 않고 명시적 오류·안내를 준다.
- C-6: 환경 검토는 읽기 전용이다. 설정 파일 생성·수정은 인터뷰에서 사용자가 확인한 뒤에만 수행한다.
- C-7: `~/.opal/` 배포본을 직접 편집하지 않는다. 소스 수정 후 install로 배포한다 (`.opal/AGENT.md` §금지사항).

## Acceptance criteria

- AC-1: E2E 환경 설정 스키마가 웹·API·macOS 앱·Windows 앱·Linux 앱·사람 참여·혼합 표면을 선언할 수 있다. 스키마 검증 명령이 유효 설정은 통과시키고, 필수 항목 누락·비밀값 원문 포함 설정은 구조화 오류 코드로 거부한다.
- AC-2: 환경 검토 명령을 설정이 없는 프로젝트에 실행하면 파일을 변경하지 않고, 표면 후보·기동 방법 후보·설치된 드라이버를 구조화 결과로 반환한다.
- AC-3: `opal-e2e` 스킬에 환경 설정 흐름(검토 → 인터뷰 → 사용자 확인 → 설정 기록 → 준비 검증)이 추가되고, 기존 3모드 호출은 그대로 동작한다.
- AC-4: 준비 검증 명령은 표면별로 실제 기동·health·드라이버 확인 결과를 판정한다. 준비 완료 표면과 미비 표면(원인·조치 포함)을 구분해 반환하고, 실행기가 없는 데스크톱 표면은 "실행기 없음"으로 명시한다.
- AC-5: `test-tool e2e run`은 프로젝트 E2E 환경 설정이 있으면 그 설정의 기동 명령·작업 폴더·health 지점으로 웹·API 대상을 띄운다. 이 저장소의 `dashboard` 기동이 설정으로 표현되어 기존 여정이 같은 판정으로 실행된다.
- AC-6: test-tool 코드에서 `dashboard` 고정 기동 경로 참조가 제거되거나, 설정이 없을 때만 쓰이는 명시적 호환 경로로 격리된다.
- AC-7: 기존 `test-tool` E2E 회귀 테스트 전체가 통과하고, 새 명령·설정 경로에 대한 테스트가 추가되어 통과한다.
- AC-8: 이 저장소 밖의 임시 프로젝트(웹 또는 API 표본)에서 검토 → 설정 → 준비 검증 → 실행 흐름이 실제로 한 번 끝까지 동작한 증거가 남는다.
