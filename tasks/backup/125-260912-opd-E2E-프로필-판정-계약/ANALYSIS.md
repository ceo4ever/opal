## Critical assumptions

| 가정 | 확인 방법·결과 | 남은 한계 |
|---|---|---|
| requirement surface를 profile로 바꿀 입력은 일반 opd와 oppl 모두에서 확보할 수 있다. | oppl은 `surfaces.json`에 `id`, `resource`, `auth`, request/response shape, `kind`를 두는 IR을 이미 가진다 (`opal/skills/opal-pilot-project-loop/references/contract.md:35-58`). 일반 sdlc-v2는 TEST-SCENARIO의 검증 대상·행동·방법/환경과 TASK 요구 문구는 있지만 actor/profile 전용 필드는 없다 (`opal/skills/op-dev-test-scenario/references/test-scenario-guide.md:21-42`). 제안서는 resolver 입력을 `surface_ref`, 요구 문구, actor로 정한다 (`/Volumes/Data/AIStudio/workspace/ai-framework/docs/proposals/opal-e2e-harness.md:343-353`). | 일반 opd에서 `surfaces.json`을 새 필수 산출물로 만들면 범위가 커진다. PLAN은 `surface_ref`가 있으면 IR을 사용하고, 없으면 scenario의 구조화 surface/actor 입력을 사용하도록 우선순위를 정해야 한다. 도구 가용성은 어떤 경우에도 profile 입력이 아니다. |

## Handoff

- PLAN에서 결정할 것: (1) `lib/e2e_contract.py`의 실제 이름과 profile/status/normalizer/validator 공개 시그니처, (2) `test-scenario.json` schema version과 신규 spec/result 필드 및 legacy 기본값, (3) `integration`/`scenario-mark` CLI에 구조화 assertion·evidence·human transition을 전달하는 인자 또는 JSON 입력 형태, (4) `resolver.py`의 `surface_ref` IR 우선순위와 일반 opd용 surface/actor 입력, (5) legacy 입력 alias 유지 기간과 public output 금지 테스트, (6) source→isolated-installed 검증 명령을 Work item 완료 기준으로 확정한다. 실제 필드 매핑은 구현 PLAN이 정한다는 TO-BE 계약을 따른다 (`/Volumes/Data/AIStudio/workspace/ai-framework/docs/proposals/opal-e2e-harness.md:618-630`).
- PLAN에서 변경 불필요로 고정할 것: Runtime Manager, 실제 Browser/API/Human executor, Playwright package·MCP·doctor·requirements 제거, 서버/port/session lifecycle은 후속 태스크다 (`tasks/125-260912-opd-E2E-프로필-판정-계약/TASK.md:12-22`; `/Volumes/Data/AIStudio/workspace/ai-framework/docs/proposals/opal-e2e-harness.md:846-860`).
- 착수 차단: 없음. `awaiting_human` 실제 재개 실행과 driver의 `wait_kind` 생성은 이번 태스크의 contract fixture로만 검증하고 후속 구현 한계로 명시하면 된다.
