## 2. 배경과 문제

OPAL은 통합 단계에서 "사용자 목표가 실제로 동작하는가"를 확인하는 검증을 수행한다. 그러나 현재는 그 검증을 수행할 실행 주체가 없다. 판정 규칙만 있고 집행자가 없는 상태다 (→ D-3 §참고).

관찰되는 문제는 네 가지다.

1. **검증 대상이 실제 변경 소스가 아니다.** 현재 Console 기동 명령은 명령을 실행한 위치가 아니라 설치본을 띄운다(`opal/tools/opal-cli/lib/console.sh:34-40`). main이나 작업용 worktree에서 실행해도 그 브랜치의 변경을 검증하지 않는다.
2. **여러 작업이 동시에 검증할 수 없다.** 화면이 바라보는 서버 주소가 한 곳으로 고정되어 있고(`dashboard/frontend/src/lib/api.ts:14`), worktree 생성은 포트 힌트만 돌려줄 뿐 실제로 포트를 확보하지 않는다(`opal/tools/worktree-tool/worktree_tool.py:971-996`). 동시에 두 검증을 돌리면 서로의 서버를 바라보거나 서로를 종료시킨다.
3. **검증이 사용자의 상시 작업 환경을 침범한다.** 종료 동작이 실행 주체를 구분하지 않고 이름이 비슷한 프로세스를 광범위하게 종료한다(`opal/tools/opal-cli/lib/console.sh:87-92`). 상시 사용 중인 Console과 검증용 서버가 서로를 죽인다.
4. **판정 계약을 집행할 실행자가 없다.** 화면 조작, 외부 API 호출, 사람이 직접 해야 하는 단계를 각각 수행할 실행자와, 그 실행자에게 검증 대상 서버를 넘겨줄 실행 관리자가 없어 계약상 `pass` 조건을 만족하는 검증을 한 건도 돌릴 수 없다 (→ D-2 §13 E2~E6).

추가로, 브라우저 자동화 도구가 기본 설치에 남아 있어 설치 비용과 "무엇이 진짜 검증인가"를 정의하는 문서가 두 곳에 존재하는 상태가 유지된다 (→ D-2 §12, §8.4).

### 2.1 이번 제품이 대체하는 과거 결정

과거에는 "브라우저 검증 도구를 cmux 1순위, Playwright 폴백으로 고정하고, 네 가지 사유는 폴백·다섯 가지 사유는 즉시 에스컬레이션한다"는 결정이 있었다 (→ D-9 §결정 내용). 이번 제품은 이 결정을 다음과 같이 **대체한다**.

- 도구 우선순위는 "cmux 우선"이 아니라 **요구사항이 드러나는 공개 표면이 실행 방식을 결정하고, 브라우저가 필요할 때만 브라우저 실행 후보를 순서대로 시도하는 구조**로 바뀐다 (→ D-2 §4.8).
- 폴백·에스컬레이션 사유 목록은 태스크 125가 사유별 신규 상태 매핑으로 이미 대체했다 (→ D-3 §결과).
- Playwright는 기본 폴백이 아니라 이행기 선택 항목이며 최종적으로 기본 설치에서 빠진다 (→ D-2 §12.1).

이 PRD가 요구하는 결과가 확정되면 해당 과거 결정 기록은 갱신 대상이다.

## 3. 대상 사용자와 사용 맥락

| 사용자 | 사용 맥락 | 이 제품에서 기대하는 것 |
|---|---|---|
| OPAL로 검증을 돌리는 개발자 (로컬 macOS) | 자기 작업 브랜치의 변경이 실제로 동작하는지 확인한다. 동시에 다른 작업도 진행 중이다. | 내 변경을, 남의 작업과 섞이지 않게, 실제 사용자 경로로 검증하고, 실패하면 원인을 결과만 보고 안다 |
| 자동 파이프라인 실행 환경 (CI·headless) | 브라우저 앱이 설치되지 않은 환경에서 같은 검증을 돌린다. | 로컬과 같은 시나리오가 같은 판정 기준으로 실행된다 |
| Console을 상시 띄워 쓰는 사용자 | 대시보드를 계속 켜 둔 채 다른 작업을 한다. | 검증이 돌아도 내 화면이 끊기지 않고, 내가 대시보드를 껐다 켜도 남의 검증이 깨지지 않는다 |

검증 대상은 세 종류로 구분된다 — 통합 기준이 되는 주 작업본, 개별 작업용 분리 사본, 배포 산출물 (→ D-2 §2.1).

## 4. 제품 목표와 비목표

### 4.1 목표

1. 검증 실행자가 검증할 대상을 지정하면, 하네스가 그 소스에서 서버를 띄우고 정상 응답을 확인한 뒤 시나리오를 실행한다.
2. 동시에 실행되는 검증끼리, 그리고 사용자의 상시 작업 환경과 서로 간섭하지 않는다.
3. 화면·API·둘의 결합·사람 협업·전면 수동의 다섯 가지 검증 방식이 하나의 판정·증적 기준을 공유한다.
4. 실제 사용자 행동과 그 결과 확인이 이루어진 실행만 통과로 기록된다.
5. 브라우저 앱이 없는 환경에서도 같은 시나리오가 실행된다.
6. 브라우저 자동화 도구의 기본 설치 비용이 사라지고, "무엇이 진짜 검증인가"의 정의가 한 곳에만 남는다.

### 4.2 비목표

- 태스크 125가 확정한 판정 계약(다섯 가지 최종 상태, 사람 대기 상태, 종료 코드)을 다시 설계하지 않는다 (→ D-1 C-1).
- 브라우저 제품이나 자동화 도구의 기능 자체를 OPAL 안에서 다시 만들지 않는다 (→ D-2 §3.2).
- 기존 시나리오 문서·데이터 형식을 전면 교체하지 않는다 (→ D-1 §Affected users and systems).
- 외부 선택지 목록(community skill)의 브라우저 자동화 항목 처리는 이번 범위에 포함하지 않는다 (→ D-2 §8.4).
- 사용자의 실행 중인 브라우저 탭, 작업 surface, 설치 환경을 임의로 정리하지 않는다 (→ D-2 §4.6).
- **격리된 배포본(임시 `OPAL_HOME`)을 생성하는 절차는 이번 범위에 포함하지 않는다.** 배포 산출물 검증 대상은 이미 준비된 격리 배포본 경로를 입력으로 받으며, 그 배포본을 만드는 일은 별도 작업이다 (→ TRD RK-4·TD-9).

## 5. 전제 (이번 범위가 재요구하지 않는 것)

태스크 125가 다음을 이미 완료했으므로 이 PRD는 이를 **입력 계약으로 전제**하고, 재설계나 재구현을 요구하지 않는다 (→ D-3 §결과, §검증).

- 공개 표면에 따른 다섯 가지 검증 방식 구분과 그 판정 (`opal/tools/test-tool/lib/e2e_contract.py:38`)
- 최종 상태 다섯 가지와 사람 대기 상태의 보존 (`opal/tools/test-tool/lib/e2e_contract.py:39-40`)
- 상태별 종료 코드 (`opal/tools/test-tool/lib/e2e_contract.py:42`)
- 브라우저 후보 단계의 "실행 수단 없음" 중간 결과를 후보 소진 뒤 최종 상태로 확정하는 규칙 (`opal/tools/test-tool/lib/e2e_contract.py:209-213`)
- 결과 확인이나 필수 증적이 빠진 결과를 통과·실사용으로 승격하지 않는 검사 (`opal/tools/test-tool/lib/e2e_contract.py:292`, 필수 증적 누락 판정 `:357-366`)

이번 범위는 이 계약을 **집행하는 실행 주체**를 만드는 것이다.

## 6. 기능 요구사항

각 요구사항은 관찰 가능한 결과로 서술한다. `AC`·`C`는 태스크 정의(D-1)의 수용 기준·제약 ID다.

### 6.1 실행 격리와 소스 증명

| ID | 요구사항 (관찰 가능한 결과) | 추적 |
|---|---|---|
| R-1 | 실행자가 검증 대상을 주 작업본·작업용 분리 사본·배포 산출물 중 하나로 지정하면, 하네스가 **그 소스 트리의 서버**를 띄운다. 배포 산출물 검증은 사용자의 실제 설치 위치가 아니라 별도로 격리된 배포 위치를 사용한다. | AC-2, C-2 |
| R-2 | 실행마다 화면용·서버용 주소를 실행 시점에 확보하고, 그 주소로 서버가 실제 기동된 뒤에만 확보를 확정한다. 이미 점유된 주소로 기동에 실패하면 정해진 횟수 안에서 다른 주소로 재확보한다. 소유 프로세스가 사라진 채 남은 확보 기록은 다음 실행이 회수할 수 있다. | AC-1 |
| R-3 | 주 작업본 1개와 서로 다른 분리 사본 2개에서 검증을 **동시에** 실행하면, 세 실행의 서버 주소·브라우저 세션·서버 프로세스가 충돌하지 않고 세 실행 모두 독립적으로 종료된다. 어느 실행의 화면도 다른 실행의 서버를 바라보지 않는다. | AC-1 |
| R-4 | 검증 실행 중 사용자가 상시 Console을 종료해도 검증용 서버는 계속 동작하고, 검증이 끝난 뒤에도 사용자의 상시 Console은 계속 동작한다. 종료 동작은 이름이 비슷한 프로세스를 광범위하게 끄는 대신 **어느 설치 환경이 소유한 프로세스인지**를 확인하고 그것만 종료한다. | AC-3, C-2 |
| R-5 | 각 실행 결과에 검증 방식, 참여한 실행 주체, 검증 대상 종류, 대상 소스 위치와 분리 사본 위치, 커밋과 미커밋 변경 여부, 실제 사용한 주소, 실행 주체·세션 종류, 실행기 버전이 남는다. 결과만 보고 "무엇을 어디서 검증했는가"를 재구성할 수 있다. | AC-2 |
| R-6 | 소스 대상 검증을 실행한 뒤 저장소에 새로운 추적·미추적 파일이 남지 않고, 사용자의 설치본 대시보드 서버가 변경되지 않는다. 증적과 빌드 산출물은 임시 산출물 위치에만 생성된다. | AC-13, C-5 |

### 6.2 화면 검증

| ID | 요구사항 (관찰 가능한 결과) | 추적 |
|---|---|---|
| R-7 | 브라우저 앱이 설치된 환경에서, 실제 화면 조작과 그 결과 확인을 포함한 시나리오가 `pass`한다. 화면을 열고 주소를 이동한 것만으로는 `pass`가 되지 않는다. | AC-4 |

| R-10 | 실행 수단이 없는 경우에만 다음 실행 후보로 전환된다. 제품 동작 실패, 결과 확인 실패, 인증 실패는 다른 실행 방식의 성공으로 덮이지 않고 그대로 실패로 남는다. 대기 종류를 구분할 수 없는 과거 형식의 결과는 실패가 아니라 인프라 오류로 처리되어 제품 실패로 오인되지 않는다. | C-3 |

## 11. 성공 판정

이 제품이 완성됐다고 판정하는 조건이다. 모든 항목은 실행 결과로 관찰된다.

1. 주 작업본과 서로 다른 분리 사본 2개에서 동시에 검증을 실행해 세 실행이 모두 독립적으로 종료된다 (R-3).
2. 검증 실행 중 사용자가 상시 Console을 종료해도 검증이 계속되고, 검증 종료 후에도 상시 Console이 동작한다 (R-4).
3. 실제 화면 조작과 결과 확인을 포함한 시나리오가 브라우저 앱 환경에서 통과하고, 같은 시나리오가 브라우저 앱 없는 환경에서도 통과한다 (R-7, R-9).
4. 결과 확인이나 필수 증적을 제거한 실행을 시도하면 어떤 경로로도 통과가 나오지 않고 누락 항목이 결과에 표시된다 (R-14).
5. 화면 행동을 API 호출로 바꾼 시나리오가 거부된다 (R-12).
6. 사람 협업 시나리오가 대기 상태로 멈췄다가 같은 실행으로 재개되고, 사람 제출만으로는 통과가 되지 않는다 (R-13).
7. 실패한 실행의 결과만 가지고 원인을 지목할 수 있다 (R-15).
8. 검증 실행 후 저장소에 새 파일이 남지 않고 설치본이 변경되지 않는다 (R-6).
9. 기본 설치에서 브라우저 자동화 도구를 제거한 뒤 신규 설치·갱신·진단 경로의 회귀가 0건이다 (R-18).
10. 검증 수준 정의가 검증 도구 계약 한 곳에만 존재한다 (R-19).
