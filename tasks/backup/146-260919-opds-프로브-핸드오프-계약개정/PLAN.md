# PLAN: OPPB Environment Probe 구조적 블로커 해결

> 입력: [TASK.md](TASK.md). ANALYSIS 없음(opds Short). 코드 근거는 `opal/tools/code-scan/run.sh search 'probe|oppb|project-slice|environment|timeout' --json`와 `opal/tools/code-scan/run.sh exports 'probe|oppb|environment|timeout' --json`로 먼저 확인했다.

## Approach

이번 PLAN은 이전 "개정 핸드오프 문서 1건" 계획을 폐기하고, 현재 TASK의 실제 범위에 맞춰 `oppb-runtime-tool` probe 구현, 공개 CLI 테스트, OPPB 계약 문서, 설치본 검증까지 묶는다. 단, PLAN 단계에서는 `PLAN.md`만 수정한다. [MUST] `docs/CONVENTIONS.md` §Guards: "승인 전 소스 코드 파일 생성·수정, 패키지 설치, 설정 파일 수정 금지"가 적용되므로 구현 Work item은 `plan.user_confirm` 이후에만 착수한다(docs/CONVENTIONS.md:208-214, TASK.md:31).

작업은 RED to GREEN으로 간다. 먼저 `test_probe.py`에 실제 Git 저장소와 공개 CLI(`run.sh probe`) 기반 RED fixture를 추가한다. 그 fixture는 `.gitattributes`의 `/tasks/ export-ignore` 같은 tracked 입력 누락과 bootstrap 산출물 전달 실패를 현재 코드에서 재현해야 한다(TASK.md:8-10, .gitattributes:15-31). 그 다음 `probe.py`의 snapshot 생성과 명령 실행 모델을 바꾼다. 현재 `_make_snapshot`은 `git archive --format=tar HEAD`를 사용하므로 export 속성을 적용하고(opal/tools/oppb-runtime-tool/probe.py:309-327), `_observe_command`는 명령마다 새 snapshot을 만든 뒤 폐기한다(opal/tools/oppb-runtime-tool/probe.py:406-420). 새 계약은 accepted HEAD의 전체 tracked tree를 export attributes 없이 격리 물질화하고, bootstrap 명령은 순차 실행해 준비 baseline으로 승격하며, 비-bootstrap 명령은 그 baseline에서 각각 독립 분기한다(TASK.md:12-16, TASK.md:35-44).

구현 후보는 임시 `GIT_INDEX_FILE`로 `git read-tree HEAD` 후 `git checkout-index --all --prefix <snapshot>/`를 실행하는 방식이다. 이 방식은 `git archive`를 쓰지 않아 `export-ignore`를 적용하지 않고, project branch·HEAD·공유 index를 건드리지 않는다. 현재 `_git`은 list argv와 `shell=False`로 git을 호출한다(opal/tools/oppb-runtime-tool/probe.py:232-244). 구현 시 `_git`에 선택 env를 받을 수 있게 하거나 별도 helper를 두되, 표준 라이브러리와 Git CLI만 사용하고 플랫폼 분기는 추가하지 않는다(TASK.md:28-31, opal/tools/oppb-runtime-tool/README.md:52-57).

태스크 144의 역할 분리는 되돌리지 않는다. 현재 `op-oppb-project-slice`는 `verify_command`와 전체 테스트 스위트를 probe에 등재하지 않고, 수용 판정은 Supervisor가 실제 워크트리에서 소유한다고 규정한다(opal/skills/op-oppb-project-slice/SKILL.md:197-218). 이번 변경은 그 분리를 유지한 채, 관측 전용 명령의 snapshot과 bootstrap baseline을 고치는 것이다.

## Decisions and contracts

| 결정 | 변경 후 계약 | 선택 이유·근거 |
|---|---|---|
| D-1. Snapshot materialization은 `git archive`를 쓰지 않는다 | `_make_snapshot` 또는 대체 helper는 accepted `HEAD`의 전체 tracked tree를 export attributes 없이 임시 격리 디렉터리에 checkout한다. 후보 구현은 임시 `GIT_INDEX_FILE` + `read-tree HEAD` + `checkout-index --all --prefix <snapshot>/`다 | 현재 `git archive` 경로는 `.gitattributes export-ignore`를 적용해 tracked 입력을 누락한다(opal/tools/oppb-runtime-tool/probe.py:309-327, .gitattributes:15-31). TASK는 export-ignore 여부와 무관한 전체 tracked-tree snapshot을 요구한다(TASK.md:12-16, TASK.md:35-36). |
| D-2. Snapshot은 독립 git repo baseline을 유지한다 | 물질화된 snapshot은 지금처럼 `git init`, `git add -A`, baseline commit을 가진 독립 저장소가 된다. `_status_changes`의 `git status --ignored=matching` 기반 미추적·ignored·tracked 변경 관측 계약은 유지한다 | 현재 status 관측은 snapshot git repo의 baseline과 비교한다(opal/tools/oppb-runtime-tool/probe.py:333-380). TASK는 원본 worktree 오염 없이 명령별 관측 귀속을 보존하라고 요구한다(TASK.md:24-29). |
| D-3. Bootstrap은 준비 baseline으로 승격한다 | `kind == "bootstrap"` 명령들은 선언 순서대로 같은 bootstrap snapshot에서 실행한다. 각 bootstrap 출력은 해당 command id로 관측·분류하고, 모든 bootstrap 성공 후 그 결과를 baseline commit으로 승격한다. 후속 비-bootstrap 명령은 이 bootstrap baseline을 공통 입력으로 받는다 | 현재 `compute_input_hash`는 bootstrap command subset을 별도 hash로 가진다(opal/tools/oppb-runtime-tool/probe.py:551-568). TASK는 둘 이상의 bootstrap 명령 순차 준비와 후속 소비를 요구한다(TASK.md:37). |
| D-4. 비-bootstrap 명령은 sibling 격리를 유지한다 | build 등 비-bootstrap 명령은 bootstrap baseline에서 명령별 snapshot을 새로 복사해 실행한다. 비-bootstrap A가 만든 출력은 비-bootstrap B에게 보이지 않고, 각 출력·실패·duration은 자기 command id에만 귀속된다 | 현재 `_observe_command`는 명령 하나를 단독 실행하고 command id별로 결과를 반환한다(opal/tools/oppb-runtime-tool/probe.py:383-429). TASK는 같은 baseline 소비와 sibling 출력 비가시성을 함께 요구한다(TASK.md:27, TASK.md:38). |
| D-5. `commands[].timeout_seconds`를 입력 계약에 추가한다 | `timeout_seconds`는 선택 필드다. 생략 시 `COMMAND_TIMEOUT_SECONDS` 180초를 유지한다. 값은 bool이 아닌 양의 정수만 허용하고, invalid 값은 실행 전 `commands_invalid`로 거부한다. timeout 실패 메시지는 해당 command id를 보존한다 | 현재 전역 timeout은 180초 상수이고 모든 명령에 동일 적용된다(opal/tools/oppb-runtime-tool/probe.py:64, opal/tools/oppb-runtime-tool/probe.py:383-403). `_validate_commands`는 현재 `id`, `kind`, `argv`, `runtime_resources`만 정규화한다(opal/tools/oppb-runtime-tool/probe.py:604-648). TASK는 명령별 timeout 계약과 invalid 거부를 요구한다(TASK.md:39). |
| D-6. Timeout은 freshness hash에 포함한다 | `_command_identity`는 `timeout_seconds`의 명시값을 포함한다. 생략값은 canonical identity에서 안정적으로 기본값 180과 동등하게 다룬다. `input_hash.commands`와 `input_hash.bootstrap`은 timeout 계약 변경 시 달라진다 | 현재 command identity는 id/kind/argv만 포함한다(opal/tools/oppb-runtime-tool/probe.py:540-548). P2.2 freshness hash는 실행 command 정의와 bootstrap 정의를 포함한다(docs/proposals/opal-oppb-project-build-pilot.md:554-559). |
| D-7. Late discovery와 `scope_violation`은 현행 유지한다 | `observe-write`의 project 밖·민감 경로·lease crossing·second discovery·policy unclassifiable 승격, budget charge, delta file 계약은 변경하지 않는다. 단 delta probe도 새 snapshot materialization과 timeout 계약을 소비한다 | 현재 late discovery는 `_observe_command`를 재사용하고, 두 번째 discovery 등은 `scope_violation`으로 승격한다(opal/tools/oppb-runtime-tool/probe.py:1021-1135). proposal도 같은 승격 조건을 규정한다(docs/proposals/opal-oppb-project-build-pilot.md:621-627). TASK는 이 계약 재정의를 금지한다(TASK.md:29). |
| D-8. 계약 문서는 코드와 같은 실행 계약으로 갱신한다 | `op-oppb-project-slice/SKILL.md`와 `docs/proposals/opal-oppb-project-build-pilot.md`는 전체 tracked-tree snapshot, bootstrap baseline, sibling isolation, `timeout_seconds`를 설명한다. `verify_command` 미등재와 Supervisor 판정 책임 문장은 유지한다 | 현재 스킬과 제안서는 아직 `git archive` snapshot 자족성 R2를 계약으로 둔다(opal/skills/op-oppb-project-slice/SKILL.md:197-205). proposal은 관측 전용 명령만 probe가 실행하고 판정은 Supervisor가 소유한다고 규정한다(docs/proposals/opal-oppb-project-build-pilot.md:542-546). TASK는 문서 계약 갱신과 역할 분리 유지 모두를 요구한다(TASK.md:26, TASK.md:40). |
| D-9. 설치 검증은 원본 142가 아니라 외부 clone에서 한다 | install은 승인 후 `scripts/install-mac.sh` 경유로 수행한다. 설치본 검증은 task 142 원본 밖 격리 clone과 신규 real-git fixture에서 수행하고, task 142 원본 capsule/profile/state 해시와 Git status는 전후 동일해야 한다 | install은 `opal/skills`와 `opal/tools`를 `~/.opal`로 배포한다(scripts/install-mac.sh:1241-1298, scripts/install-mac.sh:1338-1463). TASK는 실제 원본 worktree probe 직접 실행과 task 142 수정 금지를 요구한다(TASK.md:24-25, TASK.md:43-44). |

## Release and recovery

- 적용 순서: 사용자 `plan.user_confirm` 승인 후 P1(W-1 RED tests) -> P2(W-2 probe runtime) -> P3(W-3 contract docs) -> P4(W-4 source regression) -> P5(W-5 install and installed clone verification) -> P6(W-6 PM Gate). 같은 파일을 여러 worker가 동시에 수정하지 않도록 전부 순차 실행한다.
- 검증 범위: 결정론 검증은 pytest 신규/전체 probe tests, source/install sha256, `state-tool verify` 2종, `git diff --name-only` 범위 확인이다. 실제 연동 검증은 공개 CLI `run.sh probe seal/status`를 real-git fixture와 task142 원본 밖 clone에서 실행하는 것이다. mock/patch는 금지한다(test_probe.py:1-9, opal/tools/oppb-runtime-tool/README.md:94-100).
- 실측 경계: 명령별 timeout 기본은 180초다(opal/tools/oppb-runtime-tool/probe.py:64). 새 테스트는 장시간 sleep을 피하고 작은 timeout 값으로 failure path를 검증한다. 설치본 task142 clone seal은 PM 선조회의 8명령 기준선을 소비하되 원본 task142에서는 실행하지 않는다(TASK.md:24-25, TASK.md:43-44).
- 실패 시: W-1 RED가 재현되지 않으면 구현 착수 전 PLAN/TASK 해석을 중단하고 fixture를 조정한다. W-2 이후 회귀가 나면 `probe.py`와 `test_probe.py` 변경만 되돌리고 문서 W-3을 진행하지 않는다. W-5 install 검증 실패 시 소스 변경은 유지하되 설치본 재배포를 재시도하고, task142 원본 해시 차이가 하나라도 있으면 즉시 blocked로 반환한다. late discovery, `scope_violation`, CLI exit 계약은 어느 복구 경로에서도 완화하지 않는다.
