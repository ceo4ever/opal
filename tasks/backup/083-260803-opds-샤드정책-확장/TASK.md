# TASK: 샤드 분할 파이프라인 — 2축 판정 + 분할 집행 + 유도

> 작성일: 2026-08-03 | 작업 유형: 개선 | 적용 스킬: opds | 모드: semi-agentic
> 입력: 사용자 요청 + 태스크 082 후속 + PM 실측 분포 분석
> 출력: TASK.md

## 작업 목표

태스크 082가 만든 **"쪼개진 상태를 도구가 이해한다"**에 이어, **"쪼개는 행위를 도구가 집행한다"**를 완성한다. 탐지 정확도를 2축(바이트 상한 + 파일 수 하한)으로 올리고, 탐지에서 실제 분할까지 이어지는 경로를 만든다.

## 배경

082는 매니페스트 크기 상한을 도입해 초과를 열거한다. 그런데 **탐지 다음이 비어 있다.**

```js
violations.push({ code: 'manifest_oversize', manifest: manifestRel, detail: `${size}/${limit}` });
```
`opal/tools/code-scan/code-scan.js:2150` — 출력에 한 줄이 찍히는 것이 전부다. 누가 무엇을 해야 하는지, 어떻게 쪼개는지 안내가 없고, 분할을 수행하는 서브명령도 **0건**이다(현행 13개 서브명령에 `split` 계열 없음).

그 결과 강제력(차단/비차단)을 어떻게 정하든 결말이 같다 — 차단하면 "막혔는데 푸는 법이 없음", 비차단하면 "경고만 쌓임". **해결 경로가 먼저다.**

동시에 현행 임계값(20480 단일 기준)에는 두 가지 한계가 있다.
- **트리거가 사실상 조각 크기의 상한이 된다** — 20KB 밑으로만 내리면 요구를 충족하므로 최대치 86.4KB는 5조각 × 약 17KB가 되어 조각 하나가 여전히 무겁다.
- **바이트 단독 기준은 오탐한다** — 서술이 길어서 큰 것과 항목이 많아서 큰 것을 구분하지 못한다. 전자는 나눌 의미 경계가 없다.

## 배경 분석 (대화에서 도출 — PM 실측)

### (1) 대규모 code-map 보유 실사용 프로젝트 1곳의 크기 분포

| 지표 | 실측값 |
|---|---|
| 전체 매니페스트 | 1,012개 · 합계 1,595.1KB |
| 중앙값 / p90 / p95 / p99 | 0.8KB / 3.0KB / 4.9KB / **10.7KB** |

| 트리거 후보 | 걸리는 수 | 전체 바이트 대비 |
|---|---|---|
| 10KB | **11개** | 19.8% |
| 20KB (082 현행) | 5개 | 14.9% |

### (2) 10~29KB 구간 — 파일당 바이트로 성격이 갈린다

| 크기 | 파일 수 | 파일당 | 성격 |
|---|---|---|---|
| 28.8KB | 128 | 230B | 항목 다수 → **분할 가능** |
| 16.1KB | **26** | **635B** | 서술 장문 → 분할 경계 없음 |
| 13.4KB | **29** | **472B** | 서술 장문 → 분할 경계 없음 |
| 12.7 / 12.6 / 12.4 / 10.7KB | 46 / 46 / 40 / 40 | 274~318B | 항목 다수 → 분할 가능 |

- 파일당 평균 약 280B인데 26·29파일짜리 둘만 **470~635B로 2배 이상**이다.

### (3) 2축 적용 시뮬레이션

```
10KB 초과 11개
  ├─ 40파일 이상  9개 → 분할 대상 (292·228·128·126·103·46·46·40·40 파일)
  └─ 40파일 미만  2개 → 제외      (26·29 파일 — 서술이 길 뿐)
```

### (4) 조각 크기 관점

| 목표 | 86.4KB 분할 결과 |
|---|---|
| 20KB 이하 | 약 5조각 × 17KB — 조각이 p99의 1.6배 |
| **10KB 이하** | 약 9조각 × 9.6KB — 조각이 **p99 수준에 안착** |

### (5) 분할 작업 분해 — 5단계 중 4개가 기계 작업

| # | 단계 | 성격 | 현재 |
|---|---|---|---|
| 1 | 엔트리를 의미 그룹으로 묶기 | **판단** (서술을 읽어야 함) | 사람/LLM |
| 2 | `_shards/{label}.json` 생성 | 기계 | 수작업 |
| 3 | 베이스에 `shards` 선언 추가 | 기계 | 수작업 |
| 4 | 엔트리를 베이스 → 샤드로 이동 | 기계 | 수작업 |
| 5 | 검증(`validate` 0건 · `scaffold` no-op) | 기계 | 수작업 |

- 292개 엔트리를 손으로 옮기는 것은 현실적이지 않다. **2~5를 도구가 집행**해야 한다.

### (6) 의미 판단은 자동화되지 않는다

- 파일명 접두사로 분류하면 상위 18개 토큰이 198건만 덮고 **90건이 "기타"**로 남는다.
- 도구의 역할은 **후보 제시 + 결정 집행**까지이며, 경계 확정은 사람/워커의 몫이다.

### (7) 082가 이미 갖춘 오버라이드 뼈대

`opal/tools/code-scan/code-scan.js:70, :880-884` — 내장 기본값 + `index.json` 오버라이드 + 타입 검증(`invalid_index`)이 이미 동작한다. 083은 **키를 늘리는 작업**이지 구조를 새로 세우는 작업이 아니다.

## 제약 조건

- **배포 경계 준수** — `~/.opal/tools/code-scan/`를 직접 편집하지 않는다. `opal/tools/code-scan/`만 수정하고 install로 배포한다.
- **골든 재캡처 절대 금지** — `fixtures/golden/*` 8파일은 회귀 기준선이다.
- **판정 지점 봉인 유지** — 정책 값을 읽는 지점 1곳, 샤드 해석은 `resolveShards` 1곳. 080·082가 세운 구조를 훼손하지 않는다. 3단 우선순위(`code-scan.json` > `~/.opal/setting.json` > 코드 상수)도 그 1곳 안에서만 해석한다.
- **전역 설정 격리** — 테스트는 개발자 실제 홈의 `~/.opal/setting.json`에 좌우되지 않아야 한다. 홈 경로를 주입 가능하게 만들고, 전역값 경로는 격리된 가짜 홈으로 검증한다.
- **전역 설정 비차단 폴백** — `~/.opal/setting.json` 부재·파싱 실패·키 부재는 모두 하위 단계로 폴백한다. `headerSource`식 전 명령 차단으로 승격하지 않는다.
- **install 시드 머지 안전** — `setting.json` 시드 시 기존 사용자값(`bootstrap`·`models`)을 덮어쓰거나 유실시키지 않는다.
- **엔트리 유실 0건** — `split`은 매니페스트를 쓰는 명령이다. 실행 전후 엔트리 총합이 반드시 같아야 하며, 실패 시 부분 상태를 남기지 않는다.
- **기존 픽스처 단언 완화 금지** — 기본값 변경으로 깨지면 픽스처에 정책 오버라이드를 명시해 흡수한다. 단언 삭제·skip·조건 완화는 금지한다.
- **워커 파괴적 git 명령 금지** — `stash`/`checkout`/`reset`/`clean`/`restore`/`rm`/`commit`/`add`/`gc`. 태스크 082에서 `git stash`로 미커밋 구현 424줄이 유실된 사고가 있었다. 읽기 전용(`status`/`diff`/`log`/`show`)만 허용하며, 깨끗한 상태 확인은 `cp -R` 임시 복사로 한다.
- **커밋 금지** — 소유자의 명시 요청 전까지 커밋하지 않는다.
