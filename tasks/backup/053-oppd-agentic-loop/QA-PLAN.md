# QA: PLAN — oppd Phase 3 agentic 자율 루핑 + 병렬 실행 설계

> 검토일: 2026-03-30 | 판정: **Needs Revision**

## 1. 요약

PLAN.md는 TASK.md의 4개 축(A-로드맵 세분화, B-자동 검증 루핑, C-병렬 실행, D-스킬/하네스 반영)을 체계적으로 분해하여 5개 Step의 구현 계획으로 변환했다. 현황 조사를 통해 영향 범위를 명확히 했고, 각 파일의 변경 필요 여부를 판정했으며, 실행 체크리스트와 QA 기준을 상세히 정의했다. 다만 몇 가지 설계 명세의 모호성과 실행 순서 검토 필요 사항이 있다.

## 3. 지적 사항

### Warning 1: Step 5 (oppd SKILL.md 반영)의 실행 범위 불명확

**위치**: Step 5 "작업 내용" 섹션 (P.261~273)

**문제**:
- "Phase 2 변경", "Phase 3 변경", "STATE.md 템플릿 변경"이 나열되었으나, 각 변경이 기존 SKILL.md의 어느 섹션(라인 범위)을 대체하거나 확장하는지 명시 부족
- "분할 원칙에 '자동 테스트 가능성' 기준 추가" → 기존 분할 원칙 1~6이 유지되고 7번이 추가되는지, 아니면 기존 내용이 재작성되는지 불명확
- "검증 명령" 필드 필수화 → ROADMAP.md 테이블에 새 컬럼으로 추가하는 것인지, 기존 컬럼을 대체하는 것인지 구분 필요

**권고**: 기존 SKILL.md의 Phase 2, 3 섹션을 제시하고, 추가/변경/삭제할 부분을 비교 표시해야 명확함. 또는 Phase 5 작업 내용을 "기존 유지 + 추가" 형태로 세분화할 것.

---

### Warning 2: Step 4 (roadmap-guide.md 강화)의 의존성 순서

**위치**: 구현 순서 (P.85~91) 및 Step 4 (P.244~256)

**문제**:
- 현재 구현 순서는 Step 1 → 2 → 3 → 4 → 5로 직렬화되어 있음
- 하지만 Step 2, 3 (verification-loop-guide.md, parallel-execution-guide.md 신규 작성)은 Step 1 (하네스 확장)만 의존하고, Step 4 (roadmap-guide 강화)는 Step 2, 3만 의존함
- **이론적으로는 Step 2, 3, 4가 병렬 실행 가능**하나, PLAN에서는 순차 진행으로 제시됨

**권고**:
- PLAN의 "구현 순서"를 수정하여 Step 2, 3, 4의 병렬 가능성 명시
- 또는 순차 고집 사유를 명시 (예: Step 4가 Step 2, 3 가이드를 참조해야 하므로 순차 필수)

---

### Warning 3: Step 1 (하네스) — State 확장 설계의 구체성 부족

**위치**: "Step 1: opal-harness.md 확장" (P.95~127)

**문제**:
- "병렬 실행 State" 섹션 예시가 매우 단순함:
  ```markdown
  ## 병렬 실행 현황
  | 그룹 | 태스크 | worktree | 브랜치 | 상태 |
  |------|--------|----------|--------|------|
  ```
- 이 테이블 구조만으로는 다음이 불명확:
  1. 상태(State) 값의 열거형은 무엇인가? (`진행 중 / 완료 / 실패`?)
  2. worktree 컬럼 데이터는 어떤 형식? (`.claude/worktrees/group-a-task-1`?)
  3. 병렬 그룹이 완료된 후, 병렬 머지 결과(성공/충돌)를 어디에 기록하는가?
  4. 병렬 그룹 내 개별 태스크 상태 추적 vs 그룹 전체 상태 추적을 어떻게 구분하는가?

**권고**:
- 병렬 실행 State 예시를 확대 (실제 병렬 그룹 3개, 각 그룹 내 2~3개 태스크로 구성된 샘플 보여주기)
- "머지 후 상태" 컬럼 또는 별도 섹션 추가 (예: "## 병렬 머지 이력")
- 상태 값 정의 (State Enum)를 명시

---

### Warning 4: Step 2, 3 (가이드 작성)의 "상세 기술" 구체화 부족

**위치**: "Step 2: verification-loop-guide.md" (P.214~227), "Step 3: parallel-execution-guide.md" (P.229~242)

**문제**:
- "Layered Verification 모델 정의", "worktree 격리 전략"과 같은 목표는 명시되나, 실제 가이드 문서가 어떤 구조/섹션을 가져야 하는지 불명확
- Step 2의 "각 유형의 감지 방법, 자동 수정 프로세스, 컨텍스트 전달 방법" → 예를 들어 lint 오류를 감지하는 파이썬 정규식, 자동 수정 명령어, 오류 메시지를 워커에게 전달하는 프롬프트 형식이 무엇인지 모호함
- Step 3의 "의존성 그래프 분석: ROADMAP.md에서 병렬 그룹 판별 로직" → 실제 의존성 그래프를 ROADMAP.md의 어느 컬럼에서 추출하고, 어떤 알고리즘으로 병렬 그룹을 판별할 것인가?

**권과**:
- Step 2, 3에 "가이드 구조 예시" 추가 (예: "# verification-loop-guide.md 목차" 형태로 주요 섹션 나열)
- lint 오류 감지/수정의 구체적 예시 1개 포함 (예: "Prettier 포맷 오류 → `npm run format` 자동 실행 → 재검증" 흐름 명시)
- 의존성 그래프 판별 알고리즘 의사코드 1개 제시 (예: "의존성 컬럼 파싱 → Topological Sort → 동일 레벨 태스크 병렬 그룹화")

## 5. 판정

**Needs Revision**

PLAN.md는 TASK.md의 요구사항을 충실히 분해했고, 5개 Step의 실행 계획과 체크리스트가 체계적이다. 하지만 다음 3가지 사항을 개선해야 한다:

1. **Step 5 (oppd SKILL.md 반영)**: 기존 SKILL.md의 어느 부분을 어떻게 변경할 것인지 명시 필요 (추가/변경/삭제를 구분)
2. **Step 2, 3 (가이드 작성)**: 구체적 가이드 구조/섹션 및 1~2개 실행 예시 추가 필요
3. **Step 1 (하네스 State 확장)**: 병렬 실행 State 테이블 설계를 확대하여 그룹 추적, 머지 이력, 상태 정의 등 명확히 필요

이 3가지를 보완하면 PLAN은 실행 팀이 바로 구현에 진입할 수 있는 수준이 된다.
