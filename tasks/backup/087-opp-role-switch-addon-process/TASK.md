# TASK: 알투 역할 전환 규칙 + 태스크 추가작업 프로세스 정의

> 작성일: 2026-04-05 | 작업 유형: 개선 | 적용 스킬: opp | 모드: interactive
> 입력: 사용자 요청 + 대화 컨텍스트
> 출력: TASK.md

## 작업 목표

알투(비서)와 알투(PM)의 역할 전환 기준을 명시하고, 태스크 완료 후 추가작업 프로세스를 정의하며, op-task 스킬의 요구사항 작성 기준을 개선한다.

## 배경

### 문제 발단

디스패치 의무 원칙 위반 분석 과정에서, 근본 원인이 "하네스에 규칙이 없어서"가 아니라 "알투가 PM 모드임에도 비서처럼 직접 실행한 것"임을 확인했다. 이를 계기로 역할 전환 기준의 부재가 드러났다.

### 핵심 문제 3가지

**1. 역할 구분 불가**

캡틴이 알투와 대화 중 현재 알투가 비서인지 PM인지 알 수 없다.

> 캡틴: "PM일듯 한데, 나는 알수가 없음"

**2. 비서가 코드를 수정하면 하네스가 작동하지 않음**

- 알투는 부트스트랩 Eager 3단계에서 하네스를 로드함 (캡틴 확인)
- 그러나 하네스(Guards, Gates, QA)는 PM 프로세스에서만 작동함
- 비서가 코드를 수정하면 QA Gate, PM Gate 등 검증 장치가 전혀 없음
- **코드 수정은 반드시 PM이 해야** QA/PM Gate 등 검증이 가능함

**3. 태스크 완료 후 추가작업 절차 부재**

태스크 완료 직후 관련 수정/보완이 필요할 때 처리 절차가 없어서, 새 태스크를 만들거나 비서가 하네스 없이 직접 수정하게 됨.

### 대화에서 도출된 3가지 상황

| 상황 | 설명 | 현재 문제 |
|------|------|----------|
| 1) 태스크 없이 대화 중 | 비서로 대화하다가 코드 수정이 필요해짐 | 비서가 바로 수정 → 하네스 미적용 |
| 2) 태스크 진행 중 | PM으로 작업 중인데 캡틴이 모름 | 캡틴에게 모드 표시 없음 |
| 3) 태스크 완료 직후 | 추가 수정/보완 필요 | 처리 절차 없음 |

### op-task 스킬 문제 (이번 태스크 진행 중 발견)

087 TASK.md 초안 작성 과정에서 다음 문제가 드러남:
- 대화에서 확정된 설계 방향이 TASK.md에 반영되지 않음
- 요구사항이 "정의해라" 수준으로 두리뭉실 → PLAN 워커가 구체화 불가
- 인터뷰로 명확화해야 할 항목을 애매한 채로 넘김

## 확정된 설계 방향 (대화에서 합의)

### 1. 코드 수정 시 PM 전환 제안 메커니즘

비서가 코드 수정이 필요한 시점에 PM 프로세스를 **제안**한다. 최종 결정은 캡틴에게 있다.

```
캡틴: "여기 좀 고쳐줘"
알투(비서): 코드 수정이 필요한 작업입니다.
            PM 프로세스로 진행할까요? (QA/검증 포함)
            아니면 바로 수정할까요?

캡틴: → "PM으로 해" → 알투[PM] 전환, 하네스 작동
      → "그냥 해"   → 알투(비서)가 직접 수정, 하네스 미적용
```

- AGENT.md "주도성" 규칙과 일치: "에이전트는 제안하고 기다린다"
- 캡틴이 리스크를 인지하고 선택 → 비서용 하네스를 별도로 만들 필요 없음

### 2. 역할 전환 기준

| 케이스 | 조건 | 역할 | 동작 |
|--------|------|------|------|
| `//` 스킬 호출 | `//` 커맨드 입력 | PM | 스킬 파이프라인 진입, 하네스 적용 |
| 코드/파일 수정 필요 | 대화 중 수정 요청 감지 | **비서가 PM 전환 제안** | 캡틴 선택: PM(하네스) or 비서(직접) |
| 태스크 진행 중 | 관련 작업 | PM (이미) | 현재 파이프라인에서 처리 |
| 태스크 완료 직후 | 관련 후속 작업 | PM | 추가작업 프로세스 진입 |
| 대화/설명/분석/읽기 | 코드 수정 없는 모든 것 | 비서 | 직접 수행, 하네스 불필요 |

### 3. PM 모드 표시

- PM 모드: `📋 알투[PM]: {NNN} {태스크명} | {단계}` — 캡틴이 즉시 인식 가능
- 비서 모드: 별도 표시 없음 (기본)

### 4. 역할 전환의 주체

**규칙 기반 + 캡틴 오버라이드**
- AGENT.md에 전환 조건을 명시적으로 정의 → 알투는 규칙을 따름
- 캡틴은 언제든 오버라이드 가능 (`//` 호출 또는 "PM으로 해" / "그냥 해")

### 5. 추가작업 프로세스

- STATE.md 상태: `완료` → `추가작업중` → `추가작업완료`
- ADD_DONE.md: 추가작업 내용 기록 (DONE.md는 원본 보존)
- 진입점 2가지: PM 자동 감지 + 캡틴 명시 요청
- 공통 프로세스는 opal-harness.md에, 스킬별 검증 차이는 각 SKILL.md에서 오버라이드

### 6. 추가작업 감지 조건 (PM 자동 인식)

다음 중 하나 이상 해당 시 추가작업으로 판단:
- (a) 완료된 태스크의 산출물 파일을 수정해야 할 때
- (b) 완료된 태스크와 같은 도메인의 코드를 수정해야 할 때
- (c) 캡틴이 완료된 태스크를 언급하며 수정 요청할 때

### 7. 요구사항 작성 기준 (op-task 개선)

각 요구사항 항목은 다음을 포함한다:
- **무엇을**: 변경/생성할 내용 (구체적 행위)
- **어디에**: 반영 대상 문서 + 섹션
- **왜**: 확정 방향 참조 또는 근거
- **AC**: 검증 가능한 수용 기준 (QA Gate에서 Pass/Fail 판정 가능한 문장)
