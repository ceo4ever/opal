# PLAN: --wt 워크트리 세션으로의 태스크 소유권 이관 계약

> 입력: [TASK.md](TASK.md)

## Approach

소유권 축을 두 개 그대로 둔 채(실행 lease = `<task>/run/.runtime/owner.json`, registry `execution_ownership`), **허브 → 워크트리 세션 이관 상태를 lease 레코드에 1개 추가**해 `state init` 이후 기동이라는 현행 순서(`harness/worktree.md` §실행 세션 기동과 터미널 회수 경계 [MUST])를 바꾸지 않고 AC-1을 만족시킨다.

변경은 다섯 축이다.

1. `lease.py`에 이관 상태(`handoff_pending`)와 이관·취소 API를 추가하고, `claim`이 그 상태를 **지정된 워크트리 루트에서 온 claim에만** 개방한다(C-3).
2. `ownership_tool/cli.py`를 신설해 `run.sh`의 `not_implemented`를 없애고 조회·해제·이관 표면을 만든다(AC-5~AC-7).
3. `worktree-launcher`가 `adapter.launch` **직전**에 그 CLI로 이관을 수행한다(AC-1). launcher는 registry 쓰기를 `worktree-tool ownership-set`에 위임하는 기존 패턴과 동일하게 lease 쓰기를 ownership-tool CLI에 위임하고 자체 lease 로직을 갖지 않는다.
4. SessionStart claim 호출자(`session_start_hook.py`)와 상태 전이 claim 호출자(`state_tool.py`)가 claim 주체 루트를 명시 전달하고, registry 소유자 등록 실패에 진단을 남긴다(AC-3·AC-4).
5. `harness/worktree.md`·`harness/task-process.md`에 소유권 획득·이관·해제 계약을 신설한다(AC-8·AC-9).

범위 밖: 가드 차단 대상 도구 목록, Stop 판정, 비 `--wt` 경로, 태스크 149의 훅 런타임 루트 해석 결함.

code-scan 실측(`~/.opal/tools/code-scan/run.sh search "ownership_tool"`): `ownership_tool/` 전 모듈이 `layer=util`, `domain=opal-pipeline`으로 등재되어 있고 `lease.py`의 `exports`는 `claim`·`heartbeat`·`release`·`classify`·`resolve_ttl_sec`·`resolve_claim_source`·`CLAIM_SOURCES`, `depends`는 `ownership_tool.ownership_core` 단일이다. 이번 변경은 이 `layer`/`domain` 배치와 단방향 `depends`를 바꾸지 않는다.

| D-5. 이관에는 짧은 만료가 있다 | `handoff_expires_at` 경과 후의 `handoff_pending` 레코드는 `classify`·`claim`에서 무소유(`unowned`)로 접혀 허브가 되찾을 수 있다. 기본 이관 TTL은 lease TTL과 분리한 별도 기본값(초 단위 상수)이며 `claim`의 `ttl_sec` 해석 경로는 건드리지 않는다 | 터미널이 끝내 부팅하지 않는 경로(사용자 창 닫기 등)에서 태스크가 영구히 잠기면 이번 결함을 형태만 바꿔 재생산한다. `_revert`가 닿지 못하는 잔여 경로의 유일한 복구 수단이다 |
| D-6. `release`는 소유자 일치 또는 이관 출발 세션에만 허용하고 강제 해제(`--force`)를 만들지 않는다 | `ownership-tool release`는 `OPAL_SESSION_ID`(또는 `--session-id`)가 현 `owner_session_id`와 일치할 때만 해제하고, 불일치는 `{"ok":false,"error":"not_owner","owner_session_id":...}`로 거부한다. 부재·이미 released·만료는 `noop:true`로 성공 반환한다 | C-3은 "이전은 현 소유자의 명시 해제 또는 만료를 거친다"이다. 강제 해제 표면은 그 경계를 CLI로 우회 가능하게 만든다. 태스크 149는 허브 세션이 소유자이므로 그 세션에서 실행하면 소유자 일치 경로로 풀린다(AC-6) |
| D-7. registry 소유자 등록은 claim 성공에 계속 종속시키고, 실패 시 **진단**을 남긴다 (Open question 3) | `session_start_hook.handle()`의 claim 실패 분기가 `diagnostics`에 `registry_owner_not_registered:<classification>`을 추가하고 `registry_owner_registered=False`를 유지한다. 성공 분기 동작은 불변 | 등록을 claim 밖으로 빼면 소유하지 않은 세션이 registry의 `owner_session_id`가 되어 C-2(가드 약화 금지)와 registry의 의미가 함께 무너진다. AC-4는 "등록되지 않은 사유가 진단으로 남는다"를 대안으로 명시한다 |
| D-8. 가드·heartbeat는 변경하지 않는다 | `pretooluse_guard_hook`은 `classify` 결과가 `foreign_session_owned`일 때만 차단한다는 현행 판정(`pretooluse_guard_hook.py:158-190`)을 그대로 두고, `handoff_pending` 레코드는 `owner_session_id`가 비어 `classify`가 이미 `unowned`을 반환한다. `heartbeat`는 `owner_session_id` 일치에서만 갱신하므로(`lease.py:190-199`) 허브의 PostToolUse heartbeat가 이관된 레코드를 되살리지 않는다 | C-2. 차단 로직을 건드리지 않고 이관만으로 AC-2가 성립하는지가 이 설계의 핵심 검증 지점이며 H-1·H-4로 관리한다 |
| D-9. 문서 이력 절을 만들지 않는다 | 신설·갱신하는 harness 문서에 수기 누적 이력 절을 두지 않고 현재 계약만 기술한다 | `opal/core/references/opal-doc-standard.md` §5 |
| D-10. 배포는 install 경유다 | `~/.opal/` 배포본을 직접 편집하지 않고 프로젝트 소스 수정 후 `scripts/install-mac.sh`로 배포한다 | [MUST] `.opal/AGENT.md` 금지사항: `**\`~/.opal/\` 직접 편집 금지** — 항상 프로젝트 소스를 수정한 후 install로 배포한다.` (C-8) |

## Release and recovery

- 적용 순서: P1(W-1 lease, W-2 문서) → P2(W-3 CLI, W-4 SessionStart, W-5 state-tool) → P3(W-6 launcher, W-7 install) → P4(W-8 통합 회귀). 코드 배포는 P3 완료 후 `scripts/install-mac.sh` 1회 실행이며 `~/.opal/` 직접 편집은 없다(D-10, C-8).
- 검증 범위: 결정론 — W-1·W-3·W-4·W-5·W-6 단위 테스트(고정 `now`·임시 task 디렉터리). 회귀 — 4개 도구 테스트 전건 + `scripts/tests/test_hook_parity.py`(AC-11), 비 `--wt` 경로 불변(AC-10), harness 문서 grep(AC-8). 실제 연동 — install 후 신규 `--wt` 태스크 1건의 기동~첫 쓰기(AC-1·AC-2·AC-3·AC-12)와 태스크 149 실물 해제(AC-6). 실제 연동 2건은 TEST 단계에서 PM 승인 아래 실행한다.
- 실패 시: install 전에는 소스 되돌림만으로 복구된다(배포본 무변경). install 후 회귀가 발견되면 이전 커밋으로 되돌려 재-install하며, 그 사이 잠긴 태스크는 `ownership-tool release`(소유 세션) 또는 `handoff-cancel`로 해소한다. 이관 상태는 `owner.json` 한 파일에만 존재하므로 registry·`state.json` 롤백은 필요하지 않다.
