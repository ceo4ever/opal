# TASK: 하네스 병렬 실행 제한 및 리소스 관리 원칙 추가

> 작성일: 2026-04-02 | 작업 유형: 개선 | 적용 스킬: opp
> 입력: 캡틴 피드백 (대용량 문서 병렬 처리 시 메모리 이슈)
> 출력: opal-harness.md 수정, 병렬 실행 제어 로직 설계

## 작업 목표

1. `opal-harness.md`에 리소스 상황에 따른 **병렬 실행 제한(Concurrency Limit)** 원칙을 추가한다.
2. 대용량 애셋(문서, 코드 등) 처리 시 안전한 실행을 위한 **Adaptive Batching** 또는 **순차 폴백(Sequential Fallback)** 지침을 수립한다.

## 배경

**병렬 처리의 부작용**
최근 067 태스크에서 "독립 작업은 무조건 병렬" 원칙을 강화했으나, 문서 용량이 큰 경우 6개 이상의 에이전트가 동시 가동되면서 메모리 부족으로 시스템이 정지하는 문제가 발생함.

**유연한 제어 필요**
무조건적인 병렬이 아닌, 파일 크기나 시스템 리소스 상황에 따라 병렬 개수를 조절(예: 2개씩)하거나 순차적으로 처리할 수 있는 판단 기준이 하네스 레벨에서 필요함.

## 요구사항

### T1. 하네스 원칙 수정 (opal-harness.md §7)

- [ ] **Concurrency Limit 명시**: 기본 병렬 원칙은 유지하되, 리소스 집약적 작업(대용량 파일)에 대한 제한 규정 추가.
- [ ] **판단 기준 수립**: 파일 크기, 작업 복잡도 등에 따른 병렬 개수 권장값 (예: 대용량 문서 수정 시 Max 2).
- [ ] **순차 폴백 지침**: 리소스 이슈 발생 가능성 인지 시 PM이 스스로 순차 또는 소규모 배치로 전환하는 지침.

### T2. 오케스트레이터 적용 가이드

- [ ] `opwt` 등 다량의 문서를 다루는 스킬에서 `diagnosis.json` 배치 편성 시 리소스 부하를 고려하도록 가이드 업데이트.
- [ ] 에이전트 디스패치 전 리소스 상황(파일 크기 등)을 사전 체크하는 로직 제안.

## 제약 조건

- 기존 "병렬 우선" 기조를 훼손하지 않으면서 "안전" 옵션을 추가하는 방식으로 설계.
- 하네스 변경 사항은 모든 오케스트레이터에 즉시 적용 가능해야 함.
- 배포 동기화 필수 (`~/.opal/` 반영).
