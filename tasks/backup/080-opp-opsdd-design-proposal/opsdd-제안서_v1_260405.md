opsdd 설계 제안서                                                                                                                                      
                                    
  1. 설계 철학
                                                                                                                                                         
  SDD의 진짜 가치는 세 가지입니다:                                                                                                                       
                                                                                                                                                         
  1. 명세가 SSOT — "무엇을 만들지"가 코드에 묻히지 않음                                                                                                  
  2. 검증 선행 — 구현 전에 명세와 태스크를 검증하여 환각/스코프 드리프트 방지
  3. 양방향 추적성 — AC ↔ 테스트 ↔ 태스크 ↔ 코드의 전 과정 추적                                                                                          
                                                                                                                                                         
  리서치에서 확인된 주요 함정도 고려했습니다:                                                                                                            
                                                                                                                                                         
  ┌────────────────────────────────────────────┬───────────────────────────────────────────────┐                                                         
  │                    함정                    │                     대응                      │
  ├────────────────────────────────────────────┼───────────────────────────────────────────────┤
  │ Spec Theater (아무도 안 읽는 거대 스펙)    │ 기능 단위로 스코프 제한, 훑어보게 되면 분할   │
  ├────────────────────────────────────────────┼───────────────────────────────────────────────┤
  │ Spec/Code Drift (스펙이 금방 구식)         │ 코드 우선 원칙 유지 + opi 최신화 연계         │                                                         
  ├────────────────────────────────────────────┼───────────────────────────────────────────────┤                                                         
  │ Over-specification (버그 수정에 전체 스펙) │ opsdd는 기능 단위 개발 전용, 단순 작업은 opds │                                                         
  ├────────────────────────────────────────────┼───────────────────────────────────────────────┤                                                         
  │ Waterfall 회귀 (스펙에 고착)               │ 구현 중 발견된 통찰을 spec.md에 반영 허용     │
  └────────────────────────────────────────────┴───────────────────────────────────────────────┘                                                         
                                    
  ---                                                                                                                                                    
  2. 파이프라인 전체 흐름           
                                                                                                                                                         
  캡틴이 제안하신 프로세스를 기반으로, 6단계로 구체화했습니다:
                                                                                                                                                         
  Phase 1: SPEC        — 기능 명세 작성
  Phase 2: SPEC-VERIFY — 명세 검증 + 수용 테스트 시나리오 도출 (TDD Red)                                                                                 
  Phase 3: TASKS       — 태스크 분해                                                                                                                     
  Phase 4: TASKS-VERIFY — 분해 검증 (커버리지 + 의존관계)                                                                                                
  Phase 5: EXECUTE-LOOP — 태스크별 반복 (PLAN → EXECUTE → TEST)                                                                                          
  Phase 6: DONE        — 최종 검증 + 완료
                                                                                                                                                         
  기존 OPAL과의 비교:                                                                                                                                    
                                                                                                                                                         
  opd:    TASK → ANALYSIS → PLAN → EXECUTE → QA         (단일 태스크)                                                                                    
  opds:   TASK → PLAN → EXECUTE → QA                     (단일 태스크, 경량)
  oppd:   PRD/TRD → WBS → 액션 루프                       (프로젝트 전체)                                                                                
  opsdd:  SPEC → VERIFY → TASKS → VERIFY → 태스크 루프    (기능 단위, 명세 중심)                                                                         
                                                                                                                                                         
  ---                                                                                                                                                    
  3. 폴더 구조                                                                                                                                           
                                    
  project-root/
  ├── specs/                           ← SDD 워크스페이스 (프로젝트 레벨)                                                                                
  │   └── {feature-name}/
  │       ├── spec.md                  # 기능 명세 (SSOT)                                                                                                
  │       ├── tasks.md                 # 태스크 분해 (의존관계 + AC 매핑)
  │       ├── validate.md              # 검증 저널 (모든 검증 결과 누적)                                                                                 
  │       ├── tests/                                                                                                                                     
  │       │   ├── test-scenarios.md    # AC → 테스트 시나리오 매핑 (TDD Red)                                                                             
  │       │   └── test_*.py (등)       # 테스트 스켈레톤/코드 (EXECUTE 시 생성)                                                                          
  │       └── tasks/                                                                                                                                     
  │           ├── T1-{name}/           # 개별 태스크 실행 공간                                                                                           
  │           │   ├── PLAN.md                                                                                                                            
  │           │   └── (실행 산출물) 
  │           └── T2-{name}/                                                                                                                             
  │               └── ...           
  │                                                                                                                                                      
  ├── tasks/                           ← OPAL 오케스트레이터 상태 관리
  │   └── {NNN}-opsdd-{feature}/
  │       ├── TASK.md                  # 하네스 TASK (요구사항 정리)                                                                                     
  │       └── STATE.md                 # 진행 상태 추적                                                                                                  
  │                                                                                                                                                      
  ├── src/                             ← 실제 구현 코드                                                                                                  
  └── docs/                            ← 프로젝트 문서                                                                                                   
  
  설계 의도:                                                                                                                                             
  - specs/ — 기능별 명세+검증+실행의 자기 완결적 공간. 기능이 쌓이면 프로젝트의 기능 문서 아카이브가 됨
  - tasks/ — OPAL 하네스의 상태 관리용 (STATE.md, TASK.md). 기존 패턴 유지                                                                               
  - 구현 코드는 src/에, 테스트 시나리오 정의는 specs/{feature}/tests/에, 실제 테스트 코드는 프로젝트 테스트 디렉토리에
                                                                                                                                                         
  ---                                                                                                                                                    
  4. 각 Phase 상세 설계                                                                                                                                  
                                                                                                                                                         
  Phase 1: SPEC (기능 명세 작성)    

  수행 방식: 워커 디스패치 (신규 단계 스킬 op-dev-spec)                                                                                                  
   
  ┌──────┬───────────────────────────────┐                                                                                                               
  │ 항목 │             내용              │
  ├──────┼───────────────────────────────┤
  │ 입력 │ TASK.md (사용자 요구사항)     │
  ├──────┼───────────────────────────────┤
  │ 출력 │ specs/{feature}/spec.md       │                                                                                                               
  ├──────┼───────────────────────────────┤
  │ 워커 │ opal-task-agent → op-dev-spec │                                                                                                               
  ├──────┼───────────────────────────────┤                                                                                                               
  │ 모델 │ advanced (추론 집약적)        │
  └──────┴───────────────────────────────┘                                                                                                               
                                    
  spec.md 구조:                                                                                                                                          
                                    
  # SPEC: {기능명}
                                                                                                                                                         
  > 버전: 1.0 | 작성일: YYYY-MM-DD | 상태: Draft → Verified
                                                                                                                                                         
  ## Background                                                                                                                                          
  왜 이 기능이 필요한지 (비즈니스 맥락)
                                                                                                                                                         
  ## Goals                          
  이 기능이 달성해야 할 것
                                                                                                                                                         
  ## Non-goals
  명시적으로 범위 밖인 것                                                                                                                                
                                                                                                                                                         
  ## User Stories
  - As a {역할}, I want {기능}, so that {가치}                                                                                                           
                                                                                                                                                         
  ## Functional Requirements
  - [FR-01] {기능 요구사항}                                                                                                                              
  - [FR-02] ...                     
                                                                                                                                                         
  ## Acceptance Criteria
  - [AC-01] GIVEN {전제} WHEN {행동} THEN {기대 결과}                                                                                                    
  - [AC-02] ...                                                                                                                                          
   
  ## Edge Cases                                                                                                                                          
  - [EC-01] {예외 상황과 기대 동작} 
                                                                                                                                                         
  ## Non-functional Requirements
  - [NFR-01] {성능/보안/접근성 등}                                                                                                                       
                                                                                                                                                         
  ## Constraints
  기술적·정책적 제약                                                                                                                                     
                                                                                                                                                         
  ## Open Questions
  - [OQ-01] {미결정 사항} → 해결 전까지 Phase 2 진행 불가                                                                                                
                                                                                                                                                         
  핵심 원칙:
  - AC는 반드시 GIVEN/WHEN/THEN 형식 (테스트 시나리오 자동 도출의 기반)                                                                                  
  - Open Questions가 하나라도 남아있으면 Phase 2로 진행 불가                                                                                             
  - 캡틴이 한눈에 읽을 수 있는 분량 유지 (훑어보게 되면 기능 분할 제안)
                                                                                                                                                         
  게이트: 캡틴 승인                                                                                                                                      
                                                                                                                                                         
  ---                                                                                                                                                    
  Phase 2: SPEC-VERIFY (명세 검증 + 테스트 시나리오 도출)                                                                                                
                                                                                                                                                         
  수행 방식: 워커 디스패치 (신규 에이전트 또는 QA 에이전트 확장)
                                                                                                                                                         
  ┌──────┬────────────────────────────────────────────────────────┐
  │ 항목 │                          내용                          │                                                                                      
  ├──────┼────────────────────────────────────────────────────────┤
  │ 입력 │ spec.md + 프로젝트 컨텍스트 (ARCHITECTURE.md 등)       │
  ├──────┼────────────────────────────────────────────────────────┤
  │ 출력 │ validate.md (SPEC 검증 섹션) + tests/test-scenarios.md │                                                                                      
  ├──────┼────────────────────────────────────────────────────────┤                                                                                      
  │ 모델 │ advanced                                               │                                                                                      
  └──────┴────────────────────────────────────────────────────────┘                                                                                      
                                    
  검증 3계층:                                                                                                                                            
                                    
  ┌────────┬─────────────────────────────────────────┬────────────────────┐                                                                              
  │  계층  │                검증 내용                │        방법        │
  ├────────┼─────────────────────────────────────────┼────────────────────┤                                                                              
  │ 구조적 │ 필수 섹션 존재, AC 형식, OQ 해소 여부   │ 규칙 기반 체크     │
  ├────────┼─────────────────────────────────────────┼────────────────────┤
  │ 의미적 │ 내부 일관성, Goals↔AC 정합, 모호성      │ AI 에이전트 분석   │                                                                              
  │        │ 탐지                                    │                    │                                                                              
  ├────────┼─────────────────────────────────────────┼────────────────────┤                                                                              
  │ 도메인 │ 프로젝트 아키텍처/컨벤션과 충돌 여부    │ 프로젝트 문서 대조 │                                                                              
  └────────┴─────────────────────────────────────────┴────────────────────┘                                                                              
  
  TDD 통합 — "Red" 단계:                                                                                                                                 
                                    
  spec.md의 AC로부터 test-scenarios.md를 자동 도출합니다:                                                                                                
  
  # Test Scenarios: {기능명}                                                                                                                             
                                                                                                                                                         
  > spec.md v1.0 기준 | 자동 도출 + 수동 보완                                                                                                            
                                                                                                                                                         
  ## 추적 매트릭스                                                                                                                                       
                                    
  | AC | 시나리오 ID | 유형 | 설명 | 상태 |                                                                                                              
  |----|------------|------|------|------|
  | AC-01 | TS-01 | unit | 정상 로그인 시 토큰 반환 | ⬜ Red |                                                                                           
  | AC-01 | TS-02 | unit | 잘못된 비밀번호 시 401 | ⬜ Red |                                                                                             
  | AC-02 | TS-03 | integration | 세션 만료 후 리다이렉트 | ⬜ Red |                                                                                     
  | EC-01 | TS-04 | unit | 계정 잠금 시 429 | ⬜ Red |                                                                                                   
                                                                                                                                                         
  ## 시나리오 상세                                                                                                                                       
                                                                                                                                                         
  ### TS-01: 정상 로그인 시 토큰 반환                                                                                                                    
  - **출처**: AC-01
  - **GIVEN**: 유효한 이메일/비밀번호                                                                                                                    
  - **WHEN**: POST /auth/login                                                                                                                           
  - **THEN**: 200 + JWT 토큰 반환
  - **검증 방법**: unit test                                                                                                                             
  - **상태**: ⬜ Red (구현 전)                                                                                                                           
                                                                                                                                                         
  왜 이 단계에서 테스트 시나리오를?                                                                                                                      
  - 구현 전에 "이걸 어떻게 검증할 것인가"를 먼저 정의 → TDD의 Red 단계                                                                                   
  - 태스크 분해 시 "이 태스크가 어떤 테스트를 통과시켜야 하는지" 명확                                                                                    
  - AC가 테스트 불가능하면 이 단계에서 잡힘 (스펙 자체의 품질 검증)  
                                                                                                                                                         
  validate.md 구조 (누적형):                                                                                                                             
                                                                                                                                                         
  # Validation Journal: {기능명}                                                                                                                         
                                                                                                                                                         
  ## SPEC 검증 (Phase 2)                                                                                                                                 
  - 수행일: YYYY-MM-DD
  - 검증자: {agent}                                                                                                                                      
                                    
  ### 구조적 검증                                                                                                                                        
  | 항목 | 결과 | 비고 |
  |------|------|------|                                                                                                                                 
  | 필수 섹션 | ✅ Pass | |         
  | AC 형식 (GIVEN/WHEN/THEN) | ✅ Pass | 5개 AC |                                                                                                       
  | Open Questions 해소 | ✅ Pass | 0개 잔존 |
                                                                                                                                                         
  ### 의미적 검증                   
  | 항목 | 결과 | 비고 |                                                                                                                                 
  |------|------|------|            
  | Goals ↔ AC 정합 | ✅ Pass | |                                                                                                                        
  | FR 커버리지 | ⚠️  Warning | FR-03에 대응 AC 없음 |
  | 모호성 | ✅ Pass | |                                                                                                                                 
                                                                                                                                                         
  ### 도메인 검증                                                                                                                                        
  | 항목 | 결과 | 비고 |                                                                                                                                 
  |------|------|------|            
  | 아키텍처 정합 | ✅ Pass | |
  | 컨벤션 준수 | ✅ Pass | |                                                                                                                            
  
  ### 테스트 시나리오 도출                                                                                                                               
  - 총 시나리오: 8개 (unit: 5, integration: 2, e2e: 1)
  - AC 커버리지: 100% (5/5 AC → 8 시나리오)                                                                                                              
                                                                                                                                                         
  ### 판정: ✅ Pass (Warning 1건 — FR-03 AC 보충 권장)                                                                                                   
                                                                                                                                                         
  (이후 Phase 4, Phase 6 검증 결과가 아래에 누적됨)                                                                                                      
                                    
  게이트: 캡틴 승인 (Warning은 캡틴 판단, Critical은 재작성)

  Phase 3: TASKS (태스크 분해)      
                                                                                                                                                         
  수행 방식: 워커 디스패치 (신규 단계 스킬 op-dev-tasks-decompose 또는 기존 확장)
                                                                                                                                                         
  ┌──────┬─────────────────────────────────────────────────┐
  │ 항목 │                      내용                       │                                                                                             
  ├──────┼─────────────────────────────────────────────────┤
  │ 입력 │ spec.md + test-scenarios.md + 프로젝트 컨텍스트 │
  ├──────┼─────────────────────────────────────────────────┤
  │ 출력 │ specs/{feature}/tasks.md                        │                                                                                             
  ├──────┼─────────────────────────────────────────────────┤
  │ 모델 │ advanced                                        │                                                                                             
  └──────┴─────────────────────────────────────────────────┘

  tasks.md 구조:

  # Tasks: {기능명}
                                                                                                                                                         
  > spec.md v1.0 기준 | 총 태스크: 4개
                                                                                                                                                         
  ## 의존관계 그래프                                                                                                                                     
  T1 → T2 → T4
  T1 → T3 → T4                                                                                                                                           
                                    
  ## 태스크 목록

  ### T1: {데이터 모델 정의}                                                                                                                             
  - **범위**: User 모델 + Migration
  - **AC 매핑**: AC-01, AC-02                                                                                                                            
  - **테스트 매핑**: TS-01, TS-02, TS-03
  - **의존**: 없음 (독립)                                                                                                                                
  - **예상 규모**: Small (opds)                                                                                                                          
  - **완료 기준**: TS-01, TS-02 Green                                                                                                                    
  - **상태**: ⬜ 대기                                                                                                                                    
                                    
  ### T2: {인증 API 구현}                                                                                                                                
  - **범위**: POST /auth/login, /auth/logout
  - **AC 매핑**: AC-01, AC-03                                                                                                                            
  - **테스트 매핑**: TS-01, TS-02, TS-04
  - **의존**: T1                                                                                                                                         
  - **예상 규모**: Standard (opds)  
  - **완료 기준**: TS-01, TS-02, TS-04 Green                                                                                                             
  - **상태**: ⬜ 대기
                                                                                                                                                         
  ### T3: {세션 관리}                                                                                                                                    
  ...
                                                                                                                                                         
  ### T4: {통합 테스트 + E2E}       
  - **범위**: 전체 인증 흐름 통합 검증
  - **AC 매핑**: 전체                                                                                                                                    
  - **테스트 매핑**: TS-05 (e2e)
  - **의존**: T2, T3                                                                                                                                     
  - **완료 기준**: TS-05 Green + 전체 회귀 통과
  - **상태**: ⬜ 대기                                                                                                                                    
                                    
  핵심 원칙:                                                                                                                                             
  - 각 태스크가 어떤 AC를 구현하고, 어떤 테스트를 통과시켜야 하는지 명시
  - 의존관계로 실행 순서 결정 (병렬 가능한 것은 병렬)                                                                                                    
  - 예상 규모로 내부 스킬(opds/opd) 자동 결정        
                                                                                                                                                         
  게이트: 캡틴 승인

  Phase 4: TASKS-VERIFY (분해 검증) 
                                                                                                                                                         
  수행 방식: 워커 디스패치 (검증 에이전트)
                                                                                                                                                         
  ┌──────┬────────────────────────────────────────┐
  │ 항목 │                  내용                  │
  ├──────┼────────────────────────────────────────┤
  │ 입력 │ tasks.md + spec.md + test-scenarios.md │
  ├──────┼────────────────────────────────────────┤
  │ 출력 │ validate.md (TASKS 검증 섹션 추가)     │                                                                                                      
  ├──────┼────────────────────────────────────────┤
  │ 모델 │ standard                               │                                                                                                      
  └──────┴────────────────────────────────────────┘                                                                                                      
  
  검증 항목:                                                                                                                                             
                                    
  ┌─────────────────┬────────────────────────────────────────────────┬──────────────────┐
  │      검증       │                      내용                      │     실패 시      │
  ├─────────────────┼────────────────────────────────────────────────┼──────────────────┤
  │ AC 커버리지     │ 모든 AC가 ≥1 태스크에 매핑                     │ TASKS 재분해     │
  ├─────────────────┼────────────────────────────────────────────────┼──────────────────┤
  │ TS 커버리지     │ 모든 테스트 시나리오가 ≥1 태스크에 할당        │ TASKS 수정       │

  7. oppd와의 포지셔닝 (최종)       
                                                                                                                                                         
  oppd: 프로젝트 전체 → PRD/TRD → WBS → 액션 실행
        ├─ 단순 액션 → opds                                                                                                                              
        ├─ 복잡 액션 → opd                                                                                                                               
        └─ 기능 개발 액션 → opsdd (NEW)                                                                                                                  
                                                                                                                                                         
  opsdd: 기능 단위 → SPEC → TASKS → 태스크 루프                                                                                                          
         ├─ 경량 태스크 → op-dev-plan + op-dev-execute (직접)                                                                                            
         └─ 복잡 태스크 → op-dev-analysis 추가                                                                                                           
                                    
  opd/opds: 단일 태스크 개발 (spec 없이 TASK에서 바로 시작)                                                                                              
                                    
  opsdd 사용 시점: "새 기능을 만들어야 하는데, 무엇을 만들지 먼저 확실히 정의하고 싶을 때"                                                               
                                    
  opd/opds 사용 시점: "뭘 해야 하는지 이미 알고 있고, 바로 구현하고 싶을 때"
