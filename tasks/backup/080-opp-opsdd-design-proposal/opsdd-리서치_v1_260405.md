SDD 방법론의 OPAL 프레임워크 통합 — 상세 제안

  1. 핵심 설계 판단

  먼저 080에서 남은 미결 사항에 대한 결론부터.

  ┌──────────────────────┬────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────────────────┐
  │         미결         │            제안            │                                            근거                                             │
  ├──────────────────────┼────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────────────────┤
  │ 별도 스킬 vs 모드 vs │ 별도 오케스트레이터        │ 캡틴이 제시한 SPEC→검증→TASKS→검증→루프→DONE 파이프라인은 opd/opds와 구조가 근본적으로      │
  │  단계 스킬           │ (opsdd)                    │ 다름. 모드 플래그로는 이 차이를 수용 불가                                                   │
  ├──────────────────────┼────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────────────────┤
  │ SPEC 단계 수행 방식  │ 워커 디스패치              │ SPEC 작성은 도메인 분석 + 구조화된 명세 작업이 필요. PM이 직접 하면 컨텍스트 윈도우 소진    │

  │                      │ 상세)                      │                                                                                             │
  ├──────────────────────┼────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────────────────┤

  └──────────────────────┴────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────────────────┘

  2. 파이프라인 상세

  캡틴의 프로세스를 OPAL 구조로 매핑합니다.

  ┌─────────────────────────────────────────────────────────┐
  │                    opsdd 파이프라인                        │
  ├─────────────────────────────────────────────────────────┤
  │                                                         │
  │  ① TASK ─────── 기존 op-task (PM 직접)                   │
  │       │                                                 │
  │  ② SPEC ─────── 워커: op-sdd-spec (명세 작성)             │
  │       │                                                 │
  │  ③ SPEC-VALIDATE ── 워커: op-sdd-validate (검증)          │
  │       │         ├─ 구조 검증 (필수 섹션, AC 형식)           │
  │       │         ├─ 의미 검증 (일관성, 실현 가능성)           │
  │       │         └─ 테스트 가능성 검증 (AC → 테스트 시나리오)  │
  │       │                                                 │
  │  ④ TASKS ────── 워커: op-sdd-tasks (태스크 분해)           │
  │       │                                                 │
  │  ⑤ TASKS-VALIDATE ─ 워커: op-sdd-validate (검증)          │
  │       │         ├─ 커버리지 매핑 (모든 AC ↔ 태스크)          │
  │       │         ├─ 의존관계 유효성 (순환 없음)               │
  │       │         └─ 태스크별 테스트 케이스 생성               │
  │       │                                                 │
  │  ⑥ EXECUTE-LOOP ── 태스크별 반복:                         │
  │       │  ┌──────────────────────────────┐               │
  │       │  │ T001 → PLAN → EXECUTE → TEST │ ← 기존 스킬    │
  │       │  │ T002 → PLAN → EXECUTE → TEST │    재활용      │
  │       │  │ T003 → ...                   │               │
  │       │  └──────────────────────────────┘               │
  │       │                                                 │
  │  ⑦ DONE ─────── 최종 QA + DONE.md                        │
  │                                                         │
  └─────────────────────────────────────────────────────────┘

  기존 스킬 재활용 매핑:

  ┌───────────────────┬────────────────────────┬─────────────────────────────────────────────┐
  │    opsdd 단계     │        컴포넌트        │                  신규/기존                  │
  ├───────────────────┼────────────────────────┼─────────────────────────────────────────────┤
  │ TASK              │ op-task                │ 기존 (PM 직접)                              │
  ├───────────────────┼────────────────────────┼─────────────────────────────────────────────┤
  │ SPEC              │ op-sdd-spec            │ 신규                                        │
  ├───────────────────┼────────────────────────┼─────────────────────────────────────────────┤
  │ SPEC-VALIDATE     │ op-sdd-validate        │ 신규 (재사용 가능)                          │
  ├───────────────────┼────────────────────────┼─────────────────────────────────────────────┤
  │ TASKS             │ op-sdd-tasks           │ 신규                                        │
  ├───────────────────┼────────────────────────┼─────────────────────────────────────────────┤
  │ TASKS-VALIDATE    │ op-sdd-validate        │ 신규 (SPEC-VALIDATE와 동일 스킬, 모드 분기) │
  ├───────────────────┼────────────────────────┼─────────────────────────────────────────────┤
  │ PLAN (루프 내)    │ op-dev-plan            │ 기존 재활용                                 │
  ├───────────────────┼────────────────────────┼─────────────────────────────────────────────┤
  │ EXECUTE (루프 내) │ op-dev-execute         │ 기존 재활용                                 │
  ├───────────────────┼────────────────────────┼─────────────────────────────────────────────┤
  │ TEST (루프 내)    │ 검증 루프 (oppd L1~L3) │ 기존 재활용                                 │
  ├───────────────────┼────────────────────────┼─────────────────────────────────────────────┤
  │ DONE QA           │ op-dev-qa              │ 기존 재활용                                 │
  └───────────────────┴────────────────────────┴─────────────────────────────────────────────┘

  신규 컴포넌트 3개, 기존 재활용 5개. 최소한의 추가로 SDD 가치를 완전히 적용합니다.

  3. 폴더 구조

  tasks/{NNN}-opsdd-{name}/
  ├── TASK.md                     ← ① 기존 OPAL TASK
  ├── STATE.md                    ← 상태 관리
  │
  ├── specs/                      ← SDD 명세 공간
  │   ├── spec.md                 ← ② 기능 명세 (WHAT/WHY + AC)
  │   ├── tasks.md                ← ④ 태스크 분해 (AC ↔ 태스크 매핑)
  │   └── validate.md             ← ③⑤ 검증 결과 누적 기록
  │
  ├── tests/                      ← 검증 테스트 (TDD Red)
  │   ├── scenarios/              ← AC 기반 테스트 시나리오 (SPEC-VALIDATE 산출물)
  │   │   ├── AC-001.scenario.md  ← GIVEN/WHEN/THEN → 테스트 정의
  │   │   └── AC-002.scenario.md
  │   └── skeletons/              ← 태스크별 테스트 스켈레톤 (TASKS-VALIDATE 산출물)
  │       ├── T001.test.md        ← 또는 실제 테스트 파일 (.py/.ts)
  │       └── T002.test.md
  │
  ├── tasks/                      ← ⑥ 태스크별 실행 공간
  │   ├── T001-{name}/
  │   │   ├── PLAN.md             ← op-dev-plan 산출물
  │   │   ├── QA-PLAN.md          ← (선택) PLAN QA
  │   │   └── changed_files.md    ← op-dev-execute 산출물
  │   └── T002-{name}/
  │       └── ...
  │
  └── DONE.md                     ← ⑦ 최종 완료

  설계 의도:

  - specs/ — SDD의 심장. 명세와 검증이 한 곳에
  - tests/ — TDD의 심장. 구현 전에 "무엇을 검증할지"가 먼저 정의됨
  - tasks/ — 실행 공간. 기존 OPAL의 PLAN→EXECUTE 패턴 그대로
  - specs/validate.md — 검증 결과를 누적 기록. SPEC 검증 → TASKS 검증 → 최종 QA 순으로 섹션 추가

  4. 각 단계 상세 설계

  ② SPEC 단계 (op-sdd-spec)

  입력: TASK.md + 프로젝트 컨텍스트 (docs/, 코드베이스)
  출력: specs/spec.md

  spec.md 구조:

  # SPEC: {기능명}

  > 작성일: YYYY-MM-DD | 스펙 버전: 1.0

  ## 1. Background (배경)
  왜 이 기능이 필요한지

  ## 2. Goals (목표)
  이 스펙이 달성해야 하는 것

  ## 3. Non-goals (비목표)
  명시적으로 범위 밖인 것

  ## 4. User Stories (사용자 스토리)
  - As a {역할}, I want {행위}, so that {가치}

  ## 5. Functional Requirements (기능 요구사항)
  - FR-001: {요구사항}
  - FR-002: ...

  ## 6. Acceptance Criteria (수용 기준)
  ### AC-001: {시나리오명}
  - GIVEN: {사전 조건}
  - WHEN: {행위}
  - THEN: {기대 결과}

  ### AC-002: ...

  ## 7. Edge Cases (엣지 케이스)
  - EC-001: {시나리오} → 기대 동작

  ## 8. Non-functional Requirements (비기능 요구사항)
  - 성능, 보안, 접근성 등

  ## 9. Constraints (제약)
  - 기술적/정책적 제한

  ## 10. Open Questions (미결 사항)
  - 없음 (← 검증 통과 조건)

  핵심: 기존 TASK.md가 "작업 정의"라면, spec.md는 "기능 명세". TASK.md는 OPAL이 이해하는 형식, spec.md는 도메인이 이해하는 형식.

  ③ SPEC-VALIDATE 단계 (op-sdd-validate, mode=spec)

  검증의 3계층을 적용합니다:

  ┌─────────────────────┬───────────────────────────────────────┬────────────────────────┬─────────────────────────┐
  │        계층         │               검증 항목               │          방법          │         실패 시         │
  ├─────────────────────┼───────────────────────────────────────┼────────────────────────┼─────────────────────────┤
  │ 구조적              │ 필수 섹션 10개 존재                   │ 스키마 체크            │ SPEC 재작성 지시        │
  ├─────────────────────┼───────────────────────────────────────┼────────────────────────┼─────────────────────────┤
  │                     │ AC가 GIVEN/WHEN/THEN 형식             │ 패턴 매칭              │                         │
  ├─────────────────────┼───────────────────────────────────────┼────────────────────────┼─────────────────────────┤
  │                     │ Open Questions가 "없음"               │ 마커 체크              │                         │
  ├─────────────────────┼───────────────────────────────────────┼────────────────────────┼─────────────────────────┤
  │                     │ AC 최소 3개 이상                      │ 카운트                 │                         │
  ├─────────────────────┼───────────────────────────────────────┼────────────────────────┼─────────────────────────┤
  │ 의미적              │ Goals ↔ FR ↔ AC 일관성                │ AI 분석                │ SPEC 보완 지시          │
  ├─────────────────────┼───────────────────────────────────────┼────────────────────────┼─────────────────────────┤
  │                     │ Non-goals가 Goals와 모순 없음         │ AI 분석                │                         │
  ├─────────────────────┼───────────────────────────────────────┼────────────────────────┼─────────────────────────┤
  │                     │ 제약 조건이 실현 가능                 │ 코드베이스 대조        │                         │
  ├─────────────────────┼───────────────────────────────────────┼────────────────────────┼─────────────────────────┤
  │                     │ 기존 코드/문서와 충돌 없음            │ 프로젝트 컨텍스트 대조 │                         │
  ├─────────────────────┼───────────────────────────────────────┼────────────────────────┼─────────────────────────┤
  │ 테스트 가능성 (TDD) │ 모든 AC에서 테스트 시나리오 생성 가능 │ AI가 실제 생성 시도    │ AC 재작성 필요          │
  ├─────────────────────┼───────────────────────────────────────┼────────────────────────┼─────────────────────────┤
  │                     │ 생성된 시나리오가 자동화 가능         │ 판단                   │ 수동 검증으로 전환 표시 │
  └─────────────────────┴───────────────────────────────────────┴────────────────────────┴─────────────────────────┘

  TDD 관점의 핵심: "이 AC로 테스트를 쓸 수 있는가?"를 실제로 써보는 것이 가장 강력한 스펙 검증입니다.

  산출물:
  - specs/validate.md — 검증 결과 (Pass/Fail + 사유)
  - tests/scenarios/AC-{NNN}.scenario.md — AC별 테스트 시나리오 (TDD Red)

  테스트 시나리오 형식:
  # Test Scenario: AC-001 사용자 로그인

  > AC: GIVEN 등록된 사용자 WHEN 올바른 이메일+비밀번호 입력 THEN 로그인 성공

  ## 테스트 케이스
  - TC-001-1: 정상 로그인 → 200 + JWT 토큰
  - TC-001-2: 잘못된 비밀번호 → 401
  - TC-001-3: 존재하지 않는 이메일 → 404

  ## 검증 방법
  - [ ] 자동화 가능 (unit/integration)
  - [ ] E2E 필요
  - [ ] 수동 검증 필요

  ## 매핑
  - FR: FR-001
  - Edge Cases: EC-001, EC-002

  ④ TASKS 단계 (op-sdd-tasks)

  입력: spec.md + 테스트 시나리오 + 프로젝트 컨텍스트
  출력: specs/tasks.md

  tasks.md 구조:
  # TASKS: {기능명}

  > spec 버전: 1.0 | 태스크 수: N

  ## 커버리지 매트릭스 (Requirements Traceability Matrix)

  | AC | FR | 태스크 | 테스트 시나리오 |
  |----|-----|--------|--------------|
  | AC-001 | FR-001 | T001, T002 | AC-001.scenario.md |
  | AC-002 | FR-002 | T002, T003 | AC-002.scenario.md |

  ## 의존관계 그래프

  ```mermaid
  graph LR
    T001 --> T002
    T001 --> T003
    T002 --> T004
    T003 --> T004

  태스크 목록

  T001: {태스크명}

  - 설명: {무엇을 구현}
  - AC 매핑: AC-001
  - depends_on: 없음
  - 예상 복잡도: simple/complex
  - 추천 스킬: opds/opd
  - 수용 기준:
    - {태스크 수준 AC}

  T002: ...


  **설계 포인트**:
  - **커버리지 매트릭스가 핵심**. 모든 AC가 최소 1개 태스크에 매핑되어야 함
  - 각 태스크에 **추천 스킬**을 명시. 단순하면 opds, 복잡하면 opd
  - 의존관계 그래프로 병렬 실행 가능 그룹을 식별

  #### ⑤ TASKS-VALIDATE 단계 (op-sdd-validate, mode=tasks)

  | 검증 항목 | 방법 | 실패 시 |
  |----------|------|--------|
  | 모든 AC가 태스크에 매핑됨 | 커버리지 매트릭스 검사 | TASKS 보완 |
  | 모든 FR이 태스크에 매핑됨 | 매트릭스 검사 | TASKS 보완 |
  | 의존관계에 순환 없음 | 그래프 분석 | 의존 재설계 |
  | 각 태스크가 자기 완결적 | AI 판단 | 태스크 분할/병합 |
  | 태스크별 테스트 케이스 생성 가능 | AI가 실제 생성 시도 | 태스크 명확화 |

  **TDD 관점**: 각 태스크에 대해 테스트 스켈레톤을 생성합니다.

  **산출물**:
  - `specs/validate.md` 갱신 (TASKS 검증 섹션 추가)
  - `tests/skeletons/T{NNN}.test.md` — 태스크별 테스트 스켈레톤

  #### ⑥ EXECUTE-LOOP (기존 스킬 재활용)

  태스크별로 의존 순서에 따라 실행:

  for each task T in dependency_order(tasks.md):
  1. PLAN   ← op-dev-plan (기존)
    - 입력: T의 설명 + spec.md 컨텍스트 + 테스트 스켈레톤
    - 출력: tasks/T{NNN}/PLAN.md
  2. EXECUTE ← op-dev-execute (기존)
    - 입력: PLAN.md
    - 출력: 코드 변경
  3. TEST   ← 검증 루프 (oppd L1~L3 재활용)
    - L1: lint/format
    - L2: build/type check
    - L3a: unit/integration (테스트 스켈레톤 기반)
    - L3b: E2E (해당 시)
    - 실패 시: 자동 수정 루프 (하네스 §1 제약 준수)
  4. 태스크 완료 → tasks.md 체크박스 갱신

  **병렬 실행**: 의존관계 없는 태스크끼리는 oppd Phase 3처럼 병렬 실행 가능 (worktree 격리)

  #### ⑦ DONE

  1. 최종 QA (op-dev-qa)
     - 모든 AC 테스트 시나리오 통과 확인
     - 회귀 테스트 (기존 테스트 깨짐 없음)
     - specs/validate.md 최종 갱신
  2. DONE.md 생성
  3. 메모리 갱신
