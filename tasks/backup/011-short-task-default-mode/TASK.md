# TASK: Short Task 기본 모드 전환 및 판별 조건 개선

> 작성일: 2026-03-15 | 작업 유형: 기능 개선

## 작업 목표

Short Task를 기본 모드로 전환하고, Full Task 진입 조건을 대폭 완화하여 대부분의 작업이 Short Task로 진행되도록 한다.

## 배경

현재 Short Task 진입 조건이 너무 엄격하여 (5개 모두 충족 필요) 대부분 Full Task로 빠진다. 실제로는 단순한 작업이 Step 수가 많거나, 다중 모듈에 걸치거나, 외부 의존성이 있는 경우도 흔하다. Short Task도 Full Task와 동일한 분석 수준을 유지하므로, 모드 차이는 "단계 수"일 뿐 "품질"이 아니다.

사용자 피드백:
- 조건 2(Step ≤5), 3(단일 모듈)이 애매 — 단순한 작업도 많은 경우가 많음
- 조건 4(외부 의존성 없음) — 외부 의존성이 있어도 Short 가능
- Short Task도 Full처럼 research-plan-todo 수준이 동일해야 함
- Short을 기본으로 하고, 사용자 요청이나 명확한 조건일 때만 Full

## 요구사항

- [ ] R1. Short Task를 기본 모드로 변경 (모든 작업은 Short Task로 시작)
- [ ] R2. 기존 Short Task 진입 조건 5개를 제거하고, Full Task 트리거 조건으로 역전
- [ ] R3. Full Task 트리거 조건 정의:
  - R3.1 사용자가 "Full로 해줘" 명시
  - R3.2 예상 변경 파일 ≥10개 (대규모)
  - R3.3 다단계 기술 의사결정 필요 (아키텍처 선택, 기술 스택 비교 등 별도 RESEARCH가 필요한 수준)
  - R3.4 다중 모듈 간 연쇄 영향 (변경 A가 B, C에 연쇄적으로 영향)
- [ ] R4. Full Task 조건(R3.2~R3.4) 해당 시 Full을 "제안"하고, 사용자가 결정
- [ ] R5. 에스컬레이션 규칙 갱신: Short 진행 중 Full 조건에 해당하면 에스컬레이션 제안
- [ ] R6. Short Task 품질 보장 문구 유지/강화: "단계를 줄이는 것이지 분석을 줄이는 것이 아니다"

## 제약 조건

- 기존 Full Task / Short Task의 산출물 구조, 게이트 체크포인트, QA 호출 규칙은 변경하지 않는다
- 오케스트레이터-워커 모델은 변경하지 않는다
