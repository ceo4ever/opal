## 2-2. 핵심 설계

### A. opal-pm.md 문서 구조

```markdown
# OPAL PM — 프로젝트 매니저 행동 프로세스

> PM(에이전트)이 프로젝트에서 따르는 행동 프로세스 정의.
> `.opal/AGENT.md`(프로젝트별)가 WHAT(검토 기준, 금지사항)을 정의하고,
> 이 문서는 HOW(절차, 프로세스)를 정의한다.

## 1. PM 역할 개요
## 2. PM 컨텍스트 로드 절차

## 7. 문서/코드 불일치 판단
## 8. 워커 행동 규칙
```

### B. §1 PM 역할 개요

PM은 프로젝트에 `.opal/AGENT.md`가 존재할 때 활성화되며, 다음을 수행한다:
- 소유자의 지시를 해석하여 워커에게 디스패치
- 워커 결과를 검토하고 소유자에게 보고
- 프로젝트 지식을 축적하고 문서 일관성을 관리

**역할 분리 원칙**: 이 문서(opal-pm.md)는 PM 행동 프로세스(HOW)를, `.opal/AGENT.md`는 프로젝트별 설정(WHAT — 검토 기준, 금지사항, 확정 기준)을 정의한다. 둘을 합쳐야 PM이 완전히 동작한다.

### C. §2 PM 컨텍스트 로드 절차

AGENT.md(글로벌)의 기존 "PM 컨텍스트 로드" 절차를 이관하되, 로드 순서를 명확화:

```
1. {프로젝트}/.opal/AGENT.md Read → PM 전문 역할, 검토 기준, 확정 기준 로드
2. {프로젝트}/docs/PROJECT.md Read → 프로젝트 정의 + 문서 레지스트리 + 프로젝트 설정 로드
3. 프로젝트 설정 적용 (태스크 폴더 경로 등)
```

기존 AGENT.md L169~L172 내용을 그대로 이관. "프로젝트 설정 적용" 규칙도 포함.

### D. §3 PM 디스패치 전 프로세스 (신규 — R4, R5)

**매 디스패치마다** 동적으로 수행하는 5단계 프로세스:

```
Step 1: PROJECT.md 문서 테이블 Read → 등록 문서 전체 파악
        (opi로 추가된 새 문서도 포함되므로 매번 최신 상태 확인)

Step 2: 현재 작업과 관련된 문서 선별
        — 문서 테이블의 "참조 시점" 컬럼 매칭
        — 작업 도메인(FE/BE/인프라 등)에 따른 추가 선별

Step 3: 선별 문서 직접 Read → 핵심 제약 추출
        예: "BaseMedia 상속 필수", "미들웨어 체계 준수", "shadcn/ui 사용"

Step 4: 문서 간 종속 관계 확인
        예: BACKEND.md → BE-FRAMEWORK.md 필수 참조

Step 5: 영구적 기준 발견 시 .opal/AGENT.md 확정 기준 추가 제안
        (소유자 승인 후 기록)
```

**워커 컨텍스트 주입 템플릿** (R5):

```markdown
## 참조 문서
- `docs/ARCHITECTURE.md` — 시스템 아키텍처
- `docs/CONVENTIONS.md` — 코드 컨벤션
- (추가 선별 문서...)

## 핵심 제약
- {제약 1}: {설명}
- {제약 2}: {설명}

## 종속 문서
- {문서 A} → {문서 B} (필수 참조)

## 문서/코드 불일치 규칙
문서와 실제 코드가 다를 경우 **코드(실질적 문서) 기준**으로 작업하고, 불일치 사항을 PM에게 보고한다.
```

### E. §4 PM 검토 게이트

AGENT.md L190~L207의 기존 PM 검토 게이트를 이관:

검토 절차 7항목:
1. 관련 참조 문서가 워커에게 전달되었는가
2. 기술 스택에 맞는 MCP/스킬이 활용되었는가
3. `.opal/AGENT.md`의 PM 검토 기준 체크리스트 평가
4. TASK.md 요구사항과 산출물의 정합성
5. 참조 문서 내용이 산출물에 반영되었는가
6. `docs/PROJECT.md`의 프로젝트 원칙/기준에 부합하는가
7. 금지사항 위반 여부

판정: Pass → 보고 / Fail → 재지시(최대 1회) → 재검토 → 보고
`.opal/AGENT.md` 미존재 시 스킵 (하위 호환)

**하네스와의 관계**: 하네스 interactive §3 PM Gate가 "PM 검토를 수행하라"고 지시하면, 이 §4의 절차를 따른다. 하네스는 게이트 구조(언제), opal-pm.md는 검토 내용(무엇을 어떻게)을 정의.

### F. §5 PM 학습 루프

AGENT.md L214~L224의 기존 PM 학습 루프를 이관:

1. 질문 프로토콜: 확정 기준에 없는 판단 → 소유자에게 선택지 제시
2. 답변 분류:
   - 반복 원칙 → `.opal/AGENT.md` 확정 기준에 즉시 추가
   - 일회성 판단 → `.opal/memory/`에 기록
   - 불확실 → "앞으로의 기준으로 기록할까요?" 확인
3. 자동 적용: 다음 세션에서 확정 기준 로드 시 재질문 없이 적용

### G. §6 참조 문서 전달 의무

AGENT.md L183~L189의 기존 참조 문서 전달 의무를 이관:

1. 문서 테이블에서 "참조 시점"이 현재 작업과 매칭되는 문서 선별
2. 디스패치 프롬프트에 문서 경로 포함
3. 기술 스택 연동 지시:
   - shadcn/ui → "shadcn MCP로 컴포넌트 조회 후 구현. ui-designer 스킬 활용"
   - Python → "context7로 최신 API 확인"
   - 외부 API → "웹 검색으로 최신 문서 확인"
4. 워커 결과 검토 시 참조 문서 반영 확인

### H. §7 문서/코드 불일치 판단 (신규 — R6, R7)

**원칙**: 문서와 코드가 다를 때 **코드가 실질적 문서(source of truth)**다.

**PM 측 절차** (R7):
1. 워커로부터 불일치 보고를 수신한다
2. 불일치 내용을 `.opal/memory/`에 기록한다 (카테고리: `doc-mismatch`)
3. opi 최신화 대상으로 마킹한다 (메모리에 "opi 최신화 필요: {문서} ↔ {코드 현실}" 기록)
4. 다음 opi 실행 시 해당 문서를 우선 갱신 대상에 포함

**불일치 판정 기준**:
- 문서에 명시된 인터페이스/구조와 실제 코드의 인터페이스/구조가 다를 때
- 문서에 없는 패턴이 코드에서 반복적으로 사용될 때
- 문서가 참조하는 파일/경로가 실제로 존재하지 않을 때

### I. §8 워커 행동 규칙 (신규 — R6)

워커(서브에이전트)가 문서/코드 불일치를 발견했을 때의 행동 규칙:

```
1. 코드(실질적 문서) 기준으로 작업한다
2. 불일치 사항을 작업 결과에 명시적으로 보고한다:
   - 어떤 문서의 어떤 내용이
   - 실제 코드의 어떤 부분과 다른지
   - 코드 기준으로 어떻게 처리했는지
3. 불일치가 작업 진행을 막는 수준이면 PM에게 에스컬레이션한다
```
