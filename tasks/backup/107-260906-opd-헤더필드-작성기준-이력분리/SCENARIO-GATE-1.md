## 3. gaps

### G-1 (①) 태스크 발원 동기인 「헤더 창문 재포화 지연」이 무측정이다
PLAN.md:187이 F-003의 효과를 「`description` 총량이 약 34,000자 감소하면 `scan`/`search` 출력 바이트가 줄어 헤더 창문 재포화가 늦춰진다(**태스크 106 동기와 직결**)」로 명시했고, TASK.md §배경도 창문 재포화를 이 태스크의 출발점으로 든다. 그런데 TEST-SCENARIO.md 전문에 「창문」·「바이트」·`HEADER_READ_BYTES` 문자열이 **0회**다. TS-023이 보는 것은 `coverage.percent` **불변**(무변경 보증)이지 개선 지표가 아니다.
→ 보강: 정리 전/후 `@header` 블록 바이트 총량 재측정 시나리오(최소한 최대 감축분 `state_tool.py` 11,791자 → 축약본과 3스코프 합계). 목표가 달성됐음을 보이는 유일한 운영 수치다.

### G-2 (①) 목표 문장의 「git이 갖는다」가 문자열 채움 검사에 머문다
TS-022는 `HISTORY-EVIDENCE.md`에 「제거된 태스크 번호마다 커밋 해시 또는 DONE.md 경로가 **채워져 있다**」만 단언한다. 기록된 해시가 실제 저장소에서 resolve되는지(`git cat-file -e`), DONE.md 경로가 실존하는지는 **어느 시나리오도 확인하지 않는다**. 「미확인 1건이라도 있으면 FAIL — 이력 소실은 되돌릴 수 없다」는 문구의 강도와 실제 검사 강도가 어긋난다. 목표의 절반(제거)만 검증하고 나머지 절반(소재 보증)은 문서 작성 성실성에 의존한다.
→ 보강: 23파일 × 제거 태스크 번호 전건에 대해 기록된 해시·경로를 **실제로 조회해** 유효함을 단언하는 L2 시나리오. 비가역 작업이므로 이 축이 가장 위험하다.

### G-3 (①⑤) R-2 AC(e)의 절반(교체 문구)이 미검증이다
AC(e)는 `docs/CONVENTIONS.md`에서 ① 「헤더 내 변경이력 라인」 어구 **제거** AND ② 「R-2 원칙과 정합하는 문구로 **교체**」 두 가지를 요구한다. §4 매핑 표(287행)는 AC(e)를 **TS-006 단독**에 매핑하고 비고에 「CONVENTIONS.md 교체」라 적었으나, TS-006의 기대 결과는 `grep -rn "헤더 내 변경이력 라인"` = **0건**, 즉 제거뿐이다. 교체 문구의 존재·R-2 정합은 어디에도 없다.
→ 이 공백이 위험한 이유는 AC(e) 자신이 밝힌다 — 「이 문서는 「개발 작업 시 항상」 참조되는 [MUST] 등재 문서이므로 미개정 시 다음 태스크 워커가 이 문구를 근거로 이력을 다시 쌓는다」. 구형 문구만 빠지고 신형 지시가 안 들어가면 남는 것은 **규정 공백**이고, 그것이 바로 TASK §배경 분석 (2)가 지목한 이번 사태의 원인(「워커가 규정을 어긴 것이 아니라 규정이 갈 곳을 지정하지 않았다」)의 재생산이다.
→ 보강: CONVENTIONS.md 교체 문구 존재 + R-2 원칙(이력 소재 2곳) 정합 단언 시나리오 신설.

### G-4 (⑤) Block A 흡수 검증 결과 — S-A13 → TS-005 흡수는 **커버 면적 축소를 동반**한다
지시대로 흡수 판정을 대조한 결과, 명분상 성립하나 범위가 줄어든 건이 1건 있다. S-A13의 관심사는 「도달 경로」이고 TS-005는 이를 「원문 1개 + 나머지 포인터」로 치환했는데, TS-005의 **대상**은 `header-standard.md`·`header-rules.md` 두 문서이고 포인터 검증도 `header-rules.md` 추가 블록에 한정된다. 정작 워커의 실제 진입 문서인 `docs/CONVENTIONS.md`는 「3문서 중 원문 보유 정확히 1개」의 **부정 측 계수 대상**으로만 등장하고, 거기서 신설 규정으로 가는 **포인터가 있는지는 검사하지 않는다**. TS-005 본문이 스스로 「워커가 읽는 문서에서 신설 규정으로 가는 경로가 존재해야 한다 — 없으면 규정은 영영 안 읽힌다」고 쓰면서 진입 문서를 대상에서 뺀 것이다. G-3과 같은 구멍의 다른 면이다.
→ 보강: TS-005의 대상에 `docs/CONVENTIONS.md`를 포함하고, 진입 문서 → `header-standard.md §2.1` 포인터 존재를 단언한다.

### G-5 (①⑤) 3층 일관 적용 중 「규정층 → 신규 작성」 접합이 시나리오 집합 밖이다
목표는 규정·도구·자산 **3층 일관 적용**이다. 자산층(TS-020)과 도구층(TS-010~019, TS-041)은 검증되고 둘의 접합도 TS-020이 담당하나, 「신설 §4.2 기준에 따라 작성된 헤더가 F-002 감지기를 통과한다」는 end-to-end가 없다. 유일한 근접 항목인 §5 코드 품질 표 #4(「신설 테스트 파일 자신의 `@header` 준수 — `description` 태스크 번호 0개」)는 **TS-ID가 없고** §4 매핑 표에도, 정규화 페이로드 28시나리오에도 없어 **게이트 대상 시나리오가 아니다**.
→ 보강: #4를 TS로 승격해 매핑 표·페이로드에 편입하거나, 신설 기준 준수 헤더 1건을 신설 감지기에 통과시키는 접합 시나리오를 추가한다.
