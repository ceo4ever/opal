### 3.2 소요 3계열 분해 (캡틴 지시)

**총 리드타임 = PM + 워커 + 캡틴.** 병목은 워커 계열을, 대기 축소는 캡틴 계열을 본다.

- `PM`은 유도값이다(`행 소요 − 캡틴 − 워커`) — 별도 계측이 없다.
- **축퇴 규칙(16-a)** — 워커 미기록 행은 전액 PM에 귀속된다. 그래서 과거 22개 태스크는 기존 2계열과 **수치가 항등**이고, 오늘 확정한 `101` 425 = 105 + 320이 그대로 살아남았다.
- **상한 clamp(16-d)** — `워커 = min(기록값, 소요 − 캡틴)`이라 PM이 구조적으로 음수가 될 수 없고 3계열 합이 항상 행 소요와 일치한다.
- 진행 중 태스크는 `총 = PM + 워커 + 캡틴 + 진행중` **4구획**이다 — 실시간 총과 정적 합의 차이가 정확히 현재 행 경과 시간임을 실측했다(483 − 299 = 184 = `current_elapsed_minutes`).

### 3.3 워커 소요 계측 — 세 번 새고 네 번째에 막았다

이 태스크의 최대 산출이다. **강제 수단의 판정 근거가 사람의 자발적 표시에 있으면 규범은 반드시 우회된다.**

| 회차 | 조치 | 왜 새어나갔나 |
|---|---|---|
| 1 | `--worker-duration-minutes` 인자 신설 | 쓰라는 규범이 없어 안 씀 |
| 2 | 산문 규범 3곳 | 「소요를 넘겨라」만 있고 「워커 행임을 표시하라」가 빠짐 |
| 3 | `mark` 경고 | 판정이 `--as-worker`에 의존 → 그 인자를 안 쓰면 경고조차 침묵 |
| 4 | **행 기반 판정 + CLOSE 차단** | — |

**실측 증거** — 다른 프로젝트의 태스크가 배포 18분 뒤에 시작됐고 도구·규범이 모두 준비돼 있었는데 **15행 전건이 미기록으로 통과**했다.

최종 설계:

- **조기 경고** — `is_worker_dispatch_row()`가 행의 `stage`·`item`으로 판정한다. `--as-worker` 없이도 발동하므로 PM 의사와 무관하다.
- **CLOSE 차단** — 기록도 선언도 없는 워커 규범 행이 남으면 거부한다(`BLOCK_CODES.worker_duration_undeclared`). 통과는 `--worker-duration-minutes` 또는 `--worker-duration-unknown` 둘뿐이고, `--force --note`가 최후 우회다. **침묵은 통과하지 못한다.**
- **선언 영속화** — `--worker-duration-unknown`이 행에 `worker_duration_unknown: true`를 남긴다. 이것이 없으면 「선언」과 「침묵」을 구별할 수 없어 강제가 성립하지 않는다.
- **유예는 `created_at` 기준** — 계측 도입(2026-08-26) 이전 생성 태스크만 통과시킨다. 「기록 0건이면 유예」로 두면 전건 미기록인 신규 태스크가 그대로 통과해 강제가 무의미해진다(첫 설계가 이랬고 실증에서 드러났다).

### 3.4 시각 표기 `YY-MM-DD HH:mm:ss` (캡틴 지시)

화면이 `HH:MM`만 보여줘 **날짜 경계가 사라지고 시각이 거꾸로 읽혔다.**

- 실측 — 7개 태스크 8곳. 최대는 `100`의 「82분처럼 읽히던 구간」이 실제 **25시간 22분**.
- `date.js`에 `datetime-sec`를 **더하기만** 했다(기존 `datetime` 무변경) — 구버전 배포본은 분 해상도로 폴백해 출력이 바이트 동일이다.
- 기존 276행은 초가 없어 `:00`으로 표시한다. **소급 변환하지 않았다** — 존재하지 않았던 정밀도를 지어내는 일이다.

### 3.5 야간 시간대 보정 (캡틴 지시)

「근무시간 보정 없음」 확정을 캡틴이 뒤집었다.

- 기본 켬, `00:00~09:00`. `~/.opal/setting.json` + `{프로젝트}/.opal/setting.local.json` **2층 머지**로 시간대 변경·끄기가 가능하다.
- 효과 — `opd` 중앙값 **799 → 425분(-47%)**. `opds`·`opp`는 하루 안에 끝나 불변.
- **워커 소요는 보정하지 않는다** — 실측 벽시계이므로 야간을 빼면 실제보다 짧아진다. 워커 몫을 먼저 확보하고 남은 몫에서 뺀다.
- 화면에 「야간 제외 00:00~09:00」 배지를 세워 같은 태스크가 두 값으로 보이는 혼란을 막았다.

## 4. 사고 기록

### 4.1 `mark --force`가 시각을 덮어 6행 손상

워커 소요를 소급 기록하려 `--force`로 재마킹했는데, 그 명령이 `timestamp`도 현재 시각으로 갱신했다. 총 리드타임이 288분 → 1,354분으로 부풀고 PM 음수 2행이 생겼다.

- **원인** — 부작용을 사전에 확인하지 않고 6번 연속 실행했다.
- **복구** — 캡틴 승인 후 `state.json`을 직접 수정해 원본 시각으로 되돌렸다(원본은 `mark` 응답 기록에 남아 있었다). 299분 · PM 음수 0 · 무결성 위반 0으로 완전 복구.
- **교훈** — `--force`류는 1건 시험 실행 후 결과를 확인하고 나머지를 돌린다.

### 4.2 `prettier --write` 600줄 churn

툴팁 워커가 `TasksPage.tsx`에 포매터를 돌렸다. 프로젝트에 `.prettierrc`가 없어 기본값이 적용됐고 그 파일만 포맷이 달라졌다.

- 시맨틱 변경 0, 테스트·빌드 전건 green, `@header` 온전.
- **되돌리지 않았다** — `HEAD`의 그 파일은 606줄(태스크 023 시절)인데 현재 1,716줄이라 git 복원 시 오늘 FE 작업 전체가 사라진다.
- **조치** — 이후 모든 워커 프롬프트에 「포매터를 파일 전체에 실행하지 마라」를 명시했고 재발 0건.

### 4.3 `add-row` 역순 삽입 → 소요 귀속 오류

같은 앵커로 두 번 호출해 행 14/15 순서가 뒤집혔다. 「표기 역전일 뿐」이라 판단했으나 **틀렸다** — 3계열 확장 구간 201분이 전부 앞 행으로 흡수되고 워커 39분이 소요 0인 행에 얹혀 전액 clamp됐다.

- **복구** — 캡틴 승인 후 행 내용을 논리 순서로 재배치하고 워커를 실측값(37분)으로 정정.

### 4.4 워커 소요 오기록 → 강제 2단이 잡아냄

강제 2단 작업을 워커 45분으로 기록했으나, 실제로는 워커 3회가 API 529로 끊겨 **PM이 직접 완주**했다. 행 소요 20분보다 큰 값이라 상한 clamp가 걸렸고 `TS-107`이 실패로 표면화했다.

- **정정** — `worker_duration_unknown: true`로 교체.
- 강제 2단이 **제 오기록을 잡아낸 첫 사례**다. 사람 눈으로는 20분과 45분의 모순을 못 본다.
