# TASK: OPAL Console 태스크 진행 통계

> 작성일: 2026-08-25 | 개정일: 2026-08-26 (야간 시간대 보정 — 집계 기준 17 신설) | 작업 유형: 개선 | 적용 스킬: opd | 모드: semi-agentic
> 입력: 사용자 요청 + 캡틴 대화 확정(통계 목적·집계 기준 14항목) + 캡틴 지시 2026-08-26(야간 00~09시 제외)
> 출력: TASK.md

## 작업 목표

OPAL Console 태스크 칸반의 상세 패널에 진행 통계 4블록(A-1~A-4)을, 대시보드 화면에 횡단 통계 4블록(B-1~B-4)을 추가한다. 통계의 원천은 `tasks/*/state.json` 파이프라인 행이며, **총 리드타임을 `PM` · `워커` · `캡틴` 3계열로 분해**해 병목 단계와 캡틴 대기 구간을 동시에 드러낸다. 워커 소요가 기록되지 않은 태스크는 축퇴 규칙에 따라 `PM`+`캡틴` 2계열로 자연 축소된다(집계 기준 16-a).

## 배경

태스크 상세 패널은 현재 파이프라인 스테퍼(단계별 점 + `done_count/total`)와 산출물 탭만 제공한다(`dashboard/frontend/src/pages/tasks/TasksPage.tsx:264`). 어느 단계에서 시간이 걸렸는지, 누가 무엇 때문에 멈췄는지, 지금 어디까지 왔는지를 화면에서 읽을 수 없다.

반면 원천 데이터인 `state.json`에는 행마다 `timestamp`·`owner`·`gate`·`note`가 쌓여 있어, 추가 계측 없이 소요 시간·대기 시간·게이트 통과율을 계산할 수 있다. 데이터는 이미 있는데 화면이 버리고 있는 상태다.

## 통계 목적 (캡틴 확정)

`[결정]` 이 통계는 두 가지를 판단하는 데 쓴다 — **병목 개선**(어느 단계가 오래 걸리는지 찾아 스킬·파이프라인을 고친다)과 **캡틴 대기 축소**(게이트에서 캡틴이 붙잡는 시간을 줄인다).

두 목적은 하나의 분해축으로 동시에 답한다. **총 리드타임 = PM + 워커 + 캡틴**.

- `캡틴` = `owner=user` 행 소요 → 대기 축소가 보는 계열
- `워커` = 서브에이전트 실제 실행 시간 → 병목 개선이 보는 계열
- `PM` = 행 소요 − 캡틴 − 워커 (유도값) → 디스패치 준비·게이트 검토 오버헤드

그래서 A-2·B-2는 단일 막대가 아니라 **3색 스택 막대**다. 워커 소요가 기록되지 않은 행은 그 몫이 `PM`에 귀속되어 종전 「작업」 계열과 값이 같다(집계 기준 16-a) — 과거 태스크의 확정값이 깨지지 않는다.

## 배경 분석 (대화에서 도출)

이 태스크 착수 전, 알투(PM)가 `tasks/*/state.json`을 직접 전수 계산하고 목업을 만들어 캡틴 승인을 받았다. 아래는 그 과정과 후속 재계산에서 확인된 사실이다.

### (3) 평균은 야간 공백에 지배된다

- `TEST-SCENARIO`는 평균 236분 vs 중앙 33분, `EXECUTE`는 평균 220분 vs 중앙 73분으로 최대 7배 갈린다.
- 근무시간 보정을 하지 않기로 확정했으므로 왜곡은 대표값 선택으로 흡수한다 — 중앙값이 주 지표, 평균은 보조다.

### (4) 원천 스키마 실측 — 문서화되지 않은 3건

- **`gate`는 불리언이 아니다.** `artifacts`·`checklist` 키를 가진 객체이며, 키의 존재 자체가 게이트 행이라는 뜻이다. 38행에만 있고 `092` 이전 11개 태스크에는 0건이라, 게이트 통과율을 횡단 비교하면 구형식 태스크가 전부 0으로 깔린다.
- **`pending` 행의 `owner`는 무의미한 기본값이다.** `pending` 30행 전부가 `owner=PM`이다. 완료 시점(`mark`)에 실제 담당으로 갱신되고 그전까지는 `init` 기본값이 남는다. 따라서 진행 중 태스크에서 `owner`로 대기를 귀속하면 캡틴 대기가 PM 작업으로 잘못 표시된다 — 행 `key`의 `*.user_confirm` 패턴으로 판정해야 한다.
- **블로커는 행 `status: failed`로 표현된다.** 현재 23개 태스크 전건 0이다.
- **`*.user_confirm` 행의 41건이 `owner=auto`다** (`done` 30 + `na` 11, 전체 `user_confirm` 87행). agentic 모드에서 PM이 자율 통과시킨 게이트다. 「게이트 건수」와 「캡틴이 실제 개입한 건수」는 다른 수치이므로 분리 표기한다.
- **타임스탬프 역행 행이 실재한다.** `086`의 `plan.user_confirm`이 직전 done 행(15:47)보다 이른 15:46이라 소요가 −1분이 된다. clamp 없이 합산하면 opp 집계(n=4)가 왜곡되고 스택 막대가 음수 폭으로 깨진다.
- **`PipelineRow.row`·`updated_at`은 원천에 없는 죽은 필드다.** `_group_pipeline_stages`가 이 두 키에서 읽지만(`dashboard/backend/routers/tasks.py:259-267`) 행 키 11종에 없어, `row`는 0-based 인덱스로 폴백하고 `updated_at`은 전건 빈 문자열이다.
- **`mtime` 무효화가 작동하지 않는다.** `task_detail`·`tasks_list`·`dashboard` 세 호출부 모두 `source_path`를 넘기지 않아, 캐시는 30초 TTL 축만 살아 있다.

### (5) 현행 API가 통계 재료를 버리는 지점

- `PipelineRow`는 `row`·`stage`·`status`·`updated_at` 4필드만 노출한다 (`dashboard/backend/models.py:136-140`). 원천 행이 가진 `owner`·`gate`·`note`·`timestamp`·`key`가 프론트에 도달하지 않는다.
- 진행률은 `완료 rows / 전체 rows` 단일 수식뿐이다 (`dashboard/backend/routers/tasks.py:291-293`, `:417-419`). 시간 축 지표가 없다.
- 산출물 카운트는 6종 화이트리스트로 고정돼 있다 (`dashboard/backend/routers/tasks.py:92`). 실제 `.md` 192개 중 92개만 센다.

### (6) 대시보드 집계 경로는 이미 존재한다

- `GET /api/dashboard`가 이미 구현돼 있고(`dashboard/backend/routers/dashboard.py:109-110`), `_collect_all_tasks`가 프로젝트 전 태스크의 `state.json`을 수집한다(`dashboard/backend/routers/dashboard.py:46`).
- 프론트에도 `MetricCard`·`ActivityChart`·`StatusPieChart`·`RecentTable` 컴포넌트가 이미 있다(`dashboard/frontend/src/pages/dashboard/DashboardPage.tsx:132`, `:168`, `:253`, `:375`).
- 30초 TTL + `mtime` 무효화 캐시도 있다(`dashboard/backend/cache.py`). 23파일·303행 규모이므로 온디맨드 계산으로 충분하며, 통계 스냅샷 파일을 런타임 경로에 두지 않는다.
- 따라서 B-1~B-4는 집계 API 신설이 아니라 **기존 `/api/dashboard` 확장**이다.

### (7) 선재 결함 — 칸반 카드 제목이 전건 폴더명

- 23개 `state.json` 전부에 `title` 키가 없다.
- `tasks.py`는 `state.get("title", task_id)`로 폴백한다(`dashboard/backend/routers/tasks.py:297`, `:423`) → 칸반 카드·상세 헤더 제목이 전건 폴더명으로 표시된다.
- 반면 `dashboard.py`는 `_resolve_task_title`로 TASK.md의 H1을 읽어 사람이 쓴 제목을 복원한다(`dashboard/backend/routers/dashboard.py:90`). 같은 프로젝트 안에서 두 라우터의 제목 해석이 불일치한다.
- 본 태스크 범위 밖의 선재 결함이나, 통계 화면이 태스크를 식별해 보여주는 이상 표시 품질에 직접 영향을 준다.

### (8) 목업 검증

알투(PM)가 실측값으로 목업을 작성해 캡틴에게 제시했고 승인받았다(`mockup/`). 목업은 콘솔의 시그니처 3색·상태색 5종(`dashboard/frontend/src/index.css` `:root`)을 그대로 계승했다.

| 2 | 제외 행 | `status != "done"` 전부 — `pending`·`na`·`in_progress`·`failed`. 소요는 `done` 행만 합산한다 |

| 6 | 2계열 | `owner=user` → 대기, `PM`·`auto` → 작업 |
| 7 | 게이트 | `gate` 키 존재 = 게이트 행(객체). `092` 이전은 「미기록」 표기 |
| 8 | 블로커 | 행 `status=failed`. 현재 전건 0 |
| 9 | 산출물 | 화이트리스트 폐기, `.md` 전수 + 유형 분류 |

| 11 | 실시간 총 리드타임 | 진행 중이면 `created_at` → **현재 시각**, 완료면 마지막 done 행에서 정지 |
| 12 | 현재 행 | `in_progress` 행이 있으면 그것, 없으면 첫 `pending` 행 |
| 13 | 현재 행 소요 | 직전 done 행 → 현재 시각 |
| 14 | 실시간 대기 귀속 | 완료 행은 `owner`, 현재 행은 `key`의 `*.user_confirm` 패턴 |
| 15 | 필드 명명 | **원천 용어 정렬** — 응답 키는 `state.json` 스키마 용어(`skill`·`timestamp`·`row_id`)를 쓴다. 사표 필드 `updated_at`·`row`는 deprecated 별칭으로 존치하되 값을 채운다. 「워크플로우」는 UI 표시 라벨로만 남는다 (캡틴 확정, ANALYSIS P-1·P-2 해소) |
| 16 | **소요 3계열 분해** | 소요를 **`캡틴` / `워커` / `PM`** 3계열로 나눈다 (캡틴 확정 2026-08-25 18:30). `캡틴` = `owner=user` 행 소요. `워커` = 그 행에서 서브에이전트가 실제 실행한 시간(신규 계측). **`PM` = 행 소요 − 캡틴 − 워커** — 별도 계측하지 않고 유도한다 |
| 16-a | **축퇴 규칙** | 워커 소요가 **미기록**인 행은 그 몫을 `PM`에 귀속한다. 따라서 기록이 없는 과거 태스크는 기존 2계열(`작업`=PM+워커, `대기`=캡틴)과 **수치가 동일**하다. 이 규칙이 완료기준 (2)(3)의 확정값(425=105+320, 799/276/75)을 보존한다 |
| 16-c | **진행 중 태스크의 4구획** | 실시간 총(`created_at`→`now`)은 정적 합보다 크다 — 차이가 **현재 행 경과 시간**과 정확히 일치한다(실측: 103에서 483 − 299 = 184 = `current_elapsed_minutes`). 따라서 진행 중 태스크의 A-1은 **총 = PM + 워커 + 캡틴 + 진행중** 4구획으로 렌더해 항등을 복원한다. 완료 태스크는 「진행중」 구획이 0이라 3구획으로 축퇴한다 |
| 16-d | 음수 차단 방식 | 사후 0-clamp가 아니라 **상한 clamp**를 쓴다 — `워커 = min(기록값, 소요 − 캡틴)`. 그래야 3계열 합이 항상 행 소요와 정확히 일치한다. 사후 clamp는 총합 항등을 깬다. clamp 발생은 `worker_clamped`로 표면화한다 |
| 16-b | 워커 소요 원천 | 워커 완료 시 하네스가 반환하는 `duration_ms`. PM이 `state-tool mark`에 전달해 행에 기록한다. `state.json` 행 스키마 확장이 선행이다 |
| 17 | **야간 시간대 보정** | **캡틴 지시 2026-08-26** — 「날이 다음 날로 바뀌는 경우 보정을 해서 00시~09시는 제외. 이 시간을 환경변수 등 어딘가에 정의해서 변경 가능하게.」 매일 반복되는 제외 구간과 겹치는 분을 소요에서 뺀다. 여러 밤에 걸치면 밤마다 전부 뺀다 — 실측상 두 밤이 빠지는 것은 `100`(42시간, −1,080분) 1건이며, `083`(30시간)은 한 밤만 걸쳐 −540분이다. **아래 §확정된 설계 방향의 「야간 공백 제외는 적용하지 않는다」를 이 항목이 뒤집는다** |
| 17-a | 설정 위치 | 기존 부트스트랩 2층 머지를 그대로 쓴다 — 전역 `~/.opal/setting.json`의 `quietHours` 위에 `{프로젝트}/.opal/setting.local.json`의 `quietHours`를 덮어쓴다(로컬 우선). 시드 원본은 `opal/core/setting.default.json`, 시드 배선은 `install-mac.sh`의 `SEED_KEYS`다. **기본은 켬** — `{enabled: true, start: "00:00", end: "09:00"}` |
| 17-b | 구간 해석 | 반개구간 `[start, end)`다 — 끝 정각(`09:00`)은 제외에 포함하지 않는다. `start > end`면 자정을 넘는 구간으로 읽는다(예: `22:00~06:00`). `start == end`거나 `enabled: false`면 보정을 적용하지 않는다 |
| 17-c | **제외분 귀속 계열** | 제외분은 **그 행이 속한 계열에서** 뺀다 — `owner == user` 행이면 `캡틴`에서, 그 외 행이면 `PM`에서다. 두 계열은 상호 배타적이다(캡틴 행은 16-d의 남은 몫이 0이라 워커·PM이 함께 0이다). 야간은 대부분 캡틴 대기지만 EXECUTE 야간 실행도 있어, 행의 계열을 따르는 것이 실제 귀속과 맞는다 |
| 17-d | **워커 소요는 보정 대상 아님** | 워커 실행 시간은 실측 벽시계이므로 제외 구간을 적용하면 실제보다 짧아진다. 상한 clamp(16-d)로 **워커 몫을 먼저 확보**하고 남은 몫에서만 제외분을 뺀다. 남은 몫이 제외분보다 작으면 0으로 멈춘다 — 이 clamp가 16-d와 충돌하지 않는 유일한 순서다 |
| 17-e | 3계열 항등 유지 | 보정 후 행 소요는 **3계열 합으로 확정**한다(먼저 총을 깎고 나누는 것이 아니다). 따라서 `총 = PM + 워커 + 캡틴`이 구성적으로 성립하고, 스택 막대가 총과 어긋나지 않는다 |
| 17-f | 원천 시각 불변 | `state.json`의 `created_at`·`timestamp`는 손대지 않는다. 앵커도 원천 시각 그대로 진전하며, 제외는 **계산에만** 적용한다 |
| 17-g | 표시 | 응답에 `quiet_hours_applied`(적용 여부)·`quiet_hours_label`(`00:00~09:00`)을 실어 FE가 배지로 표시한다. 같은 태스크가 `799`분으로도 `425`분으로도 보이면 혼란이므로 수치와 「무엇을 뺐는지」가 함께 실려야 한다 |

## 제약 조건

- **읽기 전용 유지** — 칸반은 읽기 전용 화면이다(`dashboard/frontend/src/pages/tasks/TasksPage.tsx:1-9` `@header`: "[MUST] 읽기 전용"). 통계 블록에 쓰기·편집 동작을 추가하지 않는다.
- **`state.json` 직접 편집 금지** — `[MUST]` `.opal/AGENT.md` §금지사항: "STATE.md 마크다운 직접 편집 금지 — `state-tool`만 사용." 본 태스크는 조회만 하며 상태를 쓰지 않는다.
- **색상 토큰 경유** — `[MUST]` `dashboard/frontend/src/index.css` `:root` 주석: "모든 컴포넌트는 이 토큰(또는 shadcn 표준 토큰)을 경유해야 한다. hex 하드코딩 금지 — oklch() 함수 값만 사용한다."
- **@header 규칙** — 코드 파일 생성·수정 시 `@header` 메타블록을 갱신한다 (`opal/core/references/harness/header-rules.md`).
- **플랫폼 분기 금지** — `.opal/AGENT.md` §금지사항: "하드코딩된 플랫폼 분기 추가 금지".
- **배포 경계** — `.opal/AGENT.md` §금지사항: "`~/.opal/` 직접 편집 금지 — 항상 프로젝트 소스를 수정한 후 install로 배포한다."
- **가로 스크롤 격리** — 표·막대 등 넓은 콘텐츠는 자체 컨테이너에서만 가로 스크롤한다. 패널 본문이 가로로 밀리지 않아야 한다.
- **성능** — 대시보드 집계는 프로젝트 전 태스크의 `state.json`을 읽는다. 기존 캐시 경로(`dashboard/backend/cache.py`)를 그대로 사용하고 무캐시 전수 스캔을 추가하지 않는다.
- **실시간 값의 AC 금지** — 실시간 파생값은 렌더 시각에 따라 변하므로 완료기준 수치 AC는 완료 태스크로만 잡는다. 진행 중 태스크의 AC는 값이 아니라 동작으로 기술한다.
