### 핵심 설계

#### Phase 1-1: 2단계 분리 (레이아웃 탐색 → 기술 스택 분석)

현재 1-1의 고정 테이블(55~68행)을 제거하고, 2단계 구조로 교체한다.

**Step A. 프로젝트 레이아웃 탐색 (신규)**

프로젝트 루트의 디렉토리 트리를 depth 2~3으로 스캔하여 실제 구조를 발견한다.

발견된 디렉토리를 아래 기준으로 분류한다 (판별 우선순위 순):

| 우선순위 | 판별 기준 | 분류 |
|---------|----------|------|
| 1 | config 파일 존재 (package.json, pyproject.toml, go.mod, Cargo.toml, pom.xml, build.gradle 등) | **코드 디렉토리** |
| 2 | 파일 유형 (.md, .docx, .pdf 등 문서 파일 존재) | **문서 디렉토리** |
| 3 | tasks/ 패턴 | **태스크 디렉토리** |
| 4 | 위 어디에도 해당 안 됨 | **미분류** (인터뷰에서 캡틴에게 확인) |

폴더명(`frontend/`, `server/` 등)은 **보조 힌트**로만 사용한다. 최종 판별은 반드시 config 파일 존재 여부가 우선이다.

레이아웃 탐색 결과를 내부 참조용으로 정리한다:
```
[레이아웃 탐색 결과]
코드: frontend/ (package.json), backend/ (pyproject.toml)
문서: docs/, 100.기획/
태스크: tasks/
미분류: assets/, scripts/
```

**Step B. 기술 스택 분석 (개선)**

기존: 루트의 고정 파일 목록만 스캔.
변경: Step A에서 발견된 **모든 코드 디렉토리**에서 config 파일을 탐색한다.

분석 대상 (코드 디렉토리별로 각각):

| 분석 대상 | 추출 정보 |
|----------|----------|
| `package.json` | 프로젝트명, FE 스택 (next→Next.js, react→React, vue→Vue.js 등) |
| `pyproject.toml` / `requirements.txt` | BE 스택 (fastapi→FastAPI, django→Django 등) |
| `go.mod` / `Cargo.toml` / `pom.xml` / `build.gradle` | BE 스택 (Go, Rust, Java 등) |
| `.env`, `docker-compose.yml` | 포트, DB 타입, 외부 서비스 |

추가 분석 (프로젝트 전체):

| 분석 대상 | 추출 정보 |
|----------|----------|
| `README.md` | 프로젝트 설명, 설치 방법 |
| `CLAUDE.md`, `.cursorrules`, `GEMINI.md` | 기존 컨벤션, 아키텍처 규칙 |
| 발견된 문서 디렉토리 | 기존 문서 목록 (docs/ 외 포함) |

설계 결정:
- 루트에도 config가 있으면(예: 표준 FE 프로젝트) 루트 자체가 코드 디렉토리로 분류된다 → 하위 호환 보장
- 발견된 코드 디렉토리가 0개면 → 비개발 프로젝트 (또는 빈 프로젝트)

#### Phase 1-2: 카테고리 판별 확장

현재 2가지(일반/개발)를 5가지 서브 카테고리로 확장한다.

**개발 프로젝트** (코드 디렉토리가 1개 이상 발견):

| 서브 카테고리 | 판별 기준 |
|--------------|----------|
| FE 단독 | FE config만 발견 (package.json + FE 프레임워크) |
| BE 단독 | BE config만 발견 (pyproject.toml, go.mod 등) |
| 풀스택 | FE + BE config 모두 발견 |
| 기획+개발 | 코드 디렉토리 + 문서 디렉토리 모두 발견 |

**일반 프로젝트** (코드 디렉토리 0개):

| 서브 카테고리 | 판별 기준 |
|--------------|----------|
| 기획/문서 | 문서 디렉토리만 발견 |
| 빈 프로젝트 | 코드도 문서도 없음 (디렉토리가 비어있거나 미분류만 존재) |

캡틴 확인 메시지 형식 변경:

```
[프로젝트 분석 결과]

프로젝트 구조를 분석했습니다.

{레이아웃 탐색 결과 요약}
  코드: {발견된 코드 디렉토리 + 기술 스택}
  문서: {발견된 문서 디렉토리}
  미분류: {미분류 디렉토리 — 있으면}

프로젝트 카테고리:
  1. 개발 프로젝트 — {서브 카테고리} ({근거})
  2. 일반 프로젝트 — {서브 카테고리}

추천: {자동 판별 결과}. 맞나요?
{미분류 디렉토리가 있으면} "{폴더명}"은 어떤 용도인가요?
```

빈 프로젝트인 경우:
```
[프로젝트 분석 결과]

프로젝트 루트가 비어있습니다.
인터뷰를 통해 프로젝트를 파악하고 docs/를 생성하겠습니다.

어떤 프로젝트를 시작하시나요?
  1. 개발 프로젝트 — 코드를 작성할 프로젝트
  2. 일반 프로젝트 — 기획, 문서 등 비개발 프로젝트
```

#### Phase 1-2 → 1-3 사이: 분석 결과 확인 삽입

위의 카테고리 판별 메시지 자체가 확인 과정을 포함한다. 캡틴이 카테고리를 확인/수정하고, 미분류 디렉토리 용도를 알려주면 그 결과를 반영하여 인터뷰로 넘어간다. 별도 단계를 추가하는 것이 아니라, Phase 1-2 메시지에 확인과 미분류 질문을 통합한다.

- **테스트**: 최신화 시 새 코드 디렉토리가 추가된 경우를 감지할 수 있는 흐름인지 확인
- **의존**: Step 1
