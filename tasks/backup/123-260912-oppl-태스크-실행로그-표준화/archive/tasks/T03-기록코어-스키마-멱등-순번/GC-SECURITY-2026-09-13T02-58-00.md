## 5. 확인하고 문제없던 항목 (디스패치 질문에 대한 답)

지적으로 올리지 않았으나 명시적으로 검사해 **이상 없음**을 확인한 항목이다.

1. **T02 기존 방어(GC-101/102/103)의 조각 경로 — 유지되고 있다.** `run/`이 심볼릭 링크로 치환된 상태에서 `validate-run`이 `run_log_missing`으로 거부함을 실측했다(`_resolved_segments()` :300). 조각 생성 `O_CREAT|O_EXCL|O_NOFOLLOW`(:731)와 append `O_WRONLY|O_APPEND|O_NOFOLLOW`(:826)도 그대로다. **이번 변경이 기존 방어를 우회·약화시키지는 않았다** — 문제는 신설 경로에 이식하지 않은 것이다(GC-201/202).
2. **`redact()` 단일 초크포인트(D-9) — 가져오기가 올라타 있다.** `import_agentic`/`import_oppl` → `_run_import_batch`(:1034) → `append()` → :815 `safe_event = redact(full_event)`. 가져오기 산출도 디스크 직렬화 직전 `redact()`를 통과하므로, **T06이 본문을 채우면 가져오기 경로에도 자동 적용된다.** `redact()`가 현재 pass-through인 것 자체는 T06 소관이라 결함으로 올리지 않았다.
3. **16 KiB 상한 — 가져오기 경로에 걸린다.** 실측 확인(GC-209 재현 참조). `append()` :818이 `redact()` 통과 후 최종 줄의 UTF-8 바이트로 재므로 판정과 디스크 크기가 일치한다. 다만 상한 **위반 시 배치 처리**가 문제다(GC-209), 그리고 **원본 파일 읽기에는 상한이 없다**(GC-207).
4. **정규식 ReDoS — 파국적 백트래킹 없음.** 모듈의 정규식 5종(`RUN_ID_PATTERN`, `_SHA256_RE`, `_RFC3339_MS_RE`, `_LEGACY_TIMESTAMP_RE`, `_resolve_import_run_id`의 파일명 패턴)을 80,005자 적대적 입력으로 실측했다 — 전부 0.002초 이하. 중첩 수량자·모호한 교대가 없다. legacy 표 파싱은 정규식이 아니라 문자열 `split()`(:940-947) 기반이라 애초에 백트래킹 대상이 아니다. `docs/SECURITY.md` §6 임계값(패턴 100자·`.*` 3회·중첩 수량자) 전부 통과.
5. **락 이중 획득/미획득 — 정확하다.** `_run_import_batch`(:1047)가 `_with_lock`으로 락을 잡고, 내부 `append()` 호출에 `lock_held=True`(:1034)를 넘겨 재획득을 피한다. `flock`은 open file description 단위라 같은 프로세스의 두 번째 `open()`+`LOCK_EX|LOCK_NB`도 충돌하므로, 이 전달이 없으면 자기 교착 후 타임아웃이 났을 것이다. 올바르게 처리돼 있다. (다만 원본 **파싱**은 락 밖에서 일어난다 → GC-210.)
6. **비밀 유출 — `worker_log_token` 원문을 코어가 다루지 않는다.** `begin-worker`·token 발급은 범위 밖이고, 코어·CLI는 `worker_log_token_id`만 취급한다(:695, :995, :1121, :1155, :1177, CLI :77). 원문이 흘러드는 코드 경로는 없다. **단, 호출자가 중첩 `provenance`에 넣으면 막지 못한다** → GC-208.
7. **오류 `detail`의 원본 내용 유출 — 과도하지 않다.** 봉투 오류는 키 이름(:542), enum 값(:546, :581), `request_id`(:809), 크기 숫자(:823) 등 최소 식별 정보만 싣는다. 원본 본문을 그대로 싣는 경로는 없다. `refs`(:625)·`timestamp`(:630)는 호출자 자신의 입력을 되비추므로 교차 경계 유출이 아니다. 다만 **처리되지 않은 예외의 스택 트레이스**는 내부 경로를 노출한다 → GC-203~206에 포함.
8. **D-5 단방향 의존 — 위반 없음.** `run_log_core.py`·`run_log_tool.py`에 `state_tool`·`state.json` 문자열이 0건이다(grep 실측). 판정② `mode` 인자도 계약대로 **받기만** 하고(:745, :779, :699) 어디서도 읽지 않는다.
9. **테스트의 real-usage 충실도 — 지켜졌다.** `tests/test_run_log_tool.py`에 mock/patch/MagicMock 사용이 0건이고(유일한 문자열 매치는 헤더 산문), `subprocess` 실호출이 7곳이다.

## 7. 판정 근거

| 판정 축 | 값 |
|---|---|
| check status | `pass` (3개 대상 전부 읽음, `checked_files == target_files`) |
| missing_capabilities | 없음 (`docs/SECURITY.md` 존재 → T0 기준 확보) |
| blocking finding | **7건** (GC-201, 202, 203, 204, 205, 206, 207) |
| advisory | 3건 (GC-208, 209, 210) |
| informational | 1건 (GC-211) |
| **최종 판정** | **FAIL** |

`gc-finding-schema.md` §6에 따라 `INCOMPLETE` 조건(어느 check라도 partial/error, 또는 missing_capabilities 비어있지 않음)은 성립하지 않으므로, blocking 1건 이상 → **FAIL**이다.

### 조치 우선순위 권고

1. **GC-201 / GC-202** — 같은 뿌리(신설 읽기 경로에 GC-103 방어 미이식)다. `_resolved_segments()`의 검증 루프를 공용 헬퍼로 뽑아 두 가져오기 경로에 적용하면 한 번에 닫힌다. 가장 먼저.
2. **GC-203 / 204 / 205 / 206** — 전부 "신뢰 불가 원본 파싱에서 예외가 봉투를 우회한다"는 한 가지 문제의 네 얼굴이다. 파서 진입점에 통일된 예외 그물(`OSError, UnicodeDecodeError, json.JSONDecodeError, ValueError, RecursionError`)과 타입 검사를 두면 함께 닫힌다.
3. **GC-207** — 위 2번과 같은 파서 진입점에서 바이트 상한으로 처리. T06과 값 조율.
4. **GC-208** — 소유 경계 판단(코어 폐쇄형 검증 vs T06 마스킹) 후 조치.
5. **GC-209 / 210 / 211** — 계약 변경 또는 낮은 영향. 소유자 판단.
