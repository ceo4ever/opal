# PRD: 태스크 실행 로그 표준화

> 1차 입력 SSOT: `docs/proposals/opal-task-run-log.md`
> 요구·제약·수용 기준의 원천은 같은 태스크 폴더의 `TASK.md`이며, 이 문서는 참조만 하고 재정의하지 않는다.
> 스키마·필드·명령 시그니처는 CONTRACT, 구현 방식은 TRD가 소유한다. 이 문서는 무엇을 왜 만드는가만 소유한다.

---

## 배경과 문제

OPAL은 지금 하나의 태스크 실행을 세 자산에 나눠 적는다. 현재 상태와 행별 시각·주체·워커 시간은
상태 파일(`state.json`)이, 게이트·오류·수정·판단·재시도·에스컬레이션의 서술은 자유 형식 실행 일지
(`AGENTIC-LOG.md`)가, 플랫폼이 실제로 주고받은 원본 출력은 Project Loop 실행 디렉터리(`.oppl-run/`)가
가진다(제안서 §3.1 자산 역할 표). 같은 사건이 세 형식으로 흩어져 있어 집계 주체가 무엇을 세야
하는지 정해져 있지 않고, 어느 자산도 기계 검증의 원천이 아니다.

문제의 본질은 정보가 없다는 것이 아니라 **복원할 수 없다는 것**이다. 상태 파일은 행마다 시각을
하나만 가지며 상태를 진전·표시·차단할 때마다 그 값을 덮어쓴다. 그래서 전이 과정과 워커가 중간에
내린 판단·검증·재시도를 되살릴 수 없다(제안서 §3.2, `docs/proposals/opal-task-run-log.md:82-83`).
그 결과 세 가지 실제 비용이 발생한다.

1. **워커 완료가 선언만으로 통과한다.** 워커가 어떤 궤적도 남기지 않아도 완료가 인정되므로,
   품질은 프롬프트 준수라는 사람·모델 의존 조건에 걸려 있다. 하네스가 품질을 보장한다는 프로젝트
   원칙(`docs/PROJECT.md` §프로젝트 원칙)이 이 지점에서만 성립하지 않는다.
2. **시간을 사후에 만들 수 없다.** 워커가 실제로 얼마나 걸렸는지, PM·사용자 승인 대기로 얼마가
   흘렀는지가 단일 원천에 없어 통계와 병목 판단이 추정에 의존한다.
3. **이력이 지워질 수 있다.** 실행 일지는 삭제 가능한 파일이고 삭제하면 태스크가 이력 없는 상태로
   되돌아간다. 즉 이력의 존재 자체가 보장되지 않는다.

여기에 자산 간 역할 중복이 겹친다. 사람이 읽는 저널(`STATE.md`)은 이미 기계 상태의 파생물로
축소됐고 기계 상태의 유일한 원천은 상태 파일이다(제안서 §3.1). 플랫폼 원본은 실행 중 창과 판단
기록이라는 두 성격을 함께 가지므로 표준 이력으로 삼기에 형식이 고정되지 않는다. 남은 선택은
실행 이력을 소유하는 **순서 있는 표준 사건 기록**을 새로 두고, 기존 자산은 각각 현재 상태 원천과
원본 증거로 역할을 좁히는 것이다(제안서 §1 1~4항).

## 목표

관찰 가능한 결과로 다음을 달성한다.

- **G-1 이력 원천의 단일화.** 태스크 실행 이력을 묻는 모든 질문이 하나의 표준 기록에서 답을 얻고,
  같은 사건이 두 자산에 서로 다른 형식으로 남지 않는다.
- **G-2 삭제로 우회되지 않는 계약.** 태스크가 실행 로그 계약을 가졌다는 사실이 지울 수 있는 파일이
  아니라 상태 원천 안에 있고, 로그가 사라진 태스크는 계약 없는 태스크로 되돌아가는 대신 고장으로
  드러난다.
- **G-3 기계가 본 것만 완료로 인정.** 지원 채널에서 워커의 완료는 채널 변환기가 실제로 관측한
  증거로만 인정되며, 관측 능력이 없는 채널에는 관측 능력 이상의 게이트를 주장하지 않는다.
- **G-4 시간의 결정론적 복원.** 워커 실행 시간과 PM·사용자 게이트 대기 시간이 단일 원천에서 같은
  방식으로 계산되고, 사람이 값을 손으로 넣지 않는다.
- **G-5 장애에도 멈추지 않고 잃지 않음.** 기록 계층이 실패해도 상태 전이가 교착되지 않고, 미기록
  사건은 보존됐다가 복구되며, 복구가 과거를 추정으로 지어내지 않는다.
- **G-6 표준 파이프라인 전역의 선언.** 표준 파이프라인 10종이 각자 실증된 완료 판정 등급을
  선언하고, 선언한 등급에 맞는 게이트를 받는다.
- **G-7 증거의 안전한 보존.** 표준 기록은 태스크 증거로 함께 보존되지만, 원본 출력과 비밀값은
  기본적으로 디스크에 남지 않는다.

## 비목표

아래는 제안서가 1차 범위에서 명시적으로 제외한 것이며, 이 태스크의 성패 판정에 포함하지 않는다.

| 비목표 | 제외 근거 |
|---|---|
| 상태 변경을 요청·확정 두 단계 사건으로 쪼개 커밋하는 방식 | 제안서 §1 7항, §6.2 — 1차는 미전송 사건 보관함(outbox) 방식으로 해결한다 |
| 일반화된 정정·무효화 의미론(correction 체인) | 제안서 §1 7항, §4.1 — 1차 사건 집합에 넣지 않는다 |
| Console의 실행 이력 분석 화면(타임라인·재시도·병목·게이트 대기 분석) | 제안서 §1 7항, §7, §10 Phase 2 — 관측 데이터 규약과 소비 화면을 분리한다 |
| Phase 2(분석 소비·archive 연계)와 Phase 3(산출물 단위 사건·세션 로그·플랫폼별 원본 확장) | 제안서 §10 — Phase 1C 실제 표본으로 필요성과 비용을 검증한 뒤 별도 승인한다 |
| L2 경량 트랙 | 제안서 §2.2 — 태스크 폴더를 만들지 않으므로 이 계약의 적용 대상이 아니다 |
| 태스크 파이프라인을 만들지 않는 operator와 PM의 읽기 전용 분석·비서 작업 | 제안서 §2.2 — 태스크 로그를 억지로 재사용하지 않고 별도 제안으로 다룬다 |
| 기존 태스크의 실행 일지 일괄 변환 | 제안서 §3.3 — 역사 증거로 보존하고, 필요할 때만 조건부 변환한다 |
| 호환 인자의 실제 제거 | 제안서 §7 — 1.0/1.1 태스크 지원을 위해 유지하며 제거는 legacy 지원 종료에서 별도 결정한다 |

| **프레임워크 유지보수자** | 같은 사건이 세 자산에 흩어져 규범 문서와 파이프라인 지시가 서로를 복제한다 | 이력 소유가 한 곳으로 수렴해 규범·하네스·파이프라인 문서가 조건부 한 줄로 정리되고, 플랫폼 차이는 변환 계층에만 남는다(TASK.md C-7) |

채널 변환 계층의 관심사이고 표준 기록의 형태는 플랫폼과 무관하게 동일하다.

## 요구사항

제안서 §11 추적표의 R-1~R-21을 ID를 보존한 채 제품 요구 관점으로 재서술한다. 판정 방법(도구·명령)은
TRD/CONTRACT 소관이므로 여기 쓰지 않으며, "관찰 지점"은 이 요구가 참인지 사람이 확인하는 **시점과
지면**을 가리킨다.

| R-ID | 요구 | 왜 필요한가 | 관찰 지점 |
|---|---|---|---|
| R-1 | 새로 만든 태스크는 실행 이력 계약을 반드시 갖고, 파일을 지워 그 계약을 없앨 수 없다 | 이력의 존재가 삭제 가능한 파일에 달려 있으면 이력 없는 태스크가 언제든 다시 생긴다 | 태스크 초기화 직후의 상태 원천, 그리고 로그를 지운 뒤의 진단 결과 |
| R-2 | 관측 가능한 채널에서는 워커가 결과에 영향을 준 작업 경계를 남긴다 | 완료 선언만으로는 무엇을 했는지 알 수 없고 품질을 하네스가 보장할 수 없다 | 워커 완료 판정 시점에 근거로 쓰인 사건의 출처 |
| R-3 | 한 번의 워커 실행은 종료 사건을 정확히 하나만 갖는다 | 종료가 둘이면 성공·실패가 동시에 참이 되어 집계와 게이트가 갈라진다 | 워커 단위 검증 결과 |
| R-4 | 여러 기록이 동시에 일어나도 기록이 깨지지 않고, 정상 진행을 고장으로 오판하지 않는다 | 병렬 워커가 표준이므로 동시성 결함은 상시 발생하고, 오탐은 정상 작업을 차단한다 | 동시 실행 구간의 기록 순번 연속성과 완료 차단 발생 여부 |
| R-5 | 저장된 순서를 인과 순서로 착각하지 않는다 | 병렬 워커 사이에 없는 선후관계를 만들면 이후 분석이 전부 틀린 전제 위에 선다 | 병렬 구간 사건의 주체별 순번과 원인 링크 유무 |
| R-6 | 기록 계층이 실패해도 상태 전이가 교착되지 않고 사건을 잃지 않는다 | 관측을 위해 실행을 멈추면 도구가 일을 막는 것이 되고, 유실되면 관측 자체가 무의미하다 | 기록 실패를 연속으로 겪은 태스크의 진행 가능 여부와 복구 후 사건 수 |
| R-7 | 워커 실행 시간의 원천은 하나다 | 원천이 둘이면 어느 값이 맞는지 사람이 매번 판단해야 하고 통계가 흔들린다 | 태스크 통계에 노출된 워커 시간과 그 파생 관계 |
| R-8 | 비밀값은 어떤 기록 경로에도 평문으로 남지 않는다 | 표준 기록은 git으로 추적되므로 한 번 새면 회수할 수 없다 | 표준 기록·원본·가져오기 경로 각각의 저장 결과 |
| R-9 | 기존 자산과 실행 사건을 이중으로 소유하지 않는다 | 이중 소유는 지금 문제의 원인이며, 새 기록을 추가만 하면 자산이 하나 더 늘 뿐이다 | 활성 계약 태스크에서 실행 일지의 생성 여부와 저널에 남은 참조 형태 |
| R-10 | 기존 상태·통계 동작이 회귀하지 않는다 | 관측성 도입이 이미 동작하는 태스크 운영을 깨뜨리면 도입 자체가 거부된다 | 기존 상태 도구 전체 검증과 Console 동결 기준값(TASK.md C-2) |
| R-11 | 표준 파이프라인 전부가 실증된 완료 판정 등급 계약을 지킨다 | 일부만 적용하면 태스크마다 완료의 의미가 달라져 통계가 합쳐지지 않는다 | 파이프라인 10종 각 호출 경로의 등급 선언과 적합성 판정 |
| R-12 | 플랫폼 원본 형식과 표준 사건 형식이 분리된다 | 플랫폼 분기가 도구 안으로 들어오면 플랫폼 독립성 원칙이 무너진다(TASK.md C-7) | 서로 다른 플랫폼 원본이 만들어 낸 표준 사건의 동일성 |
| R-13 | PM·사용자 게이트의 대기 시간을 복원할 수 있다 | 실제 리드타임의 큰 부분이 승인 대기이며 지금은 전혀 보이지 않는다 | 게이트 요청과 해결이 쌍으로 남았는지, 짝 없는 해결이 거부되는지 |
| R-14 | 기록 도구는 상태 원천을 알지 못하며 의존은 한 방향이다 | 순환 의존은 상태 도구의 회귀 위험을 기록 도구까지 확산시킨다(TASK.md C-4) | 기록 도구 검증이 상태 자산 없이 성립하는지 |
| R-15 | 실행 일지 기록 계약을 규범 문서가 이중으로 소유하지 않는다 | 문서가 무조건 생성을 지시하는 한 활성 태스크에서도 옛 자산이 계속 만들어진다 | 파이프라인·하네스·컨벤션 문서에 남은 지시의 조건 형태 |
| R-16 | 명시적 재실행만 새 실행 단위를 만든다 | 세션 재접속이 새 실행으로 집계되면 실행 횟수와 시간이 모두 부풀려진다 | 재접속·재개 후의 실행 식별자 유지 여부와 명시적 재실행의 종료·시작 기록 |
| R-17 | 추적되는 기록 파일이 무한히 커지지 않는다 | 단일 파일이 커지면 변경 이력 열람과 손상 반경이 함께 나빠진다 | 상한 경계에서 새 조각이 생기고 기존 조각이 불변인지 |
| R-18 | 두 시간계(표준 UTC와 기존 로컬 시각)를 일관되게 해석한다 | 해석이 갈리면 날짜 경계 통계가 어긋나고 조용시간 판정이 틀린다 | 기존 통계 기준값과 날짜 경계 표본에서의 일치 |
| R-19 | 응답이 유실돼 재시도해도 사건이 중복되지 않는다 | 중복 종료 사건 하나가 완료 게이트와 시간 집계를 동시에 망가뜨린다 | 같은 요청 식별자 재호출의 결과와 다른 내용 재사용의 거부 |
| R-20 | 워커의 기록 권한을 다른 실행·사건에 재사용할 수 없다 | 권한이 새면 워커 사건을 다른 워커가 위조할 수 있어 증거의 신뢰가 사라진다 | 권한 발급·폐기 사건만으로 재구성한 권한 상태와 만료·폐기 후 재사용 시도 결과 |
| R-21 | 프롬프트 준수율만으로 강제 모드를 켜지 않는다 | 준수율은 모델·프롬프트가 바뀌면 함께 변하므로 게이트의 근거가 될 수 없다(TASK.md C-6) | 강제 승격 결정에 제출된 근거의 종류와 정량 기준 충족 여부 |

- 요구와 백로그 슬라이스의 대응은 제안서 §11.1이 소유하며, 슬라이스 식별자 자체는 설계 루프의
  백로그 단계에서 확정한다.

## 단계별 인도 범위

제안서 §10을 인도물과 게이트 관점으로 재서술한다. 각 Phase는 독립 승인·독립 완료 기준을 가지며
하나의 구현 태스크로 합치지 않는다(제안서 §10 Phase 1C 말미).

### Phase 0 — 채널 관측 능력 실측

- **인도물**: 채널별 완료 판정 등급 배정과 그 근거인 **원본 증거 파일**. 배정 결과는 기계가 읽는
  파일(`profiles.json`)로 남긴다(제안서 §4.2.1).
- **판정 대상 축 2개**: PM이 외부 에이전트 도구를 호출하는 축과, Project Loop 내부의 헤드리스 CLI
  축을 **별도로** 판정한다(제안서 §10 Phase 0). 두 축은 관측 가능한 것이 다르므로 한쪽 결과를
  다른 쪽에 전용하지 않는다.
- **범위 밖**: 도구·변환기 구현은 이 단계에 없다. 읽기·실험 전용 슬라이스다.
- **게이트 (필수·사람)**: 이 단계 완료 직후 PM은 채널별 배정과 증거를 사용자에게 보고하고
  **승인을 받는다. 승인 전에는 어떤 구현 태스크에도 진입하지 않는다.** 이 게이트는 백로그 의존
  관계로 대체되지 않으며 자율 진행 모드에서도 유지한다
  (`docs/proposals/opal-task-run-log.md:653-655`).

### Phase 1A — 기반 구축과 그림자 운영

- **첫 슬라이스(워킹 스켈레톤)**: 태스크 초기화가 새 상태 계약과 첫 기록 조각을 만들고, 사건 1건이
  기록되며, 그 경로가 검증을 통과하는 관통 1건. 이 프로젝트는 CLI·프레임워크이므로 이것이
  워킹 스켈레톤이며, 이후 모든 검증은 이 경로 위에서 실행한다. 스켈레톤 부재를 이유로 한 모의
  검증은 허용하지 않는다(제안서 §10 Phase 1A).
- **나머지 인도물**: 폐쇄형 사건 어휘와 출처 검증, 동시성 안전성과 순번 발급, 상태 원천의 미전송
  사건 보관함과 중단 가능한 초기화·복구, 비밀값 마스킹·원본 상한·추적 제외·시간계 변환, 기존
  실행 일지와 플랫폼 원본을 표준 사건으로 바꾸는 **단방향·멱등 가져오기 능력**(제안서 §10 Phase 1A
  1항, §3.3·§3.4 — 변환 방향은 원본에서 표준으로만 흐르고 역변환은 금지하며 원본은 증거로 보존한다),
  그리고 두 시범 파이프라인(`opds`, `oppl`)의 등급별 변환 계층. 이 단계의 가져오기는 능력만 갖추는
  것이고 완료 게이트와는 무관하다.
- **운영 모드**: 두 시범 파이프라인은 **그림자 모드**로 돌린다. 이 기간의 기록 원천은 여전히 기존
  실행 일지이고 새 기록은 비교 후보이므로 완료를 차단하지 않는다.
- **게이트 (정량)**: 채널별로 정상 완료 표본 20건 이상과 즉시 실패·차단·기록 실패·동시 경계 각
  1건 이상을 모으고, 등급별 포착률 100%·오차단 0건·기록 누락으로 인한 우회 0건·복구 성공률 100%를
  모두 충족해야 다음 단계 승격 후보가 된다. 관측 불가 등급은 수치와 무관하게 승격 대상이 아니다
  (제안서 §10 Phase 1A). 보존 비용 정책도 이 단계의 실측 없이는 승인하지 않는다(제안서 §8.2).

### Phase 1B — 적격 시범 파이프라인 강제 적용

- **인도물**: Phase 1A 정량 기준을 통과한 **호출 경로만** 강제 모드로 승격한다. 등급별 완료 게이트,
  게이트 요청·해결 사건, 미전송 사건 복구와 사용자 우회, 명시적 재실행, 시간 자동 파생과 구버전
  호환, 공유 규범을 "강제면 새 기록 / 구버전·그림자면 기존 일지"의 조건부 계약으로 개정, 그리고
  **가져온 사건이 워커 완료 게이트에 기여하지 않음을 집행**(제안서 §10 Phase 1B 5항과 §11.1의 R-9 배정,
  §4.3 기록 주체 표 — 가져오기 경로는 의미상 주체가 워커여도 완료 근거가 되지 않는다).
- **게이트**: 한 채널이 부적격이면 그 채널만 그림자를 유지하고 다른 시범 파이프라인의 승격을 막지
  않는다. 승격 파이프라인의 적합성, 그림자 유지 파이프라인의 비차단 회귀, 기존 상태·Console 회귀를
  함께 통과해야 한다(제안서 §10 Phase 1B).

### Phase 1C — 나머지 파이프라인 확산

- **인도물**: 남은 8종을 4배치(`opd+opdw`, `opp+opwt`, `opgc+oppd`, `opsdd+opdd`)로 확산한다.
  마지막 배치에서 태스크 프로세스·병렬 실행·하네스 2종·컨벤션 문서와 상태 도구 검증을 함께 개정해
  무조건 기록 지시를 제거하고 구버전 조건만 남긴다.
- **게이트**: 각 배치는 자기 파이프라인 적합성과 전체 상태 회귀를 통과한 뒤에만 다음 배치로
  진행한다(제안서 §10 Phase 1C).
- **종료**: 실행 루프의 완료 판정은 Phase 1C까지로 닫는다. Phase 2·3은 여기서 쌓인 실제 표본으로
  필요성과 비용을 검증한 뒤 별도 승인한다(제안서 §10, §11.1).

| RK-6 | 시작·종료만 관측되는 등급에서 기존 산출물·PM 검증은 **사유를 붙인 강제 우회가 가능**하다(제안서 §4.2) | 이 등급의 무조건적 기계 강제 범위가 시작·종료까지로 제한되어 기대보다 약하다 | 이 등급이 강한 궤적 달성으로 계산되지 않도록 보고를 분리하고, 중간 궤적 부재를 명시적으로 노출한다. 우회는 결정 기록으로 남겨 사후에 셀 수 있게 한다 |
