## 2. gap — ① 목표달성: S-23의 기대 결과 계약이 자기 fixture와 불일치

S-23은 갱신 국면의 **유일한** 런타임 증거이며, `header-rules.md` §갱신 시점 (4단) (d) 행이 인용한 탐지 조건의 실발동을 본다는 설계 의도는 정확하다. 문제는 관측 대상 필드와 사전 조건이 실제 도구 동작과 어긋나 있다는 점이다. 도구 원본(`opal/tools/code-scan/code-scan.js`) 판독 결과:

**(a) `manifest` 모드에서 관리 매니페스트가 있는 디렉토리의 신규 파일은 `newly_uncovered`가 아니다**

`code-scan.js:3207`이 미커버 파일의 하위분류를 두 갈래로 나눈다.

```
const managedByManifest = !isInlineMode && !!(mctx && mctx.manifest);
const sub = managedByManifest ? 'no_entry' : classifyUncovered(projectRoot, relPath);
```

S-23의 조건은 "`/tmp/opal-ts106/proj/` (S-20 완료 상태 — `headerSource: manifest` + code-map 존재)"다. S-20이 `scaffold`까지 완주한 상태이므로 대상 패키지에는 관리 매니페스트가 존재한다. 그 디렉토리에 @header 없는 신규 파일을 넣으면 `sub`는 **`no_entry`**(구조적 결손, git 상태 무관·항상 차단)로 분류된다. 그런데 `counts`(`:3420-3430`)에는 `no_entry` 키가 없고, `newly_uncovered`는 `:3427`에서 `v.sub === 'newly_uncovered'`만 계상한다. 즉 **게이트는 정상 차단(exit 2)하지만 `counts.newly_uncovered`는 0**이다 — S-23 기대 결과 ①의 "`counts.newly_uncovered` **≥ 1**"이 성립하지 않는다. 차단이 옳게 일어나도 시나리오는 FAIL로 기록되고, 반대로 테스트 워커가 기대치를 사후 완화하면 (d) 행의 탐지 조건이 검증되지 않은 채 통과 기록만 남는다.

**(b) 비-git 트리에서는 차단 자체가 일어나지 않는다 — exit 0**

신규 파일을 관리 매니페스트 밖에 두면 `classifyUncovered`(`:1085-1088`)를 타는데, 첫 분기가 git 가용성이다.

```
if (!isGitUsable(projectRoot)) { warnGitUnavailableOnce(); return 'pre_existing'; }
```

`isGitUsable`(`:1025-1037`)은 work-tree 판정 **AND** `HEAD` 검증을 모두 요구한다 — `git init`만 하고 커밋이 없는 트리도 false다. `pre_existing`은 `:3434-3436` 차단 필터에서 제외되어 `ok = true` → `:3455` `process.exit(0)`. §2.1의 fixture 선언은 "코드 파일 3개 이상 + `.opal/` 없음(초기 상태) / 수동 생성"뿐이고 TEST-SCENARIO.md 전문에 `git init`·git 저장소 요건 언급이 **0건**이다. 즉 fixture를 문면대로 만들면 **탐지가 발동하지 않고 exit 0**이 되어, 갱신 국면 집행이 없는 것처럼 관측된다.

**결과**: S-23이 기대 결과대로 관측되는 구성은 "신규 파일이 관리 매니페스트 밖 + 트리가 커밋 1개 이상 보유한 git 저장소"라는 좁은 조합 하나뿐이며, 시나리오는 그 조합을 어디에도 고정하지 않았다. 세 갈래(no_entry / newly_uncovered / pre_existing) 중 어디로 떨어지는지가 미결정인 채로 단일 필드에 기대치를 걸었다.

**정정 방향** (Producer 재작성 대상 — 본 평가자는 판정만 반환하며 TEST-SCENARIO.md를 수정하지 않는다):
1. S-23 조건에 신규 파일의 **배치**를 명시한다 — 관리 매니페스트 밖 경로(→ `newly_uncovered` 경로) 또는 안(→ `no_entry` 경로) 중 어느 갈래를 보는지 택일.
2. `newly_uncovered` 갈래를 택하면 §2.1 fixture 행에 **git 저장소 + 커밋 1개 이상**을 사전 조건으로 추가한다(없으면 `pre_existing`·exit 0 폴백).
3. `no_entry` 갈래를 택하면 기대 필드를 `counts.newly_uncovered ≥ 1`이 아니라 `violations[].sub == "no_entry"` + exit 2로 교정한다.
4. 어느 갈래든 (d) 행 문면이 인용한 조건과 관측 필드가 **같은 것**을 가리키는지 1줄로 대조한다 — (d)가 "CLOSE 게이트 `newly_uncovered` 누적"을 명시하는데(S-6) 실측이 `no_entry`로 차단된다면, (d) 문면 자체가 도구 동작과 어긋난다는 별개 신호이므로 F-002 문면 정정으로 되돌려야 한다.

> 4항은 단순 시나리오 수정이 아니라 **F-002 산출물 문면의 정확성** 신호일 수 있다. (d) 행이 `newly_uncovered`만 인용하는데 manifest 모드 신규 파일의 실제 차단 사유가 `no_entry`라면, 갱신 미수행 탐지 조건 기술이 불완전하다. 이 판단·반영은 PM 책임이다.

## 3. 소비 국면(R-3) 문면 전용에 대한 ①축 판정 — 감점 사유 아님(구조적 한계 수용)

R-3(2단 소비 절차)은 S-7 하나로만 검증되고 계층이 L1 문면 판독이다. 이를 ①축 감점 사유로 볼지 판정한 근거는 다음 3가지다.

1. **목표 문장이 소비 국면에 부여한 동사는 "편입"이다** — 목표는 "갱신 트리거와 소비 2단 절차를 **하네스에 편입**하여 3국면을 완결"이다. 생성·갱신 국면의 목표어("자산의 생성·갱신")는 자산 상태 변화를 함의하므로 런타임 관측이 필수지만, 소비 국면의 산출물은 하네스 규정 자체다. S-7은 그 산출물을 직접 판정한다 — §13 4열 2행 표 · 2차 전환 허용 조건 · 소유자 오버라이드와의 구분 · "Glob/Grep 직행 금지"와의 비모순 · `dispatch-process.md` 포인터 1건·원문 복제 0건 · `:237` 원문 무변경. 목표가 요구한 대상이 목표가 요구한 층에서 검증된다.
2. **F-003에는 실행 표면이 설계상 존재하지 않는다** — PLAN.md §3.4의 집행 지점 후보 비교(후보 3종·확정 1종·탈락 근거, S-8이 보존 검증)는 도구 게이트를 **F-004에만** 두었다. 2단 소비 규율을 집행하는 도구는 이 태스크 범위에 없다. 없는 표면의 런타임 관측을 요구하는 것은 시나리오 결손 지적이 아니라 **범위 확대**이며, 그것이 필요하다는 판단은 drift 신호로 PM에 에스컬레이션할 사안이지 판단축 감점 사유가 아니다.
3. **행동 준수 관측은 계약이 아니라 LLM 순응도를 측정한다** — 실제 디스패치에서 워커가 code-map을 먼저 읽었는지 관측하는 L3 시나리오는 원리적으로 가능하나, 그 관측 대상은 비결정적 순응 행동이고 산출물 계약이 아니다. 프레임워크는 규정 산출물의 검증 수단으로 L1 문면 판독을 채택하고 있으며, 이 태스크의 위험 가설도 그에 정합하게 H-2를 **L1**으로 등록했다(§1 리스크 가설 표). 시나리오 집합이 자기 가설 표의 계층 선언을 따른 것을 결손이라 볼 수 없다.

**단, 기록 요건 1건**(비차단): 소비 국면은 **문면 검증까지만** 완결된 것이므로, DONE/VERIFY 기록에서 3국면 완결을 서술할 때 소비 국면을 런타임 집행으로 기술하지 않아야 한다. 생성·갱신(런타임 관측)과 소비(문면 편입)의 증거 등급 차이를 그대로 남기는 것이 이 판정의 전제다.
