# TASK: code-scan 매니페스트 샤딩 — 파일 크기 상한 기반 분산 구조

> 작성일: 2026-08-03 | 작업 유형: 개선 | 적용 스킬: opds | 모드: agentic
> 입력: 사용자 요청 + PM 코드 실측 분석
> 출력: TASK.md

## 작업 목표

code-scan 매니페스트가 단일 파일에 과대 집적되어 이를 다루는 워커가 실패하는 문제를, 한 디렉토리의 매니페스트를 **의미 단위 샤드로 분산**하고 **파일 크기 상한을 도구가 집행**하는 구조로 해소한다.

## 배경

`code-scan`은 "소스 디렉토리 1개 = 매니페스트 1개"를 고정 규칙으로 삼는다. 디렉토리에 파일이 많으면 매니페스트가 그만큼 비대해지고, 이를 열람하는 워커의 컨텍스트가 한 번에 불어난다.

실사용 프로젝트에서 사고가 발생했다 — 단일 매니페스트가 86.4KB / 292 엔트리까지 커졌고, 해당 스코프를 담당한 워커가 매니페스트 열람 중 모델 턴 1회가 600초 워치독을 초과해 강제 종료됐다. 그 스코프의 산출물은 0건으로 남았다.

원인은 **크기 상한이 어디에도 없다**는 점이다. 현재 도구는 매니페스트가 얼마나 커지든 감지하지도, 분산하지도 못한다.

## 배경 분석 (대화에서 도출)

### (1) 자산 실측 — 대규모 code-map을 보유한 실사용 프로젝트 1곳

| 항목 | 실측값 |
|---|---|
| 전체 매니페스트 수 | 1,013개 (스코프 레지스트리 `index.json` 포함) |
| 20KB 초과 매니페스트 | 5개 (+ `index.json` 27.1KB) |
| 최대 매니페스트 | 86.4KB / 292 엔트리 |
| 상위 5개 크기 | 86.4KB(292) · 61.6KB(228) · 31.3KB(126) · 29.2KB(103) · 28.8KB(128) |

- 문제는 **국소적**이다 — 1,013개 중 5개. 다만 그 5개가 전부 핵심 도메인이라 열람 빈도가 높다.
- **파일 수는 크기의 대리지표로 부정확**하다 — 292엔트리=86.4KB, 128엔트리=28.8KB로 엔트리당 편차가 2배 이상이다.
- 초과 5개 중 **3개는 미러 하위 폴더가 이미 존재**하고 그 안에 진짜 하위 디렉토리 매니페스트가 들어 있다 — 샤드를 같은 폴더에 섞으면 두 종류가 육안으로 구분되지 않는다.
- 크기 구성은 서술 44.3% · JSON 구조 27.1% · 엔트리 키 13.4% · exports 13.4%로, 서술을 줄여도 절반이 남는다. **덩치의 지배 변수는 엔트리 개수**다.

### (2) 코드 실측 — `opal/tools/code-scan/code-scan.js` (v1.4.0, 2,180줄)

| 지점 | 현재 동작 | 샤딩 시 영향 |
|---|---|---|
| `resolveManifestContext` `code-scan.js:944-956` | `mirrorPathForDir()`로 경로를 **계산**해 매니페스트 1개만 `loadManifest` | 형제 샤드가 열리지 않음 |
| `resolveHeader` `code-scan.js:1037-1038` | `mctx.manifest.files[basename]` / `.package` 단일 참조 | 샤드 엔트리 미해석 → `uncovered` 오탐 |
| `decideTarget` `code-scan.js:1106` | `out.manifest`를 미러 경로로 고정 | 워커가 쓸 샤드를 알 수 없음 |
| `validate` `code-scan.js:1931-1935` | `actualMirrorRel !== expected` → `worker_scope_violation:dir_mismatch` | 샤드가 전량 위반 처리 |
| `validate` `code-scan.js:1957-1967` | 매니페스트별로 `files_key_added`/`files_key_removed` 판정 | 샤드마다 "디스크에 있는데 내 files에 없다" 전량 오탐 |
| `cmdScaffold` `code-scan.js:1724-1732` | `validManifestPaths`에 없는 매니페스트를 `stale`로 수집 | **샤드 전량이 stale로 오탐** |
| `mergeManifest` `code-scan.js:1600-1627` | `existing.package`만 보존 | 샤드 선언이 scaffold마다 소실 |
| `code-map-hook.js:78-80` | `decideTarget` 결과의 `manifest`를 직접 읽어 미갱신 감지 | `decideTarget`만 정합하면 자동 정합 (별도 변경 불요) |

### (3) 왜 지금 구조로는 분할이 불가능한가

`resolveManifestContext`가 파일 경로에서 매니페스트 경로를 **탐색이 아니라 계산**한다 (`code-scan.js:948-954`). 따라서 같은 디렉토리를 가리키는 형제 매니페스트를 사람이 손으로 만들어 두어도 도구는 열지 않으며, `validate`는 그 파일을 `dir_mismatch` 위반으로 거부한다. 즉 **도구 변경 없이는 자산 분할 자체가 성립하지 않는다.**

## 확정된 설계 방향 (대화에서 합의)

| # | 확정 사항 | 근거 |
|---|---------|------|
| 1 | **분산 구조를 채택한다** — 목적은 "매니페스트 파일당 크기 상한 관리"다 | 소유자 확정 |
| 2 | 샤드는 **예약 폴더 `_shards/`** 에만 둔다. 기존 "하위 디렉토리 → 미러 하위 디렉토리" 규칙은 그대로 둔다 | 초과 5개 중 3개가 미러 하위 폴더 기존재 (배경 분석 §1) |
| 3 | **베이스 매니페스트**(도구가 원래 여는 경로)가 샤드 선언을 보유한다 — 경로 계산 규칙 무변경 | `mirrorPathForDir()`가 산출하는 경로가 정확히 그 파일 |
| 4 | **크기 상한을 필수 필드로 두고 도구가 집행**한다 — 상한이 이 태스크의 목적 그 자체 | 상한 없으면 샤드 재비대로 동일 사고 재발 |
| 5 | 상한 단위는 엔트리 수가 아니라 **바이트**다 | 엔트리당 편차 2배 이상 (배경 분석 §1) |
| 6 | 샤드 메타데이터는 **최소 집합**으로 한다 — 분할 축 기록·샤드별 리뷰 상태·샤드별 출처 등 확장 훅은 두지 않는다 | PRINCIPLES §2 — 현 요구에 없는 사변 설계 금지 |
| 7 | 샤드 선언 보유 파일의 명칭은 **"베이스 매니페스트"** 로 통일한다 | 스코프 레지스트리 `index.json`과 "인덱스" 명칭이 충돌 |
| 8 | **순번 분할 금지** — 크기가 분할 트리거, 의미가 분할 경계. 각 샤드는 사람이 읽는 라벨을 갖는다 | 순번은 "어디를 열지" 예측 불가, 파일 추가 시 경계가 흔들림 |
| 9 | **옵트인** — 샤드 선언이 없으면 동작이 현재와 바이트 단위 동일 | 기존 자산 무변경, 타 프로젝트 영향 0 |
| 10 | 이번 태스크 범위는 **도구 개선까지**다. 실제 자산의 의미 분할은 도구 적용 프로젝트 측 별도 작업 | 분할은 서술 기반 의미 분류 작업으로 성격이 다름 |

## 제약 조건

- **배포 경계 준수** — `~/.opal/tools/code-scan/`를 직접 편집하지 않는다. `opal/tools/code-scan/`만 수정하고 install로 배포한다.
- **하위호환 절대 조건** — 샤드 선언이 없는 매니페스트에서는 모든 명령의 출력이 변경 전과 바이트 단위로 동일해야 한다.
- **판정 지점 봉인 유지** — 태스크 080이 `resolveHeaderSource`·`isInScope` 각 1곳으로 봉인한 모드/스코프 판정 구조를 훼손하지 않는다.
- **inline 모드 무영향** — `headerSource=inline`에서는 매니페스트를 읽지도 쓰지도 않으므로 샤드 로직이 발동하지 않아야 한다.
- **버전 관리** — code-scan 버전을 상향하고(`v1.4.0` 기준) 변경이력에 태스크 번호를 남긴다.
- **커밋 금지** — 소유자의 명시 요청 전까지 커밋하지 않는다.
