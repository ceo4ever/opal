# PLAN: OPPL 실행 안정화 — 상한·완료판정 도구 집행

> 입력: [TASK.md](TASK.md), [ANALYSIS.md](ANALYSIS.md) | 작성 시점 2026-09-14 00:24 KST | 기준 리비전 `b37cbad`, 워킹트리 `.opal-worktrees/task_131`

## Approach

제안서 §10의 9단계 순서를 4개 실행 그룹으로 압축한다. 실행 원시 기능(process group·watchdog·terminal framing·출력 writer)은 `opal-agent` 한 곳에 모으고, 회전·attempt·예산 상한은 신규 `oppl-runtime-tool`이 소유하며, 소비자(`opal-action-monitor`·loop-action-agent·OPPL 스킬)는 도구 판정을 읽기만 한다. 판정 로직을 소비자 쪽에 복제하지 않는 것이 이번 변경의 단일 축이다.

범위 경계 3가지를 먼저 고정한다.

1. `opal-agent`는 OPPL과 OPPD가 공유하는 실행 원시 기능의 단일 owner다(`docs/proposals/opal-oppd-v3-lean-project-execution.md` §4.6 `:332-346`). 따라서 `opal-agent`에 `round`·`resume` 상한·수렴 판정·phase 이름의 OPPL 의미론을 넣지 않는다. `opal-agent`는 "호출자가 준 timeout·출력 경로·mode"만 알고, 그 값이 어느 phase 정책에서 왔는지는 모른다.
2. `oppl-runtime-tool`은 OPPL 전용 상한·admission만 소유하고 PID·PGID·heartbeat·terminal result 원문을 복제하지 않는다(같은 §4.6 `:344-345`, TASK C-4).
3. 기존 `--json`·`--text` 경로는 인자 추가 없이 호출하면 관측 동작이 완전히 동일하다(TASK C-8). `code-scan depends opal/tools/opal-agent/opal_agent.py` 결과 `depended by: (none)` — 저장소 안에 정적 import 소비자가 없고 전부 CLI 호출자이므로, 회귀 경계는 CLI 표면(인자·stdout·exit code)으로 한정된다.

## Release and recovery

- 적용 순서: P1(W-1~W-4, 서로 독립) → P2(W-5 opal-agent 단일 파일 / W-6 신규 도구 본체) → P3(W-7 스킬·에이전트 문서 / W-8 monitor) → P4(W-9~W-12 문서·brain·통합 검증·배포). `opal_agent.py`는 D1·Q1·Q2가 모두 닿는 단일 파일이므로 W-5 하나·담당 하나가 전부 소유한다. 제안서 §10 순서와의 차이는 두 곳뿐이다 — §10-7(BACKLOG 머리말)을 P1로 앞당긴 것은 다른 항목과 의존이 0이고 파일이 독립이라 병렬 이득이 있기 때문이고, §10-8(통합 검증)·§10-9(배포)를 한 W로 합친 것은 AC-19가 "배포본에서 실제 호출"을 요구해 배포 없이는 검증이 닫히지 않기 때문이다.
- 검증 범위: 결정론 — W-1 fixture 기반 adapter 판정(AC-2·AC-3·AC-14), 설정 로더 거부(AC-5), 지문 동일성(AC-7). 회귀 — `--json`·`--text` 기존 경로 전건(AC-17), run_id 없는 `state.json` validate(H-2), monitor legacy 경로(AC-9). 실제 연동 — process group 소멸·손자 프로세스 회수(AC-1), 동시 `admit` lock(AC-11), 배포본 실호출(AC-19). mock 전용 통과 항목 0건(AC-20).
- 실측 경계: `hard_timeout_sec_by_phase`·`max_hard_timeout_sec`·`terminate_grace_sec`는 이번 구현에서 기본값을 코드에 박지 않는다 — 설정 부재는 실행 거부다(AC-5). 통합 테스트의 timeout fixture는 초 단위 실시간 대기를 쓰되 `terminate_grace_sec`를 테스트 전용 소값으로 주입해 총 실행 시간을 제한한다.
- 실패 시: P1~P3은 코드·문서 변경만이라 워크트리 revert로 복구된다. P4의 install 재배포 후 문제가 발견되면 이전 리비전에서 `./scripts/install-mac.sh`를 재실행해 배포본을 되돌린다 — `~/.opal/`를 직접 편집해 되돌리지 않는다(C-6). `runtime.json`은 태스크 폴더 `.oppl-run/` 하위 신규 파일이라 삭제만으로 이전 동작(monitor legacy 6상태 경로)으로 되돌아간다.
