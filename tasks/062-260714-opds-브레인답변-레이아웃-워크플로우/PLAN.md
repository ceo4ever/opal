## 1. 태스크 개요 + 기능 리스트업

### 1.1 요약

### F-001: §답변 구조 절 재작성

#### 3.1.1 파일 변경 계획

**수정**

| # | 경로 | 영역 | 변경 내용 요약 | 근거 |

| 1 | `opal/skills/opal-brain/SKILL.md` | 스킬 | `### 답변 구조 — 적응형 마크다운 계층` 절(L322~334) 본문을 6단계 워크플로우 + 6축 + 5후보 + 판정 규칙 + 가드 3종 + 2예시로 확장 재작성. **헤딩 텍스트 보존**(앵커 무결성) | TASK §확정설계 1~6 / `SKILL.md:333,423` 역참조 |

#### 3.1.2 설계 — 재작성 절 콘텐츠 명세

> 아래는 재작성 절이 담아야 할 구조 명세다(EXECUTE가 이 명세대로 산문화). 각 하위 블록은 원문 마크다운으로 작성하되, 이 절 자체가 read-only에서 JSON answer 값으로 이스케이프되어 담기는 규칙 절임을 유지한다.

**(a) 절 도입 (공통 적용 명문 — R4)**
- 리드: query 답변(대화형 `//opbr ask` · 비대화형 `--read-only` **공통**)은 **레이아웃을 먼저 추론한 뒤 그 골격에 내용을 채운다**. 레이아웃은 **질의 유형(고정 택소노미)이 아니라 주입된 하위 문서의 실제 관계 구조에서 도출**(content-driven)한다. (TASK §배경분석 판정 오류 실증 인용)
- 공통 적용 문구 + read-only 출력 계약(§비대화형 read-only 모드)과의 관계 1문장: "본 절 규칙은 두 경로 공통이며, read-only는 이 골격을 JSON `answer` 값에 이스케이프해 담는다(§비대화형 read-only 모드 출력 계약)."

**(b) 6단계 내부 워크플로우 (R1)** — 표 형식, 각 단계에 "하는 일 + 출력 여부":

| # | 단계 | 하는 일 | 출력 |
|---|------|---------|------|
| 1 | 질의 분해 | 하위 주제 수 식별(단일/복합). 고정 질의유형 택소노미 폐기 | 비출력(내부) |
| 2 | 지식 수집 | brain-tool search → score 상위 선별 Read 주입(내용만 확보) | 비출력(내부) |
| 3 | 구조 분석 | 주입 내용의 관계를 **문서 근거로** 발견(여정/병렬/계층/조건). 관측 축 값 채움 | 비출력(내부) |
| 4 | 레이아웃 설계 | 관측 축 → 후보 매핑 규칙으로 골격 선택(표면 추측 금지, content-driven) | 비출력(내부) |
| 5 | 내용 합성 | 확정 골격에 근거·인용 채움 | 출력 |
| 6 | 자기검증 | 인용 정합·구조 준수·(read-only) JSON 이스케이프 확인 후 출력 | 출력 |

**(c) 관측 축 6종 (R2)** — 표: 축 | 신호(무엇을 보는가) | 매핑 후보:

| 관측 축 | 신호 | → 후보 |
|---------|------|--------|
| 여정/라이프사이클 | 참여·상태 전이 등 시간축 서사 | Flow/단계 |
| 순서성 | 선후·의존 순서 | Flow/단계 |
| 값 보유 | 항목마다 대응 값/속성 다수 | 표(GFM) |
| 병렬성 | 대등·비종속 항목 다수 | 그룹핑(헤딩+불릿) |
| 주제 수 | 독립 하위 주제 2개↑ | 복합(섹션 헤딩 분할) |
| 분량 | 답변 총량 적음 | Flat(과잉 헤딩 억제) |

**(d) 후보 레이아웃 5종 (R2)** — 정의 + 언제:
- `Flat` — 리드 문단(+`**볼드**`), 헤딩 없음. 분량 적고 단일 주제.
- `그룹핑(헤딩+불릿)` — `## 섹션` + `-` 불릿. 대등 병렬 항목.
- `Flow/단계(번호)` — `## 섹션` + `1.` 번호. 여정/순서.
- `표(GFM)` — 마크다운 표. 값 보유(항목×속성).
- `복합(섹션 조합)` — 위 후보를 `## 섹션`으로 조합. 주제 수 2개↑.

**(e) 판정 규칙 (R2)**:
- 1차: **관측 축 → 후보 매핑 규칙** 적용(축이 가리키는 후보 채택).
- 2차: **여러 후보가 동점일 때만** tie-break — 기준은 **더 단순한 쪽**(과잉 구조 억제). 전면 가중합 스코어링 미채택(self-scoring 편향·무게 사유).
- 축→후보 충돌 예: 값 보유(→표) + 여정(→Flow) 동시 → 지배 축(서사 축 우선/문서 근거) 선택, 그래도 동점이면 단순한 쪽.

**(f) 불변 가드 3종 (R3)**:
- **G1 비출력 내부 사고** — 1~4단계는 답변에 노출하지 않는다. 최종 출력은 답변(또는 read-only JSON 펜스 하나)만. 레이아웃 개요·단계 로그를 출력 금지.
- **G2 호출 1회 유지** — 단계가 늘어도 claude subprocess 호출은 **1회**. 단계=별도 호출이 아니라 단일 세션 내부 사고. 콜드 ~56s latency 배증 금지.
- **G3 read-only JSON 이스케이프** — read-only는 최종 출력이 JSON 코드펜스 하나. 펜스 밖 raw 마크다운 금지(citations 유실 방지). §비대화형 read-only 모드 [MUST] JSON 이스케이프 계약 유지.

**(g) 두 예시 (R5)** — 축 값 → 선택 레이아웃 도출을 서술:
- **예1: "방문형 캠페인 정책 설명" → Flow/단계.** 표면상 "정책=표"로 보이나(오류), 주입된 캠페인 문서는 **참여 여정(라이프사이클)** 정책이 시간축으로 드러남 → 여정/순서 축 지배 → Flow 채택. (TASK §배경분석 판정 오류 실증 인용)

## 설계 피드백 (임의 변경 금지 — 기록만)

> 확정 설계는 그대로 준수했다. 아래는 EXECUTE/CLOSE 판단용 관찰 사항이며 임의 반영하지 않았다.

1. **frontmatter version 부채**: `SKILL.md:12` `version: "1.5"`가 이미 changelog(v1.6·v1.7)와 불일치. TASK 요구는 "변경이력 v1.8 행 추가"만 명시하나, 정합성 위해 frontmatter도 `"1.8"`로 동반 갱신하도록 F-002 Step 2에 포함했다(설계 변경 아님 — 컨벤션 정합 보정). 소유자가 원치 않으면 version 갱신만 제외 가능.
2. **적응형 규칙과 6단계의 경계**: v1.7의 "내용 성격별 깊이" 규칙 테이블은 6단계 중 4단계(레이아웃 설계)의 "후보"로 흡수된다. 재작성 시 v1.7 테이블을 삭제·대체하되, 기존 규칙(리드 문단·인라인 코드 병기·과한 헤딩 금지)은 축/후보 안에 보존되어야 한다(H-3). 이 흡수 관계가 애매하면 EXECUTE에서 명시적 "구 규칙 → 신 축 매핑" 각주를 넣는 것을 권고.
3. **검증 한계 명시 필요**: content-driven 판정의 "정확성"은 advisory LLM 행동이라 brain-tool이 강제 못 한다. TEST-SCENARIO는 문서 구조 검증(L1)을 주 계층으로, read-only 스모크(L2)는 JSON 계약 비파손 관측에 한정했다(레이아웃 품질의 정량 판정 아님).
