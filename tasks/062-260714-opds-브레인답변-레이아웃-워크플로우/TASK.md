# TASK: 브레인 답변 생성 내부 워크플로우 — content-driven 레이아웃 선택

> 작성일: 2026-07-14 | 작업 유형: 개선 | 적용 스킬: opds | 모드: agentic
> 입력: 사용자 요청 + 대화 합의
> 출력: TASK.md

## 작업 목표

`opal-brain` query 답변 생성을 **6단계 내부 워크플로우**(질의 분해 → 지식 수집 → 구조 분석 → 레이아웃 설계 → 내용 합성 → 자기검증)로 구조화하여, 주입된 하위 문서의 실제 관계 구조에서 레이아웃을 도출(content-driven)하도록 `opal-brain/SKILL.md §답변 구조`를 재작성한다.

## 배경

현행 `opal-brain/SKILL.md §답변 구조 — 적응형 마크다운 계층`(v1.7)은 "리드 문단 필수 + 내용 성격별 깊이(단순=볼드 / 나열=헤딩+불릿 / 그룹핑=번호 3단 / 비교=표)" **규칙 테이블만** 제공한다. 그러나 LLM이 답변을 작성하면서 구조를 **즉흥 선택**하므로, 동일 질의에도 레이아웃이 흔들리는 일관성 편차가 남는다. 소유자는 답변마다 "레이아웃을 먼저 추론한 뒤 그 구조에 내용을 채우는" 명시적 단계형 워크플로우를 요구했다.

## 배경 분석 (대화에서 도출)

- **현행 답변 구조 SSOT**: `opal/skills/opal-brain/SKILL.md` §답변 구조 (v1.7, 대화형 `ask`·비대화형 `--read-only` 공통).
- **read-only 경로**: `dashboard/backend/adapters/opbr_adapter.py` `prime_and_ask()` — `claude --model sonnet --effort medium -p '[ASSISTANT]\n//opbr query --read-only <질의>' --output-format json` 단일 subprocess. 콜드 ~56s 실측. 프롬프트는 `//opbr query --read-only`만 전달하므로 **답변 구조 규칙의 SSOT는 SKILL.md**이며 adapter는 얇은 프록시.
- **JSON 출력 계약**: read-only는 `[MUST] 펜스 밖 raw 마크다운 금지`(citations 유실 방지) 제약 보유. 레이아웃 사고를 노출하면 이 계약이 깨진다.
- **판정 오류 실증(대화 중)**: "방문형 캠페인 정책 설명"을 질의 표면만으로 "표"로 단정한 것은 오류였다 — 캠페인은 하위 문서 분석 시 참여 여정(라이프사이클)에 따른 정책 구조가 드러나므로 flow가 맞다. 즉 레이아웃은 질의 유형이 아니라 **주입된 실제 내용의 관계 구조**가 결정한다.

## 확정된 설계 방향 (대화에서 합의)

### 1. 6단계 내부 워크플로우 (단일 세션, claude 호출 1회 유지)

| # | 단계 | 하는 일 |
|---|------|---------|
| 1 | 질의 분해 | 하위 주제 수 식별 (단일/복합). 고정 질의 유형 택소노미는 폐기 |
| 2 | 지식 수집 | brain-tool search → score 상위 선별 Read 주입 (내용만 확보) |
| 3 | 구조 분석 | 주입 내용의 관계를 **문서 근거로** 발견(여정/병렬/계층/조건). 관측 축 값을 채움 |
| 4 | 레이아웃 설계 | 3단계 축 → 후보 매핑 규칙으로 최적 골격 선택 (표면 추측 금지, content-driven) |
| 5 | 내용 합성 | 확정 골격에 근거·인용 채움 |
| 6 | 자기검증 | 인용 정합·구조 준수·(read-only) JSON 이스케이프 확인 후 출력 |

### 2. 관측 축 6종 (레이아웃 신호)

여정/라이프사이클(→Flow) · 순서성(→Flow) · 값 보유(→표) · 병렬성(→그룹핑) · 주제 수(→섹션 헤딩 분할=복합) · 분량(→Flat/과잉 헤딩 억제).

### 3. 후보 레이아웃 5종

`Flat` · `그룹핑(헤딩+불릿)` · `Flow/단계(번호)` · `표(GFM)` · `복합(섹션 조합)`.

### 4. 판정 방식

**관측 축 → 후보 매핑 규칙**을 1차로 적용하고, **동점일 때만** 스코어로 tie-break한다. tie-break 기준은 **더 단순한 쪽**(과잉 구조 억제). 전면 가중합 스코어링은 self-scoring 편향·무게 때문에 채택하지 않는다.

### 5. 불변 가드 3종

- (G1) 1~4단계는 **비출력 내부 사고** — 최종 출력은 답변(또는 JSON 펜스 하나)만. 레이아웃 개요를 노출하지 않는다.
- (G2) 단계가 늘어도 **claude 호출은 1회 유지** — latency 방어(콜드 ~56s 배증 금지).
- (G3) read-only는 `[MUST] JSON 이스케이프` 계약 유지 — 펜스 밖 raw 마크다운 금지.

### 6. 반영 경계

- 반영 지점: `opal/skills/opal-brain/SKILL.md §답변 구조` **SSOT 한 곳**. 대화형 `ask`·비대화형 `--read-only` 공통 적용.
- `dashboard/backend/adapters/opbr_adapter.py`는 **무변경** — 답변 구조 SSOT가 SKILL.md이므로 프롬프트/코드 수정 불요(무변경임을 확인만 한다).

## 제약 조건

- **호출 1회 유지**: 워크플로우 단계 증가가 claude subprocess 호출 수 증가로 이어지면 안 된다 (콜드 ~56s latency 방어).
- **비출력 내부 사고**: 레이아웃 설계 과정을 답변에 노출 금지.
- **read-only JSON 이스케이프 계약 유지**: 최종 출력은 JSON 펜스 하나, 펜스 밖 raw 마크다운 금지.
- **배포 경계**: `~/.opal/` 직접 편집 금지. 프로젝트 소스(`opal/skills/opal-brain/SKILL.md`) 수정 후 install로 재배포.
- **문서 변경이력**: SKILL.md 수정 시 변경이력 표 행 추가 (일시 KST + 태스크 062).
