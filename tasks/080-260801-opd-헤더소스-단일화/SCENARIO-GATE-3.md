## 2. 판단축별 판정

### ① 목표 달성 — **2점** (iteration 2: 1점 → **회복**)

**핵심 질문: 문구만 바뀐 것인가, 검증 가능한 구조가 생긴 것인가.** 후자다.

**무대가 실제로 만들어졌다.** iteration 2의 감점 근거는 "형제 파일이 모드 판정 **이전에** `out_of_scope`로 탈락하므로 서로 다른 스코프의 파일이 같은 실행에서 동일 모드를 보는 장면이 발생하지 않는다"였다. 새 구조에서는 `svc/shared/` 한 디렉토리의 **4파일이 두 스코프에 나뉘어 모두 생존**하고 모드 판정 단계까지 도달한다. `VendorLegacy.java` 1건만 필터 탈락으로 상주해 **판정 이전 단계도 같은 트리에서 동시에 보인다**(PLAN `:1350`). 없던 장면이 생겼다.

**단언이 목표를 반증 가능한 형태로 고정하는가 — 그렇다.** 세 단언의 판별력을 개별로 확인했다.

| 단언 | 무엇을 반증하는가 | 판별력 |
|------|-----------------|--------|
| (e) / TS-072 — 두 스코프 4파일 동일 모드, 갈리는 파일 0건 | 스코프별 오버라이드가 재도입되면 두 스코프가 갈린다 | **있음** (단, 단독으로는 약함 — 오버라이드 미설정 상태에서는 자명하게 통과) |
| (f) / TS-073 — `target`·`scaffold`·`validate`·`scan` 4경로 모드 일치 | 경로별로 모드를 재계산하는 지점이 생기면 어긋난다 | **있음** — 4경로가 각각 다른 함수 계열을 탄다 |
| (g) / TS-074 — 전역값 **한 줄만** 뒤집으면 5경로(+hook) 동시 반전 | 어느 한 경로라도 값을 캐시하거나 독자 재계산하면 **뒤집히지 않는다** | **강함 — 이것이 목표의 정공법 반증 장치다** |

(g)가 핵심이다. "모드 결정권이 전역 키 **1곳에만** 있다"는 명제는 값을 바꿨을 때 전부가 따라오는지로만 반증 가능하며, TS-074가 정확히 그 형태다. iteration 1에서 내가 제기하고 iteration 2에서 재제기한 대조 케이스가 이번에 들어왔다.

**계층도 맞다.** S-19는 L2 · M1 · 실 CLI 5커맨드 연속 호출 · mock 0건 · 2회차 대조다. 갱신 목표의 두 절이 모두 운영 계층에서 직접 검증된다 — "조회(`scan`)·작성 판정(`target`/`scaffold`)·검증(`validate`) 전 경로 지배"는 (f)(g), "스코프 예외 없음 · 실행당 1값"은 (e)(g), "혼재 디렉토리 지원"은 (a)~(d). 앵커 2점("사용자·운영 계층에서 목표를 직접 검증")에 부합한다.

**1점이 아닌 이유**: iteration 2의 1점은 "부분 커버의 전체 참칭"이었다. 지금은 갱신 목표의 어느 절도 운영 계층 공백이 아니며, §4 매핑 표도 갱신 목표 기준으로 다시 쓰였다(`:490`). 참칭이 남아 있지 않다.

**감점하지 않았으나 기록하는 흠**: 시나리오 문서 안에 **구 픽스처 서술이 잔존**한다 — §2.1 픽스처 표(`:60`) "서비스 A 1개 + 서비스 B 3개", §2.2 S-6 행(`:76`)·S-19 행(`:89`) "형제 3파일", §3 S-6 조건(`:318`) "include 화이트리스트로 A만 지정", S-19 기대결과 (b)(`:424`) "형제 3파일이 들어가지 않는다". 확정 구조에서 필터 탈락 파일은 `VendorLegacy.java` **1건**이다. S-19 본문 조건(`:423`)은 새 구조를 정확히 서술하므로 목표 검증 자체는 성립하지만, 같은 문서 안에서 같은 픽스처를 두 구조로 서술하고 있다(§3 gap-1).

**TS-070의 "판정 vs 참조" 구분이 실행 가능한가 — 대체로 가능하나 회피 여지가 있다.**

구분 표(`:532-538`)는 금지 패턴을 `config\.headerSource` / `opts\.headerSource`로, 허용을 `ctx\.headerSource` 읽기 전용으로 **정규식 수준까지 특정**했고 근거("원천 입력 해석" vs "확정값 읽기")도 명시했다. 실행 단계에서 해석이 갈릴 모호한 규칙은 아니다. 다만 두 가지 여지가 남는다 — (a) 구조분해(`const { headerSource } = config`)나 별칭(`const c = config; c.headerSource`)은 두 패턴 어디에도 걸리지 않아 **봉인을 우회한다**, (b) "함수 본문 **밖**"을 grep으로 어떻게 경계 짓는지가 규정되지 않았다(TS-013도 동일 형태이므로 선례를 따를 수는 있다). 봉인 부재가 아니라 봉인 정밀도의 문제이므로 감점 사유로 보지 않았다(§3 gap-4).

**2점을 준 이유**: 실제로 잔존할 자산이 있는 두 구형(`auto`·`readonly`)이 판별력 있는 방향까지 갖춰 각각 4중·5중으로 검증되고, 잔존 자산이 0건인 세 번째 구형(미래 재도입 위험)은 두 파일 대칭 부정 단언 + 판정 지점 grep + 산출물 검사로 4중 봉인됐다. iteration 2에서 열려 있던 두 구멍이 모두 닫혔고 후퇴는 없다.

**감점하지 않았으나 기록하는 흠**: PLAN §3.4.2의 안내 스텁(`:961`, `:969`)이 `deprecationOnce(메시지)` 형태로, §3.2.2가 신설한 `deprecationOnce(key, message)` 계약 및 3키 표(`index_scope_readonly` / `index_scope_header_source`)와 어긋난다. 이번 보정에서 §3.2.2에 키 계약을 추가하면서 §3.4.2의 기존 스텁을 함께 갱신하지 않은 결과다(§3 gap-3).

## 3. gaps — 전량 비차단 (verdict pass, EXECUTE 진입 전 흡수 권고)

**gap-1 — 시나리오 문서 안에 구 픽스처 서술이 잔존한다 [①축 파급, 우선 처리 권고]**
`TEST-SCENARIO.md` §2.1(`:60`)·§2.2 S-6(`:76`)·S-19(`:89`)·§3 S-6 조건(`:318`)·S-19 기대결과 (b)(`:424`)가 여전히 "서비스 A 1개 + 서비스 B 3개" / "형제 3파일" / "include 화이트리스트로 A만 지정"으로 **iteration 2 이전 구조**를 서술한다. 확정 구조는 4파일 생존 + `VendorLegacy.java` 1건 탈락이다. S-19 본문 조건(`:423`)과 PLAN §3.7.2·Step 1 완료 기준은 새 구조로 정확하므로 구현 지시 자체는 모호하지 않지만, **RED 작성자가 시나리오 문서의 §2.1 픽스처 표를 보고 트리를 만들면 iteration 2의 구조가 되살아나 ①축 회복이 조용히 무효화된다.** 이번 반복의 성과를 지키는 데 직접 걸린 항목이다.
**필요한 것**: 위 5개소를 확정 구조(4생존 / 1탈락, `order-svc`·`ship-svc`·`VendorLegacy.java`)로 통일.

**gap-2 — `mixed-scope-ambiguous` 트리가 시나리오 문서에 등재되지 않았다 [⑥축]**
PLAN이 신설한 `fixtures/mixed-scope-ambiguous/`가 `TEST-SCENARIO.md`에 **0회** 등장한다. §2.1 사전 조건 데이터 표에 행이 없고(PM Gate 체크는 "10행 전량 채워짐"으로 표기), S-5 조건(`:149`)·§2.2 S-5 행(`:75`)은 `mixed-scope`에서 양쪽 include가 동시 매칭되는 것으로 서술하는데 확정 구조에서는 그 조건이 성립하지 않는다. 부정 시나리오가 사라진 것은 아니지만 **무대의 주소가 두 문서에서 다르다.**
**필요한 것**: §2.1에 트리 1행 추가 + S-5 조건에서 `scope_ambiguous` 케이스의 트리를 `mixed-scope-ambiguous`로 명시.

**gap-3 — `deprecationOnce` 키 계약이 PLAN 내부에서 어긋난다 [⑤축]**
§3.2.2가 `deprecationOnce(key, message)` + 3키 독립 표(`index_scope_readonly` / `index_scope_header_source` / `config_scope_header_source`)를 신설했으나(`:726-735`), §3.4.2의 기존 스텁 2곳(`:961` `readonly`, `:969` index 측 `headerSource`)은 **키 인자 없이 메시지만 전달**한다. `:580`의 config 측만 새 계약을 따른다. 그대로 구현되면 3키 중 2키가 성립하지 않고 안내 문구가 깨질 수 있다 — TS-005/TS-031이 "안내 1줄"을 단언하므로 RED에서 걸리긴 하나, 봉인 장치의 명세가 스스로 모순인 채로 EXECUTE에 들어간다.
**필요한 것**: §3.4.2 스텁 2곳에 `'index_scope_readonly'` / `'index_scope_header_source'` 키 인자 추가.

**gap-4 — TS-070 grep 봉인이 표현 형태에 묶여 있다 [⑤축, 정밀도]**
금지 패턴이 `config\.headerSource` / `opts\.headerSource` 리터럴이므로 구조분해(`const { headerSource } = config`)나 별칭 경유 재판정은 **검출되지 않는다**. 또 "`resolveHeaderSource` 함수 본문 밖"의 경계를 grep으로 어떻게 정하는지가 미규정이다(TS-013 선례를 따를 수는 있다). 봉인의 존재가 아니라 우회 가능성의 문제다.
**필요한 것**: 금지 패턴에 구조분해·별칭 형태를 1행 추가하거나, 함수 범위 판정 방식(예: 함수 시작~끝 라인 범위 산출 후 범위 밖 매칭 카운트)을 TS-070에 1줄 명시.

**gap-5 — `mixed-scope` 매니페스트 `files` 내용이 미명세라 3역할이 충돌한다 [⑥축]**
같은 트리·같은 매니페스트에 대해 S-19 (d)는 `validate ok: true`를, TS-015는 in-scope 파일 1건이 매니페스트에 없을 것을, TS-014는 out-of-scope 파일 미등재가 집계되지 않을 것을 요구한다. PLAN §3.7.2 구조도는 스코프 정의만 기술하고 `files` 키를 지정하지 않았다. 또한 기준 모드가 `inline`인 트리에서 매니페스트 무결성 검출기(TS-014/015)를 돌리려면 `manifest` 오버레이 또는 `scaffold` 선행이 전제되어야 하는데 그 순서가 명시되지 않았다.
**필요한 것**: TS-014/TS-015가 사용하는 트리 상태(오버레이 여부·`scaffold` 선행 여부·`files` 초기 내용)를 PLAN §3.7.2 또는 Step 5 작업 내용에 1~2줄로 확정.

**gap-6 — S-19 실행 순서가 PLAN과 반대다 [비차단, 표기]**
`TEST-SCENARIO.md:423`은 (Ⅰ) 전역 `manifest` → (Ⅱ) `inline` 순으로, PLAN TS-072/073은 전역 `inline` 기준·TS-074가 `inline` → `manifest`로 기술한다. 픽스처 기준값도 `inline`이다(`:1329`). 단언 성립에는 영향이 없으나 두 문서의 회차 번호가 반대라 RED 작성 시 혼선 소지가 있다.
