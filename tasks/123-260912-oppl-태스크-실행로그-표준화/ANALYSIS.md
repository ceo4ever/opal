## 3. 확정된 제약 — 설계가 이미 정한 것

구현이 새로 정할 게 없다. 계약이 이미 확정했다.

| 항목 | 계약 위치 |
|---|---|
| 마스킹은 **모든 writer가 통과하는 공통 경로 한 곳** | TRD D-9 |
| `redact()`는 **멱등** — 두 번 통과해도 결과 동일 | `run_log_core.py:248` 계약 주석 |
| 조각 상한 4 MiB, **닫힌 조각 불변** | CONTRACT §8.2 계열 |
| 경계 전환은 **같은 락 안에서** 검사·생성 → 정확히 한 프로세스만 실행 | TRD §동시성, D-4 |
| 시간대는 설정 2층 머지 하위 키 + **캐시 토큰 서명에 포함** | CONTRACT §3.5·§2.8 (PM 판정 M-1) |
| 시간대 해석은 **통계 계층 앞에서 종료** — `stats.py` 입력 형태 불변 | CONTRACT §2.8.1 B-1~B-4 (PM 판정 N-2) |
| 실행시간은 **단조 시계 구간 합**, 시각 차분 금지 | TRD §시간 모델 |

**특히 §2.8.1이 W-3의 핵심 제약이다.** `stats.py`의 공개 함수 6종은 `tuple[int,int]|None`을 받고, 이 시그니처가 바뀌면 C-2가 동결한 Console 테스트가 깨진다. 3필드 구조는 설정·라우터 계층 안에서만 흐른다.

## 4. 색인을 제외하는 근거 — 실측

계약(TRD D-3)은 색인을 성능 최적화로 도입하고 되돌림 비용을 **"낮음"**으로 평가했다. 실제로 얼마나 느린지 측정했다.

| 누적 사건 수 | append 평균 |
|---|---|
| 1~200 | 0.89 ms |
| 201~500 | 2.34 ms |
| 501~900 | 4.43 ms |
| 901~1,300 | **6.46 ms** |

선형 증가가 **관측된다**(7배). 그러나 1,300건 누적 총 5.2초다. 워커 디스패치 하나가 수십 분인 환경에서 **병목이 아니다.**

색인은 "느려서 불편하다"가 관측된 뒤 넣는 것이 맞다. 지금은 그 관측이 없다. **AC-9를 후속 이관하고, 위 실측값을 그 판단의 입력으로 남긴다.**

> 부수 관찰: 스캔이 필요한 이유는 **순번·멱등을 쓰기 시점에 판정하기 때문**이다. 읽기 시점 판정으로 바꾸면 스캔 자체가 사라진다. 다만 해당 코드는 이미 구현·검증 완료이므로 지금 되돌리는 것은 절약이 아니라 재작성이다. 설계 재검토 항목으로만 기록한다.

## 5. main 병합으로 달라진 전제

작업 중 main에 태스크 122·131이 머지되어 병합했다. 충돌 4건은 전부 양쪽 가산이라 병존 해소했다.

| 유입 | 영향 |
|---|---|
| `--actor pm` (122) | 실행 주체 축 신설. 이 태스크의 ANALYSIS가 그 경로로 수행됨 |
| `run-start`·`run_id` (131) | **같은 상태 파일에 `run` 개념 2종 공존** — 최상위 `run_id`(131)와 `run_log.active_run_id`(123). JSON 경로가 달라 충돌 없음. `@header`에 별개 축임을 명시 |
| OPPL 실행 상한 도구 집행 (131) | 제가 하네스 결함으로 보고한 "재시도 상한 미정의"가 이미 처리됨 |

**`run` 2종 공존은 통합 대상이 아니라 후속 검토 항목이다.** 양쪽 계약을 함께 봐야 하므로 이 태스크가 임의로 정하지 않는다.
