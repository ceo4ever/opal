# TRD: 태스크 실행 로그 표준화

> 1차 입력 SSOT: `docs/proposals/opal-task-run-log.md`
> 요구·제약·수용 기준은 `TASK.md`, 무엇을 왜 만드는가는 `PRD.md`가 소유한다. 이 문서는 **어떻게 만들 것인가**만 소유한다.
> 사건 스키마 필드 정의, CLI 시그니처 원문, 표면 인벤토리는 CONTRACT가 소유한다. 이 문서는 그 대상을 가리키기만 한다.

## 구성요소와 책임 경계

### 신설: 기록 코어 (`opal/tools/run-log-*`의 코어 모듈)

- **소유**: 사건 스키마 검증, 줄 단위 append와 fsync, 조각 경계 전환과 닫힌 조각 불변성, run 전역 순번·주체별 순번 발급, 요청 식별자 멱등 판정, 출처(provenance) 검증, 워커 쓰기 권한 범위·만료·폐기 검증, 가져오기 멱등성, 디스크 기록 전 마스킹, run 단위 집계.
- **금지**: 상태 파일을 읽지 않는다. 계약이 활성인지, 지금 어느 실행이 현재 실행인지, 재실행이 허용되는지 판정하지 않는다(D-5·제안서 §6.4). 채널 분기를 갖지 않는다(D-6).
- **인터페이스 성격**: 락을 이미 쥔 호출자를 위해 "락 보유" 모드를 받는다. 락을 누가 쥐었는지는 호출자가 선언하고 코어는 재획득하지 않는다(§6.5).

### 신설: 기록 CLI (`run-log-tool`)

- **소유**: 외부 호출자(워커, 변환기, PM 수동 진단)를 위한 명령 표면과 락 자체 획득, 표준 응답 봉투.
- **금지**: 계약 활성/비활성 판정, 현재 실행 선택, 완료 게이트 최종 판정. 검증 명령은 기록 조각과 명시 인자만 읽는다.
- **관례**: 기존 도구의 확립된 CLI 관례를 따른다 — `opal/tools/backlog-tool/backlog_tool.py`의 @header는 "state-tool 패턴(ok/err 헬퍼, 시점 처리, 오류 코드 SSOT)을 복제한다"고 선언한다. 신설 도구는 새 관례를 만들지 않고 이 선례를 따른다. 원자적 쓰기와 파일 락은 `opal/tools/memory-tool/memory_tool.py`의 락·원자 쓰기 선례(같은 파일 359·386행)를 참조한다.
- **명령 목록과 인자 시그니처 원문은 CONTRACT가 소유한다**(제안서 §9). 여기서 복제하지 않는다.

### 확장: 상태 도구 (`opal/tools/state-tool/state_tool.py`)

- **소유**: 로그 계약 활성화 여부와 운영 모드, 현재 실행 식별자, 미전송 사건 보관함, 초기화·복구·재실행 판정, 워커 완료 게이트의 최종 조합 판정, 워커 시간의 상태 투영, 배타 락 획득.
- **금지**: 사건을 직접 파일에 쓰지 않는다. 기록 조각의 순번을 스스로 발급하지 않는다. 현재 상태에서 과거 사건을 합성하지 않는다(제안서 §6.2 6항).
- **경계 근거**: 제안서 §6.4 "legacy/active 판정과 완료 게이트의 조합은 상위 state-tool만 소유한다".

### 신설: 채널별 변환 계층 (adapter)

- **소유**: 채널 원본(프로세스 시작·중간 메시지·스트림 사건·도구 결과·프로세스 종료·오류 봉투)을 표준 사건으로 바꾸는 변환, 원본의 식별자·해시·관측 시각 추출, 단조 시계 구간 측정, 자기 채널의 기계 self-test.
- **금지**: 자기 채널의 완료 등급을 스스로 선언하지 않는다(등급 배정값은 Phase 0 산출 데이터가 소유, D-8). 상태 전이를 수행하지 않는다. 마스킹을 자체 구현하지 않고 공통 경로를 호출한다(D-9).
- **채널 축의 구조적 차이**: 두 축은 관측 가능한 것이 다르다. PM이 외부 에이전트 도구를 호출하는 축과, Project Loop 내부의 헤드리스 CLI 축(`opal-agent`)은 별도 변환기·별도 판정이다. 내부 축은 결과 수거가 파일 분리 캡처로 결정론화돼 있어 프로세스 종료와 세션 식별자로 완료·재개를 판별하고, 외부 축은 도구 호출 응답 경계가 관측 단위다(프로젝트 지식 `.opal/brain/pages/concept/oppl-internal-channel-opal-agent.md`). 한쪽 결과를 다른 쪽에 전용하지 않는다(제안서 §10 Phase 0).

### 읽기 계층: Console (`dashboard/backend/`)

- **소유**: 기존 상태 기반 통계 화면과 조용시간 보정.
- **금지**: 기록 조각을 직접 읽지 않는다(Phase 2 범위). 상태 도구를 쓰기 목적으로 호출하지 않는다 — `dashboard/backend/adapters/state_adapter.py`의 @header가 "`state-tool show --format json` read-only 호출 래퍼. 쓰기 커맨드(init/advance/mark 등) 금지"로 이미 경계를 고정하고 있으며, 이 태스크는 그 경계를 그대로 유지한다.
- **관측 3층 관점**: 기록 조각은 데이터 규약(1층)이고 Console과 실행 모니터는 렌더러·발동층(2·3층)이다. 하위 층을 바꾸지 않고 상위 층만 교체할 수 있으므로 분석 화면을 Phase 2로 미뤄도 1층 설계가 불완전해지지 않는다(프로젝트 지식 `.opal/brain/pages/concept/observability-3layer-protocol-renderer-trigger-separation.md`).

### 역할 축소: 사람이 읽는 저널 (`STATE.md`)

기계 상태 SSOT는 상태 파일 하나이고 저널은 그 파생물이다. 파생 가능한 표시를 저널에 다시 만들면 "이중 표현"이 이름만 바꿔 재발한다(프로젝트 지식 `.opal/brain/pages/concept/state-md-journal-redefinition.md`). 따라서 우회 결정 같은 사건도 저널에는 **사건 식별자 포인터와 복구 필요 상태만** 남기고 원문을 복제하지 않는다(제안서 §6.2).

### 의존 방향

```text
             [Console 읽기 계층]
                     │ read-only
                     ▼
   [채널 변환기]──▶ [기록 CLI] ──▶ [기록 코어] ◀── [상태 도구]
        ▲                              ▲                │
        │                              │  (인프로세스,   │ 소유
    채널 원본                      락 보유 호출)         ▼
 (프로세스·메시지·                                 [상태 원천]
  스트림·종료 봉투)                            (계약·현재 실행·보관함)
```

- 화살표는 "호출한다"이며 역방향 호출은 없다. 기록 코어에서 상태 원천으로 향하는 화살표가 없다는 것이 D-5의 전부다.
- 변환기는 기록 CLI를 통해서만 기록에 접근한다. 변환기가 기록 코어를 직접 링크하지 않아야 채널 추가가 도구 경계를 넘지 않는다.

## 데이터 흐름

### (a) 태스크 초기화

1. 상태 도구가 배타 락을 획득한다.
2. 활성 모드를 요청받았으면 Phase 0 산출 배정 파일에서 해당 채널 항목을 찾아 변환기·receipt 해시를 검증하고 계약 블록에 고정한다.
3. 첫 원자 쓰기: 새 스키마의 상태 파일을 `status=pending`으로 쓰면서 실행 시작 사건을 compact 형태로 보관함에 함께 적재한다.
4. 실행 디렉터리와 첫 기록 조각을 만들고, 같은 식별자로 실행 시작 사건을 멱등 append한 뒤 fsync한다.
5. 두 번째 원자 쓰기: 보관함에서 해당 사건을 제거하고 `status=active`로 전환한다.
6. 락을 해제한다.

**실패 분기**
- 2에서 배정 항목이 없거나 해시가 불일치: 활성 초기화를 거부한다. 그림자 모드로는 진행 가능하다(제안서 §4.2.1·§6.1).
- 3 이후 4 이전 중단: 계약은 있고 기록 조각은 없는 상태가 남는다. 보관함에 실행 시작 사건이 있으므로 **고장이 아니라 복구 가능 초기화**로 판정하고, 복구가 디렉터리와 첫 조각을 만든 뒤 재전송한다(§6.1·AC-3).
- 4 성공 후 5 이전 중단: 같은 식별자의 멱등 append가 중복을 만들지 않으므로 복구가 안전하게 보관함만 비운다(§6.2 7항).

### (b) 워커 디스패치 ~ 완료

1. PM(또는 변환기)이 워커 실행 식별자를 발급하고, 상태 도구가 1회 디스패치 범위의 쓰기 권한을 발급한다. 이때 권한 발급 사건과 런타임 투영만 만들고 **워커 시작 사건은 만들지 않는다**(§6.4 말미).
2. 변환기가 프로세스 시작 또는 핸드셰이크를 실제로 관측한 시점에 워커 시작 사건을 만든다. 동시에 단조 시계 구간 측정을 시작한다.
3. 실행 중 변환기가 수신한 중간 메시지·스트림 사건·도구 결과를 작업 경계 단위의 진행 사건으로 변환해 append한다. 워커가 자발적으로 직접 기록한 진행 사건도 보조 궤적으로 보존하되 완료 게이트에 기여하지 않는다(§4.3).
4. 프로세스 종료 또는 오류 봉투 관측 시 변환기가 종료 사건을 만든다. 종료 사건은 측정된 구간 목록과 그 합을 함께 싣는다.
5. 상태 도구의 완료 표시 명령이 채널 등급·출처·구간 증거를 함께 검사해 완료를 인정하거나 거부한다.

**실패 분기**
- 3의 append 실패: 종료 검증이 성립하지 않아 완료가 차단된다(`run_log_write_failed`, §6.2 말미). 상태 전이는 보관함 경로가 아니므로 여기서는 재시도 책임이 호출자에게 있다.
- 중간 사건 없이 종료만 관측된 경우: 강한 궤적 등급에서는 완료가 차단된다. 예외는 작업 활동 전 즉시 실패·차단뿐이며, 이때도 종료 사건의 기록 주체가 변환기이고 출처가 프로세스 종료 또는 오류 봉투이며 종료 코드나 오류 봉투 해시가 있어야 한다(§4.3 말미).
- 응답 유실 후 재시도: 같은 요청 식별자·같은 payload는 기존 사건을 그대로 반환하고, 같은 식별자에 다른 payload는 충돌로 거부한다(§5.1 말미). 이로써 종료 사건이 둘로 늘지 않는다(R-3·R-19).
- 프로세스 경계를 넘는 재개: 실행 식별자와 워커 실행 식별자를 유지하고, 변환기가 각 프로세스 구간을 별도로 측정해 종료 사건에서 합산한다(§5.2).

### (c) 상태 전이

1. 상태 도구가 락을 획득한다.
2. 전이 결과와 compact 상태 변경 사건을 함께 구성하고 사건 식별자·UTC 시각을 **미리 확정**한다.
3. 첫 원자 쓰기: 상태 변경과 보관함 적재를 한 번에 커밋한다.
4. 인프로세스로 기록 코어를 호출해 같은 사건 식별자로 멱등 append하고 fsync한다.
5. 두 번째 원자 쓰기: 보관함에서 제거한다.
6. 락을 해제한다.

**실패 분기**
- 4 실패 또는 프로세스 중단: 보관함에 사건이 남고 계약 상태가 pending이 된다. 이 상태에서는 일반 진행을 한도 내에서 허용하되 워커 완료 표시와 종료 전이를 차단한다(`run_log_pending`, §6.3).
- 보관함 일반 사건이 한도(`전체 한도 − 우회 사건 수`)에 도달: 추가 전이를 차단하고 복구 또는 **사용자 명시 승인·사유가 붙은 1회 우회 묶음**만 허용한다(§6.2 8항).
- 게이트 요청·해결: 같은 게이트 식별자의 요청·해결 두 사건을 상태 도구가 보관함을 거쳐 중개하며, 요청 없는 해결과 중복 해결은 거부한다(§4.4).
- 명시적 재실행: 이전 실행의 종료 사건과 새 실행의 시작 사건을 한 번의 상태 원자 쓰기로 함께 커밋하고 각자의 실행 식별자로 재전송한다. 호출 전에 이미 존재하던 미해소 보관함이 있으면 거부한다(§9).

### (d) 기록 실패 ~ 복구

1. 진단이 보관함 비어 있지 않음을 확인하고 계약 상태를 pending으로 읽는다.
2. 복구 명령이 락을 획득하고, 보관함에 있는 **완전한 사건만** 대상으로 한다.
3. 필요하면 실행 디렉터리와 첫 조각을 먼저 만든다((a)의 중단 복구 경로).
4. 각 사건을 원래 식별자로 멱등 append한다.
5. 전건 반영 뒤 보관함을 비우고 계약 상태를 활성으로 되돌린다.

**실패 분기**
- 자동 확정이 불가능한 불일치: `run_log_inconsistent`로 진단하고 사용자 우회 또는 수동 복구를 요구한다(§6.3).
- 복구조차 불가능한 지속 장애: 사용자 명시 승인·사유가 있는 우회만 허용한다. 우회는 승인된 상태 변경, 결정 성격의 진행 사건, 강제 상태 변경 사건을 같은 원자 쓰기로 커밋하고 두 사건을 일반 한도와 무관하게 정확히 한 번만 적재한다. 이후 계약 상태는 `overridden`이며 그 전이 1건 뒤에는 복구 외 추가 전이를 허용하지 않는다(§6.2).
- **금지된 복구**: 현재 행의 시각이나 표준 출력에서 과거 사건을 합성하지 않는다(§6.2 6항). 복구는 이미 보관된 사건을 이관할 뿐이며, 없는 사건을 만들어내는 순간 이 설계가 주장하는 증거성이 사라진다.

### (e) 원본 단방향 가져오기

1. 가져오기 명령이 락을 획득하고 원본 위치를 읽는다.
2. 원본 항목마다 멱등 키를 만든다 — 원본 식별자가 있으면 출처 식별자와 상위 사건 식별자의 조합, 없으면 출처 식별자·위치자·해시의 조합(§3.4).
3. 이미 반영된 키는 건너뛰고, 새 항목만 표준 사건으로 변환해 append한다. 변환 전 공통 마스킹 경로를 통과한다.
4. 변환된 사건의 기록 주체는 도구이며 완료 게이트 판정에서 항상 제외된다(§4.3·§5.1).

**실패 분기**
- 역방향 변환 요청: 금지한다(§3.4). 표준 기록에서 원본을 다시 만들지 않는다.
- 원본이 단일 형식이 아님: Project Loop 실행 디렉터리는 비동기 축의 사건 로그와 루프 액션 주체가 직접 쓰는 운행 일지의 이원 구조이고, 동기 축은 단일 결과 파일을 유지한다(프로젝트 지식 `.opal/brain/pages/concept/oppl-run-record-journal-dual-observability.md`). 따라서 가져오기는 하나의 파서가 아니라 원본 형식별 변환 규칙 집합을 갖되, **출력은 하나의 표준 사건 형식**으로 수렴한다(D-6).
- 원본과 표준 사건이 함께 있는 기간: 집계 주체는 표준 사건만 센다(§3.4).

## 동시성과 실패 모델

### 락 획득 구간

- 상태 도구의 변경 명령은 **상태+보관함 원자 쓰기 이전부터, 조각 선택·순번 발급·append·fsync·보관함 제거까지** 락을 연속 보유한다(§6.5). 락을 중간에 놓지 않는 것이 D-2 보관함의 pending 창을 "프로세스가 죽은 경우"로만 한정한다.
- 외부 기록 CLI는 스스로 락을 획득한다. 이미 락을 쥔 상태 도구는 같은 프로세스의 기록 코어를 **락 보유 모드로** 호출해 재획득하지 않는다. 재획득을 시도하면 자기 자신과 교착한다.
- 별도의 상태 전용 락이나 조각별 락을 추가하지 않으므로 lock ordering 문제가 존재하지 않는다(D-4).

### 조각 경계 전환이 정확히 한 프로세스에서만 일어나는 이유

조각 상한 검사, 다음 번호 선택, 새 조각 파일 생성이 **모두 같은 락 안에서** 수행된다(§6.5). 경계 직전 여러 프로세스가 동시에 도착해도 락을 먼저 잡은 하나만 상한 초과를 관측해 새 번호를 만들고, 뒤따르는 프로세스는 락 획득 시점에 이미 전환된 상태를 보므로 다시 전환하지 않는다. 검사와 생성 사이에 락을 놓는 구간이 없다는 것이 단일성의 전부다.

수용 판정은 여러 프로세스를 경계 직전 배리어에 대기시켰다가 동시에 해제하고, 새 조각 1개·run 전역 순번 중복 0·누락 0·주체별 순번 단조성·JSON 줄 수·정상 완료 표시 오탐 0을 함께 본다(§6.5 말미, AC-8).

### 색인 부재·손상 시 재구축과 그 사이의 동작

런타임 색인은 파생물이므로(D-3) 부재·손상·불일치를 **정상 경로의 한 분기**로 다룬다.

1. 같은 락 안에서 모든 조각을 1회 스캔한다.
2. run 전역 순번과 주체별 순번의 최대값, 요청 식별자 집합, 권한 발급·폐기 사건을 전부 다시 읽는다.
3. 권한 목록은 발급·종료·실행 종료·폐기·만료를 함께 적용해 재구성하며, 만료·폐기된 권한의 재사용을 거부한다(§6.4 말미).
4. 재구축이 끝난 뒤에만 append를 진행한다.

**재구축 중에는 append와 워커 완료 표시를 fail-closed로 대기시킨다**(§5.3). 열어두면 재구축이 읽는 중에 새 줄이 붙어 순번 최대값이 어긋나고, 그 결과가 다시 색인에 고정된다. 대기는 D-4의 단일 락으로 자연히 얻어진다 — 재구축이 락을 쥐고 있는 동안 다른 호출은 락 대기열에 있다.

### 정상 호출의 일시적 미전송 상태를 다른 호출이 오탐하지 않는 이유

pending은 "보관함에 사건이 남아 있는 상태"이고, 정상 호출은 같은 락 구간 안에서 보관함을 즉시 비운다(§6.1 말미). 다른 프로세스의 완료 표시는 앞 호출이 append와 보관함 제거를 마치거나 실패 상태로 락을 놓을 때까지 **락에서 대기**하므로, 정상 호출의 중간 상태를 관측할 창 자체가 없다(§6.5). 따라서 관측 가능한 pending은 프로세스 중단이나 실제 기록 실패뿐이며, 이때의 차단은 오탐이 아니라 참이다(R-4).

### 실패 모드 요약

| 실패 | 관측 주체 | 즉시 동작 | 해소 경로 |
|---|---|---|---|
| 필수 워커 사건 append 실패 | 기록 코어 | 워커 완료 표시 차단 | 재시도 또는 종료 재관측 |
| 활성 계약인데 기록·필수 사건 부재 | 상태 도구 | 완료·종료 차단, **legacy 강등 없음** | 복구 가능 초기화면 복구, 아니면 수동 복구 |
| 보관함 미반영 | 상태 도구 | 한도 내 일반 진행 허용, 완료·종료 차단 | 복구 |
| 보관함 한도 도달 | 상태 도구 | 상태 전이 차단 | 복구 또는 1회 사용자 우회 묶음 |
| 자동 확정 불가 불일치 | 기록 CLI 검증 | 진단만 | 사용자 우회 또는 수동 복구 |

오류 코드 원문과 조건은 제안서 §6.3이 소유하며 CONTRACT가 확정한다.

## 시간 모델

### 두 시간계의 2계 해석

- **사건 시각은 UTC 밀리초**로만 저장한다. 로컬 시각 변환은 표시 계층의 책임이다(§5.2).
- **기존 상태 파일의 시간대 없는 시각**은 `Asia/Seoul`로 해석한 뒤 UTC로 바꾼다. 이 규칙은 **가져오기 전용**이며, 신규 사건의 시각을 상태 파일의 시각에서 역산하지 않는다(§5.2). 역산을 허용하면 상태 파일이 다시 사건 원천이 되어 D-1이 무의미해진다.
- 두 계의 정합은 날짜 경계 표본으로 판정한다(R-18·AC-20).

### 실행 시간을 시각 차분이 아니라 단조 시계 구간 합으로 재는 이유

시각 차분은 벽시계 조정(시간대 변경, NTP 보정, 서스펜드)에 오염되고 음수 구간까지 만들 수 있다. 워커 시간은 통계와 병목 판단의 입력이므로 **측정 가능한 경과**여야 한다. 따라서 변환기가 프로세스 시작부터 종료까지를 단조 시계로 측정하고, 강제 모드의 종료 사건은 변환기 단조 측정만 허용한다. 워커가 스스로 잰 값은 그림자 비교용이며 강제 모드의 시간 원천이 아니다(§5.2·§7).

### 프로세스 경계를 넘는 재개의 합산

같은 워커 실행이 프로세스를 새로 띄우면 단조 시계는 연속하지 않는다. 그래서 변환기가 **프로세스 구간마다 별도로 측정**하고, 종료 사건이 구간 목록을 싣되 각 구간은 자기 프로세스 출처 식별자를 갖는다. 종료 사건의 총합은 구간 합과 같아야 하고, 같은 프로세스 출처 식별자가 두 번 나오면 거부한다(§5.2). 이것이 재개를 중복 계산하지 않으면서도 합산 가능하게 만드는 유일한 구조다(AC-12).

어느 경로에서도 단조 구간을 확보할 수 없으면 값을 지어내지 않고 **미상 사유**를 기록한다.

### 상태 투영

워커 시간의 원천은 종료 사건 하나이고 상태 파일의 분 단위 값은 파생 투영이다. 변환은 `floor(밀리초 / 60000)`이며 1분 미만은 0이다. 완료 표시 명령이 종료 사건을 읽어 자동 기록하므로 사람이 값을 넣지 않는다(§7). 새 스키마 태스크에서 수동 값이 파생값과 다르면 거부하고, 같으면 수용하되 폐기 예정임을 알린다. 구버전 태스크는 현행 계약을 그대로 유지한다(§7 전환표, `TASK.md` C-3).

### 조용시간 설정의 시간대 도입과 기존 동작 보존

제안서 §5.2는 Console 조용시간 설정에 시간대 키를 추가하고, 미설정 시 기존 동작과 같은 `Asia/Seoul`을 쓰도록 요구한다. 이 도입은 이미 존재하는 설정 로딩 구조 위에서 이뤄져야 한다.

- 조용시간 설정은 전역 설정 위에 프로젝트 로컬 설정을 **하위 키 단위로 덮어쓰는 2층 머지**이고, 어느 층에도 없으면 기본값(활성·00:00~09:00)이다 (`dashboard/backend/config.py` @header, `load_quiet_hours` 정의는 같은 파일 160행). 새 시간대 키도 **같은 2층 머지의 하위 키**로 들어가야 한다. 별도 로딩 경로를 만들면 전역·로컬 우선순위가 키마다 달라진다.
- 기존 전역 설정 파일에 시간대 키가 없으면 **파일을 다시 쓰지 않고 폴백을 적용**한다(§5.2). 설치 시드 원본과 배포 스크립트의 시드 키 배선도 함께 검증한다. 이때 배포본을 직접 고치지 않고 프로젝트 소스를 고친 뒤 재배포한다(`.opal/AGENT.md` §금지사항 "`~/.opal/` 직접 편집 금지").
- **캐시 키 정합이 이 절의 핵심 위험이며, 처리 시점은 확정됐다.** 조용시간 값은 캐시 키 서명(`quiet_hours_token`, 같은 파일 196행)으로 쓰이며 현재 서명은 시작·끝 분만 담는다(같은 파일 204행). 시간대만 다르고 시작·끝이 같은 두 설정은 현재 구현에서 **같은 캐시 키를 공유**한다. 서명의 존재 이유가 "설정 변경 시 보정 전후 값이 같은 캐시 키를 공유하지 않게 한다"(같은 파일 @header)인데 시간대는 보정 결과를 바꾸는 설정이므로, 서명에서 빼면 시간대만 바꾼 설정이 낡은 캐시를 반환한다. 따라서 **설정 키 추가와 캐시 키 서명 포함을 Phase 1A에서 한 단위로 처리한다.** 겹침 계산의 실제 소비가 Phase 2인 것과 무관하다. 근거: PM 판정 M-1 / `CONTRACT.md` §3.5. 개정 후 입출력 형태는 `CONTRACT.md` §2.8이 소유한다.

## 보안과 보존

### 디스크 기록 전 마스킹의 위치

모든 변환기와 원본 writer는 **파일 쓰기 직전 공통 마스킹 경로**를 통과한다(D-9·§8.3). 위치가 writer별이 아니라 공통 경로인 이유는 판정 가능성이다 — 공통 경로가 하나면 "secret fixture가 디스크에 남는가"를 실제 파일로 판정할 수 있고, writer별이면 각 writer를 개별 검사해야 하며 새 writer는 검사에서 누락된다.

- 대상: 환경변수형 비밀값, bearer·token, API key, private key 블록. 프로젝트 보안 문서의 추가 패턴을 병합한다.
- 마스킹 불가로 판정된 원본은 **저장을 거부하고 메타데이터 사건만** 남긴다.
- Project Loop 원본 writer도 같은 경로를 통과하도록 바꾼다. 그 전에 생성된 구 원본은 추적 제외 상태를 유지하고, 표준 기록으로 가져올 때 다시 마스킹한다.
- 보안 판정은 "넣지 않는다"는 문구가 아니라 실제 fixture 비밀값이 디스크에 남는지로 한다(§8.3 말미, AC-13).

### 원본 수집 기본 비활성과 상한

- 표준 출력·오류 출력·프롬프트 원문은 **기본 수집하지 않는다**. 원본 디렉터리는 사용자가 명시적으로 활성화한 실행에서만 생긴다(§8.1, AC-14).
- 상한: 파일당 10 MiB, 실행당 100 MiB, 7일. 설정으로는 **더 작게만** 조정할 수 있다. 상한 초과 시 저장을 중단하고 제한 사실을 메타 사건으로만 남긴다(§8.3).
- 원본 파일 기본 권한은 소유자 읽기·쓰기 전용이다.

### 추적·비추적 경계

| 대상 | git 추적 | 근거 |
|---|---|---|
| 마스킹·검증을 통과한 기록 조각 | **추적** — 태스크 증거 | §8.1 |
| 원본 디렉터리(`tasks/**/run/raw/`) | 제외 | §8.1 |
| 런타임 디렉터리(`tasks/**/run/.runtime/`) | 제외 — 파생 색인·권한 검증자 | §8.1·D-3 |
| 태스크 락 파일(`.opal-task.lock`) | 제외 — 런타임 파일 | §8.1 |

현재 `.gitignore`에는 Project Loop 실행 디렉터리만 등재돼 있다(`.gitignore:38`). 위 세 항목은 신규 등재 대상이다.

### 보존 정책이 실측 없이 승인되지 않는다

표준 사건은 태스크 감사 증거이므로 개별 삭제·만료를 적용하지 않고 태스크와 같은 기간 보존한다(§8.2). 이 결정은 **전체 증거가 태스크 수에 비례해 증가한다는 비용을 의도적으로 수용**하는 것이다. 따라서 다음을 기술적 조건으로 건다.

- 고정 크기 조각 상한(4 MiB)은 **예상 사용량이 아니라 경계 전환 안전 상한**으로만 취급한다. 활성 파일의 변경 이력 크기와 손상 반경을 제한하는 것이 목적이다(§8.2).
- 그림자 기간에 태스크별·워커별 기록 바이트와 사건 수의 평균·상위 분위·최대, 기존 실행 일지 대비 증가율, 저장소 pack 증가량을 실측해 보고한다. **이 실측 없이 다음 단계 보존 정책을 승인하지 않는다**(§8.2 말미).
- 개정 기준일 비교 기준선은 태스크 전체 약 20 MiB, 실행 일지 112개 합계 약 1.02 MiB다. 이 값은 예상량이 아니라 증가율을 계산할 비교 기준이며 후속 측정에서 동일 범위를 유지한다(§8.2).
- 보존 비용을 수용할 수 없는 프로젝트는 도입 전에 전체 추적 정책을 별도 승인받는다(§8.2).

## 채널 등급 모델

### 등급 3종의 기술적 의미

등급은 "채널이 얼마나 성실한가"가 아니라 **변환기가 모델 지시 없이 무엇을 기계적으로 확보할 수 있는가**로 정해진다(§4.2·§10 Phase 0).

| 등급 | 관측 가능해야 하는 것 | 완료 게이트의 기계 강제 범위 |
|---|---|---|
| 강한 궤적 등급 | 시작 + **완료 알림보다 앞서 실제 수신된 별도 중간 사건**(메시지·스트림·도구 결과) + 종료 | 신뢰 가능한 시작 1건 + 중간 진행 사건 1건 이상 + 종료 정확히 1건 |
| 약한 종료 등급 | 시작 + 종료만 | 신뢰 가능한 시작 + 종료. 나머지는 기존 산출물 검사와 PM 게이트에 의존하며, 그 검사는 사유를 붙인 강제 우회가 가능하므로 **무조건적 기계 강제 범위는 시작·종료까지**다 |
| 관측 불가 등급 | 기계 증거 없음 | 완료 차단에 관여하지 않음. 그림자 전용 |

두 강제 가능 등급의 공통 조건은 같은 워커 실행의 시작 1건, 종료 정확히 1건, 종료 결과 또는 원인, 변환기 단조 측정 시간이다(§4.2).

중간 사건이 완료 게이트에 기여하려면 **완료 알림을 쪼개 만든 것이 아니어야 한다**. 중간 사건과 종료 사건의 출처 식별자가 서로 달라야 하고, 출처 해시도 서로 달라야 하며, 중간 사건의 관측 시각과 사건 시각이 종료보다 앞서야 한다. 하나의 완료 메시지를 위치자·오프셋·조각으로 분할해 둘을 만들 수 없다(§4.3). 이 불변식이 없으면 강한 궤적 등급은 "완료 알림 하나를 두 줄로 쓰면 통과"로 퇴화한다.

워커가 스스로 기록한 진행 사건과 가져오기 사건은 어느 등급에서도 완료 게이트에 기여하지 않는다(§4.3). PM이 워커를 대신해 쓴 사건은 사건 어휘 단계에서 거부한다.

작업 활동 전 즉시 실패·차단만 중간 사건 부재를 대체할 수 있고, 그때도 종료 사건의 기록 주체가 변환기이고 출처가 프로세스 종료 또는 오류 봉투이며 종료 코드나 오류 봉투 해시가 있어야 한다(§4.3 말미, AC-4).

### 등급 배정이 계약이 아니라 데이터인 이유

등급 **메커니즘**(enum 3종, 등급별 게이트 조건, self-test receipt 구조, 강제 허용 조건)은 계약이 소유하고, 채널별 **배정값**(어느 채널이 어느 등급인지, 변환기·receipt 해시, 판정 증거 경로)은 Phase 0 산출 기계가독 파일이 소유한다(D-8·§4.2.1).

분리 이유는 두 가지다. 첫째, 한 자산이 둘을 함께 소유하면 실측 전에 계약을 확정할 수 없고 실측 후에는 계약 자체를 되돌려야 한다. 둘째, 채널의 관측 능력은 플랫폼 변화에 따라 바뀌는 값이므로, 배정값 변경이 계약 재확정 절차를 발동하면 플랫폼이 바뀔 때마다 프로젝트 규범이 흔들린다. 분리하면 배정값 변경은 재스파이크로 끝난다(`TASK.md` C-9).

기술적 귀결: 활성 초기화는 이 배정 파일의 항목을 읽어 계약 블록에 고정하고, **항목이 없는 채널의 활성 초기화를 거부**한다(§4.2.1). 즉 배정 파일은 문서가 아니라 초기화 경로의 입력이다.

**등급 배정값 자체는 Phase 0 산출이므로 이 문서에서 확정하지 않는다.**

## 단계별 기술 도입 순서

### Phase 0 — 채널 관측 능력 실측

- **코드로 만드는 것**: 없다. 읽기·실험 전용이며 도구·변환기 구현은 범위 밖이다(§10 Phase 0).
- **산출하는 것**: 채널별 배정을 담은 기계가독 파일과 그 근거인 원본 증거 파일. 두 축(PM의 외부 에이전트 도구 호출 축, Project Loop 내부 헤드리스 CLI 축)을 각각 실제 1회 이상 호출해 시작 식별자, 중간 메시지·스트림·도구 결과, 종료 봉투·종료 코드, 단조 측정 구간을 원본으로 남긴다.
- **문서로 개정하는 것**: 없다. 계약(등급 메커니즘)은 이미 확정돼 있어야 하며 이 단계는 계약을 **소비하는 첫 작업**이다(§4.2.1 말미).
- **게이트**: 완료 직후 사람 승인. 승인 전에는 어떤 구현 태스크에도 진입하지 않는다(§10 Phase 0 말미).

### Phase 1A — 기반 구축과 그림자 운영

**첫 슬라이스(워킹 스켈레톤)**: 그림자 모드 초기화가 새 스키마 상태 파일과 첫 기록 조각을 만들고, 사건 1건이 기록되며, 실행 검증이 그 경로를 통과하는 관통 1건. 이 프로젝트는 CLI·프레임워크이므로 서버·브라우저 관통이 아니라 **이 CLI 관통이 워킹 스켈레톤**이다. 이후 전 태스크의 검증은 이 경로 위에서 실행하며 스켈레톤 부재를 이유로 한 모의 검증을 허용하지 않는다(§10 Phase 1A).

- **코드**: 폐쇄형 사건 어휘 검증과 출처·요청 멱등성·서로 다른 시점 증거 검증을 갖춘 기록 코어·기록 CLI / 태스크 배타 락·런타임 색인·run 전역 순번·동시 경계 전환 / 상태 스키마의 보관함과 중단 가능한 초기화·복구 / 공통 마스킹·원본 상한·추적 제외·시간계 변환 / **legacy 실행 일지와 Project Loop 원본의 단방향·멱등 가져오기 능력**(멱등 키 산출과 변환까지. 완료 게이트 기여 여부는 이 단계의 관심사가 아니다) / 두 시범 파이프라인의 등급별 변환기(관측 불가로 판정된 경로는 변환기를 만들지 않고 대조군으로 남긴다).
  - 가져오기를 이 단계에 두는 이유: Phase 1A가 구현하는 폐쇄형 사건 어휘와 출처 검증이 가져온 사건에도 그대로 적용되어야 하고(§3.3 태그 매핑, §3.4 멱등 키), 그림자 기간의 비교 표본이 legacy 기록과 대조 가능해야 하기 때문이다(§10 Phase 1A 1항).
- **문서**: 없음에 가깝다. 그림자 기간에는 기존 실행 일지가 여전히 기록 원천이므로 규범 개정을 하지 않는다.
- **운영**: 두 시범 파이프라인은 그림자 모드이며 완료를 차단하지 않는다.
- **게이트**: 채널별 정상 완료 표본 20건 이상과 즉시 실패·차단·기록 실패·동시 경계 각 1건 이상, 등급별 포착률 100%·오차단 0건·기록 누락으로 인한 우회 0건·복구 성공률 100%. 워커 자발적 기록률은 보고만 하고 판정에 쓰지 않는다. 보존 비용 실측 보고도 이 단계 산출이다(§10 Phase 1A, §8.2).

### Phase 1B — 적격 시범 파이프라인 강제 적용

- **코드**: 등급별 완료 게이트 집행 / 게이트 요청·해결 사건 중개 / 보관함 복구·사용자 우회·명시적 재실행 / 시간 자동 파생과 구버전 CLI 호환 / 워커 쓰기 권한의 사건 기반 전량 재구축 / **가져온 사건의 완료 게이트 불기여 집행** — 기록 주체가 도구인 사건을 신뢰 가능한 변환기 증거 판정에서 배제하고, 원본과 표준 사건이 함께 있어도 집계 주체가 표준 사건만 세도록 강제한다(§3.4·§4.3).
- **문서**: 공유 소유자·상태 문서를 "**강제면 표준 기록 / 구버전·그림자면 기존 일지**"의 조건부 계약으로 개정한다.
- **게이트**: 한 채널이 부적격이면 그 채널만 그림자를 유지하고 다른 시범 파이프라인의 승격을 막지 않는다. 관측 불가 등급 경로의 강제 설정은 거부된다.

### Phase 1C — 나머지 파이프라인 확산

- **코드**: 남은 8종에 변환기를 4배치(`opd+opdw`, `opp+opwt`, `opgc+oppd`, `opsdd+opdd`)로 확산한다. 각 배치는 자기 적합성과 전체 상태 회귀를 통과한 뒤에만 다음 배치로 간다.
- **문서**: 마지막 배치에서 태스크 프로세스·병렬 실행 규범, 하네스 문서 2종, `docs/CONVENTIONS.md`, 상태 도구 검증을 함께 개정한다. 모든 파이프라인 스킬의 무조건 기록 지시를 제거하고 구버전 조건만 남긴다.

### 배포 순서

제안서 §6.4는 **기록 코어·기록 CLI 설치·검증 후 상태 도구의 새 스키마 활성화** 순서를 요구한다. 역순이면 상태 도구가 존재하지 않는 코어를 호출한다.

이 순서는 이 프로젝트의 배포 경계 위에서 실행한다 — `.opal/AGENT.md` §금지사항: "**`~/.opal/` 직접 편집 금지** — 항상 프로젝트 소스를 수정한 후 install로 배포한다." 따라서 실제 절차는 다음이다.

1. 프로젝트 소스(`opal/tools/`)에 기록 코어·기록 CLI를 추가한다.
2. install로 배포하고 배포본에서 기록 CLI의 검증 경로가 동작하는지 확인한다.
3. 그 다음에 프로젝트 소스의 상태 도구를 개정해 새 스키마와 계약 블록을 활성화하고, 다시 install로 배포한다.
4. 변환기는 플랫폼 어댑터 계층(install·plugin)에서만 분기한다. 도구 로직에 플랫폼 분기를 넣지 않는다(`.opal/AGENT.md` §금지사항, D-6).

## 기존 자산 영향과 회귀 방어

### 상태 도구 스키마 확장이 구버전 태스크에 미치는 영향

현재 상태 도구는 행 구조에 키가 있으면 `1.1`, 없으면 `1.0`으로 스키마 판정을 내린다(`opal/tools/state-tool/state_tool.py:1402-1405`). 새 스키마는 이 판정 위에 **추가(additive)**로 올라간다.

- 구버전 태스크는 계약 블록이 **없는 것이 정상**이며, 자동 강등·자동 위치 이동을 하지 않는다(`TASK.md` C-3).
- 새 스키마 태스크에서 계약 블록이 손편집으로 제거되면 스키마 검증 실패다. 이것이 D-7의 판정 방법이다.
- 새 스키마 태스크에서 기록이 사라지면 구버전으로 강등하지 않고 고장으로 진단한다. 단 복구 가능 초기화(보관함에 실행 시작 사건이 남은 경우)는 고장이 아니다(§6.1·AC-3).
- 시간 인자는 구버전에서 현행대로 수용하고, 새 스키마에서 파생값과 불일치하면 거부한다(§7 전환표).
- 검증 자산: `opal/tools/state-tool/tests/test_state_tool.py`와 스키마 정의(`opal/tools/state-tool/schema/state.schema.json`)가 확장의 회귀 경계다.

### Console 읽기 전용 경계 유지

Console은 상태 도구를 읽기 전용으로만 소비한다 — `dashboard/backend/adapters/state_adapter.py`의 @header가 "`state-tool show --format json` read-only 호출 래퍼. 쓰기 커맨드(init/advance/mark 등) 금지"를 선언한다. 이 태스크는 이 경계를 **바꾸지 않는다**.

- Console은 기록 조각을 직접 읽지 않는다(Phase 2 범위, PRD 비목표).
- Console이 받는 변화는 조용시간 설정의 시간대 키 하나와, 시간 값이 사람 입력이 아니라 파생값이 된다는 사실뿐이다. 화면과 기준값은 그대로 유지된다.
- 설정 로딩은 기존 2층 머지 구조 안에서 확장한다(`dashboard/backend/config.py`의 `load_quiet_hours`, 160행). 캐시 키 서명 영향은 M-1로 남긴다.
