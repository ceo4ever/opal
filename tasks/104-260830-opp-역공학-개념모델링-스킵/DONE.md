## 3. 개정 내용

### 3.1 판정 채널은 2종 — 자연어는 캡틴이 반려했다

캡틴이 후보 1안(자동 감지 + 사용자 확인)과 2안(명시 플래그)을 함께 채택해 판정 우선순위를 3단으로 확정했다.

| 순위 | 채널 | 동작 |
|------|------|------|
| 1 | 명시 플래그 `--reverse`/`--rev`, `--greenfield`/`--gf` | 해당 트랙으로 즉시 확정 — 자동 감지·확인 절차를 모두 생략 |
| 2 | 자동 감지 + 사용자 확인 | 3종 인풋을 감지해 후보를 판단하고, 사용자 확인으로 확정 (감지만으로 자동 확정하지 않는다) |
| 3 | 폴백 `greenfield` | 감지 0건·code-scan 실패 시 — fail-safe = 현행 동작 |

자동 감지 대상은 기존 ORM 모델·마이그레이션(`models/`·`migrations/`), 기존 DDL 스크립트·덤프(`.sql`), 기존 물리 DBML 3종이다. 「기존 ERD」 인풋은 개념·논리 ERD일 수 있어 역공학 신호로 인정하지 않는다(오탐 억제).

작업 도중 캡틴에게 「자연어 최초 지시」를 4번째 채널로 넣을지 제안했으나 반려됐다 — 우선순위는 3단으로 남았다.

### 3.2 실행 순서는 `physical → logical` — 개념만 빼는 안은 첫 모드부터 막힌다

TASK 단계에서 미확정으로 남긴 「역공학 트랙의 논리·물리 순서」를 PLAN이 실측 2근거로 확정했다.

| 축 | (가) `logical → physical` 유지 | (나) `physical → logical` 역전 (채택) |
|----|-------------------------------|----------------------------------|
| 첫 모드 입력 전제 | **미충족** — logical 전제가 「개념 ERD 존재 또는 주입」이라 개념 스킵 시 첫 모드부터 블로커 | **충족** — 기존 DDL·ORM·DBML이 곧 물리 입력 |
| SSOT 「모드 의존」 규정 | **충돌** — 「기존 ERD가 주입되면 해당 모드부터」인데 주입된 것은 물리다 | **정합** — 규정의 직접 적용 |
| 정보 흐름 | 존재하지 않는 상위 추상에서 하위를 도출 | 확정된 하위에서 상위를 추상화 (역공학의 정의) |

**DICT 선행 제약은 한 글자도 고치지 않고 성립한다.** DICT의 역할이 「속성명을 결정한다」에서 「기존 컬럼명을 표준사전에 역등재·검증한다」로 바뀔 뿐, 그 등재 결과가 논리 모드 속성명의 SSOT로 소비되는 관계는 그대로다. 논리가 물리 뒤에 오므로 `DICT → 논리` 순서도 유지된다. SSOT가 이미 「기존 사전이 주입되면 검증·보강 모드로 축약 가능」을 규정하고 opdd STEP 2 디스패치 프롬프트도 자동 분기를 갖고 있어, 접합점이 이미 존재했다.

### 3.3 스킵은 행 삭제가 아니라 실행 순서 분기다

착수 시 가장 먼저 확인해야 했던 구조다. MODEL은 `model.modeling` **1개 행**으로만 존재하고, 3모드 순차는 STEP 3 디스패치 프롬프트의 `**실행 순서**` 줄이 지시한다. 따라서 `pipeline.json`의 행을 건드릴 이유가 없었고, `task_steps[]` 15행·key 15종을 불변으로 유지해 기존 opdd 태스크의 `state-tool init` 호환을 그대로 보존했다.

게이트 쪽은 `model.pm_gate.gate.checklist` 4항목 중 1·2번만 트랙 조건부 문언으로 교체했다. 3·4번(`논리 속성명 = DICT 용어`, `물리 DBML 존재`)은 양 트랙 공통이라 불변이고, `gate.artifacts`는 빈 배열을 유지했다 — 트랙 조건부 산출물을 `artifacts`에 넣으면 `gate_artifact_missing`으로 역공학 태스크가 영구 차단된다.

### 3.4 트랙 축은 모드 축과 직교한다

`--reverse`/`--greenfield`가 `--interactive`/`--semi-agentic`/`--agentic` 모드 플래그 개수 검사에 섞이면 `//opdd --agentic --rev` 같은 정상 호출이 `mode_flag_conflict`로 거부된다. 하네스 §2.5 워크스페이스 축(`--worktree`)의 4소절 구성을 그대로 계승해 별도 절로 못박았다.

| 소절 | 내용 |
|------|------|
| (1) 직교 축 | 모드 축은 「PM이 얼마나 자율적으로 진행하는가」, 트랙 축은 「설계 출발점이 백지인가 기존 스키마인가」. `mode_flag_conflict` 비대상 |
| (2) 미사용 시 | 현행 동작 100% 유지 — 어떤 조건부 분기도 실행되지 않는다 |
| (3) 폴백 | 감지 불능 시 `greenfield`, 태스크 중단 없음 |
| (4) 경로 계약 | `{설계}` 트리 불변, `220.개념모델링/`만 생성하지 않는다 |

### 3.5 SSOT를 함께 고치지 않으면 스킬이 자기 인용문과 모순된다

TASK.md 초안이 놓쳤던 지점이다. opdd SKILL.md는 `docs/proposals/opal-data-design.md` §3.2·§3.2.1·§3.4를 `[MUST]` **원문 인용**한다. SSOT를 두고 스킬만 고치면 스킬이 인용한 문장과 본문이 어긋나고, 워커가 어느 쪽을 따를지 미정이 된다.

이 때문에 실행 순서를 **Step 1(SSOT) → Step 2·3(스킬)** 2개 Phase로 분리했다. Step 1이 파일에 실제로 쓴 문자열을 반환하게 하고, Step 2가 그 문자열을 복사하도록 지시해 축자 일치를 구조적으로 보장했다(`grep -F` 완전일치로 검증).

반대로 §3.2 「핵심 순서 결정」 인용 블록 2문장(「DICT가 MODEL을 선행한다」·「DDL/MIGRATION은 물리 산출 이후에만 실행 가능」)은 **수정 금지**로 못박았다 — opdd SKILL.md 3곳이 축자 인용 중이라 건드리면 3곳이 동시에 깨진다. diff 0건으로 확인했다.
