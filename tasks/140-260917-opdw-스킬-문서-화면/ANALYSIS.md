## Critical assumptions

- 공개 corpus는 TASK가 지정한 bundled `opal/skills`와 `skills`뿐이다. community/user/project skill까지 합치면 55개 수용 기준과 신뢰 경계가 달라지므로 이번 API에는 포함하지 않는다.
- production backend는 installer가 만든 `~/.opal/skills`와 `~/.opal/references`를 읽고, repository test는 dependency injection으로 임시 root를 전달한다. API 호출자가 root/path를 지정할 수 없다.
- registry의 `name`과 folder basename이 canonical identity다. frontmatter `name`은 display/provenance 및 alias 후보이지 별도 entity가 아니다.
- 기존 scalar `alias`는 호환을 위해 유지한다. 다중 별칭을 registry schema에 저장할지는 PLAN 결정 사항이지만, 저장하지 않아도 Docs service가 canonical과 다른 `source_name`을 파생 alias로 취급할 수 있다.
- source body 형식은 완전히 균일하지 않다. 섹션/예제/호출 조건 추출은 보수적인 heading/fence 규칙을 사용하고, 추출 실패는 내용을 발명하지 않고 `null`/`[]`로 표시한다.
- 등록됐지만 source가 없는 상세의 권고 계약은 HTTP 200 partial response다. PLAN이 409/422를 유지하려면 error payload에 header metadata와 source 상태를 추가하도록 wireframe/API 모델을 함께 수정해야 한다.
- 55/52와 정확한 누락 3개는 기준 리비전의 관찰값이다. 구현 직전 validator를 다시 실행해 동시 변경 여부를 확인한다.
- 새 npm/Python dependency는 필요하지 않다. frontend Markdown/UI stack과 backend PyYAML이 이미 설치돼 있다 (`dashboard/frontend/package.json:6-15`, `opal/tools/requirements.txt:23-25`).

## Handoff

- PLAN은 먼저 source-missing HTTP 계약, 다중 alias의 저장 위치, 설치 bundle 검증 진입점 세 가지를 결정해야 한다. 권고안은 각각 200 partial, scalar `alias` 호환 + additive/derived aliases, 기존 validate와 분리된 explicit verifier다.
- 구현 단위는 ① registry/verifier RED→GREEN, ② backend parser/service/router RED→GREEN, ③ FE error 계약과 화면, ④ docs 갱신, ⑤ full install·설치 smoke 순으로 나눈다. 각 단위가 독립적으로 되돌릴 수 있고 실패 원인도 분리된다.
- backend cache와 installer 복사 로직은 직접 변경 목록에 넣지 않는다. 성능 측정 또는 설치 smoke 실패가 있을 때만 별도 계획 항목으로 승격한다.
- 착수 자체를 막는 외부 blocker는 없다. 다만 source-missing 계약을 확정하지 않고 API/FE를 병렬 구현하면 공개 model과 오류 UI를 재작업하게 되므로 PLAN 승인 전 결정이 필요하다.
