# TASK: 알투 보고 형식 표준 — 3블록 구조 정식 등재

> 작성일: 2026-05-10 | 작업 유형: 신규 | 적용 스킬: opp | 모드: semi-agentic
> 입력: 사용자 요청 (이전 세션 합의 + 본 세션 검토 보완)
> 출력: TASK.md

## 작업 목표

알투(에이전트)가 캡틴께 드리는 모든 응답의 보고 형식을 **3블록 구조(결론·근거·다음)** 로 표준화하고, OPAL 정식 규칙으로 영구 등재한다.

## 배경

캡틴 피드백:

1. 기존 알투의 보고가 장황하고 근거가 복잡해 결정이 어렵다
2. 문단·문맥 구분이 한눈에 들어오지 않아 비숙련자가 보기 어렵다
3. PM(태스크) 보고에만 한정하면 일반 검토/조사 응답에도 같은 부작용이 발생한다

이전 세션에서 11종 분류 + 마스터 5블록(결론·지표·근거·의견·용어)을 1차 제안했으나, 본 세션 검토에서 **과설계 + 알투 응답이 오히려 더 장황해지는 역설**이 확인되어 단순화하기로 합의했다.

## 배경 분석 (대화에서 도출)

### 현재 상태

| 영역 | 현행 | 문제점 |
|------|------|--------|
| PM(태스크) 보고 | `~/.opal/AGENT.md` "보고 형식" 섹션 (간단/상세 2종) | 작업 규모만 구분, 응답 종류·결정 요청 형식 미정의 |
| PM(대화) 응답 | 형식 규정 없음 | 알투 자율 판단 — 일관성 없음, 장황해지기 쉬움 |
| 비서 응답 | 형식 규정 없음 | 동일 |
| 객관식 제시 | 명시 규칙 없음 | 자유 응답 요구 시 캡틴 결정 비용 증가 |
| 시각 구분 | 명시 규칙 없음 | 알투가 ASCII 박스를 과사용하는 경향 |

### 1차 제안 → 단순화 결정 경로

| 항목 | 1차 제안 | 본 세션 합의 | 사유 |
|------|----------|--------------|------|
| 응답 종류 | 11종 분류 | 분류 폐기 (자유 결론 카드) | 사후 분류 함정 — 종류 경계가 흐릿 |
| 블록 수 | 5블록 (결론·지표·근거·의견·용어) | 3블록 (결론·근거·다음) | 짧은 답변에도 5블록 강제 시 더 장황 |
| 용어 풀이 | 필수 블록 | 옵션 항목 (모를 만한 용어 등장 시만) | 캡틴이 OPAL 설계자라 자기 시스템 용어 반복 학습 불필요 |
| ASCII 박스 | 표준 양식 | 폐지 (마크다운 헤딩만) | 토큰 비용 + 가독성 |
| 적용 범위 | PM(태스크) 한정 | 모든 모드 (PM 태스크 + 대화 + 비서) | 문제는 모드 무관하게 발생 |

## 확정된 설계 방향 (대화에서 합의)

### D-1. 3블록 구조 (고정)

| 블록 | 역할 | 필수/옵션 |
|------|------|-----------|
| **결론** | 핵심 답/판단/선택 요청 (캡틴이 이것만 읽고도 판단 가능) | 필수 |
| **근거** | 왜 그 결론인지 — 표·리스트 우선, 산문 최소 | 필수 |
| **다음** | 캡틴 다음 행동 / 알투 다음 행동 | 옵션 (없으면 생략) |

### D-2. 결론 카드 — 선택 요청 시 양식

캡틴 결정이 필요한 경우:

- 결론 첫 줄: "캡틴 결정이 필요합니다 — N개 옵션 중 알투 권고는 X번"
- 옵션 제시는 **근거 블록 안의 표/리스트**로 흡수 (별도 블록 만들지 않음)
- 다음 블록: "Q-번호로 답해주세요" 식 응답 형식 안내

### D-3. 일목요연 원칙 (상위 제약)

- 결론은 1~2줄
- 근거 핵심 항목 3개 이내
- 표·리스트 우선, 산문 최소
- ASCII 박스 사용 금지 (마크다운 헤딩 + `---` 구분선만)

### D-4. 시각 구분 원칙 (상위 제약)

- 블록 사이 `---` 구분선
- 블록 헤딩은 굵은 텍스트 (예: `**결론**`)
- 빈 줄로 문맥 단위 분리
- 비숙련자가 한눈에 보고 구조를 파악할 수 있어야 함

### D-5. 형식 자율성 (상위 제약 하위)

블록 구조와 위 두 원칙(D-3·D-4)은 고정. 그 외 표현 양식은 알투 자율 판단:

- 표 vs 리스트 vs 산문 선택
- 용어 풀이 끼워넣을지 / 생략할지
- 다음 블록 생략 여부
- 응답 자체를 비보고(자유 형식)로 처리할지

### D-6. 적용 범위

- PM(태스크) 모드 — 모든 단계 보고 (TASK·PLAN·EXECUTE·QA·CLOSE)
- PM(대화) 모드 — 분석/설명/검토 응답
- 비서 모드 — 일반 응답

### D-7. 영구화 방식

- 신설 파일: `opal/core/references/harness/reporting-template.md` (SSOT)
- 트리거 등록: `opal-pm.md` + `opal-harness.md` 양쪽
- 적용 매체: 알투(Claude Code 인스턴스) 일반 — 프로젝트 무관

## 미확정 사항 (PLAN에서 결정)

### M-1. 트리거 로딩 방식

| 후보 | 설명 | 검토 결과 |
|------|------|-----------|
| Lazy (광범위) | "보고/응답 작성 시" 트리거 — 사실상 첫 응답에서 무조건 로드 | 알투 비판: 사실상 Eager와 동일 |
| Lazy (좁힘) | "캡틴 결정 요청이 명시적으로 필요한 응답" 등 좁은 트리거 | 후보 |
| Eager 명시 | 부트스트랩 Eager 단계에 추가 | 후보 (정직한 표현) |

→ PLAN에서 비용·가시성·정직성 트레이드오프 분석 후 결정.

### M-2. 보고 vs 비보고 판별 기준

| 후보 | 설명 | 검토 결과 |
|------|------|-----------|
| 3개 기준 (1차안) | 결정 요청·정보 3개 이상·옵션 — 1개라도 해당 시 보고 | 알투 비판: 너무 느슨, 거의 모든 응답이 해당 |
| 단순 2개 기준 | (1) 결정 요청 (2) 의도적 구조화 필요 — 양쪽 다 아니면 비보고 | 후보 |
| 알투 자율 판단 | 명시 기준 없이 알투가 사안별 판단 | 후보 (D-5 형식 자율성과 정합) |

→ PLAN에서 결정.

### M-3. 기존 PM(태스크) 보고 형식 처리

`~/.opal/AGENT.md` "보고 형식" 섹션의 기존 간단/상세 2종 보고 형식을 3블록 구조로 통합/대체할지, 별도 유지할지 PLAN에서 결정.

### M-4. PM(태스크) 단계별 결론 카드 필드

PLAN/EXECUTE/QA/CLOSE 등 단계별로 결론 카드에 어떤 정보가 들어가야 하는지 표준화 여부. (현재는 D-5 형식 자율성으로 알투 판단 위임 가능)
