00

확정된 결정

  • ✓제어구조 — 종료조건 있는 2-루프 수렴 구조(설계 루프 + 실행 루프). 선형 Phase 아님.
  • ✓단위 — 태스크 = 얇은 수직 슬라이스. BACKLOG = 살아있는 백로그. 2단 설계(거시/미시).
  • ✓CONTRACT = 1급 산출물 — 설계 루프에서 작성, 실행 루프 매 태스크에서 리뷰·검증.
  • ✓검증 3-tier — 결정론(code) → 루브릭(LLM) → 사람(게이트). 결정론 우선·위계.
  • ✓역할 분리 — 작성=Planner · 리뷰/판정=Evaluator · 반영=PM.
  • ✓Evaluator = 전담 에이전트 opal-evaluator-agent (패턴 B, security-checker형). 순수 판정·mutate 금지.
  • ✓병렬 — 태스크 간 기본, 계약 고정 시 태스크 내 FE/BE. 병렬 그룹마다 통합 태스크 필수.
  • ✓신규 자산 — 에이전트 1개(opal-evaluator-agent) + 스킬 0~1개. 나머지는 재사용(주입+상속).
  • ✓UX 산출물 — USER_JOURNEY.md(Loop1 거시) / USER_FLOW.md(Loop2 미시), Mermaid 작성. user-facing 프로젝트만 트리거.
  • ✓디스패치 = 하이브리드(C) — 생성자(도메인 resolve) + Evaluator + 동작검증, 태스크당 ~3회. 저위험 경량화.
  • ✓검증 2원화 — Evaluator=명세 심판(구현 전) PLAN/FLOW/SCENARIO+계약 / test-agent=동작 검증(구현 후). 테스트 통과 후 변경파일 conv/sec-checker. drift 시만 Evaluator 재콜백.
  • ✓산출물 자동 생성·기록 — 기존 OPAL 리포트 준용(GC-SECURITY/GC-CONVENTION/QA-*/DONE), 없으면 VERIFICATION.md. 결과계약 {대상·PASS/FAIL·사유·시점}.
  • ✓3-SSOT (tool-gated JSON) — backlog.json(작업항목·backlog-tool 신규) · state.json(파이프라인·state-tool 재사용) · test-scenario.json(검증·test-tool 확장). 사람 뷰 자동 렌더, 손편집 금지.
  • ✓명명·전환·모드 — alias oppl · 백로그 BACKLOG.md + 태스크 PLAN.md · oppd는 병행 후 deprecate · 모드 3-way 승계(semi-agentic 기본).
01

정의와 존재 이유

oppd와 목적은 동일하다 — 규모 있는 프로젝트의 완전한 완수. 차이는 제어구조다. 선형 Phase가 아니라 종료조건이 있는 수렴 루프로 구동한다.

축oppd (현행)loop (신규)
제어구조선형 3-Phase + 전환 게이트수렴 루프 (계획→실행→검증→재계획)
실행 단위전체 WBS 일괄태스크(얇은 수직 슬라이스) 1개씩 반복
재계획scope 3분기 등 무거운 규칙루프의 일부로 자연 흡수 (백로그 갱신)
완료 판정액션 소진종료조건 충족까지 반복
검증단계 뒤 별도 게이트루프에 verify 내장 (evaluator-optimizer)
인터뷰opwt에 암묵 위임 (얕음)1급 단계로 승격

태스크 = 슬라이스

단일 책임 + 하나의 수용기준으로 독립 검증 가능한 최소 증분.

BACKLOG = 살아있는 백로그

WHAT·순서·종료조건만. 상세 설계(HOW)는 미포함. 매 루프 갱신.

2단 설계

거시(TRD+PLAN, 설계 루프) + 미시(태스크별, 실행 시점).

* UX 산출물 (조건부)

USER_JOURNEY.md(Loop1 거시 — 단계·행동·시스템 반응) / USER_FLOW.md(Loop2 미시 — 분기·상태·에러경로). Mermaid(flowchart/sequenceDiagram) 작성. user-facing 프로젝트만 트리거 — 인프라·라이브러리·CLI 내부 스킵. Flow는 인터랙션 있는 슬라이스만(순수 API/BE는 계약 테스트로 대체).

3-SSOT 체계 (tool-gated JSON)

backlog.json = 작업항목 인벤토리+상태(무엇을·순서·됐나) / state.json = 파이프라인 진행(어느 단계) / test-scenario.json = 검증 스펙+결과(통과했나). 각기 다른 축 → double-truth 방지. 사람 뷰는 BACKLOG.md·STATE.md로 자동 렌더(손편집 금지). 태스크 미시설계는 PLAN.md.

병렬 실행

기본은 태스크 간 병렬(FE/BE 슬라이스 분리 → worktree 격리). 계약 고정 시 태스크 내 FE/BE 병렬도 허용. 병렬 그룹마다 통합 태스크(머지 후 계약·E2E 검증)가 필수. STATE는 PM 단독 갱신.

04

검증 3-tier + 기준 항목

Anthropic 등급 체계(코드/LLM/사람)와 정합. 결정론 → 루브릭 → 사람 위계로, 하위 통과 후에만 상위로.

① 결정론 (code-based)

객관·재현·무료·pass/fail. 도구 집행. test-tool · L1~L3 · convention/security-checker

② 루브릭 (LLM-judge)

주관·판단. 앵커된 척도. opal-evaluator-agent

③ 사람 (human)

최종 검증·비가역 게이트. User

① 결정론 기준 항목 — binary / threshold
기준 항목판정 형태도구
Lint / Formatbinary — 오류 0L1 · test-tool
Build / Typebinary — passL2
Unit / Integrationbinary — 100% greenL3a · test-tool
E2Ebinary — passL3b
계약 conformancebinary — 스키마·시그니처 일치, 계약테스트 passtest-agent + 계약테스트
커버리지threshold — ≥ N%test-tool
보안·정적분석threshold — critical 0security-checker
② 루브릭 기준 항목 — 앵커된 척도 + 통과선
차원척도통과선앵커 예시
계약 완전성Likert 1–5≥41: 경계·엔드포인트 다수 누락 / 5: 모든 경계·데이터형·에러규약 정의
계약 일관성Likert 1–5≥41: 명명·타입 규약 모순 / 5: 내부 모순 없음
설계 정합 (구현↔CONTRACT/TRD)Likert 1–5≥41: 계약과 어긋남 / 5: 완전 부합
drift 필요성binary yes/no—계약 변경 필요? → yes면 §5 거버넌스
컨벤션 정신 (가독성·네이밍)Likert 1–5≥4기계 규칙 너머의 품질
아키텍처 적합 (레이어·의존)Likert 1–5≥4경계·의존 역전 여부
  • 평가자 ≠ 생성자 — 생성 모델과 다른(강한) 모델로 평가. Evaluator ≠ Executor/Planner.
  • SMART 기준 — Specific·Measurable·Achievable·Relevant. ❌"안전한 출력" → ✅"harmful 0.1% 미만".
  • 자동화 우선 / 다차원 — 기계 채점 가능한 건 전부 ①로. 한 항목 아닌 여러 기준 동시 판정.
  • 엣지 케이스 — 비정상·초장문·부적절·모호 입력을 시나리오에 포함.
① 결정론 실패 → Executor 재작업 (fix loop · L2 2회 / L3a 3회)
② 루브릭 미달 → Evaluator 피드백 (optimizer loop · 통과선 + 반복상한)

06

에이전트 구성

역할(Planner/Executor/Evaluator)은 안정, 도메인 지식은 가변 — 도메인은 에이전트에 굽지 않고 컨텍스트로 주입한다. Evaluator만 신규 전담 에이전트(convention/security-checker 선례), 나머지는 재사용.

opal-evaluator-agent (신규)

기준 출처 = CONTRACT.md 루브릭절 (convention-checker가 CONVENTIONS.md 읽듯). verdict-only · mutate 금지 · readonly. model: standard/advanced. 산출: {item, result, reason, suggestion}.

가변성 흡수

① 디스패치 시 docs 주입(PROJECT/ARCH/CONVENTIONS + PLAN/계약)   ② 2계층 상속(프레임워크 ← 프로젝트 에이전트). OPAL 에이전트는 고정이 아니라 역할 껍데기 + 주입 컨텍스트.

근거
