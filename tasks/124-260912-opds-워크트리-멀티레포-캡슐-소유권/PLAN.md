# PLAN: 워크트리 multi-repo 캡슐 소유권 — 계약 이관과 worktree-tool 구현

> 입력: [TASK.md](TASK.md) · 설계 원문(SSOT): `docs/proposals/opal-worktree-multirepo-ownership.md` §4·§5·§6·§7·§8 (C-1)
> ANALYSIS.md 없음(opds short). 아래 인용의 줄번호는 워크트리 현재 파일에서 직접 재확인한 실측값이다.

## Approach

제안서 §4·§5·§6이 확정한 계약을 **설정 계층 → 생성 경로 → 회수 경로** 3단으로 나눠 `worktree_tool.py` 한 파일에 순차 적용하고, 계약 규범을 `harness/worktree.md`로 이관한 뒤 제안서를 archives로 옮긴다. 새 계약은 전부 **multi-repo 분기 안**에 갇히므로 monorepo·비워크트리 경로는 코드 경로 자체에 도달하지 않는다(C-2·C-3).

`worktree_tool.py`는 단일 파일이고 변경 지점이 서로의 반환값을 소비하므로 병렬화 이점이 없다 — W-3→W-4→W-5를 P2·P3·P4로 직렬화하고, 파일 소유권을 한 워커에 고정한다.

코드 근거는 `code-scan`이 아니라 실파일 실측으로 확보했다(이 도구의 `@header`는 `domain: opal-workspace`, `layer: util`, `depends: ["git CLI 2.25+"]`, `exports` 14종을 선언한다 — `worktree_tool.py:1-16`). 변경 후 `exports`가 늘지 않으므로(신규 함수는 전부 `_` 접두 내부 헬퍼) `@header`는 `description` 갱신만 필요하다.

## Decisions and contracts

| 결정 | 변경 후 계약 | 선택 이유·근거 |
|---|---|---|
| D-1. `task_artifacts` 검증 위치 | `validate_worktree_config`가 타입·키를 검사하고, `repo != "."`이면 `TASK_ARTIFACT_REPO_UNSUPPORTED`로 즉시 차단한다. **multi-repo 분기 전용** — monorepo에서는 키를 읽지도 검증하지도 않는다 | 제안서 §4.1·§7.1. 설정 오류는 파일시스템 접근 없이 판정 가능하므로 config 계층이 소유한다. monorepo 분기 미진입이 C-2의 구조적 근거다 |
| D-2. 정규화 dict 확장 | `validate_worktree_config` 반환 dict에 `task_artifacts`(dict 또는 `None`)와 `baseBranchOverrides`(dict, 기본 `{}`)를 additive로 추가한다 | 기존 8키를 제거·개명하지 않는다. cfg는 어떤 명령 출력에도 통째로 실리지 않는다(`cmd_list`는 `cfg["layout"]`만 싣는다 — `worktree_tool.py:1027-1032`) → C-2 바이트 동일이 구조적으로 보전된다 |
| D-3. R-1~R-5 판정 위치와 순서 | **판정 순서는 R-1~R-4 → overlap(D-5) → R-5다**(D-24). `cmd_create`의 pre-flight **맨 앞**(현행 `:863` repos 실재 검사보다 먼저, `_issue_task_ownership` 호출보다 먼저)에서 실행한다. 하나라도 불만족이면 `TASK_ARTIFACT_REPO_INVALID`에 위반 조건 번호 배열(`violations: ["R-2","R-5"]` 형태)을 실어 차단한다 | 제안서 §4.1(PM 확정 개정 — R-5 신설). `_issue_task_ownership`(`:684`)이 multi-repo 소유권을 발급하려면 루트 적격이 먼저 확정돼야 한다. 전부 부수 효과 이전이므로 DEC-2 all-or-nothing은 유지된다 |
| D-4. R-2~R-5 개별 판정 | `git -C <root> ls-files -- <경로>` 3회(대상 `tasks`, `.opal/AGENT.md`, `.opal/MEMORY.json`)를 각각 실행하고 합산하지 않는다. 이어서 각 `rel ∈ repos`에 `git -C <root> check-ignore -q <rel>`을 실행해 R-5를 판정한다 | 제안서 §4.1 [MUST]. 합산 1건 통과를 허용하면 `.opal/`을 ignore하는 프로젝트가 통과해 merge 시 귀속 대상이 브랜치에 담기지 않는다. R-5는 추적이 아니라 ignore 축이라 `ls-files`로 대체되지 않는다 — 미추적이면서 ignore되지 않은 경로가 정확히 H-1의 구멍이다 |
| D-5. OVERLAP 판정 | 각 `rel ∈ repos`에 대해 `git -C <root> ls-files -- <rel>`이 비어야 한다. 1건이라도 있으면 `TASK_ARTIFACT_REPO_OVERLAP`에 위반 경로를 실어 차단하고 worktree를 하나도 만들지 않는다 | 제안서 §4.4. 겹치면 루트 full checkout과 코드 repo worktree가 같은 경로에 착지해 승자가 정의되지 않는다 |
| D-6. `plan_entries` 자료형 확장 | `(git_root, dest)` 2튜플을 **`(rel, git_root, dest)` 3튜플**로 바꾼다. multi-repo + 유효 `task_artifacts`이면 `(".", project_root, wt_root)`를 **맨 앞**에 넣는다. monorepo는 `[(".", project_root, wt_root)]` 단일 원소로 동형 유지 | 제안서 §4.5. base-ref override 조회 키가 `rel`이므로(§5.1) entry가 자기 키를 들고 다녀야 한다. `rel`은 파생값이 아니라 설정 원문이다 |
| D-7. 생성 루프 단일 소비 [MUST] | multi-repo 생성 루프(`:907-908`)의 `for rel in cfg["repos"]`를 `for rel, git_root, dest in plan_entries`로 교체한다. `cfg["repos"]`를 생성 국면에서 다시 순회하지 않는다 | 제안서 §4.5. 두 목록이 갈라지면 pre-flight 통과가 생성 결과를 보장하지 못한다(AC-7). monorepo 분기는 `plan_entries`를 쓰지 않으므로 무변경 |
| D-8. base-ref 해석 | `base_refs = {str(git_root): resolve_base_ref(git_root, overrides.get(rel, cfg.get("baseBranch"))) for rel, git_root, _ in plan_entries}`. 루트의 override 키는 `"."` | 제안서 §5.1. `resolve_base_ref`의 3단 폴백(`:310-318`)은 건드리지 않는다 — override는 `declared` 자리에 값을 넣을 뿐이다. `overrides`가 `{}`면 식이 현행과 동치라 monorepo·기존 multi-repo 출력이 바이트 동일하다 |
| D-9. `baseBranchOverrides` 키 검증 | 키가 `repos[]` 원소 또는 `"."`와 정확히 일치하지 않으면 `CONFIG_UNKNOWN_REPO`(위반 키 동봉)로 차단한다. **multi-repo 분기에서만** 검증하며 monorepo는 값이 있어도 무시하고 경고하지 않는다 | 제안서 §5.1. 오타가 조용히 전역값으로 폴백하면 잘못된 base에서 브랜치가 갈라진다 |
| D-10. 소유권 발급 분기 | `_issue_task_ownership`의 `if cfg["layout"] != "monorepo"` 가드(`:701`)를 "monorepo **또는** 유효 `task_artifacts` 보유 multi-repo"로 넓힌다. 이 경우 `task_home = str(wt_root)`, `artifact_repo = "."`로 monorepo와 동일 경로를 탄다. `task_artifacts` 미설정 multi-repo는 기존 `TASK_ARTIFACT_REPO_MISSING`(`:703`)을 그대로 유지한다 | 제안서 §4.2. slot root 자체가 루트 repo worktree이므로 `task_path == realpath(task_home/tasks/task_folder)` 불변식이 기존 검증 코드(`:715-728`) 그대로 성립한다(AC-2). `_resolve_canonical_task_path`의 허브 후보(`:1057`)도 `project_root/tasks/...`로 맞아떨어져 resolver 무변경 |
| D-11. cone 미적용 | multi-repo 분기에 `taskCapsuleCone`을 전개하지 않는다. sparse-checkout 호출은 monorepo 분기(`:948-952`)에만 남는다 | C-5 · 태스크 118 결정 · `harness/worktree.md` §cone 확장 계약. 루트가 `repos[]`를 추적하지 않음(D-5)이 보장되므로 full checkout해도 코드 repo와 겹치지 않는다 |
| D-12. 회수·롤백 순서 [MUST] | `_rollback`은 `created`를 **역순**으로, `cmd_remove`는 `entries`를 **역순**으로 순회한다(자식 → 루트) | 제안서 §6.1. 실측: 자식 worktree가 남은 상태에서 루트 `git worktree remove`는 `exit 128`, `contains modified or untracked files`로 실패한다 |
| D-13. 실패 관측과 보존 [MUST] | `cmd_remove`는 각 `git worktree remove`의 `returncode`를 확인한다. 하나라도 실패하면 `WORKTREE_REMOVE_FAILED`(실패 repo·경로·stderr 동봉)로 반환하고 `_delete_meta`(`:1216`)와 `shutil.rmtree(wt_root)`(`:1228`)를 **실행하지 않는다**. `--force`는 가드 우회에만 적용되고 이 판정을 우회하지 않는다 | 제안서 §6.2. 현행은 `:1213`에서 반환값을 버려 자식이 남은 채 메타만 사라지고 복구 경로가 소멸한다 |
| D-14. 2축 멱등 판정 | entry별로 **경로 실재**와 **Git 등록**(`_dest_registered`, `:164-172`)을 따로 보고 4칸으로 판정한다 — (없음,없음)=skip, (없음,있음)=등록 고아→차단, (있음,없음)=미등록 잔여→차단, (있음,있음)=가드 판정 후 회수. 판정은 `--force` 없이 동작한다 | 제안서 §6.3. 현행 `:1189-1193`은 경로 부재를 `--force` 없이는 `WORKTREE_NOT_FOUND`로 즉시 중단해 부분 회수 재시도가 불가능하다. `_dest_registered`는 create pre-flight가 쓰는 DEC-7 판정 그대로 재사용하며 새 기준을 만들지 않는다 |
| D-15. 자동 복구 금지 [MUST] | 불일치 2종에서 `git worktree prune`을 호출하지 않고, 미등록 잔여 디렉토리를 삭제하지 않는다. 실패 repo·경로·불일치 종류를 payload에 담고 메타·slot을 보존한다 | C-6 · 제안서 §6.3. prune은 해당 repo의 **모든** stale 관리정보를 지워 다른 태스크 슬롯을 함께 파괴할 수 있고, 미등록 디렉토리 내용은 사용자 파일일 수 있다 |
| D-16. 롤백 실패 처리 | `_rollback`이 역순 회수 중 실패하면 `shutil.rmtree(wt_root, ignore_errors=True)`(`:845`)를 실행하지 않고, 잔존 entry(경로·repo·branch)를 오류 payload에 실어 반환한다. 메타 기록 전이면 메타를 만들지 않고 잔존 목록만 싣는다 | 제안서 §6.3 말미. 흔적을 지우면 수동 복구 대상이 사라진다 |

| D-18. 오류 코드 5종 신설 | `ERROR_CODES`(`:33-64`)에 `TASK_ARTIFACT_REPO_INVALID`·`TASK_ARTIFACT_REPO_UNSUPPORTED`·`TASK_ARTIFACT_REPO_OVERLAP`·`CONFIG_UNKNOWN_REPO`·`WORKTREE_REMOVE_FAILED`를 추가한다. 기존 코드의 문구·의미를 바꾸지 않는다 | 제안서 §7.1. 기존 코드 문구 변경은 `test_s14_error_codes_are_all_distinct`(`tests/test_worktree_tool.py:121`)·`test_t118_s6_error_codes_stay_within_existing_set`(`:1688`) 회귀를 건드린다 |
| D-19. fixture 소유 위치 | multi-repo 루트 소유권 fixture 빌더는 `conftest.py`가 아니라 `tests/test_worktree_tool.py` 안의 모듈 지역 헬퍼로 둔다 | 배정된 변경 범위 밖 파일을 늘리지 않는다. `_build_independent_repo`(`tests/test_worktree_tool.py:53`)가 같은 방식의 선례다 |

- **적용 순서**: P1(W-1 RED · W-2 규범) → P2(W-3 설정) → P3(W-4 생성) → P4(W-5 회수) → P5(W-6 header·GREEN) → P6(W-7 회귀 증거) → P7(W-8 제안서 이관). `worktree_tool.py`는 W-3→W-4→W-5→W-6 한 소유자가 순차 수정하며 같은 그룹에서 나눠 갖지 않는다.
- **RED-first 판정**: W-1·W-3·W-4·W-5는 `구현 전 RED`(공개 CLI 계약 변경 + 회귀 위험). W-2·W-8은 문서라 RED 대상이 아니고 결정론 검사로 검증한다. W-6은 GREEN 확정·`@header` 갱신이라 RED 대상이 아니다. W-7은 실측 증거 수집이라 RED 대상이 아니다. 규칙 SSOT는 `opal/core/references/harness/red-first.md`.
- **검증 범위**: 결정론 — `python3 -m pytest opal/tools/worktree-tool/tests/ -q` 전건 GREEN(AC-15) + `state-tool verify <task> --plan-contract-check` · `--code-scan-citation-check`. 회귀 — W-7의 `cmp` 18쌍 이상, 정규화 0회(AC-12·AC-13). 실제 연동 — 없음. pug 실환경 연동은 범위 밖(D-22).
- **실측 경계**: H-1은 EXECUTE 착수 전 차단 항목이었고 D-23으로 해소됐다(제안서 §4.1 R-5 신설). 잔여 차단 항목 없음.
- **배포**: 실 `~/.opal/` 재배포는 본 태스크 범위가 아니다(C-8). W-7의 install은 격리 `HOME`의 임시 배포 경로에만 수행하고 측정 후 삭제한다. 소스 변경은 `install-mac.sh` 재배포로 반영되며 그 시점은 merge 이후다.
- **실패 시**: W-3~W-5는 단일 파일 변경이므로 `git checkout -- opal/tools/worktree-tool/worktree_tool.py`로 되돌린다. W-8 이관 후 문제가 발견되면 `git mv`를 역방향으로 되돌리고 `> 상태:`를 `제안`으로 복원한다 — 제안서는 삭제하지 않으므로 근거가 끊기지 않는다.
