## 작업 목표

서비스 기획의 기술 산출물을 **논리적 네트워크**로 관리하는 오케스트레이터 스킬 `otp-write-tech`를 개발한다. PM이 워커를 병렬 디스패치하여 문서를 분석/작성하고, 교차 논리 검토와 정합성 검증을 통해 문서 간 일관성을 보장한다.

## 설계 원칙

### 문서가 인터페이스다

- 스킬은 **다른 스킬의 존재를 모른다** — 스킬은 계속 바뀔 수 있다
- 스킬은 **프로젝트 문서**만 안다 — `docs/`에 있는 문서가 인터페이스
- 문서가 있으면 **활용**, 없으면 **생성**, 필요하면 **최신화**
- **PM이 전체를 관리**한다 — 어떤 스킬을 언제 쓸지는 PM이 판단

### PM 역할

- **교차 논리 검토**: 문서 간 용어/범위/기능 일관성 판단 (전체 맥락 필요)
- **진단 + 배치 편성**: 누락/불일치 식별, 작업 우선순위/병렬화 결정
- **검수 + 최종 판정**: 워커 산출물 품질 검증, 사용자에게 보고
- **문서 등록**: `docs/PROJECT.md` 문서 테이블에 산출물 등록 관리

## 배경

참조: [서비스 기획 산출물 톺아보기](docs/web-captures/it-ist-tistory-com-277.md)

서비스 기획 산출물은 서로 **논리적으로 연결된 네트워크**를 형성한다:

```
순서 체인 (기본 흐름):
  PRD → TRD → 서비스 정책서 → IA (기능 포함)

논리적 연결 (양방향):
  - 역방향도 가능 (IA 먼저 쓰고 PRD를 나중에 써도 됨)
  - 수정 시 연결된 문서 연쇄 업데이트
  - 선택 산출물은 필수 산출물과 연결
```

**논리적 연결의 의미:**
- **순서 체인 존재** — 기본 흐름은 PRD → TRD → 서비스 정책서 → IA
- **역방향도 가능** — 있으면 참고, 없으면 없는 대로 작성
- **수정 시 연쇄 업데이트** — 한 문서를 수정하면 연결된 다른 문서도 영향 분석 후 함께 수정

**실무 현실:**
- 산출물 유형당 **복수 문서** 존재 (예: 정책서 = 회원/결제/환불/개인정보 ...)
- 독립 문서는 **병렬로 작성/수정** 가능
- PM이 교차 검토, 워커가 개별 문서 처리 — **역할 분리**

## 산출물 저장 구조

### 원칙

- `docs/` = 프로젝트 환경/기반 메타 문서 (PROJECT.md, ARCHITECTURE.md 등)
- **프로젝트 산출물**(기획서, 정책서, IA 등)은 `docs/`가 아닌 **별도 폴더**에 저장
- `docs/PROJECT.md`가 폴더 구조의 **SSOT** — 여기에 기록된 구조를 따른다

### PM 판단 흐름

1. `docs/PROJECT.md` 읽기 → 기존 폴더 구조 파악
2. **구조 있으면**: 해당 구조에 산출물 폴더 추가, PROJECT.md에 반영
3. **구조 없으면**: default 구조 제안 → 사용자 확인 → PROJECT.md에 기록

### default 구조 (기존 구조가 없을 때 PM이 제안)

```
{project root}/
  ├── docs/                        ← 프로젝트 환경/기반 (PM 관리)
  │   └── PROJECT.md               ← 폴더 구조 정의 (SSOT)
  ├── tasks/                       ← 태스크 관리
  ├── .opal/                       ← PM/메모리
  │
  ├── outputs/                     ← 프로젝트 산출물
  │   ├── 01_기획/                  서비스 기획
  │   │   ├── PRD.md
  │   │   ├── TRD.md
  │   │   ├── 서비스기획서.md
  │   │   ├── 정책서/              도메인별 복수
  │   │   ├── IA/                  엑셀(.xlsx) 추천
  │   │   └── 와이어프레임/
  │   ├── 02_설계/                  기술 설계 (DB, API 등)
  │   ├── 03_개발/                  개발 산출물
  │   ├── 04_운영/                  운영 문서
  │   └── 99_참고문서/              외부 자료, 웹 캡처
  │
  ├── frontend/                    ← FE 소스 (있으면)
  └── backend/                     ← BE 소스 (있으면)
```

## otp-write-tech 커버 범위

### 필수 산출물 — 서비스 기획의 뼈대

| 산출물 유형 | 설명 | 문서 수 | 논리적으로 연결된 유형 |
|------------|------|--------|---------------------|
| PRD | 목표, 타깃 유저, 핵심 요구사항 | 보통 1개 | TRD, 서비스 정책서, IA |
| TRD | 기술 요구사항, 아키텍처, 기술 스택 | 보통 1개 | PRD, IA |
| 서비스 정책서 | 회원/결제/환불 등 비즈니스 정책 | **복수** (도메인별) | PRD, IA, 운영 정책서 |
| IA (기능 포함) | 정보구조도 + 기능 정의. JSON으로 작성 → 검토 후 xlsx 변환 | 보통 1개 | PRD, TRD, 서비스 정책서 |

### 선택 산출물 — 프로젝트 규모/필요에 따라 추가

| 산출물 유형 | 설명 | 논리적으로 연결된 유형 |
|------------|------|---------------------|
| 기능도 | 기능 계층 구조 시각화 | IA |
| 순서도(Flowchart) | 기능별 흐름 도식화 | IA |
| 운영 정책서 | CS 처리, 환불, 개인정보 파기 등 | 서비스 정책서, IA |
| 서비스 매뉴얼 | 서비스 개요, 주요 기능, 사용법 | IA, 운영 정책서 |

> 저장 위치는 PM이 PROJECT.md 폴더 구조를 기반으로 결정한다.

## 아키텍처: 4 Phase 파이프라인

```
Phase 1: 병렬 분석 — PM이 워커 N개 디스패치, 기존 문서 병렬 읽기/요약
Phase 2: PM 진단   — 교차 논리 검토 → diagnosis.json 생성 (문서별 조치/이슈/의존성/배치) → 사용자 검토
Phase 3: 병렬 작성 — diagnosis.json 파싱 → 배치 순회 → 항목별 워커 디스패치
Phase 4: 정합성 검증 — diagnosis.json 기반 검증 → QA 워커 + PM 최종 판정
```

### PM vs 워커

| 역할 | 담당 | 이유 |
|------|------|------|
| 개별 문서 읽기/요약 | **워커 (병렬)** | 독립적, 병렬화 가능 |
| 문서 간 교차 논리 검토 | **PM (직접)** | 전체 맥락이 필요한 판단 |
| 누락/불일치 진단 + 배치 편성 | **PM (직접)** | 네트워크 전체를 봐야 함 |
| 개별 문서 작성/수정 | **워커 (병렬)** | 독립적, 병렬화 가능 |
| 정합성 검증 | **QA 워커 + PM** | 워커가 체크, PM이 최종 판정 |
| docs/PROJECT.md 문서 등록 | **PM (직접)** | 프로젝트 문서 테이블 관리 |

### 3가지 모드

| 모드 | 진입 | 동작 |
|------|------|------|
| **작성** | 새 산출물 작성 요청 | Phase 2(간략) → Phase 3(작성) → Phase 4(검증) |
| **수정** | 기존 산출물 수정 요청 | Phase 1(분석) → Phase 2(영향 진단) → Phase 3(수정) → Phase 4(검증) |
| **분석** | 기존 문서 검토/최신화 요청 | Phase 1(분석) → Phase 2(진단 보고) → 승인 → Phase 3(보완) → Phase 4(검증) |

### Phase 2 진단 시 PM의 조치 판단

기존 문서가 있을 때 PM이 문서별로 조치를 판단하여 사용자에게 제안한다:

| 조치 | 조건 | 동작 |
|------|------|------|
| **보강** | 기존 문서 품질 OK, 누락/수정만 필요 | 기존 문서를 읽고 수정 사항 반영 (버전 업) |
| **재작성** | 기존 문서 구조가 표준과 크게 다름 | 기존 내용을 계승하여 표준 구조로 새로 작성 |
| **신규** | 해당 산출물이 없음 | 표준 구조로 새로 작성 |

- 재작성이더라도 **기존 내용을 버리지 않는다** — 내용을 최대한 살려 표준 구조에 재구성
- PM이 **diagnosis.json**으로 구조화된 진단 결과를 생성 → 사용자가 확인/조정
- diagnosis.json의 배열을 순회하며 Phase 3 워커 디스패치, Phase 4 검증 수행
