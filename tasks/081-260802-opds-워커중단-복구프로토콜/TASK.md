# TASK: 워커 중단 복구 프로토콜 + 디스패치 산출량 상한 + 증분 저장 규율 SSOT화

> 입력: 사용자 요청
> 출력: TASK.md

## 작업 목표

078·080 두 태스크에서 반복된 워커 인프라 실패(연결 종료·스톨)의 완화책을 PM 즉흥 대응이 아닌 하네스 SSOT 규칙으로 승격하여, 다음 PM이 규칙만으로 동일 대응을 재현할 수 있게 한다.

## 배경

078에서 워커 인프라 실패 3연속(API 연결 종료 ×2, 600초 스톨 ×1)이 발생했고, PM이 대응 조합(배치 4분할 + 전체 파일 통독 금지 + 함수 단위 저장)을 도출해 이후 전량 성공했다 (→ D-6 §운영 교훈). 079는 같은 조합을 워커 프롬프트에 선제 적용하여 인프라 실패 0건을 기록했다 (→ D-7:108).

그러나 이 조합은 **어느 SSOT에도 기재되지 않고 PM 세션 프롬프트에만 존재했다.** 080 세션에서 재적용이 누락되자 동일 실패가 5회 재발했다. 즉 문제는 완화책의 부재가 아니라 **완화책의 SSOT 미등재**다.

## 배경 분석 (대화에서 도출)

### 1. 080 세션 실패 실측 (5회, 2유형)

| 유형 | 횟수 | 증상 | 산출물 |
|------|------|------|--------|
| stream watchdog stall | 2 | 600초 무진전 | PLAN 워커 = 보존 / Step 2 워커 = 0건 |
| connection closed mid-response | 3 | 응답 도중 연결 종료 | 매회 부분 보존 |

- 실패한 디스패치는 전부 대형이었다 — Step 2는 10파일 × 67 TS 단일 디스패치, PLAN은 2,000줄 편집.
- 2~3파일로 분할한 배치(A: 2파일, B1/B2: 3+2파일)는 전부 완주했다.
- 재개(SendMessage) 3회는 모두 같은 지점에서 재실패했고, 새 컨텍스트 전환 후에야 진행됐다.

### 2. 선례 대조 (078·079)

| 태스크 | 인프라 실패 | 적용 완화책 | 결과 |
|--------|-----------|-----------|------|
| 078 | 3연속(종료 2·스톨 1) | 배치 4분할 + 전체 파일 통독 금지 + 함수 단위 저장 (+ 모델 하향) | 이후 전량 성공 (→ D-6:125) |
| 079 | 0건 | 078 조합을 워커 프롬프트에 선제 적용 | 인프라 실패 0건 (→ D-7:108) |
| 080 | 5회 | 미적용(PM 세션 프롬프트에만 존재, 재적용 누락) | 재발 |

- 관련 개선 후보 메모리 2건이 `candidate` 상태로 미졸업 상태다 — "워커 보고는 실측 대조 없이 신뢰 불가"(2026-07-29), "078 워커 실패 완화책이 079에서 인프라 실패 0건으로 재현됨"(2026-07-30) (→ D-8).
- 두 메모리는 각각 본 태스크의 R-1(실측 판정)·R-2/R-3(분할·증분 저장)에 대응한다.

### 3. 현행 SSOT 공백 실측

| 항목 | 현행 상태 | 판정 |
|------|----------|------|

| 증분 저장 규율 | `op-dev-execute` Step 4는 체크리스트 실시간 갱신만 규정, 산출물 저장 시점 규율 없음 (→ D-5:92-95) | 부재 |

### 4. 앵커 교정 근거 (초안 제안 대비 변경점)

- `parallel-execution.md`의 Lazy 트리거는 "병렬 디스패치 시"다 (→ D-1 §7). 080에서 실패한 Step 2는 **단일 디스패치**였으므로 이 문서에 규칙을 두면 로드되지 않는다.
- 배치 구성이 실제로 일어나는 지점은 `dispatch-process.md` Step 6 실행 라우팅이다 (→ D-4:145-152).
- `observability.md`는 행위 주체 선언 문서이므로 증분 저장 규율의 앵커로 부적합하다.
- 산출물 0건을 낸 워커는 PLAN 워커였으므로, `op-dev-execute`에만 규칙을 두면 재발한다 → 전 워커 공통 주입 지점인 `dispatch-process.md` 워커 컨텍스트 주입 템플릿 §핵심 제약이 SSOT여야 한다 (→ D-4:81-99).
