# PLAN: 워크트리 태스크 캡슐 소유권 — 생성 순서 전환과 monorepo 파일럿

> 입력: [TASK.md](TASK.md), [ANALYSIS.md](ANALYSIS.md)

## Approach

전환을 네 층으로 나눈다. **① 계약 정정**(`harness/worktree.md`·`harness/task-process.md`·`pm/dispatch-process.md`), **② 스위치**(`.opal/worktree.json`의 `taskCapsuleCone`), **③ 차단 해소**(`_assert_task_path_unambiguous`의 상태 의존 해석), **④ 수명주기 배선**(`opal-pilot-dev` CLOSE 스텝 5)을 P1에서 동시에 넣고, 배포·회귀(P2) → Git fixture 실증(P3) → 실태스크 파일럿(P4) 순으로 닫는다.

설계의 축은 ANALYSIS가 실측한 **경로 B 수명주기**다 — `finalize`(워크트리, merge 전) → 캡슐 커밋 → merge → `finalize-attribution`(허브) → `status --set done` → `remove`. 제안서 §6.3이 규정한 "merge 확인 → finalize" 순서는 현행 도구로 실행 불가능하고(ANALYSIS Q5·Q6), 그 불가능성의 원인인 가드를 **없애지 않고 상태 인지를 더해**(D-1) 단일 복사본 불변식(C-9)을 보존한 채 merge 후 `status` 재진입을 연다.

범위 밖: `.opal-task.lock` 구현, Phase 3 전 파이프라인 확산, Phase 4 multi-repo. `--wt`를 쓰지 않는 실행 경로에는 코드·문서 어느 쪽에도 새 분기를 넣지 않는다(C-1).

코드맵 확인: `code-scan search worktree` → 13건(`worktree_tool.py`·`state_tool.py`·`memory_tool.py`·`brain_tool.py`·`code-scan.js`·`dashboard/backend` router 2건·테스트 5건). 변경 대상은 이 중 `worktree_tool.py` 1건이며 나머지 `depends` 소비자는 회귀 경계다 — `state_tool.py`·`memory_tool.py`·`brain_tool.py`는 계약 소비자로서 무변경이고, Console router 2건은 registry `task_path` 발급값을 읽으므로 D-1 해석 변경의 관측면이다.

ANALYSIS Q6 실측이 경로 A의 finalize 차단·경로 B의 전 구간 통과를 이미 갈랐다. |

  데이터 루트를 고정하지 않으면 출력 차이가 코드 변경 탓인지 데이터 탓인지 판정할 수 없다(brain `byte-identical-proof-requires-data-root-fixed`). ③ 실제 연동 — W-9 fixture 9항목과 W-10 실태스크 완주.
- **실측 경계**: cone 활성화 후 실 허브 규모(`.opal` 추적 357 + `tasks` 1143 ≈ 1500 파일)에서 `worktree-tool create` 소요시간과 워크트리 디스크 증가를 W-9에서 1회 측정해 기록한다. ANALYSIS 미측정 항목이며 목표치는 두지 않고 관측값만 남긴다.
- **실패 시**: P1~P3은 배포 전이므로 `git restore`로 소스만 되돌리면 복구가 끝난다(격리 HOME은 삭제, `/private/tmp` fixture는 폐기). P4 실 배포 후 파일럿이 실패하면 — 파일럿 태스크만 허브 비워크트리로 명시 fallback하고(`--wt` 없이 재생성), 생성 중이던 워크트리는 `worktree-tool remove`로 회수하며 폴더를 두 위치에 남기지 않는다(C-3). `.opal/worktree.json`의 `taskCapsuleCone` 키 제거만으로 cone 스위치를 즉시 끌 수 있고(기본 `[]` 전개는 no-op), 그 상태에서 기존 워크트리·비워크트리 동작은 전환 전과 동일하다. 도구 롤백이 필요하면 `main` 소스에서 `scripts/install-mac.sh`를 재실행한다.
