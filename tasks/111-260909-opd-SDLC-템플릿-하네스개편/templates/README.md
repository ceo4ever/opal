# SDLC 문서·수행 기준 개편 초안

> 2026-09-09 | 태스크 111의 입력 제안. 실제 작업 범위는 [상위 TASK](../TASK.md)가 소유한다.

네 문서의 정보 소유권과 수행 종료 조건을 함께 바꾼다. 이 폴더는 제안 산출물이며 기존 스킬·검사기·설치본에 아직 적용되지 않는다. 실제 2시간 달성 여부는 측정 전이다.

신규 문서는 파일 첫 YAML frontmatter에 `template: sdlc-v2`를 명시한다. 신규 형식은 이 값으로만 판별하고, 절 이름을 추측해 판별하지 않는다. 단계·승인·재시도·대기·PASS/FAIL/BLOCKED 같은 상태는 `state.json`만 소유하며 문서 본문에 복제하지 않는다.

`STATE.md`는 사람이 보는 저널·렌더 결과로만 사용한다. `TASK.md`, `ANALYSIS.md`, `PLAN.md`, `TEST-SCENARIO.md`는 안정적인 의도·사실·계약·검증 기준을 담고, 시나리오별 결과·증거는 `test-scenario.json`, 최종 요약은 DONE 기록에 남긴다.

## 검토 순서

1. [TASK](TASK.md): 문제·결과·범위·제약·완료 기준.
2. [ANALYSIS](ANALYSIS.md): 필요한 사실·근거·영향 경계.
3. [PLAN](PLAN.md): 변경 계약·실행 작업·위험·적용 순서.
4. [TEST-SCENARIO](TEST-SCENARIO.md): 판정 가능한 검증 기준·실행 계약.
5. [MAMS 178 대입본과 검토 결과](MAMS-178-REVIEW.md): 동일 사례로 네 문서의 연결 확인.

## 작성 기준

| 기준 | 적용 방법 |
|---|---|
| 한 정보의 원본은 한 곳 | 목표·범위·AC·제약은 TASK, 관측 사실은 ANALYSIS, 설계 계약·W·H는 PLAN, 시나리오·예상 판정 기준은 TEST-SCENARIO가 소유한다 |
| 참조와 중복을 구별 | AC/C/H 식별자 연결은 유지한다. 다른 문서의 문장·표를 복사하지 않는다. 계약 이해에 필요한 짧은 설명은 허용한다 |
| 빈 항목 생성 금지 | 해당 없는 선택 절은 제목과 함께 생략한다. '해당 없음' 표·빈 데이터 표를 만들지 않는다. 미확인 필수 정보는 생략하지 않고 질문 또는 차단 사항으로 표시한다 |
| 현재 유효한 내용만 유지 | 설계 변경 시 해당 본문과 연결을 교체한다. 폐기안·override 우선순위를 실행 본문에 누적하지 않는다. 변경 이유는 기존 결정 기록·git에서 추적한다 |
| 완료 기준은 결과로 | 일반 기능은 사용자·운영 결과로 판정한다. 파일·표·컬럼 존재는 그것 자체가 요구사항일 때만 완료 기준으로 삼는다 |
| 필요한 상세 보존 | API·데이터·상태 전이·실패 처리·회복 계약이 바뀌면 구현할 수 있는 수준으로 명시한다. 짧게 쓰려고 모호한 '기존 방식대로'로 대체하지 않는다 |
| 단계 밖 일 확장 금지 | 관련 없는 개선은 현재 작업에 자동 편입하지 않는다. 요청 결과에 필수인 누락은 영향·근거를 제시해 범위를 갱신한다 |
| 기준과 결과를 구별 | 기대 결과는 검증 전에 정한다. 결과에 맞춰 바꾸지 않는다. 잘못된 기준의 정정은 근거·결정 주체·영향받는 검증을 기록한다 |

초기 작성 목표는 TASK 한 화면, ANALYSIS 질문 중심, PLAN 결정·작업 중심이다. 줄 수를 통과 기준으로 삼지 않는다. 복잡도가 크면 상세를 숨기는 대신 독립 완료 가능한 범위로 나눌 수 있는지 판단한다.

새 식별자는 문서 내 추적용이다. 기존 태스크를 소급 재번호하지 않는다. 신규 형식에서는 AC(요구 결과), C(제약), W(작업), H(위험), S(검증)만 기본 사용한다. F 계층은 별도 기능 그룹이 실제 디스패치·독립 완료 단위일 때만 사용한다.

## 스킬별 수행 계약

| 스킬 | 입력 | 수행 | 종료 조건 |
|---|---|---|---|
| op-task | 요청·사용자 결정·이미 확보한 근거 | 문제·결과·범위·AC를 정리하고 범위·성공 기준을 바꾸는 질문만 인터뷰한다. 구현 파일 확정과 기술 스택 전수 조사는 넘긴다 | 목표·범위·제약·성공 기준이 명확하고, 열린 질문의 결정 주체·필요 시점이 정해짐. 미결 정책을 기술 선택으로 위임하지 않음 |
| op-dev-analysis | TASK + 관련 코드·문서·유효 증거 | 미확인 질문에 답하고 변경·회귀 경계를 찾는다. 외부 연동의 핵심 가정은 최소 프로브로 확인한다 | 설계에 필요한 질문에 답했거나, 미확인과 차단 영향을 명시함. 관련 없는 전체 구조 설명은 생성하지 않음 |
| op-dev-plan | TASK·ANALYSIS | 구현 계약·파일·담당·의존·병렬 실행 그룹·위험을 결정한다. 변경된 사실이나 모순이 없으면 분석을 재수행하지 않는다 | 모든 AC가 작업으로 연결되고, 각 작업의 대상·변경·배타적 소유권·선행 조건·실행 그룹이 명확함. 같은 그룹의 파일 충돌이 없고 차단된 작업은 확정 처리하지 않음 |
| op-dev-test-scenario | TASK에서 도출한 목표 검증 + PLAN의 위험 | 목표·부정·경계·회귀·실제 연동을 검증하는 최소 충분 집합을 작성한다. PLAN과 다른 작성자·독립 평가를 유지한다 | AC/C/H 커버, 실행 가능성, 실제 연동의 한계, RED 작성 담당·선행 순서가 확인됨 |

인터뷰는 한 번에 하나씩 한다. 대표 사용 상황을 대입해 설계를 뒤집을 정책부터 확인한다. 예: '14일 보정 배치에서 동일 인증 오류가 나면 알림은 몇 건이어야 하는가?' 이미 답한 질문은 다시 묻지 않는다.

ANALYSIS에 답할 질문이 없으면 기존 유효 근거와 추가 조사 불요 이유만 남긴다. 근거의 코드·환경이 바뀌었거나 모순이 발견되면 해당 부분만 재확인한다. 근거를 무조건 신뢰하거나 무조건 재조사하는 두 방식 모두 피한다.

프로브는 승인된 환경·권한 범위에서 수행한다. 실제 발신·데이터 변경·사용자 세션 조작을 읽기 검증으로 취급하지 않는다. 불가능하면 확인했다고 쓰지 않고 구현 첫 검증으로 배치한다.

## PLAN과 테스트의 연결

- PLAN은 테스트 전문과 기능-QA 표를 만들지 않는다. W→AC/C와 위험 H만 제공한다.
- TEST-SCENARIO가 S→AC/C/H 연결과 실행 계약을 소유한다. 커버리지 표가 필요하면 이 연결에서 도구가 산출한다. 사람이 별도 표를 다시 관리하지 않는다.
- 단계·승인 상태는 `state.json`, 시나리오별 PASS/FAIL/BLOCKED와 실행 증거는 `test-scenario.json`이 소유한다. TEST-SCENARIO는 실행 전 기준 문서로 유지한다.
- RED 대상은 테스트 작성·RED 확인이 대상 구현보다 먼저 실행되도록 디스패치 의존성에 반영한다. 시나리오 문서의 RED 표기만으로 충족하지 않는다.
- unit 대역은 실패 분기를 재현하는 용도로 허용하는 제안이다. 대역의 성공을 실제 API·DB·배포 검증의 증거로 사용하지 않는다. 현행 mock 금지 규칙과의 정합 작업이 필요하다.
- 테스트 실행 명령은 구현 전 준비할 수 있으면 채운다. 새 코드 때문에 확정할 수 없으면 담당·해결 시점을 지정하고 TEST 진입 전 확정한다. RED 대상은 구현 전 확정·실행한다.
- 구현 워커와 최종 검증자는 분리한다. 동일 코드·환경·명령의 유효한 검사 증거는 재사용할 수 있으나 최종 검증자가 유효성을 판단하고, 통합 결과·위험한 경로는 독립 실행한다.
- 코드·환경·의존성 변경, 실패 수정, 증거 누락이 있으면 해당 검사와 필요한 회귀를 재실행한다. SKIP과 BLOCKED 상태는 `state.json`에서 PASS와 구분한다.

## 실제 반영 시 함께 바꿀 것

| 현행 결합 | 개편 필요 사항 |
|---|---|
| op-task 템플릿·task-guide·명확화 표 파서 | 새 TASK 절에서 동일한 4요소를 확인하도록 소비 계약 변경. 구형 태스크 지원 여부를 명시하고 버전별 해석을 검증 |
| ANALYSIS 템플릿·analysis-core·PLAN 입력 규약 | 파일 맵·Handoff 소유권 일치, 새 절에 맞는 pipeline gate checklist |
| PLAN §4.2·F/R/H 참조·워커 디스패치 | Work items를 읽는 실행 계약, 필요한 역할·파일·의존성 보존. 단순 제목 치환만으로 처리하지 않음 |
| op-scenario-gate·scenario-coverage-check | AC/C/H와 시나리오 연결을 기존 정규화 입력에 매핑. 작성자와 평가자 분리·목표 검증 유지 |
| RED-first·테스트 에이전트 | 시나리오와 실행 순서의 일치, 대역/실연동 경계, 증거 재사용 조건을 일관되게 반영 |
| pilot pipeline.json·PM Gate | 제거된 표를 보강하라고 요구하지 않도록 검사 항목 변경. 실제 완료 조건은 보존 |
| 상태·관측 도구 | 초기 실행과 재작업·사용자 대기·외부 대기를 구별. 기존 stage timestamp를 순수 작업시간으로 오해하지 않음 |

위 목록은 반영 범위 후보이며 이번 초안에서 기존 파일을 수정하거나 배포하지 않는다.

## 성능·품질 검증안

2시간의 시작·종료점과 대기시간 포함 여부는 사용자 답변 대기다. 측정 시 원래 범위의 검증 완료와 후속 범위 추가를 모두 기록하고, 후속 작업을 제외한 수치만 제시하지 않는다.

1. 난이도·영역·외부 연동이 유사한 MAMS 태스크를 고른다. 모델·도구·코드 상태 차이를 기록한다.
2. 동일한 승인 범위에서 새 형식으로 실제 개발한다. 이번 회고적 재구성의 작성시간을 개발시간 단축으로 계산하지 않는다.
3. 전체 경과시간, 대기 제외시간, 단계별 작성·검토·실행시간, 재작업 원인, 사용자 추가 질문을 측정한다. 병렬 워커 분을 합쳐 벽시계 시간으로 보고하지 않는다.
4. 목표 미검증·필수 위험 누락·완료 후 결함·사용자 판정 어려움이 늘지 않았는지 확인한다.
5. 대표 작업 여러 건의 분포와 120분 초과 사례를 함께 보고한다. 큰 작업을 임의 종료하거나 검증을 생략해 목표를 맞추지 않는다.
